# Handover

Use [automatic preparation and resource binding](../../internal/releases/REFERENCE.md#skill-activation) before this skill. Claude native session marker: `${CLAUDE_SESSION_ID}`.

Read [the shared operating brief](../../internal/workflow.md) and [the runtime interface](../../internal/runtime/REFERENCE.md). Carry the authorized work through implementation, independent assurance, verification, documentation, retrospective and follow-up triage. Autonomy comes first, independent quality second, efficiency third, within user limits.

Establish the agreed commitments, authority, dependencies, actual state and valid evidence. Preserve existing agreement and completed work; do not replay confirmation because the session compacted or a compatible spec correction landed. Accept the handover only when every queued item already has the investigated readback or concise-spec agreement described in the brief. If any item lacks it, present the outstanding readback or decisions now and settle them in this interactive exchange; accept a renewed handover only after that settlement is confirmed, never by asking the user to hand over first and settle afterwards. Before the user leaves, settle known user-owned decisions and verify essential execution, review and continuation capabilities.

Create or reconcile the durable finite queue before implementation. Verify continuation on this host first. With it verified, create a new run in unattended mode, or hand a run already underway over with the runtime `handover` operation, carrying the user's handover words as its authority and the mechanism you just verified. When continuation cannot be verified, send `handover` without a mechanism, creating a new run attended first: the handover and its report obligation are saved and the run stays attended, whereas a run created unattended refuses all work until continuation is verified. Never recreate a run to change its mode, and do not ask for another readback of settled work. Read the returned status for the actual outcome. If the operation is refused because a runtime dispatch is still running, tell the user the handover will be recorded when that assessment finishes, await it with `wait`, and retry.

Acknowledge only after the operation has returned. Say plainly that the handover is accepted and the user can leave, restate the accepted work and the limits in force in a sentence or two, say whether the run is operating unattended, and say that a morning report will be waiting in this session. Mention publication only to restate authority already granted. If a decision, a readback or runtime admission is outstanding, name it and its concrete recovery (for refused admission: approve the hook trust, or reopen the session) and do not claim acceptance; the work stays interactive until then. If the handover was recorded but the run stayed attended, name the prerequisite that failed and what it means: with the native goal verified and only Stop-hook behavior unverified, the goal carries the queue without protection against a premature yield; with the native goal itself unverified, nothing carries the queue while the user is away and work proceeds only while this session stays active. Let the user decide whether to leave.

Set the native persistent goal to continue through the agreed lifecycle until verified completion, an explicit stop/limit, or no remaining actionable authorized work or recovery. Verify native continuation and bundled hook readiness on the actual host. After yields and compaction, reconcile state, files and surviving workers before dependent actions. Await a background dispatch with the runtime `wait` operation inside the turn, repeating it on timeout. Short of verified completion, an explicit stop or exhausted limit, or a blocked run's recorded session closing, end the turn only when every remaining item waits on a user decision and no worker is active, which the Stop hook permits as a pause before session closing. Use status at consequential boundaries, preserve write ownership, and work through recoverable failures instead of ending the run.

Implement directly with a strong model. Use bounded helpers and optional lower-tier supervision where authorized and useful; keep consequential judgment and acceptance. Prefer equivalent-strength review on the other host when suitable, with fresh same-host review valid. A routine plan is not part of this lifecycle.

Every finding needs fresh skeptic validation; every repair needs relevant checks and cumulative strong broad review. Continue independent tasks when an item is blocked. Finish with documentation and backlog, then retrospective, then the morning report, then the existing one-at-a-time follow-up triage, as the brief's Close and report section describes. The report stands on its own for a reader who saw nothing of the run, optional follow-up decisions never delay it, and it ends with the first pending follow-up as a host question. Preserve unanswered follow-ups when the user is unavailable, and record the report's delivery only from the user's actual reply. Local commits follow policy; publication requires authority and the applicable review gate. Report incomplete obligations explicitly.
