# handover

## Scope

Triggered by `/nightshift:handover`, "hand over", "handover", "take over from here", or close conversational variants. The trigger is the user's. Handover is never self-invoked: a work pick from `/nightshift:ready`, a completed agreement, or a lifecycle entry reached through another skill does not start it, because the unattended rule's deferrals only make sense when the user has actually left. Agreed work without a handover trigger runs the same lifecycle attended: every checkpoint the unattended rule would defer is asked inline as it arises, nothing accumulates for a morning report, and the user may hand over at any step, from which this skill takes the rest. Handover is the autonomous portion of a feature's lifecycle: it detects where the feature currently stands (shift-start below), states the read (confirming with the user only when the detection is not clean), then drives the remaining steps through to shipped. If the late-stage tail (steps 5-12) already ran in this session, handover is a no-op.

Build a single flat step queue from the detected entry step onward before starting work, maintained in a scratch file (`.tmp/handover-queue.md` in the project root) rather than a host task tool or conversation memory: long runs cross context-compaction boundaries and outlive the session that started them. The queue is a closed protocol owned by the bundled `handover-queue.js` controller, never free-form progress authority. Its first line is protocol-version-2 canonical JSON in the exact field order `artifactPath`, `entryStep`, `implementationAuditBase`, `planFingerprint`, `protocolVersion`, and `targetScope`: `artifactPath` and `targetScope` follow the existing authority grammars, `entryStep` is the original supported integer, implementationAuditBase is either `null` or one full lowercase Git object ID of 40 or 64 hexadecimal characters, `planFingerprint` is `none` or `sha256:<64 lowercase hexadecimal characters>`, and `protocolVersion` is the integer `2`. `resumeQueue` migrates a canonical version-1 queue by inserting the null field while preserving its authority, inventory, frontier, and tail; the caller must atomically replace and verify the returned canonical bytes before continuing. During Git implementation, `bindImplementationAuditBase` accepts the current authority, queue evidence, a full ID, and the canonical source buffer and returns exactly `{ complete, nextStep, sourceBuffer }`: null binds once, the identical binding is idempotent, and a different stored value fails without replacement. The caller uses only the returned `sourceBuffer` to atomically replace and verify the queue while retaining the resolver-supplied full ID as the audit authority. Non-Git work leaves the field null. `advanceQueue` preserves the field, while every canonical restart and dead-state replacement resets it to null so an old repository boundary cannot cross runs. Beneath that header the queue carries the exact ordered procedure inventory from the original entry step through step 12; every queued step is exactly one line of the form `- [ ] <step number>. <step name>`, and `- [x]` is the sole completion mark. Before adoption and before every update, require `.tmp/handover-queue.md` to be a repository-local ordinary single-link file that is ignored and untracked, capture it through a stable two-read identity check, and pass those facts to `resumeQueue` or `advanceQueue`. A symbolic link, hard link, tracked or unignored path, read drift, authority mismatch, malformed header, missing, extra, duplicate, renamed, reordered, or non-frontier step contributes no completion marks and fails closed for an explicit discard-and-restart ruling. The controller treats the ladder as the latest safe resume bound: a queue may resume earlier than or at the detected ladder step, never later; a later queue frontier produces a canonical restart at the ladder step. Mark each step through `advanceQueue` as its sub-skill completes, supplying the retained authority as `currentAuthority` and the current artifact and plan identity as `nextAuthority`; this refreshes the header when plan creation or mutation changes the fingerprint. Immediately before replacement, repeat the stable capture and require the same bytes and identity, then atomically replace the complete queue and verify the readback. Re-marking an already-marked step after a crash is a successful idempotent write only after the durable result of that step is re-established. Create the queue after the confirm line, never before the agreement and validation steps complete; an absent file is the ordinary fresh-run case. Step 10 is a pointer rather than independently completed work: after steps through 9, step 11 is the next actionable step, and completing step 12 marks steps 10 and 12 together only once the whole tail (persistence, completion stamp, plan-removal offer) has completed. Delete the completed queue immediately afterward, alongside the follow-up items file. A session that dies mid-tail leaves steps 10 and 12 unmarked, so the next session re-runs the tail. A host that offers a native task list may mirror the validated queue into it; the scratch file stays the authority only within these bounds.

The validated flat handover queue is the procedure's sole normal stop authority within the ladder bound. A nested skill's terminal integration, branch-finishing, or other end-of-skill prompt is a deferred checkpoint, not permission to stop or bypass later queued steps; continue pulling until every canonical step in the handover queue is marked completed unless this skill's explicit halt conditions apply.

Accumulate user-decision-required items (`/nightshift:revise-spec` and `/nightshift:revise-plan` findings deferred for later, implementation-phase questions and out-of-scope findings, `/nightshift:revise-code` tech-debt findings) into a single "follow-up items" list maintained in a scratch file (`.tmp/handover-followups.md` in the project root), not conversation memory: long runs cross context-compaction boundaries, and the scratch file is the authoritative copy the morning report (step 12) reads and presents. Open it with a header line naming the spec and target scope so a leftover is attributable. Beneath that header, every item is exactly one canonical JSON line with this shape: `{"source":"<artifact type and identity>","sourceItemId":"<stable semantic ID>","text":"<exact item text>","proposedRoute":"<route>"}`. Every producer mints a stable semantic `sourceItemId` independent of list position, and the pair `(source, sourceItemId)` is unique. To add an item, write the complete next contents and atomically replace the scratch file. Revise transfers use the stable follow-up ID as `sourceItemId`; an existing matching pair is a successful idempotent handoff, not a duplicate or failure. The morning report decodes each JSON entry and retains its source identity when presenting it. At shift-start, a leftover copy from another artifact or an already-completed run is dead state: overwrite it without mining it; a live copy from an interrupted run on the same artifact and target scope is the resume case and keeps accumulating. Delete it only after step 12's whole tail (persistence, completion stamp, plan-removal offer) completes, so a session that dies mid-tail can re-run the tail from it.

**The unattended rule.** Handover exists so the user can walk away. Review checkpoints, whether a sub-skill's or handover's own (spec or plan review after a revise loop, the plan artifact's Spec Reconciliation per-edit approvals, follow-up triage, end-of-loop asks), are therefore deferred to the morning report rather than pausing the run mid-pipeline. Deferral, not waiver: each checkpoint becomes a follow-up item carrying what would have been asked, and the user answers it at the report in the checkpoint's own terms. Scope artifact-review checkpoints to artifacts that existed at shift start: a hardening delta is only reviewable against a baseline the user has seen, so for any artifact authored during the run (the plan when handover enters at the spec gate, and equally the code the run implements) the review pause collapses into the shipped-work summary -- report what the review run completed and changed, but do not pose the deltas as an approval question. The test is whether the review changed behavior that existed at shift start, not which artifact type it was: a fix that touches a pre-existing line without changing its behavior (a constant or helper extraction under the scout rule) does not resurrect the checkpoint, while a fix that alters pre-existing behavior does. A corollary: workflow-instruction files (nightshift plugin files, the user's global CLAUDE.md, memory files) are not edited mid-run, whether the impulse comes from `/nightshift:revise-lore` or from a revise loop's dimension or authoring retrospective (whose own "apply with the user's approval" instruction is one of the deferred asks, never an auto-pass); every candidate edit to them becomes a follow-up item (the concrete edit plus the session evidence motivating it), applied only after morning-report approval via the persistence mechanics in step 12. Applying instruction changes mid-run would skip the user's review of text that governs future runs and let a session-local workaround mask a defect in the instructions. The corollary is about lore, not target work: when the plugin repo itself is the project being handed over (self-hosting), its files are the implementation surface and the pipeline edits them normally. The run still stops at the shift-start confirm line where detection raises one (a clean detection proceeds on the stated read), for destructive, irreversible, or outward-facing actions, and when work is genuinely blocked on missing input. Exact equality, representation-only drift, and a validated `within-contract` refresh continue unattended without a response. Only a gate outcome that requires a fresh or renewed response blocks unattended continuation. Producing or changing the accepted decision surface remains the human's work, so an unavailable user on that response path stops the run without authority. The mode is declared, never inferred. A handover trigger puts the whole run in unattended mode, and it stays there however long the run takes and however often the user checks in: a check-in answers the question it answers (a response-path gate, a halt condition) and changes nothing else, so deferrals keep accumulating for the morning report. Only an explicit statement from the user that they are taking the work back ends unattended mode; from that point the run is attended, every deferred item is drained as an inline ask before continuing, and nothing further accumulates except mid-run captures (below). A run that has not been handed over is attended from the start and defers nothing but those captures.

**Mid-run captures.** A user capture that arrives while the lifecycle is in flight (an idea, a bug, a quick win, any thought not tied to the current work) is filed as a follow-up item in `.tmp/handover-followups.md` in both modes, never as an immediate backlog edit and commit: the capture survives the session, the pipeline is not interrupted, and the governing artifact is not edited under a running review. An unattended run presents it at the morning report like any other deferred item; an attended run presents it at the run's closing summary, since a capture is not a checkpoint and drains at the end rather than inline; this is the one deliberate exception to attended mode's nothing-accumulates standard. A check-in that only supplies a capture changes nothing else about the run's mode.

## Artifact locations and selection

Handover looks for specs and plans in the project's established locations; when a project has none, the standard project fallback is `.claude/specs/` for specs and `.claude/plans/` for plans. Inferred plan selection also considers the shared global fallback at `~/.claude/plans/`.

When multiple candidate files coexist (stale plans persist because removal is only offered, never forced), select the artifact for the feature under discussion using the same resolution order the revise skill's scope rules use: the artifact named or implied by the invocation and conversation context first. When context alone is insufficient, consider eligible candidates from the project-established plan location, the standard project fallback, and the shared global plan fallback, run the shared candidate-evidence procedure before modification time or content influences selection, and choose by captured content match and then captured modification time. Select only from that frozen evidence and retain the winning binding. A plan named or implied without candidate metadata or content proceeds directly through shared establishment after selection. The confirm line names the chosen file paths explicitly, so a wrong pick is visible before any work starts. Handover operates on one in-flight feature per invocation; coexisting artifacts are disambiguated here, not orchestrated in parallel.

Load `${CLAUDE_PLUGIN_ROOT}/internal/plan-binding.md` and `${CLAUDE_PLUGIN_ROOT}/internal/plan-binding.js` before any plan inference that uses candidate evidence, or immediately after a direct selection. Run the shared candidate-evidence procedure before modification time or content influences selection by calling `capturePlanCandidateEvidence`; call `establishPlanBinding` after a direct selection. The service solely owns plan classification, containment, link safety, repository Git policy, candidate evidence, binding refresh, and revalidation. Retain the resulting full binding for the rest of the lifecycle. Immediately before every authoritative use or plan-derived dispatch, call `revalidatePlanBinding` and consume the returned captured plan bytes directly for stage detection, hardening interpretation, planning context, task-brief derivation, and local mutation baselines. Never route plan authority through agreement CLI output or reopen the pathname between revalidation and use.

## Backlog entries count as specs

The spec role is filled by a dedicated spec file when one exists; otherwise by the backlog entry or entries whose text carries the design (a feature entry and its breakout file especially, but bug and quick-win entries too when their text is the design record). "Spec" throughout this skill means whichever artifact fills that role.

Stamp targets and completion recording follow the form. A spec file takes hardening stamps and the step-12 completion stamp as written. When the entry has a breakout file (`features/<slug>.md`, `bugs/<slug>.md`), that file is the stamp target: revise-spec hardening stamps and the step-12 completion stamp land there exactly as on a spec file, and the file's persistence after shipping makes the stamps durable. Index-only entries take no stamps: per-entry stamps inside a shared index defeat the file-scoped fingerprint and clutter the scannable backlog; their completion record is the walk-and-remove archive move (gone from the active index, present in the history archive), and their currency check is the agreement-entry validation below. At step 12, backlog-entry-specced work with no breakout file skips the stamp with a one-line note.

## Agreement and stage entry

**Target scope first.** Before walking the ladder, resolve which feature and which scope this handover takes over: from the invocation, then session context, then the spec's own phasing declaration (a phased spec names its feature phases and the sections each covers), and, when none of those establish it, by asking the user. A spec with no phasing declaration defaults to `whole file`, so the ask is reserved for genuinely phased or ambiguous cases. A feature phase is handover's conversational term for a stamp-comparable implementation scope; a revise review round or wave is an internal repeated-review unit and does not alter that target scope.

Follow this order before validation, review dispatch, queue creation, planning, or implementation:

1. Load `../spec-agreement/SKILL.md` relative to this skill and initialize its `lifecycle-entry` procedure with caller mode `handover`. Do not execute its candidate, presentation, response, or authority portion yet.

This gate re-runs repository-backed resolution before accepting the terminal result. Preserve the agreement resolver's exact unsliced-title and case-sensitive unique sliced-`displayName` rules. Ambiguous, stale, or incoherent archive evidence fails closed instead of authorizing work. For every nonterminal result, retain the resolved complete target and governing set for the following steps.

When it reports matches, use `previewLegacyMarkerDeletion`, render every exact reviewed deletion, and stop without applying it or dispatching work.

Fold the findings into the stated conclusion; validation findings are one of the signals that downgrade a clean detection into a confirm-first one. This flag is deliberately the mechanism's only resume-time detection: detection never re-enters probing on account of the markers themselves (a not-hardened spec still routes through step 1, probes included). The consult, when needed, is the entry-point action performed at shift start while the user is still present, before any unattended continuation proceeds.

Continue from the controller's returned actionable step. When the queue frontier is earlier than the ladder, re-run from that earlier queue step; when it is later, `resumeQueue` discards its marks and returns a canonical restart at the ladder step, so scratch state can never skip a lifecycle gate. Do not create or replace the queue before the agreement and validation steps above complete.

**Coverage** is containment plus currency: a stamp covers the target scope when its recorded scope contains it AND the artifact's in-scope content is unchanged since the stamp (the artifact-drift check below supplies the currency signal; drift that cannot be localized to sections counts as in-scope). Drift within the target scope defeats coverage outright, and the ladder treats the artifact as not hardened (or not completed) for that scope; this is a rung decision, not a soft flag, though the user's confirm-line answer still overrides.

Walk the ladder top-down and enter the procedure at the first rung whose condition holds. State the conclusion in one line, naming the chosen spec/plan paths, the target scope, agreement result, and any stamp or staleness details, for example: "Spec .claude/specs/foo.md agreed in this session and hardened for sections 3-5 (stamped 2026-07-04 09:41 at a1b2c3d), matching the target scope; no plan found; taking over from planning." When the detection is clean (the rung decided on solid evidence, artifact selection unambiguous, validation found no issues, and no staleness, drift, live-claim, queue-versus-ladder, or inconclusive-evidence flags are raised), proceed directly to building or resuming the step queue: the stated conclusion is the user's interrupt point, not a question. Two signals are non-flags, alone or together: a `(live-claim: provisional, awaiting <precondition>)` marker, whose clause is the artifact's own record that the provisional status is a designed outcome (a probe gated behind the named cutover or release precondition per the spec-gate rules), while a bare `(live-claim: provisional)` marker carries no such record and is not a non-flag, and a same-session mid-flight implementation resume (a hardened plan whose implementation is partially committed, resumed in the session that ran it). With only these present the detection stays clean and the run proceeds straight to building or resuming the step queue; the confirm is kept for real ambiguity, artifact-selection doubt, validation findings, drift, and a queue-versus-ladder disagreement. Any flag, ambiguity, or validation finding instead asks the user to confirm before work starts ("... Correct?"), and the user's answer always overrides inference about the stage; it never substitutes for agreement authority. References to "the confirm line" throughout this skill mean this stated conclusion; where a flag applies, it is posed as the question just described.

Throughout the ladder, "same-session evidence" means the event demonstrably happened earlier in the current conversation. Where evidence is inconclusive, the rung reads as not satisfied (a failed check is not a clean check), and the confirm line states which question could not be answered, in that rung's own terms.

1. **Late-stage tail already ran this session**: no-op; say so.
2. **Implementation complete**: the plan's tasks are committed. Commits are deliberately not labeled with plan-task numbers (plan hygiene forbids it), so the evidence is correspondence between plan-named files and commits since the plan's hardening stamp, or same-session evidence; inconclusive reads as not complete. A history rewrite breaks this evidence entirely (the stamp SHA is no longer an ancestor of HEAD); the confirm line must then say outright that handover cannot tell whether the implementation already landed, since the ladder would otherwise propose re-implementation at rung 3. If complete: enter at step 5 (the late-stage tail).
3. **Plan exists.** Hardened (stamp or same-session evidence): enter at step 4 (implementation). Not hardened: enter at step 3 (revise-plan).
4. **Current agreement exists and no plan exists.** Hardened for the target scope (coverage, per the definition above): enter at step 2 (planning). Not hardened: enter at step 1 (the spec gate). Currency is what makes the feature-phase rule work: a whole-file stamp from an earlier feature phase contains later sections by grammar, but sections added or edited after that stamp fail currency, which is exactly what mandates re-hardening for a later feature phase. Agreement remains governed by candidate reconstruction and contract fit, never by a durable stage label.

After any complete handover-controlled batch that can change a governing artifact, governing-set membership or order, target scope, or plan declarations, execute the agreement skill again in `post-mutation` phase with originating caller mode `handover` before another reviewer, planner, implementation step, verifier, or downstream transition. Exact equality, representation-only change, and a validated `within-contract` result refresh or retain volatile authority and continue immediately. Every outcome that requires a fresh or renewed response blocks without authority under the unattended rule.

## Provenance stamps

Completed spec and plan review runs append hardening stamps (see the post-loop steps in the revise skill's `spec.md` / `plan.md`). The persisted stamp token remains `graduated`; at step 12, handover writes a completion stamp only to a dedicated spec or backlog breakout artifact. All stamps live under a `## Hardening` section at the end of the artifact, created if absent:

```
- revise-spec graduated 2026-07-05 14:32 at a1b2c3d, scope: sections 3-5, content: 9f3a2b1c
- handover completed 2026-07-06 09:15 at e4f5a6b, scope: sections 3-5, content: 1c2d3e4f
```

- **Scope grammar**: `scope: whole file` for a whole-file pass, or `scope: sections <headings or ranges>` for a section-scoped pass. Plans are typically hardened whole-file. Rung comparisons are scope against scope, one grammar everywhere.
- **The SHA** is the repo HEAD commit at write time. The hardening edits themselves are uncommitted at stamp time, so a hardening stamp's SHA is the pre-hardening baseline; the artifact file itself is therefore always excluded from any SHA-based overlap diff (it would otherwise self-flag its own hardening edits), and edits to the artifact are instead owned by the fingerprint-based drift check below.
- **The fingerprint** is the short hash of the artifact's eligible design content, excluding only the terminal `## Hardening` provenance section. Use `selectArtifact` with `selectorKind: design-before-hardening`, pass that selection to `hashSelection`, and record the first eight hexadecimal characters of its `contentHash` until the portable fingerprint helper changes stamp production. The fingerprint, not any timestamp, is the drift signal: it is machine-independent and blind only to eligible provenance appends. Inline markers such as `(live-claim: ...)` are design content and DO move the fingerprint; see Post-stamp edits below. Timestamps in stamps serve the age check and latest-provenance ordering only.
- **Post-stamp edits**: when a sanctioned pipeline step edits a stamped artifact after its stamp (any live-claim marker rewrite, whichever step performs it: step 1's fold-back, an agreement-entry disposition the user requests, step 6's rewrite, a step-12 disposition; plus revise-plan's Spec Reconciliation), invoke `writeProvenanceStamp` through the shared agreement controller with the current complete-file baseline hash and the fresh stamp matching the scope of the graduated stamp it refreshes (one refreshed line per affected graduated stamp on phased specs), the current HEAD, and the new fingerprint, suffixed with the reason in parentheses, e.g. `- revise-spec refreshed 2026-08-02 17:20 at 1a2b3c4, scope: whole file, content: 9d8c7b6a (live-claim fold-back)`. The shared writer owns grammar validation, atomic replacement, readback, and applied-retry handling. The prefix names the artifact's hardening loop, whichever step performs the refresh. A `refreshed` line supplies the fingerprint for the drift check only: the age check and the content-overlap check continue to baseline on the most recent `graduated` stamp. It restores hardening coverage but never creates agreement authority. On an index-only backlog entry, which takes no stamps, skip the refresh with a one-line note.
- **Migration**: artifacts hardened before stamps existed carry none; detection treats them as not hardened and the confirm line is the correction point (self-healing: any future completed spec or plan review appends its stamp). A stamp that is present but lacks a `content:` fingerprint (hand-edited or malformed) is treated the same way for currency: not current, fail closed, surfaced in the confirm line.

## Staleness sanity check

When a detection rung rests on a stamp, sanity-check it before trusting it:

- **Age**: flag if the stamp is more than 48 hours old, baselining on the most recent `graduated` stamp (`refreshed` lines do not reset the clock, per Post-stamp edits). Hardening normally immediately precedes planning or implementation; anything older deserves a look. The number is a deliberate default guideline, not a gate.
- **Content overlap**: list files changed since the stamp commit (`git diff --name-only <sha>..HEAD`, excluding the artifact itself) and judge whether any are in the vicinity of the artifact's subject matter. A plan names its files explicitly; for a spec, infer the affected areas from the stamped scope. Unrelated churn passes silently. There is deliberately no commit-count threshold; relatedness is the signal, not volume.
- **Artifact drift**: compare the artifact's current content fingerprint against the most recent covering hardening or completion stamp. For section-scoped targets, true drift must additionally be localized: diff the artifact's current content against its content at the commit that introduced the stamp line (the post-hardening baseline; never baseline on the recorded time, which unavoidably predates the commit that carries it), and map the changed lines to sections. Drift within the target scope defeats coverage at the rung level; drift demonstrably elsewhere is a soft flag; drift that cannot be localized (untracked artifacts, unusable history) is treated as in-scope, fail closed, and the confirm line says so. This stamp check classifies lifecycle stage only. Candidate reconstruction and contract fit exclusively classify agreement currency.
- **Degraded mode**: the overlap diff is only meaningful when the stamp SHA is an ancestor of HEAD. After a rebase, squash, or on a machine that never had the commit, it is not; the overlap check is then inconclusive and reported as such, never silently treated as clean. The same ancestry break invalidates rung 2's implementation-completeness evidence; rung 2 owns how that surfaces.

The age flag, the overlap check, and out-of-scope drift are soft judgment calls, never hard gates; they surface in the confirm line together with the already-completed validity result and an offer: (a) full re-run of the scoped revise loop, (b) proceed as-is. The mandatory validation above is not repeated because no governing artifact or repository baseline changes between it and this decision. Neither choice creates or refreshes agreement authority.

## Version-control-optional artifacts

Specs and backlog files may be git-ignored by user election; the `.gitignore` is the election, checked per file (`git check-ignore`, tracked status). Plans are outside that election. The shared physical plan binding procedure owns every plan Git-policy check and repeats it at each required revalidation. Handover treats a reported plan-policy conflict as blocking before stamping, implementation, or deletion and asks the user to remediate it; when an ignore entry matches a still-tracked file, note once that untracking is incomplete and suggest `git rm --cached`. Never attempt to commit an ignored artifact. Git-based recency evidence applies only to tracked artifacts; untracked ones use file modification time as a selection tiebreak only.

## Triage during revise rounds

If a finding changes the implementation scope (what we're building, not how we describe it), block and ask: that's a brainstorm gap that needs resolving before code lands. This block survives the unattended rule as genuinely blocked work: halt the run rather than implementing all night past an unresolved design gap or silently deferring it. Polish-shaped findings (clarity, naming, missing context) go to the follow-up list and the loop continues.

## Procedure

1. **Spec gate.** `/nightshift:revise-spec` scoped to the target scope, run to completion under the skill's review rules.
