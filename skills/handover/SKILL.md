# Handover

Use [automatic preparation and resource binding](../../internal/releases/REFERENCE.md#skill-activation) before this skill. Claude native session marker: `${CLAUDE_SESSION_ID}`.

Read [the operating brief](../../internal/workflow.md) and [runtime interface](../../internal/runtime/REFERENCE.md). Handover is the sole entry creating a delivery run. Ordinary chat agreement proceeds directly; standalone revision uses a review context. Ready selection requests handover after investigation, and confirmation of its complete scope releases that request without another handover prompt. An explicit request for direct work or a pause takes precedence. Preserve confirmed commitments through compatible corrections and compaction; material changes require the user's decision.

Accept once every queued item has its readback or governing-spec agreement and applicable assessment resolved, with consequential decisions, limits and publication authority settled. Until then preserve the request and present what remains; do not claim acceptance. Check actual state, resources and surviving activity. An unfinished delivery is resumed or explicitly adopted under its ownership and inactivity rules, never replaced. Ownership transfer does not authorize resumption or enlarge scope.

Create accepted work through runtime `handover`, supplying the finite queue and a preserved UUID `handoverId` for safe retries. Record the user's actual authority. There is no attended/unattended mode. Attempt the host's continuation: the functioning registered Stop hook on Claude Code, a native persistent goal on Codex. Record observed success or technical failure with `continuation`; failure creates a follow-up and work continues without that mechanism. Leave disabled or untrusted hooks unchanged, never replace an unrelated or unfinished goal, and respect an explicit pause, stop or exhausted limit. Ownership uncertainty, invalid resources, denied permission for the requested operation and unavailable required assurance retain their own refusals.

After the runtime records the continuation outcome, emit a distinct visible acknowledgement paragraph as ordinary assistant text before engineering. Begin it `Handover accepted:`, state the confirmed scope and applicable limits, then say `You can leave.`. With functioning continuation, explain where the morning report will appear, respecting any requested hold. If continuation failed, include `Automatic continuation is unavailable`, state that the failure is recorded for follow-up, and explain that resumption is needed if the session stops before delivery. On Claude this is a normal assistant text content block, not intended narration in thinking or a tool result. A separate paragraph does not require ending the user turn. Keep this same tool-use turn active: after the text, call runtime `status` to inspect its `acceptanceCheckpoint` before requesting start-task, editing, verification or a commit. Follow `nextStep`: record the actual continuation outcome when awaiting it; emit real ordinary text and inspect again when missing; recover unavailable history with bounded diagnostics; request engineering only when the message is available. Never infer emission from intended narration or unchanged saved status. Inspection does not discharge the duty; the runtime independently observes and captures it with the first dependent transition. A saved flag, quoted example, future promise or later final report cannot substitute. Hold/stop remain available. Do not promise recovery from host exit or Windows restart. Unresolved acceptance or ownership remains pending handover.

Use a turn-ending acknowledgement only when verified continuation can continue work afterwards. Otherwise acknowledge in visible assistant output and carry on in the active turn. An interrupted acknowledgement can be repeated safely; read status before repeating acceptance or native side effects. A refusal while a dispatch owns the project is temporary: await it through runtime `wait`, reconcile and retry. A `report-delivery-pending` refusal means the project's latest delivery still owes its morning report: present that saved report to the user from its file, record `report-delivered` with their reply, then retry the handover.

Each new or resumed engineering turn needs a successful controller claim. Reconcile state, files, workers and continuation at resumption, adoption, compaction recovery, renewed handover and before a dependent yield. Failed continuation does not revoke handover or report duties. Preserve failures after recovery for triage. Retry on changed evidence or justified recovery without looping on an unchanged error. Technical inspection failure is unknown, not healthy or proof of termination.

Carry the full lifecycle through implementation, strong independent assessment, fresh skeptical validation, value/authority dispositions, relevant verification, cumulative repair closure and fresh final assessments. Respect explicit model requirements. Use [revise-code](../revise-code/SKILL.md), [revise-docs](../revise-docs/SKILL.md) and [revise-lore](../revise-lore/SKILL.md) in the existing run and record actual evidence. Continue independent authorized work when a task is blocked. Await running workers inside the turn; worker activity is not controller continuation.

An explicit hold uses `hold` to suspend engineering and continuation pressure, preserving work and reporting duties. Reconcile workers without pretending they terminated. Resume the same run only with the user's explicit authority. Completion, holds/stops, applicable limits and waiting solely on user decisions without active or uncertain workers end continuation eligibility. Do not generate turns for optional pending triage.

Finish documentation and its independent assessment, then retrospective, saved morning report and one-at-a-time follow-up triage. The final message is the complete report for someone who saw none of the work, including evidence limits, incomplete obligations and pending decisions. End with pending follow-ups and a plain question asking whether the user is ready to triage, or state that no decision is pending. Preserve unanswered follow-ups when the user is away. Record delivery only from the user's reply. Tracking edits after triage receive the closing docs assessment the brief requires.

Commit locally under project policy and confirm the branch and checkout. Publication requires separate recorded authority and current independent review. Do not widen authority, waive assurance, exceed limits or claim an omitted workflow ran.
