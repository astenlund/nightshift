# Handover

Use [automatic preparation and resource binding](../../internal/releases/REFERENCE.md#skill-activation) before this skill. Claude native session marker: `${CLAUDE_SESSION_ID}`.

Read [the shared operating brief](../../internal/workflow.md) and [the runtime interface](../../internal/runtime/REFERENCE.md). Carry the authorized work through implementation, independent assurance, verification, documentation, retrospective and follow-up triage. Autonomy comes first, independent quality second, efficiency third, within user limits.

Establish the agreed commitments, authority, dependencies, actual state and valid evidence. Preserve existing agreement and completed work; do not replay confirmation because the session compacted or a compatible spec correction landed. Accept the handover only when every queued item already has the investigated readback or concise-spec agreement described in the brief. If any item lacks it, present the outstanding readback or decisions now and settle them in this interactive exchange; accept a renewed handover only after that settlement is confirmed, never by asking the user to hand over first and settle afterwards. Before the user leaves, settle known user-owned decisions and verify essential execution, review and continuation capabilities.

Create or reconcile the durable finite queue before implementation. Every new or resumed controller turn needs a successful `claim-controller` before canonical engineering; successful `create` or `resume` supplies that turn's claim too. For another owner's run, follow the runtime's explicit adoption, inactivity and compatibility checks, reconcile workers while stopped, and resume only with authority to continue. Verify current continuation on this host: a native goal on Codex, the Stop hook on Claude Code, as the brief describes. With it verified, create a new run in unattended mode and record the mechanism just verified with `continuation`, or hand a run already underway over with `handover`, carrying the user's words and that mechanism. Then acknowledge the handover as the next paragraph describes, before resuming any work. If continuation is inactive or unknown and admission works, record `invalidate-continuation` with the observation, then record `handover` without a mechanism; create a new run attended first when necessary. This preserves the handover and report duties while work continues attended. Never recreate a run to change its mode, and do not ask for another readback of settled work. Read the returned status for the actual outcome. If the operation is refused because a runtime dispatch is still running, tell the user the handover will be recorded when that assessment finishes, await it with `wait`, and retry.

Acknowledge once the handover is in effect: when `handover` returns, or for a new run when `continuation` has recorded its mechanism after `create`, and before any further work. The user is waiting for this message before leaving, so it stands on its own and is never folded into a progress note or left in your reasoning. With verified unattended continuation on Claude Code, make it the final message of your turn, since a turn-ending message is the one the user reliably sees, and let the Stop hook resume the work. Otherwise, including on Codex, acknowledge and continue in the active turn. Restate the accepted work and limits in a sentence or two and say that a morning report will be waiting in the current owning session. With verified unattended continuation, work proceeds without the user: say plainly that the handover is accepted and the user can leave, for example "Handover accepted: I'll finish the agreed work. You can go; a morning report will be waiting here.", and keep run mode and continuation mechanism out of the acknowledgement. Mention publication only to restate authority already granted. If a decision, readback or runtime admission is outstanding, name it and its actual recovery and do not claim acceptance. Refused admission leaves saved state unchanged, including any earlier handover; do not claim a persisted downgrade or bypass admission. If the handover was recorded but continuation could not be verified, tell the user what they must do or expect: useful work proceeds in the active turn, a functioning Stop hook still resists premature yield, and the user performs any required native resumption. Let the user decide whether to leave.

Use the verified continuation mechanism to carry the agreed lifecycle until verified completion, an explicit stop/limit, or no remaining actionable authorized work or recovery. Observe it at renewed handover, adoption, resume, compaction recovery and before unattended yield: whether a goal is active, inactive or unknown, or whether the Stop hook is still registered, enabled, trusted and activated for this session. For a goal, use an authorized supported resume operation and read back its result, or name the required user action if none exists; never replace an unfinished goal to escape its state. Reconcile state, files and surviving workers, and where a goal carries the run, verify the actual registered hook behavior separately. Await background dispatches inside the turn with runtime `wait`, repeating on timeout. Short of verified completion, an explicit stop or exhausted limit, or a blocked run's recorded session closing, end the turn only when every remaining item waits on a user decision and no worker is active, or, on Claude Code, with the acknowledgement of a verified unattended handover. Preserve write ownership and recover failed workers within the agreed limits instead of yielding prematurely.

Implement directly with a strong model. Use bounded helpers and optional lower-tier supervision where authorized and useful; keep consequential judgment and acceptance. Prefer equivalent-strength review on the other host when suitable, with fresh same-host review valid. A routine plan is not part of this lifecycle.

Every finding needs fresh skeptic validation; every repair needs relevant checks and cumulative strong broad review. Continue independent tasks when an item is blocked. Finish with documentation and backlog, then retrospective, then the morning report, then the existing one-at-a-time follow-up triage, as the brief's Close and report section describes. The report stands on its own for a reader who saw nothing of the run, optional follow-up decisions never delay it, and it ends with the first pending follow-up as a plain-text question. Your final message is that full report, never a summary of it or a pointer to where it was saved, including when the run closes blocked. Present each later follow-up as a host question through the host's question tool, as the brief describes. Preserve unanswered follow-ups when the user is unavailable, and record the report's delivery only from the user's actual reply. Local commits follow policy; publication requires authority and the applicable review gate. Report incomplete obligations explicitly.
