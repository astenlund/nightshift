# handover

## Scope

Triggered by `/nightshift:handover`, "hand over", "handover", "take over from here", or close conversational variants. The trigger is the user's. Handover is never self-invoked: a work pick from `/nightshift:ready`, a completed agreement, or a lifecycle entry reached through another skill does not start it, because the unattended rule's deferrals only make sense when the user has actually left. Agreed work without a handover trigger runs the same lifecycle attended: every checkpoint the unattended rule would defer is asked inline as it arises, nothing accumulates for a morning report, and the user may hand over at any step, from which this skill takes the rest. Handover is the autonomous portion of a feature's lifecycle: it detects where the feature currently stands (shift-start below), states the read (confirming with the user only when the detection is not clean), then drives the remaining steps through to shipped. If the late-stage tail (steps 5-12) already ran in this session, handover is a no-op.

Build a single flat step queue from the detected entry step onward before starting work, maintained in a scratch file (`.tmp/handover-queue.md` in the project root) rather than a host task tool or conversation memory: long runs cross context-compaction boundaries and outlive the session that started them, so a resumed run reads its position from the file instead of re-deriving it. Open it with a header line naming the spec and target scope so a leftover is attributable. Beneath that header, every queued step is exactly one line of the form `- [ ] <step number>. <step name>`, and `- [x]` is the sole completion mark. The shape is pinned rather than left to each session's convention because a resuming session, possibly on another host, must recognize marks it did not write. Mark each step completed as its sub-skill completes; to update the queue, write the complete next contents and atomically replace the scratch file. Re-marking an already-marked step is a successful idempotent write, not a duplicate or a failure, so a crash between a sub-skill completing and the queue write costs at most one redone step. Create it after the confirm line, never before the agreement and validation steps complete. At shift-start, an absent file is the ordinary fresh-run case; a leftover copy from another artifact, or from an already-completed run (every step marked), is dead state: overwrite it without mining it; a live copy from an interrupted run on the same artifact and target scope is the resume case, and its unmarked steps are the remaining work. Mark step 12 completed only once its whole tail (persistence, completion stamp, plan-removal offer) has completed, then delete the queue immediately after, alongside the follow-up items file. A session that dies mid-tail therefore leaves step 12 unmarked, so the queue reads as live rather than dead and the next session re-runs the tail from it. A host that offers a native task list may mirror the queue into it; the scratch file stays the authority either way.

The flat handover queue is the procedure's sole normal stop authority. A nested skill's terminal integration, branch-finishing, or other end-of-skill prompt is a deferred checkpoint, not permission to stop or bypass later queued steps; continue pulling until every step in the handover queue is marked completed unless this skill's explicit halt conditions apply.

Accumulate user-decision-required items (`/nightshift:revise-spec` and `/nightshift:revise-plan` findings deferred for later, implementation-phase questions and out-of-scope findings, `/nightshift:revise-code` tech-debt findings) into a single "follow-up items" list maintained in a scratch file (`.tmp/handover-followups.md` in the project root), not conversation memory: long runs cross context-compaction boundaries, and the scratch file is the authoritative copy the morning report (step 12) reads and presents. Open it with a header line naming the spec and target scope so a leftover is attributable. Beneath that header, every item is exactly one canonical JSON line with this shape: `{"source":"<artifact type and identity>","sourceItemId":"<stable semantic ID>","text":"<exact item text>","proposedRoute":"<route>"}`. Every producer mints a stable semantic `sourceItemId` independent of list position, and the pair `(source, sourceItemId)` is unique. To add an item, write the complete next contents and atomically replace the scratch file. Revise transfers use the stable follow-up ID as `sourceItemId`; an existing matching pair is a successful idempotent handoff, not a duplicate or failure. The morning report decodes each JSON entry and retains its source identity when presenting it. At shift-start, a leftover copy from another artifact or an already-completed run is dead state: overwrite it without mining it; a live copy from an interrupted run on the same artifact and target scope is the resume case and keeps accumulating. Delete it only after step 12's whole tail (persistence, completion stamp, plan-removal offer) completes, so a session that dies mid-tail can re-run the tail from it.

**The unattended rule.** Handover exists so the user can walk away. Review checkpoints, whether a sub-skill's or handover's own (spec or plan review after a revise loop, the plan artifact's Spec Reconciliation per-edit approvals, follow-up triage, end-of-loop asks), are therefore deferred to the morning report rather than pausing the run mid-pipeline. Deferral, not waiver: each checkpoint becomes a follow-up item carrying what would have been asked, and the user answers it at the report in the checkpoint's own terms. Scope artifact-review checkpoints to artifacts that existed at shift start: a hardening delta is only reviewable against a baseline the user has seen, so for any artifact authored during the run (the plan when handover enters at the spec gate, and equally the code the run implements) the review pause collapses into the shipped-work summary -- report what the review run completed and changed, but do not pose the deltas as an approval question. The test is whether the review changed behavior that existed at shift start, not which artifact type it was: a fix that touches a pre-existing line without changing its behavior (a constant or helper extraction under the scout rule) does not resurrect the checkpoint, while a fix that alters pre-existing behavior does. A corollary: workflow-instruction files (nightshift plugin files, the user's global CLAUDE.md, memory files) are not edited mid-run, whether the impulse comes from `/nightshift:revise-lore` or from a revise loop's dimension or authoring retrospective (whose own "apply with the user's approval" instruction is one of the deferred asks, never an auto-pass); every candidate edit to them becomes a follow-up item (the concrete edit plus the session evidence motivating it), applied only after morning-report approval via the persistence mechanics in step 12. Applying instruction changes mid-run would skip the user's review of text that governs future runs and let a session-local workaround mask a defect in the instructions. The corollary is about lore, not target work: when the plugin repo itself is the project being handed over (self-hosting), its files are the implementation surface and the pipeline edits them normally. The run still stops at the shift-start confirm line where detection raises one (a clean detection proceeds on the stated read), for destructive, irreversible, or outward-facing actions, and when work is genuinely blocked on missing input. Exact equality, representation-only drift, and a validated `within-contract` refresh continue unattended without a response. Only a gate outcome that requires a fresh or renewed response blocks unattended continuation. Producing or changing the accepted decision surface remains the human's work, so an unavailable user on that response path stops the run without authority. The mode is declared, never inferred. A handover trigger puts the whole run in unattended mode, and it stays there however long the run takes and however often the user checks in: a check-in answers the question it answers (a response-path gate, a halt condition) and changes nothing else, so deferrals keep accumulating for the morning report. Only an explicit statement from the user that they are taking the work back ends unattended mode; from that point the run is attended, every deferred item is drained as an inline ask before continuing, and nothing further accumulates except mid-run captures (below). A run that has not been handed over is attended from the start and defers nothing but those captures.

**Mid-run captures.** A user capture that arrives while the lifecycle is in flight (an idea, a bug, a quick win, any thought not tied to the current work) is filed as a follow-up item in `.tmp/handover-followups.md` in both modes, never as an immediate backlog edit and commit: the capture survives the session, the pipeline is not interrupted, and the governing artifact is not edited under a running review. An unattended run presents it at the morning report like any other deferred item; an attended run presents it at the run's closing summary, since a capture is not a checkpoint and drains at the end rather than inline; this is the one deliberate exception to attended mode's nothing-accumulates standard. A check-in that only supplies a capture changes nothing else about the run's mode.

## Artifact locations and selection

Handover looks for specs and plans in the project's established locations; when a project has none, the standard fallback is `.claude/specs/` for specs and `.claude/plans/` for plans.

When multiple candidate files coexist (stale plans persist because removal is only offered, never forced), select the artifact for the feature under discussion using the same resolution order the revise skill's scope rules use: the artifact named or implied by the invocation and conversation context first, then the most recently modified candidate, with `git status` recency as tiebreaker where the candidates are tracked (untracked candidates, ignored or simply new, fall back to file modification time alone). The confirm line names the chosen file paths explicitly, so a wrong pick is visible before any work starts. Handover operates on one in-flight feature per invocation; coexisting artifacts are disambiguated here, not orchestrated in parallel.

## Backlog entries count as specs

The spec role is filled by a dedicated spec file when one exists; otherwise by the backlog entry or entries whose text carries the design (a feature entry and its breakout file especially, but bug and quick-win entries too when their text is the design record). "Spec" throughout this skill means whichever artifact fills that role.

Stamp targets and completion recording follow the form. A spec file takes hardening stamps and the step-12 completion stamp as written. When the entry has a breakout file (`features/<slug>.md`, `bugs/<slug>.md`), that file is the stamp target: revise-spec hardening stamps and the step-12 completion stamp land there exactly as on a spec file, and the file's persistence after shipping makes the stamps durable. Index-only entries take no stamps: per-entry stamps inside a shared index defeat the file-scoped fingerprint and clutter the scannable backlog; their completion record is the walk-and-remove archive move (gone from the active index, present in the history archive), and their currency check is the agreement-entry validation below. At step 12, backlog-entry-specced work with no breakout file skips the stamp with a one-line note.

## Agreement and stage entry

**Target scope first.** Before walking the ladder, resolve which feature and which scope this handover takes over: from the invocation, then session context, then the spec's own phasing declaration (a phased spec names its feature phases and the sections each covers), and, when none of those establish it, by asking the user. A spec with no phasing declaration defaults to `whole file`, so the ask is reserved for genuinely phased or ambiguous cases. A feature phase is handover's conversational term for a stamp-comparable implementation scope; a revise review round or wave is an internal repeated-review unit and does not alter that target scope.

**Coverage** is containment plus currency: a stamp covers the target scope when its recorded scope contains it AND the artifact's in-scope content is unchanged since the stamp (the artifact-drift check below supplies the currency signal; drift that cannot be localized to sections counts as in-scope). Drift within the target scope defeats coverage outright, and the ladder treats the artifact as not hardened (or not completed) for that scope; this is a rung decision, not a soft flag, though the user's confirm-line answer still overrides.

Walk the ladder top-down and enter the procedure at the first rung whose condition holds. State the conclusion in one line, naming the chosen spec/plan paths, the target scope, agreement result, and any stamp or staleness details, for example: "Spec .claude/specs/foo.md agreed in this session and hardened for sections 3-5 (stamped 2026-07-04 09:41 at a1b2c3d), matching the target scope; no plan found; taking over from planning." When the detection is clean (the rung decided on solid evidence, artifact selection unambiguous, validation found no issues, and no staleness, drift, live-claim, queue-versus-ladder, or inconclusive-evidence flags are raised), proceed directly to building or resuming the step queue: the stated conclusion is the user's interrupt point, not a question. Two signals are non-flags, alone or together: a `(live-claim: provisional)` marker whose provisional status is a designed outcome (its probe gated behind a cutover or release precondition recorded per the spec-gate rules), and a same-session mid-flight implementation resume (a hardened plan whose implementation is partially committed, resumed in the session that ran it). With only these present the detection stays clean and the run proceeds straight to building or resuming the step queue; the confirm is kept for real ambiguity, artifact-selection doubt, validation findings, drift, and a queue-versus-ladder disagreement. Any flag, ambiguity, or validation finding instead asks the user to confirm before work starts ("... Correct?"), and the user's answer always overrides inference about the stage; it never substitutes for agreement authority. References to "the confirm line" throughout this skill mean this stated conclusion; where a flag applies, it is posed as the question just described.

Throughout the ladder, "same-session evidence" means the event demonstrably happened earlier in the current conversation. Where evidence is inconclusive, the rung reads as not satisfied (a failed check is not a clean check), and the confirm line states which question could not be answered, in that rung's own terms.

1. **Late-stage tail already ran this session**: no-op; say so.
2. **Implementation complete**: the plan's tasks are committed. Commits are deliberately not labeled with plan-task numbers (plan hygiene forbids it), so the evidence is correspondence between plan-named files and commits since the plan's hardening stamp, or same-session evidence; inconclusive reads as not complete. A history rewrite breaks this evidence entirely (the stamp SHA is no longer an ancestor of HEAD); the confirm line must then say outright that handover cannot tell whether the implementation already landed, since the ladder would otherwise propose re-implementation at rung 3. If complete: enter at step 5 (the late-stage tail).
3. **Plan exists.** Hardened (stamp or same-session evidence): enter at step 4 (implementation). Not hardened: enter at step 3 (revise-plan).
4. **Current agreement exists and no plan exists.** Hardened for the target scope (coverage, per the definition above): enter at step 2 (planning). Not hardened: enter at step 1 (the spec gate). Currency is what makes the feature-phase rule work: a whole-file stamp from an earlier feature phase contains later sections by grammar, but sections added or edited after that stamp fail currency, which is exactly what mandates re-hardening for a later feature phase. Agreement remains governed by candidate reconstruction and contract fit, never by a durable stage label.

After any complete handover-controlled batch that can change a governing artifact, governing-set membership or order, target scope, or plan declarations, execute the agreement skill again in `post-mutation` phase with originating caller mode `handover` before another reviewer, planner, implementation step, verifier, or downstream transition. Exact equality, representation-only change, and a validated `within-contract` result refresh or retain volatile authority and continue immediately. Every outcome that requires a fresh or renewed response blocks without authority under the unattended rule.

## Provenance stamps

Completed spec and plan review runs append hardening stamps (see the post-loop steps in the revise skill's `spec.md` / `plan.md`); the persisted stamp token remains `graduated`, and handover writes the completion stamp at step 12. All stamps live under a `## Hardening` section at the end of the artifact, created if absent:

```
- revise-spec graduated 2026-07-05 14:32 at a1b2c3d, scope: sections 3-5, content: 9f3a2b1c
- handover completed 2026-07-06 09:15 at e4f5a6b, scope: sections 3-5, content: 1c2d3e4f
```

- **Scope grammar**: `scope: whole file` for a whole-file pass, or `scope: sections <headings or ranges>` for a section-scoped pass. Plans are typically hardened whole-file. Rung comparisons are scope against scope, one grammar everywhere.
- **The SHA** is the repo HEAD commit at write time. The hardening edits themselves are uncommitted at stamp time, so a hardening stamp's SHA is the pre-hardening baseline; the artifact file itself is therefore always excluded from any SHA-based overlap diff (it would otherwise self-flag its own hardening edits), and edits to the artifact are instead owned by the fingerprint-based drift check below.
- **The fingerprint** is the short hash of the artifact's eligible design content, excluding only the terminal `## Hardening` provenance section. Use `selectArtifact` with `selectorKind: design-before-hardening`, pass that selection to `hashSelection`, and record the first eight hexadecimal characters of its `contentHash` until the portable fingerprint helper changes stamp production. The fingerprint, not any timestamp, is the drift signal: it is machine-independent and blind only to eligible provenance appends. Inline markers such as `(live-claim: ...)` are design content and DO move the fingerprint; see Post-stamp edits below. Timestamps in stamps serve the age check and latest-provenance ordering only.
- **Post-stamp edits**: when a sanctioned pipeline step edits a stamped artifact after its stamp (any live-claim marker rewrite, whichever step performs it: step 1's fold-back, an agreement-entry disposition the user requests, step 6's rewrite, a step-12 disposition; plus revise-plan's Spec Reconciliation), invoke `writeProvenanceStamp` through the shared agreement controller with the current complete-file baseline hash and the fresh stamp matching the scope of the graduated stamp it refreshes (one refreshed line per affected graduated stamp on phased specs), the current HEAD, and the new fingerprint, suffixed with the reason in parentheses, e.g. `- revise-spec refreshed 2026-08-02 17:20 at 1a2b3c4, scope: whole file, content: 9d8c7b6a (live-claim fold-back)`. The shared writer owns grammar validation, atomic replacement, readback, and applied-retry handling. The prefix names the artifact's hardening loop, whichever step performs the refresh. A `refreshed` line supplies the fingerprint for the drift check only: the age check and the content-overlap check continue to baseline on the most recent `graduated` stamp. It restores hardening coverage but never creates agreement authority. On an index-only backlog entry, which takes no stamps, skip the refresh with a one-line note.
- **Migration**: artifacts hardened before stamps existed carry none; detection treats them as not hardened and the confirm line is the correction point (self-healing: any future completed spec or plan review appends its stamp). A stamp that is present but lacks a `content:` fingerprint (hand-edited or malformed) is treated the same way for currency: not current, fail closed, surfaced in the confirm line.

## Staleness sanity check

When a detection rung rests on a stamp, sanity-check it before trusting it:

- **Age**: flag if the stamp is more than 48 hours old, baselining on the most recent `graduated` stamp (`refreshed` lines do not reset the clock, per Post-stamp edits). Hardening normally immediately precedes planning or implementation; anything older deserves a look. The number is a deliberate default guideline, not a gate.
- **Content overlap**: list files changed since the stamp commit (`git diff --name-only <sha>..HEAD`, excluding the artifact itself) and judge whether any are in the vicinity of the artifact's subject matter. A plan names its files explicitly; for a spec, infer the affected areas from the stamped scope. Unrelated churn passes silently. There is deliberately no commit-count threshold; relatedness is the signal, not volume.
- **Artifact drift**: compare the artifact's current content fingerprint against the most recent covering hardening or completion stamp. For section-scoped targets, true drift must additionally be localized: diff the artifact's current content against its content at the commit that introduced the stamp line (the post-hardening baseline; never baseline on the recorded time, which unavoidably predates the commit that carries it), and map the changed lines to sections. Drift within the target scope defeats coverage at the rung level; drift demonstrably elsewhere is a soft flag; drift that cannot be localized (untracked artifacts, unusable history) is treated as in-scope, fail closed, and the confirm line says so. This stamp check classifies lifecycle stage only. Candidate reconstruction and contract fit exclusively classify agreement currency.
- **Degraded mode**: the overlap diff is only meaningful when the stamp SHA is an ancestor of HEAD. After a rebase, squash, or on a machine that never had the commit, it is not; the overlap check is then inconclusive and reported as such, never silently treated as clean. The same ancestry break invalidates rung 2's implementation-completeness evidence; rung 2 owns how that surfaces.

The age flag, the overlap check, and out-of-scope drift are soft judgment calls, never hard gates; they surface in the confirm line together with the already-completed validity result and an offer: (a) full re-run of the scoped revise loop, (b) proceed as-is. The mandatory validation above is not repeated because no governing artifact or repository baseline changes between it and this decision. Neither choice creates or refreshes agreement authority.

## Version-control-optional artifacts

Specs and backlog files may be git-ignored by user election; the `.gitignore` is the election, checked per file (`git check-ignore`, tracked status). Plans are outside the election: `.claude/plans/` is git-ignored unconditionally. Before trusting or writing a plan hardening stamp, verify that the selected plan is ignored and untracked. A tracked plan is a blocking legacy conflict: stop before stamping, implementation, or deletion and require manual resolution. Never attempt to commit an ignored artifact (write the edit, skip the commit with at most a one-line note). When an ignore entry matches a still-tracked file, the ignore entry wins as the statement of intent; note once that the untracking is incomplete and suggest `git rm --cached`. Git-based recency evidence applies only to tracked artifacts; untracked ones use file modification time (selection tiebreak only; nothing load-bearing).

## Triage during revise rounds

If a finding changes the implementation scope (what we're building, not how we describe it), block and ask: that's a brainstorm gap that needs resolving before code lands. This block survives the unattended rule as genuinely blocked work: halt the run rather than implementing all night past an unresolved design gap or silently deferring it. Polish-shaped findings (clarity, naming, missing context) go to the follow-up list and the loop continues.

## Procedure

1. **Spec gate.** `/nightshift:revise-spec` scoped to the target scope, run to completion under the skill's review rules. Handover's own review pause on the hardened spec (a checkpoint of this skill, not of the revise skill) is deferred per the unattended rule: the noteworthy hardening deltas become a morning-report item. Keeping this step ahead of planning puts the natural context-compaction boundary here: run it at the brainstorm tail while the design context is warm, then compact, and a fresh handover session starts directly at planning with the spec already hardened. Findings flow into the follow-up items list. **Live-claim verification** closes the gate: when the hardened spec carries `(live-claim: provisional)` markers (written by revise-spec's Design-soundness criterion on repo-unverifiable runtime claims), probe each one against the live system in every distinct context the feature covers, using whatever tooling the session has (browser automation, API access), and fold the results back before planning begins: a confirming probe rewrites the marker to `(live-claim: probed <date>)`. A contradicting probe splits three ways: a correction local to the spec's record is an inline edit plus stamp refresh; a design-affecting correction re-enters the spec gate; a contradiction that invalidates a design decision halts per the triage rule above. Probes are observation-only; a claim whose only probe would mutate outward state is carried forward as provisional with a morning-report checkpoint item naming the blocked probe (the unattended rule's halt stays reserved for unsettled claims that block the design itself, per the triage rule above). When the environment cannot reach the live system, carry the claims forward explicitly as provisional and ensure step 6's end-to-end verification covers each one. A claim whose probe requires an artifact this run cannot produce is unreachable by construction rather than merely unreached (behavior that appears only in a released or installed build or after a cutover, when that release or cutover is user-gated at the morning report): it stays provisional through step 6 without counting as a skipped verification, and its morning-report item names the release as the probe's precondition, so step 12's disposition is recorded as a knowing `deferred <date>` rather than reading as an unprobed gap; step 6 still names such a claim, and naming it satisfies coverage without resolving it. Where a placement or design choice would retire the claim outright instead of deferring it, prefer that: an unprobeable dependency avoided is worth more than one carefully tracked. Fold-back edits change the artifact after its hardening stamp: refresh the stamp per Provenance stamps.
2. **Write the implementation plan** via the `superpowers:writing-plans` skill. Consume the agreement caller result and invoke `serializePlanContract` so the returned plan contains exactly one machine-authoritative `## Governing specs` section plus its matching human-readable spec header before every other level-two section. Never substitute prose links or hand-built declarations for the returned ordered `governingScopes`.
3. `/nightshift:revise-plan`: run to completion under the skill's review rules. Its Spec Reconciliation step applies spec-worthy corrections directly; the unattended rule defers the per-edit approvals, so record each applied correction as a checkpoint item for the morning report.
4. **Implement the plan** using the `superpowers:subagent-driven-development` skill. A handover started on the default branch carries the user's handover as consent to implement there; record it as that skill's ruling instead of creating a worktree. Before the first dispatch, make sure that skill's workspace directory is git-ignored (add `.superpowers/` to the project's `.gitignore` when absent) so no implementation commit can sweep it in. One fresh subagent per plan task; dispatch in parallel where the dependency graph allows. Verify each batch's commits landed on the intended branch: a subagent that inherits a git-worktree skill may create a worktree and commit on a separate branch even when told to work on the current one, so check `git log` after each batch rather than assuming. Use subagents even when the plan contains complete verbatim code: dispatch keeps implementation churn (file contents, test output) out of the controller's context window, which is a primary benefit on its own, separate from the fresh-context review. Plans are never committed: `.claude/plans/` is git-ignored. With the plans policy verified, the plan file and its uncommitted hardening stamp remain untracked, so no implementation commit can sweep the plan in. When the plan is later removed (per the step-12 offer, or a plan task that prescribes its own cleanup), delete the untracked file directly; the spec, code, tests, and commits are the durable record, and a landed plan left in the working tree reads as in-flight work to stage detection.
5. `/nightshift:revise-code`: run to completion under the skill's review rules. Valid-but-deferred findings flow into the follow-up items list across all rounds; do not prompt on them at end-of-loop.
6. **Verify end-to-end.** Drive the affected flow in the running app or tool and observe the behavior (the `verify` skill's discipline, if that skill is available: exercise the change, don't just trust tests or typecheck). Skip with a one-line note when the session's diff has no runtime surface to drive (docs-only or test-only changes). Where the run settles any claim still marked `(live-claim: provisional)`, whatever step first surfaced it, rewrite its marker to `(live-claim: probed <date>)` on a confirming result and refresh the stamp per Provenance stamps; a contradicting result routes per step 1's three-way split, never to a marker rewrite.
7. `/nightshift:revise-docs`: update project docs to reflect what shipped.
8. **Backlog bookkeeping check.** In projects with the four-index `.claude/` layout, confirm the shipping protocol ran for everything that landed this session: history-archive entries appended (`FEATURES_HISTORY.md` / `BUGS_HISTORY.md` / `QUICK_WINS_HISTORY.md`), slice bullets struck through and the parent's top-level `**Requires:**` and `**External:**` lines advanced where a slice shipped, and the walk-and-remove sweep applied to every other `**Requires:**` line in `FEATURES.md` / `BUGS.md`. `/nightshift:revise-docs`' Completed-features guideline owns the protocol; this step exists as an explicit checkpoint because `/nightshift:ready`'s correctness depends on the sweep having run. Skip with a one-line note in projects without the layout.
9. `/nightshift:revise-lore`: review the session for CLAUDE.md / plugin updates worth persisting. Project-repo lore (the project's CLAUDE.md, backlog pattern notes) may be applied and committed directly; it is itemized in the morning report's lore-outcomes section. Workflow-instruction lore (nightshift plugin files, the global CLAUDE.md, memory files) is not applied here, per the unattended rule's corollary: draft each candidate as a follow-up item, and run revise-lore's fresh-eyes pass over the full set of drafted workflow-instruction diffs, including those proposed by earlier steps' dimension and authoring retrospectives, before the morning report presents them, so the user reviews vetted proposals.
10. **Persist workflow edits.** A pointer, not work: approved plugin follow-ups are applied inside step 12's post-triage tail, never earlier. The step stays in the queue so a resumed session sees persistence as part of the pipeline; mark it completed together with step 12.
11. **Full test suite.** Run the project's full test suite as defined in the project's CLAUDE.md. This phrase is the explicit ask that overrides any per-project "never run the full suite without filter" rule. If the suite is not green, halt and surface failures before triage; test failures are not follow-up items.
12. **Morning report.** Open with the shipped-work summary and verification outcome, then two sections that are easy to omit and must not be: **lore outcomes** (the session's whole lore ledger: project-repo lore applied directly, with commit ids, plus every drafted workflow-instruction proposal awaiting triage, whichever step proposed it; retrospective-proposed plugin edits live here, not in the next section) and **retrospective outcomes** (each revise loop's dimension- and authoring-retrospective outcomes, explicitly including null results like "no prompt changes warranted" or "no habit worth promoting", pointing at lore outcomes for any edits either proposed; a silent retrospective is indistinguishable from a skipped one). Then surface the accumulated follow-up items (from all prior steps) with a default route proposed for each: (a) fix now (small, scout-rule, low-risk), (b) track, (c) skip. Two shapes need their own terms: deferred review checkpoints are asked as the question they carry (approve, adjust, revert), not forced into fix/track/skip; and a route-(b) item tracks in its own home: the handed-over project's `QUICK_WINS.md` for project items, and for workflow-lore items the plugin repo's own tracking (its backlog if one exists; otherwise ask at triage where to put it).

    Presentation mechanics. The user saw none of the churn behind the list, so present items strictly one at a time: one item per message, rendered as a self-contained dialog whose question text carries the background needed to decide in isolation (where the item came from, what changed since, the exact proposed edit) plus the recommended action, then stop the turn and wait for the user's decision before presenting the next item. Never batch the remaining items into one message, even as a numbered summary with per-item recommendations and a bulk-approve escape hatch; the sequential ask IS the review surface, and a batched list forces the user to either rubber-stamp or re-request the per-item flow (observed 2026-08-02: a batched morning report had to be re-run item by item on request). The dialog (AskUserQuestion or the harness equivalent) presents the routes as options carrying per-option consequence descriptions, the recommended route first; everything the user needs goes inside the dialog because text placed before a dialog in the same turn may not render. Fall back to plain prose plus a text question only when an item's background genuinely exceeds what the dialog can carry. This mechanics rule supersedes the revise skill's bulk-approval ask for the morning report only; standalone revise runs keep bulk-approve, since their user is present and holds the loop's context.

    Plugin follow-ups approved here are applied with release provenance: edit the plugin repo clone (not the installed cache), bump the plugin version once per unpushed batch, commit in the clone, and leave pushing to the user unless directed. Approved global-CLAUDE.md and memory edits are persisted via whatever mechanism backs each file; for gist-backed files, flag the local-vs-gist divergence so the user can sync.

    After triage completes, everything is verified, and every required agreement response is resolved: report any surviving `(live-claim: provisional)` markers and record the user's disposition for each in the marker itself (`probed <date>` if the run settled it, `deferred <date>` on a knowing deferral, so the ruling survives the conversation and the completion stamp is never written over silently-unprobed claims), then invoke `writeProvenanceStamp` through the shared agreement controller with the current complete-file baseline hash and the completion stamp for the spec. The shared writer owns grammar validation, atomic replacement, readback, and applied-retry handling; write it BEFORE the next offer, so a session that dies in between leaves the plan in place and the next handover merely re-runs the tail, wasteful but safe, then offer to remove the plan file (plans are ephemeral scaffolding once work lands; the spec stays). Invalidate volatile agreement state on completion before returning. Re-entry after any partial run resumes the detected stage from the handover queue's first unmarked step; resume within a single procedure step is deliberately not tracked across sessions.
