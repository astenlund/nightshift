Stop Guard Cook-Along

Hand Claude a task list and walk away, and two things go wrong: it stops before the list is done, or it loses track of the list when the conversation is compacted. You will build two small hooks against both, one idea at a time, testing each step before Claude runs it. They are simplified versions of the hooks I chose for Nightshift, my plugin for handing agreed work to Claude Code and Codex overnight.

Step 013 min

Setup

At the end: a folder with a task list, a small codebase, a hook tester and a catch-up script.

The idea

Models judge, deterministic code keeps the books

Leave engineering and product judgment to the model. Give the bookkeeping to plain code wherever a mistake would lose work, corrupt state or misreport what happened: what was promised, what is done, and what is still owed.

Hooks are where that split lives in Claude Code. A hook is your own program, and the harness runs it at a fixed moment. Claude cannot skip it or talk its way past it; it can only decide what to do with the hook's answer. Today you build two of them:

Why I chose this for Nightshift Nightshift carries agreed work through implementation, review and verification while I sleep. I can't check on the model at 3 a.m., so the bookkeeping that decides whether a night's work counts as done lives in code the model can't skip, and the model keeps the engineering decisions.

Likely question

Simplified compared with what? What does Nightshift add?

Two things: sturdier versions of these two hooks, and a workflow around them.

  • In the hooks themselves. The record is a database of the run instead of a Markdown file, and Claude changes it only through checked operations. Progress counts only when something is recorded, such as a check that ran. Before I leave, Nightshift verifies that the hook is actually loaded and active in that session. On Codex it uses Codex's own goal instead.
  • Before the work. Claude reads back what it understood and asks whether to begin. Larger work gets a short spec, which is reviewed too.
  • After the work. A fresh model reviews the whole change, and every finding is checked by a second, skeptical model before anything is repaired. I prefer the reviewer to run on the other host, so Codex reviews Claude's work and the other way round.
  • At the end. Updated docs and backlog, reviewed as well, a short retrospective, and in the morning a report of what was delivered, how it was verified and what is still waiting on me.

The hooks keep a run going while I sleep. Everything around them is what lets me trust what it did without reading the code. The wrap-up compares the hooks side by side.

Step 115 min

The guard

At the end: Claude cannot end its turn while TASKS.md has an open task.

The idea

Stop is the moment the work can be checked

Every time Claude is about to end its turn, Claude Code fires the Stop event. It runs your command, writes a description of the event to its stdin as JSON, and reads stdout. If you print {"decision": "block", "reason": "…"}, Claude receives the reason as Stop hook feedback and keeps working. If you print nothing, the turn ends.

The hook does not ask Claude whether it is done. It looks at the record. Claude Code now also has a built-in /goal, which turns out to be a Stop hook as well; Questions compares the two.

Why I chose this for Nightshift When I hand work over to Nightshift on Claude Code, a Stop hook like this one keeps Claude working until the run is done. Codex models tend to end their turn early, so on Codex I rely on its own persistent goal instead.

    Claude, after the guard sent it back

    If your Claude does all three tasks in one go, the guard never needed to speak. That is the guard working too.

Likely question

Why not just type /goal?

Often you can. /goal is this same mechanism, built in: the docs call it a wrapper around a session-scoped prompt-based Stop hook, where a separate small model judges your condition from the conversation after every turn.

  • /goal fits when the work fits one session, when done is something Claude can show in the conversation, such as a passing test run, and when you want a model other than the worker to judge it.
  • A hook and a record fit when the rule must hold in every session and for everyone on the project, when done should be read from a file or a command instead of judged from the conversation, and when you need your own exit rules, such as pausing for questions or giving up without progress.

In rehearsal, /goal with a task only the user could do looped nine times, exactly like step 2's first guard, until we wrote an exit rule into its condition. The full answer has the details.

Talk about it

Step 215 min

A guard that knows when to let go

At the end: the guard pushes while Claude makes progress, then stops pushing and tells you plainly what is unfinished.

Cook along: break it first

  1. Reset the demo. This unticks every task, restores src/text.js and deletes the test file:

    node catchup.js reset

  2. Add a task Claude cannot do as the last line of TASKS.md:

    - [ ] Get the product owner's sign-off on the slug format. Only the user can arrange this.

  3. In Claude, run /clear for a fresh conversation, then:

    >Work through TASKS.md.

  4. Claude finishes the three coding tasks, explains that only you can arrange the sign-off, and tries to stop. The guard blocks. Claude explains again. The guard blocks again.

    Claude, fourth time round

    The hook blocks every stop while any box is unchecked, including tasks only you can do, so it will keep firing.

    On Claude Code 2.1.288 the loop ended after nine blocks with this warning. On older versions it never ends: press Esc.

    A hook blocked the turn from ending 9 consecutive times — overriding and ending turn. For Stop/SubagentStop hooks, check stop_hook_active in the input and return success while it's true. Set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP to raise this limit.

The idea

Three ways to let go

  • Check stop_hook_active. The event says true when Claude is already continuing because a Stop hook sent it back. Returning early whenever it is true is what the warning suggests. It means one nudge, ever, even while Claude is doing real work.
  • Lean on Claude Code's cap. It overrides your hook after nine blocks in a row. That is late, nine turns spent, and the warning says nothing about what is unfinished. The built-in /goal ends up here too: given this task list, its checker said not met nine times until the cap.
  • Count reminders that bought no progress. Any change to the record resets the count. After three reminders with nothing changed, let Claude stop and tell the user, in plain words, that the work is not done.

Progress means something you can observe, here a change to TASKS.md, rather than something Claude says. And stopping only beats looping if the stop says plainly what is unfinished: quietly dropping work, or calling an unfinished run done, is worse than both.

Now imagine the stuck task had read Publish the package to npm. A guard that never lets go pushes an agent towards actions nobody authorised.

Why I chose this for Nightshift Nightshift uses the third way: after three reminders without recorded progress, the run stops and is reported as incomplete, never as done. For the same reason it asks before any destructive, irreversible or outward-facing action I haven't explicitly authorised, and when I'm not there it parks that task and carries on with the rest.

Talk about it

What could fool a guard that counts any change to TASKS.md as progress?

Rewording a line resets the count. Ticking a box costs one keystroke whether or not the work was done. That is why, in Nightshift, I count only progress that Nightshift records itself, such as a check that ran or a review that came back.

Step 312 min

Whose turn is it?

At the end: the guard only acts on work you handed over, and Claude can park a question for you and carry on with the rest.

The idea

Autonomy bought with trust is not reliability

Stop fires after every reply: a finished task, a plain answer, a question only you can answer. A guard that blocks a question forces Claude to guess. You get a run that never waits for you, and a result you can no longer trust.

Handing work over has two halves. The run should not wait for you without need, and it should not lower its standard to avoid waiting. Neither half is worth having at the other's expense. Two rules keep both:

  • Guard only what was handed over. Stop follows every reply, so while you are at the keyboard the guard stays quiet. And only you decide that the work is handed over.
  • Park decisions, keep working. While you are away, Claude records the question, sets that task aside and carries on with everything that does not depend on the answer.

Why I chose this for Nightshift Nightshift's Stop hook follows both rules, because I want to come back in the morning to work that is either done or clearly waiting on me, never guessed.

Cook along

  1. Replace TASKS.md. It gains a handover line, which only you change, and a - [?] state for tasks waiting on you.

  2. Replace the guard. It now returns early unless the work was handed over, and lets Claude stop with a pause message when only parked tasks remain.

Likely question

What if Claude asks with the question dialog instead?

Then no Stop hook runs at all. The multiple-choice dialog (the AskUserQuestion tool) keeps the turn open and, by default, waits until someone answers. While you are at the keyboard that is the best way for Claude to ask. During a handover it is a trap: in rehearsal the dialog sat unanswered for four minutes while nothing ran.

Two fixes, both rehearsed. The askUserQuestionTimeout setting closes an unanswered question after 60 seconds, 5 or 10 minutes, but its timer does not count down while your terminal window is focused and never starts while Remote Control is connected. A PreToolUse hook can refuse the dialog during a handover and tell Claude to park the question instead, which works in every case. The full answer has the hook's code.

The summary is not the record

At the end: after any compaction, Claude gets the open tasks straight from TASKS.md.

  2. /clear, then:

    >Start on TASKS.md with the first task.

  3. Squeeze the conversation hard. /compact takes instructions for its summary:

    >/compact Keep only one short sentence, and leave out every task detail.

  4. Ask what is left, from memory only:

    >Without opening or reading any files, answer from what you already know: what is still left to do?
    Claude, in rehearsal, without the hook

    I can't tell you whether there are more tasks after task 4. The summary of our earlier conversation was cut down to one sentence, so I've lost the full list. The numbering above comes from my last message to you.

    Your Claude may still list every task. After compaction, Claude Code re-reads up to five files that Claude read or edited with its own file tools, so if Claude ticked task 1 with its Edit tool, TASKS.md comes back by itself. In this rehearsal Claude ticked it with a shell command (sed), which Claude Code does not track, so only src/text.js came back. Press Ctrl+O to see which tool Claude used. Either outcome makes the point: without the hook, whether the list survives depends on how Claude happened to touch the file.

The idea

Put the obligations back at the boundary

Compaction replaces the conversation with a summary. A long handed-over run compacts many times, and each summary may drop or blur what is still owed. The fix is to keep the record outside the conversation and put a short brief of what is owed back in front of the model at the moment it needs it: right after compaction.

Claude Code already brings some things back after compaction. According to its list of what survives compaction, the project-root CLAUDE.md is re-read from disk, and so are up to five files Claude read or edited, most recently modified first, though a file over 5,000 tokens comes back only as a path. Everything else, including instructions you gave only in conversation and context that hooks added earlier, goes through the summary.

For anything else that must come back, the boundary is the SessionStart event with the matcher compact, which fires after both /compact and automatic compaction (confirmed in rehearsal for both). Whatever the hook returns as additionalContext is added to Claude's context. The brief should also tell Claude to check the record against the files, because a task can be half done.

Why I chose this for Nightshift After every compaction, Nightshift's hook hands Claude a short brief of what is still owed, built from the run's saved state, and tells it to check that against the actual files before doing anything that depends on it. A run I hand over at midnight can compact several times before morning, and I don't want its obligations to depend on how well each summary turned out.

Likely question

Aren't compaction summaries usually fine?

Often they are. In rehearsal, automatic summaries of 3,300 to 6,100 characters kept every task's status. They are not fine in these cases:

  • Something was only said in conversation. The docs say it directly: instructions given only in conversation may be lost. A constraint you mentioned once, such as don't touch the public API, survives only if the summary keeps it. Put lasting rules in the project-root CLAUDE.md, which is re-read from disk.
  • The exact detail matters. Claude Code's own summaries carry the warning If you need specific details from before compaction (like exact code snippets, error messages, or content you generated), read the full transcript. The exact wording of an acceptance criterion is that kind of detail.
  • The run is long. Each summary squeezes everything still owed into a few thousand characters, and the next compaction summarizes that summary together with the newer work, so detail can wear away round by round. Context a hook added earlier is summarized too, which is why restore-tasks.js runs again after every compaction.
  • The record did not come back from disk. Claude Code re-reads at most five files Claude touched with its own file tools, and a file over 5,000 tokens comes back only as a path. In rehearsal Claude ticked TASKS.md with a shell command, so the list did not come back.
  • Work was half done. A summary records what Claude believed when it was written, not what is on disk. That is why the hook tells Claude to check TASKS.md against the files.
  • Compaction itself fails. When large tool output refills the context faster than compaction can clear it, Claude Code stops with Autocompact is thrashing and ends the turn. In rehearsal that also cleared an active /goal.
  • Someone steers the summary. /compact takes instructions, and a Compact instructions section in CLAUDE.md shapes automatic summaries too. Our demo used that to throw the list away.

The hook costs one file read, does not depend on any of these, and runs after every compaction. A /goal also survives compaction, but it carries only its condition; we tested that too.

Step 615 min

Questions people ask

Answers with the rehearsal evidence behind them, and when each one applies.

Why not just set a goal with /goal?

For a session's worth of work, do. /goal is the built-in version of step 1. The docs describe it as a wrapper around a session-scoped prompt-based Stop hook, and when we set one in rehearsal Claude Code said so itself: A session-scoped Stop hook is now active. It also has a real strength: completion is decided by a fresh model rather than the one doing the work. Three things differ from what you built today:

  • What gets checked. The checker doesn't run commands or read files independently, so it judges what Claude has said and shown in the conversation. In rehearsal its verdict cited three Edit operations in the transcript. Your guard reads TASKS.md itself. Neither checks that the work is right; that is take-home 1.
  • How it lets go. With the sign-off task, /goal Every task in TASKS.md is ticked off. was judged not met nine times in a row, until Claude Code's block cap ended the turn: the same loop as step 2. Writing step 3's exit rule into the condition (…or marked [?] with a question for me because only I can do it) fixed it, and the goal was met on the first check. With /goal, exit rules are sentences a model interprets. In a hook, they are code.
  • How long it lasts. One goal per session. It survives compaction and resuming the session (see the next question), but /clear removes it, and so does an error you have to fix, such as exhausted credits or a context overflow that compaction cannot clear. A new session or a teammate starts without it. A Stop hook in settings applies to every session in its scope, and the record lives in the repository.

Choose /goal when:

  • the work fits one session, and you will set the goal again if it is cleared;
  • done is something Claude can show in the conversation, such as a test run that passes or a build that exits 0;
  • a task Claude cannot finish is unlikely, or you write the way out into the condition;
  • you would rather write a sentence than code, and want a model other than the worker to judge it.

Choose a hook and a record when:

  • the rule must hold in every session and for everyone who opens the project;
  • done should be read from a file or a command, not judged from what Claude said;
  • you need exit rules that behave the same every time: stay quiet while you are there, park questions, give up after three reminders without progress;
  • the list of what is owed has to outlive the conversation, its summaries and the session.

The two also combine: a goal and your hooks run side by side, and a settings hook can itself be a prompt hook when a judgment is what you need. Nightshift needs everything on the second list, which is why it uses a Stop hook and its own record. Sources: Claude Code goal docs, rehearsal runs on Claude Code 2.1.288.

Does a goal survive compaction?

Yes. We tested it three ways on Claude Code 2.1.288, forcing compaction early with a 100K-token window:

  • Manual. With a goal active, /compact Keep only one short sentence, and leave out every task detail. squeezed the conversation into Everything I can do is finished, and the one remaining item is waiting on the user. /goal still reported Goal active, and once we confirmed the sign-off, the goal was judged met.
  • Automatic. On a ten-task list the goal survived two automatic compactions. Claude finished nine tasks with all tests passing, and the checker kept judging correctly from what Claude re-read after each compaction. The automatic summaries, of 4,100 and 5,400 characters, kept every task's status.
  • Too much compaction. When we set the threshold barely above the starting context, compaction ran every few tool calls until Claude Code stopped with Autocompact is thrashing. That error cleared the goal, as the docs say an error you have to fix will, with nothing ticked yet. With the hooks, nothing is cleared, because the record and the hooks never lived in the session.

Claude Code keeps the condition outside the conversation and writes it back into the transcript after every compaction. So compaction is not the case for hooks over /goal. The case is everything a goal does not carry: your task list (only the condition survives, and the summary has to carry the rest), your exit rules, and anything beyond the session.

What happens when Claude needs to ask me something?

It depends on how Claude asks.

  • In a reply. The question ends Claude's turn, so the Stop hook runs and your code decides. Step 3's guard lets the question through while you are there; during a handover it sends Claude back to park the question as - [?] and carry on. A hook never pauses itself, so there is nothing to switch back on: once you answer, it runs again at the end of the next turn. /goal pushes back instead. Its checker says not met and Claude keeps working, until the goal is met, judged impossible or stopped by the block cap. After that the goal stays set, and your next message resumes it.
  • In the question dialog. Claude can also ask through a multiple-choice dialog, the AskUserQuestion tool. While you are at the keyboard this is the best way to ask. The dialog does not end the turn, though, so no Stop hook or goal check runs while it waits, and by default it waits until someone answers. In rehearsal, with the work handed over, the dialog sat unanswered for four minutes while nothing ran. In a headless claude -p run the problem does not arise: the docs say the tool is offered there only when the run has a permission host to answer it.

Two fixes, both rehearsed in an interactive session:

  • Let unanswered questions time out. Set askUserQuestionTimeout to 60s, 5m or 10m in your user settings or under /config. In rehearsal a countdown appeared near the minute, the dialog closed on its own, and Claude parked the question in TASKS.md and stopped with the guard's pause message. The docs list the catches: the timer does not count down while your terminal window is focused, and it never starts in a background session or while Remote Control is connected.
  • Refuse the dialog while you are away. A PreToolUse hook can deny the tool and say what to do instead. In rehearsal Claude parked the question, and ten seconds later the Stop guard let it end with Paused on your decision. This works whatever the window focus, and with Remote Control connected.

Permission prompts, including plan approval, are the same kind of trap, and they never time out. In our first attempt at this test, a prompt to approve a sed command held the run in exactly the same way. Give an unattended run the permissions it needs before you leave, or use auto mode.

Why not just tell Claude to keep going, in the prompt or in CLAUDE.md?

An instruction is advice that Claude weighs against everything else it has been told. A hook is a check the harness runs at every stop. Where you write the instruction matters too: the project-root CLAUDE.md is re-read from disk after every compaction, while a prompt lives in the conversation and survives only as well as the summary carries it.

An instruction is enough for short work you are watching. In rehearsal, Work through TASKS.md. got all three tasks done without a single block. It falls short when:

  • Your words and the instruction pull different ways. Told Do the first task, Claude kept to those words over the hook nine times (step 1). An instruction in CLAUDE.md gets the same weighing.
  • The work cannot be finished. Never stop until TASKS.md is done has no way out, so Claude must either break the rule or keep going with nothing to do (step 2).
  • You are sometimes there. CLAUDE.md applies to every session, including the one where you only want to ask a question (step 3).
  • Nobody checks the record. With only an instruction, done is Claude's own reading of the situation, not what TASKS.md says.

Do Claude models actually stop early?

Less than you might expect, but they stop in predictable places. Building Nightshift, I found that Codex models tend to end their turn early and Claude models mostly don't, which is why on Claude Code the Stop hook is a safety net rather than the engine. In rehearsal Claude did not stop early when the scope was the whole list: Work through TASKS.md. finished everything in one turn. It did stop:

  • At the end of the scope you named. Start on TASKS.md with the first task. stopped after task 1 to report back (step 1).
  • At a decision only you can make. The sign-off task ended turns again and again (step 2).
  • When an error ended the turn. Compaction thrashing did it in rehearsal; the goal docs list usage limits, exhausted credits and failed authentication as others.
  • To ask. A question in a reply ends the turn; a question in the dialog holds it open instead (see above).

The guard earns its keep on long runs, after compaction, when a prompt is ambiguous about scope, and at 3 a.m. when nobody is there to type carry on.

Couldn't Claude just tick the boxes, or edit the hook?

It could tick the boxes. The guard checks the record, not the work, and TASKS.md is an ordinary file. In rehearsal Claude refused, even under nine blocks in a row: ticking it would record a sign-off that nobody gave. That is judgment, not a guarantee. The pressure is highest when ticking is the only way out: a task Claude cannot do, a guard that never lets go, and no honest way to pause. Step 2's limit and step 3's - [?] exist to give it honest ways out. Stronger defences check evidence instead of ticks (take-home 1) and keep the handover line out of Claude's reach (take-home 2).

Editing the hook is harder. .claude/ is a protected path: writes there are never auto-approved. In the default and accept-edits modes Claude has to ask you first, in auto mode a classifier decides, and an allow rule in settings changes neither; only bypassPermissions skips the check. During a handover that prompt would simply hold the run until you answer it.

That is why, in Nightshift, the agent never edits the record directly: it changes state only through checked operations, and nothing counts as done until an independent reviewer has looked at it and the evidence is recorded.

Isn't this what auto mode or skipping permissions is for?

They solve a different problem, and an unattended run needs both. A permission mode decides whether Claude may act without asking; the guard decides whether it may stop. In the words of the goal docs: Auto mode on its own approves tool calls within a single turn but doesn't start a new one. Without the right permissions, a handed-over run stops at the first prompt it cannot answer: in rehearsal a prompt to approve a sed command held a run just like an unanswered question. Without a guard, Claude stops whenever it judges the work done. Before you leave, pre-approve what the work needs or use auto mode, and give the run a guard and a record.

What happens if the hook crashes?

It fails open: Claude stops as if the hook were not there. In rehearsal we deleted TASKS.md, the guard threw an error, Claude Code reported a non-blocking hook error, and Claude stopped normally. The same happens when node is not on the path Claude Code uses, when the hook prints something that is not valid JSON, or when it runs past its timeout, which for a command hook is 600 seconds by default. Only exit code 2 blocks; a crashing Node script exits with 1 (hooks reference).

Failing open is the right default, because a broken guard should not trap a session. The risk is reading that stop as done. I made Nightshift's hook fail open too, and kept the question of whether a run is complete separate: that is decided from recorded evidence, never from the fact that Claude stopped. To catch a broken guard early, run node run-hook.js stop before you leave, and check /hooks.

What does a blocked stop cost?

Each block is another model turn with the whole conversation as input, so the cost grows with the context. The blocked turns in rehearsal were short, a few sentences each, but in a long run every one re-sends a large context. In step 2's rehearsal the same work took 22 turns with the first guard and 14 with the three-reminder rule. Costs add up fastest when:

  • a guard never lets go and Claude Code's nine-block cap is the only limit;
  • the context is large, since the docs point out that compaction itself reads the whole conversation it summarizes;
  • a goal runs, since /goal adds one call to a small model per turn, which the docs call typically negligible.

Does this carry over to Codex or other agents?

The idea does; the mechanism depends on the host. For Nightshift I use Codex's own persistent goal there, because Codex models tend to end their turn early, and the Stop hook on Claude Code. The hosts also differ when the agent stops to ask. In my Nightshift runs on Codex, a goal that is paused or blocked while the agent waits for an answer stays that way, even after Nightshift picks the run up again, until I reactivate it. In September 2026 the goal tools available to the agent could mark a goal complete or blocked but could not resume it, and whether Codex pauses the goal itself or Nightshift has to block it is not settled yet. On Claude Code a hook has nothing to resume, and a /goal stays set (see above).

Why a Markdown file, and not a database or Claude's own to-do list?

The record has to meet three needs: the hook can read it without trusting the conversation, you can read and edit it, and it outlives the session. A file in the repository is the simplest thing that meets all three, and changes to it show up in a diff. A file stops being enough when:

  • several agents or sessions write to it at once, since nothing stops two writers from overwriting each other;
  • you need history or evidence, such as which check proved a task done and when;
  • an agent should not be able to rewrite it freely, which is the tick-the-box problem above.

Those are the reasons I gave Nightshift a database instead of a file, changed only through checked operations.

When something does not work

Claude stops and nothing happens
Run /hooks in Claude and check your hook is listed. Check node --version works in the terminal Claude runs in, that .claude/settings.json is valid JSON, and that node run-hook.js stop blocks. Restart claude if the hook still is not listed.
Claude did every task in one turn
The guard never needed to block. To watch it run anyway, add fs.appendFileSync(path.join(root, 'events.log'), raw + '\n'); as the first line inside the 'end' handler: every event Claude Code sends then lands in events.log.
Step 2's loop never ends
Older Claude Code versions have no block cap. Press Esc to interrupt.
A demo left a mess
node catchup.js reset unticks every task, sets Handed over: no, restores src/text.js, deletes test/text.test.js and forgets the guard's count. Your hooks and settings stay as they are.
Your hook files are broken beyond repair
node catchup.js N rewrites every workshop file as it is at the end of step N, including the hooks and settings.json.
