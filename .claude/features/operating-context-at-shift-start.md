# Operating context at shift start

Feature: the operating-context check runs at shift start before the agreement digest under the `handover` and `lifecycle` entries, the derived sections and their settled rigor are held in memory and rendered in the digest for verification and tier override, and they are written to the governing artifacts only on agreement. Promoted on 2026-09-02 from the quick win "Run the operating-context check at shift start, before the agreement digest, and render the section in the digest" during its spec gate, when the round-2 scope review found the bullet feature-sized; the two live-claim quick wins it was batched with shipped with it and are archived in `QUICK_WINS_HISTORY.md`. This file is the authoritative design record.

## Problem

In `skills/handover/SKILL.md` the Validate-before-proceeding step flags an absent or skeletal `Operating context` section, and the grounding step that derives or consults for it (`internal/revise/spec.md`) describes itself as running "at the start of the review run, at the entry point where the user is still present (shift start)", while handover's step 9 says the consult "is the entry-point action performed at shift start"; in the procedure as ordered, though, the grounding step runs only when the spec gate's revise-spec run starts, after agreement, validation, the stated conclusion, and queue creation, so the prose claims a timing the pipeline does not deliver. Observed 2026-08-23: the check landed well after the user had handed over, so a consult-needing section would have halted an unattended run. The validation agent and the operating-context check are the two gates that can still need the user before the run becomes autonomous.

## Design

### Shift-start check

Run the operating-context check (derive, and consult if durable knowledge runs short) at shift start before the agreement skill captures its presentation baseline, under the two request modes that lead into a spec gate with the user present, `handover` and `lifecycle` (the mode a `/nightshift:ready` pick or any other natural-language lifecycle entry starts; user ruling 2026-09-02), but hold the derived section and any deviation entries in the volatile controller context rather than writing them to the artifact: nothing lands in a governing artifact before the user agrees to the digest (user ruling 2026-09-02). The check runs after governing-set resolution and the unfinished-design guard have passed and immediately before the presentation baseline is captured, so a `brainstorming-required` outcome holds nothing and a design rewritten by brainstorming is derived from fresh at the next shift start. It runs per governing artifact, excluding the index-entry companion the resolver adds beside a feature or bug breakout file (its excerpt is a summary and the breakout owns the section, so the field renders nothing for it and the write skips it): an artifact whose section is already complete keeps it, and the controller derives and holds a section only for each absent or skeletal member (a skeletal section is held as its completed replacement: the authored bytes plus the missing inputs appended as bullets and the derivation record rewritten in place or, when the section carries none (grounding-step rule (b)), inserted in the section's own authored form: as the Derived rigor bullet immediately after the last input bullet when the inputs are bullets, or as a trailing derivation paragraph after the section's last paragraph when the inputs are prose, the record closing the held section after any appended input bullets in either form; never a from-scratch section).

### Digest field

The decision-complete digest in `skills/spec-agreement/SKILL.md` gains a twelfth mandated field, **Operating context**, rendered per governing artifact in candidate order so the user verifies it with agreement: each artifact renders as one block: a first line `<artifact> (<marker>)` using the digest's artifact identifier, where the marker is `complete` for a complete section rendered from the presented baseline, `derived, written on agreement` for a held section, `overridden, written on agreement` for any member carrying an override (a held member with one, or a complete member held as its overridden replacement), or `absent` or `skeletal (<reason>)` as below; then the section body: for a section derived from scratch, normalized to the same top-level bullets whatever placement shape the artifact uses (the six input bullets, the Derived rigor bullet, and any deviation entries, so an indented continuation, a heading-form block, and a file section render identically); for a complete section, its bytes as written, since shipped sections also exist as prose paragraphs and the check has already judged them complete; for an overridden complete member and for a skeletal section held as its completed replacement, the artifact's authored bytes with only the derivation record rewritten in place (or, for a skeletal section carrying no record, inserted in the section's own authored form: the Derived rigor bullet after the last input bullet, or a trailing derivation paragraph after the last prose paragraph, the record closing the section after any appended input bullets) and, for the skeletal case, the missing inputs appended as bullets, so authored prose is never discarded; then the rigor line. A governing set may mix these markers; identical sections render in full; collapsing them into one rendering that lists the artifacts sharing it is the work of [Shorten the decision-complete digest and cut what it costs to produce](../QUICK_WINS.md#agreement-digest-economy), not of this feature. A tier divergence across the set (the settled tiers of the covered artifacts that have a tier are not all equal; artifacts without a tier never trigger it) renders as a divergence line in the field, `Divergence: <artifact> <tier>; <artifact> <tier>` over every artifact the check covers, in candidate order, showing each member's settled tier (the overridden one where an override applies) and recomputed on every re-presentation (an absent or skeletal member renders `<artifact> not derived`), where `<artifact>` is the digest's own artifact identifier (`<path>:<line>` for an index or bullet entry, the bare path for a file spec), and the user may resolve it at the same reading (an override or a requested change); a divergence left standing at agreement is not an error: each artifact keeps its own section, and the review run surfaces the divergence as the finding `internal/revise/plan.md` already defines. When a caller in any other mode presents before its grounding step has run, the field renders `absent` or `skeletal (<reason>)` per artifact, where `<reason>` lists every failing skeletal rule in letter order, each with its missing or offending items comma-separated and rules separated by semicolons (rule (a) items are the six input labels `deployment`, `audience`, `failure`, `concurrency`, `reversibility`, and `lifetime`; rule (b) has the single item `derivation`; rule (c) the single item `tier`; items render in that label order; for example `skeletal (a: deployment, audience; c: tier)`), with a note that a standalone revise-spec run's grounding step derives it (the revise-plan wrapper raises its structural-precondition error and revise-code has no grounding step, so under those wrappers the marker stands as rendered), never an inferred section.

### Rigor line and override

For every complete or held section the field closes with the settled rigor on its own line, in one of two literal forms: `Rigor: <tier> (derived: <audience category>, <n> uplifts fired); effort: validation <v>, recovery <v>, compatibility <v>, observability <v>, proofEffort <v>` for a derived tier, or `Rigor: <tier> (overridden by user <date>: <basis>; derived: <derived tier> from <audience category>, <n> uplifts fired); effort: validation <v>, recovery <v>, compatibility <v>, observability <v>, proofEffort <v>` for an overridden one (with `<basis>` rendered as `none stated` when the user gave none), where the parenthetical repeats the two derivation inputs (for a held section, the ones the controller passed to `internal/revise/rigor.js`, which reports only the tier and the effort; for a complete section, the ones its own derivation record names, whether a `- **Derived rigor**:` bullet or a trailing derivation paragraph, both shipped forms) and the effort tail is rendered from the derivation rule's Step 3 for the settled tier in the literal spellings above, whatever spelling the section's own record uses, and the `<n>` slot renders as a numeral and the `<audience category>` slot in the derivation rule's own spelling, both recomputed from the inputs the record names rather than copied from its prose; when [Rigor-steered lifecycle](rigor-steered-lifecycle.md) rebases the derivation on more inputs, this grammar and its fixtures change with it, and that feature's reciprocal pointer names this line as a dependent. An `absent` or `skeletal` artifact closes with `Rigor: not derived` instead. The line exists so the user can override the final tier at the same reading. Reasoning: the derivation is deterministic to keep the tier out of the author's taste, but the six inputs are the user's facts and the tier is a review budget the user pays, so the user may elect a different tier in either direction within the scale, provided the election is recorded beside the derived value with its basis so reviewers see the delta; this is the digest-time form of the user election that [Rigor-steered lifecycle](rigor-steered-lifecycle.md) Mechanism 5 declares at shift start, and that feature file gains a reciprocal pointer in the same change set. Until [Accept an unambiguous qualified agreement without re-presentation](../QUICK_WINS.md#agreement-response-classification) ships, an override names one or more members or, when it names none, applies to every member of the set, and each affected member gets its own deviation entry; it is a design change with its own lifecycle: the controller records it as a deviation entry that is the rewritten Derived rigor bullet itself, in the literal form given below (no separate line is written, because the bullet already has a literal form and a placement site, so a second entry would duplicate both), naming the overriding tier, the user, the date, the derived tier it replaces, and the user's stated basis (the `<basis>` slot everywhere in this feature is the user's words normalized to one line, whitespace runs collapsed and any backtick or semicolon removed so the literal grammars stay parseable, or the literal `none stated`); for a held member the entry lands in the held section and that section's derivation record is rewritten in whichever form it has (the Derived rigor bullet or the trailing derivation paragraph, both shipped forms whatever the input shape) to the same overridden literal form given below, exactly as the complete-member branch does, so the member renders marked `overridden, written on agreement` like an overridden complete member; and for a complete member the controller holds that member's section as its overridden replacement (its derivation record, whichever form it has, rewritten to the literal form `- **Derived rigor**: overridden by user <date>: <basis>; derived tier <derived tier> from audience <category> plus <n> fired uplifts via node internal/revise/rigor.js; effective tier <tier>; per-dimension effort: validation <v>, recovery <v>, compatibility <v>, observability <v>, proofEffort <v>`, so the bullet never asserts that the derivation command yields the overridden tier; that rewritten bullet is the deviation entry), so an overridden complete member becomes a written member on `continue` and the write's untouched-members rule applies only to members without an override. A further override on the re-presented digest supersedes the earlier one: its deviation entry replaces the earlier entry and still names the derived tier, never the superseded election. The override keeps the held sections through its re-presentation (it is the one requested change that edits the held sections in memory instead of discarding them, because discarding would re-derive the same sections, could re-fire the shift-start consult mid-agreement, and would lose the deviation entry the override just recorded): the controller re-presents the digest with the overridden tier and accepts a plain agreement on that presentation; the grounding step's skeletal rule (c) (a stated tier that does not follow from the inputs) is amended so a tier backed by a user-override deviation entry counts as complete, and per-dimension effort follows the overridden tier through the derivation rule's Step 3.

### Post-agreement write

A held section is part of the decision surface: retained authority (exact equality, a representation-only change, or a validated `within-contract` refresh) may continue only when no held section is still unpresented, and a held section not yet shown to the user forces a fresh presentation instead. A successful write releases the held set: written members become complete members, so nothing is held after it and every later boundary in the run continues on retained authority as before. On the gate's `continue`, when no section is held and no override was recorded, the write step is skipped entirely: no boundary call, and the echo line reads `Operating context: no writes (no held sections)`; the write step and its echo exist only under the two governed modes, and so does the override channel: in any other mode the rigor line still renders for a complete section, but a tier election there is an ordinary requested change and nothing is held: under a standalone revise-spec run it routes to that run's grounding step, which records it as a deviation entry, and under the revise-plan and revise-code wrappers, whose grounding step cannot record anything (revise-plan only checks and propagates, revise-code has none), it is a requested change to the governing spec's own section and returns to design like any other. Otherwise the controller writes each held section (with its deviation entries) into its own governing artifact per the grounding step's placement rules, one governing scope at a time in candidate order (the digest's artifact order; scopes that share a file are written in sequence) through a new shared controller operation in `skills/spec-agreement/spec-agreement.js` (`operating-context-write`, exposed on the CLI beside `provenance-write`) that inserts or replaces one artifact's Operating context section at its placement site (for a bullet-form index-only entry, the indented continuation under its bullet per the grounding step; for a heading-form index-only entry with no breakout, a block placed directly after the entry's Requires and External lines and their wrapped continuations, ahead of any Slices block (a top-level bullet appended after the slice bullets would read as one more slice to the ready parser), whose first line is the top-level bullet `- **Operating context**:` followed by the six input bullets, the Derived rigor bullet, and any deviation entries in the same shape as the indented continuation (the Check step and the replace path key on the prefix `- **Operating context**` at the start of that line, so an optional parenthetical note after the label, as the shipped continuations carry, still matches; the same prefix rule anchors the indented continuation), which the shipped `index-entry` selector already covers; for a file spec, a `## Operating context` section inserted immediately before `## Status` when that section exists (the position the rigor-profile precedent `review-orchestration-tests.md` uses; no heading is common to every feature file, so the rule is a fixed fallback chain rather than a shared anchor, and placing it beside the scope anchor was rejected because the first section's role varies across shipped files, so that site is not deterministic), otherwise before the terminal `## Hardening` section, otherwise at the end of the body; a replace keeps the section's existing position) through the same per-file atomic replacement, readback, and applied-retry path the provenance writer uses, with its own already-applied predicate (a retried write is already applied when the artifact's current bytes at the placement site equal the intended section bytes, in which case it is an idempotent no-op success rather than a stale baseline) (each member's complete-file baseline hash is captured immediately before that member's own write, so sequential writes into one file do not invalidate each other; an edit to a governing selection between presentation and `continue` is caught earlier by the gate's reconstruction check, and an edit elsewhere in the same file is tolerated because the write replaces only the section site), since today that path accepts only stamp lines (there is no cross-artifact transaction, and none is needed: see the crash rule below), leaves complete members untouched, runs the grounding step's fingerprint step (its Persist substep already ran at shift start when a consult answered a gap, because the instruction file it writes is not a governing artifact, so neither the hold rule nor the never-write carve-out reaches it), and passes the whole write through the `post-mutation` boundary, where the digest's own Operating context field (which rendered every held section and deviation entry) is the containment evidence citing every hunk for a `within-contract` verdict; the controller's closed citation vocabulary (`DIGEST_FIELDS` in `skills/spec-agreement/spec-agreement.js`) gains an `operatingContext` member so that citation is expressible, and the same change set extends the prose statement of that closed vocabulary in `.claude/features/present-spec-for-agreement.md` (the `digestFields` value list) with the new member and adds the Operating context member to that file's decision-surface list, so the design record and the validator name the same set. A returned per-file write failure on any member (an adapter error, a readback mismatch, a stale baseline because the artifact's complete bytes changed between that member's own baseline capture and its atomic replacement, which only a concurrent writer can cause; the operation is unbound and carries no file-binding check, because the bound variant guards a multi-step provenance flow against a file identity change between steps, while this write captures its baseline immediately before its single atomic replacement, so a binding would add a check with nothing left to protect) halts before the post-mutation boundary: the controller invalidates authority per the agreement skill, leaves the already-written prefix in place (git-tracked backlog files, revertable), and reports which members were written and which failed; the next shift start converges the prefix exactly as the crash rule below describes. Any other verdict (`changes-contract` or `uncertain`) on a completed write is a controller or judge defect, since the written block is the digest's held section in the artifact's placement shape and the semantic judgment is told, through the `operatingContext` citation, that the digest field's normalization rule already maps every placement shape to the rendered bullets, so shape divergence (the indentation, the label line, the heading line) is contained by construction and only the content is judged: the controller invalidates authority, leaves the writes in place, and halts reporting the verdict evidence. Under the unattended rule either halt stops the run without authority. After a successful boundary it echoes one line the user can check at a glance, in the literal form `Operating context: wrote <n> (<artifact> <tier> <derived|overridden>; ...); deviation entries <k>; persisted <yes|no>`, listing every written artifact in candidate order by the digest's artifact identifier, so the line grows by one item per written artifact and never wraps to a second line (user ruling 2026-09-02), where `persisted` is a single per-run boolean that reads `yes` when the shift-start Persist substep wrote consult-gathered facts to the project's instruction file for at least one covered artifact and `no` otherwise (no consult ran, creation was refused, or the facts stayed in a spec's own derivation notes); the validation agent then confirms every member's section (every artifact the check covers) is present and complete, both user-needing gates resolve before the stated conclusion, and the spec gate finds the sections present.

### Held-section lifecycle

Lifecycle of the held sections: a decline, an abandoned presentation, or a requested change other than a tier override discards them with the pending presentation (a reply carrying both a change and an override discards and re-derives, then re-applies the override to the re-derived sections), so a rejected digest leaves the backlog untouched, while the shift-start Persist write to the project's instruction file, which is not held, stays in place on every discard branch because it records durable project facts rather than this design decision (after a requested change the next presentation re-derives and re-holds the sections first, a volatile-store failure that quarantines the store under the agreement skill's storage-failure rule discards them with the pending presentation and abandons any write that a `continue` had triggered but not yet performed, with the forced fresh presentation re-deriving and re-holding them exactly as a requested change does, and the agreement skill's stability recheck does the same when it restarts from a replacement baseline, re-applying any recorded override to the re-derived sections exactly as a combined reply does, so no held section outlives the bytes it was derived from and no election is lost to drift; re-firing the consult only if durable knowledge again runs short, which lands on the present user); a crash between agreement and the last write leaves a prefix of the set written, which is a designed state rather than corruption: volatile authority is gone with the session anyway, and the next shift start's per-artifact check finds the written members complete and the rest absent or skeletal, derives and holds sections only for the rest (from the same durable knowledge, so normally identical; a consult may repeat), presents the mixed set in the digest, and on agreement writes only the missing members, so the half-written state converges without rollback. An override recorded at agreement but not yet written is lost with the session like any held section: the next presentation shows the derived tier again and the user re-elects; no override is inferred from a crashed run.

### Landing order and tensions

This feature has no sub-slice: the override channel lands with the digest field by user ruling (2026-09-02: the rigor line is in the digest so the user can override the final tier at the same reading), and it reuses the hold, deviation-entry, and write machinery, so a core-first split would ship a rendered rigor line that accepts no election, the shape the ruling rejected. Within this batch, the three entries edit the same Validate-before-proceeding paragraph of `skills/handover/SKILL.md` and land in this order, one atomic commit each: the Reconcile quick win (sentence softening), then the Make quick win (marker grammar and the designed-ness read), then this feature (the shift-start invocation). Landing order against [Present the controller's assessment of the governing text before the digest](../QUICK_WINS.md#agreement-presentation), which edits the same pre-digest sequence in `skills/spec-agreement/SKILL.md`: this entry lands first, and the assessment then renders after the operating-context derivation so it reads the held sections.
