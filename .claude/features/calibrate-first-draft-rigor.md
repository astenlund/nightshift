# Calibrate first-draft rigor to deployment context

Feature: every first design-spec draft states an explicit rigor profile derived from the feature's operating context, with correctness as a non-negotiable floor and validation, recovery, compatibility, observability, and proof effort scaling with consequences and context. This file is the authoritative design record.

## What it does

Today the first design-spec draft carries no declared standard for how hard it will be validated, how much recovery and compatibility machinery is warranted, or how far observability and proof effort must go. Rigor is whatever the author's default habits happen to produce, and fresh reviewers have no shared reference for the standard the draft holds itself to. In high-consequence deployment contexts that risks under-engineering; in low-consequence personal tooling it risks over-investment out of proportion to the trust and exposure at stake.

This feature adds an explicit rigor profile to the first spec draft: a statement of the operating context the feature will live in and the rigor warranted above the correctness floor. Correctness is never negotiable; the dimensions above it scale with consequences.

The profile is an active design input, not a passive annotation: the rigor derived from the operating context may legitimately change the solution's architecture, machinery, and validation level, since it governs the mechanism rather than the requested outcome. Because the revise lifecycle does not own how the initial spec is drafted, it cannot assume the section is already present; a grounding step owned by the revise lifecycle ensures the profile is derived and present before any review begins, applies it to the design, and feeds it to reviewers as calibration context.

## The profile's content

The profile records the operating context drawn from these inputs:

- deployment environment and operational criticality;
- audience, the derived classification of userbase size, trust boundary, exposure, and the commercial-deployment relationship (individually named below; see `## The audience classification`);
- failure consequence and data or security sensitivity;
- concurrency and compatibility risk;
- reversibility and recovery cost;
- expected feature lifetime.

From these it derives the rigor standard for validation, recovery, compatibility, observability, and proof effort above the correctness floor. Dimension effort scales with consequences; it never drops below the correctness floor, and a profile that reads "low rigor" still means low effort on the *scaling* dimensions, never permission to relax correctness or omit known requirements.

## Placement: an operating-context section in the spec

The profile lands as a prose `Operating context` section in the spec body, paired with the [durable scope anchor](durable-scope-anchor.md). The two sections split cleanly and do not overlap:

- the scope anchor records the requested outcome and the material exclusions that bound it: *what* the user asked for;
- the operating-context section records the environment the answer must hold in and the rigor it warrants: *in what context*, at what rigor.

The profile does not re-open the anchor's exclusions, and the anchor does not lift rigor. Both are sections of prose, not machine-parseable fields, consistent with the anchor's decision form.

## The audience classification

Audience ("who is this for") is a derived classification, not an independent hidden input: it summarizes four input components, userbase size, trust boundary, exposure, and the commercial-deployment relationship, and audience is the label the profile carries over those components. The category set, surfaced from the durable-scope-anchor migration:

- personal use;
- trusted circle;
- paying customers;
- organization;
- public.

The set is non-exhaustive. There is no fixed component-to-category rule; mapping the four components to a category (e.g. how large or paid a userbase crosses from trusted circle to paying customers) is a judgment boundary the author makes and records as a deviation entry with its basis, exactly as Step 1's closest-match and Step 2's uplift predicates are recorded. This keeps the grounding-step machinery deterministic on a settled category without inventing a numeric scale that would imply false precision, and it means two implementers given the same components still record the same reasoning rather than silently diverging. When no category fits cleanly, the closest match is the recorded deviation. Treating audience as a derived classification avoids double-counting it against the four components it summarizes.

## Derivation: durable project knowledge first

The profile is derived from durable project knowledge before the user is consulted. If repository guidance, architecture documents, or established project conventions already answer a question about the operating context, those answers are used. The user is asked only when the feature differs materially from the documented defaults, or when unresolved ambiguity would change a design decision.

Any feature-specific deviation from the project's documented defaults is recorded in the spec, so fresh reviewers apply the intended standard without repeatedly reopening the question.

The setup may run short of durable project knowledge. Persistence is scoped to the gap, not the deviation. The consult fires for one of two reasons: durable knowledge ran short (no documented answer existed to consult), or the feature deviates from a documented default. Only the first case persists: when the consult answered a question durable knowledge left unanswered, the operating-context facts gathered are written to the project-local `CLAUDE.md`/`AGENTS.md` instruction file, so the knowledge-first derivation has more to draw on the next time and the user is not re-asked about the same context. A deviation from a documented default is the second case and is never persisted: it is a feature-scoped decision, already recorded in the spec per the deviation rule above, and writing it back to the instruction file would corrupt the next feature's defaults. The persistence target is project-local instruction prose, not the feature backlog: these are durable facts about the project's environment, not design decisions tied to one feature.

A project may have neither instruction file. In that case the persistence step creates the instruction file the host that performed the derivation reads: `CLAUDE.md` under Claude Code, `AGENTS.md` under Codex (the active host is known at derivation time, so the selection is not ambiguous). This creates the file a future session of the same host will read at startup, exactly the case where persisted facts have the most future value.

The target file may also be a pointer rather than a home for content. In a shared setup one instruction file can simply reference the other (e.g. a `CLAUDE.md` whose body is only `@AGENTS.md`), with the real content living in the referent. The persistence step writes to the file that actually holds durable content, not to a pointer: if the chosen host file is a pointer to the other, the facts are persisted to the file it points at. A pointer otherwise gives the impression of a persistence home while hiding the write in a file the next session may not load as the primary source. If creation is refused or the project deliberately tracks no durable instruction prose, the gathered facts stay in the spec's own derivation notes rather than being silently dropped, so the next session still re-derives them without re-asking the user.

## Enforcement: a grounding step in the revise lifecycle

The section must exist before review begins, and the revise lifecycle owns the point where spec work passes into review, so the enforcement lives there: the lifecycle that runs the review is the point Nightshift controls, and it cannot assume the section arrived with the draft. The two lifecycle entry points run different sides of the grounding step, because they review different artifacts:

- **`revise-spec` operates on the spec body itself.** The step checks the spec for the operating-context section; when it is absent or skeletal, the step derives it from the knowledge-first derivation above, consulting the user only when durable project knowledge runs short; then it recalculates the fingerprint after adding or filling the section, so every reviewer in the run calibrates against a complete profile. "Skeletal" has a fixed meaning: the section is present but omits any of the six operating-context inputs, or records inputs without applying the derivation rule in `## Derivation rule: input to tier to dimension effort` to yield a tier and per-dimension effort, or states a tier that does not follow from the inputs under that rule. Absent means no `Operating context` section at all. A section that passes both checks is complete and review proceeds. Determining whether the section omits an input is a semantic judgment over the section's prose, the same class of judgment the derivation rule concedes for its Step 2 boundaries. When that classification boundary is not mechanically decidable from a fixed vocabulary, the grounding step records the detection call and its basis as a deviation entry, exactly as Step 2 does, so two grounding-step implementers do not silently diverge on whether a section is skeletal.
- **`revise-plan` operates on the upstream spec(s), not the plan.** The plan artifact is a separate ephemeral `.claude/plans/*.md` file that carries no operating-context section of its own, and plan-vs-spec fidelity is already routed through the plan review's Spec Reconciliation step, which reconciles against each upstream spec. So the revise-plan grounding step verifies each upstream spec the plan carries a complete operating-context section before planners and reviewers calibrate; it does not duplicate the section into the plan. A plan may reference one or more upstream specs, or none at all. For each referenced spec, if its section is absent or skeletal, the grounding step raises the same structural precondition error rather than inventing a plan-local copy, and the plan's author is directed to harden that upstream spec first. When the plan has no upstream spec (the plan review's Spec Reconciliation step already supports spec-less plans, skipping with a one-line note), the revise-plan grounding step takes the same skip-with-a-note path rather than raising an error against a nonexistent spec: there is no operating-context section to verify, so the plan's rigor calibration is simply recorded as absent and the plan proceeds without that baseline.

In both entry points, the check runs before any reviewer or skeptic launches, and an absent or skeletal section is a structural precondition error rather than a reviewer finding. The consult is an entry-point action performed at shift start while the user is still present; the run continuation may later be unattended, but the section is filled first. No defaults-substitution or fail-closed halt path is needed, and this spec defines none; the grounding step asks and fills, then proceeds.

**The structural precondition error has a fixed identity and shape.** It is a single named error emitted by both grounding steps, reported before any reviewer or skeptic launches, and both `revise-spec` and `revise-plan` raise the same literal name so the two share one identity. The name is `structural-precondition-error` and it is fixed here. Its content is three fields: the artifact path that failed the check, the reason (absent or skeletal, with the specific missing input or rule violation), and the remediation direction (for a spec, derive or fill the section; for a plan, harden the upstream spec, or the skip-with-a-note path when no upstream spec exists). The error's *shape* is deterministic: same name, same three fields, regardless of which check fired, so the author fixes the gap before review proceeds. The emission is mechanical once the absent/skeletal determination is made; the determination itself, where it rests on prose classification rather than a fixed vocabulary, follows the deviation-recording caveat described in the skeletal definition, and is not claimed deterministic.

The step is owned by the revise parameter files (`spec.md` and `plan.md`), not by `SKILL.md`, since it is artifact-specific.

## Stability: frozen unless the user revises

The profile is written once at spec creation and remains stable as implementation mechanics are refined, mirroring the scope anchor's freeze. If the user's operating context genuinely changes mid-flight, the profile is revised and the revision itself is recorded (old text, new text, why), so reviewers who saw the previous context know what shifted.

## Propagation: reviewer payloads as context

The operating-context section is copied unchanged into reviewer payloads as common context, alongside the scope anchor, so fresh reviewers in every dimension and phase calibrate findings against the same environment and rigor standard. The source differs by artifact: for a `revise-spec` review the section is copied from the spec body; for a `revise-plan` review the sections are copied from each upstream spec the plan references (the plan carries none of its own, so the calibration channel pulls them from the specs the plan came from), which is how the plan-side grounding step's "reviewers calibrate against the upstream sections" is realized. When a plan references multiple upstream specs whose operating-context sections declare different rigor tiers, the divergence is itself a finding reviewers surface (the calibration baselines conflict), directing the plan's author or the upstream specs' owners to reconcile them before the plan's rigor is trusted. It is a grounding input to review, not a review outcome. This propagation is also the mechanism by which the profile acts as an active design input, in both directions: a reviewer who sees a declared `high` tier and a design body whose validation, recovery, compatibility, or observability machinery reads as minimal is expected to flag the under-engineering as a finding; a reviewer who sees a declared `low` tier and a design body carrying heavy machinery the profile does not warrant is expected to flag the over-investment as a finding (in the design-soundness or requirements dimensions), directing the author to conform the mechanism to the warranted rigor in whichever direction it deviates. The profile's design-shaping effect runs through that calibration channel, not through a separate conformance gate; the claim that it may change the architecture is realized as review findings, and the conformance success criteria below test exactly that channel in both directions. Whether fresh reviewers reliably flag either mismatch is a runtime-owned behavior the repository does not settle; the conformance criteria below are provisional probes of it `(live-claim: provisional)` until a real review run confirms the mismatch surfaces.

## Derivation rule: input to tier to dimension effort

The derive step fixes the shape of the derivation so the same operating context produces the same rigor machinery: the baseline tier, the uplift set, the cap, and the deviation-recording path are all fixed, and no step's mechanism is left to the author's taste. Step 1's category-to-tier mapping and Step 3's tier-to-effort mapping are deterministic once their inputs are settled. Where any step needs a judgment boundary rather than a mechanical gate — the audience-component-to-category classification in `## The audience classification`, Step 1's closest-match when no category fits, or a Step 2 uplift predicate when the boundary is not mechanically decidable — the decision is not silently made by two implementers differently; the author records the boundary call and its basis as a deviation entry, so any reviewer of the same spec reads the same reasoning for the same context. It proceeds in three firm steps.

**Step 1, the baseline tier from audience.** Map the audience category to a three-level tier (low, medium, high): personal use and trusted circle map to `low`; paying customers map to `medium`; organization and public map to `high`. Audience anchors the baseline because it is the *who* of the feature, the single input that most directly expresses whom a failure afflicts and how much trust those people place in it; the other five inputs are *how* the context aggravates that baseline, so they can only raise it. The specific mapping follows from that principle: a tool for personal use or a trusted circle fails on a person who chose to run it and can reconfigure it themselves, so its consequences are locally contained (low); a paying customer has exchanged money for a promise, so failure breaks an explicit commercial contract (medium); an organization or the public is an anonymous, unfixable-by-its-users blast radius whose failure cascades beyond the immediate user (high). This is why internal `organization` outranks `paying customers`: a contract is reparable, an org-wide or public failure is not. The audience set is non-exhaustive. When no category fits cleanly, the closest match is used and the choice is recorded as a deviation entry with its basis (per the unified judgment-boundary rule above), rather than silently forced; this is the audience classification's "the closest match is the recorded deviation" rule.

**Step 2, tier uplift from the remaining inputs.** The deployment-environment and operational-criticality input raises the tier one level when the feature runs in a production environment whose outage has observable external effect (a deployed service others depend on, an always-on surface, an environment where failure is visible beyond the immediate user). The failure-consequence and data-or-security-sensitivity input raises the tier one level when the answer handles, stores, or transmits data whose loss or disclosure has external consequence, or when the surface is security-sensitive even with no external data to disclose (a credential store, an authentication boundary, a privileged execution path whose compromise is an incident regardless of a disclosure target). The concurrency and compatibility risk input raises the tier one level when unsynchronized writers or a broken interface contract would corrupt or strand data. The reversibility and recovery cost input raises the tier one level when a failed rollout cannot be rolled back cheaply. The expected-lifetime input raises the tier one level when the feature is expected to outlive its initial deployment. Uplifts are applied to the baseline, each one level, and the tier is capped at `high`. Any of three cases is recorded as a deviation rather than silently settled: a raise that would pass the cap, an uplift that would double-count the same fact, or a judgment boundary where the predicate is not mechanically decidable (for example whether a rollout "cannot be rolled back cheaply"). A deviation records the boundary call and its basis, so reviewers of the same spec read the same reasoning.

**Step 3, dimension effort from the tier.** The tier maps to effort on the five scaling dimensions: `low` means minimal validation beyond the correctness floor, basic recovery, default compatibility, lightweight observability, and proof by inspection; `medium` adds targeted validation for the named risks, recovery for the identified failure modes, compatibility checks for the interfaces actually used, per-risk observability, and proof by targeted tests; `high` means systematic validation, full recovery machinery, strict compatibility contracts, comprehensive observability, and proof by documented test evidence. The mapping is fixed so the tier name alone determines the effort level on each dimension.

## Constraint semantics: proportionate engineering

A profile derived from a low-consequence context is a statement of the environment the answer must hold in, not a license to skip required work: correctness stays the floor, and known requirements still bind. A profile derived from a high-consequence context raises the proof and validation bar and may reshape the architecture, recovery, and observability machinery to match.

Rigor governs the mechanism, never the outcome. What the user asked for, and the anchor's exclusions, remain the scope anchor's domain; rigor changes the *how* (architecture, validation, recovery, compatibility, observability, proof effort), not the *what*. A high-consequence profile therefore legitimately drives design changes that a low-consequence profile would not warrant, and review dimensions treat that as an expected consequence rather than scope drift.

**Success criteria.** This feature is done when:

- a `revise-spec` run on a spec lacking an `Operating context` section derives one (from durable project knowledge, or from a user consult when that runs short and a user is present at the interactive entry point) before any reviewer or skeptic launches, and runs review against a fingerprint that includes the derived section;

- a `revise-plan` run whose upstream spec carries a complete section calibrates planners and reviewers against it without duplicating the section into the plan;
- a `revise-plan` run whose upstream spec lacks a complete section raises the structural precondition error and directs the author to harden the upstream spec;
- a `revise-plan` run with no upstream spec takes the skip-with-a-note path and proceeds without an operating-context baseline;
- a `revise-spec` review of a spec whose design body contradicts its declared rigor tier, in either direction — a `high`-tier profile over a minimal-mechanism design (under-engineering) or a `low`-tier profile over heavy machinery (over-investment) — surfaces that mismatch as a reparable finding, so the profile's design-shaping role is enforced through review rather than declared but untested `(live-claim: provisional)`;
- a user consult during derivation persists the gathered operating-context facts to project-local instruction prose (creating the file when neither exists), so a later derivation re-uses them.
