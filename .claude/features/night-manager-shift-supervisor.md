# Night manager and shift supervisor

Feature: reorganize autonomous Nightshift runs around a two-level management hierarchy. The Night Manager is the top-level user-facing agent role that owns the result, protects the accepted intent, makes executive decisions, watches convergence, stops or redirects unhealthy work, devises controlled experiments, and delivers the morning report. An on-demand Shift Supervisor owns workers and minute-by-minute orchestration so routine dispatch traffic and detailed agent output do not consume the Night Manager's strategic context.

This is an exploring umbrella draft. It records the role and authority decisions settled in the 2026-08-31 design discussion while leaving implementation-tuning numbers, durable schemas, and host-specific dispatch mechanics for graduation.

## Scope anchor

Requested outcome: Give autonomous Nightshift runs a persistent logical Night Manager role with enough context and authority to steer toward a useful result, backed by an on-demand Shift Supervisor that manages workers, preserves execution continuity, and reports decision-ready evidence upward.

Material exclusions:

- Do not name or model the user as another Nightshift role. The user sets direction, grants authority, and receives the Night Manager's morning report.
- Do not make the Shift Supervisor mandatory for deterministic or otherwise worker-free operations.
- Do not define fixed non-convergence time limits yet. Hourly reporting for long revise waves is settled, but stop-work baselines remain implementation-tuning work.
- Do not silently promote experimental instruction variants into canonical workflow instructions.
- Do not design a cross-host or cross-provider second-opinion strategy in this feature. Until a formal consultation contract exists, managerial second opinions use the same role and model as the requester.
- Do not grant publication, destructive-action, permission-bypass, or other authority the user did not already delegate.

## Agent hierarchy

The user sits above and outside the Nightshift agent hierarchy as the source of direction and authority and as the recipient of the morning report. Nightshift assigns the user no internal role name.

| Role | Scope | Primary responsibilities |
|---|---|---|
| Night Manager | Executive ownership of one lifecycle run | Preserves intent, arbitrates ambiguity, steers against drift, judges convergence, makes go or no-go and scope decisions within delegated authority, governs recovery, authorizes experiments, seeks managerial peer advice, and owns the morning report. |
| Shift Supervisor | Operational ownership of worker activity within that run | Dispatches and tracks workers, handles minute-by-minute scheduling and retries, consolidates evidence, maintains execution checkpoints, reports progress and exceptions, and escalates decisions outside its authority. |
| Workers | Bounded specialist assignments | Perform implementation, review, verification, research, or other scoped work and return evidence to the Shift Supervisor. |

`controller` stops being the public role name for the top-level agent. It remains the correct term for deterministic state-machine code and for durable mechanics that code owns, and that machinery is not a fourth role. Existing `controller-owned` references require classification rather than blanket renaming: executive judgment, user communication, and discretionary authority move to the Night Manager, while deterministic ledgers, provenance, admission, detection, and state transitions remain controller-owned.

## Activation and authority lifecycle

- Every autonomous lifecycle run has one authoritative logical Night Manager. Each authoritative instance carries a monotonically increasing Night Manager authority generation within the lifecycle run identity. Replacement must fence the prior generation before mutation, so two authoritative Night Manager instances never govern the same generation.
- The Night Manager requests one authoritative logical Shift Supervisor when the run requires meaningful worker orchestration. The deterministic controller performs the authority transition and returns the active supervisor identity after commit. Shift Supervisor instances use the same generation-and-fencing rule for their logical role. A same-role peer consulted for advice is not another authoritative supervisor.
- Worker-free deterministic operations remain directly owned by the Night Manager and do not create an empty supervisory layer. If such a run later needs workers, the Night Manager requests Shift Supervisor activation before dispatch.
- The Night Manager gives the Shift Supervisor the accepted intent, governing artifacts, execution boundaries, authority limits, current checkpoint, and expected reporting contract. The Shift Supervisor decomposes that mission into bounded worker assignments.
- The Shift Supervisor may resolve routine execution choices within the accepted contract. It escalates when evidence conflicts with governing intent, a choice would reinterpret or materially expand scope, recovery cannot reconcile state, an unsafe condition appears, or work cannot show credible movement toward convergence.
- The Night Manager may continue, run a bounded recovery experiment, redirect execution within accepted scope, adjust scope within authority already delegated for autonomous execution, or stop and preserve state. During design it involves the user in material judgment. During autonomous execution it decides and reports every decidable within-authority choice, including go or no-go and scope adjustments, and involves the user only for new authority, a design-phase decision, or a genuinely blocked path. Its discretion lies in classifying that boundary and selecting among authorized actions, not in interrupting an autonomous run for a decision it already owns.
- If a Shift Supervisor cannot be recovered or replaced during non-terminal execution, the deterministic controller fences the supervisor generation and atomically makes every active attempt inactive with a persisted `revoked`, `interrupted`, `isolated`, completed `read-only-result-fenced`, or `read-only-fence-pending` disposition before the Night Manager chooses disposition. Every external revocation, interruption, or isolation carries proof bound to the attempt identity; `read-only-fence-pending` checkpoints and stops without replacement until `read-only-fenced(A)` is complete. If durable inactivation and required proof cannot both be verified, no new mutation or supervisor activation occurs and the run checkpoints, stops, and escalates. After a verified fence, the Night Manager may request a new supervisor when the lifecycle phase permits it, or checkpoint and stop or escalate; it never takes over worker edits directly.
- Lifecycle completion, deliberate stop, and abandonment share one shutdown ordering. The deterministic controller closes supervision through the replayable terminal-closure state machine, preserving existing terminal outcomes, classifying and terminalizing outstanding work, revoking active attempts, and producing a closure evidence packet without depending on a live Shift Supervisor. The Night Manager completes final acceptance or abandonment disposition and the morning report from that packet while its authority remains active; the final lifecycle transition then makes the Night Manager generation and lifecycle run identity inactive before the terminal outcome is acknowledged.

## Context and communication flow

The hierarchy protects the Night Manager's context by changing what crosses each boundary:

- Workers receive role instructions, one bounded assignment, relevant artifacts, acceptance criteria, and the evidence required for completion. They do not receive the entire lifecycle transcript by default.
- Workers return detailed results and evidence to the Shift Supervisor.
- The Shift Supervisor keeps routine scheduling, retries, deduplication, and worker dialogue below the executive boundary. It sends the Night Manager compact executive packets with direct evidence references instead of raw worker transcripts.
- The Night Manager receives enough detail to judge intent, risk, convergence, and authority without reconstructing worker mechanics. It sends the user the result, material decisions, risks, experiments, and routing choices in the morning report.

## Executive packets and revise convergence

Executive packets are event-driven at lifecycle gates and exceptions. Revise runs add convergence reporting because a long wave can remain locally active while the lifecycle drifts or stalls.

- A revise run reports its starting convergence baseline, every completed wave, material fingerprint invalidation or reactivation, holistic-verifier start and result, and any detected stall, regression, or spinout condition.
- An unfinished revise wave sends a timed executive packet when it has run for one hour and then hourly while that same wave remains active. A wave that converges within its first hour sends only its ordinary completion packet and no extra timed report.
- Every convergence packet identifies the lifecycle run identity, current subordinate review-run identity, artifact fingerprint, wave and round, applicable cells by certified, stale, active, or blocked state, findings by verified and unresolved disposition, certifications invalidated by fixes, reactivation causes, verifier eligibility, direction since the prior packet, and the next concrete convergence event.
- Packets report observable state rather than speculative percentages, completion dates, or worker activity presented as progress.
- Exact intervention thresholds remain intentionally unsettled. The Night Manager nevertheless owns the judgment and responsibility to stop, redirect, or elevate work that is spinning out of control, regressing, repeatedly invalidating itself, consuming effort without credible progress, or unable to show signs of convergence over an extended period.
- An immediate safety, authority, or repository-integrity violation bypasses periodic reporting. The Shift Supervisor pauses safe-to-stop activity, preserves evidence, and wakes the Night Manager for disposition.

## Compaction, crash, and resume

Recovery reconstructs a logical role from durable evidence rather than trusting conversational memory. Clean recovery continues automatically without asking the user. A replacement Shift Supervisor reports a clean reconciliation to the Night Manager as information and does not wait for acknowledgment before continuing.

The durable checkpoint must be sufficient to recover:

- the mission, accepted governing decisions, governing artifact identities, lifecycle run identity and active state, current subordinate work or review identity when one exists, current Night Manager authority generation and role state, and current Shift Supervisor generation with role state (`absent`, `active`, `fenced`, `closing`, or `closed`);
- the lifecycle phase, last completed gate, current convergence state, and next safe action;
- material Night Manager rulings and the current authority boundary;
- every worker assignment, its monotonic assignment sequence, lifecycle run identity, subordinate work identity when applicable, assignment fingerprint, open or terminal state, execution mode (`read-only`, `shared-mutable`, or `isolated-mutable`), terminal-outcome classification and complete terminal-transition payload when terminal, current attempt identity and active state, worker identity, supervising role generation, mutation authority, isolation identity, or explicit read-only state as applicable, fencing disposition and proof or explicit pending-proof state when the supervisor is fenced or closing, owner, evidence, and supersession state;
- unresolved escalations, experiments, second-opinion consultations, report obligations, the terminal closure packet's absent or present state with its complete payload when present, and terminal Night Manager progress through closure consumption, disposition, report-packet persistence, complete delivery substate, append-only user-disposition sequence, and final deactivation;
- every partially persisted transition once the concrete write schema is chosen.

Checkpoint refresh occurs at assignments, material decisions, applied fixes, completed evidence-producing boundaries, escalation disposition, experiment transitions, and lifecycle gates. A pre-compaction checkpoint improves fidelity when the host provides warning, but recovery correctness must not depend on receiving that warning.

The lifecycle run identity names one autonomous Nightshift lifecycle. It is created active before the first checkpoint, remains immutable across stages, compaction, crash, and role replacement, and becomes inactive through the shared completion, deliberate-stop, or abandonment shutdown transition. A later lifecycle receives a new identity. It contains no stage-specific artifact path, scope, base commit, or fingerprint. Each revise or other work stage retains its existing frozen work identity as a child of the lifecycle identity; a standalone revise run creates one lifecycle identity and one subordinate review identity together. The initial Night Manager generation is created active with the lifecycle; the Shift Supervisor generation is explicitly absent until activation, initialized active on activation, moved to `fenced` with an inactive generation when failure fencing succeeds, atomically replaced by the next active generation when permitted, and made inactive when supervision closes. All role generations and worker attempt identities are scoped to the lifecycle run identity and cannot cross into another lifecycle.

`read-only-fenced(A)` is the shared proof contract for read-only attempt `A` across failure replacement, terminal closure, and restart. It requires `A` durably inactive, result admission guaranteed to reject `A`, mutation authority explicitly absent, promotion authority explicitly absent, and either a worker-control or interruption identity with its receipt or an explicit proof that the host exposes no such primitive. Until every predicate is durable, the disposition is `read-only-fence-pending`; only the complete proof may set `read-only-result-fenced`, permit replacement, permit restart, or satisfy closure.

Fresh lifecycle creation and role-generation acquisition are deterministic controller-owned authority transitions rather than role-issued side effects. Fresh creation validates the expected absent lifecycle and generation state, then atomically creates the active lifecycle identity, initial active Night Manager generation, and first checkpoint. Initial Shift Supervisor activation is one atomic compare-absent-and-create transition that validates an active lifecycle phase permitting worker orchestration and the expected absent supervisor generation before creating it active. Normal replacement validates the active lifecycle, a lifecycle phase and role state permitting replacement, and the exact expected generation as both current and active, then atomically makes that generation inactive and creates the next active generation. Failure fencing is a separate controller transition that validates the exact current active supervisor generation, atomically makes it inactive, records supervisor state `fenced`, makes every active attempt inactive, and persists the mode-specific complete proof or pending disposition. Replacement from `fenced` validates the exact active lifecycle identity and state, a non-terminal worker-orchestration phase, exact fenced inactive generation, and complete durable proof for every attempt affected by that failure-fencing transition, including `read-only-fenced(A)` for each affected read-only attempt, before creating the next active generation. Night Manager replacement remains permitted during terminal shutdown only while its generation is active and only to complete shutdown and the morning report. Terminal shutdown forbids supervisor activation and replacement, and a closing or closed supervisor cannot be replaced. A failed comparison changes nothing and cannot produce clean recovery. The controller returns the new authority identity only after the transition commits; every subsequent role-issued side effect uses the ordinary current-active-generation guard.

### Terminal closure state machine

Terminal shutdown is controller-owned and continues from durable state even when the Shift Supervisor crashes. Entering shutdown blocks new dispatch, activation, and supervisor replacement. A Night Manager replacement during shutdown may wait for or consume controller closure, make final disposition, and deliver the morning report; it cannot restart worker operations.

| Prior supervisor and closure state | Controller transition | Durable state after the successful write and deterministic resume |
|---|---|---|
| `absent`, packet absent, zero assignments | Record no-supervision closure | Supervisor stays absent; the closure packet records lifecycle identity, an explicitly absent supervisor generation, zero assignment outcomes, explicit evidence absence, and unresolved or missing-work state; controller resume selects the next row. |
| `absent`, packet present, zero assignments | Replay no-supervision closure | Exact packet equality is an idempotent no-op and the Night Manager may proceed to final disposition and reporting; any mismatch fails closed. |
| `active`, packet absent | Begin terminal closure fencing | Supervisor becomes `closing`; ordinary supervisor and worker admission is rejected; the write records every affected attempt identity and execution mode, makes each attempt durably inactive, and records its required `revoked`, `interrupted`, or `isolated` proof, complete `read-only-result-fenced` proof, or explicit mode-specific pending disposition including `read-only-fence-pending`; controller resume selects the next row. |
| `fenced`, packet absent | Begin terminal closure after failure | Supervisor becomes `closing`; prior authority and attempts remain inactive; existing per-attempt dispositions and proofs carry forward; controller resume selects the next row. |
| `closing`, packet absent, pending fencing proofs | Complete the lowest-sequence pending fence | Persist mode-specific proof bound to the attempt identity: mutation-authority revocation or interruption for `shared-mutable`, isolation plus promotion-authority revocation for `isolated-mutable`, or the complete `read-only-fenced(A)` proof for `read-only`; controller resume repeats this row. Missing or unverifiable required proof performs no terminalization and fails closed. |
| `closing`, packet absent, all fencing proofs durable, open assignments present | Terminalize the lowest-sequence open assignment | That assignment carries its complete terminal-transition payload and inactive attempt; untouched assignments remain open but frozen; controller resume repeats this row. |
| `closing`, packet absent, all fencing proofs durable, no open assignments | Persist closure evidence | Supervisor remains `closing`; one closure packet records lifecycle identity, supervisor generation, every assignment outcome, every final evidence identity or explicit absence, all fencing dispositions and proofs, and unresolved or missing work; controller resume selects the next row. |
| `closing`, packet present, no open assignments | Close supervision | Supervisor becomes `closed`, its generation becomes inactive, and the closure packet remains available to the Night Manager. |
| `closed`, packet present, no open assignments | Replay closure | Exact closure-packet equality is an idempotent no-op; any mismatch fails closed. |
| Any other combination | Reject malformed closure state | No mutation occurs; recovery fails closed with the observed supervisor, packet, and assignment states. |

The controller may use the still-live supervisor as an evidence source before or during the `active` to `closing` transition, but closure correctness depends only on evidence already made durable. A supervisor failure at any row loses no committed evidence and cannot block progress through the remaining rows.

### Terminal Night Manager sequence

Closure is complete only when the supervisor is `absent` with a valid no-supervision packet and zero assignments, or `closed` with a valid closure packet, no open assignments, and complete mode-specific fencing proof for every affected attempt. Let `G` be the exact current Night Manager generation. `active-terminal(G)` means lifecycle phase `terminal-shutdown`, lifecycle state active, and Night Manager generation `G` current and active. `finalized(G)` means the same lifecycle identity inactive with that exact generation `G` inactive. The complete delivery substate contains the current delivery identity and monotonic attempt sequence, state (`not-started`, `in-flight`, `delivery-uncertain`, `delivered`, or `user-waived`), immutable append-only attempt history, receipts, channel capability and lookup evidence, and append-only user-disposition records keyed by disposition sequence and target delivery attempt. `not-started` requires an explicitly absent current delivery identity and empty attempt, receipt, capability-evidence, and user-disposition collections. Every table reference to a delivery state compares this complete substate, not the state label alone. The terminal action classifier evaluates the requested action together with the complete tuple `(closure, consumption, disposition, report packet, complete delivery substate, lifecycle phase and state, Night Manager generation identity and state)`, so first writes, replays, later actions, and malformed states are disjoint.

| Requested action and complete durable predecessor | Durable result and resume |
|---|---|
| `consume-controller-closure`; closure complete, consumption absent, disposition absent, report absent, delivery `not-started`, authority `active-terminal(G)` | Persist the exact consumed closure-packet identity. |
| `consume-controller-closure`; closure complete, consumption present, disposition absent, report absent, delivery `not-started`, authority `active-terminal(G)` | Exact consumed-packet replay is a no-op; a different packet fails closed. |
| `final-disposition`; closure complete, consumption present, disposition absent, report absent, delivery `not-started`, authority `active-terminal(G)` | Persist the final disposition and immutable morning-report packet together with one stable report identity; delivery substate remains `not-started`. |
| `final-disposition`; closure complete, consumption present, disposition present, report present, delivery `not-started`, authority `active-terminal(G)` | Exact disposition and report replay is a no-op; any payload mismatch fails closed. |
| `prepare-report-delivery`; closure complete, consumption present, disposition present, report present, delivery `not-started`, authority `active-terminal(G)` | Create the first monotonic delivery identity and persist delivery `in-flight` before any external send. |
| `deliver-morning-report`; closure complete, consumption present, disposition present, report present, delivery `in-flight`, authority `active-terminal(G)` | Use channel idempotency or identity lookup before send or retry; confirmed delivery persists its receipt and `delivered`, while an indeterminate outcome persists `delivery-uncertain`. |
| `resolve-report-delivery`; closure complete, consumption present, disposition present, report present, delivery `in-flight` or `delivery-uncertain`, authority `active-terminal(G)` | Query or retry only through a channel mechanism that proves the stable delivery identity; persist `delivered` with its receipt when proved, otherwise remain `delivery-uncertain` and stop for user disposition. |
| `deliver-morning-report` or `resolve-report-delivery`; closure complete, consumption present, disposition present, report present, delivery `delivered`, authority `active-terminal(G)` | Exact stable delivery identity and receipt replay is a no-op; any mismatch fails closed. |
| Controller-owned user disposition; closure complete, consumption present, disposition present, report present, current delivery attempt `delivery-uncertain` with no disposition record targeting that attempt, authority `active-terminal(G)`, immediate explicit user response bound to the report digest and complete delivery substate | Append the next monotonic user-disposition record keyed to the uncertain attempt and persist exactly one authorized result: `delivered` with out-of-band confirmation receipt, `in-flight` with a new monotonic capable-channel delivery identity while preserving prior attempt and disposition history, or `user-waived` with explicit authority to terminate without confirmed delivery. |
| Controller-owned user-disposition replay; closure complete, consumption present, disposition present, report present, target delivery attempt has a disposition record and current delivery substate reflects its persisted confirmation, reroute, or waiver, authority `active-terminal(G)` | Exact complete decision-payload, target-attempt identity, append-only histories, and resulting-substate equality is a no-op; any mismatch fails closed. |
| Controller finalization; closure complete, consumption present, disposition present, report present, delivery `delivered` or `user-waived`, authority `active-terminal(G)` | Compare-and-replace that exact phase, lifecycle, generation, delivery state, and user authority when waived; atomically make generation `G` and the lifecycle inactive, then acknowledge the lifecycle outcome. |
| Controller finalization replay; closure complete, consumption present, disposition present, report present, delivery `delivered` or `user-waived`, authority `finalized(G)` | Verify the complete tuple including the same finalized generation identity `G`, receipt when delivered or explicit user authority when waived, perform no mutation, and acknowledge the already-committed lifecycle outcome; any mismatch fails closed. |
| Any other requested action or state tuple | No mutation or external send occurs; recovery reports the complete observed tuple and fails closed. |

Persisting `in-flight` before the external send makes a crash distinguishable from a never-attempted delivery. Recovery never blindly resends from `in-flight`: it uses channel idempotency or identity lookup, and a channel without either capability maps the attempt to `delivery-uncertain`. The user-disposition presentation includes the immutable report packet and complete delivery substate where the user can actually inspect them before choosing confirmation, reroute, or waiver; when no user is available, the lifecycle remains active and `delivery-uncertain`. A reroute appends a new attempt with no disposition record targeting it, so a later uncertainty can append another decision rather than being blocked by earlier dispositions. Night Manager replacement during terminal shutdown resumes from this table and receives no broader action authority. The final controller transition refuses to deactivate the lifecycle until closure consumption, final disposition, immutable report persistence, and either confirmed report delivery or explicit user waiver are all durable.

Every replacement Night Manager, Shift Supervisor, or worker follows a role-specific bootstrap:

1. Stop mutations until its state is reconciled.
2. Reload global, project, plugin, and role-specific instructions.
3. Read the governing artifact and accepted decision surface relevant to the role.
4. Read the latest durable checkpoint and verify repository state, artifact fingerprints, lifecycle run identity, subordinate work identity when present, and the role's recorded authority or attempt identity.
5. Before any role-issued write, a replacement Night Manager or Shift Supervisor requests the controller-owned compare-and-replace transition that acquires the next role authority generation and fences its predecessor. A replacement worker validates the current assignment attempt and its mutation authority or isolation boundary.
6. Reconstruct assignments, authority, unresolved decisions, evidence obligations, and the next safe action against the post-acquisition state.
7. Record a compact reconstructed-state declaration before resuming.

After controller-owned creation or acquisition, one ordered admission classifier covers every role-issued side-effecting surface, including repository mutation, durable-state writes, dispatch, interruption or worker-control actions, and external tool actions. Controller-owned authority and terminal transitions use their dedicated compare-and-replace predicates before this classifier. Every role-issued action then requires an active lifecycle, current active role generation, lifecycle phase permitting that action class, and role state permitting that action class before action-specific identity or authority checks run. Generation acquisition also revokes, interrupts, or isolates side-effecting actions already launched by the prior instance. Completion, deliberate stop, abandonment, and supervision closure revoke the affected active states through their controller-owned transitions before acknowledging the outcome. Recovery is not clean and cannot continue automatically when the host cannot enforce that boundary.

The classifier maps every non-terminal execution stage to the operational policy: ordinary Night Manager actions are allowed, ordinary Shift Supervisor and worker actions additionally require supervisor state `active`, and dispatch or restart also requires a phase that permits worker orchestration. In `terminal-shutdown`, ordinary supervisor and worker actions, results, dispatch, and restart are rejected; the Night Manager allowlist is only `consume-controller-closure`, `final-disposition`, `prepare-report-delivery`, `deliver-morning-report`, and `resolve-report-delivery`, each guarded by the Terminal Night Manager sequence's exact complete state tuple. In the terminal lifecycle state, every role-issued action is rejected. No fallthrough selects a more permissive policy when the lifecycle phase, role state, action class, or predecessor state is missing or unknown.

A replacement Shift Supervisor reconnects to a live worker only when the lifecycle is active, the new Shift Supervisor generation is current and active, the assignment is open, the attempt is active, and the lifecycle identity, subordinate work identity when present, assignment fingerprint, attempt identity, and worker identity all match the current assignment record. Successful reconnection atomically rebinds that attempt to the new supervising generation before worker activity resumes. If reconnect fails, a read-only assignment may restart under a new monotonically increasing attempt identity only after `read-only-fenced(A)` is durable for the prior attempt and the durable assignment record supersedes it. A prior `shared-mutable` attempt must be durably inactive, stale-result-fenced, and carry verified revocation or interruption of its mutation authority before any replacement attempt, shared or isolated, becomes active. A prior `isolated-mutable` attempt must be durably inactive, remain confined to its recorded isolation boundary, and carry verified revocation of its promotion authority before a new isolated attempt becomes active. If the prior mode's complete safeguard is unavailable, the Shift Supervisor pauses and escalates rather than activating replacement work.

An open assignment receives its monotonic assignment sequence and creates its initial active attempt identity before first dispatch. Restart is a separate two-boundary process: the prior attempt first becomes durably inactive and satisfies its complete execution-mode fencing proof; only afterward may one controller compare-and-replace transition validate the exact inactive proved attempt, open assignment, active supervisor generation, permitted worker-orchestration phase, and assignment identity, then atomically supersede that attempt and create the next active attempt. The closed mode-transition set is `read-only` to `read-only`, `shared-mutable` to `shared-mutable` or `isolated-mutable`, and `isolated-mutable` to `isolated-mutable`; every other transition fails closed. After the admission classifier selects the operational policy and confirms supervisor state `active`, the shared worker predicate requires a current active supervising generation, open assignment, active attempt, and matching lifecycle run identity, subordinate work identity when present, assignment fingerprint, attempt identity, and recorded worker identity. Direct mutation additionally requires current mutation authority. Isolated promotion additionally requires the recorded isolation identity and current promotion authority. Worker-result admission requires the shared predicate but no mutation authority, so a read-only attempt can report normally. A new worker-reported completion or failure first validates the shared predicate; cancellation or abandonment during active supervision also validates the initiating role's authority. Once supervision is `closing`, controller-owned closure terminalization instead validates the active lifecycle, exact closing supervisor generation, open frozen assignment, current attempt when present, and complete assignment identity tuple without requiring ordinary role or worker authority. The selected branch then atomically persists the complete terminal-transition payload, makes the assignment terminal, and makes its active attempt inactive before acknowledging the transition. That payload contains the terminal outcome, lifecycle and subordinate work identities, assignment fingerprint, terminal attempt and worker identities or their explicit absent values, final evidence identity or an explicit absent value, and transition authority generation. Supervision closure preserves an already-terminal outcome and applies `stopped-at-supervision-closure` only to outstanding open work.

Terminal replay is a separate deterministic-controller branch selected before normal admission. When the assignment is already terminal, it compares the complete persisted payload and returns an idempotent no-op only on exact equality without requiring the assignment or attempt to be active; any mismatch, including outcome, evidence, attempt, worker, or authority identity, fails closed. Worker results always enter through worker-result admission and cannot invoke terminal replay. Late results and mutations from an inactive lifecycle, role, assignment, or attempt are rejected even when every identifier still matches. Tool failure or ambiguous status maps to the most cautionary available state, never to clean completion.

Recovery is clean only when governing identities, repository state, durable transitions, authority, and assignment states reconcile without conflict. Any mismatch without a deterministic recovery branch stops mutation and reaches the next authority level. The exact state schema, write ordering, and durable state after each successful write remain uncovered until the implementation mechanism is selected; graduation must supply the complete crash-state matrix rather than inferring it from this role-level contract.

## Night Manager experiments

The Night Manager may devise, authorize, and direct bounded experiments without advance user approval when every variant remains within the accepted authority, preserves mandatory gates, and does not place the primary result at material risk. Experiments with material outcome, permission, publication, destructive-action, or user-intent risk require user authority before execution.

- The Night Manager records a hypothesis, control and treatment when comparable arms exist, assignment method, measurements, stop conditions, cost boundary, contamination boundary, rollback, and the result needed to decide the hypothesis.
- The Shift Supervisor executes the experiment, keeps arms isolated, fingerprints every variant, and preserves enough evidence to distinguish treatment effects from task differences. A separate evaluator judges outcomes when practical.
- An experiment requires an active Shift Supervisor only when it dispatches or coordinates workers. If none exists, the Night Manager defines a real bounded worker assignment, requests activation through the controller-owned compare-absent-and-create transition, and leaves dispatch to the activated Shift Supervisor. A genuinely worker-free, one-step executive probe may be performed directly by the Night Manager when it needs no operational loop and does not threaten executive-context preservation. Worker-free experimental work that is repeated, tool-driven, comparative, or otherwise too operational for the Night Manager must be converted into a bounded worker assignment or deferred; it never activates an empty Shift Supervisor.
- Instruction experiments use temporary fingerprinted overlays rather than silently rewriting canonical Night Manager, Shift Supervisor, or worker instructions during the run.
- A/B-style control is preferred when comparable work exists. When it does not, the Night Manager may use a weaker design but must report its confounders and may conclude that the evidence is inconclusive.
- Low-risk variants may participate in real work only when every arm remains compliant and useful. A variant that could jeopardize the primary result runs in shadow mode or waits for user authority.
- Experimental output never promotes itself. The morning report states the hypothesis, method, sample, observed effects, costs, limitations, side effects, conclusion, and recommendation, then offers routing such as adopt, repeat, revise, track, or discard for the user to decide.

The neighboring [Controller-owned session experiment ledger](controller-owned-session-experiment-ledger.md) draft owns the durable evidence-record mechanics. This umbrella owns the Night Manager's authority to initiate experiments, the Shift Supervisor's execution role, the safety boundary, and morning-report responsibility.

## Same-role second opinions

Until Nightshift has a formal cross-host or cross-provider consultation contract, managerial second opinions optimize for comparable general ability and predictable cost rather than claiming a qualitatively different error distribution.

- A Night Manager seeking a second opinion creates a fresh Night Manager peer using the same role profile, model route, and intended reasoning tier as itself. In the intended Claude Code mapping, Fable consults Fable.
- A Shift Supervisor seeking a second opinion creates a fresh Shift Supervisor peer using the same role profile, model route, and intended reasoning tier as itself. In the intended Claude Code mapping, Opus consults Opus.
- Workers request managerial help through the Shift Supervisor rather than creating Night Manager or Shift Supervisor peers.
- The advisory peer receives applicable instructions, governing context, deciding evidence, and a neutral question, but not the requester's preferred conclusion or rationale. It has no authority to mutate state or decide for the requester.
- Responsibility stays with the requester. A Shift Supervisor that cannot resolve disagreement within its authority escalates to the Night Manager. A Night Manager decides within delegated authority or involves the user.
- If a matching peer cannot be created, the Shift Supervisor escalates rather than silently substituting another model. The Night Manager either proceeds cautiously when the decision permits it or records the unavailable consultation and stops or involves the user when independent judgment is necessary.

This temporary policy is distinct from [Second-opinion gates](second-opinion-gates.md). That feature owns future lifecycle checkpoints whose active ingredient is a different model family and whose channels include another provider or host. Once a formal consultation interface can discover capabilities, transfer bounded context, protect privacy, account for cost, recover failures, and normalize results, Nightshift must revisit managerial second-opinion routing explicitly. The later policy should seek qualitative improvement from a differently trained system rather than merely buying another sample of the same capability.

## Model routing and host boundary

The role contract is host-neutral even though the initial desired Claude Code mapping is Night Manager to Fable and Shift Supervisor to Opus. The Night Manager role calls for the strongest available executive judgment, while the Shift Supervisor role calls for strong, predictable orchestration at a lower cost than the executive seat. The host adapter should resolve those semantic roles to models it actually exposes, freeze the resolved map for the lifecycle run identity, and avoid silent managerial downgrades. The exact semantic role names, availability probe, effort settings, fallback rules, and cost evidence remain open until design work can verify the supported host surfaces.

Workers may use models appropriate to their bounded assignments. That worker routing does not change the same-role peer rule for Night Managers and Shift Supervisors.

## Morning report

The Night Manager, not the Shift Supervisor, delivers the morning report. It includes:

- the outcome and its verification evidence;
- progress toward convergence and any material stall, regression, or stop decision;
- executive decisions, deviations, scope adjustments, and unresolved risks;
- crash or compaction recovery events that affected confidence or work identity;
- experiments with their design, results, limitations, recommendation, and requested routing;
- second-opinion disagreements or unavailability that materially affected a decision;
- work deliberately stopped, deferred, superseded, or left for the user.

The report remains concise and decision-ready. Detailed worker transcripts stay behind evidence references unless the user requests them or they are necessary to support a material claim.

## Open design questions before graduation

- Define the exact observable predicate that activates a Shift Supervisor and whether standalone revise runs, handover runs, and other worker-bearing workflows share one activation service.
- Define task-and-dispatch scratch ownership and deferred cleanup: bind each directory to its lifecycle run, assignment, and attempt identities; validate the physical root identity before reuse or cleanup; discover ownership across sessions; and reclaim abandoned directories without racing a live or replacement supervisor. Automatic cleanup remains excluded until this contract is complete.

Define the lifecycle-stable outer identity and its binding to existing stage-scoped work identities, atomic authority-generation acquisition, manager and worker fencing, and isolated-attempt promotion, then enumerate creation, initialization, refresh, invalidation, scope, bounds, malformed or stale behavior, every reader, every successful-write state, and deterministic resume from each partial transition.

- Define semantic model roles and the initial Fable and Opus mappings against actual host model surfaces, including unavailable-model behavior and cost controls.
- Calibrate qualitative spinout signals and numeric intervention baselines against real revise traces close to implementation. Hourly long-wave reporting remains fixed while those thresholds are tuned.
- Define experiment budgets, arm assignment, contamination controls, evaluator independence, and what evidence is sufficient for the Night Manager to call a result directional, conclusive, or inconclusive.
- Define how Workflow acceleration and manual host adapters preserve the same Night Manager and Shift Supervisor authority, packet, recovery, and same-role consultation contracts.
- Plan the terminology migration so user-facing `controller` references become `Night Manager` while deterministic controller code and historical records remain unambiguous.
