# Review orchestration tests

Feature: turn the revise review engine's wave, convergence, and completion decisions into executable, fixture-tested invariants. This file is the authoritative design record.

**2026-08-20 re-derivation note:** the invariant set below was re-derived from the shipped wave-convergence lifecycle in `internal/revise/SKILL.md`, which removed phases, replacing the phase-model transition matrix this file carried from the 2026-08-11 migration. The extraction purpose and module shape are unchanged.

## What it does

The deterministic backlog parser (`skills/ready/ready.js`) has strong behavioral test coverage via `ready.test.js`. The review engine is the more consequential component by overall quality impact, and today it has none at the orchestration level: the wave/convergence/adjudication decisions live only as prose in `internal/revise/SKILL.md`, restated by the controller every cycle. `revise-round.test.js` covers one round's Workflow dispatch (concurrency, reviewer-to-skeptic fan-out, result normalization, fingerprint validation). It does not cover the machinery that decides whether a cell certifies or reactivates, how the staleness sweep resolves an all-inactive boundary, when the verifier may launch or stamp, or whether the run completes.

This feature extracts those orchestration decisions into a deterministic, importable Node module with a `ready.test.js`-style fixture suite, driven by mocked reviewer and skeptic results rather than agent dispatch. It promotes the workflow rules from prose into fixture-bound executable invariants: an invariant change on either side must land as a matching module-and-fixture update in the same change set, so a regression introduced through the repository surfaces as a failing fixture or a visibly incoherent change set at review or CI time instead of as silent behavior drift. Design decisions confirmed during backlog migration on 2026-08-11, restated in wave terms after the 2026-08-20 re-derivation:

- **Substrate**: extract pure transition logic; SKILL.md prose stays authoritative for execution, the module is a consultable spec-check that binds the invariants.
- **Boundary resolution**: encode the full all-inactive evaluated-boundary rule, in order: the blocked-boundary guard is a precondition checked before any transition (a pending controller mutation, a pending user request, a non-`none` agreement boundary, or an absent current agreement-gate result resolves to `blocked` with no transition and no dispatch); then the staleness sweep runs first among the transitions (reactivation, N/A promotion and demotion, empty-applicable-set failure); wave convergence without a current stamp launches the verifier; wave convergence with a current stamp enters post-review.
- **Certification span**: a cell is inactive exactly while it holds a certification; within a run's normal flow only a staleness-sweep boundary (reactivation on fingerprint inequality, or demotion to N/A) or a scope-remap boundary clears a certification, and the user-authorized `Restart run` clears every certification outside that flow. (The queued durable-scope-anchor feature adds a third in-flow trigger; see Relationship to neighboring features.)
- **Cross-cell mutation**: a sibling's accepted edit preserves every cell's current state until the sweep; the sweep is the global re-review barrier. One invariant with both halves tested.
- **Rejected findings**: the current disposition rule set (every finding-bearing round keeps the cell active, including an all-refuted or acknowledgement-only round; only a later explicit clean LGTM certifies it; no side effects on other cells).
- **Execution failure**: the state-derived run-level fail-closed contract with explicit disposition, cap preflights and fixtured terminal-state exits included; environment-level failure routes (dispatch and checkpoint I/O) stay controller-owned by design.
- **Completion invariant**: the stamp conjunction (wave convergence and a verifier stamp over the same current fingerprint), tested to return false in every non-completing combination, with cap asymmetry (a cap-forced end never completes) absolute.

## The substrate: a pure transition module

Extract the review-state transition decisions into one bundled Node module, mirroring the `ready.js` / `ready.test.js` pattern: deterministic, importable, no test framework, exit code 1 on failure. The transition rules' testable form lives only in the module (no fixture or helper hand-approximates them elsewhere), while SKILL.md prose stays authoritative for how the controller executes the run; the module is the single authority for the transition decisions in their executable form and the exact surface the tests bind to, and the same-change-set convention below keeps the two representations aligned.

Why a consultable spec-check rather than controller-executed code: runtime execution is feasible (the engine already loads a Node module at round boundaries for fingerprinting), but rewiring the shipped controller's boundary execution to act on module output is a behavior change with its own review surface, while this feature's goal is to bind the invariants without changing engine behavior. Executing the module inside the loop was therefore considered and rejected for this slice; it is the natural direction for the Review host adapters slice of [Agent-host-agnostic Nightshift](agent-host-agnostic-nightshift.md), which can wrap this same module behind a host adapter. What keeps prose and module from drifting apart is the repository's cross-file consistency convention made specific here: any lifecycle-invariant edit to `internal/revise/SKILL.md` and the module's transition table or fixtures land in the same change set. The convention is CI-backed where a sentence is pinned and review-backed elsewhere: `revise-round.test.js` already prose-pins exact SKILL.md sentences with mutation probes (the dispatch-guard rule and the checkpoint contract), so a SKILL.md-only edit to a pinned sentence fails CI today. This module's fixture suite extends that shipped technique to the lifecycle sentences whose rules it encodes; a SKILL.md-only edit to unpinned prose remains the review convention's catch. Each pinned sentence lives in exactly one suite, so the dispatch-guard and checkpoint-contract pins stay in `revise-round.test.js` and this suite pins only the sentences it newly encodes. That pinned set is enumerated here and closed, each sentence identified by its rule and pinned verbatim from the live file: (1) the limits sentence (30 rounds, 10 verifier launches, 3 execution-repair launches); (2) the `Launch verifier` evaluated-or-idle precondition; (3) the post-review stamp-conjunction sentence; (4) repair safety rule 1 (no deactivation without a clean LGTM with a concrete nonblank rationale); (5) the `Status: failed` never-auto-resumes sentence; (6) the cap-asymmetry sentence. The demotion-only-sweep sentence was deliberately dropped from the set by the membership criterion below: its rule is densely bound by behavioral fixtures (the demotion-only fall-through cases), so a meaning-changing rewording already forces a fixture-visible module update. Fixture cases: each pinned sentence has one pin-plus-mutation-probe case that reads `internal/revise/SKILL.md`, asserts the sentence verbatim, and proves the assertion bites by mutating it, the exact technique `revise-round.test.js` ships; an edit to any pinned sentence fails CI. The membership criterion, stated so future encoders can apply it: verbatim pins are brittle against innocuous rewording, so pinning is reserved for sentences whose silent drift the behavioral fixtures cannot catch, the authority statements and caps (limits, launch preconditions, the stamp conjunction, the safety and terminality rules). A rule already bound by dense state-in/result-out fixtures is deliberately unpinned: rewording it without changing meaning is free, and changing its meaning forces a module-and-fixture update the same-change-set convention carries. A neighbor that encodes a new SKILL.md sentence applies the same test: pin it only when no behavioral fixture would catch its drift.

The module answers the orchestration questions as pure functions over the review state:

- how the all-inactive evaluated boundary resolves (blocked, sweep reactivation, verifier launch, post-review entry, or failure);
- how certification, the staleness sweep, and a scope-remap change affect each cell's active, inactive, or N/A status;
- how a rejected finding affects a cell's convergence;
- how each verifier boundary disposes the stamp (stamp, relaunch at the same fingerprint, or return to the sweep);
- how execution failure and limit exhaustion terminate a run, and how the terminal states are exited;
- whether the run can complete.

The surface names one pure function per decision, each returning a closed discriminated result:

- `resolveBoundary(state, applicability, gateCurrent, remap)` -> `{transition: 'blocked'}`, `{transition: 'reactivate', activated}`, `{transition: 'launch-verifier'}`, `{transition: 'post-review'}`, or `{transition: 'failed', failure}`, where every non-`blocked` result also carries `promotions`, `demotions`, `preserved` (all possibly empty), and `clearStamp` (true when a reconciled scope-map change requires `Verifier stamp` cleared to `none`), so demotion-only sweeps and remap effects are observable by the caller on the fall-through transition. `activated` and `promotions` are lists of cell IDs; `demotions` and `preserved` are lists of `{cellId, reason}`, echoing each freshly evaluated nonblank reason: `preserved` carries the cells whose not-applicable verdict is unchanged (SKILL.md's third re-evaluation outcome, whose reason is re-encoded fresh even when the status holds), so the boundary rewrite takes every N/A reason from the result without the controller re-reading `applicability`. `applicability` is the controller's freshly evaluated N/A applicability verdicts, exactly one per cell in the state (per cell: applicable or not, with a nonblank reason for a not-applicable verdict); the applicability judgment itself is controller-owned and the module owns what follows from it. A set missing a cell or naming an unknown cell is refused under the input contract. `gateCurrent` is the caller's assertion that a current successful entry or post-mutation agreement-gate result exists; the gate result lives only in volatile agreement context the checkpoint cannot carry, so the module receives it as an input and a false value resolves to `blocked`. `remap` is `null` or the not-yet-reconciled scope-map change this boundary reconciles, shaped as `{affected}` where `affected` is a nonempty list of the cell IDs the controller classified as affected (whole-scope and cross-cutting cells on any map change, local cells on slice-membership change). Deriving `affected` inside the module was considered and rejected: slice-membership change detection requires comparing the pre-change and post-change resolved scope maps, and the module receives one state, not that map pair, so the classification stays controller-owned like applicability. `remap` models only cells present in the state it receives: cell-set membership changes at a map change (minting, retirement, and split or merge with the predecessor-lineage certification inheritance `wave-lifecycle.md` records as the one deliberate exception to membership-change clearing) are the controller's three-table refresh, applied to the state before the reconciling boundary is resolved, so the module sees the post-membership cell set, `affected` names only surviving cells whose certification the shipped rule clears, and an inherited certification on a minted split child arrives in the state as an ordinary certification the remap effects deliberately do not clear. Encoding the minting and inheritance rules in the module was considered and rejected for the same reason as deriving `affected`: they read the pre- and post-change resolved map pair and the predecessor lineage the state projection does not carry. The unreconciled-ness has a named durable source, so `remap` survives a resume: the controller derives it fresh at every boundary by comparing the checkpoint's persisted scope map against the freshly resolved current map. That derivation requires the deferred-refresh convention: the persisted map is rewritten only in the reconciling boundary's rewrite, never at detection. SKILL.md's drift prose is ambiguous on this timing (its detection path lists a map refresh while the reconciling template contains no map write), so this spec resolves the ambiguity in the deferred direction and ships the clarifying sentence into `internal/revise/SKILL.md` in the same change set; under that convention an interrupted session re-derives the same non-`null` remap on resume, and `null` occurs only when the maps genuinely match, never as a fail-open default. A non-`null` remap drives the certification clearing, `clearStamp`, and remap re-evaluation the GUARD branch describes; a remap with an empty `affected` list or naming a cell absent from the state is refused (the malformed case). `clearStamp` reports the rule's requirement, not a state delta: it is true for every non-`null` remap, and applying it to a stamp already `none` is a no-op. `resolveBoundary`'s domain is exactly the all-inactive evaluated boundary of a `reviewing` run: a state with any applicable cell active, with `Status` `failed` or `post-review`, or with `Round status: in-flight` (a reviewer or verifier round still in flight; the verifier cell sits outside the applicable set, so an in-flight verifier round is otherwise indistinguishable from a resolved boundary) is refused. The legitimate boundary carries `Round status: evaluated` or `idle`, matching `Launch verifier`'s shipped precondition, and the same conjunct governs the verifier preflight, so a resume mid-verifier-round can never burn a second launch. The symmetric window one step later is closed by a caller precondition, stated rather than silently relied on: the controller applies an evaluated round's dispositions, `verifierBoundary` included, before resolving the boundary, so a resume that finds `Round status: evaluated` with an undispositioned round result on disk re-enters adjudication first (the round result scratch survives until the next `Start round` replaces it, so the ordering is disk-recoverable); without that ordering, a crash between the adjudication rewrite and the verifier-boundary rewrite would resolve straight to a second verifier launch, discarding a usable verifier result and burning one of the ten launches. The checkpoint alone cannot carry a refusal conjunct for this window (the crashed state is byte-identical to the legitimate post-relaunch-disposition state), which is why it is an ordering precondition rather than a domain check. The boundary condition is computable from the state, so off-domain calls fail closed rather than falling through the pseudocode.
- `cellAfterRound(cell, roundOutcome, fingerprint)` -> `{status, certification, ledger}`, or a refusal for an impermissible disposition per the rejected-findings rules: `status` is `'active'` or `'inactive'`, `certification` is `null` or exactly the passed reviewed `fingerprint` (a clean LGTM certifies it), and `ledger` is the closed set of effects the controller must record as three boolean flags (reasoned acknowledgement, authoritative open follow-up row, applied-change entry). A blank or whitespace-only `verifiedNote` is refused on every outcome, finding-bearing rounds included (the dispatch schema requires the note unconditionally), and an LGTM without a concrete nonblank note is refused exactly as at the verifier boundary: repairable reviewer output upstream of this function, never a certification. Only an `active` cell record is accepted input: a round outcome arriving for an inactive or N/A cell is a stale or misrouted replay and is refused. Caller precondition, stated rather than silently relied on: `roundOutcome` is the current round's adjudication-ready result for this cell at the passed `fingerprint`; the whole-round barrier and the round/fingerprint/delivery-snapshot identity checks that discard outdated results (SKILL.md repair rule 4) are controller-owned upstream, and the module's own defenses are the cell-status refusal and fingerprint-bound certification. The bare cell record instead of the state is deliberate: the function adjudicates one cell's outcome in isolation, called per cell behind the barrier before any boundary state exists to consult, and withholding the state keeps cross-cell decisions in the boundary functions that own them; the trade is exactly the recorded caller preconditions above in place of state-readable checks. The ledger itself stays controller-owned; checkpoint bookkeeping never enters the module.
- `verifierBoundary(state, verifierOutcome)` -> `{stamp, next}` where `stamp` is `null` or the exact reviewed fingerprint string (`sha256:` plus 12 lowercase hexadecimal characters, mirroring the checkpoint's `Verifier stamp` values) and `next` is `'post-review'`, `'sweep'`, or `'relaunch-verifier'`, or a refusal for an impermissible outcome: an LGTM without a concrete nonblank note is not a stampable outcome (it is repairable reviewer output upstream of this function), and the acceptance rules refuse the same dispositions `cellAfterRound` refuses. `next` names the rule-required continuation, not a performed transition: the controller acts on it only through the guarded boundary machinery (`resolveBoundary`, `preflightLaunch`), so `verifierBoundary` deliberately takes no guard inputs. Caller precondition, stated rather than silently relied on: `verifierOutcome` is the current verifier round's adjudication-ready result at the state's current fingerprint (a fingerprint move mid-round discards the round upstream, per SKILL.md's drift rule), so the stamp value, always the state's current fingerprint, is under that precondition exactly the reviewed one. The function refuses a state whose `Status` is not `reviewing`, whose `Round status` is not `evaluated`, or whose Agents section carries no `verifier` Role row: the verifier row is the checkpoint-readable signal that the evaluated round was a verifier round (appended skeptic rows for its findings may coexist), so a reviewer cell's clean LGTM can never be presented as a stampable outcome. `verifierOutcome`'s `appliedFix` and `authoritativeDeferredFollowUp` are derived redundancy over the per-finding dispositions, which are authoritative: `appliedFix` must equal whether any finding carries `disposition: 'fix-applied'`, `authoritativeDeferredFollowUp` must equal the disjunction of the findings' `actionableFollowUp` values, which under the per-disposition rules is exactly whether any finding records an authoritative follow-up, and a mismatch is refused. Computing the two flags module-side, as `cellAfterRound` does with its ledger flags, was considered and rejected: the flags are the controller's own summary of its adjudication, so requiring them as inputs and cross-checking them against the per-finding dispositions turns a controller summary that drifted from its adjudication into a fail-closed refusal, where a module-side computation would be silently self-consistent with whatever it was handed; the redundancy is the check.
- `preflightLaunch(state, launch, gateCurrent)` -> `{ok: true}`, `{ok: false, failure}`, or `{ok: false, blocked: true}`, where `launch` is `{kind: 'round'}`, `{kind: 'verifier'}`, or `{kind: 'repair', cellId}`; the repair budget is per stable cell, so the repair kind requires the cell identity. Every launch kind also evaluates the blocked-boundary guard, with one deliberate kind-scoped exception: a pending controller mutation, a non-`none` agreement boundary, or a false gate assertion blocks every kind, while a pending user request blocks only the `round` and `verifier` kinds. The `repair` kind proceeds under a pending user request because the drain is gated on full round evaluation, which can require exactly that repair: blocking it would deadlock the round against its own drain (an in-flight request appends its pending row and the round continues, per SKILL.md's in-flight rule). This kind-scoping is a deliberate reconciliation of SKILL.md's two rules (the pending-request dispatch-blocking rule, which the engine states in two sentences as described below, and the in-flight continuation rule), recorded here so the divergence from a literal all-dispatch reading of the former is visible; reconciling the engine prose itself is a queued follow-up of this feature, deferred rather than shipped in-slice because, unlike the two in-slice engine-sentence edits, it feeds no module input: it aligns prose to behavior the module already encodes. The engine states the pending-request block twice inside the Governing agreement boundary subsection: the boundary-batch drain sentence, whose condition clause `revise-round.test.js` already asserts through its required-contracts inclusion check (rewording that clause fails CI today), and the trailing all-dispatch `Also block` sentence, which no suite pins. The reconciliation therefore edits both sentences and lands the matching required-contracts clause update in the same change; whether the reconciled sentences earn a full verbatim pin with a mutation probe is decided in that follow-up under the pin-worthiness criterion. Precedence is domain first, then guard, then caps: an off-domain state (wrong `Status`, the repair kind's round or row status, or the verifier kind's in-flight `Round status`) is refused before the guard is evaluated, a blocked in-domain state returns `{ok: false, blocked: true}` without evaluating caps, and a cap preflight fails the run only from an unblocked in-domain state. Every launch kind requires `Status: reviewing`: a `failed` or `post-review` state refuses every preflight (`off-domain`), since a failed run is exited only through `exitTerminal` and never by an implicit launch. The `Round status: in-flight` conjunct deliberately binds only the `verifier` kind: a legitimate `Start round` can fire from an in-flight state (the delivery-map abandonment resume path discards the round and invokes `Start round` for the next one), and whether to abandon-and-relaunch or resume is controller-owned (it turns on the delivery-projection byte comparison the module cannot see), so the `round` kind returns `{ok: true}` on an in-flight state and the round-cap preflight is what every relaunch still pays. The `repair` kind carries the converse precondition: a repair targets unfinished work inside an in-flight round (the engine keeps the round in flight through partial results and repairs), so a repair preflight with `Round status` `evaluated` or `idle`, or naming an Agents row already `completed`, is refused off-domain. The engine's fourth dispatch class, the original mid-round skeptic fan-out, is deliberately outside this enumeration: it is round-internal dispatch owned by the round pipeline (its Agents rows start at zero repairs, so it is not the repair kind), and the same drain-ordering rationale as the repair exemption applies, since full round evaluation depends on it.
- `exitTerminal(state, disposition, applicability, failure)` -> `{exit, effects}`, or a refusal; `disposition` is `{kind: 'retry', cellId}`, `{kind: 'restart'}`, `{kind: 'abandon'}` on a state-derived `Status: failed`, and `{kind: 'reviewable-change'}` or `{kind: 'finalize'}` on `post-review` (see Terminal-state exits). The state's `Status` is the function's domain check, refused like its siblings' off-domain inputs: retry, restart, and abandon require `Status: failed`, reviewable-change and finalize require `Status: post-review`, and a `reviewing` state is refused for every disposition. The `failure` record rides only the failed-state dispositions; a post-review disposition carrying one is refused. The post-review dispositions also carry the checkpoint-readable half of the blocked-boundary guard: a pending user request, a pending controller mutation, or a non-`none` `Agreement boundary` refuses reviewable-change and finalize, since the drain and agreement resolution precede any post-review boundary and finalize's state deletion would otherwise drop them irrecoverably; the volatile gate assertion is deliberately not required here because these exits are not dispatches, and the checkpoint-readable conjuncts alone carry the drain requirement. `exit` is one of `'reviewing'` (retry and reviewable-change), `'restarted'`, `'terminated'` (abandon), or `'finalized'`, and `effects` is the complete replacement values for exactly the state fields the disposition's route enumerates in Terminal-state exits. Controller-owned values a route needs ride the disposition: `{kind: 'retry', cellId, identityMatched}` carries the caller-asserted round/fingerprint/snapshot identity check (false is refused as a retry; the drift-abandonment route it falls to is controller-owned), `{kind: 'restart', currentFingerprint}` carries the controller-computed current fingerprint the reset adopts, `{kind: 'reviewable-change', nextFingerprint}` carries the controller-computed refreshed fingerprint, and `{kind: 'finalize', recheckMatched}` carries the caller-asserted final fingerprint recheck result; a missing or malformed carried value is refused. A caller-asserted class without the round-trip was also considered and rejected: the dispositioning invocation is normally a later session inferring from free text, so an assertion would have no ground truth to check against, while the round-tripped record is the assertion-free discriminator. `failure` is the module's own failure record round-tripped: whenever a `failed` transition or a not-ok cap preflight lands the run in `Status: failed`, the controller writes the record's compact canonical JSON as the checkpoint's `Failure JSON` content, nested inside the field's canonical JSON string literal (the field itself stays a string per the checkpoint encoding contract; resume decodes the field, then parses the record from its text) (shipping this feature adds that one-sentence persistence convention to `internal/revise/SKILL.md` in the same change set, per the same-change-set convention), and the dispositioning invocation, normally a later session, parses it back and passes it to `exitTerminal`. The record's failing rule is the class discriminator; state values cannot substitute for it because at-cap values are ordinary non-failing state (a state at a cap is valid input) and the four classes co-occur in them. The module still sanity-checks the record against the state where a contradiction is derivable (a `round-cap` record with round below 30, a `verifier-cap` record with launches below 10, a `repair-exhaustion` record naming a cell below its cap) and refuses on contradiction. The `empty-applicable-set` class is the exception: its failing sweep's rewrite is discarded (`Status: failed` with current diagnostics is written instead, leaving the prior cell table authoritative), so the persisted table may legitimately still show applicable cells; that class's sanity check therefore reads the record's own diagnostics, which must show the sweep-derived applicable set as empty, and never the retained cell table. The discard rule governs the checkpoint, not the record: the failing sweep's demotion reasons and `preserved` reasons are never persisted, while the record's per-cell status snapshot is the status set the failing rewrite computed (statuses only, reasons not carried), which is exactly what shows the applicable set as empty for this class's check; and a retry disposition's `cellId` must equal the cell the `repair-exhaustion` record names: retry resets the exhausted cell, never a sibling that merely sits at its cap. `failure` is required for the failed-state dispositions and must be absent on the post-review ones; a missing, unparseable, or unknown-class record refuses every exit as environment residue, and environment-route recovery (with its abandon) stays controller-owned prose, per the scope split above. `applicability` carries the same controller-evaluated verdicts as `resolveBoundary` and is required for the restart disposition (whose N/A re-evaluation is controller judgment) and refused when present on any other disposition. A disposition applied off its route is refused, never partially applied: retry is permissible only for the execution-repair exhaustion route, restart only for the cap and empty-applicable-set routes, abandon for any state-derived route. Permitting restart on any failed state was considered and rejected: a repair-exhaustion failure is cell-scoped with an intact run around it, and restart offers no remedy retry lacks, since the restarted wave re-runs the same cell into the same execution defect while discarding every intact certification and resetting budgets run-wide, whereas retry resets exactly the exhausted cell's budget at no wider cost; the route table pairs each class with the cheapest disposition that can cure it, mirroring SKILL.md's terminal-exit sentence, which names restart only for the cap failures.
- `canComplete(state)` -> boolean.

`roundOutcome` is the cell's normalized round result: `{lgtm, verifiedNote, findings}`, with `findings` a list of `{verdict, disposition, actionableFollowUp}` where `verdict` is `CONFIRMED | REFUTED | JUDGMENT_CALL` and `disposition` is `fix-applied | deferred-follow-up | refuted | accepted-judgment-call`. The engine's full contradictory-output class is refused, not just the blank note: `lgtm: true` with a nonempty findings list, and `lgtm: false` with an empty findings list, are both refused as repairable reviewer output upstream of any disposition. `actionableFollowUp` is a boolean: true exactly when the finding records an authoritative open follow-up row (always for `deferred-follow-up`; optionally for `accepted-judgment-call`, and optionally for `fix-applied` when the in-surface fix leaves an out-of-surface remainder queued as an authoritative row, the pairing SKILL.md's boundary recording performs routinely), and refused as inconsistent when true on a `refuted` finding or false on a `deferred-follow-up` finding (whose authoritative row is unconditional); `verifierOutcome`'s `authoritativeDeferredFollowUp` must equal the disjunction of its findings' `actionableFollowUp` values. `verifierOutcome` is the same shape plus `appliedFix` and `authoritativeDeferredFollowUp` booleans. `failure` (the "current diagnostics" every failure path preserves) is a closed record carrying the failing rule as the closed enum `repair-exhaustion | round-cap | verifier-cap | empty-applicable-set` (the discriminator the terminal-exit routes key their off-route refusals on), plus round, fingerprint, per-cell status with certification and repair counter, and the verifier counters; a `repair-exhaustion` record additionally carries the exhausted cell's identity (`cellId`), the value the retry route's equality check and the below-cap contradiction check read, and an `empty-applicable-set` record's per-cell status is the failing rewrite's computed status set (statuses only, no demotion reasons), the field its class check reads. Exact serialization and field spelling are an implementation-plan decision; the fixture suite binds the named fields and asserts the listed content is present.

Input contract: every function takes the review state or, for `cellAfterRound`, a single cell record, in either case already past the checkpoint schema validation SKILL.md prescribes (canonical parse, hex, row ordering). `state` is the decoded in-memory projection of that validated checkpoint: one record carrying the header fields (status, round status, round, fingerprint, stamp, verifier launches, agreement boundary, autonomous handover, artifact edited, post-review step, failure), the cell table (per cell: id, kind, status, N/A reason, certification), the Agents rows (role, cell ID, status, repair counter), the pending user-request and controller-mutation sections, the post-review work items, and the ledger sections (prior failures included). The pseudocode's dotted fields (`state.fingerprint`, `state.stamp`) name members of this projection while raw backticked labels name the persisted checkpoint form; exact member spelling is an implementation-plan decision the fixture suite binds. Absent-value sentinels follow the same split: the checkpoint's raw `none` decodes to `null` in the projection, and every module-surface input and result uses `null`; a literal `'none'` string reaching the surface is refused as malformed. The module additionally refuses, fail-closed, any input violating the semantic invariants it depends on: a cell is inactive exactly when it holds a certification, an N/A row carries a nonblank reason, cell IDs are unique, counters are integers in 0..cap inclusive (a state at a cap is valid input; the cap-exhaustion rules fire on the next attempted launch, and only a counter beyond its cap is refused), an applicability set covers exactly the state's cells, and a repair or retry `cellId` names a current Agents row (a well-formed but unknown or not-currently-launched identity has no counter to consult and is refused).

A refusal is one shape everywhere it appears in this spec: a thrown structural error carrying a closed reason code, the same pattern the agreement controller's `AgreementError` uses. The closed reason-code set is `invalid-state` (the state record alone violating its own invariants), `invalid-input` (a non-state parameter or carried value failing its rule), `off-domain` (a function applied to a state outside its declared domain), `impermissible-outcome` (`roundOutcome` or `verifierOutcome` content no disposition may consume), and `off-route` (a terminal disposition whose kind is not permitted for the derived failure class). Where a condition could read as more than one code, this assignment rule decides: `impermissible-outcome` is more specific than `invalid-input` for the outcome parameters, so a rule on `roundOutcome` or `verifierOutcome` content binds `impermissible-outcome`; for every other parameter, a rule attached to a parameter or carried value is `invalid-input` even when evaluating it reads the state or the failure record (the applicability-set coverage rule, the retry `cellId`-vs-record equality, `identityMatched: false`, a failed `recheckMatched`, and the derivable-contradiction checks are all `invalid-input`); readiness conjuncts on a function's entry (the post-review drain-and-agreement conjuncts, the verifier-row discriminator, `Round status` and `Status` checks) are `off-domain`; `off-route` is exactly the class-route table. Every refusal condition in this spec maps to exactly one code under that rule, the fixture suite binds the code rather than only the throw, and finer within-code discrimination is an implementation-plan decision. It is distinct from a `failed` transition (a valid state whose rules land the run in `Status: failed`) and from a `{ok: false}` preflight result (a valid state failing a cap check). All six functions, `canComplete` included, throw the same structural refusal on invalid input; `canComplete`'s boolean is defined only over valid inputs. A refusal is never a transition: it produces no sweep, launch, completion, or failure disposition. Fixture cases: an active cell carrying a certification is refused; an inactive cell without a certification is refused; an N/A row with a blank reason is refused; duplicate cell IDs are refused; a counter beyond its cap is refused while a counter at its cap is accepted; an applicability set missing a cell or naming an unknown cell is refused; `resolveBoundary` with an applicable cell still active, with `Status` `failed` or `post-review`, or with `Round status: in-flight` is refused as off-domain, and a verifier preflight with `Round status: in-flight` is refused the same way, including when the state is also blocked (no second launch against an in-flight verifier round, and domain precedes guard for this kind exactly as for the others); a literal `'none'` string reaching any module-surface field is refused as malformed per the sentinel split (state fields as `invalid-state`, parameters and carried values as `invalid-input`, under the code-assignment rule); a refusal produces no transition.

Limit values are data, not literals scattered through logic: the transition table is declared configuration carrying the current shipped values (30 rounds per run with verifier rounds included, 10 verifier launches per run, 3 execution-repair launches per stable reviewer, skeptic, or verifier cell per round). Declared-up-front makes a future cap change a table-and-fixture update in its own change set; a lifecycle redesign (new transitions or boundary rules) remains a module-and-fixture change, merely a localized one because the transition rules live in one module.

The module lives under `internal/revise/` (for example, `internal/revise/orchestration.js`) with its fixture suite beside it (for example, `internal/revise/orchestration.test.js`), runnable the same way as the existing suites. When the feature ships, the universal-entry topology fixture's hardcoded relocated-engine-files list gains both new files in the same change set, following the `rigor.js` plus `rigor.test.js` precedent already in that list, so the suite then requires them to remain internal at their engine-root paths; the fixture treats neither `internal/revise/` as a closed file set nor unlisted files as constrained, which is exactly why the two entries must be added rather than assumed; every repository site that enumerates the test suites gains this one (the Commands guidance in `AGENTS.md`, where both the per-suite bullet list and the separate suite-count sentence update, the README's suite run-list, and `.github/workflows/ci.yml`, which gains a per-file step), and the agreement controller suite's literal pin of that count sentence (`skills/spec-agreement/spec-agreement.test.js` asserts the exact `CI runs all six suites on Node 22.` line) updates in the same change set, since the stale count would otherwise fail that pin or, left unedited, ship as a false statement no other check catches; and the Operating context's runs-in-CI claim holds only once that CI step lands.

## Boundary resolution and the staleness sweep

At every evaluated boundary where all applicable cells are inactive, the controller resolves the next transition in one rewrite, sweep first:

```text
Inputs: every applicable cell inactive (the boundary condition),
current fingerprint F, verifier stamp S, pending controller mutation
or user request P, agreement boundary marker A, unreconciled
scope-map change M, controller-evaluated N/A applicability
verdicts V, caller-asserted current gate success G (the volatile
agreement context's entry or post-mutation result, which the
checkpoint cannot carry).

GUARD (before any transition)
  P pending, A != none,
  or G false            -> {transition: 'blocked'}: no transition
                            and no dispatch until the mutation batch
                            drains, the agreement boundary clears,
                            and a current gate result exists
  M unreconciled         -> the reconciling boundary clears Verifier
                            stamp S to none if set, clears affected
                            certifications directly, and re-evaluates
                            every N/A declaration in both directions
                            before the sweep reads certifications

SWEEP (first transition step)
  apply the controller-evaluated applicability verdicts V first, in
  both directions (promotion yields active with no certification;
  demotion clears certification and records the freshly evaluated
  nonblank reason; an unchanged not-applicable verdict stays N/A and
  re-encodes its freshly evaluated reason); then reactivate exactly
  the still-applicable cells whose certified fingerprint != F,
  clearing each reactivated cell's certification. A cell demoted by
  its verdict never counts as activated, even when its certification
  was also stale.
  applicable set empty after sweep  -> run fails (convergence is
                                       never vacuous)
  sweep activated at least one cell -> Start round
  demotion-only or no-op sweep      -> fall through (converged)

WAVE CONVERGENCE (every applicable cell's certification equals F)
  S != F (none or stale) -> Launch verifier
  S == F                 -> post-review (complete)
```

Staleness is evaluated only at this boundary, never mid-round: accumulated edits batch into one wave instead of re-running settled cells per small delta. No artifact edit or finding disposition reactivates a cell directly; fingerprint movement reactivates only through the sweep. The one exception is a resolved-scope-map change, which fingerprint inequality cannot detect: the boundary that reconciles it clears every affected cell's certification directly (whole-scope and cross-cutting cells on any map change, local cells on slice-membership change) and performs the same N/A applicability re-evaluation in both directions that the sweep performs (the remap re-evaluation); within a run's flow, N/A promotion and demotion happen at exactly these two boundaries, and the user-authorized `Restart run` re-derives applicability wholesale as part of its out-of-flow reset (see Terminal-state exits).

Fixture cases:

- all inactive, one certification stale -> exactly that cell reactivates with cleared certification and a round starts; currently certified cells stay inactive;
- all certifications current, stamp none -> verifier launch; read under the stated ordering precondition: an evaluated round's dispositions are applied before the boundary is resolved, so this fixture presumes a dispositioned round;
- all certifications current, stamp equal to the current fingerprint -> post-review;
- demotion-only sweep -> no round; resolution falls through to the convergence branch with the demotions carried on that result;
- a stale-certified cell whose applicability verdict demotes it -> demoted with certification cleared, never counted as activated; a sweep whose only changes are such demotions falls through to the convergence branch;
- a preserved N/A cell whose fresh verdict changed only the reason text -> carried on `preserved` with the fresh reason, status unchanged;
- sweep leaves the applicable set empty -> run fails with current diagnostics;
- contradicted N/A -> promoted to active with no certification, so the run cannot complete without reviewing it;
- mid-round edit -> no sweep until the next all-inactive boundary;
- scope-map change at an unchanged fingerprint -> `clearStamp: true` (a no-op when the stamp is already `none`), affected cells' certifications cleared directly, and every N/A declaration re-evaluated in both directions at the reconciling boundary;
- a remap with an empty affected list or naming a cell absent from the state -> refused;
- a resume between map-change detection and the reconciling boundary -> recorded as a controller-owned convention, not a module fixture: the persisted-vs-current map comparison re-derives the same remap and `null` is never a default, a derivation the module cannot observe (it receives one state, not the map pair); the module-side half the suite binds is the malformed-remap refusal above, and the convention itself ships as the deferred-refresh engine sentence this feature carries;
- a verifier preflight exceeding both the round cap and the verifier cap -> the failure record carries `verifier-cap`, matching the shipped `Launch verifier` template, which fails on the verifier cap before its `Start round` application ever pays the round cap;
- pending user request or controller mutation, non-`none` agreement boundary, or a false gate assertion -> `{transition: 'blocked'}`, no transition and no dispatch.

## Certification span

A cell that converges cleanly (explicit LGTM with a concrete nonblank verification rationale) becomes inactive, certifying the exact fingerprint it reviewed. The run does not relaunch it in any later round while it stays certified, no matter how long a sibling cell takes; within a run only a staleness-sweep reactivation or a scope-remap clearing returns it to active, and the user-authorized `Restart run` resets every cell outside that flow (see Terminal-state exits). Round numbers are monotonic while the run is reviewing and never reset mid-flow; only the user-authorized `Restart run` returns the run to round 0. (The queued fix-scoped-rounds feature will add a full-payload precondition to this certification transition; see Relationship to neighboring features.)

Fixture case:

- round N: D1 LGTM after one note-backed review, D2 requires seven reviews at an unchanged fingerprint -> D1 is launched zero times across the remaining six rounds.

## Cross-cell mutation

One invariant with two halves, both fixture-tested:

- **Preserve until the sweep.** A sibling cell's accepted artifact edit moves the fingerprint and preserves each cell's current active or inactive state until the next all-inactive boundary. D1 that already certified is not reactivated mid-run by D2's fix, even though the artifact changed under D1's certification. The staleness sweep is what provides the global re-review barrier.
- **Reactivate at the sweep.** At the all-inactive boundary, the sweep reactivates exactly the cells whose certification differs from the current fingerprint, clearing each reactivated certification. D1's prior LGTM buys it nothing against a moved fingerprint.

Fixture cases:

- round N: D1 certified, D2's accepted fix moves the fingerprint -> D1 still inactive for every remaining round before the boundary, launched zero times;
- at the boundary: the sweep reactivates D1 with `Certified fingerprint: none`, while a cell certified at the moved fingerprint stays inactive.

## Rejected findings

The disposition rule set, with the refuted and valid-but-deferred branches both covered:

1. A valid-but-deferred finding, or an accepted judgment call with an actionable follow-up, keeps its cell active. The disposition is not a convergence device and never produces LGTM by itself.
2. A round whose skeptic-verified findings all landed as refuted or as acknowledgement-only accepted judgment calls keeps the cell active with no certification. The reasoned acknowledgements enter the next payload, and only a later explicit clean LGTM with a concrete nonblank verification rationale deactivates the cell. The module refuses to record a refutation from a controller rejection that lacks a skeptic-verified verdict, and the acceptance branch applies only to findings whose skeptic verdict is JUDGMENT_CALL.
3. A rejected finding neither moves the fingerprint nor counts as a per-finding clean conclusion.

Valid-but-deferred additionally records its actionable follow-up and the acknowledgement or caveat, with no applied-change entry. A REFUTED finding records a reasoned acknowledgement and no follow-up or applied-change entry. A fix-applied finding keeps the cell active and is the one disposition that sets the applied-change ledger flag, with no acknowledgement flag from that finding and the follow-up flag exactly when its `actionableFollowUp` is true (an in-surface fix whose out-of-surface remainder is queued as an authoritative row); an accepted-judgment-call finding always sets the acknowledgement flag, with the follow-up flag exactly when its `actionableFollowUp` is true; the artifact edit itself, the post-fix steps, and `Artifact edited: yes` are controller-owned boundary effects outside the module.

Why refutations never certify: a refutation defeats one claim, not the cell's whole scope; it is not a fresh clean look, and certifying on it would let a wrong finding stand in for verification of the ground the reviewer never covered. The predecessor rule that deactivated a cell on an all-refuted round was considered and retired by the 2.4.4 clean-LGTM correction (recorded in `wave-lifecycle.md`, Rejected alternatives).

Fixture cases:

- reviewer finding F, skeptic REFUTES it, no other findings in the round -> cell D stays active with no certification, and the reasoned acknowledgement enters the next payload;
- reviewer finding F, controller rejects it without a skeptic-verified refutation -> the disposition is refused and D stays active;
- mixed round: one refuted finding plus one valid-but-deferred -> D stays active, with the follow-up and acknowledgement recorded;
- accepted judgment call with an actionable follow-up as the round's sole finding -> D stays active, with the follow-up row recorded;
- acknowledgement-only accepted judgment call as the round's sole finding -> D stays active with no certification and receives another fresh review at the same fingerprint;
- deferred in round N, all findings refuted in round N+1 -> D stays active while the round-N follow-up row stays open, and only a later clean LGTM can deactivate D;
- a confirmed finding with disposition fix-applied -> D stays active, the applied-change flag is set and the acknowledgement flag is not, with the follow-up flag equal to its `actionableFollowUp`; both flag combinations are fixtured (a self-contained fix, and a fix with a queued out-of-surface remainder);
- after any finding-bearing round, a later clean LGTM with a concrete nonblank rationale -> D becomes inactive and certifies that clean review's fingerprint;
- attempting the acceptance branch on a CONFIRMED-verdict finding is refused;
- an LGTM with a blank or whitespace-only verification note is refused as repairable reviewer output, with no certification and no status change;
- a round outcome for an inactive or N/A cell record is refused as a stale or misrouted replay;
- `lgtm: true` with a nonempty findings list, or `lgtm: false` with an empty findings list -> refused as `impermissible-outcome` (the contradictory-output class), at `cellAfterRound` and `verifierBoundary` alike;
- `actionableFollowUp` true on a `refuted` finding, or false on a `deferred-follow-up` finding -> refused as `impermissible-outcome` at both boundaries;
- for the refusal and rejected-disposition cases the fingerprint does not move; the fix-applied case's controller-owned artifact edit advances it once at the boundary, per the fix-applied disposition rule; in every listed case no sibling cell changes state and no per-finding clean conclusion is counted.

## Verifier stamping

The holistic verifier launches only at wave convergence and follows the same finding and skeptic pipeline as dimension cells. Its cell (`verifier/whole-artifact`) sits outside the applicable set: the sweep and wave convergence never count it. Its stamp names only the fingerprint it reviewed; a stamp whose fingerprint no longer matches the current fingerprint is stale and authorizes nothing. The transition module covers every verifier boundary:

1. A clean LGTM with a concrete nonblank verification note stamps the current fingerprint.
2. A no-fix verifier round whose findings are all refuted or accepted as acknowledgement-only judgment calls leaves the stamp unset, carries the reasoned acknowledgements forward, and launches another fresh verifier at the same fingerprint.
3. Only a current no-fix verifier round that creates an authoritative deferred follow-up may stamp without a clean LGTM. The stamp attests review coverage while the authoritative follow-up records the accepted debt.
4. A verifier round that applies any fix leaves the stamp unset, advances the fingerprint once at the boundary, and returns to the staleness sweep. An authoritative deferred follow-up in the same round does not override the applied-fix branch.

Fixture cases:

- verifier returns clean LGTM with a concrete note -> current fingerprint is stamped;
- verifierBoundary on an evaluated boundary whose Agents rows are reviewer rows only -> refused; no reviewer round can produce a stamp;
- verifier returns LGTM without a concrete nonblank note -> refused as an impermissible outcome: no stamp and no boundary transition (the outcome is repairable reviewer output, not a stampable conclusion);
- every verifier finding is skeptic-refuted, no fix or follow-up -> stamp stays unset and another fresh verifier is required at the same fingerprint;
- every verifier finding is an acknowledgement-only accepted judgment call, no fix or follow-up -> stamp stays unset and another fresh verifier is required at the same fingerprint;
- verifier creates an authoritative deferred follow-up and applies no fix -> current fingerprint may be stamped without LGTM, with the follow-up retained;
- verifier creates an authoritative deferred follow-up and applies a fix -> stamp stays unset, the fingerprint advances, and the staleness sweep resumes;
- verifier applies a fix with no deferred follow-up -> stamp stays unset, the fingerprint advances, and the staleness sweep resumes.

## Execution failure

The run-level fail-closed contract, which is distinct from the round-level `needs-reviewer` status that `revise-round.test.js` already covers:

- a missing or malformed reviewer or skeptic output is repairable within the affected stable cell's execution-repair budget; the module models `Status: failed` entry for the state-derived routes: no repair attempt remains, a cap preflight would be exceeded, or the staleness sweep leaves the applicable set empty;
- the environment-level routes that set the same `Status: failed` through controller prose (a manual Agent path without background submission or attributable completion primitives, a failed checkpoint write, a non-migrated pre-wave state file) are deliberately out of the module's scope: their entry conditions and recoveries are functions of dispatch primitives and I/O rather than of review state, and their exits stay owned by `internal/revise/SKILL.md`. The post-review tail's own machinery (step sequence, work-item enumeration, post-review mutations and their recovery) is out of scope the same way: the module owns only the boundaries into and out of `post-review` (entry via the stamp conjunction, re-entry to reviewing, finalization), never the tail's internals. New-run creation is likewise out of scope: it is entry-gate machinery that runs before any state exists for the module to read, and it initializes the same counters and cell states as `Restart run` (SKILL.md's shared template), so the implementation may share the reset-effects helper while the entry gate itself stays controller-owned;
- the failed run is not a convergence data point: no boundary transition, no partial certification, no completion, and no manufactured LGTM, stamp, or refutation from any limit path;
- a failed run never auto-resumes; it surfaces `Failure` and requires explicit user disposition (retry, restart, or abandon in interactive mode; autonomous handover stops for user disposition). Disposition authorization itself is controller-owned, like the drift-abandonment route: the user's authorization is a conversational event the checkpoint cannot carry, and `Autonomous handover: yes` deliberately does not refuse an exit, because the disposing invocation may be a later interactive session over the same checkpoint. The module's contribution is refusing every implicit or automatic resume; who may authorize an explicit one stays prose.

Limits: 30 rounds per run (verifier rounds included), 10 verifier launches per run, 3 execution-repair launches per stable reviewer, skeptic, or verifier cell per round. The repair counter's lifecycle is round-scoped: `Start round` re-creates every launched cell's counter at zero, `Restart run` clears the Agents rows and with them every counter, and the authorized-retry exit resets only the affected cell's counter; the increment itself is controller-owned bookkeeping (like the ledger), so the module only reads whatever counter the checkpoint carries. `Start round` and `Launch verifier` preflight their caps: a launch that would exceed a cap fails the run before any agent launches. Exhaustion of any limit is terminal until explicit disposition, and a cap-forced end never produces completion.

Fixture cases:

- reviewer output missing/malformed with repair budget remaining -> repairable, never a run failure, an LGTM, or a refutation;
- reviewer output missing/malformed with the cell's repair budget exhausted -> `Status: failed`, round, fingerprint, and cell diagnostics preserved, no transition, no completion;
- a `Start round` that would exceed round 30 fails the run before any agent launches, preserving round-30 diagnostics;
- an eleventh verifier launch fails the run at the preflight;
- a repair counter at 3 within its round fails the run before another agent launches (counters are round-scoped and re-created at zero by `Start round`);
- any launch kind attempted with a pending controller mutation, a non-`none` agreement boundary, or a false gate assertion -> `{ok: false, blocked: true}`, and no agent launches;
- a round or verifier launch attempted with a pending user request -> `{ok: false, blocked: true}`, while a repair launch under the same pending request proceeds (the deadlock exemption);
- a round preflight with `Round status: in-flight` and no blocking condition -> `{ok: true}`; only the `verifier` kind carries the in-flight conjunct, so the delivery-map abandonment relaunch stays viable;
- a state both blocked and at a cap -> `{ok: false, blocked: true}`, never a cap failure; the run fails on a cap only when the launch is otherwise permissible;
- the module refuses to turn any limit-exhausted state into an LGTM, a stamp, or a refutation.

## Terminal-state exits

`Status: failed` and `post-review` are exited only by explicit transitions, and for the state-derived failure routes the module owns their state effects:

1. For an execution-repair exhaustion failure, a user-authorized retry whose round, fingerprint, and delivery snapshot still match sets `Status: reviewing`, clears `Failure`, resets only the affected stable cell's repair counter, sets that cell's Agents row to `needs-retry` and its unfinished result work to the matching repair status (`needs-reviewer` for a reviewer or verifier cell, `needs-retry` for a skeptic finding), and preserves every completed result; an identity mismatch follows drift abandonment instead.
2. For a round-cap or verifier-cap failure, a user-authorized restart records the failure and invokes the complete `Restart run` template: `Status: reviewing`, `Post-review step: not-started`, `Failure: none` (with the prior failure copied into Prior failures), round 0, `Round status: idle`, `Verifier launches: 0`, `Verifier stamp: none`, the current fingerprint, `Artifact edited: no`, the Agents rows cleared (and with them every repair counter), post-review work items and any pending mutation cleared, and every applicable cell active with `Certified fingerprint: none` with N/A cells re-evaluated with freshly encoded reasons, while artifact and scope identity, acknowledgements, user requests, applied changes, follow-ups, prior failures, and the `Agreement boundary` marker are preserved; a pending user request survives restart and must drain before the restarted run may dispatch.
3. An empty-applicable-set failure is exited by explicit abandon, or by a user-authorized restart once the artifact or resolved scope has changed. SKILL.md's terminal-exit sentence enumerates no route for this class; the abandon-or-restart shape follows the precedent of its non-migrated-state-file disposition (restart or abandon), and retry is excluded because its repair-counter mechanics have no referent in a sweep failure. With that provenance recorded: `Restart run` re-evaluates every N/A declaration, so a restart that still derives an empty applicable set fails again deterministically; the module never loops or invents applicability.
4. Explicit abandon exits any state-derived `Status: failed` terminally: the controller shows the retained failure and deletes only the review scratch, the state file included, so no checkpoint remains to re-disposition; terminality is enforced by deletion exactly as finalization's is, not by a marker. A retained failed checkpoint means the abandon never completed, and it stays dispositionable by design. The module's contribution is refusing to derive any transition, LGTM, stamp, or refutation from an abandoned run.
5. A reviewable post-review mutation, or drift detected by the pre-stamp or pre-cleanup fingerprint recheck, returns the run to `reviewing`: `Post-review step: not-started`, the post-review work items reset to their empty sentinel, the completed mutation cleared, `Verifier stamp: none`, and the fingerprint replaced by the controller-computed `nextFingerprint` carried on the disposition, so the staleness sweep drives re-review. Finalization requires both preconditions: `Post-review step: done` (checkpoint-readable, refused otherwise) and a caller-asserted matching final fingerprint recheck carried on the disposition (fingerprinting is controller-owned, like applicability); a failed recheck is refused as a finalize and routes to the reviewable-change disposition instead. Successful finalization deletes the state file: the run's normal terminal exit, with no persisted completed status.

Fixture cases:

- authorized retry with matching identity -> reviewing, `Failure` cleared, only the affected cell's repair counter reset, every completed result preserved;
- an authorized retry, restart, or abandon on a state with `Autonomous handover: yes` -> permitted exactly as with `no`; authorization is controller-owned and the flag never refuses an exit;
- authorized retry with mismatched identity (`identityMatched` false) -> refused as a retry, no counter reset; the drift-abandonment route that follows is controller-owned, outside the module;
- a repair preflight or retry naming a cell with no current Agents row -> refused;
- a repair preflight with `Round status` `evaluated` or `idle`, or naming a completed Agents row -> refused off-domain;
- a retry whose `cellId` is not the cell the `repair-exhaustion` record names -> refused, even when that cell also sits at its cap;
- verifierBoundary with `Status` not `reviewing`, `Round status` not `evaluated`, or an `appliedFix`/`authoritativeDeferredFollowUp` flag contradicting the per-finding dispositions -> refused;
- restart after a cap failure -> round 0, verifier counter and stamp reset, every applicable cell active with no certification, agreement boundary preserved;
- restart after an empty-applicable-set failure with applicability unchanged -> fails again with the same failure class;
- after an empty-applicable-set failure, the retained cell table still showing applicable cells does not refuse restart or abandon; the class contradiction check reads the record's diagnostics, not the table;
- explicit abandon -> terminal by scratch-and-state deletion; no transition, LGTM, stamp, or refutation is derived from the abandoned run, and no checkpoint survives for a later disposition;
- reviewable post-review mutation, or post-review drift at the fingerprint recheck -> reviewing, post-review step and work items reset, stamp cleared, fingerprint refreshed;
- finalization with post-review step done and a matching fingerprint recheck -> state deleted, no persisted completed status;
- finalize with the post-review step not `done` -> refused;
- finalize with a failed fingerprint recheck -> refused; the drifted state's route is the reviewable-change disposition;
- finalize or reviewable-change with a pending user request, a pending controller mutation, or a non-`none` agreement boundary -> refused; the drain and agreement resolution come first;
- retry on a cap or empty-applicable-set failure, or restart on a repair-exhaustion failure -> refused as an off-route disposition, with no partial state effects;
- a failed-state disposition with a missing, unparseable, or unknown-class `failure` record -> every exit refused as environment residue; environment-route recovery never becomes a module transition;
- a `failure` record contradicting the state where derivable (a `round-cap` record with round below 30, a `verifier-cap` record with launches below 10, a `repair-exhaustion` record naming a cell below its cap) -> refused; the `empty-applicable-set` class instead checks the record's own diagnostics, per its carve-out;
- a post-review disposition carrying a `failure` record, or any disposition applied to a `reviewing` state -> refused (the `Status` domain check);
- any preflight kind on a `Status: failed` or `post-review` state -> refused off-domain, never `{ok: true}`, and refused even when the state is also blocked (domain precedes guard);
- for the state-derived routes, no exit from `Status: failed` other than authorized retry, authorized restart, and explicit abandon exists: the module refuses any implicit or automatic resume.

## Completion invariant

The run enters `post-review` only on the conjunction:

```text
canComplete(state)
  = applicable set nonempty
    AND every applicable cell inactive
    AND every applicable cell's certification == state.fingerprint
    AND state.stamp == state.fingerprint
```

The stamp is a conjunction, not an authority: the verifier never launches before wave convergence, so no single agent and no cap path can complete the run alone. Any reviewable edit after a stamp moves the fingerprint, and any scope-map change clears the stamp to `none` and the affected certifications directly; either event invalidates completion, and certification loss is the single re-entry path; the queued durable-scope-anchor feature adds anchor revision as a further certification-and-stamp invalidation trigger when it lands.

The predicate is tested to return false in every failing combination independently (false is a valid answer over a valid state, distinct from the thrown structural refusal reserved for invalid input):

- some applicable cell active -> false;
- all inactive, one certification at an older fingerprint -> false (sweep territory, not completion);
- converged, stamp none -> false (verifier territory);
- converged, stamp at an older fingerprint -> false;
- applicable set empty -> the run fails and never completes;
- converged with stamp none and verifier launches exhausted -> the run fails and never completes (cap asymmetry);
- converged with stamp none and the next verifier round exceeding round 30 -> the run fails and never completes (the round cap binds verifier rounds too);
- converged with an N/A cell present (its certification the raw `none`) -> true; the certification quantifier ranges over applicable cells only, so a not-applicable row never blocks completion;
- completes only on: nonempty applicable set, every applicable cell inactive, every applicable cell's certification current, stamp equal to the current fingerprint.
