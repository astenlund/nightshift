# Changelog

Release notes for the Nightshift plugin, newest first. The plugin manifests carry the current version. Deterministic and zero-inference checks remain distinct from model-owned observations.

The entries through 3.3.3 were moved here from the README on 2026-10-05 and split by version. A version without an entry had no notes recorded there.

## 3.3.19

- An attached check's reproduction is now drawn from the failures of the same name and command in the last series on the same task that no successful run of that name, under any command, interrupts, not only its last failing run; pending runs, runs that exited zero while their inputs changed and failures of another command neither belong to that series nor end it. It gives the first failure with its input count and digest, and under `laterFailures` the outcome and output tail of each of the next three, with `omittedFailures` counting any after them, since the records do not say which failure the controller confirmed fails for the finding's reason. `passesSince` counts the successful runs between that series and the passing check, not counting a run that exited zero while its inputs changed, and the prompt says that reruns after later edits make it nonzero, so the reviewer judges from the failure output whether the series belongs to the fix under review. Each input that differs between the first failure and the passing run carries both runs' hashes, so a file only one run declared, or one run found missing, can be told apart from a changed one.
- Executables compare after path normalization, and on Windows executables and input paths compare without regard to case; one check recorded on several tasks with executables that compare equal this way is listed once, but now only when none of the tasks has a reproduction for it, each task with one getting its own entry: 3.3.18 showed the first reproduction it found among the merged tasks for all of them and dropped the others', so a covered task's own reproduction could be replaced by an unrelated one. When searching for a reproduction, a check record without an exit code is now judged by whether it passed, where 3.3.18's search took every such record that was not pending for a failure. For a project in a subdirectory of its repository, the reviewer's `diff.patch` now uses project-relative paths, matching the reviewer's copy, as the touched inputs already did.
- The prompt says a check's inputs are the ones it declares. The repair rule in status, the operating brief and revise-code say to rerun the same command under the same name on the same task after a repair; status and revise-code also say to rerun that reproducing check before a review once its inputs change, and the brief says so for any check whose inputs changed, since a stale check is not attached and neither is its reproduction. The runtime reference states the probe copy's layout.
- Evidence: the runtime review, docs-review and probe suites and the seeded-defect suite fixtures passed (211 tests), with new regressions for a multi-attempt repair, a long failure series, a pass under another command ending a series, one check whose reproductions differ across tasks, an error-only, a pending and an input-drifted run, a respelled executable, case-differing paths, a check record without an executable or exit code, the repair rule in status and a project in a subdirectory of its repository, its untracked files included, plus the packaging tests and the release gate. No live-model campaign or installed-host test exercised the changed prompt text.

## 3.3.15

- The repair step is one rule in the operating brief's review-and-repair section. Each repair is the smallest change that fixes the property the finding's obligation keys on, not only the reported case, with removing or generalizing machinery preferred over adding it, and its approach is stated before editing, starting from the skeptic's repair proposal. A repair of a finding that reports misbehavior is preceded by a check that reproduces it and fails for the finding's reason, rerun under the same name afterwards, or, when no practical automated reproduction exists, by a recorded reason and stand-in evidence, with the missing reproduction reported as a verification limit. Since reviewers do not receive recorded checks, that reproduction evidence, both runs or the reason and stand-in evidence, is cited in the requirements of the review that assesses the repair. Before a batch closes, a repair that changed which record, status or case a decision or obligation reads has every reader and writer of that state traced. A second missed case of the same kind after a repair, a repair undoing an earlier one or a repeated invariant violation, counting misses across repair attempts rather than findings one review reports together, now calls for fixing the shared cause, replacing the earlier signal of three successive passes with related findings. revise-code and the status rules string carry a summary; the skeptic prompt asks for a repair proposal of that shape, and the Tests and evidence lens, in the brief and in the reviewer prompt, asks whether a fix of misbehavior carries a failing check, and the reviewer prompt has it judged from the tests in the change and the reproduction evidence the requirements cite. It delivers the feature "Reproduce a bug with a failing check before repairing it", widened from defect work to every repair of misbehavior, and the quick wins on tracing the readers of changed state and on preferring the smallest repair. The behavior is model-owned; deterministic checks only, not observed on an installed host.

## 3.3.14

- Every reviewer dispatch now sends one report schema per kind, the same from a reviewer's first call to its last. The request id, the finding ids a skeptic judges or a continued lead closes, and a dialogue turn's positions are no longer bound in the schema; the report is checked against them when it arrives, as `validateReport` already did. The report schema requires `closures` and `positions` on every lead report, empty unless the dispatch asks for them: an entry in either on a dispatch that did not ask for it, or a value that is not an array, is refused with `invalid-result`. The prompt asks for the request id verbatim in `requestId` and the full finding id verbatim in closures and positions. Probes on 2026-10-20, recorded in [the resume-cost record](.nightshift/features/resumed-reviewer-cost.md), showed on Claude with Opus 5.5 and on Codex with Sol, outside any dispatch, that a schema differing only in its request id kept a resume's first call from reading its history from the prompt cache while an unchanged one did not. Whether runtime resumes now read from cache is to be read from the native event files of the first resumed dispatches on this release, which their receipts name; it is not claimed here.
- Reading a receipt back from its native report now treats absent and empty `positions` alike, since the report schema now requires the field on every lead report, which earlier releases asked for on a dialogue reply only.
- Evidence: recorded checks passed on this release: the runtime review, resume, docs-review and probe suites (177 tests), the host, core, regression, handover, continuation, adoption and scratch suites (188), and the delivery, ownership, release-delivery, acknowledgement, acceptance-checkpoint, hook-diagnostics, progress, creation-consistency and legacy-migration suites (342), plus the packaging test and the release gate. ## 3.3.13

- Every reviewer and skeptic report now carries a required `toolFailure` statement, empty when the reviewer's tools worked. A report that names a failure of the reviewer's own tools is not a usable assessment, whatever its status: its attempt fails with `reviewer-tools-unavailable` naming the reported failure, the dispatch tries its next candidate instead of ending on an incomplete report, a resumed dispatch fails with `resume-failed`, and receipt import refuses such a report. A report without the statement is refused with `invalid-result`. This fixes [A reviewer the host leaves unable to run commands ends its dispatch](.nightshift/BUGS_HISTORY.md#a-reviewer-the-host-leaves-unable-to-run-commands-ends-its-dispatch).
- A failed dispatch's `failure.json` records its final error `code` and, for a resume, `sessionFailed`, which is true when the attempt failed in its session, also when `termination-unverified` outranks `resume-failed`, and when a launched attempt ended with unproven termination before its report was judged usable, since its outcome is then unknown. Each status `resumeTargets` entry gains `continue`: `replace` once a resume of the named reviewer failed in its session or ended after launching its host without saving an outcome, holding through later failed replacements until a later dispatch of the lineage produces a receipt, and `resume` otherwise. A resume is never refused on its account.
- Each attempt that ends without a usable report records `hostFailure`, the terminal error its host reported, at most 2,000 characters, and its error message ends with `; the host reported: ` and that text. On Codex it comes from a failed turn, an `error` notification the host did not retry, a JSON-RPC error response to one of the attempt's own requests, whose rejection now names only the request, or, when no turn completed, a notification the host meant to retry. On Claude it comes from an error result with its API status and terminal reason, or the end of stderr when no result arrived. This delivers [Name the host's own failure in review attempt errors](.nightshift/QUICK_WINS_HISTORY.md#name-the-hosts-own-failure-in-review-attempt-errors).
- The handover acknowledgement observer reads a native history whole up to 64 MiB and beyond that by its last 64 MiB, plus a Codex rollout's first line within 1 MiB, instead of refusing a larger file. Each complete line read must decode as valid UTF-8, while an unfinished final line, which may still be mid-write, and the partial line before a larger file's window are not checked, so unlike 3.3.12 an invalid byte in an unfinished final line no longer makes the history unavailable. A Codex message without its own id is identified by its line's byte offset. An acknowledgement older than the window reads as missing, so repeating it recovers. This fixes [An oversized native session history blocks a handover it already accepted](.nightshift/BUGS_HISTORY.md#an-oversized-native-session-history-blocks-a-handover-it-already-accepted).
- A fix that an active feature would make obsolete is now carried by that feature instead of becoming a quick win or bug entry. Before recommending that a triaged fix be tracked, the operating brief's follow-up triage looks for an active feature that would remove or rewrite the lines the fix touches, excluding Exploring drafts and features that merely touch the same module, and names it or says that none qualifies; folding adds the fix as one line under the feature record's `## Carried fixes` heading. When the feature would remove only part of what a fix changes, and that part fails and can be verified on its own, only that part is folded and the rest stays a quick win or bug entry that names the carried part and links the heading, while the carried line links its evidence rather than that entry. The quick-wins and bugs templates carry the same rule, which existing indexes receive through setup's template adjudication below. The features template defines the heading. A feature's readback or spec and its acceptance cover its carried fixes, its history entry lists them, the pointer of an entry that kept the rest of a split fix is removed when the feature ships, and carried fixes are triaged again when the feature is retired, deferred indefinitely or marked won't fix, a split part rejoining its entry while that entry is active. On a sliced feature a carried line begins with the name of the slice whose work removes its lines; that slice covers it in its readback or spec, acceptance and history line, and the line leaves the record when the slice ships. Ready reports `carriedFixes` on each ready work unit of a feature whose record carries any, counting the bullets at column 0 under level-two `## Carried fixes` headings outside fences and raw HTML; the Ready skill shows the count beside the feature, and Ready reports a notice, which fails `--check`, for an Exploring draft whose record carries fixes.
- Setup now presents, on every run, where an existing backlog file's text differs from its bundled template, and changes that text only as the user decides, as [the governing spec](.nightshift/specs/setup-index-text-adjudication.md) describes. Inspect reports, per file, template guidance the file lacks and retired template text it still holds, the latter from `skills/init-backlog/retired-guidance.json`, which `tools/retired-guidance.js` generates from the templates' published history and the release gate keeps complete. Without an answer nothing changes. This is how existing projects receive the fold rule's template paragraphs.

## 3.3.10

- Handover is the only path that creates a delivery run. Ready explains before selection that choosing work requests delivery after investigation; a reply naming items selects them and keeps that handover request without creating a run, and confirmation of the investigated scope releases it. Ordinary chat agreement is carried out directly, and explicit requests for direct work or a pause take precedence. New delivery records keep the user's handover authority apart from observed continuation health and have no attended/unattended mode; a removed mode value is refused. Existing runs keep their exact retained runtime and historical mode. This fixes [Agreement reached in ordinary chat activates the lifecycle](.nightshift/BUGS_HISTORY.md#agreement-reached-in-ordinary-chat-activates-the-lifecycle) and retires the mandatory three-choice proposal of [Choose how agreed work proceeds](.nightshift/features/agreed-work-choice.md).
- Standalone revise-code, revise-spec, revise-docs and revise-lore open durable review contexts in `.nightshift/runs/review-state.sqlite` instead of delivery runs. They keep attributed receipts, skeptic verdicts, dispositions, repair closure, limits and the writer protection shared with delivery, and add no continuation, morning report, retrospective or triage; revision inside an owned delivery keeps using its task. A context takes no controller claim: its operations authenticate the owner's native activity, and its canonical actions recheck repair scope and writer ownership. A standalone docs context can record a mechanical-change exemption. Staged-only, unstaged-only and historical-range capture remain tracked under [Run-free revise](.nightshift/features/run-free-revise.md).
- Handover always attempts the host's continuation, a persistent goal on Codex and the registered Stop hook on Claude Code, and records the observed outcome. A technical failure is recorded once per distinct failure as a follow-up and accepted work continues in the current turn, while ownership, permissions, resources, explicit stops and exhausted limits keep their gates. An explicit `hold` stops the run while preserving its handover, so the Stop hook, which blocks only a running run, spends no reminders against it, and resumption needs a fresh continuation observation. The owner's visible acknowledgement, beginning `Handover accepted:` and saying `You can leave.`, is observed in the native history before runtime engineering is admitted, and status offers a read-only acceptance checkpoint that tells a pending continuation outcome, missing output, available output and unavailable history apart. Optional hook diagnostics describe unavailable hook integration, and historical wording aliases preserve earlier failure episodes and their follow-ups.
- Continuation reminders follow semantic progress. A cumulative achievement frontier backs a three-reminder allowance that repeated handover, claims, observations or restored proofs cannot replenish. Progress, reminders and closing discharge are kept as independent provenance outside the replaceable run state and written in the same transaction; when accounting is unavailable, automatic pressure stops without revoking admitted work. A record that carries schema-2 accounting without its provenance has lost it and grants no new continuation.
- A new handover is admitted only when every surviving delivery's obligations are authenticated as discharged, checked within fixed bounds inside the creation transaction. When the selected delivery itself is not yet replaceable, renewed closing obligations included, `handover` refuses with `overlapping-run`; when evidence is unavailable or cannot be authenticated, a verification bound is exceeded, or another surviving delivery is undischarged, it refuses with `delivery-consistency-unavailable`. It also refuses with `report-delivery-pending` while the latest completed handed-over delivery's morning report awaits its recipient's reply, which another admitted session of the same project, resource mode and retained store can record on that completed run. A completion discharges only the closing record it completed, so a delivery triaged again or given a closing reset after completion holds replacement back until it completes again. Closing reviews and checks are bound to the closing record they were dispatched for. Retained admission and the review inventory refuse a delivery or review database whose schema version they do not support. Windows write ownership admits only ordinary path spellings: it refuses a segment ending in a dot or space, a colon (NTFS stream syntax and drive-relative forms), a reserved device name, and a spelling such as an 8.3 short name that differs from an existing component's filesystem name other than in case. A reservation stored with a refused spelling fails closed for every writer while read-only assessment stays available.
