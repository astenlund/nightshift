# Changelog

Release notes for the Nightshift plugin, newest first. The plugin manifests carry the current version. Deterministic and zero-inference checks remain distinct from model-owned observations.

The entries through 3.3.3 were moved here from the README on 2026-10-05 and split by version. A version without an entry had no notes recorded there.

## 3.3.28

- A GLM reviewer on Mistral Vibe can now be resumed. `review.resume` on a Vibe receipt no longer refuses with `resume-unsupported` because of the host; a resumed Vibe session keeps the directory it started in, so the dispatch refreshes the lineage's private copy under `.nightshift/runs/c/` at the path its first dispatch recorded, recreating it when the disposable copies were cleared, materializes the current snapshot there, and runs `vibe.exe --resume <session>` with every other flag kept, from an attempt home seeded with the predecessor attempt's exported session store and the predecessor home's pinned plugin store (without which Vibe refuses to resume before any model call) and under the predecessor's reviewer prompt byte for byte, since Vibe replaces a session's stored system instructions with changed ones and a changed prefix loses the cache; the dispatch's rules reach the reviewer through its turn prompt, which says the copy at the same path was refreshed and that earlier reads may be stale. `resume-unsupported` now names the reason a Vibe session's retained source cannot be reused (a private copy not recorded as one, one still holding a `project/` folder, changed attribution evidence, or a missing session store, plugin store or prompt), status's `resumeTargets` advise `replace` only then or after a resume failed in its session, and a Vibe resume that fails in its session is `resume-failed` as on the other hosts. The report of a resumed Vibe run is taken after the last user message of its output, which carries the whole conversation. Every Vibe attempt and receipt records `vibeCalls`, the model calls its exported session journal holds with their input and cached input totals and the first call's input and cached input, so a resumed turn's cost can be judged against a replacement's: Vibe resends the session's whole context on every call, and over the replacement closures recorded in two stores a resumed turn equals a replacement's input after about 14 and 26 calls at the predecessor's final context, so the saving holds only while resumed turns stay short, which the quick win "Keep resumed Vibe turns short enough to beat replacement" tracks. [The Vibe reviewer host spec](.nightshift/specs/vibe-reviewer-host.md) records the source reading behind the design.
- Evidence: in `tests/runtime-vibe.test.js`, a Vibe lineage resumed through the real launcher against the fake executable in its refreshed copy, recreated after the copies were cleared, with the seeded stores, the carried prompt, the resumed prompt text, the report taken after the last user message, `vibeCalls` on the receipt, the closure ended, a dialogue turn and replacement once a resume fails in the session, which fails on 3.3.27 with `resume-unsupported`; each refusal registering no worker and routing closure to replacement; the launcher's `--resume` invocation, seeding, prompt carry-over, journal figures and refusals. The Vibe (34 tests), continuation (9), review (89) and resume (54) runtime suites, the packaging and release-gate suites (20), the release manifest check, the ready parser check and the backlog line check passed. The fake Vibe executable now holds its input open until the launcher ends it: ending the input of an already exited stand-in raised EPIPE, which the launcher counts as a failed attempt, and made the launcher tests fail intermittently under load on 3.3.27 as well. Live evidence is from standalone probes of 2026-11-03 on installed Vibe 3.0.3 with `glm-5-3` under the launcher's isolation recipe, outside the runtime: a session resumed four times with its directory replaced in place read the new content each time and ignored a decoy `--workdir`, resumed from a fresh home seeded with the exported session store and the plugin store, and read 97 and 73 percent of its first resumed call's input from cache within about two minutes, 18 percent after a prompt change and 32 percent after a 21-minute gap. ## 3.3.26

- A delivery run or standalone review context the user considers settled can now be closed. The administrative migration entry gains a read-only `close-manifest`, which shows what closing drops, and `close`, which records the user's exact reply and reason and moves each member to a new final status, `closed`, distinct from `complete`. Stopped records can be closed, and so can running ones whose former owner has ended, by adoption's inactivity evidence. One manifest can span both run stores. The current release can close records bound to any older release, as this repository's two review contexts bound to 3.3.12 need.
- An older-release guard keeps sessions that cannot read `closed` from failing project-wide. Close refuses while another unfinished record bound to an older release exists, unless the user's reply acknowledges that record by name, and while a session bound to an older release lists the project with an activation owner that is alive or cannot be inspected; a binding with no recorded activation, or whose ended owner is followed by a newer failed activation, is listed as a warning instead. The guard sees only sessions in the admitted release registry.
- A closed record is read-only in the current release: every runtime operation and store write that would change it refuses with `run-closed`, while status, inspection, history and `wait` still read it; through an installed release, a session other than its controller on its exact binding is refused earlier by release admission, with `resource-owner-mismatch` or, for adoption, `adoption-run-unavailable`. Its `status` carries its closure and no next tasks, and it owes no morning report, follow-up notice or acceptance checkpoint. The creation gate counts it discharged by its close row, the release service treats it as finished, Ready omits it and offers close beside the existing pickup, and `wait`, hooks, setup and standalone repair treat it as ended.
- Evidence: a new deterministic suite (`tests/runtime-close.test.js`) covers closing a stopped delivery and a running review context, a two-store close with a failed second transaction and its identical retry, the runtime's refusal codes (close's release-admission refusals, `resource-operation-busy` and `hook-activation-required`, rest only on a test pinning close as a migration write action), the write guard, the closed status brief, the creation gate's close-row rule (including a status-preserving revision appended by a simulated older runtime, and a status edited without a close row), the older-release guard with acknowledgement, and Ready's close offer. Two release-harness suites run the installed boundary: `tests/release-close-migration.test.js` closes two running review contexts bound to an older release, with ended owners, through the migration entry under real administrative admission, after which `compact-history` swaps their version-2 store, and refuses while another connection holds the write-ownership mutex; `tests/release-closed-records.test.js` covers `resolve` admitting a handover over a closed selection, older-bound or resource-less, and collection dropping a bundle referenced only by closed records. No installed host has run the change, so the model-owned close presentation in Ready and handover is unobserved, and the live close of this repository's two 3.3.12 review contexts is a post-release follow-up and has not run.

## 3.3.23

- Run history no longer keeps a full state copy for every revision. Store version 3 keeps each run's current revision and every 64th revision as a full row and every other revision as a backward structural delta from the next revision, with each row's byte length and SHA-256; every history reader goes through one module that returns the exact text a full row would hold and fails with `history-unavailable` when a rebuild does not match. A store this release creates starts at version 3; an earlier store keeps full rows until the new administrative migration action `compact-history` rewrites it, retired runs included, without changing a byte that inventory, certificates or accounting recovery read; inventory's store hash counts a version-3 store as version 2, so retirement approvals and identical retries stay current across compaction. The action refuses while any record in the store is running, builds the migrated store beside the original, verifies every row, swaps by renaming, keeps the original as a backup, and resumes from any state an interruption or a blocked rename leaves; `finish` verifies again and deletes the backup. Releases before 3.3.23 refuse a version-3 store with `state-version`. On a copy of this repository's 8,612,036,608-byte delivery store, compaction took 216 seconds and produced a 238,313,472-byte store, with 17,124 delta rows holding 5,093,893 bytes and 342 full rows holding 144,915,789; `finish` took 47 seconds.
- Evidence: new deterministic tests for the delta grammar, compact writes and reads on version 1, 2 and 3 stores, damaged rows, the action's refusals and every resume state, including a swap blocked by an open handle on Windows, a version-1 store without artifacts and a row that is not JSON, and compaction of retired deliveries with a superseding certificate, after which inventory, its hash, raw inspection and an identical retirement retry match, and `tools/fortnight.js` numbers match before and after compaction. On the real-store copy, inventory's three pages, raw inspection of four revision ranges, one across a keyframe, and `tools/fortnight.js` output matched the uncompacted store. No installed host has run the change.

## 3.3.22

- Delivery creation and migration inventory and manifest no longer refuse a store whose referenced evidence has grown past the totals their evidence passes allowed. Each pass hydrated every run's referenced artifacts under one budget, at most 64 MiB of distinct bodies and 256 MiB with repeat references counted again, and discarded the result: creation over retired and resource-only legacy records, inventory and manifest over every record. Each pass now verifies the references instead, reading, identity-checking and parsing each distinct body once and keeping none, so a repeat reference reads nothing and no pass has a total; a single body over 64 MiB, the most the old allowance ever admitted, is still refused with `migration-evidence-bound`. Missing, changed and malformed evidence keep their codes. Raw inspection keeps its own 8 MiB bound, and the 64 MiB ceiling on current and latest states plus accounting input is unchanged. On this repository's store, inventory's pass held 54.34 of its 64 MiB distinct and 229.61 of its 256 MiB expanded allowance, and the largest referenced body was 213 KiB, so the totals, not any single body, would have refused it as runs accumulated.
- Evidence: the creation and migration runtime tests passed, with new cases for evidence past both old totals through creation, inventory and manifest, a body read once however often it is referenced, an oversized body, and the missing, changed and malformed evidence codes; the new creation, inventory and manifest case fails on 3.3.21 with `migration-store-unavailable`. No installed host has run the change.

## 3.3.21

- Delivery creation and migration inventory no longer refuse a store whose artifact bodies total more than 64 MiB, which blocked new delivery with "Artifact identity scan exceeds its bound" and diagnosis with "Retirement artifact inventory exceeds its bound". Their identity scan now reads only the bodies whose top level carries `runId`, the ones its owner, identity and retirement certificate checks need, after requiring every body to be valid JSON nested at most 1000 levels deep, and refuses a run-bound body over 8 MiB, the bound each of its writers enforces, instead of capping the store's total artifact size and row count. A body holding a raw NUL byte, which 3.3.20 admitted by reading it only up to that byte, is now refused as invalid JSON; no writer produces one. Because the total check ran before most of creation's and inventory's other checks, a store it refused is admitted, without changes to it, by a handover the 3.3.21 runtime executes, unless one of those later checks, which the earlier refusal masked, refuses it with its own message. That handover needs a native session started after the update: a session already bound to an earlier release keeps that release's creation gate, so a retry there is refused again, or with `migration-new-session-required` where retirements exist.
- Evidence: the creation, migration, delivery and progress runtime tests passed, with new cases for other evidence past 64 MiB, an oversized run-bound body, a JSON5 body, a run-bound body with an unknown owner or a corrupt identity, and the points where SQLite's reading of a body could part from `JSON.parse`: an escaped `runId` key, which SQLite selects as `JSON.parse` reads it, a body holding a NUL byte, which is refused as invalid JSON, and nesting past 1000 levels, which SQLite's JSON functions refuse. On this repository's store the run-bound bodies the checks receive held 8,170,725 of 66,104,393 bytes of artifact bodies, while SQLite still validates and selects across every body. No installed host has run the change, and the project whose handover was refused has not retried it.

## 3.3.19

- An attached check's reproduction is now drawn from the failures of the same name and command in the last series on the same task that no successful run of that name, under any command, interrupts, not only its last failing run; pending runs, runs that exited zero while their inputs changed and failures of another command neither belong to that series nor end it. It gives the first failure with its input count and digest, and under `laterFailures` the outcome and output tail of each of the next three, with `omittedFailures` counting any after them, since the records do not say which failure the controller confirmed fails for the finding's reason. `passesSince` counts the successful runs between that series and the passing check, not counting a run that exited zero while its inputs changed, and the prompt says that reruns after later edits make it nonzero, so the reviewer judges from the failure output whether the series belongs to the fix under review. Each input that differs between the first failure and the passing run carries both runs' hashes, so a file only one run declared, or one run found missing, can be told apart from a changed one.
- Executables compare after path normalization, and on Windows executables and input paths compare without regard to case; one check recorded on several tasks with executables that compare equal this way is listed once, but now only when none of the tasks has a reproduction for it, each task with one getting its own entry: 3.3.18 showed the first reproduction it found among the merged tasks for all of them and dropped the others', so a covered task's own reproduction could be replaced by an unrelated one. When searching for a reproduction, a check record without an exit code is now judged by whether it passed, where 3.3.18's search took every such record that was not pending for a failure. For a project in a subdirectory of its repository, the reviewer's `diff.patch` now uses project-relative paths, matching the reviewer's copy, as the touched inputs already did.
- The prompt says a check's inputs are the ones it declares. The repair rule in status, the operating brief and revise-code say to rerun the same command under the same name on the same task after a repair; status and revise-code also say to rerun that reproducing check before a review once its inputs change, and the brief says so for any check whose inputs changed, since a stale check is not attached and neither is its reproduction. The runtime reference states the probe copy's layout.
- Evidence: the runtime review, docs-review and probe suites and the seeded-defect suite fixtures passed (211 tests), with new regressions for a multi-attempt repair, a long failure series, a pass under another command ending a series, one check whose reproductions differ across tasks, an error-only, a pending and an input-drifted run, a respelled executable, case-differing paths, a check record without an executable or exit code, the repair rule in status and a project in a subdirectory of its repository, its untracked files included, plus the packaging tests and the release gate. ## 3.3.15

- The repair step is one rule in the operating brief's review-and-repair section. Each repair is the smallest change that fixes the property the finding's obligation keys on, not only the reported case, with removing or generalizing machinery preferred over adding it, and its approach is stated before editing, starting from the skeptic's repair proposal. A repair of a finding that reports misbehavior is preceded by a check that reproduces it and fails for the finding's reason, rerun under the same name afterwards, or, when no practical automated reproduction exists, by a recorded reason and stand-in evidence, with the missing reproduction reported as a verification limit. Since reviewers do not receive recorded checks, that reproduction evidence, both runs or the reason and stand-in evidence, is cited in the requirements of the review that assesses the repair. Before a batch closes, a repair that changed which record, status or case a decision or obligation reads has every reader and writer of that state traced. A second missed case of the same kind after a repair, a repair undoing an earlier one or a repeated invariant violation, counting misses across repair attempts rather than findings one review reports together, now calls for fixing the shared cause, replacing the earlier signal of three successive passes with related findings. revise-code and the status rules string carry a summary; the skeptic prompt asks for a repair proposal of that shape, and the Tests and evidence lens, in the brief and in the reviewer prompt, asks whether a fix of misbehavior carries a failing check, and the reviewer prompt has it judged from the tests in the change and the reproduction evidence the requirements cite. It delivers the feature "Reproduce a bug with a failing check before repairing it", widened from defect work to every repair of misbehavior, and the quick wins on tracing the readers of changed state and on preferring the smallest repair. The behavior is model-owned; deterministic checks only, not observed on an installed host.

## 3.3.14

- Every reviewer dispatch now sends one report schema per kind, the same from a reviewer's first call to its last. The request id, the finding ids a skeptic judges or a continued lead closes, and a dialogue turn's positions are no longer bound in the schema; the report is checked against them when it arrives, as `validateReport` already did. The report schema requires `closures` and `positions` on every lead report, empty unless the dispatch asks for them: an entry in either on a dispatch that did not ask for it, or a value that is not an array, is refused with `invalid-result`. The prompt asks for the request id verbatim in `requestId` and the full finding id verbatim in closures and positions. Probes on 2026-10-20, recorded in [the resume-cost record](.nightshift/features/resumed-reviewer-cost.md), showed on Claude with Opus 5.5 and on Codex with Sol, outside any dispatch, that a schema differing only in its request id kept a resume's first call from reading its history from the prompt cache while an unchanged one did not. Whether runtime resumes now read from cache is to be read from the native event files of the first resumed dispatches on this release, which their receipts name; it is not claimed here.
- Reading a receipt back from its native report now treats absent and empty `positions` alike, since the report schema now requires the field on every lead report, which earlier releases asked for on a dialogue reply only.
- Evidence: recorded checks passed on this release: the runtime review, resume, docs-review and probe suites (177 tests), the host, core, regression, handover, continuation, adoption and scratch suites (188), and the delivery, ownership, release-delivery, acknowledgement, acceptance-checkpoint, hook-diagnostics, progress, creation-consistency and legacy-migration suites (342), plus the packaging test and the release gate. ## 3.3.13

- Every reviewer and skeptic report now carries a required `toolFailure` statement, empty when the reviewer's tools worked. A report that names a failure of the reviewer's own tools is not a usable assessment, whatever its status: its attempt fails with `reviewer-tools-unavailable` naming the reported failure, the dispatch tries its next candidate instead of ending on an incomplete report, a resumed dispatch fails with `resume-failed`, and receipt import refuses such a report. A report without the statement is refused with `invalid-result`. This fixes [A reviewer the host leaves unable to run commands ends its dispatch](.nightshift/BUGS_HISTORY.md#a-reviewer-the-host-leaves-unable-to-run-commands-ends-its-dispatch).
- A failed dispatch's `failure.json` records its final error `code` and, for a resume, `sessionFailed`, which is true when the attempt failed in its session, also when `termination-unverified` outranks `resume-failed`, and when a launched attempt ended with unproven termination before its report was judged usable, since its outcome is then unknown. Each status `resumeTargets` entry gains `continue`: `replace` once a resume of the named reviewer failed in its session or ended after launching its host without saving an outcome, holding through later failed replacements until a later dispatch of the lineage produces a receipt, and `resume` otherwise. A resume is never refused on its account.
- Each attempt that ends without a usable report records `hostFailure`, the terminal error its host reported, at most 2,000 characters, and its error message ends with `; the host reported: ` and that text. On Codex it comes from a failed turn, an `error` notification the host did not retry, a JSON-RPC error response to one of the attempt's own requests, whose rejection now names only the request, or, when no turn completed, a notification the host meant to retry.
