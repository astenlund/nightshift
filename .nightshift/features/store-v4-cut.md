# Cut store v4 and reduce the release system

Created on 2026-11-10 from a step of [the assessment worklist](../reports/assessment-worklist-20261018.md), at the user's decision, so that the cut has one owner. It covers the worklist's Remove 1, 2 and 4 and Add 12.

## Scope

One breaking release: a new store version that refuses older ones; legacy migration and the provenance tables deleted; the release system reduced to the bundle copy, bootstrap, locator, registration and lookup in the same cut, since the run state carries the registry's identifiers. Keep the runtime-derived reminder cap and, for now, the PowerShell process inspection. Running runs complete before the upgrade, the run that delivers v4 runs on 3.3.x, and the first v4 run starts fresh.

The cut keeps what the conditions work on the current store built, and adds the open run from [Keep a handed-over run open for triage after delivery](handover-open-for-triage.md): reopening after triage, a live defect returning as a repair, a spec amended under a recorded decision, and a settled run reopened by a later decision of the user until a later run supersedes it. It also adds the three condition classes in its gate design, and keeps the recorded-decision operation, which [Recorded decisions on the unsettleable closing hold](../specs/recorded-decisions.md) ships on the current store from 3.3.38 for the closing hold no task assessment can settle; the cut decides whether the closing changes Open names become settleable too. Its derived reminder cap writes no revision, which closes the Stop hook race recorded under the worklist's Remove 1.

A release that adds a dependency on a slated module records here what the cut must keep.

## Decisions

- 2026-11-09, the user: `close`, `close-manifest` and `compact-history`, which today enter through `migration-cli.js` and `legacy-migration.js`, move to a small administrative entry that survives the cut, with the constants and table definitions they share with the legacy modules relocated. `store.js` imports its table definition from the same place.
- 2026-11-09, the user: a run settled in a store older than v4 does not reopen across the cut, and a defect found in its work goes to a new run.
- 2026-11-17, the user: the v4 delivery creation gate keeps the property [Settled-record verdicts at delivery creation](../specs/settled-record-verdicts.md) gives the current store, that its work follows what changed since it last ran rather than the project's whole history.
- 2026-11-23, the user: step 3b of [the assessment worklist](../reports/assessment-worklist-20261018.md), the session-close sequence with its publication choice and completion stamp, acceptance of unmet obligations at the final gate and the intermediate stage barriers, follows this cut and is built on the v4 store.

## Open

- The v4 store design, including whether `compact-history` is still needed; if it is not, it goes too.
- The reduced release system's bootstrap keeps the hook text identical across releases, which [Codex keeps asking to trust Nightshift's hooks again](../BUGS.md#codex-keeps-asking-to-trust-nightshifts-hooks-again) needs; added on 2026-11-11 at the first pruning pass.
- Decide with the cut whether the user's decision can settle closing changes since triage that cannot be established (a missing baseline on a run of only spec tasks, an unusable stored baseline whose digest, files or artifact body fail their checks, and a baseline outside Git that cannot be compared), which [Recorded decisions on the unsettleable closing hold](../specs/recorded-decisions.md) leaves unsettleable. Three obstacles stand in the way. A decision there needs a stand-in baseline wired through every closing reader. Progress accounting cannot become current again after an unusable baseline, which matters until the cut removes that accounting. And outside Git, capturing an inventory for the decision fails whenever the comparison does. Added on 2026-11-16 by the user's choice.

## Carried fixes

- A hook generation change strands a running run's session: a new generation in the locator leaves a session that observed the old one refused with "This session has not observed the registered hook generation", under `internal/releases`, even from an automatic preparation. The replacement drops generations and activations, so a running session keeps working across a plugin update or setup. Evidence: [the moved bug report](../bugs/hook-generation-strands-running-session.md).
- Delivery creation in `internal/runtime/creation-consistency.js` hydrates every completion snapshot, including superseded ones, before judging discharge. A single completed run whose evidence exceeds the 8 MiB allowance can block every new handover. Verify completion evidence identity without hydrating every snapshot and resolve only the evidence the discharge decision needs. Evidence: [the moved bug report](../bugs/creation-hydrates-completion-snapshots.md).
- Close's no-activation warning names a remedy that cannot clear it: the older-release guard in `internal/runtime/close.js` warns `no-activation` for a session bound to a release older than close support with no recorded activation, telling the user to end or restart it, which cannot clear the warning while the binding stays `bound`; only retiring the binding does, and that can itself be unavailable on an old registration base. The replacement guard warns only about what the user can clear and names a remedy that works. Evidence: [the moved quick win](../bugs/close-no-activation-warning.md).
- A Stop hook reminder write can invalidate a request launched in the background: `handleHook` in `internal/runtime/hook.js` calls `store.remind`, whose write advances the run revision, so a revision-stamped request a controller launched in the background before ending its turn is refused `stale-owner` or `stale-state` when the reminder write lands before admission; seen in five Hermes runs: on 2026-10-11, on 2026-10-24, in two later runs, one of them on 2026-11-09, and on 2026-11-19 in delivery `2b1f0df2` on 3.3.40, where requests passing each result's revision forward were refused `stale-owner` after checks of 15 to 40 minutes. Hermes delivery `c4991249` on 3.3.36, which the bug report also records, is not among the five, since its reporter inferred the hook's write from timing and a `hookIntegration.observedAt` stamp that cannot tell the hook's write from another. The replacement's derived reminder cap writes no revision, so a request stamped at the pre-reminder revision stays admissible; until then, staying in the turn until the worker registers and holding it on runtime `wait`, with a send helper that re-reads status and retries, has avoided it. Evidence: [the moved bug report](../bugs/stop-hook-reminder-race.md), and for delivery `2b1f0df2` the maintainer inbox report `2026-11-19-closing-review-probe-and-revision-races.md`.
- A store past the creation gate's shared input allowance with no verdict progress cannot be closed or handed over: when a pass of the gate in `internal/runtime/creation-consistency.js` runs out of that allowance before it keeps any verdict, every retried handover makes no progress, and the administrative close, which re-runs the same pass in `internal/runtime/close.js`, refuses `close-bound-unavailable` and rolls back, so handover and close stay refused until the charged input fits or verdicts accumulate. Found on 2026-11-22 by the spec assessment in delivery `e3ad3279-9d50-4a4f-97c0-8d82790d76ba` and accepted by the user that day as a stated limit of this release, so it has no stopgap; folded here from its bug entry by the user's pruning pass of 2026-11-27. The v4 creation gate never leaves a store whose pass keeps no verdict without a route to handover or close. Evidence: the Administrative close paragraph of [the post-completion closing hold's routes](../specs/post-completion-closing-hold.md#5-routes).
