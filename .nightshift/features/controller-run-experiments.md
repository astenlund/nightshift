# Controller-run experiments

## Origin

Raised again by the user on 2026-10-03, after a backlog session that ran several experiments by hand (a dual review by two reviewer models, compacting a reviewer thread before its resume, explicit dependency and link checks), when proposing to compare a reviewer guided by the review lenses with an unguided one, in their words: "i was thinking this could be part of the "controller running experiments" feature; the controller decides which experiment to run (astra vs fable, guided vs unguided, etc.)". On learning that nothing in the backlog tracked it any longer: "that's unfortunate, i definitely want it back."

## How it was lost

Nightshift v2 carried the capability inside an Exploring draft for a two-level run management design, a run manager with an optional shift supervisor, which never shipped. On 2026-09-06 the v3 migration simplified that draft into the optional supervisor now tracked by [Spawn a shift supervisor when admin work fills the controller's context](context-triggered-supervisor.md), and its disposition did not name the experiment authority. A sibling draft for an experiment evidence ledger was simplified into recording material conclusions in the ordinary run record, "without a separate ledger or experiment framework" ([V3-MIGRATION.md](../../V3-MIGRATION.md)), now tracked by [Carry settled decisions and experiment evidence into later reviews](v3-review-decision-context.md). The 2026-10-01 audit of capabilities that left v2 without a disposition covered shipped capabilities, so this part of an unshipped draft went unnoticed until 2026-10-03.

## Delivery-boundary reconciliation

[Handover as the delivery boundary](handover-only-delivery.md) makes handover the sole creation path for new delivery runs and removes attended/unattended modes. This experiment feature remains unimplemented. Its original dated answers about experiments inside agreed runs keep their authority and budget requirements; references below to attended runs preserve the earlier delivery boundary, not a current creation path. Any implementation spec must apply the current handover boundary to experiment delivery and preserve ordinary chat as direct work.

## Direction

Restated from the v2 draft as the starting point. The answers the user agreed on 2026-10-05, under Settled at graduation, adopt most of it and narrow its first point; the details they do not settle are named under Before implementation:

- The controller may devise, authorize and run bounded experiments without asking first when every variant stays within the authority already granted, keeps every mandatory gate, and does not put the primary result at material risk. An experiment that risks the outcome, permissions, publication, destructive actions or the user's intent needs the user's authority before it runs.
- Each experiment records its hypothesis, control and treatment arms when comparable work exists, how work is assigned to arms, what is measured, its stop conditions and cost limit, how contamination between arms is avoided, its rollback, and the result that would decide the hypothesis.
- Arms are kept isolated and every variant is identified, with enough evidence to tell a treatment effect from differences between tasks; a separate evaluator judges the outcome where practical. A/B control is preferred when comparable work exists; otherwise a weaker design may be used, with its confounders reported and an inconclusive result allowed.
- Instruction variants run as temporary overlays, never by silently rewriting the canonical instructions during a run.
- A variant joins real work only when every arm stays compliant and useful; one that could jeopardize the primary result runs in shadow or waits for the user.
- Results never promote themselves. The report states the hypothesis, method, sample, observed effects, costs, limits, side effects, conclusion and recommendation, and offers adopting, repeating, revising, tracking or discarding the change for the user to decide.
- In the v2 draft a shift supervisor executed experiments that dispatch workers and the run manager ran only one-step probes itself; in v3 the controller can coordinate directly, and the optional supervisor is still Exploring.
- Added by the user the same day, in their words: "revise-lore could suggest experiments too, recorded somewhere durable for future sessions". A session retrospective may then propose experiments grounded in that session's evidence, kept where a later session can find and run them.
- Added by the user the same day, in their words: "`/ready` should perhaps ask the user upon task selection whether it's allowed to spend extra tokens on experiments or not". Spending extra tokens on experiments would then be part of the authority granted when work is selected, not assumed under the first point above. The user refined it at once, in their words: "perhaps only ask if it actually aims to run any experiments, to reduce noise"; the question is asked only when the controller plans an experiment for the selected work. The user then suggested how that plan is made, in their words: "the "should we run any experiments?" question could be a subagent task running in parallel with the readback review". A background agent decides whether the selected work warrants an experiment and proposes it while the user reads the readback, alongside the background work of [Background review and assessment of selected work](selection-review-and-assessment.md), so the permission question arrives with a concrete proposal without delaying the readback. The user settled its form, in their words: "permission and token allowance should be settled in a single question-response. the controller should suggest a number that the user can adjust". One question proposes the experiment with a suggested token allowance, and the user's single answer grants it, adjusts the number or declines.

## Settled

- **A separate experiments ledger.** The user decided on 2026-10-03, in their words: "a separate experiments ledger would be good too, not fond of the simplification". This reverses the part of the 2026-09-06 migration decision that kept experiment evidence only in the ordinary run record "without a separate ledger". Restated as the starting point: the controller owns the ledger; it records only material conclusions and the evidence that decides them, never dialogue transcripts or routine progress; entries are written at the boundaries that produce evidence about an experiment, such as a review round's adjudication, a repair decision, a verification or a recovery; and the report disposes every retained experiment toward workflow machinery, instructions, backlog work, further experimentation or rejection, for the user to decide.

## Candidate experiments

From 2026-10-03: the reviewer model (Astra versus Fable); a reviewer guided by the review lenses versus an unguided one that receives the change and the governing requirement but no lenses; dual versus single review; and compacting a Codex reviewer thread before its resume, and above which threshold. That day's manual trials are recorded in [Dual strong review for critical work](dual-strong-review.md) and [Make resumed reviewers actually cheap](resumed-reviewer-cost.md).

From 2026-10-04: the keyword scoring of [A greppable format for open and settled questions](open-questions-format.md), which gives each keyword +10 for a confirmed match and -1 for a rejected one; the user suggested that experiments settle its retirement floor, starting score, the two weights and whether old credit fades, in their words: "the scoring system could be an object for the experiment feature to settle".

## Settled at graduation

The user agreed these answers on 2026-10-05, when the entry graduated from Exploring to current work. Each question is kept with its answer.

- The authority boundary, reconciling the first point of the direction with the token permission asked at selection. Settled: an experiment that spends no extra tokens, such as analysing evidence already recorded or choosing among assignments the controller would make anyway, may run without asking within the authority already granted. Anything that spends extra tokens needs the allowance granted at selection. No experiment may weaken a mandatory gate or put the primary result at risk; such a variant runs in shadow or waits for the user.
- The 2026-09-06 migration agreed on no separate experiment framework; the user has since asked for controller-run experiments and a separate ledger, so how much further structure they need, such as a recorded design with arms and a report section, is to be settled with the user. Settled: each experiment records its design in the ledger before it runs, meaning its hypothesis, arms and how work is assigned to them, what is measured, its stop condition, its cost limit and the rule that decides the outcome. Instruction variants run as temporary overlays, never as edits to the canonical instructions, and results never promote themselves. Nothing beyond the ledger and its runtime operations is built as a framework.
- Budgets, arm assignment, contamination controls, evaluator independence, and what evidence counts as directional, conclusive or inconclusive. Settled: an experiment's cost limit comes out of the granted allowance. Arms run in fresh contexts without shared transcripts, and where practical a separate evaluator judges the outcomes without knowing which arm produced them. A result is conclusive only when the decision rule declared beforehand is met, directional when it is consistent but under-sampled, and otherwise inconclusive, with its confounders named.
- The ledger's home and lifecycle: where it lives and whether it is scoped to one run or outlives runs; its creation, identity, refresh and invalidation, and what every reader does when it is absent, stale or malformed; atomic appends and deterministic resume after a partly persisted write; compaction without losing evidence the report needs; and whether a fully disposed ledger is archived or deleted, and what provenance remains. Settled: the ledger lives in the project's run store, the SQLite database the runtime already owns, and outlives runs; the first experiment operation creates it, and each experiment has its own identity. It is written only through runtime operations, so every append is atomic and resume after an interrupted write is deterministic, and compaction cannot lose it, since it lives outside the controller's context. Each entry moves through proposed, approved, running, concluded and disposed; the user disposes each concluded result by adopting, repeating, revising, tracking or discarding it; and disposed entries stay as history rather than being archived or deleted. An absent ledger means no experiments, and a malformed one makes experiment operations refuse with an error naming it while primary work continues.
- The permission asked at selection: how the suggested allowance is estimated and what the controller does when an experiment approaches it; what the background agent that proposes experiments receives, such as the selected entries, the readback, the ledger and pending proposals from retrospectives, and how its proposal reaches the user; what happens when an experiment only suggests itself later in the work; how it combines with the other questions at the end of Ready, such as [Ready handover confirmation](handover-only-delivery.md) and the quick win [Offer to revisit an entry's settled decisions before starting work](../QUICK_WINS.md#offer-to-revisit-an-entrys-settled-decisions-before-starting-work), so that the questions stay few; how it relates to a run's budgets in [Preserve run preferences and enforce supported resource budgets](v3-run-preferences.md); and what the controller may still do without it, such as analysing evidence already recorded at no extra token cost. Settled: the suggested allowance is estimated from the experiment's arms and the recorded cost of their roles, and an experiment nearing it stops at its stop condition and reports inconclusive rather than overrunning. The background proposal agent, which by the direction above judges the selected work while the user reads the readback, also sees the ledger's pending proposals relevant to it, and its proposal reaches the user as the one experiment question, asked only when an experiment is proposed and alongside the other questions at the end of Ready rather than as a round of its own. An experiment that suggests itself mid-run is asked about then when the user is present, and otherwise recorded as proposed for a later session without spending. Without an allowance, the controller may still run experiments that cost no extra tokens, as the authority answer above says.
- Where experiments that a retrospective proposes are kept so that later sessions find them, such as the ledger outliving runs or a section of the backlog, and how a later session learns of them and picks one up, for example through Ready; how a proposal differs from an experiment already run, and who decides to run it; and how that destination sits beside those that [Retrospective routing by audience and instruction precedence](revise-lore-audience-routing.md) settles for the retrospective's other output. [Answer open backlog questions cheaply in retrospectives](retrospective-open-questions.md) would hand questions too costly to answer cheaply to this entry as proposed experiments. Settled: proposals are kept in the ledger as proposed entries, not in the backlog, and the ledger is the experiments' destination beside those the routing entry settles. A later session learns of them through the background proposal agent at selection, and the user decides at selection whether to run one; questions handed over by the open-questions retrospective arrive the same way.
- How the ledger relates to [Carry settled decisions and experiment evidence into later reviews](v3-review-decision-context.md), which records material conclusions in the run record and delivers them to later reviews. Settled: concluded results reach later reviews through that entry's delivery, which this ledger feeds.
- Whether experiments run only inside agreed runs or also on their own, and how the authority boundary is stated where a run loads it. Settled: experiments run inside agreed runs, attended or handed over, and a user who wants an experiment on its own asks for it as agreed work. The operating brief states the authority boundary.
- How it relates to [Measure whether the lifecycle catches defects](defect-detection-measurement.md), whose planted-bug suite is a controlled harness for comparing review arms, and to [Model knowledge base](model-knowledge-base.md), where results about models would land. Settled: the planted-defect suite can serve as a harness, and a result about a model becomes a proposed entry for the model knowledge base, which lands only with the user's yes like any other.

## Before implementation

The entry ships in three slices, as the index records: the MVP covers the authority boundary, experiment designs, the ledger and the selection question for experiments the controller proposes in agreed runs, asked with the readback; the second slice adds retrospective proposals and their pickup; and the third adds the background proposal agent at selection, built on [Background review and assessment of selected work](selection-review-and-assessment.md). Two points the controller added while recording these answers, which the user has not yet confirmed, are for the MVP's spec to settle: whether an experiment whose run ends before it concludes is recorded as interrupted and reported inconclusive, and whether the granted allowance counts toward the run's budgets once [Preserve run preferences and enforce supported resource budgets](v3-run-preferences.md) ships. The direction's remaining details, which the settled answers do not cover, are likewise for that spec to settle with the user: each experiment's rollback, its contamination controls beyond fresh contexts, the identification of every variant and enough evidence to tell a treatment effect from differences between tasks, the preference for A/B control with a weaker design allowed when no comparable work exists, the rule that a variant joins real work only when every arm stays compliant and useful, and the report's full list of fields. Each slice settles its operations and wording in a concise governing spec in `.nightshift/specs`, rides with a plugin version increase, and decides at the start of its work between a budgeted installed-host check of the model-owned behavior it adds and deterministic evidence only. Tracking and readiness do not authorize implementation.
