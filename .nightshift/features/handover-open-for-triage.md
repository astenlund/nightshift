# Keep a handed-over run open for triage after delivery

Raised by the user on 2026-09-30 in run `f440497c-a0cc-4375-bada-e834e32b49a6`, while triaging a follow-up about a stale triage record on a completed handed-over run. Asked how to track it, the user replied: "or should we extend the run to include the follow-up dispositions, since the triage is often likely to include backlog edits?" After the controller set out what that would run into, the user settled the direction: "i think the run should be treated as not closed, but after delivery, the stop hook can be lifted", and then: "let's graduate this feature, so we can pick it up in the next session".

## Problem

A handed-over run completes before the user answers its follow-ups. [The operating brief](../../internal/workflow.md) has it record the morning report and triage evidence stating which decisions stay deferred, then "complete with those follow-ups pending", and says optional follow-up decisions "never delay closing, the morning report or a completed delivery". When the user returns, triage happens on a complete run:

- `triage` is refused on a complete run, so the recorded triage keeps saying the decisions stayed deferred while `resolve-followup` records the user's actual decisions. The handover-close fixture of run `f440497c` (fixture run `a64f7816`) shows this, and [the acceptance report](../reports/independent-documentation-review-20260929.md) lists it under its limits.
- Triage usually brings backlog edits. Reviewing them after completion needed dedicated machinery: [Independent documentation review](independent-documentation-review.md) added a closing docs review that is admitted on a complete run as bookkeeping and gates no task or completion there. Since 3.3.10 it does bear on replacement: a closing record reopened after completion holds a new handover back until the run completes again, and a closing check recorded on the record after completion holds it back until the latest qualifying closing assessment covers what the check recorded, while later file changes without recorded closing work do not.
- Follow-on work agreed after the report needs a new run. On 2026-10-03, after the morning report of run `e92922e8-d20f-4674-907c-bf3277f5f184`, the user agreed a one-sentence change to the operating brief before triaging that run's seven pending follow-ups. A complete run takes no new task and runtime writes must name the checkout's current run, so the change got run `4ba1ff28-1b06-4c93-b5ff-17f6c7365e04`, which left the first run's follow-ups unresolvable and out of the SessionStart morning-report notice; the controller copied them into the new run. Asked how to track the gap, the user said: "feels to me like we shouldn't need a new run in this situation".
- Continuation keeps pressing while the run waits for the user. On 2026-10-09 in run `67af3471-c7c7-4e28-ab57-88e3ba299126`, on the retained 3.3.8 runtime, the Stop hook kept returning continuation reminders after the morning report was recorded, while it was presented and while the user's reply and triage answers were awaited. ## Agreed direction

- The morning report starts session close while the run remains open. Dispose every follow-up and apply its agreed repairs or tracking edits together with other cleanup, then run final validation and the release gate against the resulting candidate. Intermediate reviews guide progress and hold only work depending on an unresolved consequential answer; the final gate requires applicable independent assurance. This sequence was agreed by the user on 2026-11-04.
- After delivery, continuation stops pressing the run: the Stop hook no longer resists the controller yielding, so the run waits for the user rather than keeping a session busy. Amended on 2026-10-09: the release comes before the morning report is presented, so presenting it and awaiting the user's reply already happen without reminders.
- Follow-on work the user agrees at the report or during triage joins the still-open run as a new task, so its pending follow-ups and the new work stay in one run. Added at triage on 2026-10-03.
- Settlement was refined by the user on 2026-11-04: after follow-up disposition, cleanup and final validation, the runtime asks whether to publish the changes or leave publication to the user. Requested publication happens before the completion stamp; the stamp identifies the final candidate, validation outcome, settled exceptions and actual publication outcome. Leaving publication to the user is complete. Failed or uncertain publication keeps close pending until reconciled and completed or the user explicitly takes over. An unanswered choice stays pending. This replaces the 2026-11-03 shortcut in which a report reply with no triage could itself complete the run. A run never settled waits for its closing decision or the user's administrative close as unfinished, which does not assert successful completion. A settled run can reopen by a later user decision when live use finds a defect, until a later run supersedes its work; earlier reports and completion records stay as history. The session-close work remains on the current store and reopening belongs to the later store cut, as the assessment worklist records. Preserve the earlier requirement for an administrative close from the live owning session while awaiting settlement; reconcile that eligibility with [Close settled records](../specs/close-settled-records.md) without labeling unfinished work successfully completed.
- Preserved explicitly by the user on 2026-11-06: Ready offers a never-settled run both routes, continuing toward successful completion under the full closing sequence or administrative close as unfinished. A settled run reopened by the user returns to running with a repair task and completes again with a second report, preserving the earlier report, triage and completion records. The newer final-validation, publication-choice and completion-stamp ritual governs that completion. These remain future design commitments; reopening implementation stays with the later store redesign.
- A finding during final validation returns to the affected decision or repair and then validation. Unchanged report delivery, retrospective and settled triage do not repeat. The stamp links the morning report and subsequent changes rather than asserting that the report already described the final candidate. Publication recovery reconciles actual external effects after a crash or partial failure and never blindly repeats an uncertain action; the agreement defines whether publication includes a push, release or other named action.

## Historical agreed direction

Superseded versions are reproduced here for provenance, retaining unchanged clauses where they provide the original context. Repeated standalone unchanged commitments have been removed. Agreed direction above owns the current design commitments and their dates; historical text is not a second current source to update when that direction changes. The historical closing shortcut does not replace the later session-close settlement.

### Earlier direction

- After delivery, a handed-over run is treated as not closed: follow-up triage, the tracking edits it calls for, their rerun checks and their closing docs review happen in the still-open run, under the same gates as any delivery close, and the run completes after them.
- Settlement, decided by the user on 2026-11-03 after the VISION update of that day: the run completes on the user's recorded decision, in their words, once the follow-ups are triaged, the same shape as the `report-delivered` reply, and where there is nothing to triage the report reply can carry those words and be the record; a run never settled has two exits, both the user's, settling it or closing it under [Close settled records](../specs/close-settled-records.md), and the runtime never completes it for them, with Ready listing it with both offers meanwhile; and a settled run reopens by a later recorded decision of the user, with their reason, when live use finds a defect, returning to running with a repair task and completing again with a second report, while the earlier completion, report and triage stay as history, until a later run has superseded its work, after which the defect belongs to that run. The settlement record and the two exits are closing-stage changes on the current store; reopening touches run status transitions and the report, so it belongs with the v4 cut the assessment worklist schedules. The close exit needs one change to [Close settled records](../specs/close-settled-records.md), which admits a running record only when its owner is proven inactive: a run awaiting settlement must be closable from its live owning session, either by widening close's eligibility to that state or by offering settlement and close through the same closing-stage operation.

## Before implementation

[Assessment change conditions](../specs/assessment-change-conditions.md) is the draft design context for assessment applicability and its final-gate boundary. This feature owns the session-close sequence; the completion stamp and publication recovery contracts still need implementation design.

- Define the delivered-but-not-closed state: which recorded boundary counts as delivery (the recorded morning report or the user's `report-delivered` reply; for the Stop hook the 2026-10-09 amendment places the release before the report is presented), how `status` and the closing stages show it, how the SessionStart morning-report notice and delivery recording work with it, and how the controller-owned closing work after triage, meaning the tracking edits, their checks, the closing docs review and completion, continues once the hook no longer presses.
- Release a native persistent goal after delivery as well as the Stop hook: [the runtime reference](../../internal/runtime/REFERENCE.md) requires a goal, where the host requires one, to refer to verified run completion, and [the handover skill](../../skills/handover/SKILL.md) carries the lifecycle "until verified completion", so a goal-carried run kept open after delivery would keep continuation pressing. Releasing a goal before run completion must also be reconciled with the rule, stated in both, never to replace an unfinished goal.
- Reword the guidance that assumes completion before triage: the brief's Close and report section, including the rule that optional follow-up decisions never delay a completed delivery and the instruction to complete with follow-ups pending, the handover skill, and the runtime reference, and reconcile historical complete runs that still have pending follow-ups without representing them as having passed the new closing sequence.
- Decide how a delivered but open run interacts with other work in the checkout. `handover` refuses a new run with `overlapping-run` while an unfinished run owns the checkout, and [Ready offers to pick up an interrupted run](ready-interrupted-run-pickup.md) would otherwise offer it as interrupted. As agreed when that feature graduated on 2026-10-03, whichever of the two ships second makes Ready present a delivered but still open run as delivered and waiting for the user's follow-up triage, with an offer to continue that triage in a new session, never as interrupted. The user's 2026-11-06 reaffirmation additionally preserves Ready's offer to administratively close as unfinished under this feature's closing eligibility, alongside continuing toward successful completion.
- A run whose follow-ups remain unanswered waits for the user or their administrative close as unfinished. A successful completion stamp requires the full closing sequence above, even when there were no follow-ups; no report acknowledgement alone substitutes for final validation and the publication choice.
- Add an operation that adds an agreed task to an open run, recording its agreement as `handover` does; [Review retrospective instruction proposals like any other change](lore-proposal-review-gate.md) needs the same operation for a retrospective's proposal, and whichever feature ships first builds it, as agreed on 2026-10-03; its inverse, [Carve a task out of a running run](mid-run-carve-outs.md), shares one record of a change to a run's tasks with it, whichever of the two ships first defining that record, as agreed on 2026-10-13; and decide how a run that has recorded its retrospective, report or triage returns to engineering for the new task and which closing stages it then repeats.
- Revisited on 2026-11-03, once VISION.md carried the framing below: the direction stands. The original settlement is retained under Historical agreed direction; Agreed direction carries the 2026-11-04 closing refinement and the 2026-11-06 confirmation preserving the Ready offers and reopened repair/report commitments. The record had asked to revisit its direction once VISION.md carried the user's framing of 2026-11-03, given at the inbox triage that folded the reopen accounts above into this record, in their words: "i think part of the problem is that the runs are waterfall-shaped. we should make the process more agile. perhaps the design specs are too detailed; ai models are getting smarter and smarter and can do more and better work if they're not too locked down by overly-detailed specs. the other part is that we need to distinguish between recording a decision and locking it down. the former is needed for provenance, the latter leads to the blocking behaviour we keep seeing." The user chose then to update VISION and take another pass at the assessment before resuming work; the reopening of a run after a triage decision or a failed live retest, which their words of 2026-10-30 and 2026-11-02 above ask for, follows the updated vision rather than a direction fixed here first.
- Define the completion stamp and publication record lifecycle, exact candidate and authorization binding, recovery after every partially persisted or externally applied transition, and the distinction between successful completion and administrative close as unfinished. Keep a published candidate and an unknown or partially published outcome distinguishable from publication left to the user.
- Settle these in a concise governing spec in `.nightshift/specs`. Shipped runtime, hook and skill changes need a plugin version increase, and the start of the work decides between a budgeted installed-host campaign and deterministic evidence only, with model-owned behavior marked unverified.
