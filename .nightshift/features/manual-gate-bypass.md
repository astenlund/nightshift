# Manual gate bypass on the user's responsibility

## Origin

Raised by the user on 2026-10-12, in their words: "manual gate bypass for situations when the runtime refuses to complete a step for technical reasons. the agent provides the context the user needs for an informed bypass decision, and the user assumes responsibility for the continuation."

Asked whether a bypass should reach only refusals whose evidence is wrong or cannot be obtained, with genuine waivers such as accepting a result without strong review going through renegotiation of the agreement, or any gate at the user's discretion, the user answered: "we'd have to figure out the proper shape for each type of gate. e.g. a spec can be re-negotiated; code defects could be deferred."

Asked whether a run with a bypassed step may publish like any other or needs its own confirmation naming the bypass, the user answered: "the user takes over publication responsibility and has to provide confirmation at run completion (an earlier confirmation doesn't carry when a bypas has been executed). any bypass should make the run degraded. what's new for degraded runs is that the user can now accept the outcome, letting the run complete."

Asked whether every bypass should also produce a defect report, since a technical refusal points at a runtime defect, the user answered: "offer to file a report, don't do that automatically. the reason for a bypass can only be guessed by the model, and might be different than the actual reason the user had."

Later the same day the user added: "it would be good if we could make the bypass approval impossible (or at least difficult) to counterfeit". Asked whether the approval must resist a model that records approval it did not get, by misreading or fabrication, or an agent that deliberately tampers with the run store or the runtime, the user answered: "guarding against the first one: a confused agent making a mistake, not an adversarial one".

## Direction

The earlier bypass decisions below concern accepting unmet obligations, not ordinary engineering with assurance still pending. On 2026-11-04 the user separated intermediate reviews from the final release gate: deferring assurance during engineering is not a waiver and creates no degraded status or bypass approval. The final gate must distinguish evidence-established readiness from explicitly user-accepted exceptions. The user settled the replacement on 2026-11-04: no confirmation code, an explicit reply independently verified and bound to the exact exception briefing and candidate, with ambiguous or unverifiable replies left pending. Completion is labeled "completed with user-accepted exceptions" and lists the exceptions; this is distinct from pending assurance during engineering. Publication now belongs before the completion stamp in the [session-close sequence](handover-open-for-triage.md#agreed-direction). These commitments describe proposed behavior.

- **Informed decision.** The controller gives the user the context an informed bypass decision needs, and the user assumes responsibility for the continuation.
- **Per-gate route.** A refused step follows the route for its kind: a spec or agreement change uses the existing material-change path, a required code defect may be deferred by the user through an explicit agreement change, and only an eligible review or check refusal uses manual bypass.
- **Visible result.** Completion with accepted unmet obligations says "completed with user-accepted exceptions" and lists them, as decided on 2026-11-04. Evidence retains its actual strength and limitations; the completion label does not claim that assurance passed. This replaces the earlier blanket degraded-run completion label, not the record of weaker assessment evidence.
- **User acceptance.** A run with listed unmet obligations can complete through the session-close sequence after the user explicitly accepts those obligations. [Degraded assessment mode](degraded-assessment-mode.md) shares this acceptance route; acceptance alone does not skip final validation, the publication choice or the completion stamp.
- **Publication.** After a bypass or user-deferred required code defect, earlier publication authority does not suffice. The user accepts the listed exceptions and chooses publication during session close, after final validation and before the completion stamp; they may instead leave publication to themselves. This is the timing agreed on 2026-11-04, replacing publication after completion.
- **Defect report.** The controller offers to file a report about the refusal and files one only when the user agrees, because the model can only guess the user's reason for the bypass.
- **Approval that resists counterfeiting.** A bypass approval should be impossible, or at least difficult, to counterfeit by a confused agent making a mistake. Resisting a deliberately adversarial agent is out of scope.

## Current understanding

The runtime has no bypass, and some of its rules say so. A search of [the runtime reference](../../internal/runtime/REFERENCE.md) on 2026-10-12 for "bypass", "force", "override" and "waive" found these rules against getting past a refusal or obligation, which a bypass design has to reconcile: `adopt` has "no force-adopt or replacement-run escape for missing evidence"; admission says "Never use development mode to bypass the binding"; `dispose` says "Required obligations cannot be deferred or skipped" and "Do not use classification to waive an agreed commitment", and edits made before a disposition re-establish current evidence "instead of bypassing freshness". The other hits are out of scope: paused goals and native `usageLimited` or `budgetLimited` states, which the reference calls holds or limits "not technical failures to bypass", are native host states rather than runtime refusals; the adoption export route's statement that it does not override managed-process reservations defines that route's reach; and the rest are unrelated uses of the words. Refusals that state no such rule refuse all the same.

[VISION.md](../../VISION.md#invariant-priorities) says the invariant priorities "do not create authority to expand scope, bypass restrictions, or exceed a user-set limit", which concerns the controller's own authority; a bypass here rests on the user's. Under [Review for useful decisions](../../VISION.md#review-for-useful-decisions) it says "A failure to meet an agreed requirement must be repaired or explicitly renegotiated; cost alone cannot waive it", which the user's spec example fits.

Tracked cases where a refusal left no supported route, found by reading the active indexes on 2026-10-12 and offered as examples rather than a complete classification: [Recover a run whose owner can no longer act while its host process lives on](stalled-owner-recovery.md), whose live case needed an administrative stop outside the public interface, and which since 2026-10-13 plans a supported route for its own case; [A resource blocker refuses read-only diagnostic review of saved evidence](../BUGS.md#a-resource-blocker-refuses-read-only-diagnostic-review-of-saved-evidence); and [Carve a task out of a running run](mid-run-carve-outs.md), whose run could complete only by taking the task back, and which since 2026-10-13 plans a supported route for its own case.

## Counterfeit resistance

Today nothing the runtime records about the user's assent resists counterfeiting. User authority is nonempty text the controller supplies, as for `adopt`, `hold` and `open-review` in the runtime reference. The runtime's independent provenance (`internal/runtime/provenance-store.js`) cross-checks saved state against content hashes in a separate table, which catches an inconsistent direct save, but the hashes are unkeyed, so it holds no secret a forger would lack. A search of the repository's scripts on 2026-10-12 for `createHmac`, `createSign`, `createVerify`, `generateKeyPair`, WebCrypto `subtle` and DPAPI found no keyed cryptography. The controller also runs as the same operating-system user, so operating-system permissions do not separate it from the user. What limits it is the host's sandbox and approval rules, which vary by host and mode, as [Codex sandbox blocks the launcher from starting the host](../QUICK_WINS.md#codex-sandbox-blocks-the-launcher-from-starting-the-host) shows, so a secret stored where the user can read it is out of the controller's reach only as far as those rules keep it there.

Candidate approaches considered on 2026-10-12; none was verified on either host:

- **Host-native approval.** A host permission prompt could bind the refusal to a user action, but the runtime cannot prove it was shown and automatic modes may skip it. Whether either host prompts reliably is unverified (live-claim: provisional).
- **Runtime-owned confirmation.** A runtime dialog could record the user's answer independently of host permission modes, but it requires the interactive desktop and excludes remote-only approval.
- **Signed approval.** A WebAuthn assertion over the refusal, briefing and run revision could provide stronger evidence if the threat changes, but it requires enrollment and browser or native-helper work.
- **The local limit.** An agent able to alter the user-writable verifier or enrolled credential could defeat same-machine checks; deliberate tampering is outside the user's threat.

The user's answer on 2026-10-12 set the threat as a confused agent misreading assent, applying approval to another refusal or recording one with no user present. The earlier selected confirmation code bound one refusal to an independently verified user reply. On 2026-11-04 the user replaced the confirmation code with an explicit reply independently verified and bound to the exact briefing answered, identifying the candidate and named unmet obligations. An ambiguous or unverifiable reply remains pending. This preserves protection against misattributed assent without requiring a code; the host evidence still needs verification. Host prompts can be silently skipped, desktop dialogs do not reach remote users, and signed approval remains an option if the threat changes.

## Settled questions

The user agreed the graduation answers on 2026-10-14, when the entry moved from Exploring to current work, with "agree with all of it". Unchanged original questions and answers remain here alongside the dated current amendments; superseded versions are preserved under Historical graduation answers below. The required-defect responsibility rule was added on 2026-10-15; its current answer below records the later amendment, and its original wording remains in the historical section. The 2026-10-13 graduations of [stalled-owner recovery](stalled-owner-recovery.md), [mid-run carve-outs](mid-run-carve-outs.md) and [run preferences](v3-run-preferences.md) agreed on future routes without shipping them. Until those routes ship, the existing refusals and recorded limits remain binding; this bypass proposal covers only eligible review or check refusals after available recovery, not those separate cases.

- Which gates and refusals exist and the shape for each. Settled: a spec or agreement is renegotiated through the existing path for material changes, not bypassed. A code defect a review requires can be deferred by the user through an explicit, recorded change to the task's required obligation; the defect and deferred work remain visible. This is a user decision about the agreement, not a technical bypass. The governing spec must reconcile that change with the runtime's current prohibition on deferring required findings, preserving the obligation until the user's authority and revised requirement are recorded. A strong review or check that cannot be obtained, or is refused for technical reasons such as missing or wrong evidence, can be bypassed. Refusals that protect saved state or work stay beyond any bypass: a stale owner or revision, a wrong project, active or uncertain workers and operations, run-store integrity, unsafe paths and executable identity.
- How a user-deferred required code defect affects completion and publication. The 2026-10-15 decision labeled the run degraded to reflect increased user responsibility. On 2026-11-04 the user selected "completed with user-accepted exceptions" for completion, listing accepted unmet obligations, including required-defect deferrals, without presenting them as assurance established by evidence. Earlier publication authority does not suffice; acceptance of exceptions and the closing publication choice remain separate, before publication and its completion stamp.
- How the briefing tells a technical refusal from available recovery or a genuine unmet obligation, and what it contains. Settled: a bypass is offered only after the controller has tried the authorized recovery, such as retries, other eligible reviewers and, once shipped, [Degraded assessment mode](degraded-assessment-mode.md). The briefing names the refused step, the runtime's refusal code, the evidence that is missing and why, what was tried, what the result will not be able to claim, and the alternatives of renegotiating, stopping or waiting. The runtime refuses a bypass of a refusal that is not bypassable.
- What acceptance records and when it needs renewal. Amended on 2026-11-04: preserve the exact briefing, candidate identity, named unmet obligations, missing evidence, consequences, alternatives, the independently verified user reply and its provenance, and the user's reason when given. Renew approval only when later changes affect the accepted exceptions or their consequences; record why an earlier acceptance applies to the later candidate without changing its original binding. If applicability cannot be established, acceptance stays pending. Unrelated changes require no repeated approval but still receive their own applicable assurance.
- Whether a bypass is possible only with the user present, and what happens to the refusal otherwise. Settled: only with the user present. With no user available, the refusal waits as a user decision while independent work continues, and the morning report carries the briefing.
- Which outcomes share exception acceptance. Amended on 2026-11-04: bypasses, weaker assessment coverage and user-deferred required code defects keep their specific evidence and limitations. The run lists every bypass, degraded assessment and user-deferred required code defect; status, the obligation brief and the morning and completion reports show that list during the run and at closing. Accepted unmet obligations also appear in the closing result and completion stamp under "completed with user-accepted exceptions", with the full accepted list and actual user reply preserved. The same route permits a run with only weaker coverage to complete through the closing sequence without claiming that coverage was strong. Ordinary pending assurance during engineering is not an exception.
- How publication relates to earlier authority and completion. Amended on 2026-11-04: the closing publication question follows final validation and any informed acceptance of unmet obligations, and precedes the completion stamp. Earlier authority does not silently carry past a bypass, user-deferred required defect or degraded assessment. The user chooses publication or takes it over; the stamp records the actual outcome. A failed or uncertain requested publication keeps close pending until reconciled and completed or handed to the user.
- Which approval channel guards against a confused agent recording assent that was not given. Settled on 2026-11-04: the briefing names the candidate, unmet obligations, missing evidence, consequences and alternatives, then explicitly asks whether the user accepts those exceptions for that candidate. No confirmation code is required. The runtime independently verifies the actual user reply and binds it to that exact briefing; a controller-supplied summary is insufficient. Ambiguous, absent or unverifiable replies leave acceptance pending. Record acceptance separately from evidence and publication permission. Renew it only if later changes affect the accepted exceptions or their consequences. Native verification remains to be established (live-claim: provisional on Claude Code; live-claim: provisional on Codex).
- How it relates to the stalled-owner recovery and carve-out records. Settled: both stay separate routes, and the defect report stays an offer as the user settled on 2026-10-12. The entry requires nothing.

## Historical graduation answers

Superseded versions of questions and answers are reproduced here for provenance, with unchanged clauses retained where they provide the original context. Repeated standalone unchanged answers have been removed. Settled questions above owns the current answers and their dates; historical text is not a second current source to update. The earlier timing, labels and approval mechanisms below do not govern the amended direction.

- How a user-deferred required code defect affects degraded status, completion and publication. Settled by the user on 2026-10-15: the deferral makes the run degraded for now. Degraded here marks that the user takes more responsibility for the end result, not that the deliverable is low quality; the label may be revisited later. The run records the deferred defect beside bypasses and degraded assessments, and the user accepts the complete list at completion. Earlier handover publication authority is suspended, nothing is published before completion, and publication then requires the user's informed confirmation.
- What a bypass records, and whether the gate judges afresh once the inputs of the refusal it covers change. Settled: it records the refusal and the identity of its inputs, the briefing shown, the user's words and the user's reason only when the user gives one. When those inputs change, the gate judges afresh and the bypass no longer applies.
- What a degraded run is, where it shows and what acceptance records, and whether acceptance also completes a run degraded only by Degraded assessment mode. Settled: the run lists every bypass, degraded assessment and user-deferred required code defect, and status, the obligation brief, the completion report and the morning report show that list. The user's acceptance at completion records the user's words and the list. There is one notion of a degraded run, so acceptance also completes a run degraded only by degraded assessments, which amends that entry's agreed commitments, as its record notes.
- How the publication confirmation at completion relates to the publication authority recorded at handover, and what may be published before completion once a bypass has happened. Settled: a bypass or user-deferred required code defect suspends the publication authority recorded at handover, nothing is published before completion, and at completion the user confirms publication knowing the list. The same holds for a run degraded only by degraded assessments.
- Which approval channel guards against a confused agent's mistakes, and how it reaches a user away from the machine's interactive desktop. Settled: a confirmation code bound to one refusal. The runtime generates a short code for the refusal, and the briefing shows it. The bypass is recorded only when the exact user reply contains that code and the runtime verifies the reply's user role and content independently of controller-supplied authority text. The governing spec must identify that host evidence on both hosts; a code without verified reply provenance does not establish user presence and cannot authorize a bypass. Bound to one refusal with that provenance, the code guards against reading assent into an ambiguous reply, applying approval to another refusal and recording one with no user present. The intended channel works over Remote Control, unlike a dialog on the interactive desktop; its verified user-reply check cannot be skipped by an automatic permission mode, unlike the host's own prompt. Host evidence for that channel remains to be established. The signed approval stays recorded above in case the threat changes.
