# Design principles in a reference file and a run-time file

## Origin

Raised by the user on 2026-10-05, outside any run, during a backlog session that graduated a series of Exploring entries, in their words: "wondering if we also should add a PRINCIPLES.md file next to VISION.md and WORKFLOW.md -- what do you think?", then "as with WORKFLOW.md vs workflow.md, we could have one file for reference and one file for run-time", and "to protect against unnoticed corruption, we should probably use guid anchors".

## Current state

Checked on 2026-10-05. [VISION.md](../../VISION.md) states the purpose, the invariant priorities and the direction, and some of its sentences are design principles, such as "Models own engineering and product judgment. Deterministic tools own mechanics where a mistake would lose work, corrupt state, or misrepresent what happened" and "The amount of machinery should be proportionate to the consequence it prevents". [WORKFLOW.md](../../WORKFLOW.md) describes how a run proceeds. No file collects the reusable rules that settled decisions produce. They live in the feature records that settled them, and during the 2026-10-04 to 2026-10-05 session the controller re-derived several of them in successive graduation discussions instead of citing them.

The repository already splits workflow guidance by role: the root `WORKFLOW.md` is design reference that no run loads, and [the operating brief](../../internal/workflow.md) ships in the plugin and is what runs load. [Rename one of the two workflow files](../QUICK_WINS.md#rename-one-of-the-two-workflow-files) records that their names, differing only in case and folder, let readers and agents mix them up.

## Direction

- Two files split by role. A reference `PRINCIPLES.md` at the repository root, beside `VISION.md` and `WORKFLOW.md`, gives each principle its reasoning and links the decisions that established it. A run-time file shipped in the plugin states each rule in one sentence for the agent that applies it.
- The run-time file is the only home of each rule's wording. The reference file links to each rule rather than restating it, and adds only reasoning and evidence.
- Every rule carries a GUID anchor, so that rewording or retitling a rule cannot silently break a link or redirect it to another rule, as a heading-derived anchor would. A packaging test checks that every run-time rule has a reference entry and that every reference entry points at an existing rule.
- The run-time file is loaded by the work that makes design decisions rather than by every run step: revise-spec, the repair guidance in revise-code, and the Exploring skill, whose graduation discussions are where such decisions are settled.

## Guardrails

- A principle needs at least two settled decisions behind it, linked from its reference entry, so the files do not become a dumping ground or a checklist that grows with every decision.
- Neither file restates VISION.md. A principle VISION.md already states either moves or is linked, so the two do not drift.
- Names tell the two roles apart, so the pair does not repeat the confusion the workflow rename addresses. As refined at graduation, the run-time file is named for its role and the reference file keeps its topic name.

## Settled questions

The user agreed these answers on 2026-10-15, when the entry graduated from Exploring to current work, by taking the recommendations put to them that day. Each question is kept with its answer; the last was raised at graduation. Checked the same day: no `PRINCIPLES.md` exists, the principle sentences quoted above are still in [VISION.md](../../VISION.md#a-controller-that-owns-the-result), and the workflow rename has not happened. The release payload holds only the two plugin manifests, `LICENSE`, `hooks`, `internal` and `skills` (`PAYLOAD_ROOTS` in `internal/releases/manifest.js`), so VISION.md, WORKFLOW.md and a root `PRINCIPLES.md` do not ship, and neither the skills nor the operating brief link outside the payload. Five skills link the operating brief directly. The packaging test that resolves local links in the skills, AGENTS.md, the brief and the runtime reference (`tests/package.test.js`) drops each link's fragment, so nothing outside the backlog checks an anchor today.

- The two files' names, coordinated with [Rename one of the two workflow files](../QUICK_WINS.md#rename-one-of-the-two-workflow-files) so that both pairs follow one convention, for example a run-time file named for its role such as `internal/design-rules.md`. Settled: reference files at the repository root keep topic names in capitals, as `VISION.md` and `WORKFLOW.md` do, and a shipped run-time file is named for what the agent does with it, so the two files of a pair read apart by name rather than only by case or folder. The reference file is `PRINCIPLES.md` and the run-time file `internal/design-rules.md`. The same convention points the workflow rename at the shipped brief, for example `internal/operating-brief.md`, which is what prose already calls it; that rename stays its own quick win, with its version increase and reference sweep, and this feature does not wait for it.
- The GUID anchor's form in Markdown and how the packaging test reads it, given that Ready's link checks cover only links between backlog files. Settled: each rule in the run-time file starts with an inline `<a id="<uuid>"></a>` carrying a version 4 UUID, which renders invisibly, and `PRINCIPLES.md` links to a rule as `internal/design-rules.md#<uuid>`. A new test in `tests/package.test.js` reads both files and fails on a rule without its anchor, a duplicate id, a rule that no reference entry links, a reference entry that links no rule, or a link whose fragment names no rule; the readback fixes how the test recognizes a rule and a reference entry. This is new checking: Ready checks anchors only in links between backlog files, and the existing link test drops fragments.
- The route into what a run loads, coordinated with [Separate run-time guidance from reference material](runtime-guidance-separation.md), which draws the same line between run-time guidance and reference. Settled: revise-spec, revise-code for its repair guidance, and the Exploring skill link the run-time file directly, as five skills already link the operating brief, and the file joins the packaging test's list of files whose local links must resolve. It does not route through the run-time operations guide that feature creates, which carries runtime operations rather than design rules, so neither feature waits for the other; they edit the same skills, so their edits are coordinated.
- Which of VISION.md's principle sentences move to the new files and which stay and are linked. Settled: none move in the first version, which holds only the six candidate principles above. None of them restates VISION.md: the nearest, "Silence writes nothing", is broader than VISION.md's "recording a question does not supply its answer", since it also covers declined questions and questions a present user leaves unanswered. VISION.md stays the agreed direction. Since VISION.md does not ship, a run-time rule cannot link to it, and the run-time file links nothing outside the release payload; moving a VISION.md principle needed at run time into the run-time file is left for a later decision.
- Whether a graduation or spec that applies a principle cites its GUID, and whether a decision that contradicts a principle must say so. Settled: citing a rule is optional. A decision that contradicts a rule says so where it is recorded, naming the rule, and either amends the rule and its reference entry or records why the case is an exception, so the files never drift silently from the decisions made. How this reads in a project other than Nightshift, where the shipped rule cannot be amended and no `PRINCIPLES.md` entry exists, is left to the readback.
- How it relates to [Ground Ready recommendations in the project's direction](ready-project-direction.md), which reads the project's durable direction. Settled: no special handling. AGENTS.md lists `PRINCIPLES.md` beside VISION.md and WORKFLOW.md, so Ready finds it through that feature's agreed route, the documents a project's instruction files name as its direction, once that feature ships; neither waits for the other.
- Which projects the run-time file governs. Because it ships, revise-spec, revise-code and the Exploring skill apply it in every project that uses Nightshift, not only in this repository, and some candidates are worded for Nightshift alone, such as "Plugin defaults stay plugin-owned". Settled: every shipped rule is worded to hold in any project, for example "shipped defaults stay owned by their shipper; user files layer on top and win", and Nightshift-specific reasoning and examples stay in `PRINCIPLES.md`.

## Before implementation

The new run-time file and the three skill edits change shipped plugin behavior, so the work ships with a version increase and a regenerated release manifest. It changes model-owned behavior on both hosts, so at start the user decides between a budgeted installed-host campaign and deterministic evidence only, with the model-owned behavior marked unverified. The record states the files, anchors, route and test, so an agreed readback is enough without a separate spec. The readback also settles how the test recognizes a rule and a reference entry, and how the contradiction rule reads outside this repository. No dependency blocks the work; coordinate with [Rename one of the two workflow files](../QUICK_WINS.md#rename-one-of-the-two-workflow-files) and [Separate run-time guidance from reference material](runtime-guidance-separation.md), which edit the same skills, and with [Select Exploring drafts by number for a staged graduation](../QUICK_WINS.md#select-exploring-drafts-by-number-for-a-staged-graduation), which rewrites how the Exploring skill presents a graduation, so that whichever ships second fits its Exploring edit around the first. Tracking and readiness do not authorize implementation.
