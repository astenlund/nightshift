# Carve a task out of a running run

## Origin

Raised by the user in Hermes (`C:/Users/asten/AppData/Local/hermes`), run `451da04e` on installed 3.3.9, and reported to the maintainer inbox on 2026-10-11 at the user's request, in their words: "add mid-run scope carve-outs as an idea in the nightshift inbox", after asking "i want to complete the run. so splitting things off isn't possible?". Tracked as Exploring at inbox triage on 2026-10-11.

## Current understanding

Partway through a long run the user decided to carve one queued code task out of it: park its finished but unreviewed code on a local branch, record it as its own backlog item and finish the rest. The controller blocked the task as a user decision, parked the code and wrote the backlog item as tracking edits. When the user then asked to complete the run, the carve-out had no runtime form. The task stayed in the queue, blocked; a documentation task that depended on it could not proceed, so its agreed edits went in as closing tracking edits; `complete` requires every queued task to be complete; and `stop` is not to be used to sidestep incomplete work, while the operating brief forbids replacing an unfinished run, so a later run for the carved-out work would have had to resume this one. The only way to complete was to bring the task back into the run. In the 3.3.10 runtime no operation removes or withdraws a task from a run. The run's other remaining tasks waited on live steps the user had reserved, a different kind of pending work that also kept it from completing.

[Keep a handed-over run open for triage after delivery](handover-open-for-triage.md) plans the inverse, an add-task operation for follow-on work agreed at the report or during triage. [State the expected size and offer slices before handover](../QUICK_WINS.md#state-the-expected-size-and-offer-slices-before-handover) would offer slicing before a run starts, which would make carve-outs rarer but not unnecessary.

## Settled questions

The user agreed these answers on 2026-10-13, when the entry graduated from Exploring to current work. Each question is kept with its answer, and the last was added by the user at graduation. Checked the same day in `internal/runtime/lifecycle.js`: a task is `pending`, `active` or `complete`, with no state for withdrawn work; `complete` refuses with `unfinished-work` unless every task is complete; a task whose upstream task is incomplete cannot advance, refused with `dependency-blocked`; a blocked task lets the run's closing stages proceed but never lets the run complete; `unblock` of a user-decision blocker can replace the task's agreed outcome through `updatedOutcome`, adding the decision to its agreement and raising its requirements revision, which makes every earlier review of the task stale; and no runtime record holds a live test apart from the task whose agreed acceptance includes it.

- How a carve-out treats tasks that depend on the carved-out task, and whether their agreed edits move with it. Settled: for each dependent task the user chooses either to carve it out too or to keep it with the dependency dropped and its agreement adjusted, recorded as the user's decision. The runtime refuses a carve-out that would leave a remaining task depending on one that is gone.
- How it changes the run's agreement and what the user confirms, including whether the carved-out code is parked, kept in place or reverted, and who records its backlog item. Settled: a carve-out changes the run's agreement, so it needs the user's direction, recorded as authority as `hold` records it, and it is refused while the task has an active worker. The carved-out task's code is parked by default, on a local branch or as a patch, with the record naming where; it is reverted only on the user's choice, and never kept in place, since the delivered state is to hold only reviewed work and code left in place would fall under the run's review anyway. The controller writes the backlog item as a tracking edit within the run, so the run's closing docs review covers it, recording the task's agreement, any governing spec, where the work is parked and how far it got.
- What closing evidence, the retrospective and the morning report say about carved-out work, and whether the run then completes normally. Settled: a carved-out task takes a terminal state of its own, never `complete`, which `complete` accepts. The morning report lists carved-out work apart from delivered work, with no claim that it was reviewed or verified, as well as tasks delivered without a carved-out live step; the retrospective covers carved-out work like any other; and the run then completes normally.
- How it relates to the planned add-task operation, to adoption, and to resuming the carved-out work later in a new run. Settled: the carve-out and the add-task operation that [Keep a handed-over run open for triage after delivery](handover-open-for-triage.md) plans share one record of a change to a run's tasks, and whichever ships first defines it; neither waits for the other. Adoption carries carved-out tasks like any other record. The carved-out work resumes in a new run from its backlog item, where the parked work is a starting point rather than evidence and receives fresh review.
- Whether a carve-out can take out a live test the run is waiting on, without carving out the whole task. Raised by the user at graduation, in their words: "live tests should be included in the carve-out, otherwise it would be difficult to complete the run, right?" Settled: yes. On the user's direction, a carve-out can remove a live test or other live step a task still owes, such as one the user reserved, while the task keeps its reviewed work and completes. The step moves to the carve-out's backlog item with what it was meant to show, and the task's completion records that it was not verified live, which the morning report qualifies in the same way, so it never reads as fully verified. The controller never carves out a step on its own initiative, and a live test it cannot run for lack of capability or budget stays with its existing blocker routes. Whether removing only a verification step makes the task's earlier reviews stale, as any change to its agreement does today, is left to the governing spec.
