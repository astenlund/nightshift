# Recover a run whose owner can no longer act while its host process lives on

## Origin

Reported to the maintainer inbox on 2026-10-07 from this repository at the user's explicit request, in their words: "yes. also file a report to the nightshift inbox; this should be officially supported". Run `67af3471-c7c7-4e28-ab57-88e3ba299126`, on the retained 3.3.8 runtime, was owned by Codex chat `01a11295-41c4-7ae0-ac66-458b36c6b1d6`, which stalled after its context overflowed, as [Codex controller overflows its context window instead of compacting](../BUGS.md#codex-controller-overflows-its-context-window-instead-of-compacting) records, and which the user closed. A new chat's `adopt` was refused with `controller-not-inactive`, "The exact former controller process is live or its inactivity is unknown": the saved controller identity and the new chat ran in the same live `codex.exe` process, which hosts every chat of the Codex app, so closing the chat could not show the former controller inactive. Restarting the app would have interrupted the user's work in other projects. With the user's approval the controller recorded an administrative user stop outside the public interface, at revision 172, after backing up the run database, checking the backup's integrity and the exact saved run content, and verifying that every recorded worker had ended; normal adoption then succeeded at revision 173 and left execution stopped until resumption was authorized. Tracked as Exploring at inbox triage on 2026-10-11.

## Current understanding

The refusal follows [the run-adoption and continuation spec](../specs/run-adoption-and-continuation.md): an explicitly stopped run can move to another session while the former chat or host process stays open, but a run still marked running also needs confirmed inactivity of its former controller, which the runtime judges by the controller's process. A controller that can no longer take a turn cannot stop its own run, and on Codex Desktop its process outlives the chat, so the only supported recovery is quitting the whole app, as the user did after the second overflow in the same run on 2026-10-08. The administrative stop kept the former owner, queue, findings, evidence, workers, limits and publication authority, and recorded the operator, the approval, the native observation and the backup's identity; it was an explicit exception, not a supported path. The app's own chat state reported the former chat as not loaded, with a failed latest turn; the report did not claim that this proves every assignment or descendant ended. Claude Code, separate native processes and other host states were not tested.

The same recovery hit an unrelated limit in its own scratch script: hashing the 2,328,989,696-byte backup with `readFileSync` exceeded Node's 2 GiB read limit. The run store's growth is tracked in [Run store keeps a full state copy for every revision](../BUGS.md#run-store-keeps-a-full-state-copy-for-every-revision).

## Settled questions

The user agreed these answers on 2026-10-13, when the entry graduated from Exploring to current work. Each question is kept with its answer. Checked the same day: `adoptState` in `internal/runtime/ownership.js` adopts a run marked running only when its former controller's claimed process is shown to have exited, and otherwise refuses with `controller-not-inactive`, while a stopped run can be adopted with the former chat or host process still open; `RunStore.update` in `internal/runtime/store.js` lets only the owning controller change a run, `stop` included, refusing with `wrong-owner`, and its one exception is the recipient's confirmation of a completed delivery's morning report from another admitted session; the release launcher in `internal/releases/service.js` likewise refuses a mutation from anyone but the current controller with `resource-owner-mismatch`; and `stop` records only its kind and reason, with no user authority, unlike `hold`. [The run-adoption and continuation spec](../specs/run-adoption-and-continuation.md) states that a live source process, including a shared app-server process, does not satisfy its abandoned-running predicate, and records a feasibility observation in which a Codex app-server reader reported a separately streaming assessment as `notLoaded`.

- What evidence shows that a former controller can no longer act when its process is shared, such as the host's own chat or thread state, and how that evidence is captured and recorded. Settled: the user's direction decides it, naming the former chat and stating that it can no longer act. The controller records the host's own status for that exact chat when the host offers one, with its source and observation time; a status showing the chat active or busy refuses the stop, and an unavailable status is recorded as unavailable and does not block. A host status alone never counts as proof that a chat is inactive, since the feasibility observation above found one reporting an active assessment as not loaded.
- Who may record the stop from another session and under what user direction, and whether that is a new runtime operation or an extension of `stop` or `adopt`. Settled: an extension of `stop`, which any admitted session in the same project may record on the run's behalf under the user's direction, recording that authority and leaving the owner unchanged. Ordinary adoption of the stopped run then transfers ownership, so `adopt`'s rule for a run marked running stays as agreed. If the former chat recovers before adoption, its owner can still resume the run.
- Which safeguards it keeps from the manual recovery: worker termination checks, a backup or integrity check, and a record of the operator, approval and observation. Settled: the stop records the session that recorded it, the user's authority and the host's status for the former chat, and it is refused while a project operation is active or its termination is uncertain. Worker termination checks stay with adoption, which already requires them. No backup or integrity check is needed, since the stop goes through the ordinary transaction and the run's history keeps the earlier state.
- How it interacts with ownership checks, an operation still in flight and publication authority, and whether Claude Code needs the same path. Settled: the stop leaves the owner, publication authority and limits unchanged, and adoption keeps the stop reason, as it keeps any existing stop. An operation in flight refuses the stop as above. The operation is the same on both hosts; on Claude Code, where each chat has its own process, it is needed only when a chat's process hangs rather than exits.
- How it relates to [Ready offers to pick up an interrupted run](ready-interrupted-run-pickup.md), which offers no pickup while the run or its workers may still be active. Settled: Ready pickup's agreed commitments are unchanged, and it still offers no pickup while a run may be active. Whichever of the two features ships second makes Ready name this user-directed stop as the way forward for a run marked running whose former controller's process is still live.

## Relationships

[Manual gate bypass on the user's responsibility](manual-gate-bypass.md) cites this entry's live case as a refusal that left no supported route; this entry plans that route for its own case, independently of the general bypass proposal. The route has not shipped. [Codex controller overflows its context window instead of compacting](../BUGS.md#codex-controller-overflows-its-context-window-instead-of-compacting) keeps the overflow that caused the live case, and fixing it would make the case rarer without removing it, since a chat can stop acting for other reasons. Each can ship without the other, so the entry declares no `**Requires:**`.

## Before implementation

Settle the extended `stop` request and what it records, the host status readers for each host, and the refusal while an operation is active in a concise governing spec in `.nightshift/specs`, amending the run-adoption and continuation spec, whose running-source rule gives the user two routes: stopping the run in the original session, or closing the owning host. The change alters the runtime, its reference and the operating brief, so it rides with a plugin version increase, and the start of the work decides between a budgeted installed-host check on Codex Desktop, where the case arose, and deterministic evidence only. Tracking and readiness do not authorize implementation.
