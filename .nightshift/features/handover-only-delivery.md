# Handover as the delivery boundary

Delivered in the local 3.3.10 candidate on 2026-10-09 in run `67af3471-c7c7-4e28-ab57-88e3ba299126`, which this record governed; the candidate has not been published, and [the feature history](../FEATURES_HISTORY.md) records the delivery. This feature preserves the complete agreed governing design. The [acceptance report](../reports/handover-only-delivery-20261009.md) records the review history, the deterministic and installed-host evidence and their limits. The remaining advanced scope selection is tracked separately in [Run-free revise](run-free-revise.md).


## Outcome and priorities

A Nightshift delivery run means that the user has handed over a defined task or finite queue for the complete lifecycle. Handover is the only entry that creates one. Reliability remains autonomy and trust together: continue authorized work through recoverable failures, preserve independent assurance and durable evidence, respect user authority and limits, and report incomplete work truthfully. Efficiency follows those requirements.

Ordinary chat agreement authorizes the requested work directly. A project's requirement to use Nightshift does not turn that agreement into handover. Explicit standalone revise requests retain Nightshift's review machinery without creating a delivery run. Work already within a valid delivery run retains its commitments and obligations.

## Selection, agreement and acceptance

Ready explains before selection that choosing an item requests handover after investigation and scope confirmation. Selection preserves that intent; it creates no run and authorizes no implementation. Investigate the selected work, settle consequential decisions and limits, and present the readback or governing spec. Confirmation of that investigated scope releases the pending handover without another handover question or request. A compatible correction preserves agreement; a material change needs confirmation of the changed commitments. An explicit request to pause or implement directly overrides the pending handover, and ordinary chat work uses the direct path.

An explicit handover in prose or through the skill follows the same settlement boundary. If commitments or required spec assessment remain unresolved, keep the handover pending and present what remains. A finite queue is accepted only once every item is settled. No acceptance is inferred from silence, an existing file, Ready invocation alone or an idea discussed in chat. After compaction or a session change, recover the actual selection, request and agreement; if their provenance cannot be established, ask rather than reconstruct authority from backlog status.

Create the accepted delivery with its queue, authority, owner, resources, limits, publication authority and closing duties in one durable transition. The operational creation surface requires handover; a direct create request or a standalone revise path cannot provide a second creation route. Preserve existing overlap, worker, ownership and resource checks. Repeating the same acceptance after an interruption reconciles its result instead of creating another run. A pending or active incompatible run is never replaced by a new selection.

## The handover acknowledgement

After durable acceptance and a recorded continuation outcome, immediately show a separate user-facing acknowledgement before further engineering. It states the accepted scope and applicable limits, confirms that handover is accepted and says the user can leave. Publication is mentioned only when already authorized. The message must appear in the host's assistant output, not only in reasoning, a tool receipt or a saved file.

With working continuation, say that the morning report will be waiting in the current owning conversation. With failed continuation, still confirm acceptance and say the user can leave, while disclosing that automatic continuation is unavailable, the failure is recorded for follow-up, and resumption will be necessary if the session stops before delivery. Continue useful work in the current turn. Do not promise automatic recovery from host exit or Windows restart. If ownership, durable acceptance or required authority is unresolved, describe handover as pending and identify the actual blocker.

Use a turn-ending acknowledgement only when the host's verified mechanism can continue the work afterwards. Otherwise deliver the acknowledgement through visible assistant output and keep working in the active turn. Test acknowledgement visibility and ordering independently on Claude Code and Codex.

### Observable acknowledgement before runtime engineering

The recorded Claude attempts establish that stronger wording and a returned reminder do not reliably produce the required assistant message. New delivery records therefore retain an acknowledgement obligation until the runtime observes that message in the owning host's native history. This is a narrow admission check for runtime engineering; it does not claim to intercept arbitrary editor or shell writes. The controller still must acknowledge before those tools, and installed-host evidence must assess actual ordering rather than infer it from admission.

Use a separate assistant message beginning `Handover accepted: <scope and limits>. You can leave.`. The scope slot contains the confirmed outcome and applicable limits, expressed for the user; it is nonempty and introduces no new authority. The prefix and departure sentence are case-insensitive ASCII phrases, with ordinary whitespace and Markdown emphasis normalized for recognition. The rest of the message gives the report location and, on failed continuation, explicitly states that automatic continuation is unavailable, the failure was recorded and resumption is needed if the session stops. These statements are user-facing prose, not a run identifier or a tool receipt. Instructions, quoted examples, reasoning, user messages and tool results cannot serve as acknowledgement evidence.

The governing record is `acknowledgement: {schema: 1, status, runId, controller, scopeHash, renewalRevision, renewedAt, requiredAfter, observation?}`. Like continuation, `runId` and `{host, session}` bind the exact saved run and current native owner without trimming or substitution. Unlike continuation, status is `pending` or `observed`; there is no execution mode or caller-supplied verified flag. `scopeHash` is the SHA-256 of the canonical JSON projection of user-owned queued task identities, kinds, user-owned dependencies, agreed outcomes, material `agreement.decisions`, each task's `requirementsRevision`, and the applicable recorded limits, excluding linked internal governing-spec tasks and mutable assessment evidence. Missing historical decisions are an empty array and missing historical requirements revisions have their historical initial value, zero. A changed material decision therefore changes the binding even when outcome wording stays identical. `renewalRevision` is the nonnegative safe-integer run revision committed with creation, material agreement renewal or adoption; `renewedAt` is that transition's UTC recording time. `requiredAfter` is null while the applicable continuation outcome is pending, then its UTC recording time; pending observations of a genuinely changed outcome may only advance that boundary. An observation holds the owning host/session, canonical native-history path, native message identity or ordinal, the individual event hash, bounded visible text, emission time, observation time, renewal revision, scope hash and the outcome identity it followed. Its emission must strictly follow both `renewedAt` and `requiredAfter`, and its renewal and scope bindings must match the current obligation. Every observation field is derived from native history or that established obligation, never accepted as a runtime request assertion. An empty or malformed scope, illegal status, unsupported schema, absent observation, wrong owner/run, stale renewal/scope or an emission at or before either applicable boundary cannot discharge the obligation.

Creation initializes the obligation pending with its creation revision, recording time and agreed-scope binding. The first recorded continuation outcome supplies its time and identity; repeated observations of the same outcome do not move a renewal boundary or erase an already established acknowledgement. Before runtime engineering, observe the current owner's native assistant output after both boundaries, then record the valid observation and the requested transition or worker reservation in one SQLite transaction. The admitted retained registration supplies the host profile. Claude evidence comes from that session's ordinary persisted assistant text, excluding synthetic and sidechain output; Codex evidence comes from that thread's attributed visible assistant message, excluding analysis. Validate native session and project attribution, regular unlinked source files and the supported message shape. Bound source discovery, bytes inspected and captured text; report exceeded bounds or unavailable, incomplete, malformed or unattributable history as unavailable evidence. Do not guess another profile or use development mode to bypass a bound record.

If the observation cannot establish emission, keep the obligation pending and refuse new runtime engineering with a concrete acknowledgement diagnostic. Emit or safely repeat the separate message and retry; an unavailable native-history surface remains a capability limitation, not proof that the message was absent or permission to invent evidence. Status/history/wait, claims, continuation observation, hold/stop, ownership recovery, receipt import and independent bookkeeping retain their own admission rules. Read-only Ready and standalone review contexts acquire no delivery acknowledgement duty. Every public delivery operation that starts or advances engineering, repairs, checks/probes or a new assessment must consume this obligation; completion cannot bypass it. Existing bound releases retain their own behavior.

### Nonterminal emission and read-only checkpoint

Acceptance proceeds through ordinary visible assistant text, a read-only observation, then engineering. A separate acknowledgement means a distinct visible paragraph, not necessarily an end to the user turn. On Claude it must be a normal assistant text content block, not intended narration held in thinking. After the recorded continuation outcome, emit the complete acknowledgement through that ordinary text surface and invoke status in the same ongoing tool-use turn before requesting engineering. The cold Claude trace establishes that introductory ordinary text followed by a Read tool is possible; it does not establish this complete acknowledgement sequence. With unavailable continuation, final-only emission cannot serve as the route into engineering and must not deliberately require another user reply. Genuine unavailable evidence still remains a capability limitation.

The owning runtime status result supplies `acceptanceCheckpoint` while the delivery acknowledgement duty remains pending. It also remains the initial acceptance checkpoint returned after creation. The checkpoint retains `requiredNextAssistantOutput`, bound to the instructions for ordinary visible acknowledgement of the current agreed scope and continuation outcome; `observedContinuation`, bound to the saved current outcome as `available`, `failed` or `pending` when no current outcome exists; and `assistantOutputEvidenceRequired: true`. It adds `inspection: {status, reason}` and `nextStep`. Status is exactly `awaiting-outcome`, `missing`, `available` or `unavailable`: a missing or stale recorded outcome/boundary requires reconciliation before emission; a complete attributable history with no matching text is missing; matching text current under the saved run, owner, scope, renewal and outcome is available; unavailable history, malformed or stale duty bindings, exceeded bounds, denied access and inspection failures are unavailable. Reason is explanatory ASCII text bounded to 1,200 characters, or null when no explanation is needed. NextStep is exactly `record-continuation`, `emit-text-then-status`, `request-engineering` or `recover-history`, respectively. These are workflow step labels, not additional runtime operation names. Empty or unrecognized status is never available.

Inspection is read-only and reuses the native observer and its source, attribution, size and discovery bounds. It does not set acknowledgement observed, replace its bindings, refresh a continuation outcome, discharge an obligation or authorize engineering. It reads the saved current bindings without inventing a missing renewal or boundary. A freshly admitted integration failure inconsistent with that recorded outcome is awaiting-outcome until the actual outcome is durably reconciled; an availability snapshot alone is not a verified continuation mechanism. A matching message is only evidence available for the next engineering request, which independently observes and validates it and commits capture with its dependent transition. Changes between inspection and that request must remain governed by the existing scope, renewal, outcome and atomicity checks.

The diagnostic has no persisted lifecycle or cache: it is created from current saved state and the admitted owner context for each creation/status response, initialized without an observation, refreshed by each new read, and discarded after that response. Scope is that exact owning native session and delivery. A standalone review context and a legacy record without this duty return null. An already discharged current duty returns null without rereading a rotated or removed source. A foreign session can still view the ordinary saved status but receives no owner checkpoint and cannot infer that the obligation is discharged. Failure and unavailable evidence select the cautionary status while preserving the duty. There is no automatic polling loop: missing text calls for actual emission; unchanged unavailable evidence calls for bounded recovery and an explicit limitation. Read-only inspection cannot consume no-progress reminders or count as engineering progress.

Every consumer is explicit: the CLI supplies this ephemeral checkpoint on creation and status; handover and the operating brief follow its nextStep and require text plus status before engineering; the runtime reference documents all fields and meanings. Hooks retain the saved pending-obligation reminder and do not run another native-history inspection. Ready and standalone revision acquire no duty or diagnostic. The existing engineering gate, store transaction, ownership renewal and continuation writers remain authoritative and do not accept an inspection result as a caller assertion. Interrupted states are unchanged: after acceptance/outcome, emit or repeat text; after an available inspection with no committed engineering, inspect again against current bindings; after committed capture and engineering, reconcile that transition. An inspection result lost on interruption has discharged nothing.

Deterministic cases cover missing/available/unavailable histories, pending outcomes, stale bindings and admitted outcome drift, foreign/legacy/review viewers, preservation of run state and reminders, and unchanged atomic admission. Native acceptance separately requires ordinary text after the outcome, status inspection, admitted engineering and the edit/check before terminal output without an intervening user reply or Stop-based restart on the failed-continuation branch. Claude and Codex remain separate live claims; the observed introductory-text shape is feasibility evidence only, and the new sequence is unverified on either host until exercised. An observed record preserves the captured event as historical evidence even when the native log is later appended, rotated or removed; it is not a cache that has to reread the whole growing log. A user hold or same-owner resumption preserves a discharged acceptance duty and cannot grant engineering while stopped or before refreshed continuation. Adoption establishes a new pending owner-bound renewal in its ownership transaction, retaining the former evidence in history. Every recorded material agreement change establishes a new pending scope/renewal binding and recording-time boundary in the same transition, including a user-decision resolution that changes `agreement.decisions` and `requirementsRevision` without supplying `updatedOutcome`. It does not require inventing a continuation refresh solely to reject an old message: emission must follow the newer agreement-renewal boundary as well as the applicable continuation outcome. Compatible spec corrections and assessment bookkeeping change neither binding. A retry preserves the established renewal revision and time, and recovery may reuse an unrecorded emission only when it belongs to that current renewal and follows both boundaries. If renewal identity or time cannot be established, retain the pending duty instead of replacing it with an earlier boundary. Missing, unreadable, duplicated, malformed or unexpected acknowledgement state remains pending until actual matching emission is established. No reset, retry, re-recording or record replacement may silently remove this duty.

Expected interruption states are acceptance or renewal with its pending boundary; recorded continuation with acknowledgement still pending; actual assistant emission with no saved observation; and atomic saved observation plus the first dependent transition or reservation. Resume each deterministically: preserve the existing renewal, observe continuation first when due, emit or repeat the message next, recover matching current-renewal native emission before retrying the transaction, and reconcile the saved transition and worker after it committed. Never mark acknowledgement delivered before emitting it. A failed observation write preserves the earlier pending obligation; a failed dependent transition cannot leave a prospective observed flag behind. Test these branches, both host message grammars, source failures and attribution, scope/owner changes, unchanged-outcome material decisions, rejection of pre-renewal messages, recovery of post-renewal emission, repeated observations, compatible corrections, permitted suspension, exact retained routing and the limits of the runtime-only check. Each host's actual acknowledgement-before-engineering behavior remains a separate live claim, and the previous failed Claude attempts remain failed evidence.

## Continuation without execution modes

New delivery runs have no attended/unattended mode or mode-selection question. Keep authority, execution status, ownership, continuation health and remaining obligations as separate facts. Resource execution modes such as bound versus development remain distinct and keep their existing protection purpose.

For every eligible delivery run, attempt and maintain the host mechanism: the registered, enabled, trusted and observed Stop hook on Claude Code; a native persistent goal for the owning run on Codex. Codex hooks remain useful integration and protection, but a Stop hook is not a substitute for a Codex goal's ability to start another turn. Observe the actual host rather than infer health from configuration or a previous successful attempt. Always attempting continuation does not authorize enabling deliberately disabled hooks, granting native trust or replacing an unrelated goal.

Initialize continuation as needing observation at acceptance. Refresh it at resumption, adoption, compaction recovery, renewed handover and before a yield that depends on it. A technical failure, absence, unusable hook or failed inspection invalidates the current observation and records a follow-up. Such failure does not revoke handover, change commitments or prevent otherwise authorized engineering. Retry when a changed circumstance or a relevant recovery justifies it; avoid repeated setup and recovery loops on unchanged evidence. Failed inspection is unknown, never healthy or proof of termination.

Preserve the distinct cases of an active mechanism, a missing or failed mechanism, an explicit user pause or stop, an exhausted limit, an unrelated existing goal, and unknown evidence. Respect a user-paused goal associated with this run as a hold rather than an error to bypass. Never replace an unfinished goal or use another worker's activity as the controller's continuation. Goal completion follows verified runtime completion, not a model's assertion.

## Failures, admission and authority

Separate execution admission from continuation health. Missing SessionStart activation, untrusted or disabled hooks and a failed continuation inspection may make continuation unavailable while the explicitly requested runtime work remains admissible through independently verified session identity, ownership, resource integrity and applicable permissions. Leave hook configuration and trust unchanged unless separately authorized; declining to execute an untrusted hook does not grant it trust.

Disabled or uninstalled Nightshift itself, a removed registration, invalid or mismatching retained resources, unknown controller ownership, denied permission for the requested operation, exhausted limits and unavailable required assurance retain their applicable refusals. A continuation fallback cannot bypass them. Report the actual category, preserve progress and continue independent authorized work where possible. An error recording the accepted run or its evidence is a durability failure, not merely unavailable continuation.

Selected-record suspension and read-only Ready do not require a complete unrelated ownership inventory. Read the explicitly selected valid record and its exact owner/resources independently of sibling records; an invalid selected record still refuses its mutation. Across pre-operation, abandoned-operation and post-operation reconciliation, update only references whose actual selected state is established and leave every unavailable sibling reference or unresolved operation protection intact. A missing database, missing row, corrupt/unreadable database, unsupported record, malformed state or unexpected record kind is never silently recast as an empty complete inventory. Canonical ownership acquisition/exercise, adoption, retirement and collection continue to require the complete protected inventory and fail closed when it cannot be established. Scoped suspension or Ready cannot discharge a sibling's retention or writer obligation, and their success does not authorize repairing, replacing or deleting that sibling's state. Cover both delivery/review selection directions and unsupported sibling rows within an otherwise readable store, as well as separate unavailable stores; preserve the selected-record identity, stopped status, existing references and refusal of unsafe canonical work and collection.

Each continuation failure records the mechanism, operation, actual cause, current owner and run, observation time, and a pending follow-up. Repeated observations of the same unresolved failure update or refer to that episode instead of generating duplicate follow-ups. Keep distinct failures distinguishable. A later successful observation establishes current health and retains the historical failure and its triage obligation; success alone does not invent a user disposition. No failure may disappear through invalidation, recovery, resumption, adoption or record replacement. Use bounded diagnostics and the existing evidence/history handling rather than embedding unbounded native logs in current state.

## Partial acceptance and deterministic recovery

Before the accepted-run write, handover remains pending and engineering has not started. After that write but before continuation is attempted, the run contains an outstanding continuation-observation and acknowledgement obligation; recovery performs those before dependent work. If the native mechanism was changed but its result was not saved, observe the actual run-associated mechanism before retrying so recovery does not duplicate or replace it.

Persist the continuation outcome and any failure follow-up together. If that transition fails, retain the earlier pending obligation and native evidence and reconcile the write before claiming a recorded outcome. Once the outcome is durable but acknowledgement has not been emitted, deliver the acknowledgement before engineering. If acknowledgement emission was interrupted or cannot be established, repeat the acknowledgement safely without repeating acceptance. Historical assistant output can establish that it was emitted; a prewritten delivered flag cannot.

These states are expected interruption points. An unreadable, malformed, duplicate, stale or unsupported acceptance or continuation record cannot count as completed reconciliation. Preserve the authority and obligations that can be established; fail the dependent transition closed when its ownership or durable outcome is unknown. Claims, observations and retries that change no engineering or lifecycle state do not reset the existing no-progress protection.

## Semantic progress and bounded continuation pressure

The concurrency revision records every committed write. It is not evidence of engineering or lifecycle progress. A central pure semantic projector and comparator determine whether a validated transition establishes new execution authority, lifecycle progress or an engineering/assurance obligation for substantive inputs. Unknown evidence is never progress. Existing ownership, admission, acknowledgement, evidence and freshness gates remain authoritative; progress accounting grants none of those permissions and replaces none of that evidence.

New delivery state carries `progress = {schema: 2, runId, atRevision, token, frontierHash, encodedHash, reminderHash, status, reason}`. `runId` is the containing immutable run identity; `atRevision` is its nonnegative safe-integer concurrency revision. Current metadata has lowercase 64-character SHA-256 values for `token`, `frontierHash` and `encodedHash`, `status: current` and `reason: null`. Unavailable accounting has `status: unavailable` and a fixed diagnostic code in `reason`; an unknown predecessor may render `token` and `frontierHash` null, which never permits automatic reminder pressure. `encodedHash` binds canonical stored state, including root, kind and run identity, excluding `progress` and `stopRecovery`; it detects damaged or stale accounting, not progress. Canonical serialization sorts object keys ordinally, sorts and deduplicates semantic sets, preserves meaningful order and uses documented historical defaults for absent optional fields.

`frontierHash` identifies a versioned artifact in the existing immutable artifact table: `{schema: 2, runId, credits: [...], closingBasis: [...]}`, with the same run identity and sorted unique SHA-256 fingerprints of already credited semantic achievements. Its cumulative closing subset and reminder binding follow the positive-provenance contract below. It is a dedicated reference loaded by accounting and recovery, not a generic artifact field automatically hydrated by ordinary reads. It contains no reports, native output or caller progress flag. Keep at most 65,536 entries in each credit set and 8 MiB of serialized UTF-8 for the entire frontier. This bounds the accounting mechanism rather than engineering or model use. At the bound, preserve the last valid frontier and obligations, mark accounting unavailable and stop automatic pressure; do not rotate or discard credits to refill it. Useful independently admitted active-turn work remains available.

Creation establishes an initial token and frontier from admitted initial facts, with provenance that no reminder is outstanding. Later meaningful progress derives a new token from the previous token and canonical validated progress delta. Hash tokens avoid a separate numeric progress-counter overflow. Credited achievements accumulate for the run and survive removal/restoration of evidence, closing replacement, repair, owner transfer and recovery. Losing evidence, reopening work or restoring the same already credited proof earns nothing. A new timestamp, identity, revision, attempt, successful operation return or arbitrary JSON difference is never sufficient.

The semantic projector covers every consumer and field family as follows. Task subjects use established task identity/kind and the internal spec association `agreement.specReviewTaskId`; their substantive context includes dependencies, outcome, decisions, spec path/content and applicable engineering inputs. Requirement/repair/review revisions establish ordering/currentness and never earn a credit by themselves. Titles, source descriptions and authority wording alone do not earn progress. An admitted material user decision can change execution commitments without changing outcome text. Snapshot identities use validated recorded files sorted by path and content hash, together with inventory, backlog-only and inclusion/exclusion semantics; validate their existing digest before normalization. Additional blob IDs and generated receipt/event identifiers are metadata. Projection reads recorded proof rather than rescanning the worktree; ordinary freshness gates continue to inspect actual files.

Credit the first admitted repair obligation, then require changed-input verification/assurance to establish subsequent substantive work; do not infer another edit from a new repair revision. `RunStore.save` is the central writer inside the existing project-lock and SQLite transaction. It derives accounting from the committed predecessor and validated candidate, not caller-supplied `progress` or `stopRecovery`. Cover creation, acceptance reconciliation/replay, ordinary updates, adoption and trusted direct saves. A missing current row with existing run history is not first creation. Validate predecessor and concurrency revisions; refuse an unsafe increment past `Number.MAX_SAFE_INTEGER` before mutation, never wrap/reset it. Creation/replay/adoption retain their authority and exact-resource rules. A replay with no write changes nothing; integration/process-only reconciliation does not mint progress. The reminder grammar is `stopRecovery = {schema: 2, runId, token, reminders, atRevision}`. Its run identity is the containing run; `token` is the established progress token last reminded; `reminders` is an integer from 1 through 3; `atRevision` is that committed reminder write. Absence means no outstanding reminder only when the schema-2 reminder binding and creation or complete successful reconciliation positively establish it. A dedicated internal reminder operation rechecks owner, current revision, existing eligibility and accounting under the transaction and issues only the next permitted count. It accepts no arbitrary caller token/count. Concurrent change requires rereading. An unchanged valid token preserves the count; proven new progress starts its next sequence at one. At three with no new progress, return `continue: false` without persisting four. A mismatch alone proves nothing.

Stop keeps lightweight unhydrated reads, validates marker/root/kind/run/revision/binding and reminder provenance, and compares the validated tokens. It does not load all assurance bodies, rerun Git, inspect native acknowledgement history or prove current filesystem freshness. Retain existing early behavior for absent/foreign/non-handover contexts, completion/holds, exhausted limits, explicit interruption, decision-only waits and nonactionable work. Standalone review contexts acquire no progress pressure. Status/history/wait/checkpoint inspections never consume reminders. Unavailable deciding accounting returns an explicit bounded stop response instead of disappearing into an empty outer-hook fallback. It neither kills workers nor revokes handover or grants engineering/collection permission.

For an existing delivery with absent, stale, malformed, foreign or unsupported accounting, perform bounded historical reconciliation: at most 256 revisions and 16 MiB of raw history plus referenced accounting artifacts. Locate complete creation provenance or a trustworthy schema-2 accounting checkpoint establishing the cumulative frontier, reminder and closing bindings, then replay semantic transitions and actual reminder writes in order, validating SQL/JSON revisions, root, kind, run identity and every required artifact. A legacy reminder anchor supplies a lower bound only and cannot initialize a complete frontier or prove an unused allowance within a truncated window. A limit hit, missing/contradictory row, future anchor or unreadable input is unavailable reconciliation. An old `{reminders, revision}` anchor never proves subsequent progress. Preserve its valid count; historical resets without semantic progress conservatively accumulate actual reminders up to three. Zero requires complete creation provenance or a validated accounting record establishing no outstanding reminder. Without complete recovery, retain any known lower bound and mark unavailable; do not grant its apparently unused remainder. Persist positive reconciliation in the next authorized writer/reminder transaction without crediting reconciliation itself. Preserve unavailable state and obligations until positive recovery; deletion/replacement is not recovery. Independently admitted work, hold or stop may continue where their underlying state is valid. Exact retained legacy releases continue using their own code; this machinery authorizes no migration or runtime substitution.

Deterministic verification covers equivalent no-op operations and real transitions; repeated check pass/pending/pass and failed attempts; review/validation/disposition/repair duplicates; closing clear/restore; acknowledgement capture and outcome cycling; replay/resume/adoption/direct saves; each rollback boundary; encoded/hydrated equivalence; damaged/missing artifacts and marker/reminder forms; bounded history/frontier recovery; and count/revision overflow. Assert tokens and preserved reminder obligations, together with unchanged ownership, acknowledgement, eligibility and resource-routing refusals. Reconcile operating guidance that currently implies observation or capability changes alone reset reminders. Model-owned continuation/stop behavior remains a separate per-host live claim with unexercised contexts marked provisional.

Optional hook diagnostics describe hook integration rather than unconditional overall continuation availability. Codex goal health remains independently observed and can be available while hooks are unusable; absent/stale/unrelated goal evidence remains pending, unknown or failed according to its own evidence. Claude unusable-hook precedence and active-turn/resumption guidance remain intact. Usable configuration alone proves neither host's continuation. Strict/non-optional recovery messages and refusal codes remain unchanged. ### Positive reminder provenance and bound closing discharge

The repaired progress marker is schema 2: `{schema: 2, runId, atRevision, token, frontierHash, encodedHash, reminderHash, status, reason}`. The existing identity, revision, token, frontier, encoded-state hash and current/unavailable rules remain. For current accounting, `reminderHash` is the lowercase SHA-256 of canonical JSON `{schema: 1, runId, reminder}`: `runId` is the containing immutable run identity, and `reminder` is either the exact validated schema-2 `stopRecovery` object or explicit null establishing that none is outstanding. Null is an attested state, never a fallback for missing input. An unavailable marker retains a known binding or renders it null only when unknown. The marker's encoded-state hash continues to exclude `progress` and `stopRecovery`. Validate the reminder binding against both current state and committed provenance; matching absence in current/history rows does not create a new null attestation.

The frontier artifact is schema 2: `{schema: 2, runId, credits, closingBasis}`. `credits` retains its cumulative semantic-achievement meaning. `closingBasis` is a sorted unique subset of those SHA-256 credits representing material task commitments, qualifying engineering verification/assurance and task completion. Closing achievements, diagnostics, observations, generated identities and reminder bookkeeping are excluded. Initialize the basis from admitted initial facts and accumulate qualifying substantive achievements; never shrink it on reopening, proof loss, evidence restoration or closing replacement. The closing-context hash is SHA-256 of canonical `{schema: 1, runId, closingBasis}`, with the containing run identity and that complete cumulative subset; the empty basis is `[]`, not unknown. Both credit sets remain bounded by 65,536 entries, and the entire serialized frontier, including the basis, by 8 MiB. Exhaustion preserves the last valid frontier and obligations and marks accounting unavailable; no provenance is evicted to restore pressure.

An internal closing binding is `{schema: 1, runId, contextHash}`: its run is the containing run and its hash is the established closing-context hash captured at the admitted discharge. Scalar lifecycle evidence has `closing.progressBindings = {retrospective, report, delivery, triage}`, each slot holding its binding or explicit null when that fact is absent. Retrospective captures the established context. Its report, actual recipient-confirmed delivery, triage and resulting closing record inherit that cycle's context.
