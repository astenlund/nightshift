# Make Ready and Exploring links open at their target

## Origin

Tracked from 2026-09-13 as the quick win "Align Exploring source-link guidance with Ready" and moved to Exploring on 2026-09-30 at the user's direction, once it had grown to include an investigation of links that open at a line. The quick win's two evidence paragraphs follow unchanged apart from their link paths.

Confirmed during review and skeptical validation of the Ready presentation change on 2026-09-13: `skills/exploring/SKILL.md` requests breakout links but lacks the explicit index-relative resolution, index-file fallback, absolute-link preservation and Windows Markdown formatting guidance now present in `skills/ready/SKILL.md`. Earlier Ready probes exposed failures under similarly thin guidance; the Exploring skill itself was not probed, so a corresponding behavior failure remains an inference. The user chose to track this follow-up rather than implement it. See [the Ready presentation evidence](../reports/ready-exploring-presentation-20260912.md).

Extended on 2026-09-30 at the user's choice, after a Ready report in this repository on Claude Code 2.1.285 with installed 3.2.17 showed that Ready's own guidance has a gap as well. The report linked Exploring drafts as `.nightshift/features/<slug>.md`: resolved against the right base, the index directory, but written relative to the working directory. Those links were not clickable in Claude Code's terminal UI, while the same links written as absolute paths, such as `C:/Git/nightshift/.nightshift/features/finding-affected-surfaces.md`, were confirmed working by the user. A later absolute link to this entry, written without a line number, did not open at the entry, so the user had to search the file for it. `skills/ready/SKILL.md` asks for a clickable link and names the resolution base but never requires an absolute target, and the parser emits the index name and the relative `link` with no line, so the model chooses the final form; the shipped [Ready Exploring visibility record](ready-exploring-visibility.md) prescribed the repository-root-relative form that failed. The 2026-09-12 presentation probes checked link destinations and file existence, not click handling. [Present a governing spec as a link with a change list](../QUICK_WINS.md#present-a-governing-spec-as-a-link-with-a-change-list) records the same rendering in chat on 2026-09-29, when relative links rendered as invalid and the session used absolute `file:///` links.

## Line-number links

On 2026-09-30, in the same Claude Code 2.1.285 session running in Windows Terminal, the user followed three links meant to open `QUICK_WINS.md` at line 207: a Markdown link whose absolute target ended in `:207`, the bare absolute path followed by `:207`, and a Markdown link whose absolute target ended in `#L207`. None opened, and the bare form did not render as a link. A Markdown link with a plain absolute target opens the file, but not at a line.

The user recalled an earlier investigation, several hours long and possibly needing some kind of adapter, that had found a form opening at the right line. It exists, and on 2026-09-30 the user confirmed it still works: from the same session, a Markdown link whose target was `subl://open?url=file:///C:/Git/nightshift/.nightshift/features/source-link-targets.md&line=19` opened this record at line 19 in Sublime Text. The adapter is the user's own machine setup. A `subl://` URL protocol is registered under the user's classes and runs `subl-protocol.py` from the user's PowerShell scripts; the user's PowerShell profile says `Install-Linkify.ps1` wires that handler and Windows Terminal's `safeUriSchemes`. The profile and the user-scope environment set `NIGHTSHIFT_LINE_LINK_FORMAT` to `subl://open?url=file:///{path}&line={line}`, using ripgrep's `--hyperlink-format` placeholders, and the variable reaches Claude Code sessions; the Codex configuration sets it too, together with `NIGHTSHIFT_FILE_LINK_FORMAT` and `NIGHTSHIFT_LINK_RENDERING`.

Nightshift v2 consumed the variable. Commits 602acdb and 7cbdf06 (2026-08-23) and 01c6d81 (2026-08-24) had the spec-agreement skill's `locate` operation fill it with an entry's absolute forward-slash path and line, fall back to the bare absolute path when it was unset or empty, and render OSC 8 links for Codex when `NIGHTSHIFT_LINK_RENDERING` was `osc8`. The v3 change 8ca3cb4 (2026-09-08) deleted the spec-agreement skill, the variable's only consumer, as the migration retired the agreement digest. No disposition in [the v3 migration](../../V3-MIGRATION.md) or [the migration status](../MIGRATION_STATUS.md) names line links. They went with the agreement digest's presentation, which the migration replaced by decision on 2026-09-06: the concise spec or readback and material-delta agreement replace that presentation contract, with the full spec and supporting evidence kept accessible. The only archived mention found, [a v2 proposal](../migration/v2/QUICK_WINS.md#agreement-digest-economy) for a composite entry operation returning each artifact's `locate` result with its line and rendered link, was retired with it. Restoring line links is therefore new scope beside that replacement rather than the recovery of an accidental loss; [Audit capabilities that left v2 without a disposition naming them](../QUICK_WINS_HISTORY.md#audit-capabilities-that-left-v2-without-a-disposition-naming-them) looked for others like it on 2026-10-01 and found eight, recorded in [its report](../reports/v2-capability-audit-20261001.md).

On 2026-09-30 the mechanism was at first reported as recorded nowhere: nothing an agent loaded at the time named the variable (the user's global instructions have named it since), and the first search looked for guessed keywords in transcripts, memories and the backlog, not in this repository's history or the environment, and read a search cut off at 30 files as absence. The documentation review of this record found it. The 2026-09-29 session had recovered only the absolute file link. Codex sessions write links such as `[name.md:25](C:/Git/nightshift/.nightshift/features/name.md:25)`, Codex's own convention and the first form tested above.

## Direction

Reconcile the Exploring skill's source-link guidance with Ready, and have both skills write every local link in their reports with an absolute target, resolved against the containing index directory. Restore line links: when `NIGHTSHIFT_LINE_LINK_FORMAT` is set and non-empty, both skills link an entry held in an index at that entry's line through it, and otherwise fall back as v2 did to the plain absolute file link, with the line in the link text. Record the form where agents load it, so it is not lost again. Verify both skills' output on installed hosts by following the links in the terminal UI, not only by destination checks, including relative records, drafts without record links, absolute links and Windows paths containing spaces, whose angle-bracket form has not been checked for clicking. Preserve the Exploring view's full draft presentation and separation from ready work. The skill changes ship with a version increase.

## Open questions

- Whether the skills read the variable and build the links themselves or the parser supplies finished link targets, as v2's `locate` operation did, and how the line is found: a new parser output field, which changes a shape both skills and `skills/ready/ready.test.js` consume, or the model looking the line up in the index. On 2026-10-01 the user proposed the parser output field, in their words: "add line numbers to the ready output so you don't have to hunt for them". That followed a Ready report in this repository that linked every index-held entry at its line by looking up the index line of all 81 ready, blocked and external entries with a scratch script, because none of the parser's items carries a line: ready items give the index, title and excerpt, and Exploring items add the relative `link`. Whether the parser also supplies finished link targets stays open.
- Whether whole-file links use `NIGHTSHIFT_FILE_LINK_FORMAT`, which the Codex configuration sets but the user-scope environment does not, and whether Codex needs v2's OSC 8 rendering; how Codex's terminal UI treats these links and its own `path:line` convention is to be established from Codex's own evidence rather than inferred from Claude Code's.
- How the plugin describes the adapter to other users, since the handler and the variable are the maintainer's machine setup and the fallback is all a user without them gets.
- How clicking is verified, since it needs a person or terminal automation; the 2026-09-12 campaign used model probes with automated destination checks.
- How this relates to [Present a governing spec as a link with a change list](../QUICK_WINS.md#present-a-governing-spec-as-a-link-with-a-change-list), which needs the same link form for spec links and also covers the web app over Remote Control, where that session sent the file instead.
