# Support Mistral Vibe as a controller host

The user approved GLM in the Vibe host context for the controller role on 2026-10-26, recorded in [the approval report](../reports/glm-controller-role-approval-20261026.md); that approval is settled and must not be asked for again. The integration is separate and not built: the Vibe reviewer host delivery excluded Vibe as a controller, and `internal/runtime/ownership.js` admits only Claude and Codex controllers today. Tracked in [the feature index](../FEATURES.md#support-mistral-vibe-as-a-controller-host). The original capture is follow-up `vibe-controller-host-support` in run `dcd9e840-e8b6-4f28-9c6e-b5aaaaac9847`.

## Requested direction

- Let a Vibe session own a Nightshift delivery as controller with the same durability, ownership and reconciliation guarantees as a Claude or Codex controller.
- Preserve the recorded GLM controller approval and the per-role approval direction; formal controller approval criteria remain open.

## Probe observations (2026-10-27)

The probes ran from a live Vibe 3.0.2 GLM session on Windows (session eedf3550-9567-1094-ff65-ac0b5c951ff7) through the development CLI against a scratch project, with scripts and outputs in the session folder `.tmp/vibe-controller-exploration-20261027`. They establish the controller-side facts; dispatching Vibe reviewers is already covered by the reviewer-host delivery.

- A `handover` naming `controller: {host: vibe, session: <real id>}` is refused with `invalid-controller` by the identity check in `internal/runtime/ownership.js`, which admits only Claude and Codex controllers, and `internal/runtime/store.js` holds a second `unsupported-host` gate at creation behind it.
- Creation observes the native controller process even in development mode: the same request naming a Claude controller from the Vibe process chain was refused with `controller-claim-unavailable` because the ancestry holds no `claude.exe`.
- `observeNativeOwner('vibe')` finds the live `vibe.exe` in the calling process ancestry with no code change; the walk is about ten levels from a shell-tool node process, within the inspector's 16-level budget, and background processes started through Vibe's sandbox process tools reach `vibe.exe` as well. The walk matches any `vibe.exe` in the chain, which identifies the session whose chain the runtime was invoked in.
- The Vibe session ids observed in the probes are lowercase hex UUIDs matching the runtime's UUID identity regex. The per-session lock files in the Vibe home name the process owning the session, that process sat in the probed session's own ancestry, and the ancestry walk matches any `vibe.exe` in the chain rather than the session's owner process, so with concurrent Vibe sessions possible, adoption's exact-former-controller inactivity proof needs the per-session identity, not only a live `vibe.exe`; two sessions were live during the probes, a probe-transcript observation rather than a surviving artifact.
- The Vibe session journal is append-only hash-chained JSONL under `logs/session/unified/<session>/journal` in the Vibe home, rotated to a new sequence-named file as the session advances generations, with plain singly linked BOM-free files; its `projection_delta` rows carry assistant message entries with stable entry ids, `createdAt` timestamps and session attribution, and `meta.json` attributes the working directory. A probe extracted every assistant message of the probed session this way and the runtime's `acknowledgementText` accepted the required paragraph shapes, so a Vibe branch of the native acknowledgement observer is implementable; the journal's schema is Vibe-internal, so it carries the same version-drift risk the reviewer host accepted for the configuration schema. The probes also observed the journal's `action_result` completion records carrying `text` (the visible part), reasoning and tool-call parts with per-record usage counts, a probe-transcript observation, raw material for any future Vibe in-host worker evidence branch.
- Vibe 3.0.2 offers hooks of kinds `post_agent`, `pre_tool` and `post_tool`, registered through `hooks.toml` files, a project `.vibe/hooks.toml` in trusted folders or the user `hooks.toml`, beside a native plugin's `ai.mistral.vibe/hooks.toml`; hook payloads carry `session_id`, `transcript_path` and `cwd`. A `post_agent` hook runs once per turn after the agent finishes, and its deny injects the reason as a retry user message capped at three retries per turn; there is no SessionStart or PreCompact hook and no persistent goal mechanism. The `/loop` scheduling persists across resume and runs only while the session is live, and `vibe --resume <id>` is not folder-scoped, so a user can resume a delivery session by hand; no mechanism relaunches an exited host, as on the other hosts.
- No environment variable carries the session id to tool subprocesses, so the handover skill's `${CLAUDE_SESSION_ID}` equivalent must come from a hook payload or from matching the lock file's process id against the session's own ancestry.
- The dispatch path is controller-host-agnostic: it takes each worker's host from its candidates and records the session each dispatched reviewer actually ran in, and the reviewer-host delivery already ships headless Vibe reviewers running in their own fresh session ids, so the dispatch path itself holds no further host-keyed work once ownership admits a Vibe controller, while the continuation observation and the acknowledgement that precede every dispatch still need their Vibe branches; and the runtime's exclusion of controller and former-controller sessions from independent review, keyed on session identity alone, then covers it without change. `wait` is host-agnostic. This is a code reading, not a probe: no Vibe controller can own a run today, so no dispatch from one was exercised. The runtime does not model-gate the controller, so the recorded GLM controller approval needs guidance changes only; no runtime model gate exists to change for it.

## Details to settle

- Controller process identity: the ancestry `vibe.exe` observation serves turn claims unchanged, but adoption's exact-former-controller inactivity proof must distinguish concurrent Vibe sessions, likely through the session lock's owning process id beside or instead of the ancestry match.
- Execution resources and the operation lease: development runs carry no resource binding, while a bound Vibe controller needs a Vibe branch through the retained releases layer's registration and execution binding, whose host-keyed parts are the registry host list and the native executable and settings integration; the lease and serialization machinery itself is host-agnostic.
- Continuation: add a third mechanism kind backed by a registered `post_agent` hook, and decide whether its weaker guarantees, the three-retry cap per turn and the absent session-start and compaction notice routes, count as verified continuation or are always recorded as a limitation with a follow-up; the brief tolerates a weaker or failed mechanism either way.
- Session identity discovery for the controller: a hook payload versus lock-and-ancestry matching, possibly a small hook feeding the session id and activation to the runtime as the analogue of `CLAUDE_SESSION_ID`.
- The acknowledgement observer's Vibe branch and its journal-schema drift policy, including a Vibe version floor and the recourse when a later version changes the journal.
- In-host workers: keep them closed for a Vibe controller, which then dispatches reviewers instead, or build native worker evidence for Vibe.
- Scope: development-mode controller support touches the runtime core gates alone (ownership identity, the creation request and saved-record host gates, continuation kinds, the acknowledgement branch and the worker-evidence policy), while installed bound runs also need a Vibe branch through the retained releases layer and a packaging decision, since Vibe's Claude plugin adaptation carries skills and MCP servers only and hooks need either a native `ai.mistral.vibe` plugin or registration into `hooks.toml`.
- The report-delivered confirming actor: a complete delivery's report confirmation may come from another admitted session of the same project, and the runtime validates that confirming actor's host against Claude and Codex only, so decide whether a Vibe session may confirm a delivered report and under what admission.
- The formal controller approval criteria the approval report leaves open, which are policy rather than runtime work.

Tracking does not authorize implementation and does not claim any of these capabilities exist.
