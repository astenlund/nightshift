# Refusal friction

Recorded on 2026-11-03 from the maintainer inbox report `2026-11-03-refusal-friction-landscape.md` and agreed at the user's inbox triage that day. The report came from the Hermes home project (session of 2026-11-01 to 2026-11-03, delivery runs `41e7d80c` and `e43c9099`, review context `2b1e2818`, installed 3.3.25) at the user's request, to describe the landscape with examples and directions without prescribing fixes. It groups the earlier inbox reports by title only, so each report's fit with its shape is unverified; this record keeps that qualification.

## The user's words

"we can't keep working like this. refusals. the 'can't do that now' sort of stuff. i realize we need som checks for provenance, but i've been dealing with a ridiculous amount of this sort of stuff lately. we need to change something."

## The principle the user set at triage

At the inbox triage of 2026-11-03 that settled this report, the user framed the cause in their words: "i think part of the problem is that the runs are waterfall-shaped. we should make the process more agile. perhaps the design specs are too detailed; ai models are getting smarter and smarter and can do more and better work if they're not too locked down by overly-detailed specs. the other part is that we need to distinguish between recording a decision and locking it down. the former is needed for provenance, the latter leads to the blocking behaviour we keep seeing." They chose to update VISION.md with that framing and to take another pass at the assessment before resuming work on its worklist; the refusal-code audit under Open below is an input to that pass. The prototype idea of 2026-11-02 belongs to the same framing and is carried into the VISION update: after Hermes' dual-channel approval feature went through an agreed spec, spec review, two delivery runs with lead, skeptic and fresh-pass reviews and closing before its owner first used it, and each live session then changed what the reviewed spec had fixed (a window became a toast and attachments an outbox mount, the toast never appeared, a 32-character id was impractical to type on a phone, the delegating model never reached the feature, the acknowledgements were noisy), the user said: "i think this workflow isn't ideal. perhaps it would be better to work on a prototype at first, that could be iterated on, before nailing things down." An Exploring draft filed for it on 2026-11-03 was folded into the VISION update at the same triage; its open questions, which features qualify and who decides, what a prototype may skip and keep, how its lessons become the spec and when the full lifecycle takes over, go with it (maintainer inbox report `2026-11-02-prototype-before-spec.md`). The user decided those questions on 2026-11-04; VISION.md carries the shape and WORKFLOW.md the procedure.

## The shapes

1. **Every obligation is enforced as a hard refusal.** Checks that protect provenance and ownership and checks that keep bookkeeping tidy fail the same way, and the controller has to find a ritual that satisfies the gate. The report's new example: closing run `e43c9099`, `complete` refused `stale-review` because Hermes itself had written a one-line runtime flag (`onboarding.seen.busy_input_prompt: true`) into the tracked `config.yaml`; reverting the line made `complete` refuse `closing-review-required`, because triage had been recorded with the line present; the way out was to revert the line, record `triage` again, `complete`, then restore the line, a ritual with no assurance value. From the same session's notes, not re-checked: a review import refused `changed-base` until its base named the run's original base, a `dispose` refused `missing-validation` over the nested finding-id format, an `advance` refused `review-required` because a reproduction check had gone stale, and earlier in the project post-triage spec and `config.yaml` edits made the closing review unimportable (`closing-scope`, run `41e7d80c`), editing an accepted spec mid-delivery made `repair` refuse `spec-review-required` (run `f198f65c`), and listing the feature record as a spec-review artifact let a docs-stage edit stale the spec assessment (run `41e7d80c`). Reports grouped here by title: completed-code-review-staled-by-docs-task, docs-stage-edits-below-root-stale-code-review, governing-spec-edits-stale-code-assessments, stale-validation-after-repair-edit, closing-cleared-by-spec-reassessment, covering-docs-import-reopens-completed-tasks, deferral-route-edit-stales-docs-assessment, failing-spec-task-check-blocks-code-checks, stale-task-check-after-closing-on-complete-run, queued-spec-task-cannot-gate-code-task.
2. **The owner's decision is not a way out.** When the user says work is settled or a gate's remaining concern does not matter, no recorded owner decision replaces the refused condition. Examples: review context `2b1e2818`, the standalone spec review of the 2026-11-02 amendment, is still `running`; its assessment was clean, the user accepted the spec and a delivery used it, but nothing prompted `advance` and `complete`, and completing it now would most likely be refused as stale (`specAcceptance.current: false`). After the report was first written the user asked to close that context: the read-only `close-manifest` of 3.3.26 showed nothing in the way (29 workers complete, no pending findings, no follow-ups, only the context's own `#review` task incomplete), but its older-release guard refused with "close from a new session on a current release", because the requesting session (`bcb063c6`) is bound to 3.3.25, the release that created the context, so the session that owns the record and knows its history cannot close it and the user has to start another session. And the live retest after delivery `e43c9099` found a defect that the closing scope kept out of the run, so the fix went outside Nightshift at the user's direction. Reports by title: no-route-for-fix-now-followups, triage-decisions-never-recorded-in-runtime, reopen-run-after-triage, reopen-delivery-after-live-defect.
3. **The lifecycle is one-way.** Spec, delivery, closing; nothing goes back, and real use kept changing what the feature should be, each change costing a full cycle. Reports by title: prototype-before-spec, reopen-delivery-after-live-defect, reopen-run-after-triage.
4. **Pressure and cost where none is wanted.** The Stop hook resumed `e43c9099` three times while only the user's triage remained; GLM reviewers on Vibe are never resumed; the ready parser cannot run as a recorded check. Reports by title: stop-hook-loops-at-triage-awaiting-user, unattended-churn-while-user-away, stop-hook-revision-refuses-background-dispatch, vibe-reviewers-never-resumed, ready-parser-unrunnable-as-recorded-check, runtime-friction-large-delivery.
5. **Refusals that do not say what to do.** A condition named without its route out, or one cause reported as another. Reports by title: stale-artifact-refusal-unnamed, stale-revision-reported-as-stale-owner, concurrent-dispatch-refusal-code, advance-documentation-evidence-field-name, advance-from-documentation-needs-two-calls.

The report observes that, by title, a large share of the reports it groups concern staleness, refusals, closing or continuation rather than wrong results, and sets aside the controller's own slips in that session.

## Directions and their owners

Each direction is the report's; the owner is where the backlog already carries it, so that this record consolidates rather than duplicates. An owner named as a worklist item is a step of [the assessment worklist](../reports/assessment-worklist-20261018.md), which is the current focus.

- **Separate the two kinds of check**, which the user's principle above states as recording a decision for provenance without locking it: hard refusals for provenance, ownership and safety; bookkeeping conditions recorded as findings the run shows rather than walls. Owners: worklist Add 14 (invariants that are gates against judgment that stays prose), Add 3 (scoped evidence) and Remove 6 (the lifecycle on tracking prose). The report's proposed first step, an audit of the refusal codes against that split to see how much friction is the second kind, has no owner; it is the one open item below.
- **Give the owner a recorded way out**: a user decision ("this is settled", "accept this evidence as is", "close it") recorded with reason and scope and then honoured. Owner: [Manual gate bypass on the user's responsibility](../features/manual-gate-bypass.md), whose agreed scope reaches a strong review or check refused for technical reasons and says refusals protecting saved state or work never can be bypassed; whether bookkeeping refusals join its scope is a design question for that feature. The user's acceptance of a spec already has a route (`spec-accepted`), and [Close settled records](../specs/close-settled-records.md) shipped `close` in 3.3.26 for records the user considers settled.
- **Judge staleness by relevance**: staleness that considers what the evidence covered, or asks before invalidating. Owners: worklist Add 3 and step 3; [Probe evidence about the host is discarded on any edit](../BUGS.md#probe-evidence-about-the-host-is-discarded-on-any-edit); [Documentation and backlog edits land before the first cumulative assessment](../QUICK_WINS.md#documentation-and-backlog-edits-land-before-the-first-cumulative-assessment), which since 2026-11-03 carries the path-classification accounts; [Resolve a deferred finding only once its destination exists](../QUICK_WINS.md#resolve-a-deferred-finding-only-once-its-destination-exists) for the route edit. The runtime-written `config.yaml` flag above is a new example of a change with no bearing on what the evidence assessed.
- **Allow going back**: reopen a delivery when live use finds a defect, and a lighter iterative phase before a spec is fixed. Owners: [Keep a handed-over run open for triage after delivery](../features/handover-open-for-triage.md), which carries the user's words asking for reopening after triage-decided work and a failed live retest and whose direction was revisited on 2026-11-03 once VISION carried the framing, with settlement decided the same day under its Agreed direction, and the prototype idea under the principle above, carried into the VISION update and shaped on 2026-11-04.
- **Close what is finished**: a review context whose assessment fed a delivery, or whose work the user considers done, closed or offered for closing instead of left `running`. Owners: Ready's run-state section since 3.3.24 lists every open record with an offer, and 3.3.26's `close` closes what the user considers settled, which covers the mechanism but not the prompt to use it, and which a session bound to the older release that created the record cannot run, as the `2b1e2818` attempt above shows, so the owner must hand off to a new session, which [Say at handover when the session runs an older release than the installed one](../QUICK_WINS.md#say-at-handover-when-the-session-runs-an-older-release-than-the-installed-one) would at least announce; the Exploring draft [End-of-shift wrap-up with a diary for the next session](../FEATURES.md#end-of-shift-wrap-up-with-a-diary-for-the-next-session) would supply the prompt at session end. Review context `2b1e2818` is the live case.
- **Size the machinery to the work**: a lighter path per piece of work, or a clear signal of when the heavy path is worth it. Owners: [State the expected size and offer slices before handover](../QUICK_WINS.md#state-the-expected-size-and-offer-slices-before-handover), the Exploring draft [User-configurable workflow composition](../features/workflow-composition.md) and the prototype idea above; [VISION.md](../../VISION.md#invariant-priorities) rules out trading trust for speed, which any lighter path has to reconcile.
- **Make every refusal actionable**: each refusal names the condition, why it holds and the cheapest legitimate way forward, including the owner decision that would settle it. Owners: worklist Add 8 and Add 14, under which status names the operation and fields due; [Name the stale check when completion refuses](../QUICK_WINS.md#name-the-stale-check-when-completion-refuses); [Name the changed inputs of a stale assessment in status](../QUICK_WINS.md#name-the-changed-inputs-of-a-stale-assessment-in-status); [Report a revision mismatch as stale state rather than a stale owner](../QUICK_WINS.md#report-a-revision-mismatch-as-stale-state-rather-than-a-stale-owner); [Say what a review import does to a task's stage and which stage an advance reached](../QUICK_WINS.md#say-what-a-review-import-does-to-a-tasks-stage-and-which-stage-an-advance-reached); and the lease-code note under [Mid-run follow-up capture is refused while a dispatch runs](../QUICK_WINS.md#mid-run-follow-up-capture-is-refused-while-a-dispatch-runs).

## Open

- The audit of refusal codes against the provenance-or-bookkeeping split, which the report proposes as the way to measure how much of the friction is the second kind, was made on 2026-11-03 as [the refusal-code audit](../reports/refusal-code-audit-20261103.md) and fed the assessment pass the user chose that day: 993 refusal sites over 359 codes, 541 of them slated for the removals of the worklist's steps 4 and 5, all but seventeen in modules the worklist names, and the friction concentrated in one comparison over a snapshot of the whole project inventory, `evidence.js:fresh` and, for the closing baseline, `changedPaths`, which the worklist's step 3 now re-scopes.
- The report did not analyse whether any listed refusal was strictly necessary for provenance; some may be load-bearing in ways it does not see, so the grouping above is a map of complaints, not a verdict on the gates.
