## Outcome and scope

Resume the same authorized work after an interruption or a change of controller session, preserving its commitments and evidence. Fix [Run ownership is locked to the creating host session](../BUGS_HISTORY.md#run-ownership-is-locked-to-the-creating-host-session) and [Renewed handover yields with blocked native continuation](../BUGS_HISTORY.md#renewed-handover-yields-with-blocked-native-continuation). Autonomy comes first, independent quality second, efficiency third, within the user's authority and limits.

Add an explicit adoption operation for the checkout's current unfinished run. Support another session on the same host and a switch between Claude Code and Codex on the same Windows machine and project. Adoption requires the user's actual direction to resume that run in the adopting session. It does not require renewed agreement on unchanged work. A renewed handover likewise preserves agreement and resumes useful authorized work while establishing what can continue after the turn ends.

This scope excludes transfer from an active controller, remote-machine migration, adoption of completed or superseded runs, automatic host relaunch, and Ready's proposed interrupted-run notice. Those are distinct decisions or backlog work. Publication remains separately directed by the user.

## Adoption eligibility and authority

The request identifies the current run, its observed revision and previous controller, the actual adopting native session, and the user's adoption authority. Existing host/session grammar is unchanged: host is `claude` or `codex`, session is a nonempty actual native identity. Run identifiers and revisions use their existing grammar. Authority is nonempty user-direction text; omission, fabricated authority, self-adoption, a different active run or stale observations cannot mutate ownership.

The positive eligibility rules are different for the two source states:

| Source state | Sufficient evidence, alongside ordinary admission and explicit adoption authority |
| --- | --- |
| Explicitly stopped | The current saved stop, confirmed worker termination under the rules below, and no active or uncertain project operation. The former chat or host process may remain open. No additional controller-process inactivity proof is required. |
| Abandoned but running | The latest supported controller claim identifies the former controller's exact native process; that process is confirmed terminated; the claim and run revision remain unchanged under project admission; every worker is confirmed terminated; and no active or uncertain project operation survives. |

The running-source rule uses the claim protocol below to exclude a resumed controller using an obsolete process association. A bare old activation record or PID is insufficient. A live source process, including a shared app-server process, does not satisfy this first implementation's abandoned-running predicate. The user can stop the run in the original session, or close the owning host and retry after its work is reconciled. Session-level idle status may support a future broader predicate, but this change does not claim it. Unknown activity never permits adoption. Temporary inspection failures permit a later retry; missing historical proof with an unavailable original owner leaves the running run protected and locked. No force override or replacement run escapes that state. State this permanent limitation when applicable instead of implying that repeated retries will invent evidence.

Add `claim-controller`, an owner-only admitted operation for a running run. It obtains the actual controller process identity from the native host context, not an arbitrary request PID. Before canonical engineering in every new or resumed turn, the controller must obtain a successful claim; `create` and `resume` perform the same claim step for their current turn. An unavailable claim permits diagnostics and recovery only. This is a required model-owned entry protocol, verified on both hosts, and it does not sandbox arbitrary filesystem writes outside the cooperating workflow.

If initial claiming fails, `create` commits no run row or active-pointer replacement. Owned inspection storage may remain, but no run or engineering grant is reported; retry after the capability is restored. An unavailable claim during `resume` records the failed observation when admitted and keeps the existing run stopped. Per-turn refresh is model-owned; the runtime enforces owner and process incarnation, not an unavailable native turn token.

The latest `controllerClaim` records the exact existing `{host, session}` owner grammar, `process` as `{pid, created, name}` using the positive native PID, native creation-time string and executable basename returned by process inspection, `revision` as the claim write's revision, and `observedAt` as UTC ISO time ending in Z. Its scope is one run and owner. An unavailable process is null with a nonempty `reason`; a usable process has a null reason. Missing historical claim means unknown on the running branch and does not bar the agreed stopped branch. Native process identity is independent of hook activation and survives retirement of an activation record. Each claim replaces the current observation and preserves the old one in history; no elapsed-time expiry substitutes for inspection. Adoption clears the current claim. A failed identity refresh records an unavailable claim when admitted and returns `controllerReady: false`; failure to record it also refuses engineering. An admitted caller cannot continue using a preceding successful claim after either failure. `controllerReady` is a grant in the successful claim/create/resume response for the caller's current turn; a read-only brief reports the stored observation without granting work. Engineering operations require a claim matching the actual caller incarnation, and the model checks its grant before direct file edits. Observation calls are bounded; timeout or malformed results mean unavailable.

Claims and adoption serialize through the same project admission boundary, including development execution. Adoption observes the exact claimed process and rechecks the claim, revision and owner before committing. A source that resumes first must publish a new claim before writing, which changes the checked revision or identifies a live process. A source that resumes after the transfer fails the owner check. This is the sufficient combination behind the process-termination predicate; death of an arbitrary earlier process remains insufficient. Read-only operations never grant a claim. Hook-driven mutations recheck the current owner under the project/store locks and cannot resurrect a former owner.

The shared correctness boundary is the run-store transaction plus durable reservations for execution outside it. State-only changes use the existing owner/revision transaction. `dispatch` keeps its worker reservation; `check` and `probe` gain internal, non-model workers with role `operation`, registered as starting before any command launch or lasting external work. This applies in both bound and development modes, independently of the retained launcher's additional operation lease. A reservation records its action, task and check/probe identity, actual helper-process identity, and launch/termination evidence as it becomes available. Unknown launch or termination stays active/unverified. Known pre-launch abandonment can become failed once its helper is confirmed gone; known terminated work can be reconciled by the adopter under the worker rules. Reservation and adoption race through the same transaction: either the reservation is visible and prevents adoption, or adoption wins and the former owner cannot reserve work.

Registering a check also records a non-passing pending result for that check name, so a crash cannot expose an older passing result as the latest check. Commit the actual result and the operation worker's terminal status together; after a crash without a collected result, retry the check rather than inventing its outcome. Probe and dispatch completion similarly retain failure/unknown evidence and never fabricate usable assurance. Internal completion uses the reserved worker identity and current owner, tolerates intervening bookkeeping revisions, and grants no new execution. Active or uncertain reservations prevent adoption and completion; read-only diagnostics remain available. These records reuse the worker lifecycle and run database, not a new development-only lease database.

The public model-worker roles remain unchanged; only runtime command execution creates internal `operation` workers. Status, wait, Stop and completion consider them for activity, while attribution and model-budget logic never treat them as model assessments or model dispatches. Controllers must still register separately surviving work outside runtime calls. Older development operations predating reservations are not proved quiescent by missing records: obtain factual quiescence evidence from the owning host/operator that accounts for those commands, distinct from adoption permission. If that evidence is unavailable, keep adoption blocked. The protocol does not discover arbitrary unrelated processes or coordinate writers outside the workflow.

For bound runs, the launcher authenticates the adopting host/session and checks enabled registration, current activation and the exact retained release before the exceptional ownership change. Reconcile operation termination under project admission before deciding eligibility. Inside the ownership transaction, recheck the run, revision and former controller and exclude racing mutations. At most one competing adopter succeeds. Once adoption commits, every ordinary mutation and hook from the previous controller is refused or ignored, including a resumed old conversation. Read-only diagnostics remain available.

Real development-to-development adoption uses the same two eligibility branches when the executing runtime implements this contract. It retains the developer-operated trust boundary: the operator supplies actor identity and authority; retained-host authentication is not claimed. Validate their shape and expected owner, preserve explicit development mode, and use the same admission serialization, claims, worker and independence rules. A missing historical claim blocks the running branch, not the stopped branch. Tests may inject observations only as fixture evidence. Legacy state not identified as development is not silently converted.

Stopped runs stopped for resource limits retain those limits and stop reasons. Adoption never replenishes a budget, clears a deadline, unblocks a task or treats adoption authority as permission to change the work. Failed workers keep their failure records and are replaced only through ordinary authorized recovery.

### Worker termination and unfinished records

Worker records and worker activity are distinct. Existing terminal records are accepted according to the ordinary lifecycle contract unless current evidence contradicts them. For a non-terminal contained dispatch, verify the saved run/worker association and confirmed empty process job, or equivalent complete termination evidence for its runner and descendants. A vanished child PID alone does not prove its still-live runner cannot launch another attempt. New managed launches retain process creation identities; a reused PID can then be distinguished. With only a historical PID, an absent process proves that process gone, while a live or uninspectable PID remains ambiguous. This alone does not prove unrecorded descendants gone.

For an in-host helper, use an attributable terminal native result/status for that exact session and assignment, or verified containment evidence covering the helper. Do not infer termination merely from controller death. Missing or inaccessible evidence is unknown and blocks adoption; the original owner may reconcile it when available. The empty-worker case passes.

Adoption may commit with non-terminal worker records only when all those workers have positive termination evidence, stored in the adoption record. It must not fabricate successful assessments from that evidence. After the ownership commit, the new owner records the terminated workers through `worker-finished` while the run is stopped, using `failed` or `stopped` unless successful completion is independently established. Resume requires that reconciliation to finish. A crash between these writes leaves the new owner, the saved evidence and the unresolved worker records visible; retry the unfinished bookkeeping without re-adopting. Unknown workers cause no ownership change.

## State, resources and recovery

Keep the same run identifier, project, objective, authority, task graph, agreements, stages, checks, assessments, findings, dispositions, workers, follow-ups, publication authority, limits, dispatch count, handover, report and closing evidence. Ownership transfer itself does not stale engineering evidence. Existing content and commitment freshness checks still apply before subsequent use. Preserve the original creation and resource provenance; record each adoption with previous and new controller, user authority, the eligibility evidence and its observation time, and the committed revision. History retains every transfer; the focused status shows the current controller and latest adoption only.

Separate current `executionResources` from immutable run `resources` and assessment provenance. The new field mirrors the existing resource object's `schema`, canonical `store`, opaque `registration`, actual native `session` and exact manifest `identity` grammar; it is run-level, has no textual separators or wrap-joining, and null is its development-mode empty form. Empty strings, partial objects and a null bound execution binding are invalid. A missing historical field means the original `resources` binding, not the newest installation. Creation initializes both equally; adoption replaces only execution registration/session after exact identity/store checks; claims and ordinary operations leave the binding unchanged. Inspection failure leaves it unchanged and blocks dependent execution. Worker assignments and receipts retain their original resource bytes, and new dispatches record their current execution resources and controller. There is no arbitrary-session admission exception.

Bound-to-bound adoption requires the same retained store and a release that implements this contract. A fresh unbound session may select the run's exact available release; a differently bound session cannot silently switch. Missing, corrupt or retired resources, another store, an older retained release lacking adoption, and mixed development/bound or unclassified legacy state receive a specific diagnosis without mutation. No generic release migration is introduced. Explicit development runs with understood state can use the new development runtime: historical stopped runs need no controller claim, while historical running runs without one cannot use the abandoned-running path. These compatibility limits must remain visible in delivery reports.

Persist ownership and its history atomically in the project database. Protect the target session and bundle reference in the retained registry before committing ownership; after commit, reconcile the target's run reference before dependent work. The expected crash states are: original ownership with only an extra protected target reference, where a retry revalidates eligibility; new ownership with attachment reconciliation pending, where neither controller executes dependent work until reconciliation finishes; and new ownership with reconciled attachment, where the new owner may proceed. Preserve the source binding and historical references rather than deleting them during adoption. Retrying after a lost response recognizes the committed transfer by its run, former controller, new controller and original observed revision, returns its result without a second transfer, and still verifies current admission and ownership. A later intervening transfer or revision change requires fresh reconciliation. Failed reconciliation retains resources and blocks dependent writes; it never rolls ownership back silently. Recovery and collection must recognize each partial state even when the initiating process no longer exists.

After committed ownership and the target reference are reconciled, the source's run reference becomes historical. It preserves provenance but no longer gives source ownership or requires stopping the adopted run to retire the source session. A source session that remains bound still retains its bundle under ordinary policy; retiring it removes only that session's retention claim. The target's live run reference retains the exact payload and historical evidence dependencies until its own ordinary retirement requirements are met. If a crash occurs before source reclassification, conservatively retain the source reference and retry reconciliation from the committed adoption record. Never reinterpret a reference as historical from a caller's assertion alone. Missing run state or an incomplete target reference blocks retirement and collection. Development runs have no retained-registry attachment or reclassification steps; their ownership/history commit is their durable transfer boundary.

Ownership transfer and resuming execution are separate durable steps. `adopt` always leaves the run stopped and attended, clears the current claim, continuation verification and Stop reminders, and preserves prior observations in history. Keep an existing stop reason; an abandoned-running source receives an adoption-reconciliation stop reason. The new owner reconciles terminated worker records, then `resume` under explicit authority to continue establishes its claim and returns to running, attended operation. Unavailable claim evidence leaves execution stopped with a diagnostic. Adoption authority that authorizes ownership alone never resumes work. Existing limits remain effective throughout.

## Independent evidence after adoption

Already imported assessments keep their historical attribution and can remain usable while their inputs and commitments are current. Adoption does not rewrite them as if the new controller had dispatched or accepted them. Preserve the controller at each dispatch and the controller history as the authority for independence checks. Exclude every session that controlled the run from new reviewer and skeptic assignments; comparing only with the current controller would let a former author review their own work.

Completed but unimported receipts remain bound to their original assignment, resources and inputs. A receipt authored by the adopting controller cannot be newly imported or used as that controller's skeptical validation; request a fresh independent assessment. Other historical receipts may be imported when original and current independence requirements, unchanged inputs and ordinary attribution checks pass. An earlier imported assessment authored by the adopting session remains historical evidence; subsequent changes still require fresh cumulative assessment by another eligible session. Missing historical attribution is not silently guessed. The implementation must preserve verifiable historical attribution or diagnose the specific unavailable import, without discarding the saved receipt.

## Renewed continuation

At renewed handover, adoption, resume, compaction recovery and before an unattended yield, reconcile the saved queue, actual files, workers and the host's current continuation state. Reuse compatible agreement; user intervention that restores a goal does not establish that the plugin restored it. A reviewer running elsewhere does not carry controller continuation.

Classify the native goal as active, inactive, or unknown from an actual host observation, keeping absent, blocked, paused and complete states distinct in the evidence. Use a supported native resume operation only when one exists and the user's direction authorizes it; read back the result. Never replace an unfinished goal just to escape its state or claim success from a requested transition. Current Codex tools expose no goal-resume operation; the controller must name the user action required to resume it and verify the resulting active state when observed. Host capability changes require verification, not a permanently hardcoded claim that resume can never be supported.

Continuation evidence is scoped to the current controller, run, mechanism and observation. It is initialized as unverified, refreshed at the reconciliation boundaries above, and invalidated by ownership change, observed inactivity, missing or failed inspection, deliberate disablement, or loss of trust/activation. No time-to-live substitutes for checking those boundaries. Store only the latest focused observation in current state and retain prior observations in history; absent or old unscoped evidence is unverified after a reconciliation boundary until refreshed. Ordinary source edits alone do not erase an unrelated host observation.

Add owner-only `invalidate-continuation` with nonempty observation/reason text. It is admitted bookkeeping, including on a stopped run or one saved as unattended with stale verification. In one write it records the latest unverified observation, sets mode to attended, and preserves run status, handover, limits, agreements, evidence and closing obligations. Retry after response loss reads status and repeats only if a newer observation needs recording. It grants neither execution nor a native goal. `continuation` and `handover` still reject a supplied unverified mechanism without writing; callers use the explicit invalidation operation for a negative observation. A verified `continuation` records the observation but does not itself grant handover authority or change attended mode. An ordinary successful `handover` with a currently verified mechanism can restore unattended mode.

The durable execution states are: stopped/attended after adoption; running/attended after invalidating a running run; stopped/attended after invalidating an already stopped run; and running/unattended with current verification after successful handover. Invalidation never stops a running run. Stopped/unattended states already saved by an ordinary stop retain their stop and must be reconciled before resume; resume with unavailable continuation records attended mode. Historical running/unattended/unverified state admits invalidation as its recovery operation. These modes are orthogonal to absent or recorded handover: invalidation never removes a handover or adds one. The existing three handover categories therefore remain, with an explicit unattended-to-attended transition and a separate observation explaining it. Completed runs do not resume or adopt.

An active verified goal may carry unattended work, with Stop protection reported separately. A verified alternate mechanism may carry it only if it independently satisfies the existing continuation contract. With usable runtime admission but unavailable continuation, invalidate the observation and continue useful authorized work attended. Preserve handover and report obligations. Without the user's needed answer, keep that decision pending and continue independent authorized work; stop or close as incomplete under the ordinary lifecycle rules when none remains.

Refused runtime admission is a different branch. Disabled installation/hooks, missing trust or activation, or failed admission inspection can prevent invalidation itself. Then no downgrade is claimed or persisted: the saved run, handover and report duties remain unchanged, and saved verification is explicitly unusable as evidence of current continuation. Name the actual recovery, such as user restoration of deliberately disabled integration, approval of native trust, or genuine activation in a reopened session. Use only the already-permitted diagnostics/maintenance and work independent of that unavailable admission. Do not run the bound workflow through development mode or silently restore trust. After admission returns, reconcile fresh evidence and persist the appropriate mode before dependent work resumes.

For a running handed-over run, a functioning Stop hook continues the existing resistance to premature yield after downgrade to attended mode. Select protection from recorded handover or verified unattended mode, preserving the three-reminder bound, user-decision pause, closing duties, explicit user stop and limit precedence. Active workers still require collection. A merely attended run without handover retains conversational yielding. An unavailable hook supplies no protection; use the admitted or admission-refused branch above as appropriate. This neither resumes a native goal nor overrides a user pause. The working-hook downgrade and unavailable-hook branches each need their own observation on both installed hosts and remain `(live-claim: provisional)`.

Claim-only writes and repeated invalidation observations that change no execution state do not reset the no-progress reminder count. Preserve revision increments for concurrency while carrying the reminder count across those observational writes. The reference's existing intervening-transition rule must name this exception, and verification must exercise claims between successive reminders.

Recover failed reviewers within the accepted model choices and resource limits, reconcile their termination, await surviving workers inside the active turn, and keep the queue moving. A user-requested stop or pause and exhausted limits still win. No reminder reset, adoption or renewed handover may bypass them.

## Native feasibility evidence

On 2026-09-21, a no-inference probe launched real `claude.exe` and `codex.exe` processes, observed each PID with its native creation-time identity through the existing Windows process helper, and verified `ownerAlive` changing from true to false after deliberate contained termination. Both jobs reported descendants reclaimed; no model input was sent. This establishes the native process primitive used by the closed-process predicate, not adoption or the new claim protocol. Raw evidence is [the process probe result](../../.tmp/adoption-native-process-feasibility.json); the driver is `.tmp/adoption-process-feasibility.cjs`.

A separate no-inference `claude agents --json --cwd` query observed a real ongoing assessment by exact session ID, PID and `busy` status. Codex's generated protocol exposes `ThreadStatus` and loaded-thread listing, but a different app-server reader reported a separately streaming assessment `notLoaded`. These observations do not establish a safe global idle-session predicate, so neither is used to waive the first delivery's closed-process rule for running sources. Their evidence is retained under `.tmp/adoption-claude-session-feasibility.json` and `.tmp/adoption-codex-schema`; these are qualified investigation results, not installed adoption acceptance.
