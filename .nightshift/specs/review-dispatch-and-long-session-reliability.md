# Review dispatch and long-session reliability

## Outcome

One release repairs three tracked defects, tracked in [BUGS.md](../BUGS.md) and [QUICK_WINS.md](../QUICK_WINS.md) until they are fixed. A reviewer whose own tools fail no longer ends its dispatch with an unusable incomplete report ("A reviewer the host leaves unable to run commands ends its dispatch"). A failed attempt names the failure its host reported ("Name the host's own failure in review attempt errors"). A controller session whose native history has outgrown the observer's read bound can still discharge its handover acknowledgement ("An oversized native session history blocks a handover it already accepted"). The shipped changes are runtime code and runtime reference guidance, with their tests alongside. They ship as 3.3.13, with both plugin manifests bumped, the release manifest regenerated and a CHANGELOG entry. The three entries move to BUGS_HISTORY.md and QUICK_WINS_HISTORY.md, any dependency references they satisfy are removed from the active indexes, and `node skills/ready/ready.js --development . --check` is run again.

## Reported tool failure

Every assessment report, of every kind and including dialogue turns, gains a required string field `toolFailure` in the producer schema, so both hosts' structured output must supply it. The prompt defines it as empty when the reviewer's tools worked or it worked around a failure, and otherwise as the tool and the error it returned, when a failure of the reviewer's own tools kept it from reading or inspecting what its assessment needed. A deciding check that the read-only tools cannot run by design stays a probe request, not a tool failure.

A report with a nonempty `toolFailure` is not a usable assessment, whatever its `status`. Its attempt fails with the new code `reviewer-tools-unavailable`, whose message carries the reported failure, bounded, and the dispatch tries its next candidate as for any other failed attempt. The failed attempt keeps its native events and `result.json`, report included, and writes no receipt, so its findings and probes cannot be imported. When the last candidate fails this way, the dispatch fails with `reviewer-tools-unavailable` and records `failure.json` as today. A resumed dispatch that fails this way fails with `resume-failed`, whose message carries the reported failure, since a further resume of that session would meet the same tools; its recovery is `review.replaces`, as for any `resume-failed`. A report with an empty `toolFailure` behaves exactly as today. A report whose `toolFailure` is missing or not a string is refused with `invalid-result`. Receipt import refuses with `changed-result` a receipt whose native report names a tool failure; receipts from earlier releases, whose reports lack the field, import as before. The runtime does not infer tool failures from host events: an unreported failure leaves a report exactly as usable as it is today.

## Closure routing after a failed resume

A failed dispatch's `failure.json`, which the dispatcher writes before it throws, records the dispatch's final error `code` and, for a resumed dispatch, `sessionFailed`: whether its attempt failed in its session, which stays true when `termination-unverified` outranks `resume-failed`. Because the file is written by the dispatch itself, a lost worker update or a later worker reconciliation cannot erase it. If writing `failure.json` itself fails, the dispatch still fails with its own error, whose message adds the write failure. In status, each `resumeTargets` entry gains `continue`, which is `replace` when any dispatch of that lineage on the task, registered after the dispatch the entry names, resumed that dispatch's session and either has a `failure.json` with `sessionFailed` true, or is no longer active, recorded a host process id and left neither a receipt nor a `failure.json`, since its session's outcome is then unknown. Otherwise it is `resume`. The routing therefore stays `replace` through later failed replacements and retries, and returns to `resume` only when a later dispatch of the lineage produces a receipt, which then becomes the dispatch the entry names. A resumed dispatch that ended before launching its host counts toward neither, and a `failure.json` without `sessionFailed`, as earlier releases write it, does not count. `review.resume` is not refused on that basis, so a controller may still retry a resume whose failure it judges transient.

## Host-reported failure

Each attempt that ends without a usable report records `hostFailure`: the terminal error its host reported, bounded to 2,000 characters, or null when the host reported none. On Codex it is, in order of preference, the `error.message`, with `error.additionalDetails` when present, of a `turn/completed` notification whose turn status is `failed`; that of the last `error` notification for the attempt's thread; or the `message`, with `data` when present, of a JSON-RPC error response to one of the attempt's own requests (`initialize`, `thread/start`, `thread/resume`, `turn/start`), as the installed codex-cli 0.163.0 app-server protocol schema defines them. Such a rejected request's own error message then names the request instead of serializing the response, so the host's text appears once. On Claude it is the `result` text of the final `result` event when that event has `is_error: true`, followed by its `api_error_status` and `terminal_reason` when present, as Claude Code 2.1.302 emitted them for a refused model on 2026-10-18; when the attempt produced no `result` event at all, it is the end of the attempt's stderr, bounded the same way, or null when stderr is empty. Whenever an attempt has a `hostFailure`, its `error` message ends with `; the host reported: ` and that text, so `unusable-review`, `resume-failed` and every other failure of that attempt name it. Failure codes do not change. The attempt records in `failure.json` and in a later receipt's `attempts` carry `hostFailure`, so a controller can tell an authentication failure from a model or attribution failure without reading raw events, and the attempts' hosts show when a fallback left the reviewer's original host.

## Acknowledgement in a long-lived session

The native acknowledgement observer reads at most the last 64 MiB of each candidate history file, instead of refusing a file larger than that. A file within the bound is read whole, as today. For a larger file it reads the final 64 MiB at the size it observed, discards the bytes up to and including the window's first newline, which cannot split a UTF-8 sequence, and parses the remaining lines under the existing rules. A Codex rollout's attribution comes from its first line, `session_meta`, so for a larger Codex file the observer also reads that first line within a 1 MiB bound, refusing with `acknowledgement-source-unavailable` when no newline ends it there. For a larger file the encoding preconditions apply to the bytes actually read: the file's first three bytes are read for the BOM check, the window after its first newline and any first line read must be valid UTF-8 under the fatal decoder, and bytes outside them are not checked. The fallback identity of a Codex message without its own id becomes its line's byte offset in the file, `offset:<n>`, for every read, so it stays stable as the file grows and the window moves. Every other precondition stays: an ordinary, singly linked file inside the admitted profile, the entry and candidate-file bounds, the 65,536-character message bound, and an unfinished final line remaining unusable. An acknowledgement older than the window is not found, so inspection reports `missing` and the controller repeats the message, which the existing recovery already provides. Captured evidence persists as today. Handover acceptance gains no history size check.

## Evidence

Deterministic tests cover these cases:

- A tool-failure report from a fresh candidate is followed by the next candidate.
- A tool failure on the last candidate fails the dispatch with `reviewer-tools-unavailable`.
- A tool failure on a resumed dispatch fails with `resume-failed`.
- A missing or non-string `toolFailure` is refused.
- Import refuses a receipt whose native report names a tool failure.
- `resumeTargets` says `replace` after a resume of the named dispatch failed in its session, still says `replace` after a later failed replacement and after a session failure masked by `termination-unverified`, says `replace` for an ended resumed dispatch that recorded a process id and left neither a receipt nor a `failure.json`, says `resume` for one that ended before launching its host and for an earlier release's `failure.json` without `sessionFailed`, and returns to `resume` once a later dispatch produces a receipt.
- A failed `failure.json` write leaves the dispatch's own error code, with the write failure added to its message.
- Codex host failures from a failed turn, an `error` notification and a JSON-RPC error response, and Claude host failures from an error `result` and from stderr without a `result`, appear as `hostFailure` and once in the attempt error.
- The observer finds an acknowledgement in the tail of an oversized Claude history and of an oversized Codex rollout, using that rollout's first-line attribution.
- The observer reports `missing` when the acknowledgement lies before the window.
- An oversized Codex rollout whose first line exceeds 1 MiB is refused.
- An invalid byte before the window of an oversized file does not refuse, while a BOM at its start still does.
- A Codex message without its own id keeps the same `offset:<n>` identity in a whole-file read and in a tail read of the same file after it grows.

A read-only installed check runs the observer over this repository's 2026-10-17 Claude session history, over 200 MB, and shows that it returns a result instead of `acknowledgement-source-unavailable`. Installed-host evidence for the schema is one small live dispatch per host through the development runtime against a disposable fixture, Codex `gpt-6-sol` and Claude `claude-opus-5-5`. Each shows that its host accepts the extended schema and returns an empty `toolFailure` with working tools, within the aggregate token budget the user sets at handover. The tool-failure branch has no live claim, since no tool failure can currently be induced on either installed host; it rests on the deterministic fixtures (live-claim: unverified).
