# Independent documentation review

Governing spec for [Independent documentation review](../features/independent-documentation-review.md), run `f440497c-a0cc-4375-bada-e834e32b49a6`. It carries the record's agreed Widened scope and Tracking direction, and the readback the user answered "yes" on 2026-09-29: backlog-only edits during a task's documentation stage are covered by a clean docs review, a live campaign on Claude Code with Opus under a 64M-token ceiling, and a preference for Codex Astra reviews. The user accepted this spec on 2026-09-29 with "spec accepted", after its fifth independent assessment found no remaining gaps. On 2026-09-30 the user decided two fail-open defects found during implementation: tracking edits outside Git fail closed, and a closing baseline whose changes lack review survives re-recorded triage; the Lifetime and Backlog only rules below carry both decisions.

## Outcome

Documentation and backlog changes get a strong independent review with a documentation lens, the way code gets one with the code lens. Backlog edits that apply triage decisions after the last review no longer force a completion workaround or reach publication unreviewed.

## The docs review kind

`dispatch` accepts `kind: docs`. The lead is a fresh strong reviewer under the same model, independence, attribution, private-copy, probe and fallback rules as a code lead, and receives the same complete cumulative change from the run base, the whole project snapshot, the requirements and the rules. Its five dimensions replace the six code dimensions:

- `claim-accuracy`: each changed or affected claim matches the code, records and evidence it describes, at the version it names.
- `sweep-completeness`: documentation, changed or not, that the cumulative change left stale, contradictory or missing, including navigable references and history moves.
- `backlog-conventions`: the project's documented backlog grammar, dependency, history and retirement conventions; parser validity itself is evidenced by the controller's recorded ready parser check.
- `sibling-consistency`: agreement with sibling entries, index excerpts and their records, and history files.
- `proportionality`: depth proportionate to importance, useful reasoning and evidence preserved, nothing overstated or stated as current before it exists.

The code in the change is context: the reviewer judges what documentation says about it, not whether the code is correct. The brief also asks the reviewer to report any changed file it judges to be operating instructions, so the controller routes it to code assessment. A complete report covers all five dimensions with evidence. Findings take the same fresh skeptic validation, disposition, repair and cumulative reassessment as code findings, through the same operations.

Which files are documentation follows the user's review convention: descriptive prose such as the README, specs, reports and backlog records is documentation; files an agent loads as operating instructions (skills, the operating brief, the REFERENCE files, instruction files such as AGENTS.md) are code and need code assessment even when revise-docs edits them. [Separate run-time guidance from reference material](../features/runtime-guidance-separation.md) may later move parts of the REFERENCE files; until then they stay code. The runtime classifies paths only for the backlog relief below.

## Where it is required

Every code task and every docs task needs a current docs review to complete, checked when it advances from documentation, when a reopened completed task returns from review straight to completion, and again at run completion. Current means the same conditions the code gate applies to code assessments: owned by the task or covering it through `coveredTaskIds` as cumulative code assessments do, complete, strong, independent, attributed, covering all five dimensions, fresh against current inputs, bound to the task's current commitments, with every finding it raised validated and disposed and no repair of a docs finding after it. Spec and lore tasks have no docs gate; a lore task's assessment still gains the backlog relief below through the closing docs review. The code gate is unchanged apart from that relief and the kind rule below; a docs task still needs it only when it imported a code assessment. Docs tasks lose the direct completion path the runtime reference describes today; lore tasks keep theirs.

A purely mechanical change (a version string, a regenerated file, nothing decided by judgment) is exempt. The controller records the exemption and its reason when advancing the task from documentation, and the runtime binds it to the project inventory at that moment, as a review snapshot is bound. It stands in for the docs review only while that content is fresh. Once anything in the inventory changes, it no longer counts and the task needs a current docs review; for a task already complete, that is the closing docs review. Reopening, repair or an advanced requirements revision clears it outright. A task without a current exemption needs the docs review. Status shows the exemption and whether it is current, and the closing report names it.

## Backlog relief

Backlog paths are `.nightshift/FEATURES.md`, `.nightshift/BUGS.md`, `.nightshift/QUICK_WINS.md`, `.nightshift/PATTERNS.md`, `.nightshift/FEATURES_HISTORY.md`, `.nightshift/BUGS_HISTORY.md`, `.nightshift/QUICK_WINS_HISTORY.md`, and files under `.nightshift/features/`, `.nightshift/bugs/` and `.nightshift/patterns/`.

A task's code assessment, which snapshots the whole project inventory, that is stale only because backlog paths changed, appeared or disappeared since its snapshot counts as current when a current docs review covers that task: for a code or docs task, its own or a covering docs review, or the closing docs review; for a lore task, only the closing docs review, since task-level docs reviews do not cover lore. This holds wherever the gate is evaluated: advancing a task, task completion and run completion. Spec assessments are excluded, because a change to a governing artifact always needs whole-spec reassessment. Any other difference, including other documentation, keeps today's rule that a stale assessment needs reassessment. Checks are unchanged: every latest named check must still pass on current inputs, so a check whose inputs the backlog edits touched, such as the ready parser check, is rerun.

Each gate counts only the findings and repairs of its own kind. A repair of a docs finding is followed by a docs reassessment, and it bears on the code gate only through the files it changed, where the backlog relief applies. A repair of a code finding still needs a cumulative code reassessment, and because it changes the inventory, the task needs a current docs review again as well.

## Closing docs review

Tracking edits applied after follow-up triage are reviewed by a closing docs review: a run-level record rather than a task's review. It is dispatched, imported, validated, disposed, repaired and checked through the existing operations with a closing target in place of a task; the runtime reference gives the request shape.

- **Admission.** On a running run once triage evidence is recorded, and on a complete run as owner bookkeeping that needs no engineering claim, like the report operations. Refused before triage evidence exists and on a stopped run, which the user resumes first as for any other work.
- **Limits.** Closing operations obey the run's recorded limits, including its deadline and dispatch allowance, on a complete run as on a running one. When an exhausted limit prevents the closing review or one of its checks, nothing is overridden or renewed: the record stays absent or unresolved, the controller reports the tracking edits as not covered by it, a running run's completion stays refused as for any missing assessment, and on a completed run publication then needs other independent review of those edits.
- **Scope.** It covers every code, docs and lore task. Recording it, its findings, their repairs and its checks never reopens a task and never clears closing evidence.
- **Lifetime.** Anything that clears closing evidence clears the record, including a new retrospective, new engineering and re-recorded triage, which starts a new record. The baseline outlives its record: a later triage keeps the run's earlier baseline while the changes since it lack independent review, so recording triage again never absorbs unreviewed tracking edits. Those changes are reviewed once a current resolved closing review covers them, or once a complete cumulative code or docs assessment of a task is fresh against the whole inventory; then, or when no earlier baseline was captured, triage records a new one.
- **Completion.** On a running run, a current clean closing docs review satisfies each code and docs task's docs gate and supplies the backlog relief for every covered task's code assessment. An unresolved finding or failing check of a closing review blocks `complete`. If a repair or tracking edit touches a path outside the backlog, the relief does not apply and completion refuses as it does today; recovery is ordinary cumulative reassessment, which reopens the task and clears closing evidence.
- **Backlog only.** Recording triage evidence also records the closing baseline: the project inventory at that moment, unless the Lifetime rule keeps an earlier baseline. In a project positively outside Git, where there is no inventory and no review can be dispatched, the baseline is the backlog files on disk and any backlog change after triage refuses completion; inside Git, a failure that leaves no baseline fails closed. A closing docs review is imported only when every difference between the current inventory and that baseline lies in backlog paths, leaving out user-owned unrelated files named in the dispatch's `excludedPaths` as review does; otherwise the import is refused. The baseline does not depend on task assessments, so a task that completed under an exemption or without any assessment needs no separate comparison, and each task's own gates still apply at completion as stated above.
- **Complete runs.** On a completed handed-over run, the record gates nothing in the runtime; it is the independent review that covers the tracking edits at publication. Its repairs stay within backlog paths. A finding whose repair needs any other change is not repaired under the record: it is deferred with a durable route, such as a follow-up or backlog entry for new work the user directs, so the record can still close over the backlog edits. A finding whose obligation is required cannot be deferred, so it leaves the record unresolved, and an unresolved record does not count as review coverage for publication.

## Guidance

- revise-docs obtains the docs review of its complete change, or records the mechanical exemption, and runs the same skeptic, disposition and cumulative repair loop as revise-code; edits to operating instructions also get code assessment.
- The operating brief's Close and report section, the runtime reference and the status brief's rules give the closing order: documentation edits and their docs review, then any code reassessment, the retrospective, the report for a handed-over run, triage, tracking edits, rerun checks, the closing docs review and `complete`. For a handed-over run that completed before triage, tracking edits are followed by closing checks and the closing docs review as bookkeeping.
- Other skills and the README are swept for statements the change contradicts.

## Boundaries

Out of scope: path classification beyond the backlog relief, relief for other documentation, [Run-free revise](../features/run-free-revise.md), the quick win that lands documentation edits before the first cumulative assessment, and Codex live verification. Runs keep their bound release; the new gates apply to runs created on 3.2.16.
