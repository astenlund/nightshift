# Close settled records

## Outcome

Give the user a supported, final way to close a delivery run or standalone review context whose work they consider settled, without running its remaining lifecycle. A closed record ends in a new terminal status, `closed`, distinct from `complete`: it records that the user dropped the record's remaining obligations, in their own words, not that those obligations were discharged. Every current consumer treats a closed record as finished and final, like a retired one, and no operation of the current release can change it afterwards; Write guard names the narrow older-release paths this does not cover. This governs the feature [Close settled records](../FEATURES.md#close-settled-records), which graduated from the Exploring draft "Close a stopped record the user considers settled", widened by the decisions below to running records whose owner has ended.

The motivating case: this repository's review store holds two review contexts, `2b758039-e78b-44b2-9674-ae58ea91db0c` and `cd347a08-b11f-49d4-af26-3c19b7630534`, saved as `running`, bound to release 3.3.12, owned by a Claude session whose process has ended and whose workers have all finished. Release 3.3.12 can no longer open this project, since the delivery store was compacted to store version 3 on 2026-11-01, so neither record can be stopped, resumed or adopted through its own release, and both block compaction of the review store. Close must reach them.

## Decisions

Settled by the user on 2026-11-01, outside any run:

- **Distinct terminal status.** The result is `closed`, stored in the record's `status` field, not `complete` with a marker. The user chose the stored status over a retirement-style closure table after weighing that older releases accept only `running`, `stopped` and `complete`; the older-release guard below is the agreed mitigation.
- **Scope.** A `stopped` record may be closed, and so may a `running` record whose owner is proven inactive by the same evidence adoption uses. Active or uncertain workers refuse.
- **Administrative entry.** Close is an action of the current release's `migration` entry, like `retire` and `compact-history`, so the current release can close a record bound to any older release, without using, requiring or changing that record's release binding.
- **Shown manifest and the user's reply.** Like `retire`, close first presents a manifest of everything closing drops, and the user's exact reply is bound to that manifest's hash.
- **Older-release guard.** Close refuses while anything else in the project could still be read by a release that does not know `closed`, as Older-release guard defines; the records being closed are exempt. Amended by the user on 2026-11-02, after the final review showed the strict form could block every close (more than 20 such records, one that close cannot take and its own release cannot finish, or any unfinished development-mode record): a guard-named unfinished record does not refuse close when the user's reply explicitly acknowledges it by name, and that acknowledgement is bound into the approval.

## Status model

`closed` joins `running`, `stopped` and `complete` as a fourth record status in both stores, the delivery store `.nightshift/runs/state.sqlite` and the review store `.nightshift/runs/review-state.sqlite`. It is terminal in the current release: no transition of the current release leaves it, and no operation other than read-only diagnostics accepts a closed record, as Write guard specifies, including the older-release paths it does not cover.

A closed record carries `closure`, beside `stop` and `hold` on the state:

```text
closure: {authority, reason, manifestHash, approval, reconciledWorkers, previousStatus, previousRevision, recordedAt, actor}
```

- `authority`: the user's exact final reply after the manifest was presented, nonempty, at most 4 KiB, the same limit and refusal (`migration-authority-required`) as `retire`.
- `reason`: the user's reason for closing in their own words, nonempty and at most 1 KiB, refused with `close-reason-required` when empty or longer; when the user gives no separate reason, the controller asks for one rather than deriving it from the authority. It is shown by `status` and `inspect` on the closed record, and by the `close` result, which the Ready skill relays after the user approves; Ready's run-state section does not list closed records.
- `manifestHash`: the approved manifest's hash, as Manifest defines.
- `approval`: the content identity of the approved manifest, saved by the close as an artifact in the record's own store (the `artifacts` table both stores already have), whose body is exactly the object Manifest hashes, holding every member's projection, every choice and the guard warnings the user saw, so the report and follow-up decisions survive beside the record rather than only inside a hash. The artifact identity and `manifestHash` are computed independently and are not required to be equal; a reader verifies an approval by fingerprinting its body and comparing that with `manifestHash`.
- `reconciledWorkers`: one `{id, previousStatus, evidence}` for each worker whose saved status still read active (`workerIsActive` in `workers.js`) but whose termination `adoptionEligibility` proved, where `evidence` is `{kind}`, the kind of termination evidence that verdict proved for the worker, kept compact so the entries the user cannot shorten add as little as possible to the closure's size bound; an empty array when there were none.
- `previousStatus`: `running` or `stopped`, the status the record held when closed.
- `previousRevision`: the record's revision immediately before the close write.
- `recordedAt`: the UTC ISO timestamp of the write.
- `actor`: the admitted `{host, session}` that recorded the close, forced from the admitted context as migration actions already do.

Field ownership follows every existing store writer (`update`, `adopt`, `remind`, acceptance replay): the close writer sets `status: "closed"`, adds `closure`, sets each worker listed in `closure.reconciledWorkers` to status `stopped`, so no reader can see a closed record as busy, sets `revision` to one past the committed revision and sets `updatedAt` to `closure.recordedAt`, then calls `RunStore.save`, which checks that the revision immediately follows its committed predecessor (refusing with `stale-state` otherwise), records `updatedAt` as the history row's time, and, for a delivery, derives `progress` and `stopRecovery`, so the progress marker is current at the close revision. Every other field deep-equals its value at `previousRevision`: `stop`, `hold`, workers apart from the reconciled statuses, tasks, findings, evidence, follow-ups and the closing record stay readable as history of what was dropped. It does not set `stop`; a closed record's stop is whatever it was.

## Eligibility

A record is eligible when all of these hold. The project-operation condition is checked at admission, as its bullet says; the others are evaluated as Writing orders them: process liveness of owners and workers is inspected before any store transaction, and inside each store's closing transaction the record conditions are re-evaluated from re-read rows, with `adoptionEligibility` given an `ownerAlive` that answers only from those earlier inspection results and treats an identity it did not inspect as uncertain:

- It exists in the store its member names, and its status is `running` or `stopped`. A member whose id is absent from its named store, including an id that exists only in the other store and a named store whose file is absent with no SQLite sidecars and no compaction backup or build file, is ineligible with `migration-run-unavailable`; a member whose named store is present but unreadable, or absent beside such leftovers, is ineligible with `migration-store-unavailable`, beside the guard refusal naming that store, reported per member by `close-manifest` with its store and id only, and refused by `close` like any other ineligible member. A `complete` record refuses with `close-not-needed`; a closed one whose `closure.manifestHash` equals the request's is handled by Writing's already-closed rule and otherwise refuses with `run-closed`; a delivery record retired by legacy migration refuses with `retired-run`.
- `adoptionEligibility(state, {}, dependencies)` from `internal/runtime/ownership.js` returns `eligible: true`. For a running record this proves its saved owner process (`controllerClaim` for a delivery, `ownerObservation` for a review context) has ended; for every record it proves each worker terminal or terminated. Its refusal codes (`controller-activity-unknown`, `controller-not-inactive`, `worker-activity-unknown`) are returned unchanged, so an unknown or live owner or worker refuses close as it refuses adoption. Close accepts no `workerEvidence` export in this release; a record whose workers need one stays unclosable until that is added, and the refusal says so. A worker whose termination the verdict proves while its saved status still reads active is reconciled by the close write, as Status model states, since close has no adopter to reconcile it afterwards.
- For a delivery, its accounting can be current at the close revision. A delivery store that lacks the schema-2 accounting tables (`accounting_commits`, `discharge_index`) refuses every delivery member with `close-accounting-unavailable`, since saving into it would create those tables and change how the creation gate judges the store's other legacy records; a stopped or complete legacy delivery there is retired instead, and a running one has no close or retire route in this release (retire refuses running records) and must first be stopped through its own release where that release can still open the project, or acknowledged as Older-release guard describes. In a store with those tables, `close-manifest` reads the member's current account through the progress store and reports `close-accounting-unavailable` when it is not current, and `close` checks the marker `RunStore.save` derived for the close revision and refuses with the same code, rolling the transaction back, when it is not `current`, so close never commits a closed delivery the creation gate could not count as discharged.
- No release-registry project operation is active in the project, or of uncertain termination. The migration entry's existing service admission already enforces this for every action that is not read-only, refusing with `resource-operation-busy` in the release registry's transaction before the runtime runs, so registering `close` as a non-read-only migration action is the whole mechanism. `close-manifest` is read-only, so that admission skips the check for it; the manifest does not report this condition, which is transient and is enforced when `close` itself is admitted. Separately, `close` refuses with `runtime-ownership-busy` while another writer holds the project write-ownership mutex that Writing has it acquire.
- For a delivery, the current selection may be closed or not; closing the current selection does not clear the `active` pointer, and the creation gate treats the closed selection as replaceable, as Creation gate specifies.

Eligibility does not depend on which release the record is bound to: `resources` and `executionResources` are not compared with the current release, and are left unchanged.

## Older-release guard

Before writing, close refuses with `close-older-release-present` while either of these exists, naming each one found, except a record the user has acknowledged as the first branch describes:

- **An unfinished record bound to an older release.** Any other record in either store whose status is `running` or `stopped` and whose release identity names a version below `CLOSE_SUPPORT_VERSION`. A record's release identity is resolved by the same rule as `executionResources()` in `internal/releases/entry.js`: its `executionResources` when that key is present, even when null, otherwise its `resources`, and then that value's `identity`. A record whose resolved identity is null, as for development-mode and legacy records, or names no parseable version, counts as older and is named with its resource mode. Records in the requested close set are exempt; `complete`, `closed` and retired records are not checked. Each record this branch names is listed in the manifest's guard findings with its store, id, status, resource mode, release identity and why it is at risk (an older session could resume or write to it and would then fail project-wide), together with its own close eligibility, so the user can choose among the remedies: include it in the close set when it is close-eligible (for a delivery, with current accounting), finish it through its own release where that release can still open the project, retire it when it is a stopped or complete legacy delivery, or acknowledge it. Acknowledgement is the route for every record no other remedy reaches, including more records than one manifest can hold, a record close cannot take whose release cannot finish it, and development-mode records: both actions take a top-level request field `acknowledgedRecords`, beside `members` and `choices`, holding the records this branch names that the user's reply acknowledges by name, where a reply names a record by its full id or by a prefix of it that matches exactly one record among the named records the controller presented (the controller may show a shortened id), the controller resolving it to the full `{store, id}` before putting it in `acknowledgedRecords`, which accepts full ids only, and a collective reference names nothing; a reply holds at most 4 KiB, so acknowledging more records than one reply can name needs several manifests that close records first, and a named record in that list no longer refuses close. Its entries pass the same entry check Manifest defines for `members`; an absent field means an empty list; an entry failing the check, or a duplicate, refuses with `migration-decision-unavailable`. The list is hashed as its own key, sorted by store then id, so the order a request gives does not matter and the approval binds it, and a record this branch names that is missing from it still refuses with `close-older-release-present`; an entry naming a record the branch does not name refuses the manifest with `migration-decision-unavailable`. The controller presents each named record and its risk before asking, and never acknowledges one the user's reply does not name. Both actions read both stores for this branch with one rule: a store whose file is absent and that has no SQLite sidecars holds no records, as the existing store openers treat it, so a project with only review contexts and no delivery store passes; a store that is present but unreadable (surviving sidecars with or without its file, an absent file beside a compaction backup or build file, which `history-compaction.js` names and whose remedy is to run `compact-history` to finish the swap or restore the backup as its message directs, an opener refusal, an unsupported store version, or a row that fails its state check) is a guard refusal naming that store.
- **A live session bound to an older release in this project.** Any release-registry session binding in state `bound` whose `projects` include this project's root and whose identity names a version below `CLOSE_SUPPORT_VERSION`, classified in this order into refusing, warned and passing bindings: a refusing binding refuses close when its `activation` record names an owner that `ownerAlive` reports alive (`true`) or whose liveness inspection fails (`null`), the owner being the host process SessionStart found among its ancestors rather than the conversation, so a conversation ended inside a host process that still runs counts as live, and the refusal names that owner process with its remedies: exit that host process, or retire the old session binding, whatever any failure record says, and the admitted session counts as live here in both `close-manifest` and `close`; otherwise a warned binding is listed as a warning when it has no activation record, or when `ownerAlive` positively reports its activation's owner ended (`false`) and an `activation-failure` record for that session key, of whatever generation, is newer than that activation, comparing the two records' `observedAt` timestamps as instants, a tie not counting as newer (a newer failure shows only that the latest SessionStart for that session failed, so the session may be live in a process the registry never recorded); otherwise a passing binding, an ended owner with no newer failure, neither refuses nor warns. A warned binding is not treated as live; the manifest lists such bindings as a warning, with their session and version, so the user sees them before replying, and they do not refuse close. This is a deliberate exception to treating uncertain liveness as live: a bound binding without an activation record comes from a SessionStart that failed or never ran, from host removal (which removes every activation of the registration and leaves its bindings bound, including across a later fresh setup), or from a binding recorded before activation records existed, so such bindings persist and refusing on all of them could block close indefinitely. An ended session usually is not among them: it keeps its activation with an ended owner, which the guard neither refuses nor warns about, so each warning may be a live session. An activation with an ended owner usually, not always, means an ended session: a session resumed in a new host process whose SessionStart never ran keeps the earlier activation and is not detected, an uncovered case the controller names when presenting the manifest. The cost is that such a live session can fail closed on later store-reading operations after the close, or, when its run's deadline has passed, have one of its hooks append the exhausted-limit stop that Write guard's re-close recovers; the controller says so when presenting the warnings, so the user can end or restart those sessions before replying. Both `close-manifest` and `close` evaluate this branch in the runtime, reading the release registry the admitted migration context names (its `store`, which `validateContext` in `internal/releases/entry.js` already opens on every admitted migration execution): they list session records, read each matching binding's activation record and its registration's profile, and call `processes.ownerAlive(activation.owner, registration.profile, ...)` as the release service does. `close` performs those liveness inspections before any store transaction and, inside each, re-reads the session, activation and registration records, reusing the earlier liveness results, as Writing specifies. It fails closed: an unreadable registry, session, activation or registration record counts as a guard refusal naming what could not be read, and either action without an admitted migration context refuses, since the guard cannot run. The admitted session itself is not exempt, and its liveness is positive evidence: the migration entry's admission of the non-read-only `close` action requires the requesting session's live activation (refusing with `hook-activation-required` otherwise), and both `close-manifest`, whose read-only admission does not, and `close` treat the admitted session as live, so the two actions classify it identically and the manifest predicts the refusal `close` will meet: the migration entry admits a session bound to an older release while keeping that binding, and such a session's own runtime could not read a closed record afterwards, so closing from it refuses naming that session, and the remedy the refusal states is to close from a new session on a current release.

`CLOSE_SUPPORT_VERSION` is a constant equal to the first release that ships this spec, expected 3.3.26, defined once in the runtime and compared numerically by major, minor and patch.

The guard exists because those releases parse both stores with whitelists of `running`, `stopped` and `complete` (in this checkout: `creation-consistency.js`, `run-overview.js` `parseRunState`, `review-inventory.js` `parseReviewState`, `legacy-inventory.js`, `setup.js` `assertQuiescent`), so once a closed record exists, any session still bound to one of them fails on every operation that reads a store, project-wide. The guard turns that into a refusal before the close, naming what to finish or restart first. What the guard covers is a property, not a list: its session branch sees only bindings in the admitted context's release registry that already list this project, judged by their activation records as stated above. Any other session that later reads this project through a release or checkout older than `CLOSE_SUPPORT_VERSION` fails closed with its release's `*-state-unavailable` refusals until it moves to a current release, which is the remedy. That includes, among others: a session recorded in another release store (another host profile attached to a different store, or another operating-system user's default store); a session in the admitted registry whose binding does not yet list this project; a resumed session whose SessionStart never ran; a session running an older development checkout, which has no registry binding; a session bound to an older release that starts after the close; every new session on a host registration whose base release predates `CLOSE_SUPPORT_VERSION`, until that host's plugin is updated; and an older-release session in another project whose bundle collection or operation reconciliation reads this project through a binding that lists it. The controller says so when presenting the manifest, and the manifest warns about the host-registration case by listing each registration in the admitted registry whose base bundle identity is older, with that remedy. Releases before 3.3.23 already cannot read a store compacted to version 3, but the guard still reports any unfinished record or live session bound to them as defined above, since compaction neither removes stopped records nor checks sessions, and the other store may be uncompacted.

## Manifest

Close is two migration actions, mirroring `manifest` and `retire`:

- `close-manifest` (read-only): takes `members`, one to 20 distinct `{store, id}` pairs, where `store` is `delivery` or `review` and `id` an exact record id in that store, plus optional proposed `choices` and `acknowledgedRecords`. One manifest may span both stores, so records whose older bindings would otherwise refuse each other's close through the guard, such as an old stopped delivery and an old running review context, can be closed together. One entry check serves both `members` and `acknowledgedRecords`: an entry is a `{store, id}` object with exactly those two keys, `store` being `delivery` or `review` and `id` a nonempty string, and the entries of one list are distinct. Malformed `members` (a count outside one to 20, or any entry failing that check) fails the whole call with `migration-manifest-unavailable`, as malformed `retire` input does. It returns exactly `schema: 1`, `members`, `records` (the member projections), `ineligible` (each ineligible member with its code and message), `guard` with `named` (every record the guard's record branch names, acknowledged or not, with its status, risk and own close eligibility), `refusals` and `warnings`, `acknowledgedRecords`, `choices` and `hash`, so the user can act on every guard finding before approving, null when `choices` is omitted, as for `manifest`. It runs the same eligibility checks without writing, apart from the project-operation condition that Eligibility leaves to `close`'s admission, and reports each ineligible member with its refusal code rather than failing the whole call, so one call shows the user everything; `hash` is null while any member is ineligible or any guard refusal stands.
- `close`: takes the same `members`, `choices` and `acknowledgedRecords`, the `manifestHash`, `authority` and `reason`, and the admitted `actor`. It recomputes the manifest under the write lock and refuses with `migration-manifest-stale` when the hash differs.

This list is the authoritative definition of a member, which projects exactly what closing drops and has exactly these keys: `store`, `id`, `revision`, `status`, `objective`, `stop`, `hold`, `identity` (the release identity resolved by the rule Older-release guard states, or null), `workers` (each `{id, status, active, reconciles}`, where `reconciles` is the termination evidence kind `adoptionEligibility` proved for a worker whose saved status still reads active, which the close write will reconcile to `stopped`, or null), `incompleteTasks` (each `{id, title, stage}` for a task whose status is not `complete`), `findings` (counts over every finding of the record's tasks, of its closing record and of `closing.carriedFindings` that still owes something by lifecycle's own predicate, `!settled(finding) || finding.pendingClosure`, as `carriedFindings` computes it, reusing lifecycle's predicates so the two cannot drift, each counted once in the first category it matches: `pendingClosure` for a finding still pending closure by the reviewer that raised it, `pendingRepair` for one disposed `implement` and not yet repaired, with `pendingRepairRequired` counting those whose obligation is required, `unverified` for one with no skeptic verdict or with the verdict `unverified`, `pendingDisposition` for one with any other verdict and no disposition; every counted finding falls in exactly one category, and findings that are settled and not pending closure are not counted), and `followups` (the pending follow-up items); a delivery member also has `closing: {stage, report: {recorded, delivered, path}}`, where `stage` is `closingStage(state)` (`retrospective`, `report`, `triage` or `complete`, the last for a record stopped after triage but before completion). A review-context member has the same keys without `closing`. It reuses these pieces of the retirement projection in `legacy-approval-v1.js`: the worker active rule, the unresolved-follow-up filter, `closingStage` and the report recorded, delivered and path derivation; `identity`, `findings` and the task subset are new. Artifact-backed fields appear as content hashes, as in `retire`.

`choices` is an array holding one `{store, id, report, followups}` per member, as retire's choices hold one per record:

- `report`: retire's grammar, an object `{kind}` read as retire reads `choice.report.kind`, normalized to `{kind, sha256}` for the hash, where exactly one `kind` is valid for each member. A missing or malformed `report`, a `kind` not valid for the member, or a `choices` list that does not cover each member exactly once fails the whole `close-manifest` or `close` call with `migration-decision-unavailable`, as retire's manifest does. A review context, and a delivery without a handover, take `none`. A handed-over delivery whose saved report has a valid recorded delivery takes `already-delivered`. Every other handed-over delivery, which `reportAwaitsRecipient` in `creation-consistency.js` reports as owing its report whether or not a report file was ever saved, takes `waived`, and the manifest shows whether a report is saved and its path so the user knows what they waive. `confirmed` is not offered: confirming a report goes through `report-delivered` on the record's own runtime, which close does not replace.
- `followups`: one `{id, disposition, destination}` per pending follow-up, `tracked` with an existing active backlog entry as `destination` or `dismissed`, with exactly `retire`'s grammar and validation for tracked destinations, checked when the manifest is computed and again under the write lock. A member with no pending follow-ups may omit it. After the close, the decisions live in the `approval` artifact; no later gate rechecks a tracked destination, since a closed record holds no handover back.

The hash is `progress.fingerprint` over `{schema, members, records, choices, acknowledgedRecords, guard}`, where `acknowledgedRecords` is that list sorted as Older-release guard states, `members` is the requested `{store, id}` list in request order, `records` the member projections defined above in the same order, `choices` the choices in `retire`'s normalized form (the report as `{kind, sha256}`, with `sha256` the saved report's hash or null, and each follow-up as `normalizeChoice` in `legacy-inventory.js` builds it, a tracked destination carrying the entry hash `targetEntry` binds, so an edit to that backlog entry between `close-manifest` and `close` stales the approval and the approval artifact records the entry content the user approved), and `guard` the guard's warnings; there is no store-wide inventory hash, since each member's revision and projection anchor its staleness, so a newly appearing older-release binding stales the approval. Limits follow `retire`: the canonical approval body is at most 8 MiB, a larger one refusing the whole call with `migration-manifest-unavailable` as `retire`'s does, and the authority at most 4 KiB; the `closure` field itself must serialize under 8 KiB, and a larger one refuses with `migration-certificate-bound`, whose message mirrors `retire`'s whole bound message: it asks for a shorter reply or reason, and when the closure would exceed the bound even with the shortest reply and reason, it says the record cannot be closed in this release and stays unchanged until a separately authorized limit change.

Presentation is the controller's: present the complete manifest, every member's dropped obligations and any guard warnings, and ask for the user's final reply and reason; never close from an abbreviated preview, an earlier broad choice or an unavailable user.

## Writing

`close` writes each store its members name inside that store's own `RunStore.transaction`, the delivery store first, then the review store; each transaction takes the project write-ownership mutex (`.nightshift/runs/write-ownership.sqlite`) itself, as every runtime write does, so close holds the mutex only while a store transaction runs, never across the whole action. Like `compact-history`, both `close` and `close-manifest` are dispatched before the migration entry's delivery-store lookup and before it opens its read-only delivery connection, so its no-delivery-store refusal applies to neither, and no connection of the entry's own holds the delivery store while close writes; it never calls `update()` or `adopt()`, which are bound to the active selection and to the record's owner. Process inspection, which can take seconds, runs before any store transaction: `close` first evaluates each member's owner and worker liveness and each older binding's activation liveness outside the lock. Inside each transaction it then re-reads the store rows and the registry records, applies the already-closed rule below to every member, and refuses with `migration-manifest-stale` if any other member revision, binding or activation record differs from what it inspected, recomputes the full manifest from those reads and the earlier liveness results (an exact process identity proven ended stays ended), and refuses with `migration-manifest-stale` unless the hash still matches, so the lock is held only for SQLite reads and writes; it then saves the approval artifact and, for each of that store's members in id order, applies the close state change itself, as `adoptState` is applied for adoption, not through lifecycle `transition()` or `assertAction`, whose non-running refusal (`run-stopped`), limit and continuation checks do not govern an administrative close: it applies the writer-owned changes Status model lists and nothing else, and saves the result as a new revision with history kind `close` through the store's ordinary save path, so history, the version-3 compact history encoding and, for a delivery, schema-2 progress and provenance accounting stay coherent with every other transition. Within a store, either every member closes or none does.

Two stores cannot share one transaction, so a manifest spanning both has one expected partial state: the delivery transaction committed and the review transaction failed or never ran. Its durable states are therefore none closed, the delivery members closed, or all closed. One already-closed rule governs every recomputation, in this call's later store transaction as in a retry: a member already closed whose `closure.manifestHash`, `closure.authority` and `closure.reason` all equal the request's, matching authority as retire's `existingRetry` does, is checked by comparing its `closure.previousRevision` with the revision inspected for it (or, when this call closed it, with that inspected revision directly), is projected from its `previousRevision` history row as a pure function of stored data, taking each worker's `reconciles` from `closure.reconciledWorkers` and inspecting no process liveness for it, so the hash recomputes unchanged, and is skipped when writing; the remaining members are written as usual. A closed member that matches the hash but not the authority or reason refuses with `run-closed`, so one approved manifest records one reply. So a manifest spanning both stores closes in one call, and resume is the identical retry. An identical retry, the same members, choices, manifest hash, authority and reason, with every member already closed under that hash returns the existing closures without writing. Any other request naming a closed record refuses with `run-closed`. The action's result lists every member closed with its `closure`, reason included, and, on failure, which store committed, so the controller retries rather than presenting a new manifest. When the identical retry refuses for any reason, or the action ended without a result, the controller reads each member's status to learn what committed, reports the closed members from their closures, and presents a new manifest naming only the members not yet closed for a fresh approval.

Close does not stop or signal any process, delete any artifact, run copy or worker evidence, or change release bindings, bundles or hooks. Bundle collection and release reconciliation see the record as finished, as Consumers specifies.

## Write guard

A closed record is immutable in the current release. The guard has two layers:

- **Lifecycle.** The closed-status refusal is the first check in `assertAction`, ahead of the closing-target early return into `assertClosingAction` and ahead of the `bookkeeping` exemption for non-running records, so it refuses every action on a closed record with `run-closed`, whichever path the action would otherwise take, including closing-record receipt imports on a closed delivery that has triage evidence, without listing actions. `adopt`, `resume` and `claim-controller` are refused the same way. Read-only `status`, `inspect`, `history` and `wait` still work.
- **Store.** `RunStore.update`, `save` and `adopt`, and their review-store equivalents, refuse with `run-closed` when the record's saved status is `closed`, except for the close write itself. This backstops any path the lifecycle check misses, as `isRetired` does for retired records.

No SQL trigger is added. The current release is kept away by these two checks. A session bound to an older release reaches its hooks and runtime only through its own release service, whose `readRun` (or `readReviewReference`) parses the target record with the three-status whitelist and throws before any hook or runtime code runs, so it fails closed on a closed record. Two narrow paths stay uncovered: a hook of any registered event (SessionStart, PreCompact or Stop) of an older-bound owner of the active delivery whose release service's `readRun` of the active delivery lands just before the close commits while its hook's own read of that delivery lands after, so the hook sees the record closed and, when the run's deadline has passed, can append the exhausted-limit stop with a current revision (a stop based on a read taken before the close is refused as stale; hooks never read the review store, so a closed review context is not exposed to this race, and Interrupt is not a registered hook event on either host), and an older development checkout's runtime run directly, without a release service, against a closed development-mode record. A similar check-then-act window on the runtime path is closed by release-registry project-operation serialization: close runs as a non-read-only project operation from admission until its child terminates (Eligibility's project-operation condition), and every release service, older ones included, admits a runtime write only in a registry transaction that re-reads the target and refuses while such an operation is active, so the window is closed for every session recorded in the admitted registry, with or without an activation record; it stays open only for a session recorded in another release store, whose registry never sees close's operation, which the guard already names as undetected. This depends on close staying a non-read-only migration action. A status-changing write on any of these paths (a stop, a hold, the older hook's limit stop) leaves a record whose status is no longer `closed` but which still carries `closure`; such a record is eligible again on its new status, and closing it again through a fresh manifest restores it, with the earlier `closure` kept in its history. A status-preserving write (bookkeeping such as a follow-up, or a closing-record import) leaves the record `closed` and still discharged under Creation gate's close-row rule, with the later rows kept as history and their content outside the user's approval.

## Creation gate

The delivery creation gate (`creationAssessment` in `creation-consistency.js`) accepts `closed` in its shape check and counts a closed delivery as discharged, with `closingOpen: false`, when its current status is `closed` and its `closure` is well formed, the history row at revision `closure.previousRevision + 1` exists, is kind `close`, and holds status `closed` with a `closure` deep-equal to the current one, and its accounting is current as for any other record; it never replays the dropped lifecycle. Anchoring on the close row rather than on the latest row keeps the authenticity check (a status edited without a close row still fails) while a later status-preserving revision cannot undo discharge. A closed selection is replaceable when it is discharged and no worker is active, the same discharge rule applying to the selection as to every other record. A closed record owes no morning report: `reportPending` is false for it, since close either found no report awaiting its recipient or recorded the user's waiver. `historicalDischarge` in `lifecycle.js` is not consulted for closed records.

## Ready

Ready's run-state section does not list closed records. For every listed `running` or `stopped` record, Ready evaluates close eligibility on its own, independently of the pickup's adoption routing (`routingRefusal` in `run-overview.js`, whose not-current, owned-by-this-session, no-retained-release and not-development refusals are adoption-only), with the status condition, `adoptionEligibility(state, {}, dependencies)` and, for a delivery, its saved accounting marker (`progress`, which run-overview already parses from the stored state, so Ready opens no accounting table): an absent marker or one whose status is not `current` fails with `close-accounting-unavailable`, whose remedy depends on the record: for a running delivery, run `close-manifest`, whose accounting replay is the authoritative check, or stop it first through its own release; for a stopped delivery, consult the migration inventory, which classifies it, and retire it when the inventory lists it as legacy, otherwise inspect it with `raw-inspect` and restore its accounting evidence, while `close` keeps the authoritative save-time check; Ready adds `close` to every listed record with the grammar of its sibling `pickup`: `{offer: 'close'}` when the evaluation passes, `{offer: 'none', reason, message}` when it fails, where `reason` carries the eligibility refusal code (`adoptionEligibility`'s codes or `close-accounting-unavailable`) as `pickup.reason` carries `adoptionEligibility`'s, and `null` for a listed record Ready does not evaluate for close, such as the current complete delivery awaiting its report, as `describe` initializes `pickup`; the Ready skill offers, for a record whose `close.offer` is `close`, beside whatever pickup is offered, to close it through the migration entry after presenting its manifest. The older-release guard is not part of this evaluation, since `close-manifest` reports it. The offer is an offer only: the controller carries it out only after the user says yes, through `close-manifest` and `close` with the user's reply, relays each closed member's closure and reason from the result, and relays any refusal as authoritative. A record whose close eligibility fails gets no close offer, and the Ready skill reports its `close.message` beside the pickup refusal it reports as today. A compaction entry's `blockedBy` keeps naming running records only, so a record leaves it when it stops, completes or is closed; the Ready skill's compaction wording says compaction is blocked until those records stop or are closed.

## Out of scope

- Closing a record whose workers need native worker-evidence exports; the eligibility refusal names it, and such a record bound to an older release does not block other closes once acknowledged.
- Closing or retiring a running legacy delivery in a store without the accounting tables; it must be stopped through its own release first, or acknowledged.
- Reopening a closed record. Closing is final in the current release, as retirement is; Write guard names the older-release paths that can still change one and how each is recovered.
- Closing more than 20 records in one manifest; larger sets close in several manifests, each acknowledging the older-bound records it does not include.
- Closing records in another project, or from a development checkout's runtime on a bound store.
