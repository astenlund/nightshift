# Resumable reviewer and adversarial repair dialogue

Governing spec for [Resumable reviewer and adversarial repair dialogue](../features/resumable-reviewer-dialogue.md). It carries that record's Settled questions and Before implementation, agreed with the user on 2026-10-01, and the user's evidence decision of the same day: a budgeted check on the installed candidate on both Claude Code and Codex.

## Outcome

The reviewer that raised a finding verifies its repair with its own context, and the controller can extend the exchange between that reviewer and the skeptic when a finding's consequence, value or repair quality stays unclear or disputed. Continuity never replaces fresh eyes: a review gate passes only on a fresh-context reviewer's assessment, so every loop that used a continued reviewer ends with one.

## Terms

- A fresh assessment starts a new host session that receives no earlier findings beyond the recorded acknowledgements. Every assessment is fresh today.
- A resumed assessment continues the native session of an earlier completed dispatch of the same run.
- A replacement assessment starts a new session that stands in for a reviewer, or for a skeptic in dialogue, that cannot be resumed, and receives what that participant's findings and dialogue require.
- Resumed and replacement assessments are continued assessments. A receipt without the new continuation field, including every receipt from earlier releases, is a fresh assessment.

## Resuming a session

`dispatch` accepts `review.resume` naming the request id of the latest completed dispatch on a native session of the same run and task. The runtime takes host, model, effort and native session from that dispatch's saved worker and receipt; the request supplies no candidates, a required model must equal the resumed model, and a resumed dispatch never falls back to another candidate. It is refused when the named dispatch is unknown, belongs to another run or task, did not complete, has no recorded session or is not the latest completed dispatch on its session, or when an active or unverified worker holds that session.

Each resumed dispatch captures a new private copy and context exactly as a fresh dispatch does. Its prompt names the new location, states that earlier copies are stale and must not be read, and lists the reviewer's findings pending closure and the dispositions recorded since the session's last imported report. On Claude Code the runner adds `--resume <session>` to the dispatch's usual arguments with the new copy as working directory. On Codex a new app-server process calls `thread/resume` with the thread id, the new copy as `cwd`, the same model, the read-only sandbox, the never-approval policy and the configuration `thread/start` uses. A probe on 2026-10-01 resumed a session from a different directory on both hosts: Claude Code 2.1.286 kept the session id and earlier context and read the new copy's file; Codex CLI 0.158.0 kept the thread id and earlier context and reported the new directory, while reading from the new copy was not exercised.

The receipt records `continues: {kind: "resumed", requestId}`. Attribution additionally requires the reported session to equal the resumed session; independence, model, input-freshness and drift rules are unchanged. Codex reports cumulative thread usage, so a resumed attempt records the difference between the thread total at the end of its turn and at its start; Claude usage stays per invocation. A resumed attempt counts toward `maxDispatches` like any attempt.

A resume that fails because of its session, meaning the host cannot find or continue the session, the session's context is exhausted, the attempt times out or the attempt returns no usable report, fails the dispatch with a distinct `resume-failed` error and its attempt evidence. Failures that do not concern the session keep their existing codes and handling, among them input and snapshot drift, resource and operation time limits, and independence refusals; after input drift the controller resumes again rather than replacing. Unproven termination outranks both: a resumed attempt whose process termination is unproven fails with `termination-unverified` and leaves its worker unverified, as every dispatch does, so the session stays held until reconciliation proves the process ended. After `resume-failed` the controller dispatches a replacement; the runtime does not substitute one itself.

## Replacement

`dispatch` accepts `review.replaces` naming the latest completed dispatch on a session of the same run and task, with ordinary candidates. A lead's replacement receives that reviewer's findings from the run record, each with its durable id, disposition and repair state, with the findings pending closure marked as unverified repairs, and inherits those pending closures. A skeptic is replaced only for a dialogue turn, as Dialogue states. The receipt records `continues: {kind: "replacement", requestId}`, and later resumes continue the replacement's own session. A request cannot combine `resume` and `replaces`.

## Repair reasoning and closure

Every confirmed verdict adds `repairProposal`: the approach a repair would take, with enough reasoning to judge it and without a complete patch, whatever the skeptic recommends about implementing it; an import refuses a confirmed verdict without one. The proposal is recorded with the verdict, and a re-validation that replaces the verdict replaces it, history keeping the earlier one. The `repair` operation refuses a finding disposed `implement` whose current verdict carries no proposal, as a refuted or unverified verdict does; the controller then obtains one through a dialogue turn with the skeptic before editing. The controller decides every disposition and applies every repair; reviewers and skeptics never edit reviewed inputs.

Pending closure is a finding's own durable state, separate from its verdict, disposition and repair state. The `repair` that records a finding sets it, naming the dispatch that raised the finding, and only an imported complete report of that reviewer, or of its replacement, that records the finding closed ends it. A continued lead's report adds `closures`, exactly one per finding pending closure for that reviewer when the dispatch captures its inputs: `{id, closed, evidence}`, where a closed entry may report that the finding no longer applies. A closure with `closed: false` must be matched by a finding in the same report and leaves the finding pending closure. An incomplete report's closures are not recorded, and a dialogue reply, a failed dispatch, a failed or refused import, and any re-validation or later disposition, including one that clears the repair state as `validate` does today, record none, so the finding stays pending. Replacing the closing record, by any operation that resets closing evidence or by a re-recorded triage, carries the findings pending closure and their originating dispatch into the new record. Every gate that checks a finding, including the closing record's and run completion, refuses while it is pending closure. Besides closures, a continued lead assesses the complete cumulative change, or the whole spec, across every dimension, as any lead does; during the loop its assessment is the strong cumulative assessment each repair batch needs.

## Dialogue

When skeptic validation leaves a finding's consequence, value or repair quality unclear or disputed, the controller may relay between the reviewer that raised it and the skeptic that validated it, never connecting them directly. A dialogue turn is a resumed dispatch carrying `review.dialogue: {findingIds, message}`. When the participant's session cannot be resumed, the turn goes to a dialogue replacement, `review.replaces` with `review.dialogue`, which receives the named findings with their current verdicts, the dialogue evidence recorded so far and the message. A lead's reply gives, per named finding, `{id, position, evidence}` with position `maintain`, `revise` or `withdraw`, and is imported with a new `dialogue` operation as evidence on those findings. A skeptic's reply is a verdict list over the named findings, imported with `validate`, which replaces the finding's current verdict while history keeps the earlier one. Dialogue receipts never satisfy a review gate and never record closures. The controller may end a dialogue at any point and dispose on the recorded evidence; a finding whose validity stays undecided remains unresolved. Validation of a new finding always uses a fresh skeptic.

## Ending the loop

A continued assessment can raise findings, which are validated and disposed like any other, but it never satisfies a gate or coverage condition. Every check that today accepts a complete strong assessment, all of which go through `completeAssessment` in `internal/runtime/lifecycle.js`, accepts only a fresh one: the code, spec, lore and docs task gates, coverage of earlier tasks through `coveredTaskIds`, the closing record's review, and the triage baseline's test for reviewed changes.

While any finding of the task is disposed `implement` and not yet repaired, the controller repairs and resumes first. After a continued assessment that leaves no critical or important finding awaiting repair, each being refuted or settled without an edit by a skip or a deferral under the applicable authority, and no finding pending closure, the controller dispatches a fresh lead over the complete cumulative change, or the whole spec, with the settled findings among its acknowledgements. `dispatch` accepts `review.acknowledgements`, a list of settled statements recorded with the request and presented as settled: dispositions, refuted findings, and intentional choices the governing requirement or the user made, each scoped narrowly and never the author's reasoning. A fresh dispatch receives no other earlier findings. When the fresh assessment's findings are all resolved without edits, by skip, deferral with a route, or refutation, the gate passes as today without another pass; the controller may defer minor findings at its discretion. Repairing any of its findings resumes that reviewer and repeats the cycle.

After a repair batch the controller resumes, each to verify the repairs and reassess its own kind's complete cumulative change: the reviewer that raised each repaired finding; the latest reviewer of any other review kind whose reviewed files the repairs changed; and, whenever a repair changes code, the latest docs reviewer of the affected tasks, when one exists. Each that cannot be resumed gets a replacement, and each continued reviewer's loop ends with a fresh assessment of its kind as above. This is the user's own review-loop rule, which sets the minimum for this behavior.

## Boundaries

- No direct reviewer and skeptic channel, no agent edits of reviewed inputs and no size threshold for fixes.
- Reviewer peer dispatch stays with its own entry, which this work unblocks.
- The runtime does not predict context exhaustion; a continued reviewer that fails is replaced.
- Existing runs and receipts need no migration: a run keeps the runtime of the release that created it, so pending closure and the fresh-assessment gate apply only to runs this release creates, and earlier receipts count as fresh.

- On the installed candidate, on Claude Code and on Codex, within an aggregate token budget the user sets before the campaign, the campaign attempts each model-owned branch: a resumed lead reads the new copy and reports a closed and a not-closed closure, the latter with its matching finding; a lead replacement after a forced resume failure; a dialogue round with a lead reply in each of the maintain, revise and withdraw positions and a skeptic verdict reply; a skeptic dialogue replacement; a skeptic verdict with a `repairProposal`; and a fresh lead given acknowledgements that it treats as settled. The gate refusing a continued assessment until a fresh one passes is also observed. Each branch not observed on a host is reported unverified for that host.
