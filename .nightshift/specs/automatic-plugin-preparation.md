# Automatic Nightshift preparation

## Agreement and outcome

The user approved automatic preparation on first use, retained releases for every installed operation, Ready and Exploring without continuation activation, and user-facing interruptions only for necessary host actions or unrecoverable preparation failures. The work began attended; the user subsequently invoked handover and granted 4,000,000 aggregate tokens for live testing, including retries. Actual continuation capabilities and limitations are recorded in the run. Publication is not authorized. Use Opus for Claude work while Fable is unavailable; supported fresh Astra assessments may supply the existing review gate. The original retained-release design remains authoritative except for the explicit changes below.

Invoking a skill prepares Nightshift and continues the requested work. Users do not manage release stores, locators, bindings, launchers or request files. A successful preparation produces no setup conversation. Actual failures explain the affected requested action and the concrete recovery, with technical details retained for diagnosis.

## Preparation and authority

All eight public skills share one preparation procedure before binding. Skill invocation authorizes Nightshift-owned local preparation and necessary hook registration in the actual host profile. It does not authorize engineering work beyond that skill, changing unrelated configuration, granting native trust, enabling a deliberately disabled plugin or hook, or restoring an explicitly removed registration. Passive hooks do not perform first-use installation merely because an unrelated session starts.

Preparation uses the actual native session, enabled plugin identity, profile and project. It verifies a complete release before using it and applies the existing bounded source rediscovery rules. Existing bindings, including resumable runs and workers, retain their exact identities; an existing binding cannot be replaced by preparation. New sessions may adopt the currently enabled release. Preparation must work across an upgrade from a registered 3.1.0 installation as well as a profile with no prior registration. It must not depend on an old retained launcher already understanding the new preparation action. Preparation establishes or reconciles the durable session binding before returning its launcher and bound root. This reuses the existing binding lifecycle and ensures concurrent old-session activity cannot redirect an unbound new session through an older administrative fallback. A crash after binding but before return keeps that exact binding for retry. Resource binding is permitted before native activation, but does not admit a dependent operation or fabricate continuation evidence. Runtime preparation carries the intended create action or explicit run identity so existing completed and unfinished runs retain their established selection rules.

Use the existing registration journal and registry rather than a second setup state machine. No registration means prepare and register owned resources. A matching usable registration is reused without duplicated hooks or trust changes. Interrupted preparation resumes only after writer liveness and saved configuration establish a safe recovery. A removed registration, deliberate disabling, conflicting profile/store, malformed state or unavailable native inspection is a distinct failure, never an absent-installation signal. Repeated and concurrent calls converge on one registration or report a bounded busy condition. A failed or uncertain writer is never displaced without established recovery evidence. Before first-registration recovery, native inspection uses the saved pending definitions when committed definitions do not yet exist; it preserves the same disabling and conflict checks.

Retain the existing durable setup sequence and recovery contract: verified bundle/launcher preparation, pending registration and configuration journal, applied configuration, committed registration, then locator publication. Each successful write can be the crash boundary. Resume reuses verified payloads, reconciles unchanged or already-applied journal bytes, finishes a missing locator, and preserves conflicting bytes for explicit resolution. Partial or failed preparation cannot admit ordinary work. Preparation never retires bindings, collects bundles or changes an existing session's release.

## Admission and continuation

Ready admission is a narrow administrative compatibility boundary, including for existing retained 3.1.0 bindings. The current verified administrative release may establish read-only eligibility and execution leases, but it runs the Ready parser from the original bound bundle. The binding identity, parser bytes, saved run resources, runtime implementation and hook handler remain unchanged. Other operations retain their original bound dispatch and admission behavior. Legacy runs without resource identities keep the existing explicit-reconciliation boundary; this is not a generic runtime migration.

Preparation publishes the current administrative bootstrap in the existing per-user launcher store and atomically updates the registration's `bootstrap`, `bootstrapHash` and `baseBundle`, retaining the previous bootstrap in `routes`. It preserves the actual native `definitions` and `generation`, so existing hook commands and trust do not change. The new bootstrap uses the protected administrative bundle for preparation and Ready resolve/run requests, and the original bound bundle for runtime and hook requests. Every selected administrative bundle is manifest-verified; the existing bootstrap/entry leases protect administrative code and the original parser independently while an operation is running. Collection already retains the registration's base bundle and both operation bundle references. No new registry record kind or session identity is introduced.

If publication stops after writing the bootstrap but before the registry commit, the unselected verified file is reusable on retry and the old registration still governs. After the registry commit but before locator publication or session binding, the registration protects the new administrative bundle and retains the old native hook route; retry publishes the matching locator and reconciles the original or newly selected session binding. Existing 3.1.0 bind callbacks cannot replace the new administrative base because the primary bootstrap hash has changed. Current callbacks may advance the base only for genuinely new release selection, never when revisiting an existing binding or explicitly selected run. Missing or unverifiable administrative resources fail dependent view admission with a recoverable diagnosis; they never authorize unbound execution or changing the original work identity. Disabling/removal still wins. Use the current preparation result when first invoking a skill from this release; subsequent calls can reuse it while its registration matches, even when the bound parser comes from an earlier release.

Separate verified resource availability from verified continuation. A registered retained release is still required for every installed operation. Ready and Exploring both use the existing `ready` launcher entry and may run without trusted hooks or an observed activation in this session. They still require a complete retained bundle, enabled plugin, valid non-retired binding, consistent registration, ownership reconciliation, execution lease and normal entry validation. An untrusted newly registered hook does not block these read-only views; an explicitly disabled plugin or hook is not automatically enabled.

The exception is a closed list containing only the `ready` entry. Unknown entries fail. `unwrap`, project `setup`, and non-maintenance `runtime` operations retain their existing activation requirements. This covers init-backlog, handover and all four revise skills. Existing runtime diagnostics and narrowly defined maintenance operations retain their current recovery permissions and cannot create new work bindings through maintenance. Direct installed scripts do not gain an unbound fallback, and development mode remains an explicitly selected repository/test surface.

An operation that needs continuation checks native trust and actual session activation at admission, even if that session already ran Ready successfully. Ready must never create an activation record or mark continuation verified. Denied trust, missing activation, disabled hooks and failed native checks remain distinct and fail dependent operations closed. Enabling trust remains a host-owned user decision. Request reopening only when the current session cannot establish genuine activation; neither a saved flag nor simulated invocation proves activation.

## User-facing behavior

The shared skill instructions direct the controller to prepare and continue without asking a separate setup question. Instructions and machine diagnostics stay out of ordinary reports. If native trust is needed for the requested operation, explain the capability and exact host action in plain language. If that action is denied or no user is available, preserve progress and leave dependent work pending. Configuration conflicts and failed preparation explain the blocked request and a concrete recovery; they do not present an empty backlog or claim successful continuation. Repeat use in an unchanged session does not repeat a resolved prompt. Status and explicitly requested troubleshooting may expose technical detail.
