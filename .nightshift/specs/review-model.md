# Project review model

## Project default and setup

Nightshift uses the bundled review model automatically when the project has no `.nightshift/REVIEW.md`. `init-backlog` creates that file from the bundled template when absent. The project copy is user-editable and supplies the project model. Setup preserves an existing copy when only one side has changed, including an untouched seeded copy on a bundled update. A present model that cannot be read is reported as unavailable so the controller can resolve it before relying on review evidence.

On a rerun, `init-backlog` offers interactive merge assistance when the project copy and the bundled template have diverged and both have changed since the copy was seeded or last reconciled. Compare both versions with the prior bundled text where available, show the user the changes and any overlap, and agree on the resulting text together. Matching versions establish the current baseline without a merge. If the baseline is unavailable and the two available versions differ, disclose the uncertainty and offer a side-by-side comparison. Apply only the exact merged text the user approves, and recheck the compared inputs before writing. Preserve the project copy while the decision is pending or declined. Setup can resume safely after interruption and keeps enough provenance for later comparisons.

## Effective model for a review

Use the project model when present and the bundled default otherwise. Every model guides judgment within the accepted scope and mandatory review and verification obligations. The user approves any changes to those commitments. When a work-specific override would matter, the controller proposes and explains it in the scope readback. Apply only overrides the user approves and record them with the agreed scope or governing spec. The project file stays user-owned throughout delivery. Handover carries the agreed scope and makes the full template available on request.

Each lead assessment records the effective model for each scope it covers, including approved overrides, which apply only to the work they name. The skeptic and controller use those same scoped versions to verify and interpret the assessment's findings. An updated model governs new assessments. Before relying on existing evidence under the updated model, reassess coverage affected by a changed deciding boundary, including cases an earlier clean assessment may have omitted. A lead may raise an observation it judges outside the effective model with `required: false`. The skeptic verifies the facts and checks reachability under the captured model. A confirmed observation outside the accepted scope or excluded by the effective model appears as advisory in the report and creates neither repair work nor a backlog entry. This includes observations about in-scope components whose failure trigger the model excludes. Accepted commitments govern the disposition in every case. Scope decisions remain distinct from factual verdicts and from an assessment of practical value.

## Bundled default text

Apply these defaults where the user's agreed requirements leave room for judgment. Take binding commitments from the accepted scope and any later changes the user approves. Use more detailed implementation notes as context for understanding the design. Assess those details by whether they help deliver the agreed outcome.

Trust internal callers. Validate inputs at boundaries the project does not control, including user input, external tools, and files written by people or other programs. Cover conditions the project can encounter in practice, including interrupted writes, data from earlier releases, and environmental failures. Deliberate tampering with project-owned state is in scope only when explicitly agreed.

The lead explains what each recommended repair would address and why it is in scope. If a finding concerns an explicit commitment, cite where the user agreed to it and demonstrate the mismatch. This applies to required behavior, deliverables, and acceptance conditions. For other behavioral findings, name a trigger a supported workflow can encounter and the harm or disruption the fix would prevent. For other findings, state the practical consequence and give evidence appropriate to the review dimension.

The skeptic independently verifies the evidence. For an explicit commitment, verify its authority and the mismatch. For a finding that rests on practical harm, check that the trigger is reachable and the claimed consequence follows. Propose a repair for every confirmed finding. The controller classifies the finding as required, optional, or out of scope and checks that any fix it takes on addresses the verified finding. Confirmed observations outside the agreed scope may be reported as advisory.

For an optional repair, weigh its practical benefit against the cost and risk of the change, including any additional verification or review. Prefer to include a worthwhile fix in a batch that already owes the relevant review. When a fix would trigger another round, weigh that cost against what the current stage can still prevent.

- In `revise-spec`, another round is often worth it when it catches a mistake in the requirements or architecture before implementation. Leave implementation details open when the alternatives meet the same commitments. If an unresolved technical question could change a governing decision, run a bounded spike when the investigation fits the work's authority and limits. Use the result to recommend a direction. Changes to governing requirements still need user approval.
- In `revise-code`, give little weight to optional edge cases and nits without a practical consequence. If a worthwhile optional fix warrants a decision but the current batch cannot justify the extra review, bring it to delivery triage or list it as a follow-up in the standalone revision's final report. At triage, pursuing a fix requires implementation authorization and further code review. Tracking edits can share one closing documentation review after triage. Skipping the finding closes the question.
- In `revise-docs`, decide during the current pass whether a finding warrants an edit. Defer the decision only when it genuinely needs user input.

## Verification and close

- Deterministic checks cover creation, preservation on one-sided changes, automatic fallback, merge detection and missing baseline, interactive approval bound to the compared versions, interrupted setup, model selection and approved overrides including an assessment covering work with different effective models, evidence currency including scope expansion after a clean review, and advisory disposition for a trigger excluded by the model in an otherwise in-scope component.
- Installed-host evidence shows the effective model reaching the reviewer roles. Compare prior and candidate review behavior on matched seeded-defect fixtures with comparable reviewer models and run conditions. Include fixtures that declare a trust boundary and contain a true finding about an in-scope component with an excluded trigger. Measure the share of true out-of-model issues a lead marks required and recall for reachable defects before and after skeptic validation. Agree on an aggregate token budget before the live campaign. Report measured overreach and recall together, distinguish directional results from demonstrated improvement, and disclose inconclusive or missing evidence.
- After the other delivery work is complete, add a quick win to review each active bug and quick win for possible closure. Word it in light of the finished review model. The audit should bring evidence-backed closure candidates to the user for disposition and is separate from this delivery.
