# Handover transition, acknowledgment and morning report

Status: commitments agreed by the user on 2026-09-18; revised after four independent assessments, whose confirmed findings are corrected here. On the same day the user chose recorded report delivery over untracked delivery, and directed that cross-session continuity come from resuming the run, never from pointing the user at report files.

## Agreement and outcome

The user selected three ready entries on 2026-09-18: [Handover omits the morning report](../BUGS.md#handover-omits-the-morning-report), [Handover leaves existing runs in attended mode](../BUGS.md#handover-leaves-existing-runs-in-attended-mode) and [Acknowledge accepted handovers clearly](../QUICK_WINS.md#acknowledge-accepted-handovers-clearly). The user decided that report delivery becomes runtime state, that the morning-report obligation follows an explicit handover only, that every run (attended included) still ends by listing its pending follow-ups and other loose ends, and that the behavior is verified on both Claude Code and Codex. Publication is not authorized by this spec.

After this change a user who hands work over is told unmistakably that the handover was accepted, the run they hand over actually operates unattended when the host can sustain it, and they return to a report that stands on its own. None of the three depends on the model remembering an unrecorded duty: the handover, the mode, the report and its delivery are saved run state that survives compaction, yields, completion and reopening.

Throughout this spec, "handed-over run" means a run with a recorded handover, whatever its saved mode, and "run without a handover" means a run with no such record. The saved mode (`attended` or `unattended`) is a separate fact.

## Handover as a recorded transition

Add one lifecycle action, `handover`, for a running run owned by the calling controller. The request carries `authority` (non-empty text: the user's actual handover words or a faithful description of them) and an optional `mechanism` with the same shape the `continuation` action accepts. It is an ordinary guarded action, not bookkeeping, so the existing owner, revision and limit checks apply unchanged and the action is refused on a stopped run with the existing `run-stopped` error; the controller resumes a stopped run under user authority with the existing `resume` action before handing it over. The action does not resume a run itself.

The action performs exactly one write with two possible outcomes. With `mechanism.verified === true` and non-empty `mechanism.evidence`, it stores the mechanism as `state.continuation`, sets `mode` to `unattended` and records `state.handover = {authority, revision}` where `revision` is the revision the write produces. Without a `mechanism`, it records `state.handover` and leaves `mode` and `state.continuation` untouched: the handover and its report obligation are saved although unattended enforcement is not available. A `mechanism` that is present but not verified, or verified without evidence, is rejected with the existing `unverified-continuation` code and writes nothing. The response is the standard obligation brief, which now carries `mode` and `handover`, so the controller reads the actual outcome instead of assuming it.

Carrying the mechanism inside the same request is deliberate: a `verified` flag saved earlier in the run is not evidence that continuation works at the moment of handover, and one write leaves no partially applied transition to recover. The durable states are therefore exactly three: no handover recorded; handover recorded with the run still attended; handover recorded with the run unattended. A repeated `handover` on a run that already has a record keeps the original `authority` and `revision`, may upgrade attended to unattended when it supplies a verified mechanism, and never downgrades an unattended run. An interrupted call either committed or did not, and the controller re-reads status to tell which; retrying is always safe.

The transition changes nothing else. Run identity, queue, task states, workers, agreements, accepted spec and review evidence, requirements revisions, limits, follow-ups, publication authority and any closing evidence already recorded are preserved, and `resetClosing` is not invoked. `create` with `mode: unattended` records the same `state.handover` from the run's `authority`, so new and existing runs converge on one state shape. A state without `handover` means no handover happened; that is the literal historical meaning, and runs created by earlier releases read that way.

Two unavailable-enforcement cases are distinct. When the runtime admits the session (registered retained release, trusted hooks, observed activation) but the native goal or Stop behavior cannot be verified, the mechanism-less outcome above applies: the handover is recorded and the run stays attended. When admission itself is refused (untrusted or disabled hooks, or no observed activation for the session), no runtime action runs, this one included; `internal/releases` admission is unchanged and gains no exemption, consistent with the retained-release design's ban on a silent plugin-only continuation fallback. In that case nothing is recorded, the controller does not accept the handover, and it tells the user the exact recovery in plain language (approve the hook trust, or reopen the session) and that the work stays interactive until then. No report obligation arises because no handover exists; the attended loose-ends readout below still applies. Development-mode runs are never admission-blocked and always reach the action.

Retained-release binding is unchanged: a run bound to an earlier release keeps that release's runtime and does not gain this action. For such a run the handover skill reports the limitation and relies on the native goal, as today.

## The morning report as a closing stage

`state.closing` gains `reportEvidence` and `reportDelivery` beside `retrospectiveEvidence` and `triageEvidence`; `resetClosing` and `recordRetrospective` clear both with the others, so resumed engineering makes an earlier report stale exactly as it makes the retrospective stale. Absent fields mean not recorded.

A new bookkeeping action, `report`, requires `closingReady`, recorded retrospective evidence and a recorded handover, and takes `path`: a project-relative Markdown file under `.nightshift/runs/reports/`, which the project already ignores. The runtime reads the file, rejects a missing, empty or out-of-tree path, and stores `{path, sha256}`. On a run without a handover the action is rejected with `report-not-due`. A repeated `report` replaces the evidence and clears any recorded delivery, since a changed report has not been delivered.

The closing order for a handed-over run is retrospective, report, triage, completion. The brief's `closing.stage` reads `retrospective`, then `report` while a handover exists without report evidence, then `triage`, then `complete`. On a handed-over run `triage` requires report evidence (`report-required`), and `complete` checks report evidence itself with the same code rather than relying on `triage` having enforced it, so a handover that arrives after retrospective and triage were already recorded still cannot complete without a report; in that ordering the stage returns to `report`, and the earlier retrospective and triage evidence stand. Runs without a handover keep today's two-stage closing unchanged. The unattended Stop hook needs no new branch for the stage: it already resists a yield while closing is due and the stage is not `complete`. The existing pause on task blockers that are all user decisions is preserved.

Saving the report is not delivering it. A second bookkeeping action, `report-delivered`, requires a recorded handover and report evidence, takes `authority` (non-empty text: the user's actual message received after the report was presented, which is what shows a user was present), and stores `reportDelivery = {authority, revision, sha256}` bound to the delivered report's hash. It re-reads the report file and is rejected with `report-stale` when the file is missing or its hash differs from the recorded evidence. It is accepted on a running, stopped or complete run, as `resolve-followup` already is, and it is idempotent for the same report. It never gates `complete`: an absent user must not block a finished delivery. A final message sent into an empty room is not delivery, and the controller does not infer an answer.

The report and the follow-up triage are one hand-off. While a handed-over run has report evidence and either no matching delivery or any pending follow-up, the owning session's SessionStart context carries a morning-report notice: whether the report is undelivered, its path, whether the file still matches its recorded hash, and the ids of pending follow-ups. This requires one logic change in `internal/runtime/hook.js`: its early return for complete and stopped runs gains an exception for that condition, which returns the notice (without the full obligation brief for a complete run). The exception applies to SessionStart only. Stop never resists a yield for an unrecorded delivery or a pending follow-up on a closed run, in any mode, because both need a user who may be absent. PreCompact is unchanged. The durable states after closing are: report saved and undelivered; report delivered with follow-ups pending; report delivered with none pending, where the notice ends. Each can coincide with a complete or a not yet complete run, and a crash at any point lands in one of them, so the next SessionStart of that session resumes the hand-off from the saved state. A report file that no longer matches is reported as stale in the notice, never silently treated as delivered or presentable; the recovery is to rewrite the file and record `report` again, which is accepted on a complete run and clears the earlier delivery.

The notice, the hand-off and `report-delivered` reach only the checkout's active run and only its owning session, as every hook output and mutation does today; none takes a run selector, and this spec adds no report duty that would have to reach a replaced run or another session. That boundary is stated here and deliberately not worked around. The user's direction on 2026-09-18 is that continuity across sessions comes from resuming the run in the new session, after which everything behaves exactly as it does in the owning session, and never from pointing the user at saved report files. That is the separate [run-ownership defect](../BUGS.md#run-ownership-is-locked-to-the-creating-host-session) together with a Ready feature the user proposed the same day (a new session is told about interrupted work and offered to pick it up), recorded as a follow-up of this run. Until those land, a handed-over run's report reaches the user through the owning session: its final message, or the SessionStart notice when that session is reopened. The saved file exists for the controller to re-present the report, not as something the user is sent to find.

The report is written for a reader who saw nothing of the run: it does not assume progress output, the continuous log or a question asked while the user was away were read. It contains, in this order: what was delivered and its verification with stated limits; which of revise-code, revise-docs and revise-lore actually ran, with any omitted, blocked or later-recovered stage named as such; commits and publication status; the material retrospective outcomes, distinguishing implemented repairs, open tracked work, recovered incidents with no durable follow-up, and instruction proposals or the reason none was worthwhile; every unresolved item with what it is, where it is, what failed, its impact and the pending choice; and whether the run operated unattended or remained attended with the recorded limitation. A technical acceptance artifact, a saved retrospective or a commit confirmation does not substitute for it. "Follow-ups are tracked" or "triage is complete" is not a readout.

Optional follow-up decisions never delay the report or block a completed delivery. With the user absent, the controller records the report, records triage evidence stating that the listed decisions remain deferred, completes with those follow-ups pending, as the runtime already permits, and ends with the report as its final message. The report as presented always ends with the first pending follow-up as a host question carrying its context, recommendation and the effect of each choice, or with a plain statement that no decision is pending. When the user is next present in the owning session, whether they answer the final message or the SessionStart notice appears after reopening, the controller presents the report that way if the user has not yet seen it (from the saved file when the original message is out of view). The user's first reply after the presentation, typically the answer to that first question, is the delivery authority: the controller records `report-delivered` and the answer's `resolve-followup`, then presents the next follow-up after each answer. The user never has to reply merely to unlock triage. Unresolved delivery blockers are reported as blockers, never as optional follow-ups. This replaces the brief's current instruction to "ask first and close after the answers", which is narrowed to task blockers that are user decisions: those still pause before closing, and the pause message carries the same stand-alone context as a report item.

A run without a handover has no report stage and no runtime gate. The brief's closing text requires its final message to list pending follow-ups and other loose ends (unfinished or blocked obligations, qualified verification, unpublished commits) with enough context to act on, alongside the existing readout of which workflows ran.

## Acknowledgment

After the `handover` action returns, the handover skill has the controller say plainly that the handover is accepted and that the user can leave, restating briefly the accepted work and the limits in force, stating whether the run is operating unattended, and saying that a morning report will be waiting in this session. When the `handover` action is refused with `resource-operation-busy` because a runtime dispatch holds the project lease, the refusal is temporary and needs no trust or reopening recovery: the controller awaits the dispatch with `wait`, retries the action, and acknowledges only after it returns, telling the user meanwhile that the handover will be recorded when the running assessment finishes. No lease exemption is added. The acknowledgment does not reopen settled requirements, ask for another readback approval, or mention publication unless publication authority was already granted, in which case it restates that grant without widening it. When a material decision, an unsettled readback or refused admission is outstanding, the controller names it and the recovery instead of claiming acceptance; when only unattended enforcement is unavailable on an admitted runtime, it says the handover is recorded, names which prerequisite failed and what that means for the user, and lets the user decide whether to leave. The consequence depends on the failure: when the native goal is verified and only Stop-hook behavior is not, the goal carries the queue without protection against a premature yield; when the native goal itself cannot be verified, no unattended continuation is established, the work proceeds only while the session stays active, and the controller says so instead of implying that anything will carry the queue.

## Consumers and documentation

Every consumer of the changed state is listed here with its handling. `internal/runtime/lifecycle.js`: new `handover`, `report` and `report-delivered` actions, the stage computation, the `triage` and `complete` preconditions, `mode`, `handover` and the delivery status in `obligationBrief`, and the new actions placed in the correct `assertAction` lists (`report` and `report-delivered` are bookkeeping, `handover` is not). `internal/runtime/store.js`: `create` records `state.handover` for unattended creation; the mode validation, the active-pointer replacement and `update`, which still mutates only the active run, are unchanged. `internal/runtime/hook.js`: the SessionStart exception described above, including the file hash check; Stop and PreCompact logic unchanged apart from the new brief fields arriving through `obligationBrief`. `internal/runtime/cli.js`: no run selector is added and its `wrong-run` rejection stands; otherwise untouched unless action routing requires registration, which implementation confirms by reading its dispatch. `internal/releases`: no change; `service.js` keeps `MAINTENANCE` and `ACTIVATION_EXEMPT` as they are, so all three actions need ordinary admission, and its hook wrapper passes the notice through as it passes any hook output; `mode` there is the unrelated resource mode. `internal/runtime/REFERENCE.md`: documents the three actions, the three durable handover states, the closing order, the delivery states, the SessionStart notice, the admission boundary and the retained-release limitation. `internal/workflow.md`: Durable execution names the transition for an existing run; Close and report gains the morning report, its delivery, the narrowed ask-first sentence and the loose-ends readout for runs without a handover. `skills/handover/SKILL.md`: the transition, the acknowledgment, the refused-admission answer and the report obligation. `skills/revise-lore/SKILL.md` and `skills/revise-docs/SKILL.md`: checked for sentences asserting the old closing order and reconciled if any exist. README and the v3 feature record are reconciled where they describe handover or closing. The three backlog entries move to their history files, the quick win's cross-references are removed, and the ready parser is re-run.

## Verification

Deterministic coverage in `tests/runtime*.test.js`: handover of an attended run with and without a mechanism; rejection of an unverified mechanism with state unchanged; repeat and upgrade behavior with the original record preserved; refusal on a stopped run and for a non-owner; preservation of queue, active workers, evidence, limits, publication and earlier closing evidence across the transition; `create` with unattended mode recording the handover; `report` acceptance, its rejections, its invalidation by resumed engineering and delivery being cleared by a replaced report; `triage` and `complete` each refusing without a report on a handed-over run, including the ordering in which retrospective and triage were recorded before the handover, and proceeding unchanged on a run without one; `report-delivered` on running, stopped and complete runs, its rejections including `report-stale` for a changed or missing file, and idempotence; `report` re-recorded on a complete run; stage values in the brief; the Stop hook resisting a yield at the report stage, still permitting the user-decision pause, and never resisting for an unrecorded delivery or a pending follow-up on a closed run; SessionStart emitting the notice for a complete handed-over run with an undelivered report, still emitting it after delivery while a follow-up is pending, marking a stale file, and emitting nothing extra once delivery is recorded with no follow-up pending, for another session, or for a run without a handover. A state fixture without `handover`, `reportEvidence` or `reportDelivery` proves earlier runs read as not handed over.

Installed-host evidence on both Claude Code and Codex, against a small fixture project so context stays cheap, combined into five scenarios per host: (1) a new-run handover through acknowledgment, absent-user completion with optional follow-ups, then the session reopened so the SessionStart notice appears and the report is presented ending with the first follow-up as a host question, the single reply recording both delivery and that decision, with a second pass in which the saved report file is altered before the reopening, showing the stale notice, the controller rewriting the file and recording `report` again, and only then the normal presentation; (2) an attended run already underway, with an active registered worker (not a running runtime dispatch, whose lease makes the action wait as the acknowledgment section describes), that is handed over without a verifiable mechanism and then handed over again with one, showing the record preserved, the upgrade to unattended, the worker untouched and the acknowledgment without a repeated readback, with a second pass in which a real runtime dispatch is in flight at the moment of handover, showing the controller telling the user the handover will be recorded when the assessment finishes, awaiting it, retrying, and acknowledging only after the action returns; (3) a handover with an unresolved prerequisite and one with admission refused, each showing the named limitation and recovery without a claimed acceptance, plus a handover on an admitted runtime whose continuation cannot be verified, showing a report that is still delivered; (4) a handover interrupted by compaction or reopening before the report, then resumed to a complete readout, covering a completed delivery with no pending decision but material retrospective outcomes and one with a genuine blocker; (5) a run without a handover closing with listed loose ends. Together these cover the both-host verification clauses of the two bug entries: new and existing runs, active workers, repeated handover, failed continuation prerequisites and recovery, the readout after a resumed handover and after a mode-transition failure, and the returning-user cases. The aggregate live-verification allowance is 4,000,000 tokens covering probes, retries and cached input on both hosts, with accounting from each host's finalized usage records; it is an allowance, not an estimate or target, the controller sizes probes within it on its own authority, and it is never exceeded or renewed without the user. If a host lane is unavailable when evidence is due, that host's cases stay qualified as unverified and the limitation is reported; they are not replaced by the other host's results.
