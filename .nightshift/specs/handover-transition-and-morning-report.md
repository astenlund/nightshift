# Handover transition, acknowledgment and morning report

Status: draft for user review. Not yet independently assessed. Drafting does not authorize implementation.

## Agreement and outcome

The user selected three ready entries on 2026-09-18: [Handover omits the morning report](../BUGS.md#handover-omits-the-morning-report), [Handover leaves existing runs in attended mode](../BUGS.md#handover-leaves-existing-runs-in-attended-mode) and [Acknowledge accepted handovers clearly](../QUICK_WINS.md#acknowledge-accepted-handovers-clearly). The user decided that report delivery becomes runtime state, that the morning-report obligation follows an explicit handover only, that every run (attended included) still ends by listing its pending follow-ups and other loose ends, and that the behavior is verified on both Claude Code and Codex. Publication is not authorized by this spec.

After this change a user who hands work over is told unmistakably that the handover was accepted, the run they hand over actually operates unattended when the host can sustain it, and they return to a report that stands on its own. None of the three depends on the model remembering an unrecorded duty: the handover, the mode and the report are saved run state that survives compaction, yields and reopening.

## Handover as a recorded transition

Add one lifecycle action, `handover`, for a running run owned by the calling controller. The request carries `authority` (non-empty text: the user's actual handover words or a faithful description of them) and an optional `mechanism` with the same shape the `continuation` action accepts. It is an ordinary guarded action, not bookkeeping: a stopped run is resumed first, and the existing owner, revision and limit checks apply unchanged.

The action performs exactly one write with two possible outcomes. With `mechanism.verified === true` and non-empty `mechanism.evidence`, it stores the mechanism as `state.continuation`, sets `mode` to `unattended` and records `state.handover = {authority, revision}` where `revision` is the revision the write produces. Without a `mechanism`, it records `state.handover` and leaves `mode` and `state.continuation` untouched: the handover and its report obligation are saved although unattended enforcement is not available. A `mechanism` that is present but not verified, or verified without evidence, is rejected with the existing `unverified-continuation` code and writes nothing. The response is the standard obligation brief, which now carries `mode` and `handover`, so the controller reads the actual outcome instead of assuming it.

Carrying the mechanism inside the same request is deliberate: a `verified` flag saved earlier in the run is not evidence that continuation works at the moment of handover, and one write leaves no partially applied transition to recover. The durable states are therefore exactly three: no handover recorded; handover recorded with the run still attended; handover recorded with the run unattended. A repeated `handover` on a run that already has a record keeps the original `authority` and `revision`, may upgrade attended to unattended when it supplies a verified mechanism, and never downgrades an unattended run. An interrupted call either committed or did not, and the controller re-reads status to tell which; retrying is always safe.

The transition changes nothing else. Run identity, queue, task states, workers, agreements, accepted spec and review evidence, requirements revisions, limits, follow-ups and publication authority are preserved byte for byte, and `resetClosing` is not invoked. `create` with `mode: unattended` records the same `state.handover` from the run's `authority`, so new and existing runs converge on one state shape. A state without `handover` means no handover happened; that is the literal historical meaning, and runs created by earlier releases read that way.

Retained-release binding is unchanged: a run bound to an earlier release keeps that release's runtime and does not gain this action. For such a run the handover skill reports the limitation and relies on the native goal, as today.

## The morning report as a closing stage

`state.closing` gains `reportEvidence` beside `retrospectiveEvidence` and `triageEvidence`; `resetClosing` and `recordRetrospective` clear it with the others, so resumed engineering makes an earlier report stale exactly as it makes the retrospective stale. A new bookkeeping action, `report`, requires `closingReady`, recorded retrospective evidence and a recorded handover, and takes `path`: a project-relative Markdown file under `.nightshift/runs/reports/`, which the project already ignores. The runtime reads the file, rejects a missing, empty or out-of-tree path, and stores `{path, sha256}`. On a run with no handover the action is rejected with `report-not-due`.

The closing order for a handed-over run is retrospective, report, triage, completion. The brief's `closing.stage` reads `retrospective`, then `report` while a handover exists without report evidence, then `triage`, then `complete`. `triage` on a handed-over run requires report evidence (`report-required`), and `complete` therefore requires it transitively. Runs without a handover keep today's two-stage closing unchanged. The unattended Stop hook needs no new branch: it already resists a yield while closing is due and the stage is not `complete`, and the new stage sits inside that condition. The existing pause on task blockers that are all user decisions is preserved.

The file is the durable copy; the delivery is the controller's final user-facing message, which carries the same content. The report is written for a reader who saw nothing of the run: it does not assume progress output, the continuous log or a question asked while the user was away were read. It contains, in this order: what was delivered and its verification with stated limits; which of revise-code, revise-docs and revise-lore actually ran, with any omitted, blocked or later-recovered stage named as such; commits and publication status; the material retrospective outcomes, distinguishing implemented repairs, open tracked work, recovered incidents with no durable follow-up, and instruction proposals or the reason none was worthwhile; every unresolved item with what it is, where it is, what failed, its impact and the pending choice; and whether the run operated unattended or remained attended with the recorded limitation. A technical acceptance artifact, a saved retrospective or a commit confirmation does not substitute for it. "Follow-ups are tracked" or "triage is complete" is not a readout.

Optional follow-up decisions never delay the report or block a completed delivery. With the user absent, the controller records the report, records triage evidence stating that the listed decisions remain deferred, and completes with those follow-ups pending, as the runtime already permits. When the user returns, the SessionStart brief shows the report stage and pending follow-ups; the controller presents the report (the saved file when the original message is out of view), then immediately presents the first pending follow-up as a host question with its context, recommendation and the effect of each choice, and the next after each answer. Unresolved delivery blockers are reported as blockers, never as optional follow-ups. This replaces the brief's current instruction to "ask first and close after the answers", which is narrowed to task blockers that are user decisions: those still pause before closing, and the pause message carries the same stand-alone context as a report item.

An attended run has no report stage and no runtime gate. The brief's closing text requires its final message to list pending follow-ups and other loose ends (unfinished or blocked obligations, qualified verification, unpublished commits) with enough context to act on, alongside the existing readout of which workflows ran.

## Acknowledgment

After the `handover` action returns, the handover skill has the controller say plainly that the handover is accepted and that the user can leave, restating briefly the accepted work and the limits in force, and stating whether the run is operating unattended. The acknowledgment does not reopen settled requirements, ask for another readback approval, or mention publication unless publication authority was already granted, in which case it restates that grant without widening it. When a material decision, an unsettled readback or a continuation prerequisite is outstanding, the controller names it instead of claiming acceptance; when only unattended enforcement is unavailable, it says the handover is recorded, names the limitation and what it means for the user (the native goal carries the queue without Stop-hook protection), and lets the user decide whether to leave.

## Verification

Deterministic coverage in `tests/runtime*.test.js`: handover of an attended run with and without a mechanism; rejection of an unverified mechanism with state unchanged; repeat and upgrade behavior with the original record preserved; refusal on a stopped run and for a non-owner; preservation of queue, workers, evidence, limits and publication across the transition; `create` with unattended mode recording the handover; `report` acceptance, its rejections, and its invalidation by resumed engineering; `triage` and `complete` refusing without a report on a handed-over run and proceeding unchanged on a run without one; stage values in the brief; and the Stop hook resisting a yield at the report stage while still permitting the user-decision pause. A state fixture without `handover` or `reportEvidence` proves earlier runs read as not handed over.

Installed-host evidence on both Claude Code and Codex, against a small fixture project so context stays cheap, combined into five scenarios per host: (1) a new-run handover through acknowledgment, absent-user completion with optional follow-ups, then a returning user who receives the report followed by the first follow-up as a host question; (2) an attended run already underway that is handed over, showing the saved mode switch and acknowledgment without a repeated readback; (3) a handover with an unresolved prerequisite, and one where continuation cannot be verified, showing the named limitation and a report that is still delivered; (4) a completed delivery with no pending decision but material retrospective outcomes, and one with a genuine blocker; (5) an attended run closing with listed loose ends. The aggregate live-verification allowance is 4,000,000 tokens covering probes, retries and cached input on both hosts, with accounting from each host's finalized usage records; it is an allowance, not an estimate or target, the controller sizes probes within it on its own authority, and it is never exceeded or renewed without the user. If a host lane is unavailable when evidence is due, that host's cases stay qualified as unverified and the limitation is reported; they are not replaced by the other host's results.
