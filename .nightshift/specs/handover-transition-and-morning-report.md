# Handover transition, acknowledgment and morning report

The [run-adoption and renewed-continuation design](run-adoption-and-continuation.md) amends this contract with adopted-owner continuity and explicit continuation invalidation. The commitments below include those amendments; their actual delivery and per-host evidence remain qualified in the [adoption report](../reports/run-adoption-and-continuation-20260921.md). Earlier handover evidence does not establish the later adoption branches.

The [per-host continuation fix](../BUGS_HISTORY.md#unattended-mode-requires-a-native-goal-on-hosts-that-do-not-need-one) of 3.2.10 further amends the mechanism, Stop protection and acknowledgment sentences below: a verified Stop hook carries unattended work for a Claude Code controller, a native goal remains required on Codex, and the acknowledgment of a verified unattended handover says plainly that it is accepted without naming mode or mechanism. Its evidence and limitations are recorded in [its acceptance report](../reports/unattended-stop-hook-20260926.md).

Status: commitments agreed by the user on 2026-09-18; revised after five independent assessments, whose confirmed findings are corrected here, and after implementation and installed-host evidence added the new-run fallback, the state-specific notice and the full-report final message. On the same day the user chose recorded report delivery over untracked delivery, and directed that cross-session continuity come from resuming the run, never from pointing the user at report files.

## Agreement and outcome

The user selected three ready entries on 2026-09-18: [Handover omits the morning report](../BUGS_HISTORY.md#handover-omits-the-morning-report), [Handover leaves existing runs in attended mode](../BUGS_HISTORY.md#handover-leaves-existing-runs-in-attended-mode) and [Acknowledge accepted handovers clearly](../QUICK_WINS_HISTORY.md#acknowledge-accepted-handovers-clearly). The user decided that report delivery becomes runtime state, that the morning-report obligation follows an explicit handover only, that every run (attended included) still ends by listing its pending follow-ups and other loose ends, and that the behavior is verified on both Claude Code and Codex. Publication is not authorized by this spec.

After this change a user who hands work over is told unmistakably that the handover was accepted, the run they hand over actually operates unattended when the host can sustain it, and they return to a report that stands on its own. None of the three depends on the model remembering an unrecorded duty: the handover, the mode, the report and its delivery are saved run state that survives compaction, yields, completion and reopening.

Throughout this spec, "handed-over run" means a run with a recorded handover, whatever its saved mode, and "run without a handover" means a run with no such record. The saved mode (`attended` or `unattended`) is a separate fact.

## Handover as a recorded transition

Add one lifecycle action, `handover`, for a running run owned by the calling controller. The request carries `authority` (non-empty text: the user's actual handover words or a faithful description of them) and an optional `mechanism` with the same shape the `continuation` action accepts. It is an ordinary guarded action, not bookkeeping, so the existing owner, revision and limit checks apply unchanged and the action is refused on a stopped run with the existing `run-stopped` error; the controller resumes a stopped run under user authority with the existing `resume` action before handing it over. The action does not resume a run itself.

The action performs exactly one write with two possible outcomes. With `mechanism.verified === true`, non-empty `mechanism.evidence` and a `mechanism.kind` the controller's host supports (`goal` on either host, `stop-hook` only for a Claude Code controller), it stores the mechanism as `state.continuation`, sets `mode` to `unattended` and records `state.handover = {authority, revision}` where `revision` is the revision the write produces. Without a `mechanism`, it records `state.handover` and leaves `mode` and `state.continuation` untouched: the handover and its report obligation are saved without new continuation assurance. A `mechanism` that is present but not verified, or verified without evidence, is rejected with the existing `unverified-continuation` code, one without a known kind with `invalid-continuation-kind`, and a `stop-hook` for a Codex controller with `unsupported-continuation`; a rejected mechanism writes nothing. The response is the standard obligation brief, which carries `mode` and `handover`, so the controller reads the actual outcome instead of assuming it.

Carrying the mechanism inside the same request is deliberate: a `verified` flag saved earlier in the run is not evidence that continuation works at the moment of handover, and one write leaves no partially applied transition to recover. The durable handover categories remain exactly three: no handover recorded; handover recorded with the run attended; handover recorded with the run unattended. A repeated `handover` keeps the original `authority` and `revision` and can restore unattended mode with a freshly verified mechanism. The handover action itself does not downgrade mode; the explicit invalidation action below does. After an interrupted call, re-read status, reconcile current evidence and retry only the still-needed transition.

At renewed handover, adoption, resume, compaction recovery and before unattended yield, reconcile saved work, actual workers and the current host mechanism. Continuation starts unverified and is scoped to the run, current controller, mechanism and observation. Refresh it at those boundaries; ownership change, observed inactivity, missing or failed inspection, deliberate disablement and lost trust/activation invalidate it. Missing or unscoped historical evidence grants no continuation, and elapsed time does not substitute for inspection. Keep the latest focused observation in state and earlier observations in history. Ordinary source edits alone do not invalidate an unrelated host observation.

Owner-only `invalidate-continuation` takes nonempty `reason` text describing the actual observation. It atomically records unverified continuation and sets mode to attended on either a running or stopped run, preserving status, handover, limits, agreements, engineering evidence and closing duties. It grants no native goal or engineering claim. After response loss, read status and repeat only for a newer observation. A later verified `continuation` observation alone does not change mode; an authorized `handover` with current verification can restore unattended operation. This supersedes the original no-downgrade constraint without changing the three handover categories or accepting an unverified mechanism in ordinary `handover` or `continuation` requests.

The handover transition changes nothing else. Run identity, queue, task states, workers, agreements, accepted spec and review evidence, requirements revisions, limits, follow-ups, publication authority and any closing evidence already recorded are preserved, and `resetClosing` is not invoked. `create` with `mode: unattended` records the same `state.handover` from the run's `authority`, so new and existing runs converge on one state shape. A state without `handover` means no handover happened; that is the literal historical meaning, and runs created by earlier releases read that way.

Two unavailable-enforcement cases are distinct. When runtime admission is usable but no goal or alternative mechanism can be verified, persist invalidation of stale continuation and continue useful authorized work attended; a mechanism-less handover records the reporting duty in that mode. Create new work attended when verification is unavailable. Unverified unattended state permits the designated claim/invalidation recovery paths, not dependent engineering under stale assurance. Stop protection is observed separately: a verified goal can carry work even when Stop protection is unavailable, and a working Stop hook establishes unattended continuation only when it is itself verified as the `stop-hook` mechanism of a Claude Code controller.

When admission itself is refused by disabled integration, missing trust/activation or failed inspection, neither handover nor invalidation gains an exemption. No downgrade or new handover is recorded, but any existing handover and report duties remain unchanged; historical verification is unusable as current evidence. Name the concrete recovery and continue only permitted diagnostics/maintenance and independent authorized work. Do not silently restore trust or use development mode to bypass admission. Once genuine admission returns, reconcile fresh evidence before dependent execution. If there was no prior handover, refusal creates none; the ordinary loose-ends readout still applies. Explicit development runs lack retained-host admission but retain their runtime owner, revision, limit and continuation gates.

The retained payload identity is unchanged by adoption: a run bound to an earlier release keeps that runtime and does not gain operations it lacks. Current execution ownership may change only through a compatible adoption; no silent upgrade supplies missing handover or recovery operations. Report the retained-release limitation and rely only on continuation actually verified for that context.

## The morning report as a closing stage

`state.closing` gains `reportEvidence` and `reportDelivery` beside `retrospectiveEvidence` and `triageEvidence`; `resetClosing` and `recordRetrospective` clear both with the others, so resumed engineering makes an earlier report stale exactly as it makes the retrospective stale. Absent fields mean not recorded.

A new bookkeeping action, `report`, requires `closingReady`, recorded retrospective evidence and a recorded handover, and takes `path`: a project-relative Markdown file under `.nightshift/runs/reports/`, which the project already ignores. The runtime reads the file, rejects a missing, empty or out-of-tree path, and stores `{path, sha256}`. On a run without a handover the action is rejected with `report-not-due`. A repeated `report` replaces the evidence and clears any recorded delivery, since a changed report has not been delivered.

The closing order for a handed-over run is retrospective, report, triage, completion. The brief's `closing.stage` reads `retrospective`, then `report` while a handover exists without report evidence, then `triage`, then `complete`. On a handed-over run `triage` requires report evidence (`report-required`), and `complete` checks report evidence itself with the same code rather than relying on `triage` having enforced it, so a handover that arrives after retrospective and triage were already recorded still cannot complete without a report; in that ordering the stage returns to `report`, and the earlier retrospective and triage evidence stand. Runs without a handover keep today's two-stage closing unchanged. A functioning Stop hook protects a running run with recorded handover or unattended mode while actionable work, workers or closing duties remain, including after invalidation to attended mode. Explicit user stops and exhausted limits take precedence; a user-decision-only pause remains permitted when no actionable work or active worker remains. An unavailable hook supplies no protection. The three-reminder no-progress bound survives claim-only writes and repeated invalidation observations that change no execution state; a real progress transition resets it.

Saving the report is not delivering it. A second bookkeeping action, `report-delivered`, requires a recorded handover and report evidence, takes `authority` (non-empty text: the user's actual message received after the report was presented, which is what shows a user was present), and stores `reportDelivery = {authority, revision, sha256}` bound to the delivered report's hash. It re-reads the report file and is rejected with `report-stale` when the file is missing or its hash differs from the recorded evidence. It is accepted on a running, stopped or complete run, as `resolve-followup` already is, and it is idempotent for the same report. It never gates `complete`: an absent user must not block a finished delivery. A final message sent into an empty room is not delivery, and the controller does not infer an answer.

The report and the follow-up triage are one hand-off. While a handed-over run has report evidence and either no matching delivery or any pending follow-up, the owning session's SessionStart context carries a morning-report notice: whether the report is undelivered, its path, whether the file still matches its recorded hash, and the ids of pending follow-ups. In `internal/runtime/hook.js`, the early return for complete and stopped runs has an exception for that condition, which returns the notice without restoring the full obligation brief for a closed run. A still-running handed-over run in that condition gets the same notice after its obligation brief. The notice opens with an instruction fitting the state: rewrite and record a report that is missing or changed, present one that is undelivered, or continue triage once it is delivered. The exception applies to SessionStart only. Stop never resists a yield for an unrecorded delivery or a pending follow-up on a closed run, in any mode, because both need a user who may be absent. PreCompact retains its reconciliation reminder. The durable states after closing are: report saved and undelivered; report delivered with follow-ups pending; report delivered with none pending, where the notice ends. Each can coincide with a complete or a not yet complete run, and a crash at any point lands in one of them, so the next SessionStart of the current owner resumes the hand-off from saved state. A report file that no longer matches is reported as stale in the notice, never silently treated as delivered or presentable; the recovery is to rewrite the file and record `report` again, which is accepted on a complete run and clears the earlier delivery.

The notice, hand-off and `report-delivered` reach only the checkout's active run and current owning session; they do not select a replaced run or grant a non-owner access. Authorized adoption changes that owner through the [adoption contract](run-adoption-and-continuation.md), preserving the recorded report, delivery hash, follow-ups and closing duties. Hooks resolve the current execution binding and cannot let a former owner emit continuation instructions or mutate the run. The new owner can perform permitted stopped report bookkeeping without an engineering claim; explicit resume is required before engineering, which retains its ordinary closing-evidence invalidation. Thus cross-session continuity follows the same adopted run rather than a file pointer. A new interrupted-run notice in Ready remains separate work. The saved file exists for the current controller to present the report, not as something the user is sent to find.

The report is written for a reader who saw nothing of the run: it does not assume progress output, the continuous log or a question asked while the user was away were read. It contains, in this order: what was delivered and its verification with stated limits; which of revise-code, revise-docs and revise-lore actually ran, with any omitted, blocked or later-recovered stage named as such; commits and publication status; the material retrospective outcomes, distinguishing implemented repairs, open tracked work, recovered incidents with no durable follow-up, and instruction proposals or the reason none was worthwhile; every unresolved item with what it is, where it is, what failed, its impact and the pending choice; and whether the run operated unattended or remained attended with the recorded limitation. A technical acceptance artifact, a saved retrospective or a commit confirmation does not substitute for it. "Follow-ups are tracked" or "triage is complete" is not a readout.

Optional follow-up decisions never delay the report or block a completed delivery. With the user absent, the controller records the report, records triage evidence stating that the listed decisions remain deferred, completes with those follow-ups pending, as the runtime already permits, and ends with the full report itself as its final message, never a summary of it or a pointer to where it was saved, including when the run closes blocked. The report as presented always ends with the first pending follow-up as a host question carrying its context, recommendation and the effect of each choice, or with a plain statement that no decision is pending. When the user is next present in the owning session, whether they answer the final message or the SessionStart notice appears after reopening, the controller presents the report that way if the user has not yet seen it (from the saved file when the original message is out of view). The user's first reply after the presentation, typically the answer to that first question, is the delivery authority: the controller records `report-delivered` and the answer's `resolve-followup`, then presents the next follow-up after each answer. The user never has to reply merely to unlock triage. Unresolved delivery blockers are reported as blockers, never as optional follow-ups. This replaces the brief's current instruction to "ask first and close after the answers", which is narrowed to task blockers that are user decisions: those still pause before closing, and the pause message carries the same stand-alone context as a report item.

A run without a handover has no report stage and no runtime gate. The brief's closing text requires its final message to list pending follow-ups and other loose ends (unfinished or blocked obligations, qualified verification, unpublished commits) with enough context to act on, alongside the existing readout of which workflows ran.

## Acknowledgment

After successful handover, acknowledge the accepted work and limits and the morning report owed through the run's current owner. With verified unattended continuation, say plainly that the handover is accepted and the user can leave, in the turn-ending message, keeping run mode and mechanism out of it; the morning report later states whether the run operated unattended. Say the user can leave only with an honest description of what can continue. If a runtime dispatch holds the project lease, `resource-operation-busy` is temporary: await it with `wait`, retry and acknowledge only after the action returns. Do not reopen settled agreement or widen publication authority. Name an outstanding consequential decision or admission recovery instead of claiming acceptance. When admitted without a verified continuation mechanism, say the handover is recorded and work can proceed in the active turn, while explaining the action needed for continuation after it ends. A verified goal, or on Claude Code a verified Stop hook, can carry the queue. A working Stop hook protects recorded handover after downgrade but does not restore a native goal, and it proves unattended continuation only through a fresh `stop-hook` verification on a Claude Code controller. Observe actual inactive states and read back any authorized supported restoration; never replace an unfinished goal or credit user/client restoration to the plugin.

## Consumers and documentation

The original handover/report consumers remain, with these adoption amendments. `internal/runtime/lifecycle.js` owns handover, report, delivery and invalidation transitions, closing gates and focused status; report/delivery/invalidation are bookkeeping, while handover retains ordinary runtime gates. `internal/runtime/store.js` keeps active-run selection and transactional owner/revision checks, records adoption atomically and carries no-progress reminders across observation-only writes. `internal/runtime/ownership.js` supplies native claims, adoption eligibility and former-controller exclusion. `internal/runtime/hook.js` selects the current owner, routes the report notice and protects recorded handover after downgrade; PreCompact retains its reconciliation reminder. `internal/runtime/cli.js` routes the actions without weakening ordinary wrong-run checks; adoption alone admits the authorized ownership transition. `internal/releases` resolves current execution resources, authenticates adoption and reconciles retention; report, delivery, handover and invalidation still require their ordinary host admission. Its resource mode remains distinct from attended/unattended runtime mode.

The runtime and retained-resource references document these boundaries. The operating brief and handover skill describe fresh continuation observations, the acknowledgment, admission recovery and preserved reporting duty. Revise-docs and revise-lore retain documentation-before-retrospective-before-triage ordering, with a handed-over report between retrospective and triage. README and the v3 feature record follow the supported behavior. The original three handover entries and their history remain historical delivery records; adoption backlog reconciliation follows its own current evidence and the real ready parser.

## Verification

Deterministic coverage in `tests/runtime*.test.js`: handover of an attended run with and without a mechanism; rejection of an unverified mechanism with state unchanged; rejection of a mechanism without a known kind and of a `stop-hook` for a Codex controller, and acceptance of a `stop-hook` for a Claude Code controller; repeat and upgrade behavior with the original record preserved; refusal on a stopped run and for a non-owner; preservation of queue, active workers, evidence, limits, publication and earlier closing evidence across the transition; `create` with unattended mode recording the handover; `report` acceptance, its rejections, its invalidation by resumed engineering and delivery being cleared by a replaced report; `triage` and `complete` each refusing without a report on a handed-over run, including the ordering in which retrospective and triage were recorded before the handover, and proceeding unchanged on a run without one; `report-delivered` on running, stopped and complete runs, its rejections including `report-stale` for a changed or missing file, and idempotence; `report` re-recorded on a complete run; stage values in the brief; the Stop hook resisting a yield at the report stage, still permitting the user-decision pause, and never resisting for an unrecorded delivery or a pending follow-up on a closed run; SessionStart emitting the notice for a complete handed-over run with an undelivered report, still emitting it after delivery while a follow-up is pending, marking a stale file, and emitting nothing extra once delivery is recorded with no follow-up pending, for another session, or for a run without a handover. A state fixture without `handover`, `reportEvidence` or `reportDelivery` proves earlier runs read as not handed over.

Installed-host evidence on both Claude Code and Codex, against a small fixture project so context stays cheap, combined into five scenarios per host: (1) a new-run handover through acknowledgment, absent-user completion with optional follow-ups, then the session reopened so the SessionStart notice appears and the report is presented ending with the first follow-up as a host question, the single reply recording both delivery and that decision, with a second pass in which the saved report file is altered before the reopening, showing the stale notice, the controller rewriting the file and recording `report` again, and only then the normal presentation; (2) an attended run already underway, with an active registered worker (not a running runtime dispatch, whose lease makes the action wait as the acknowledgment section describes), that is handed over without a verifiable mechanism and then handed over again with one, showing the record preserved, the upgrade to unattended, the worker untouched and the acknowledgment without a repeated readback, with a second pass in which a real runtime dispatch is in flight at the moment of handover, showing the controller telling the user the handover will be recorded when the assessment finishes, awaiting it, retrying, and acknowledging only after the action returns; (3) a handover with an unresolved prerequisite and one with admission refused, each showing the named limitation and recovery without a claimed acceptance, plus a handover on an admitted runtime whose continuation cannot be verified, showing a report that is still delivered; (4) a handover interrupted by compaction or reopening before the report, then resumed to a complete readout, covering a completed delivery with no pending decision but material retrospective outcomes and one with a genuine blocker; (5) a run without a handover closing with listed loose ends. Together these cover the both-host verification clauses of the two bug entries: new and existing runs, active workers, repeated handover, failed continuation prerequisites and recovery, the readout after a resumed handover and after a mode-transition failure, and the returning-user cases. The aggregate live-verification allowance is 16,000,000 tokens, raised by the user on 2026-09-19 from the 4,000,000 first agreed once measured handover scenarios proved to cost about a million tokens per host process, covering probes, retries and cached input on both hosts, with accounting from each host's finalized usage records; it is an allowance, not an estimate or target, the controller sizes probes within it on its own authority, and it is never exceeded or renewed without the user. If a host lane is unavailable when evidence is due, or the allowance cannot cover a scenario or pass, those cases stay qualified as unverified in [the acceptance report](../reports/handover-transition-and-morning-report-20260919.md) and the limitation is reported; they are not replaced by the other host's results or claimed from deterministic coverage.

The adoption amendment adds deterministic coverage for scoped continuation invalidation, repeated observation writes within the reminder bound, admitted versus refused recovery, and current-owner report/delivery preservation across transfer. Its separate per-host live claims include working and unavailable Stop protection after downgrade, user-stop/limit precedence and adopted report routing. Observed report preservation alone does not prove a later SessionStart notice. The [adoption report](../reports/run-adoption-and-continuation-20260921.md) records actual results and unsupported or unobserved contexts; the five original scenarios and their 16,000,000-token allowance above remain the historical handover campaign, not authority for further adoption probes.
