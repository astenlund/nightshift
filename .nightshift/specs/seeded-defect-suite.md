# Seeded-defect suite

## Outcome and boundary

Measure whether a fresh lead reviewer and its skeptic catch defects, through the runtime's own prompt and schema, against a fixed suite of small project states whose defects are known. It realizes the Exploring record [Measure whether the lifecycle catches defects](../features/defect-detection-measurement.md) and the worklist item "Seeded-defect measurement, with the criteria written first" in [the assessment worklist](../reports/assessment-worklist-20261018.md).

What the suite measures is bounded by what reaches a reviewer: the prompt and schema `internal/runtime/review.js` builds, its lens and severity text, the reviewer model and host, and the conventions text the harness passes as `rules`. A change to any of these is judged by rerunning the suite. A change to the operating brief or a skill reaches a reviewer only through the requirements and conventions a controller writes, so the suite measures it only where the change is carried into the fixtures' requirements or the suite's conventions text; a brief change that alters controller behavior alone, such as how repairs are chosen, is outside what this version can measure.

This first version measures one fresh code lead and one fresh skeptic per fixture. It runs no controller, repair, resumed closure or fresh gate, so it narrows the worklist item in three ways: it does not measure the fresh-gate catch rate, which needs fixtures that run a repair, a closure and a gate; it cannot grade an out-of-scope finding as "raised and disposed as out of scope", since disposition is the controller's and only the reviewer's advisory `required` flag exists here, so it reports out-of-scope findings as raised with that flag beside them; and the suite holds 23 fixtures, seventeen in its first baseline, against the thirty to fifty the item names, growing toward that range as each baseline shows what a fixture costs. The first two belong to a second version that runs the lifecycle around the review, specified once this version's numbers exist. Documentation and spec review kinds are later versions too.

The suite ships nothing: the harness lives under `tools/` and its fixtures under `tools/seeded-defects/`, outside the plugin payload, so no plugin version increase follows from it.

## Fixtures

A fixture is a directory under `tools/seeded-defects/fixtures/` holding a `base/` tree, a `change/` tree and a `fixture.json`. The harness materializes it as a fresh Git repository in a new directory under the operating system's temporary directory, outside this checkout, so that no ancestor of the reviewed copy contains the suite: `base/` is committed, then `change/` is copied over it uncommitted, so the review sees the change as the diff against the base commit. Line-ending conversion is turned off, hooks and the attributes file point at paths that do not exist, and the diff settings a machine can change (algorithm, prefixes, context, renames, color and path quoting) are pinned to Git's defaults, all in the fixture repository's own Git configuration, so that neither the harness's Git commands nor the runtime's own, which inherit that configuration, let this machine's settings alter the committed bytes or the diff. After materializing, the harness lists the repository's files as the runtime does, tracked plus untracked files that are not ignored, and treats a truth entry's file or any reviewed file missing from that list, as when a global ignore file hides it, as a fixture error. Before its first dispatch a run materializes every selected fixture once and refuses to start on any fixture error, naming it; a fixture error met later, when a dispatch materializes its repository, stops the run before that dispatch's intent is written, so it leaves no record to reconcile and the rerun meets the same check. A file present in `base/` and absent from `change/` is not deleted; a fixture that needs a deletion lists it in `fixture.json` under `deletions`. `fixture.json` itself is never copied into the repository.

`fixture.json` carries:

- `requirements`: the agreed outcome text the lead receives, written as a controller would write it.
- `defects`: the planted truth, each with an `id`, a `dimension` naming one of the six code dimensions by the runtime's id (`requirements-ux`, `correctness-integration`, `security-data-safety`, `design-maintainability`, `performance-resources`, `tests-evidence`), a `file`, a `lines` range in that file as the reviewed project holds it (the `change/` tree's copy, or the `base/` tree's for a sibling the change leaves untouched), a `symbol` when one names the defect site, a `severity` under the rubric below, a one-sentence `consequence`, and an `origin`: the BUGS.md or BUGS_HISTORY.md entry title or the receipt id of a defect a fresh gate caught that the defect is drawn from, or `synthetic`. A fixture whose `defects` and `incidental` lists are both empty is a clean fixture.
- `outOfScope`: true findings outside the agreed outcome, each with the same fields as a defect. A clean fixture may carry them; they are true findings, not defects of the change.
- `decoys`: false findings for the skeptic, each with a `severity`, `consequence`, `evidence` and `required` as a lead would report them, and a recorded reason it is false; the harness assigns their ids.
- `incidental`: real issues in the reviewed project that were neither planted nor out of scope, which the maintainer adds by hand after an adjudication finds one, as below, each with the same fields as a defect, its `origin` being the string `adjudicated:` followed by the name, not the path, of the run folder whose adjudication found it. The loader accepts that form only in `incidental` and refuses it in `defects` and `outOfScope`, so it never counts toward the real-source quota. They are never planted truth: they count in no detection or severity figure, and a finding matched to one counts in no false-positive figure. A new fixture starts with an empty list.
- `audited`: the date the fixture's author last checked that the planted, out-of-scope and incidental entries are every real issue in the reviewed project that a reviewer could reasonably report, so that an unmatched finding is expected to be adjudicated false.

The loader refuses a fixture whose truth entries overlap: two entries in the same file whose line ranges, each widened by three lines, intersect, or that share a symbol. Distinct defects at one site are one defect for grading. It also refuses a fixture whose trees hold a `.gitignore` or any path under `.nightshift/runs/`, `.nightshift/inbox/` or `.tmp/`, which the runtime leaves out of a reviewer's copy, so that every truth entry lies in a file the reviewer receives. These path checks compare without regard to case, since the verified Windows filesystem resolves `.GIT` or `.Gitignore` to the same entries, and the loader also refuses any path segment shaped like a Windows 8.3 short name, such as `GIT~1`, which can alias `.git`. Materialization checks the same thing on the disk: before copying each tree, it refuses one whose top-level entry already resolves to the repository's `.git` folder under another name. It refuses as well any path inside a `.git` folder, since materialization copies the trees over a configured repository and such a file could replace that configuration and run commands, and any entry that is neither a regular file nor a directory, such as a symbolic link or junction, the `base/` or `change/` folder itself included, even when the link's target is missing, since the copy would carry it through unchecked.

At least half of the first suite's planted defects take their `origin` from a real source, including at least two from BUGS.md or BUGS_HISTORY.md entries and at least two from defects a fresh gate caught, the two sources the worklist item names; `synthetic` defects fill the coverage the real ones leave. The first suite covers every code dimension with at least one planted defect, holds at least three clean fixtures, at least two with an out-of-scope true finding and at least two with a defect in a sibling path the diff does not touch, and gives every fixture with defects at least one decoy. A fixture's `change/` tree stays under about 400 lines, since fixture size dominates a dispatch's tokens; this is a guideline for fixture authors that the loader does not check. The loader checks these composition rules whenever a run selects the whole suite, with clean status and origins read from the current fixtures, a bug origin counting only when it names an entry heading, a third-level heading, in the checkout's BUGS.md or BUGS_HISTORY.md, never a section heading such as Current, so a mistyped title cannot satisfy the quota, and a receipt id checked by its form alone, since the receipts live in other projects' run stores, so incidental entries that make a clean fixture no longer clean are noticed: a whole-suite run whose fixtures no longer meet the rules refuses to start and names the unmet rule. A run of selected fixtures checks no composition rule and its report says it is a subset.

## Harness

`node tools/seeded-defects.js run --fixtures <dir> --out <run folder> --model <host>:<id>[@<host>:<id>] [--model <host>:<id>[@<host>:<id>]...] [--repeat <n>] [--fixture <name>...] --budget <tokens>` runs each selected fixture once per model per repetition. For each, it materializes the repository and calls `dispatchReview` from `internal/runtime/review.js` with kind `code`, the fixture's requirements, the suite's fixed conventions text from `tools/seeded-defects/rules.md` as `rules` (which the runtime places in the reviewer's system prompt, where a controller's applicable conventions go, and which asks every finding to name its file and line or symbol in its evidence, so that location matching measures what a reviewer found rather than how it phrased it), and a single candidate of that model at xhigh effort (an evaluated host receives no effort setting, as described below); it then calls `dispatchReview` with kind `skeptic` on the union of the lead's findings and the fixture's decoys, on the same model unless the `--model` value names a different skeptic model after `@`, so that one model can check another's lead findings; such a pair is one model for keys, figures and reports, labeled `<lead>@<skeptic>`, each stage's result record names the host version of the model that ran it, and a pair naming the same model twice is that model alone. A host must be letters and digits, and a model id letters, digits, `.`, `_` and `-`, beginning with a letter or digit and holding no `__`, since both become path segments of a fixture run key, `<fixture>__<host>-<id>`, followed by `__s-<host>-<id>` for a pair's skeptic, so neither may imitate a separator; a fixture name follows the model id's rule for the same reason, so no two fixture runs share a key; a run naming the same model twice is refused, two models differing only in case counting as the same since run keys become folder names on a case-insensitive filesystem, since both would share one fixture run key and count one model's results twice. The harness gives every claim in that union a fresh id of one form, `F1` onward, in an order set by a seeded shuffle, and records the mapping from each id to its lead finding or decoy and the seed in the run folder, so the skeptic cannot tell a decoy from a lead finding by id or position and no id collides. A lead with no findings sends its fixture's decoys alone; a fixture run with neither findings nor decoys dispatches no skeptic, and its skeptic figures have nothing to count.

A host the runtime's reviewer gate does not admit can be evaluated, so that the suite's figures can inform a separate decision to admit it; the harness knows one, `vibe` (Mistral Vibe, for example `--model vibe:glm-5-3`). For such a model the dispatch names a gate candidate the runtime accepts, Sol on Codex, and injects a launcher, `tools/seeded-defects/vibe-launcher.js`, as the dispatch's agent runner, which runs the evaluated host and model instead with the same prompt and system text. Vibe's command line has no structured-output, system-prompt, model or effort option, so the launcher puts the system text before the prompt and states the report schema in it, and Vibe's own system prompt stays in place. Vibe's configuration, read from the folder its `VIBE_HOME` variable names, can replace that system prompt (`system_prompt_id`, naming a built-in prompt or a custom `.md` file), trim what Vibe adds to it (`include_prompt_detail`, `include_project_context`, `include_model_info`) pin the model (`active_model`) and set each model's `thinking` level, which plays the part of effort; the launcher uses none of these and runs with whatever Vibe configuration its environment finds, by default the user's own, so the evaluated model is whichever one that configuration makes active, the attempt failing attribution when it is not the requested one, and Vibe thinks at that configuration's level while the harness's records echo the requested xhigh; it hands the runtime the final message's last fenced JSON block, an untagged or `json`-tagged fence, every fence being matched whatever its tag so that a block of code shown before the report cannot pair with the report's opening fence, or else the span from its first opening brace to its last closing one, and the runtime's own parser and validation judge that as they judge any host's report. Vibe runs headless with only its `read_file` tool enabled; its code mode's `run_typescript` stays available and runs TypeScript in Vibe's own sandbox, which in the GLM 5.3 evaluation reached the workspace only through `read_file`, every shell call being denied, so a reviewer's executed evidence there comes from transcribed copies of the code rather than the project. It runs inside the same Windows job the runtime's host launchers use, so its termination is proven the same way; the launcher holds Vibe's output whole for parsing, so it stops the process and fails the attempt once its output passes 24 MiB, below the Windows job's own 32 MiB output capacity so that the launcher's check, which names the cause, fires first, rather than exhaust the harness; its tokens are the total in the `export.json` Vibe writes, and the attempt is attributed only when Vibe's session journal names the evaluated model. The runtime's records then name the gate candidate in each attempt and the evaluated host and model in the receipt, and the harness's result record names both, so a reader of either can tell which model ran. Grading and reports name the evaluated model. An evaluated host's figures are evidence for that decision only: the runtime's gate is unchanged, and its targets, like any model's, come from a baseline that includes it.

The harness keeps the contamination tokens below out of everything it supplies to a reviewer: it names each temporary repository with a neutral prefix and a random suffix, and refuses to start when `rules.md`, any selected fixture's `requirements`, any field of its decoys or any file of its `base/` or `change/` tree contains `seeded-defects` or `fixture.json`.

At the start of a run the harness copies each selected fixture directory, its `base/` and `change/` trees and its `fixture.json`, and `rules.md` into the run folder with their hashes, and both dispatching and grading read only that copy, so every model and repetition reviews the same project state and is graded against the truth it was dispatched with, whatever happens to the source fixtures meanwhile. The manifest is written last, so a run whose folder holds files but no manifest, as after an interrupted start, refuses to start rather than copy over them, since an overlay could keep files a source fixture has since dropped; the user removes the folder or names a new one. A resumed run and a grading both first recompute the fixture set hash over the frozen copy and the hash of the copied `rules.md`, and refuse the run folder when either differs from the manifest, so no later dispatch reviews, and no grading reads, a state the run did not start with. A resumed run, one whose run folder already holds a manifest, reads the same copy and neither loads nor checks the source fixtures or `rules.md`, so a source fixture removed, added or broken meanwhile cannot refuse it. Its arguments are checked as any run's are, a missing budget included, and its models, repetitions and fixture selection must equal the manifest's, where a run with no `--fixture` selection matches a whole-suite run folder and a selection matches a subset run folder of exactly those fixtures.

Each dispatch has its own temporary repository, materialized from the run folder's copy, so the skeptic's repository is a fresh one and the lead's receipt and event files, which the runtime writes inside the lead's repository, are never where the skeptic can read them. Materialization writes a random owner token into the repository's `.git` folder, outside the reviewed tree. Before each dispatch the harness writes an intent record naming the fixture run, the stage, the repository, its owner token and the identity described below that the dispatch runs under; the runtime writes its receipts and private copies inside that repository; after the dispatch the harness writes its own result record for it, with the error code and message when it failed and the tokens of every attempt, copies whichever of the receipt, `failure.json`, request and attempt event files the runtime created into the run folder, marks the intent done and deletes the repository, keeping it instead when the dispatch reports unproven termination of its host process. The harness deletes a repository, after a dispatch or a reconciliation alike, only when it is the repository that intent materialized: a directory directly under the temporary directory, carrying the harness's repository prefix, whose owner token equals the one the intent recorded. An intent is data in the run folder, so any other path it names is left in place, a directory of the same shape without the matching token included, and so is the repository of an intent that records no token. A dispatch that failed before any attempt launched a host spent no tokens, whatever partial artifacts the runtime left, such as its request directory and `request.json`, and its result record says so. The runtime begins an attempt, with an attempt folder and a null token placeholder, before its runner spawns the host, and every runner reports the spawned process through the dispatch's `onProcess` callback, so the harness tells the two apart by that callback: a failed dispatch whose callback never fired launched no host and spent nothing, whatever placeholders `failure.json` holds. Once a host launched, a failed dispatch with `failure.json` records its attempts' tokens, and one with neither receipt nor `failure.json`, as when the runtime's own write of `failure.json` failed, has unknown spending, with the consequences below. A reconciliation cannot observe the callback; it records a receipt or `failure.json` it finds, and treats a repository holding neither as a lost outcome, as described below. Each result record also carries the identity the dispatch ran under and its elapsed time. The identity has two parts a comparison holds equal: the review machinery hash, one hash over the path and content of every module Node has loaded once `internal/runtime/review.js` is required, which are the prompt and schema builders, everything they import and the host launchers, so that uncommitted edits to them are identified; and the hash of `tools/seeded-defects.js` and its evaluation launcher that dispatched it. It also has two informational parts: the checkout's commit and the version the host executable reports when the run invocation starts; the manifest keeps the versions of the run's first invocation, and a resumed invocation records in its dispatches the versions it finds, since a host can update itself between invocations. Apart from the temporary repositories, the harness writes only inside its run folder. It writes each of its JSON records, intents, results, blocking, completion, claims and supersession records among them, through a temporary file and a rename, so an interruption leaves the earlier record or none, never a partial one that every later resume would fail to parse.

Token accounting reads the `tokens` of every attempt the dispatch records, from the receipt's `attempts` when it succeeded and from `failure.json` when it failed. The budget is a stop line, not a guarantee: before each dispatch the harness stops when the tokens spent so far plus the largest single dispatch seen in this run, or 2,000,000 before any has completed, would exceed `--budget`. While every dispatch's spending is known, an overrun is therefore bounded by one dispatch's excess over that reserve, and is reported: every `run` returns its budget and its overrun beside its spending, including a run that completed after its last dispatch passed the budget. Once any spending is unknown or estimated, as below, no bound on actual spending holds: the report says so and gives the estimate, and the user decides whether a retry is worth that uncertainty. An attempt whose `tokens` is null makes the run's spending unknown: the harness stops before the next dispatch and the report marks the run's token figures incomplete. A run without `--budget` refuses to start.

A fixture run is graded incomplete for that model and repetition, never as a miss or a pass, when its lead dispatch fails or returns a report whose status is incomplete, such as one requesting probes, which this version does not execute; its skeptic is then not dispatched. A skeptic that fails or returns an incomplete report leaves the lead's figures graded and the run's skeptic figures incomplete: the run counts in neither false-positive figure nor in skeptic accuracy, since each of them counts verdicts, and the report lists it.

A dispatch whose host termination is unproven stops the run before the next dispatch, as an unknown token reading does, since the host may still be spending; the harness writes a blocking record naming it, its request id and the retained repository, and the report shows both. The blocking record is written before the stage's result record and before its intent is marked done, whether the outcome comes from the dispatch or from reconciling a pending intent, so an interruption at any point leaves either the blocking record or a pending intent whose reconciliation finds the same unproven outcome and blocks again. A rerun of a run folder holding a blocking record dispatches nothing until it is passed `--termination-checked`, the user's statement that the host process has ended, which the harness records beside the blocking record before resuming; a dispatch whose request id a confirmed record names then settles without blocking again, its repository still kept.

A fixture run's required stages follow from its lead's result: the lead alone when the lead failed, returned an incomplete report, or left no claims for a skeptic; the lead and the skeptic otherwise. When its last required stage is done, the harness writes a completion record for it, naming the stages it ran. A rerun with the same run folder resumes by these records. A fixture run with a completion record is skipped. One without resumes at its first required stage without a done intent, so after a done lead its skeptic is dispatched next; when every required stage already has a done intent, as after an interruption between the last intent and the completion record, the harness writes the completion record without dispatching. An intent not marked done is reconciled from its recorded repository, and its result record takes the identity the intent recorded, not the identity of the reconciling run, so a resume after a change to the harness or the review machinery still attributes the outcome to what dispatched it, and the report marks the run mixed when its dispatches then differ; an intent that records no identity, as one written before intents carried it, refuses the run, since its outcome cannot be attributed. A receipt or `failure.json` found there is copied and the intent completed, without dispatching again; a repository holding neither, or a missing repository, means the stage's paid outcome is unknown, so that stage is graded as if it had failed, a lost lead making the fixture run incomplete and a lost skeptic leaving the lead's figures and making the skeptic figures incomplete, and its spending is counted as the largest single dispatch the run has recorded, or 2,000,000 when it has recorded none, with the report marking its token figures as estimated.

A rerun passed `--retry` dispatches again every stage that is graded incomplete, whatever the cause: a known failure, an incomplete report, a lost outcome, or a contaminated fixture run, whose lead is retried; `run` decides contamination with the same rule and the same code that `grade` uses. A pass over a fixture run reconciles its pending intents before `--retry` reads its results, so an outcome that reconciliation finds lost is retried in that same pass. Each retried stage gets a freshly materialized repository and passes the same budget check as any other dispatch. A retried lead also discards that fixture run's earlier skeptic result, since the skeptic's claims come from the lead. Before any retried stage's intent is written, the harness creates a new folder under the fixture run's `superseded/`, named by its timestamp and a random suffix and never reused, so two supersessions with the same timestamp stay apart, writes into it a moving record naming the superseded stages and the cause, moves into it the fixture run's completion record, the superseded stages' intent and result records and artifacts, and the claims record when the skeptic is superseded, and only then writes its cause record, naming the cause and the superseded stages that had records, and removes the moving record. The moved records are kept for audit, their tokens still counted in the run's spending; grading takes findings, verdicts and figures from the latest records only, while the check for a mixed run reads every result record, superseded ones included. Every pass over a fixture run first finishes any supersession whose folder still holds a moving record, moving whatever of its stages' records remain in place, before it reads any stage, so an interruption at any point of the move never leaves a stage half moved, as a result left in place without its intent would be dispatched over and its tokens lost from the spending; an interruption after the move leaves a fixture run with no completion record and no records for the retried stages, which the resume rules above already cover. Without `--retry` a rerun dispatches nothing that already has an outcome, so a run folder can reach a baseline with no incomplete fixture runs without starting over.

## Grading

`node tools/seeded-defects.js grade <run folder>` grades from the saved artifacts, with no model as grader and without dispatching, so grading can be repeated and its rules changed without paying again.

- Matching is one to one. A lead finding is a candidate for a truth entry, planted, out of scope or incidental, when its evidence or consequence text names the entry's file and either a line inside its range or within three lines of it, or, in its evidence alone, the entry's symbol, since a consequence names callers and other sites in passing. The candidate pairs are ranked by distance, zero for a line inside the range or a named symbol and otherwise the line distance, then by the finding's position in the report, then by the entry's position in `fixture.json`, and assigned in that order, skipping a pair whose finding or entry is already assigned. Findings left over are unmatched.
- Detection rate: planted defects with a matched finding, over planted defects, overall and per dimension.
- False positives: two figures, reported separately. Clean-change false positives are unmatched findings the skeptic confirmed on clean fixtures, per clean fixture, the worklist item's "findings confirmed on changes with no defect"; a finding matched to an out-of-scope entry is true and never counts. Unmatched confirmations are unmatched findings the skeptic confirmed on every fixture that is not clean, per such fixture, so a fixture whose only truth is incidental still counts. The report lists every unmatched lead finding, whatever the skeptic's verdict: `report.json` names each fixture run's unmatched findings, adjudicated or not, and both it and the Markdown report name those still awaiting adjudication. The maintainer adjudicates each, recorded with a reason in the run folder's `adjudications.json`, as one of three outcomes; grading refuses the run folder when any adjudication in the file names any other outcome or gives no reason, whether or not its finding is unmatched, since a misspelled outcome would otherwise settle a finding silently. False: it counts in the false-positive figures when the skeptic confirmed it, and in no figure otherwise. Attributed: it reports an existing truth entry, named by id, that location matching missed, as when a defect is reported at its symptom rather than its line or reported twice; if that entry has no matched finding the attributed finding is assigned to it and counts as its match in every figure, and otherwise it is a duplicate that counts in no figure; the report gives the number of attributions, so matching misses stay visible. Real: it is an issue no truth entry describes, so the fixture's audit missed it; it counts in no false-positive figure for that run, and its fixture is not clean for that run. Every figure of a run is marked provisional until every unmatched lead finding has an adjudication, since an attribution changes detection, severity and skeptic figures as well. The run folder's frozen copy is never edited; the run's figures come from that copy plus its adjudications. Grading reads `adjudications.json`, so the figures stay code-computed while the judgment of an unforeseen finding stays the maintainer's. A real adjudication also tells the maintainer to correct the source fixture by hand, adding an `incidental` entry or reworking the fixture, which the loader validates like any fixture edit.
- Out of scope: out-of-scope entries with a matched finding, over out-of-scope entries, reported with how many of those findings carry `required` false. The flag is the reviewer's advisory view, not a disposition, so this version reports it without grading it.
- Severity accuracy: matched planted defects whose finding's severity equals the planted severity, over matched planted defects.
- Skeptic accuracy: verdicts that agree with the truth, confirmed for a finding matched to a planted or out-of-scope entry and refuted for a decoy, over all verdicts on such findings and decoys. An unverified verdict counts as disagreement.
- Tokens and time per fixture: the lead's and the skeptic's attempt tokens summed, and their elapsed times summed, with incomplete figures marked. A fixture run never dispatched, as when the budget stopped the run before it, is incomplete and counts in neither average, since it has no cost to average.
- Contamination: a fixture run whose attempt event files mention the suite's directory name `seeded-defects` or a fixture's file name `fixture.json` is reported as contaminated and left out of every rate, since the reviewer may have read planted truth.

The report is `report.json` in the run folder, with a Markdown summary, `report.md`, beside it. The summary prints the shortened fixture set, conventions and grader hashes, whether the run is a subset or mixed, a table of the figures per model and pooled, with numerators and denominators for the rates and averages for tokens and time per fixture, a token average marked incomplete or estimated when it is, the targets, an active block, the incomplete, contaminated and skeptic-incomplete fixture runs, the retried stages and the findings awaiting adjudication; the spreads, the dispatch identities and detection per dimension are in `report.json` alone. `report.json` gives each figure with its numerator and denominator per model and pooled, the spread across repetitions where `--repeat` exceeds one, the fixture set hash (one hash over the frozen copies of the selected fixture directories, not `rules.md` and not the adjudications), the conventions text's hash, the hash of `tools/seeded-defects.js` that graded the report, the dispatch identities from the result records, the incomplete and contaminated fixture runs, an active blocking record with its dispatch and retained repository, the fixture runs whose lead left claims but whose skeptic is not complete, and the number of retried stages per model and per cause (known failure, incomplete report, lost outcome, contamination), a supersession of both stages counting as two when both had records, so that a figure computed after retries shows how many first attempts it replaced. When a run's dispatches, superseded ones included, do not all share one review machinery hash and dispatching harness hash, as after a resume or a retry across a change to either, the report marks the run as mixed and lists them; differing commits or host executable versions are listed without marking it mixed.

## Acceptance of later changes

The first baseline runs each fixture twice per model, on Opus 5.5 on Claude and Sol on Codex, so the report shows how much the figures move between identical runs. It was preceded by smoke runs of three fixtures, one repetition each, two on Opus 5.5 and one on Sol, which validated the harness against live hosts and gave the first per-dispatch token figures; the smoke runs and the baseline together ran under a budget the user set at 16,000,000 tokens and raised on 2026-10-23 to 17,000,000 before the baseline started and to 24,000,000 during it; the smoke runs spent 1,418,391 tokens and the baseline 18,393,718. The user sets targets from a baseline, as the worklist item asks, for the figures the user chooses; those set on 2026-10-24 cover detection, both false-positive figures, severity accuracy, skeptic accuracy and tokens per fixture, and leave out of scope, time per fixture and detection per dimension without a target. The targets are recorded in `tools/seeded-defects/targets.json` with the baseline report they were set from and its fixture set hash. Targets can be set only from a whole-suite baseline that is not mixed, has no incomplete or contaminated fixture runs, has figures that are no longer provisional and has no finding adjudicated real; a baseline with one shows that a fixture's truth was incomplete, so the maintainer corrects the fixture and runs the baseline again, and until then no figure has a target. A later report on the targets' fixture set hash shows its figures against them, whatever its own adjudications, which affect only its own figures; a report on a different hash, as after any fixture is corrected or added, shows the targets as stale and compares nothing with them until the user sets targets again from a baseline on the new hash. The first baseline had findings adjudicated real, so the fixtures were corrected and extended, and on 2026-10-24 the user set the targets from an Opus 5.5 baseline over the corrected suite, recorded in [the seeded-defect baseline report](../reports/seeded-defect-baseline-20261024.md). Targets are keyed on the fixture set hash alone, but a comparison holds the dispatching harness hash equal, so after any change to the harness a later change is compared against a new baseline dispatched by the current harness on the targets' fixture set; the harness changed after the 2026-10-24 baseline, so the next comparison needs that new baseline first, while the targets stay current.

`node tools/seeded-defects.js compare <baseline run folder> <later run folder>` compares two graded run folders from their `report.json` files and prints the comparison report as JSON on standard output, writing nothing. A later change is compared on the same fixture set hash, with every input the Outcome section names held equal except the one the change alters, as the recorded identities show: a prompt change keeps the models and the conventions hash, a model change keeps the review machinery hash and the conventions, and a conventions change keeps the machinery and the models, the dispatching harness hash being held equal in every case. Commits and host executable versions are informational: the comparison report lists any difference in them beside the figures without calling the comparison confounded, since unrelated commits land and hosts update themselves; both reports are graded by the same grader hash, regrading the older run from its saved artifacts when the grader changed. A comparison whose recorded identities differ in more than the varied input, including any difference in the dispatching harness hash, or that uses a mixed run or a report with incomplete or contaminated fixture runs or runs without a complete skeptic, whose figures then cover a different sample, is reported as confounded, and one that uses a report whose figures are still provisional is reported as provisional. The same models named in another order count as the same models. The comparison report names the varied input and gives, for detection overall and per dimension, both false-positive figures, out of scope, severity accuracy, skeptic accuracy, and tokens and time per fixture, each figure's baseline and later values and change beside the baseline spread and the targets; a change no larger than the baseline's spread between repetitions is reported as no measured effect. The report records each of these figures' spread across repetitions per model, so a baseline of one model run at least twice supplies it and a pooled baseline of several models does not, and the targets are those `tools/seeded-defects/targets.json` holds when the comparison runs, when they are current on the later report's fixture set hash, not the snapshot the later report took when it was graded. Whether to accept a change stays the user's decision on that report, since detection, false positives, severity, skeptic accuracy and tokens can move in different directions; the suite supplies the numbers, not the verdict.

## Prior tools

Anthropic's evals cookbook and its test-and-evaluate guidance recommend code-based grading wherever a ground truth exists, which this suite follows. `claude plugin eval` runs a full Claude Code agent session per case against a plugin, scored by per-case graders, some of them model graders, and reaches neither a Codex host nor the runtime's `dispatchReview`, so it cannot drive one review dispatch through the runtime's own prompt and schema on both hosts; the suite therefore has its own harness.

## Severity rubric

Critical: the defect loses or corrupts data or state, breaks a security or authority boundary, or lets a gate pass that should refuse. Important: the defect gives wrong behavior on a path the agreed outcome covers, or breaks a stated requirement, without the critical consequences. Minor: the defect is real but leaves agreed behavior intact, such as a misleading message or a missed simplification. Planted severities follow this rubric; defining severity in the review prompt is a separate later change that the suite then measures.
