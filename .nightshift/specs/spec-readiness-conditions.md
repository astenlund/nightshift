# Spec readiness as a condition

## Outcome and authority

A code task that names a governing spec proceeds while that spec's independent assessment is pending, stale after an edit, or awaiting the reviewer's applicability call. Spec readiness holds only the task's completion and the run's completion, and status names the condition, its cause and the way forward at every point before them. This is part five of step 3 in [the assessment worklist](../reports/assessment-worklist-20261018.md), following [Implement beside the spec review after a broad-strokes pass](../features/implement-beside-spec-review.md), and it closes that record's carried fix, [the spec amendment that blocks its code task](../bugs/spec-amendment-blocks-code-task.md), including both further reaches that record names. [Assessment change conditions](assessment-change-conditions.md) is the design context; this spec replaces its statement that the bounded implementation retains the legacy spec-readiness prerequisite.

## Commitments

1. **Where readiness holds.** Spec readiness, as defined in commitment 2, is required by every transition that completes a `code` task, whether `advance` from documentation or a reopened task's return from review straight to completion, and by run `complete`, each refusing `spec-review-required` with the cause commitment 5 defines. No other action refuses on spec readiness: `start-task` and every task action today's `assertAction` holds on it (`check`, `dispatch`, `probe`, `validate`, `dialogue`, `dispose`, `repair` and `advance` short of completion) proceed whatever the spec's assessment state. Other conditions are unchanged. The scope of a finding raised by a code or docs review includes the governing spec of every task its review covers, as part three shipped it, and a finding with no saved scope falls back to the whole-project comparison, so any edit to the spec, a compatible correction included, still stales the validations of those findings, and `dispose` of them refuses `stale-validation` until a fresh skeptic validates them again; a finding already disposed for implementation keeps its disposition, and its `repair` proceeds, since `repair` checks commitments and not receipt currency. The need to revalidate undisposed findings after a spec edit is the remainder of the worklist's "a repair of an unrelated finding proceeds" this spec leaves open, recorded as the instruction and reference section says. A code task whose `requires` names its spec task still waits for that task under `dependency-blocked`, since the queue's declared dependency is the user's agreement and not a spec-readiness hold. Review contexts and tasks whose agreement has no `spec` key are unaffected, as today. A code task already complete when its spec changes is not reopened; the run's completion holds instead.

2. **What readiness is.** A code task naming a spec is ready when one of these holds:
   - its agreement carries `specReviewed: true` with no link in either place commitment 3 names and a single-file `specSnapshot` of that spec that still matches, as today; when that snapshot is missing, malformed or no longer matches, readiness falls through to the governing spec task of commitment 3; while it matches, the task is ready whatever the state of a queued spec task commitment 3 resolves, which status still names as `specTaskId`;
   - its governing spec task, as commitment 3 resolves it, is `complete`, names the same spec, and its lead assessment passes the spec task's review gate with checks left out. The gate's applicability rule replaces the separate whole-snapshot comparison `specReady` adds today, so a preserving relevance decision from the spec's originating reviewer or its independent replacement settles a compatible spec edit. Today's acceptable-assessment check stays beside the gate, so the assessment must still match the spec task's current requirements revision and commitments, and no relevance decision covers a material amendment. A reassess or unresolved answer, a requirements revision the assessment predates, an unsettled or unclosed spec finding, or a structural failure leaves the task unready.

   The spec task's own checks stay its own obligation and are verified at run completion with every other task's, so a failing check on a complete spec task no longer holds the code task, its completion included; an incomplete spec task still needs its checks to complete, and until it completes the code task's completion is held because the spec task is not complete. An agreement naming a spec with no route that holds is unready. `add-spec-review` is the way forward only when the task has no link and commitment 3 finds no governing spec task, the missing and ambiguous cases; when a spec task governs, the way forward is to complete, assess or obtain the applicability call for that task, never to create another, and `add-spec-review` on a task that a unique queued spec task governs refuses with the existing `duplicate-task` code, naming that task, and on a task whose `spec` value is unusable refuses `missing-spec`, as it already does for an absent one.

3. **Which spec task governs.** A code task's link is `agreement.specReviewTaskId`, which handover may supply, or the link `add-spec-review` records. From this release `add-spec-review` records its link as the task's own `specReviewTaskId` field, holding the spec task's id with the same grammar as its sibling inside the agreement, beside the agreement rather than inside it and leaves `specReviewed` untouched, for the reason `spec-accepted` already records beside it: every validation, and every assessment covering the code task, binds the whole agreement, so a write there would stale them and refuse an unrelated `repair` or `dispose`, which commitment 1 now lets run before readiness. Records written earlier keep the link inside the agreement, and every reader of a link reads both places, the one beside the agreement first; an absent or falsy value is no link, as today, and any other value that does not resolve is an unresolvable link. For a code task whose agreement names a spec, `handover` now refuses `invalid-queue` when that agreement's `specReviewTaskId`, other than an absent or falsy value, does not name a queued task of kind `spec` with the same `agreement.spec`, or names one that requires the code task, directly or through other tasks' `requires`, which would hold each task on the other; it also refuses `invalid-queue` for a `specReviewTaskId` key with any value placed on a handover task outside its agreement, which handover would otherwise drop silently, since it accepts the link only inside the agreement. A link inside the agreement of any other task is accepted unchecked, as today. Opening a review context applies none of these refusals. With these checks at handover, an unresolvable link is possible only in records written before this release, since links are never rewritten, tasks never removed and a spec file that later goes missing is reported by its own cause below rather than as an unresolvable link, with one further exception: a link accepted as a case variant becomes unresolvable if the filesystem later stops establishing file identity, as when a checkout moves to a share without inode numbers; status's agreement echo keeps reporting as `specReviewTaskId` the link read from either place, never an inferred queued task, which `specReadiness` reports as `specTaskId`. `add-spec-review` on a task already ready through a fresh `specReviewed: true` still creates and links its task, as today, and the new link then governs, unless a unique queued spec task governs, when it refuses as commitment 2 says. The linked task governs when present; an unresolvable link, one naming a missing task, a task of another kind, a spec task over a different spec or a spec task that requires the code task directly or through other tasks' `requires`, leaves the code task unready with a structural cause, since `add-spec-review` does nothing for a linked task and no runtime operation repairs a link; its way forward is the user's decision on the run, because no operation settles the condition until part six ships. Without a link, the run's single queued spec task over the same spec governs: a task of kind `spec` that no task of any kind links in either place, the same notion of linked the acknowledgement scope hash uses (a linked task is internal and left out of the acknowledgement scope hash, and one a code task links also completes without a documentation stage, while a queued task is one the user agreed in the queue; a spec task linked only by a task of another kind is therefore neither queued nor internal to `advance`, governs no code task and keeps its documentation stage, as today; so a sibling code task over a spec another code task linked needs its own assessment, a deliberate cost a controller avoids by queueing one spec task for the siblings and linking none of them to it, neither at handover nor through `add-spec-review`) and that does not itself require the code task, directly or through other tasks' `requires` (such a task follows the code task in the queue, as an as-built update does, and governing by it would hold each task on the other), whose `agreement.spec` names the same file as the code task's `agreement.spec`. Every comparison of two spec paths this spec makes, in the queued route, the linked route's same-spec check, the handover check and historical discharge, matches when the two strings are equal or, when both files exist, when their file identities are equal, as the assessment gate's governing-input check compares them through `fileIdentity` in `internal/runtime/evidence.js`; since the path grammar already refuses `.`, `..` and other alternate forms, the second clause admits case variants of one file on a case-insensitive filesystem. An identity that cannot be established counts as no match, never a match. Historical discharge, which judges recorded evidence, therefore keeps a run discharged by string equality whatever happens to the files later, and a run discharged only through matching identities becomes undischarged if a spec file it matched is later removed or renamed, an accepted consequence. Before any link or governance comparison, a code task whose governing spec file is missing is unready with that cause of its own, whose way forward is restoring the file, or otherwise the user's decision on the run as for the two causes no operation repairs, since no operation rewrites `agreement.spec` and an amendment leaves the cause in place. With none, or with more than one, none governs, and the cause says which. Governance is itself a dependency, since a code task's completion waits for its governing spec task, so `requires` edges and governance edges together must stay acyclic: `handover` refuses `invalid-queue` when, after this resolution, they form a cycle through several tasks, and in a record written earlier a linked spec task on such a cycle is an unresolvable link, while a queued spec task on such a cycle governs none of the code tasks whose governance edges lie on it, which then have no governing spec task. One queued spec task can govern several code tasks over the same spec; a user-decision amendment on any of them reopens it under commitment 4 and so holds the completion of every code task whose readiness rests on it until its fresh assessment. The resolution is read each time and persists nothing, so existing records need no migration. A session bound to an earlier release keeps its own runtime for delivery creation and reads neither the link beside the agreement nor the queued route, so its historical discharge refuses a run completed under this release through either, unless the code task also carries `specReviewed: true` with its recorded snapshot, which the older reader accepts instead; such a session restarts on this release before handing over again, which the release notes and the runtime reference state.

4. **Amendments and acceptance.** The changes below apply to a user-decision `unblock` on a code task; on a task of another kind it keeps today's effects unchanged. A user-decision `unblock` on a code task, with or without `updatedOutcome`, keeps today's effects: it advances the code task's requirements revision, records the decision and reopens a linked spec task, now only when that task governs under commitment 3, a structural link being left untouched. As new effects, it clears `specReviewed` on a task naming a spec whether or not a link exists, and when no link exists it reopens the queued spec task that governs under commitment 3, if any, even when the `specReviewed: true` route held before the amendment, recording the decision on it and advancing its requirements revision as it does for a linked task. Every user-decision `unblock` stays material, as today, so this new reopening inherits the open bug [Permission-only recovery invalidates accepted specs](../BUGS.md#permission-only-recovery-invalidates-accepted-specs), which reopened an accepted spec task when only a permission or a budget changed and advanced the requirements revision on an execution-hold release; the bug stays open, and its resolution narrows the linked and queued routes alike. A material amendment therefore never leaves readiness standing on an assessment that predates it, by any route. The handover acknowledgement's scope hash includes an unlinked queued spec task, so its renewal at `unblock` is computed after every spec-task change, keeping the renewed obligation current. Under commitment 1 the code task keeps working meanwhile, unless a declared dependency holds it: a code task whose `requires` names the reopened spec task, and every other task that requires it, waits under `dependency-blocked` until that task completes again, checks included, as a deliberate consequence of the queue the user agreed. Otherwise only its completion waits for the reopened spec task's fresh assessment. A compatible correction to the spec text moves no requirements revision and, where a spec task governs, is settled through the spec reviewer's applicability call at the completion boundary, or a fresh assessment when that call asks for one. On the `specReviewed: true` route there is no assessment in the run to call applicability on, so a compatible edit falls through to a unique queued spec task or, without one, needs `add-spec-review` and a fresh whole-spec assessment; this is a deliberate limit of this part, which a controller avoids for an amendment it expects by settling the spec through a spec task in the run. On any spec task, importing a fresh assessment of changed spec text, or any import that raises findings, resets closing evidence and returns the spec task to review as the review import does today, which this spec leaves to part four and step 3b. `spec-accepted` gates nothing, as today; status reports whether the user's recorded acceptance covers the spec's current content beside the readiness condition, so an accepted amendment reads differently from an unaccepted one. Until [the recorded-decision operation](../features/manual-gate-bypass.md) ships under step 3's part six, neither the user's acceptance nor a recorded decision settles a hold by itself: each cause is settled only by evidence, such as a reviewer's applicability call, a fresh assessment, restored spec content, the spec task's completion with its findings settled, or `add-spec-review` followed by an assessment where no spec task governs. The exception is the two causes no operation repairs, an unresolvable link and an unusable `spec` value, whose way forward is the user's decision on the run, and a missing spec file that is not restored, which takes the same way.

5. **Status.** Spec readiness no longer substitutes a `governing-spec-review` stage for a listed task's stage, and that label retires; the continuation-observation override is unchanged. A delivery's status gains a run-level `specReadiness` list with one entry `{taskId, ready, specTaskId, cause, next, specAcceptance}` for every code task whose agreement has a `spec` key, completed tasks included and an empty, whitespace-only or non-string value given a structural cause, since run completion still holds on them after they leave the brief's `next` list; a review context's status and a closed record's status omit it. `specTaskId` is the governing spec task under commitment 3 or null; `cause` is null when ready and otherwise one sentence naming why, for every way commitments 2 and 3 can leave the task unready, including: no assessment route, meaning no link, no matching reviewed snapshot and no governing queued spec task, with its sub-cause (no reviewed snapshot or a stale, missing or malformed one, and no queued spec task, several, or one over this spec excluded because it requires this task or lies on a dependency cycle); an unresolvable link (one naming a missing task, a task of another kind, a spec task over a different spec, a spec task that requires the code task, or one on a cycle of `requires` and governance edges); an unusable `spec` value, possible only in records written before handover validated it; a missing governing spec file; the spec task not complete, blocked or held by an incomplete upstream task, the assessment stale, awaiting applicability or answered reassess or unresolved, with the changed paths, a requirements revision it predates or commitments it no longer matches, no complete assessment, a missing dimension, a repair after the latest review, unsettled or unclosed spec findings, and a structural failure; `next` is null when ready and otherwise the way forward for that cause: for a missing governing spec file, restoring it, and otherwise what follows for the two causes no operation repairs; for those two, an unresolvable link and an unusable `spec` value, a request for the user's decision on the run that names, for a code task not yet complete, blocking it with kind `user-decision`, so the run pauses on the user through the existing blocker, whose later `unblock` is material and so inherits the permission-only bug commitment 4 cites, and for every code task `hold`, `stop` and the administrative `close` once stopped, where the runtime reference admits it, as what the controller can do on that decision until part six ships; for a spec task that is blocked or held upstream, the blocker or the incomplete upstream task; and for a structural failure of the assessment comparison the applicability condition's own way forward; `specAcceptance` is the same `{recorded, current}` reading status gives listed tasks today, so commitment 4's acceptance report reaches completed tasks too. With freshness verification skipped, the whole `specReadiness` list reads `'reconcile at acceptance'`, as `staleChecks` does. The `spec-review-required` refusal carries the same cause and way forward. Status inspection writes nothing.

6. **Scheduling stays guidance.** The rule that the main cumulative code review normally waits for the spec task to settle, with the reasoned early exception, remains controller guidance; the runtime neither refuses nor records that choice. The brief, skill and workflow sentences that order implementation after resolved spec assessment, and the broad-strokes pass, ride the brief rewrite of step 6, as the feature record says.

## Instruction and reference text

Every statement of the runtime's spec-readiness behavior changes with it, found by a sweep for the claim (readiness, the governing-spec prerequisite, whole-spec reassessment of a changed spec or governing artifact, `spec-review-required`, the `governing-spec-review` stage, `specReviewed`) across `internal`, `skills`, `hooks`, WORKFLOW.md, VISION.md, README.md, [assessment change conditions](assessment-change-conditions.md) and the backlog records under `.nightshift` that state current runtime behavior (among them the feature record's Problem paragraph and the degraded-assessment record's account of `specReady`), each hit classified by its whole paragraph: a statement of what the runtime refuses or requires is updated; ordering guidance for the controller is left for step 6 and named in the release notes. Known hits include the runtime reference's handover paragraph ("Changed spec content requires whole-spec reassessment"), its `unblock` paragraph on reopening a linked governing-spec task or clearing `specReviewed`, its statements that a changed governing artifact needs whole-spec reassessment and that the legacy spec-readiness prerequisite remains at run completion, the operating brief's legacy-prerequisite sentence and its statement that the remaining spec-readiness barriers stay, WORKFLOW.md's "legacy readiness and stage prerequisites" and its statement that the bounded implementation retains the legacy spec-readiness prerequisite, and the design context's matching sentence. The runtime reference documents `specReadiness`, the retirement of the `governing-spec-review` stage, the queued-task resolution, where `add-spec-review` records its link and its refusal while a queued spec task governs, and handover's refusals of a link that does not resolve, depends on its code task or sits outside the agreement, with the values that count as no link. A spec task's own repair loop keeps whole-spec reassessment; that rule is untouched. When the release ships, the worklist records part five as shipped except the revalidation remainder commitment 1 names, which it records as open, and notes that settling a hold by the user's acceptance or by a recorded decision rides part six, as its note of 2026-11-10 says; the carried line leaves the feature record's `## Carried fixes`, and, since no existing route covers a carried fix closing while its feature stays active, BUGS_HISTORY.md records the fix with a link to the bug record as a deliberate choice; the feature itself stays active. The operating brief's "revised specs receive whole-spec assessment", WORKFLOW.md's "A revised spec likewise receives another whole-spec review" and the revise-spec skill's whole-spec reassessment after each repair batch are scoped in the same release to a spec task's own repair loop: an edit to the spec text made from a code task, such as a deferred spec finding repaired there, is a compatible correction settled as commitment 4 says for its route, or a material amendment through the user-decision route. WORKFLOW.md's "it returns to the reviewer as a whole like any revised spec", about an amendment while the run is open, is scoped the same way in the same release; its "a revised spec returns to the reviewer as a whole", about drafts before handover, is unchanged.

## Lifecycle and consumers

The one new persisted field is the link `add-spec-review` records beside the agreement under commitment 3; its lifecycle (created by `add-spec-review`, never refreshed or cleared, read by every link reader beside the older field inside the agreement, a malformed or dangling value giving the structural cause) is defined at its governing module, and no schema migration is required. The implementation enumerates every reader of a link and of spec readiness, including status, task completion, run completion, historical discharge (`historicalDischarge`, which keeps its own copy of the readiness routes and which delivery creation reads, so a run completed through an inferred spec task must stay discharged), the acknowledgement scope hash, the progress fingerprint and status's agreement echo, which name the link, `unblock`, `advance`'s completion of an internal spec task without a documentation stage, and any progress or reminder consumer of the stage label; and every writer of the state those readers use, including `handover`, `add-spec-review`, `dispatch` (whose registry order selects the latest assessment and decision the gate reads), `start-task`, `block`, `unblock`, `review`, `validate`, `dispose`, `repair`, `advance` and `spec-accepted`. It settles each reader's behavior when the governing spec task is absent, ambiguous, dangling, pending, reopened, stale, unreadable or complete. A failed or structurally broken comparison leaves the task unready with a structural cause, never ready.

## Verification and release

Deterministic tests cover:

- each formerly refused action proceeding on an unready task, and a code task whose `requires` names its spec task still held by `dependency-blocked`;
- completion refusing with the named cause on both completing paths, `advance` from documentation and a reopened completed task's return from review, and run completion refusing likewise;
- a compatible spec edit settled by a preserving relevance decision and held by reassess, unresolved and absent ones, and completion held by an unsettled or unclosed spec finding and by a structural comparison failure;
- `add-spec-review` on a started code task that has no assessment route, leaving its validations and code assessments current, so a later `dispose` and `repair` of an unrelated finding proceed; a spec edit staling the validations of findings bound to that spec: `dispose` of an undisposed finding refusing `stale-validation` until it is validated again, while `repair` of a finding disposed before the edit proceeds; and then, for a completed code task, readiness reached through the new spec task; `add-spec-review` refusing while a unique queued spec task governs; a record whose link sits inside the agreement still resolving; a link recorded beside the agreement that leaves the acknowledgement scope hash unchanged, so a later engineering action through the full `execute` path passes, lets its spec task go from review straight to completion without a documentation stage, and appears in the progress fingerprint and in status's echo as `specReviewTaskId`, and a run completed through it remaining historically discharged, so a later delivery can be created; a code task whose `spec` key holds an empty, whitespace-only or non-string value, with its structural cause, and `add-spec-review` on it refusing `missing-spec`; two code tasks governed by one queued spec task, where an amendment on one holds the other's completion too; a queued spec task that requires the code task, directly and through another task, not governing it, with the cause naming that exclusion; a queued spec task naming the code task's spec under another spelling of the same path governing it, and a link likewise accepted at handover; a spec-path comparison whose file identity cannot be established counting as no match; a spec file deleted after a link under another spelling was accepted, reported as a missing spec file with restoring it as the way forward, a user-decision amendment leaving that cause in place, and the task ready again once it is restored; a run completed through a queued spec task under the same string, then its spec file deleted, still historically discharged;
- a material amendment followed by a preserving relevance decision on the old spec assessment, which must leave completion held until a fresh assessment;
- a user-decision amendment reopening a linked spec task while the code task keeps working, and holding under `dependency-blocked` a code task whose `requires` names that spec task;
- the unique queued spec task resolved as governing and reopened by an amendment; the missing and ambiguous cases reported with their cause and a `next` naming `add-spec-review`; a spec task linked by another code task not counted as queued;
- a dangling link, a link to a task of another kind and a link to a spec task over a different spec, each left untouched by a user-decision `unblock` and reported with its structural cause and a `next` naming the user's decision with a `user-decision` block for an incomplete code task and `hold`, `stop` and `close`, and for a completed code task without the block, the unusable `spec` value likewise; `handover` refusing `invalid-queue` for each of those three link kinds, for a link to a spec task that requires the code task directly and through another task, and for a `specReviewTaskId` outside the agreement, while accepting an absent or falsy link as no link, which resolution also treats as no link, and accepting unchecked a link on a task other than a code task naming a spec; `add-spec-review` doing nothing for a task already linked in either place; a spec task linked only by a docs task not counted as queued; status's echo staying null while `specTaskId` names an inferred queued task; and a record holding different links in both places resolving the one beside the agreement; `next` naming the governing queued task rather than `add-spec-review` while that task is pending or stale;
- a user-decision amendment on a code task governed by an inferred queued spec task, which must reopen that task, leave the code task unready and, once the renewed acknowledgement is observed, let a later `check` on the code task pass with the scope hash current; and the same amendment on a code task that started with `specReviewed: true` beside a unique completed queued spec task over the same file;
- `add-spec-review` on a code task ready through a fresh `specReviewed: true` with no queued spec task, after which readiness is held on the new spec task, `specReviewed` stays `true` and `specTaskId` names the new task;
- a queue in which two code tasks' governing spec tasks each require the other code task refused `invalid-queue` at handover, and the same shape in an older record reported as described for a linked and for a queued spec task;
- a governing spec task that is blocked, or held by an incomplete upstream task, with `next` naming the blocker or that task;
- `specReviewed: true` fresh beside a pending unique queued spec task, ready with `specTaskId` naming that task; and stale, missing or malformed, each falling through to a unique queued spec task and to none;
- a user-decision `unblock` on a docs task naming a link or a spec keeping today's effects;
- a failing check on a complete spec task no longer refusing code-task actions or code-task completion while still failing run completion;
- a completed task's `specAcceptance` entry before and after `spec-accepted` on amended content, with readiness still held;
- a spec edit after the code task completed, through both the spec-task route and the `specReviewed: true` route, reported in `specReadiness` while the brief's `next` list is empty;
- a run completed through an inferred spec task remaining historically discharged;
- status fields with and without freshness verification, and their absence in a review context and a closed record;
- an existing record from before the change, including one whose link names a spec task that requires its code task, reported as an unresolvable link and left untouched by a user-decision `unblock`.

Every existing test that expected the old behavior, the refusals, the stage label and the link inside the agreement after `add-spec-review`, is updated to the new boundary, not deleted. The change ships as its own 3.3.x release with a CHANGELOG entry stating its instruction word change as step 6's interim rule requires; whether it ships through a handed-over run or direct work, and any installed-host evidence, are decided when the work starts, with model-owned behavior marked unverified.
