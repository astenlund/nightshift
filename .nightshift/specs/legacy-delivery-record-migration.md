# Legacy delivery record migration

## Intent and boundary

Nightshift provides a reusable way to retire delivery records saved without independent schema-2 accounting by an older retained release, regardless of when the record was written. Retirement is an explicit user disposition of historical obligations. It does not manufacture accounting provenance or assert that a completed status proves discharge. The original run state, history and artifacts remain stored. A new handover is allowed only after every surviving delivery is either authenticated by the current creation gate or covered by a current, valid legacy retirement decision, and the selected delivery has no separate pending report obligation.

This feature applies to delivery stores in any project, including stores containing both legacy and current records. It never treats a schema-2 record with lost provenance as legacy. It does not alter a retained older runtime, resume a stopped legacy run, repair contradictory historical evidence, or delete historical rows. Retired records cannot be resumed or amended through the new runtime. [Reactivation of retired work](../features/retired-delivery-reactivation.md) is Exploring and outside this feature; until a separate route exists, preserved evidence is the recovery source and retirement remains an explicit choice.

## Administrative route and admission

The installed current-release launcher exposes inventory, approval manifests, bounded raw inspection and retirement through a narrow administrative migration entry, without adding a ninth public skill. Its bootstrap and service select the current enabled administrative bundle for that entry even when the caller's session or the selected historical run is bound to an older release. They preserve an existing binding's release identity and bundle, though admission may add the project to its project list; ordinary runtime execution, hooks and continuation keep their exact retained bundle. The current bootstrap routes handover and older `create` resource resolution and run requests through the current service regardless of whether retirement has happened yet. That service may still select the original bound runtime for an eligible replay. Routing every creation request through it removes the preliminary-retirement-probe window before older-service admission. When any retirement reference exists, a handover with tasks and an absent or different handoverId takes current creation admission even when runId names the requested record. A nonempty identity matching the saved acceptance is eligible for retained-runtime replay of an unretired record; the existing no-selector replacement rule still applies to a completed or fully stopped selected record. An exact replay of a running record or other nonreplacing action still executes its original bound runtime. Retained bootstrap files from older releases cannot acquire this new check; callers must use the current bootstrap returned by preparation, but retirement's database triggers protect only retired IDs and do not stop insertion of another run or a change of active selection through an older launcher. A session first admitted through migration receives a normal current-release bundle binding; when any retirement reference exists, an older bound session needs a new native session for every delivery-creating handover classified as new-run work, including a nonmatching identity or a matching replay without runId of a replaceable selected record, even if a later overlap or identity check would refuse it. Through the current bootstrap, an exact acceptance replay targeting any retired record also takes this new-run admission path, whether or not the request names that run by runId, so an older bound session receives migration-new-session-required before its retained runtime runs; a nonselected target remains refused before mutation, either at release admission or by a runtime identity or consistency check. The entry accepts only the documented migration actions, never arbitrary runtime actions. An absent current installation or administrative route is a diagnosed capability limit, not a reason to select checkout code or reinterpret the old run as current.

A plain-language request to migrate legacy delivery run records uses the existing handover skill as a discoverable route. Its migration branch prepares entry migration through the current installed release, reads the administrative contract from that release, and leaves the delivery steps without accepting handover or creating a run. Backlog-index migration remains with init-backlog; an absent compatible installation leaves the request pending rather than using checkout code.

Read-only inventory checks project identity and installation enablement; raw inspection also checks its exact requested run ID. Neither claims the historical run. Retirement additionally requires an authenticated live native session, permitted operation, the exact user decision and manifest, project writer serialization, and positive evidence that no relevant worker or operation is active or uncertain. Missing identity, owner, permission, liveness or resource evidence fails closed. Each inventory, retirement and ordinary runtime operation takes its own project registry lease and delivery-store protection; no lock is held while the user decides. A handover admitted through the current service rechecks retirement references while registering its project operation after resource resolution, refusing a stale older bundle before launch if retirement committed in between; an unavailable recheck fails closed. Once registered, its project operation prevents a concurrent retirement from starting until that operation ends. The approval manifest's storeInventoryHash detects intervening selection and run-inventory changes, while its member and file identities detect relevant content drift. The administrative entry never upgrades a run's execution resources, takes over its controller, or grants engineering authority. A development checkout cannot use this route to mutate an installed bound store.

## Read-only inventory

A genuinely read-only connection lists each delivery by exact stored ID, revision, status, active selection, task and closing state, worker status, accounting class, report state, every pending follow-up and retirement state. Legacy classification requires absent schema-2 accounting and absent independent accounting and discharge rows. A schema-2 record without independent accounting commits, or with discharge rows missing when its provenance requires them, is damaged, not eligible; an empty discharge index with no expected admissions is valid. The inventory distinguishes a valid retirement from a missing, stale or malformed one. It reports a bounded count and bounded ID list when the output is too large. The read-only inventory accepts a version-1 store without an artifacts table and treats absent accounting-commit, discharge-index and retirement tables in earlier stores as empty. A version-1 state that references a nonexistent artifact, a version-2 store without its artifacts table, malformed present tables, missing runs, active or history tables, unreadable rows, duplicate identities, unknown worker states and exceeded read bounds produce an unavailable diagnosis, never an eligible or clean result. A missing or corrupt artifact referenced by any saved current or latest-history state makes the whole inventory and every proposed manifest unavailable, even when that run is outside the batch. The error names the run; bounded raw inspection of that ID can diagnose it, and retirement waits for evidence recovery. When the delivery database and its SQLite sidecars are absent, inventory reports no store and offers no eligible IDs; surviving sidecars instead refuse with migration-store-unavailable until the database is restored or reconciled, and a leftover `.claude/runs` database refuses with legacy-run-state until setup migration. Inventory creates no table and changes no run, selection or evidence.

For a proposed retirement batch, read-only inventory combines observed records with the controller's proposed choices into one canonical approval manifest {schema, records, choices, storeInventoryHash}: schema is the literal integer 1 for this release and selects its retained projection and validation grammar; records is the sorted exact run IDs, safe revisions, status, accounting classification, active-selection and retirement state, SHA-256 identities of raw current and matching latest history states, and observed obligations; choices is the sorted per-member retirement, report and follow-up disposition table, with every tracked destination's entryHash derived by the runtime from its current target entry, and storeInventoryHash is the SHA-256 of the canonical sorted projection of every saved run ID, safe current revision and raw state hash, matching latest history revision and raw hash, the one active selection ID, database version and current retirement references. For an empty inventory the run and reference lists are empty and the selection is null; malformed or missing expected state is unavailable. An absent choices set returns a diagnostic manifest without an approval hash; an incomplete supplied set refuses with migration-decision-unavailable and produces no approval pages. After all saved current and latest-history artifact references pass hydration, each member shows its objective, stop and hold, worker statuses, every task whose status is not complete under incompleteTasks, the computed closing stage and report, retrospective and triage flags, the full saved closing record for both completed and stopped deliveries, and every pending follow-up with its exact identity, status and content. Completed task histories stay in the saved state and matching latest history, whose raw hashes bind the full bytes; they are not copied into approval pages. Artifact-backed fields in the projected task or closing record appear by content-addressed reference after validation, not as expanded artifact bodies; a decision that requires the body remains pending until separate read-only evidence is presented.

Each member includes a report projection {owed, savedHash, file}: owed is true when a handed-over report lacks matching saved recipient confirmation or any saved report lacks that confirmation, and false otherwise; savedHash is the saved report-evidence hash or null when no valid saved hash exists; a saved report with no valid hash remains owed and needs an explicit waiver; file is {status, sha256, reason}, where present requires a regular singly linked .md file at a safe path under .nightshift/runs/reports/ no larger than 1 MiB, sha256 is the hash of bytes read within that bound, and reason is null; missing means a safe path is absent, with sha256 null and reason set to the literal token missing; unavailable means an unsafe path, link, special file, oversized file, read error or file change during read, with sha256 null and reason set to the corresponding literal token unsafe-path, linked, special, oversized, read-error or changed-during-read; none means no saved report evidence, with sha256 and reason null. The operation validates path, type, link count, size and identity before reading and rechecks them after; it never reads or displays bytes from an unsafe or oversized target. Report-file reads for one manifest are bounded to 16 MiB in aggregate; exceeding that bound makes the batch unavailable until it is split.

Current versus stale is derived only by comparing a present file hash with savedHash. The manifest does not claim that every older history revision or artifact is valid. Its schema is stored with the approval artifact and never silently upgraded: manifest creation uses the latest supported projection, while inventory, certificate validation, creation admission, retry and supersession validate each stored manifest and ancestor with the projection grammar of its saved schema. A later projection change requires a new schema and retention of all prior readers and validators; schema 1 freezes its historical closing-stage, worker-activity, report-delivery and saved destination path grammar. The current certificate alone checks tracked entry content through the live backlog scanner; changes to that scanner or its heading rules can stale a current tracked certificate and require approved supersession. Current and ancestor certificates use their saved schema to reconstruct the approved task, closing and follow-up projection from the bound historical state; ancestors retain their original destination identity without requiring the old target to stay live. An unsupported schema makes that retirement unavailable and keeps creation blocked until compatible code is restored. Its hash covers the exact canonical schema, storeInventoryHash, records and choices shown together across the approval pages; that same object is retained as a content-addressed artifact when retirement commits. Any approved-member, worker, report-file or tracked-destination change, or a storeInventoryHash change, before commit makes it stale. Unrelated evidence outside that identity remains subject to the independent creation-gate checks. A broad instruction such as "retire all completed runs" is resolved to this fixed manifest before approval and cannot include records discovered later.

The short observation-only inventory preview is diagnostic, not an approval surface. An approval batch contains at most 100 records and an encoded full manifest of at most 8 MiB; a member that cannot fit is diagnosed and remains unretired. The full manifest is available in deterministic pages of at most 20 records with the same total page count and canonical full-manifest hash on every page. Every page includes each member's status, incomplete tasks, closing obligations, pending follow-ups, report projection and proposed dispositions; an omitted or truncated projected member cannot be approved. Pages are recomputed without a mutable snapshot cache, so a hash change between pages requires starting the review again. Retirement recomputes the entire manifest under its writer transaction and accepts only that exact approved hash and member set. The full manifest artifact, rather than a preview, is retained with the certificates.

## Authorization and eligibility

An admitted controller presents every page of the complete approval manifest, including its disposition table, and records one final user reply approving that exact combined object. Each completed or stopped record has its own retirement row; each stopped row names the work and obligations being abandoned, and a reply approving several rows does not merge those decisions. Each owed report has a separate confirm or waive choice in its record row: the controller shows a current matching saved report when available and otherwise explains the absent, stale or unreadable condition, and the final reply comes after that presentation. Each pending follow-up has its own track or dismiss choice and source context. Before a track choice, explain that editing the target entry or moving it to history makes the retirement stale and blocks new handover until the user approves a superseding certificate; dismissal records an explicit end to that carried obligation. Silence, unavailable user input, a broad earlier choice to retire completed records, or an omitted disposition leaves the affected record unretired. Running records, records with active or uncertain workers or operations, damaged schema-2 records, records with missing or contradictory current identity or latest history, and records changing during the request are ineligible. The current and latest history states must hydrate within the stated bounds; failure is diagnosed rather than treated as discharge. A completed or stopped status alone never grants eligibility.

Inside the project transaction the runtime recomputes the observed records and storeInventoryHash, combines them with the supplied per-member choices after independently re-deriving each tracked destination entryHash, verifies the exact canonical approval-manifest hash and complete member coverage, and checks the admitted session and nonempty exact final approval reply. The reply is the authority for every displayed retirement, stopped-work, report and follow-up choice in that manifest; earlier exploratory replies are not silently substituted. Each certificate binds its own manifest member and copies that final authority, so one batch reply has an unambiguous durable mapping to each record and choice. The runtime does not infer any decision from status. It refuses a stale, partial or ineligible batch without retiring any member. If no user can decide, the controller reports the pending decision to the user, leaves the saved record and its obligations unchanged, and leaves it blocking new handover. A refusal identifies the affected record when safe and preserves the inventory for another read.

## Durable retirement and recovery

An approved retirement writes a content-addressed certificate and a unique current `legacy_retirements` reference for its run ID in one delivery-database transaction. The write path avoids the ordinary RunStore constructor's schema mutation before approval. For a version-1 store, it creates the artifacts table and sets version 2 in the approved retirement transaction; for either supported version, it creates missing accounting-commit, discharge-index and retirement tables in that transaction after validating any present tables. A rollback preserves the prior version and tables. Before an approved retirement commits, no record is retired. The certificate is `{schema: 1, runId, revision, stateHash, historyHash, manifestHash, status, disposition, report, followups, authority, recordedAt, supersedes}`: `runId` is the exact stored ID; `revision` is its checked safe current revision; `stateHash` and `historyHash` are lowercase SHA-256 hashes of the exact UTF-8 bytes of the current state and matching latest history state; `manifestHash` is the content identity of the exact approved manifest artifact, which must be present and valid; `status` is their checked `complete` or `stopped` value; `disposition` is `retired-complete` or `retired-stopped` accordingly; `report` binds the saved report as described below; `followups` binds every pending follow-up and its approved disposition as described below; `authority` is the nonempty exact final user reply approving the presented disposition table for the manifest; `recordedAt` is the runtime's UTC time; and `supersedes` is null on first retirement or the exact previous certificate identity on a later approval. Empty or unsupported fields and a disposition inconsistent with status are invalid. Existing run, history and artifact rows are not rewritten or removed.

The report field is {kind, sha256}: sha256 is the exact valid saved report hash, or null when that hash is absent or invalid, even if report evidence exists; kind is none only when no report is owed and no report evidence exists, already-delivered only when saved recipient confirmation matches that hash, confirmed only when the user saw report bytes matching the saved evidence hash and replied, or waived only when the user expressly waived the owed report after seeing its accurate manifest condition. Empty, mismatched and unrecognized forms are invalid. For a selected retired legacy record, confirmed or waived discharges the report handover block without mutating the old run; already-delivered retains its existing discharge. A nonselected legacy report receives the same explicit disposition so migration does not silently lose its recipient obligation. Before committing, the runtime rechecks the report projection against the approved manifest and saved state; a changed observed file hash or availability, or a changed saved report, requires a new manifest and decision. An unreadable file cannot be byte-compared, so only an explicit waiver of that unavailable state can retire its report obligation.

The followups field is a sorted array containing exactly one {id, sourceHash, disposition, destination} for each saved follow-up whose status is not resolved: id is its exact saved identity; sourceHash is the SHA-256 of that item's canonical saved content; disposition is tracked or dismissed; and destination is {path, anchor, entryHash} for tracked, where path is the safe project-relative active-backlog record or index path, anchor is its checked heading anchor or null only for a whole breakout record, and entryHash is the SHA-256 of the target entry text after CRLF and lone CR characters become LF; destination is null for dismissed. Heading and duplicate-slug lookup follows the Ready backlog link scanner on LF-based lines before hash normalization, preserving lone CR while finding the raw section. A top-level fence left open under that model makes the target unavailable; nested fences follow Ready heading visibility but do not alone trigger this guard. An empty array means the run has no pending follow-ups; at request time an omitted list for such a run normalizes to that empty form, while omission with pending items is invalid. Tracking requires an existing reachable entry in a regular singly linked backlog file before retirement; its target entry is limited to 1 MiB and aggregate destination reads for a manifest to 16 MiB, with an oversized or unsafe target unavailable rather than approved; dismissal requires its own explicit row in the approved table. Missing, duplicated, changed or unsupported entries refuse the batch. The manifest artifact retains each source item and choice after the old run loses its active notice, and each certificate binds its exact member in that artifact. The current administrative inventory and new-release status expose retired follow-ups and flag tracked destinations that later disappear or differ from the approved entryHash; the creation gate treats either as stale retirement until an approved supersession, and no reader treats that follow-up as resolved or erases its original content. Retargeting or dismissing a carried item requires a newly approved manifest and a superseding certificate, preserving earlier decisions.

The first approved retirement also installs database triggers in the same transaction that reject inserts, updates and deletes affecting a retired ID in runs, history, accounting commits and discharge indexes; a new handover may still change the active selection. Later retirements retain those triggers, and creation verifies their exact supported definitions whenever retirement references exist. Missing or changed protection fails closed. An older retained runtime can still work on a nonretired run, but a write to a retired run aborts without modernizing it or changing its certificate. The transaction makes an interrupted retirement either absent or complete. An identical retry returns the current certificate. A changed approved disposition or tracked destination can be superseded after a fresh inventory and user decision: one transaction validates the current still-legacy state, writes a new certificate whose supersedes field is the prior identity, and changes the unique current reference. Earlier certificates remain in the content-addressed store and raw inspection follows the bounded chain. A stale certificate from external or unsupported mutation blocks new handover; supersession is allowed only when the record remains genuinely pre-schema-2 with coherent state and history. A record that gained schema-2 accounting is not re-retired and requires separate diagnosed recovery rather than being laundered as legacy. A missing current reference, missing certificate or approved manifest artifact, broken or cyclic chain, hash mismatch, duplicate or unexpected reference, or certificate for a schema-2 run is unavailable evidence, not a valid retirement. There is no automatic refresh, expiration or deletion.

Authority text is limited to 4 KiB in UTF-8, each certificate to 8 KiB, and the aggregate retirement certificate chain read by the gate to 8 MiB, and approved manifests read across one gate, inventory or retry to 64 MiB. The retirement transaction checks post-write resource bounds for current and required latest history, artifact bytes and count, newly approved certificates, and independently authenticated modern provenance and completion reads. The creation gate uses separate 64 MiB ceilings for total artifact bodies and for current/latest state plus required accounting input; scanning artifact bodies does not consume the latter allowance. The full-store validation, selected page or batch, and creation hydration passes each have a 64 MiB distinct-body read allowance and a 256 MiB cumulative expansion-work allowance; inventory and manifest run the full-store pass before their separate output pass, while creation hydrates retired and resource-only legacy records. Each repeat reference counts toward expansion but reads the stored body only once. Retirement's resource-only preflight defers unrelated damaged provenance, stale retirement obligations and replay of unretired legacy records to ordinary creation, without treating them as discharged. An unretired legacy record may still consume a replay bound at later handover; it remains blocking until authenticated or explicitly retired, and that later handover fails closed with its ID, a `legacy-replay-bound` reason and a migration-inventory direction. A resource-limit failure in the checked paths rolls the retirement transaction back and names the limit. The newly approved certificates must validate before commit. An oversized user reply must be restated concisely, not truncated into different authority. If the certificate still exceeds 8 KiB, `migration-certificate-bound` names the run and leaves it unretired; the user must give a shorter exact approval reply; if no reply can make the certificate fit, the record stays unretired until a separately authorized certificate-limit change is delivered. Supersession stops at the bound without declaring a valid retirement.

Raw read-only inspection of a retired record returns bounded encoded state and history rows, the artifact identities reached within its read limit, and a diagnosis when references are missing, corrupt or exceed that limit; an evidence diagnostic does not claim to list every referenced artifact. Its hydration of each raw state has a separate 8 MiB bound on both distinct referenced bytes and expanded references, so intact evidence larger than that still gets a bound diagnostic and a partial identity list. Hydrated inspection remains available when those artifacts are intact. The feature preserves all existing bytes but does not claim to repair earlier loss or guarantee hydration of every older revision. Mutation, adoption and resume routes in the new runtime refuse a currently retired run. Older retained runtimes may still write nonretired records; database protection refuses writes to retired IDs.

## Creation and reporting

The creation gate inventories retirement references alongside runs, selection, history, artifacts, accounting commits and discharge indexes. It still checks owner identities, row shape, latest history, unknown artifacts, active workers and existing bounds. For a validly retired legacy record it checks the certificate, its report and follow-up dispositions, and every tracked destination identity instead of replaying missing accounting or treating old closing evidence as authenticated discharge. It continues to authenticate unretired records under the existing rule when accounting support tables are present; when they are absent, an unretired legacy record remains blocked as no-independent-accounting without creating those tables during refused admission. An unretired running or stopped legacy record lacking authenticated discharge produces the grouped consistency refusal before overlapping-run; running work is finished or reconciled through its retained release when available; if that release is unavailable, keep the refusal and seek separately authorized recovery rather than retiring a running record or creating another run. Stopped unfinished work needs its own retention or retirement decision. Retention leaves the record unretired and creation blocked; ordinary resume or adoption applies only to the selected record when its retained release and acknowledgement route permit it, and a nonselected stopped record needs separately authorized recovery if it is not retired. A selected retired record may be replaced only when every other record is authenticated or validly retired and its report projection shows no obligation or a valid already-delivered, confirmed or expressly waived disposition. Within the new runtime, an exact acceptance replay of a retired record may return the current record without writing; when replay would refresh a claim, integration or other saved state, the runtime refuses with retired-run. Installed admission can refuse first with migration-new-session-required for an older-bound session, or with an ownership error for a different owner. Every branch leaves the retired record unchanged. A retired acceptance identity cannot be reused for a new delivery.

Creation and fresh-identity persistence open a pre-existing store without constructor-side schema changes and run consistency checks before any schema upgrade. Under the writer transaction they revalidate the exact inventory and apply any supported version-1 table upgrade together with the new delivery and selection. A failed admission, consistency check or resource bound rolls back the schema version, tables, rows and selection; no constructor may upgrade a store merely by attempting a handover. The same rule covers the direct fresh-identity save path. A genuinely empty project keeps ordinary initial creation, which may leave an empty initialized database after a refused first handover but never a run row, selection or obligation; this exception is outside migration of an existing store. A pre-existing version-zero file refuses with state-version until explicitly reconciled, and a missing database with surviving SQLite sidecars refuses with missing-predecessor until the original database is restored or reconciled; neither condition licenses automatic reinitialization.

When an unretired legacy record blocks creation, the refusal names its ID and directs the user to migration inventory. Once one such blocker is known, the gate still checks later current/latest identities and retired certificates but stops further unretired replay; later legacy IDs receive `replay-deferred-after-blocker`, and later modern accounting is deferred until those blockers are resolved. Migration inventory classifies modern records independently. A grouped legacy refusal preserves the total count and bounded IDs by status and reason; other damage, stale retirement, stopped work, pending report and verification-bound failures remain distinct when reached. If current plus latest state alone exceeds the aggregate input cap, the refusal names bounded IDs and reports that migration inventory cannot run under the same cap; bounded raw inspection or external store recovery is needed. A migration or handover refusal against a pre-existing store leaves its version, tables, rows and selection unchanged; a refused first creation in an absent store may leave only its empty initialized database. Missing or unreadable state never becomes an empty inventory or permission to create a new run.

## Delivery of this feature

Implement the reusable inventory, retirement, raw inspection, creation-gate integration and diagnostics, with a monotonic plugin version increase and documentation for both hosts. Verify completed, stopped, mixed, damaged, stale, superseded, interrupted, trigger loss and older-runtime write refusal, bounded, unsafe and oversized report, pending follow-up disposition and destination drift, and retry cases in deterministic fixtures. Check that existing creation, exact replay, report delivery, worker and ownership gates still refuse their negative cases. Verify the user-visible inventory and approval flow on each supported host where available, marking any unexercised host provisional. Run the appropriate packaging, parser and line-ending checks. Publication remains separately authorized.

After the feature is implemented and independently assessed, use an installed compatible current-release administrative route to inventory this repository again; a local checkout alone cannot migrate its bound store, and publication is not assumed. Its read-only inventory on 2026-10-15 found 45 records without independent accounting, of which 43 were complete and two stopped; one completed nonselected record had saved but unconfirmed report evidence, and two completed records held four pending follow-ups. Present the then-current exact manifest and obtain the user's explicit approval of its members and every report, follow-up and stopped-work disposition before any retirement; the earlier choice of a completed-record policy is not that approval. Any changed manifest before retirement, including a metadata-only change, requires a new manifest and approval. At design approval the two stopped records needed individual decisions and blocked new handover until resolved; do not present feature completion as this repository's migration being complete while any such decision remains. The [application report](../reports/legacy-delivery-migration-20261015.md) records their later exact approvals and final inventory.
