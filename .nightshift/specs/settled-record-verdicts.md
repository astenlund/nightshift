# Settled-record verdicts at delivery creation

## Outcome and authority

The delivery creation gate stops re-proving, at every handover, what it already proved about records that have not changed since. Once the gate has judged a record settled, it records a verdict bound to that record's revision and stored bytes, and later gates confirm the verdict from metadata instead of parsing, replaying and re-judging the record. The gate's work then follows what changed since it last ran rather than the project's whole history, so the 64 MiB input allowance bounds the records still in play instead of every record the store has ever held.

This fixes [The creation gate re-reads every settled record at every handover](../BUGS_HISTORY.md#the-creation-gate-re-reads-every-settled-record-at-every-handover), whose stopgap shipped in 3.3.39. The user chose on 2026-11-17 to fix it on the current store and carry the property into [the store v4 cut](../features/store-v4-cut.md), to confirm verdicts from metadata with freeze triggers as retirement does, to have the gate write verdicts as it judges, and to let a pass the allowance refuses keep the verdicts it established, so that re-judgment proceeds across handovers; on 2026-11-18 the user chose to bound artifact reads per record within the shared input allowance, in migration inventory as at creation, to have a runtime leave a later release's protection and verdicts untouched, and to catch a missed rule-identity change with a digest the release gate pins.

## Commitments

1. **What a verdict vouches for.** The gate writes a verdict for a record it has judged in full when that record is not the selected delivery, is discharged with no open closing work, has no active worker, and is either a modern record with current independent accounting or a retired record whose certificate validated. A verdict binds the record's id, revision, current-state byte length and digest, its latest history revision and that row's byte length, its accounting journal's latest revision, its acceptance handover id, the identity of the judging rule and, for a retired record, the artifact id of its current retirement certificate. Unretired legacy records, records that are not settled and the selected delivery are judged in full at every pass, as today.
2. **Confirming a verdict.** A later gate accepts a verdict, without reading the record's state, history, accounting or completion evidence, only when every bound value still matches the store's metadata (the record's revision and state byte length, its latest history revision and that row's byte length, its journal's latest revision and, for a retired record, its retirement reference) and the verdict's rule identity is the current one. Any mismatch makes the verdict stale: the gate judges that record in full and replaces or removes its verdict, except that a verdict under a rule identity the runtime recognizes neither as its own nor as an earlier runtime's is a later release's: it is not accepted and stays unchanged whatever its other values, its record is judged in full, and every other verdict is handled as usual. Every legitimate change to a record's own rows either goes through a save that advances its revision or, for a retired record, replaces its retirement reference through re-retirement, and both stale the verdict, so a reopened, amended or re-retired record is re-judged without a special case.
3. **What the allowances bound.** Records with an accepted verdict are not charged to the shared input allowance, including the up-front check of current states and latest rows. The records judged in full keep the per-record completion-row bound and every refusal their allowances raise today, with two changes. The up-front check of current states and latest rows ends a pass before any judgment only when the selected delivery's current state and latest row cannot fit the allowance; every other record without an accepted verdict is charged as the gate reads it, one record at a time, until the allowance is reached, and a record the judgment finds not settled, or unretired legacy, is judged in full at every pass as before. The 8 MiB allowance for accounting and provenance artifacts, today shared across the pass, applies to each record judged in full, and the artifact bytes it charges also count against the shared input allowance, which stays the one bound across the pass; the completion evidence a completed record's discharge judgment hydrates keeps its own per-record 8 MiB allowance, not counted against the shared input allowance. Store-wide checks that read only metadata (record count, identity sizes, selection, orphaned evidence, retirement references) keep running over every record. Acceptance identity stays unique across verdicts and fully judged records.
4. **Retired records stay validated.** A verdicted retired record keeps its certificate validation at every pass, within the certificate, manifest and tracked-destination budgets that validation has today, so its tracked follow-up destinations are still compared with the project's backlog files, its certificate chain is still walked, and the end-of-pass check that every retirement certificate lies on a validated chain still holds. The verdict vouches for the results of the checks that depend only on the record's own state and latest history row (its state and history hashes, its still being legacy, the shapes of its disposition, report and follow-ups, and the verification of the evidence that state and row reference, which the threat model's given-up detection covers), which cannot change while its bound values and certificate id match, since those rows are frozen and the certificate and manifest are content-addressed; every pass reruns only the checks that depend on anything else, so the record is not charged to the shared input allowance. Migration's retirement preflight neither accepts nor writes verdicts; retirement already refuses a store whose current states and latest rows together pass the same 64 MiB bound, in migration inventory, so that adds no refusal. The preflight follows the gate's artifact allowance under What the allowances bound, as migration inventory does, with the consequences Other writers of the store states for every action that loads inventory.
5. **Freeze protection.** While a record's verdict matches its current revision, the store refuses rewriting in place or deleting that record's current row and any of its history, accounting journal or discharge-index rows, and refuses, for a run whose id has a verdict, every write to its runs row other than a move to a higher revision under the same id (a rewrite at the same revision, lowering it, renaming the row away or another onto it, deleting it, and inserting it at or below the verdict's revision or the revision its row is at, a replacing insert included), none of which any writer does, so a verdicted run cannot be moved back to the revision its verdict names, through SQL triggers in the manner of the retirement guards, which already cover all of a retired run's rows in those tables; a save to a new revision is unaffected, including the rewrite of the previous history row that a save on a compact store performs. The gate checks that this protection is installed exactly as the runtime defines it. If it is missing, this runtime's own guards without their verdict table included, the gate accepts no verdict, judges every record in full, and in one write reinstalls the protection and removes every verdict written before it, since the rows those verdicts vouch for were unprotected meanwhile; a pass the allowance refuses still keeps that write under Failure branches. Since the guards name the verdict table, this runtime's own guards without it refuse every write that fires one of them, which is every save of a run by any runtime and any rewrite or deletion of a run's history, accounting journal or discharge-index rows, so every save of this runtime first recreates the absent table empty, as a creation pass that writes does, and the repair never waits for a creation pass to commit. A release that changes the protection keeps every guard this runtime defines, or changes the verdict table's definition or a guard's text, so that this runtime reads the result as a later release's rather than as its own guards partly removed. No earlier release defined this protection; a release that changes it recognizes every earlier release's definition, this one included, as an earlier runtime's, replaces it with its own and keeps the verdicts it protected. A protection definition or verdict table shape the runtime recognizes neither as its own nor as an earlier runtime's is taken to be a later release's: the runtime then accepts and writes no verdict, judges every record in full and leaves that protection and every verdict unchanged, so a session bound to it has the bounds of a release without verdicts.
6. **Threat model.** Verdicts keep the gate's present protection against rollback, against a hand edit that writes a new revision, and against an in-place edit or deletion of a protected row while the triggers stand. They give up one kind of detection: a verdict fixes, as of the pass that judged the record, every result resting on inputs outside the record's own frozen rows and content-addressed artifacts, namely the presence and integrity of the artifacts it references (its accounting, frontier, provenance or snapshot bodies) and the project-file identity a spec-path comparison consults, so a change to such an input is not detected until the record is next judged in full. The run-bound artifact scan does not stand in for that, since it identity-checks only artifacts that are present and carry a run id. Verdicts do not defend against a deliberate actor with write access to the database who forges a verdict row or alters the triggers and the rows together; neither does the present gate against one who forges consistent accounting, provenance and certificates. A dropped or unreadable verdict row only costs a full judgment; a dropped verdict table blocks the writes Freeze protection names, by any runtime, until this runtime next saves a run or a creation pass of it writes.
7. **Rule identity.** A release that changes what any check whose result a verdict vouches for accepts or refuses (the record's identity and shape, the agreement of its state with its latest row, its discharge, and the retired-record checks Retired records stay validated names) changes the rule identity, so every verdict written under the old rule is stale and re-judged, across passes where the allowance requires. The runtime reference states when the identity must change and names the sources those checks reach. That set covers every runtime module the checks reach: a module a pinned source requires is either pinned itself or named as excluded, with why it cannot change what a vouched check accepts or refuses, and the release gate fails on one that is neither. A missed change cannot ship silently: the release gate pins a digest of those sources, and a change to any of them fails it until the release either changes the rule identity or re-pins the digest together with a changelog statement that what the vouched checks accept or refuse is unchanged, by the user's choice of 2026-11-18.
8. **Failure branches.** A verdict that is malformed or names a record the store does not hold settles nothing: the gate judges the record in full where it exists and removes the offending verdict. A verdict whose acceptance identity collides with another verdict's or a fully judged record's refuses the pass as an ambiguous acceptance identity, as a full judgment would, since a collision cannot say which side is wrong. A verdict table or trigger whose shape is not the runtime's own is an earlier runtime's or a later release's, handled as Freeze protection says. A pass that refuses creation for any reason other than the shared input allowance writes nothing, as today. Running out of the shared input allowance anywhere in a record's judgment, a legacy record's replay included, counts as the allowance refusing the pass. A pass the allowance refuses, when every check it completed before reaching the allowance passed, keeps its verdict and protection writes (the verdicts it established for the settled records it judged in full, its removal of offending or stale verdicts, and the write Freeze protection makes on reinstalling protection, its removal of earlier verdicts included) and writes nothing else, so successive delivery-creating handovers re-judge the store a part at a time until it fits; this holds equally for a store already past the allowance before any verdict exists and for one whose verdicts all went stale together. The refusal says whether the pass kept verdicts, and the handover route retries a refusal that kept them, with the same acceptance identity, until it is admitted or a refusal keeps none; a refusal that keeps none is the stuck case and goes to the diagnosis route as today. A settled record that cannot fit beside the records judged at every pass stays refused, as today, with no administrative route. A pass's writes persist together or not at all.
9. **Other writers of the store.** Runs bound to earlier 3.3.x releases keep working on a store that holds verdicts and triggers: none of their writes may be refused by the protection except an in-place rewrite or deletion of a verdicted revision's rows, and, while the verdict table is dropped beneath this runtime's guards, the writes Freeze protection names, every save of a run among them, until a runtime carrying this change saves a run or a creation pass of it writes, and nothing they do may make the new gate accept a stale verdict. An earlier release's creation gate ignores verdicts and keeps its present bounds, so a session bound to one is refused delivery creation on a store that fits only through verdicts; such a project creates deliveries under a release carrying this change. `compact-history` carries verdicts and their protection over exactly. An earlier release's `compact-history` refuses a store holding verdicts and changes nothing: a version-3 store, which is what this runtime creates, as already compact, and a version-1 or version-2 store because its verification finds the verdict table was not copied. Migration inventory keeps its 64 MiB bound on current states and latest rows, neither accepts nor writes verdicts, and takes the gate's artifact allowance under What the allowances bound: each modern record's artifacts are bounded on their own and counted against that 64 MiB, so inventory and creation judge artifacts alike. Every consumer of the inventory load (the migration inventory, manifest and retirement actions, and the delivery status brief's legacy follow-up report) may therefore newly refuse, or report unavailable, a store whose current states, latest rows and artifacts together pass 64 MiB, and newly admits one whose artifacts together pass the 8 MiB that inventory and the retirement preflight each share across the store today.
10. **The artifact scan stays store-wide.** The run-bound artifact scan, which parses and identity-hashes every artifact carrying a run id at every handover (8,216 artifacts, 23,238,227 bytes in this repository's store on 2026-11-17) and is not charged to the input allowance, keeps covering every record, verdicted or not, by the user's choice of 2026-11-17; its growth with history remains, as the bug entry records.

## Acceptance evidence

Deterministic fixtures show:

- a store whose settled records together exceed the input allowance admits creation once those records hold verdicts, and the fixture for this fails against the 3.3.40 gate;
- the same store, with every verdict made stale by a rule-identity change, or with its protection removed, reaches admission through successive handovers even though its current states and latest rows alone exceed the allowance, each refused pass keeping the verdicts it established and any protection it reinstalled, and so does a store past the allowance before any verdict exists;
- accounting and provenance artifact reads are bounded per record judged in full and counted against the shared input allowance, so a store whose records' artifacts together pass 8 MiB, refused by the 3.3.40 gate, is admitted when the input allowance fits;
- a settled record that cannot fit beside the records judged at every pass stays refused with the allowance's reason and no word of kept verdicts, while a refusal that kept verdicts says so, and the handover skill retries only the latter;
- a pass refused for any other reason (a per-record bound, a legacy blocker found before the allowance is reached, or an integrity refusal) leaves every verdict and the protection as they were, while running out of the shared allowance inside a record's judgment, legacy replay included, keeps the pass's writes;
- changing a source the pinned digest covers, with neither a changed rule identity nor a recorded re-pin, fails the release gate, and so does a pinned source requiring a runtime module neither pinned nor excluded;
- a stale verdict by each bound value, and by rule identity, leads to a full judgment and a replaced verdict;
- an in-place rewrite and a deletion of each protected row of a verdicted record, the earlier completion row, the close row, a reminder issuance row, a non-latest journal row and a discharge-index row included, are refused by the store;
- missing protection, this runtime's own guards without their table included, leads to full judgment and is reinstalled, and on a store needing more than one pass afterwards no verdict written before the reinstall is accepted; and an unrecognized protection definition or verdict table shape leads to full judgment with that protection and every verdict left unchanged;
- a verdict under an unrecognized rule identity stays unchanged and its record is judged in full, while the store's other verdicts are still confirmed;
- moving a verdicted run back by any route (an update lowering its revision, deleting its row, renaming it away or another row onto its id, or a replacing insert at or below its verdict's revision or below its current one) is refused by the store;
- a pass the allowance refuses whose kept writes fail to commit keeps none of them, and its refusal carries no word of kept verdicts and names the failure, so the handover skill stops retrying;
- with the verdict table dropped beneath this runtime's guards, a save succeeds and recreates the table empty;
- malformed and orphaned verdicts settle nothing, and a verdict whose acceptance identity collides with another's refuses the pass as ambiguous;
- a record reopened by a new revision is re-judged, on a compact store as well as a full one;
- a verdicted retired record keeps its certificate validation, its re-retirement stales the verdict, an edited tracked destination still refuses creation, the retirement preflight neither accepts nor writes verdicts, and a store whose artifacts alone decide retirement's admission is judged under the gate's artifact allowance by both migration inventory and the preflight, with the inventory action and the status brief's legacy follow-up report reaching the same outcome;
- `compact-history` carries verdicts and protection over exactly;
- the writes of the 3.3.40 runtime on such a store succeed, its creation gate refuses a store that fits only through verdicts, and its `compact-history` refuses a version-2 and a version-3 store holding them, changing nothing, shown by recorded probes that drive its retained bundle; for older 3.3.x releases the claim rests on their only write to a runs row being the same upsert to the next revision since the 3.0 runtime, as their source history shows.

Each refusal and fallback fixture asserts its specific reason. Read-only probes that drive the changed gate against copies of field stores report the shared charge on the first and second passes. No installed host has to run the change before release; the changelog says whether one has.

## Out of scope

The v4 store design, which inherits only the property that the gate's work follows what changed; migration inventory's bound on current states and latest rows; hydration of completion evidence, tracked as [Creation hydrates every completion snapshot to judge a completed run's discharge](../bugs/creation-hydrates-completion-snapshots.md), which this spec makes run once per settled revision rather than at every handover. The existing `discharge_index` table indexes the closing-discharge provenance artifacts the gate reads for each record, not a judgment the gate could trust, so it serves no part of this beyond the protection Freeze protection gives its rows. Runtime changes ship with a version increase. This spec authorizes no publication.
