# Vibe reviewer host

## Outcome and boundary

Let the runtime dispatch lead assessments through Mistral Vibe on GLM, so that lead review tokens, the largest share of review spend, come out of the Vibe plan instead of Claude or Codex usage. The fortnightly baseline in [the assessment worklist](../reports/assessment-worklist-20261018.md) measured, over this store's repair batches, about 367M tokens on fresh leads, 165M on resumed leads and 49M on skeptics. It realizes the Exploring entry [Admit Mistral Vibe and GLM as a reviewer host](../FEATURES.md#admit-mistral-vibe-and-glm-as-a-reviewer-host), on the evidence of [the GLM 5.3 review evaluation](../reports/glm-5-3-review-evaluation-20261023.md) and [the cross-paired run](../reports/seeded-defect-baseline-20261024.md#cross-paired-glm-53-run).

GLM is admitted as a strong lead for every lead kind, including a fresh assessment that closes a task or record, and is never admitted as a skeptic. The evaluation found GLM at parity on detection, decoy refutation and clean-change false positives, but its lead raised more weak scope findings, and as a skeptic it confirmed every unmatched finding it judged, from its own lead and from Opus's alike. The skeptic is the role that filters noise, so it stays on the Claude and Codex strong families. Detection was at the ceiling for every model in the suite, so GLM's ability to close a task on harder defects is unmeasured, an accepted risk of this design.

In scope: the `code`, `spec` and `docs` assessment kinds, fresh, resumed (closure and lead dialogue turns) and replacement dispatches, in delivery runs and standalone review contexts alike. Out of scope, each staying as today: Vibe as a controller host; Vibe for in-host workers registered through the `worker` action, peers included; the `skeptic` kind, including a skeptic's dialogue turn; implementers; model families other than GLM on Vibe; operating systems other than Windows.

## Admission

`internal/runtime/models.js` replaces the single strong test with admission by role. A role is `skeptic` for the `skeptic` kind and `lead` otherwise: the `code`, `spec` and `docs` kinds and an omitted kind, which dispatch already records as `code`, so validation and import key the role on the same defaulted kind the receipt carries. The Claude and Codex families and their floors are unchanged and admitted for both roles. Vibe gains one family, `glm`, with floor 5.3, admitted for `lead` only. Vibe's plain identifier form is `glm-<major>[-<minor>]`, mirroring the sibling forms: version parts of at most three digits with no leading zero, and a missing minor compared as zero, as `compareVersions` already does. It matches the identifier Vibe journals as its active model (`glm-5-3`); a variant or suffix is refused like any other non-plain form.

Both existing gate points apply the role: `validateRequest` in `internal/runtime/review.js` checks every candidate against the role of the request's kind, and `readReceipt` checks the receipt's host and model against the role of the receipt's kind. A Vibe candidate on a skeptic request is refused with `review-strength`, whose message names the role. The receipt's `strength` stays `strong`, meaning admitted as strong for its kind, so the fresh-assessment test in `internal/runtime/lifecycle.js`, which requires `strength === 'strong'`, is unchanged and a clean fresh GLM assessment passes the gate. `requiredModel` and `substitutionReason` keep their rules; a candidate list may mix Vibe and other hosts.

## Launcher

`internal/runtime/hosts.js` gains `runVibe`, promoted from `tools/seeded-defects/vibe-launcher.js`, and `executable` and `runAgent` accept `vibe`. The suite then uses the runtime's launcher for Vibe leads, and keeps its evaluated-host injection only for a Vibe skeptic, which the runtime does not admit.

- Process: the native `vibe.exe` resolved by `resolveTrustedExecutable`, run headless in the dispatch's private copy (`--workdir`, `--prompt-file`, `--output json`, `--output-dir` under the attempt's artifacts, `--time-limit` derived from the attempt's timeout, without `--trust` unless the isolation bullet's fallback for an unavoidable trusted run applies) inside the runtime's Windows job, with stdout and stderr bounded below the job's output capacity, as the suite's launcher does. Startup, termination-proof and artifact-write failures follow the same paths as `runClaude`.
- Isolation: like the Claude launcher (`--safe-mode`, `--strict-mcp-config`) and the Codex launcher (`project_doc_max_bytes: 0`, hooks, plugins, apps and multi-agent off), a Vibe reviewer's instructions, tools, tool descriptions, prompts, model and configuration come only from the launcher and Vibe's built-in defaults: no other configuration source may add to or change them, apart from the credential, provider and model catalog Vibe needs to reach the model. Every other source is a channel to close. Installed Vibe 3.0.0 has these channels, all enabled by default:
  - project scope, admitted only in a trusted folder: `AGENTS.md` files, including their lazy injection into `read_file` results; `.vibe/config.toml`, which overrides user configuration; `.vibe/hooks`, `.vibe/skills`, `.vibe/tools` with their `tools/prompts` description overrides, `.vibe/agents`, `.vibe/prompts` and `.vibe/plugins`; and `.agents/skills`;
  - user scope, admitted whatever the trust setting: `~/.vibe/AGENTS.md`, `~/.vibe/hooks.toml`, tool description overrides in `~/.vibe/tools/prompts` (which matter even with only `read_file` enabled), custom tools, prompts and agents, `~/.agents/skills`, `~/.vibe/plugins` with every component (knowledge, libraries, hooks, agents, MCP servers, connectors and adapted plugins from other hosts), and configuration settings that change the prompt, tools, MCP servers, connectors, skills or subagents;
  - configuration layers outside both, from Vibe's configuration orchestrator: inherited `VIBE_*` environment variables, which the runtime passes on with the controller's environment; GrowthBook experiments, which can set the system prompt, model routing, shell tools and registry skills; and the admin layer, fetched from Mistral's managed-config endpoint whenever a Mistral API key resolves, whose values outrank every other layer. The launcher drops every inherited `VIBE_*` variable from the reviewer's environment except those the credential and provider need; it turns experiment fetching off per invocation and sets its own values for every setting an experiment can assign, which outrank the GrowthBook layer in any case; the admin layer cannot be outranked or turned off per invocation, and it is the one channel accepted as part of the provider boundary, like the credential and model catalog, on condition that the effective-configuration check below passes on every attempt.
  After every attempt, before its report is used, the launcher compares the effective configuration Vibe records under `config` in `export.json` with an expected configuration: the launcher's own value for each key it set, else Vibe's built-in default for that key, so a key the launcher leaves unset on a fallback branch is still compared. The comparison covers every key of the recorded configuration except a named allowlist of keys that cannot change the reviewer's instructions, tools, agents, prompts or model: the credential, provider and model catalog keys, and the keys that only affect Vibe's terminal interface (theme, cursor, banner, clipboard, notifications, voice and narration). The probe fixes that allowlist for each probed version from Vibe's configuration schema; every key not on it is compared, so a key the allowlist does not name, including one a new Vibe version adds, fails by default rather than passing unchecked. Any difference, from any layer, active on that day or not, fails the attempt as `unusable-review` naming the differing keys, and the next candidate is tried; an `export.json` whose `config` lacks a compared key, or records a key with no expected value, fails the same way. Hooks and instruction files are not configuration keys; they stay closed by the untrusted run and the user-scope mechanisms, which the probe's markers establish, not by this check.
  The reviewer runs untrusted: no `--trust`, and the private copy is not trusted through the user's trusted-folder list or an ancestor in Vibe's trust chain, which closes the project scope with one mechanism. Every private copy lies under the reviewed checkout and Vibe decides trust at each launch by walking the copy's ancestors, so a later trust grant on the checkout or an ancestor would reopen the project scope; the untrusted condition is therefore established before every launch, either by a per-invocation override that forces an untrusted run whatever the trusted-folder list says, if the probe finds one, or else by reading Vibe's trust state and applying its ancestor walk. When the copy or an ancestor is trusted, or the trust state cannot be read or parsed, the attempt fails before launch with `vibe-trust-unavailable`, whose recovery names the trust entry to remove, and the next candidate is tried. Each user-scope channel is turned off per invocation, without editing the user's Vibe configuration and without copying any credential under `.nightshift`. These mechanisms are provisional and settled by the probe below, which derives the layer set from Vibe's configuration orchestrator source, checks every listed channel and records any further instruction or extension channel it finds. If the reviewer cannot run untrusted, each project-scope channel needs its own per-invocation off switch instead, applied on every launch whatever the trust state, so that a later trust grant cannot reopen a channel.
  Isolation is established for the Vibe versions the probe ran on, which the launcher lists; Vibe updates itself. Each Vibe attempt and receipt records the Vibe version, and the launcher refuses a version whose major or minor part is not listed, or one it cannot read or parse, before launch with `vibe-version-unprobed`, and the next candidate is tried. Admitting a new version is a maintainer action outside any run: rerun the isolation probe and release the plugin with the version listed. Until then Vibe is unavailable and the fallback candidates run with the substitution reason recorded; the refusal is a note for the user, never a controller action, and pinning Vibe or turning off its automatic update is the user's own mitigation.
  If any channel other than the admin layer, listed or found, cannot be turned off, or the probe shows that `export.json` does not record every key the effective-configuration check compares, Vibe is not admitted, since a reviewer that obeys instructions in the change under review or in configuration outside the launcher is not independent. Nothing Vibe-specific is then implemented or shipped: no launcher, role admission, import branch or prompt sentence, and none of the guidance, tracking or Vibe verification below. The probe result is recorded and the delivery task is blocked as a user decision, so an unattended run records it and continues independent work. The per-host split of `tools/fortnight.js`, which is repository-only and useful without Vibe, may still proceed.
- Tools: `read_file` only, through `--enabled-tools`.
- Prompt and report: Vibe has no structured-output or system-prompt option, so the system text precedes the prompt and the report schema is stated in it; the report is taken from the last assistant message's last untagged or `json` fenced block, else its outermost braces, and then validated by `validateReport` unchanged.
- Attribution: the session id from `export.json`, and the model from the session journal's runtime state, which must name one active model across every generation, equal to the requested one. A resumed attempt must also report the session it resumed.
- Tokens: `usage.total_tokens` from `export.json` for a fresh attempt. For a resumed attempt, the attempt's own usage when Vibe reports it per invocation, or the cumulative total less `priorThreadTokens` when it reports cumulatively, and unknown (null) when the implementation cannot establish which; the probe below settles it. Vibe's count is its own accounting and is not comparable with Claude or Codex figures, which the receipt's host already makes visible.
- Host failure: an attempt that ends without a usable report records as `hostFailure` the error `export.json` reports, else the end of stderr, bounded at the runtime's 2,000-character limit, ending the attempt's error message as for the other hosts. Vibe's JSON output exposes no partial output, so like Claude attempts its attempts are not checked for output loops; the output bound above caps a runaway stream.
- Configuration (provisional, settled by the probe below): the launcher pins the model, sets the thinking level, replaces Vibe's coding system prompt and turns off code mode's `run_typescript` per invocation, under the same constraints as isolation. A replacement system prompt never resolves by id from a project or user prompt location, since that would let the reviewed copy or user configuration supply it; without another mechanism the replacement falls back as below. The evaluation ran with none of these, so each that cannot be applied per invocation falls back as follows: an unpinned model still has to pass attribution, so a mismatch fails the attempt; the thinking level falls back as the effort bullet states; Vibe's own system prompt stays in place; and `run_typescript` stays available, with the evidence rule below.
- Effort: Vibe's thinking levels are `off`, `low`, `medium`, `high` and `max`. A Vibe candidate's `low`, `medium` and `high` run at the thinking level of the same name, `xhigh` runs at `high`, and an omitted effort runs at `high`, as on the other hosts; `off` and `max` are never used, and the launcher returns the level it applied. `validateRequest` keeps today's permitted set, so no Vibe candidate is refused for its effort, and the seeded-defect suite's pinned `xhigh` runs GLM leads at `high` without a change. The receipt records the level that ran, which is always `low`, `medium` or `high`, so a resumed dispatch, which takes its effort from the receipt, always carries a level the launcher can apply. When the probe shows the thinking level cannot be set per invocation, the launcher reads the configured level before launch: a configured `low`, `medium` or `high` runs, whatever effort the candidate named, and the receipt records it; a configured `off` or `max`, or one the launcher cannot read, fails the attempt before launch with `effort-not-permitted` naming the configured level, and the next candidate is tried.

## Sandbox execution evidence

Where `run_typescript` stays available, a Vibe lead can run a copy of code it transcribed into Vibe's sandbox. The evaluation found such claims real but sometimes wider than the recorded call. The lead prompt for a Vibe attempt, built per attempt in `dispatchReview`, states that sandbox runs of transcribed code are not execution evidence of the project and that deciding execution goes through a probe request, as for every host. The skeptic, always a Claude or Codex model, validates each finding against concrete evidence as today. Two paths have no skeptic: closures in a resumed GLM lead's report, and a clean fresh GLM assessment with no findings. On those paths the prompt rule is the only guard. A closure never passes a gate, since a fresh lead must follow it, and the clean-pass case is part of the accepted risk above, so no runtime gate changes.

## Resume

Whether `vibe --resume <session> --prompt-file <file>` runs headless and resumes a session from a different working directory, since every dispatch gets a new private copy, is unverified and settled by the probe below.

- When it does: resumed closure and lead dialogue turns resume Vibe sessions exactly as for the other hosts, with the runtime taking host, model and effort from the receipt. A session Vibe no longer holds fails as `resume-failed`, and the controller replaces the reviewer through `review.replaces`, as today.
- When it does not: `resolveContinuation` refuses `review.resume` on a Vibe receipt before anything launches, with a new code `resume-unsupported` whose recovery names `review.replaces`, so no tokens are spent on a resume that cannot work; `closureRoute` in `continuation.js` returns `replace` for a named dispatch whose receipt host is `vibe`, so status's `resumeTargets` advise replacement rather than a resume dispatch would refuse. Closure and lead dialogue turns of a Vibe lineage then go through replacement. Replacement candidates may be any admitted lead, Vibe included.
- Either way, a resumed Vibe dispatch has one candidate, taken from the receipt, so a refusal before launch (`vibe-trust-unavailable`, `vibe-version-unprobed`, or `effort-not-permitted` for a configured `off` or `max` level) has no next candidate. On a resume such a refusal names `review.replaces` as its recovery, and `dispatchReview` records it in `failure.json` with `sessionFailed` true, so `closureRoute` routes the lineage to `replace`. Removing a trust entry stays a note for the user, never a controller action.

## Receipt import

`readReceipt` gains a Vibe branch beside the Claude and Codex ones. The Vibe launcher writes Vibe's JSON output entries as `events.jsonl`, already hashed into `eventHash`; `dispatchReview` also records on a Vibe receipt `attributionEvidence`, the project-relative paths and SHA-256 hashes of the attempt's `export.json` and of every generation's runtime-state file in the attempt's session journal. Import refuses a Vibe receipt with `unattributed-review` when `attributionEvidence` is absent or empty, lacks the attempt's `export.json`, or omits a generation present in the attempt's session journal, and refuses a Claude or Codex receipt that carries the field. The session, outcome and model checks read exactly the listed files and no others: import refuses unless every listed file still has its hash, the listed export's session id equals the receipt's session and its outcome is finished, the listed runtime-state files name exactly the receipt's model, and the report taken from the events by the launcher's rule equals the receipt's findings, probes, coverage, closures and positions, with `changed-result` or `unattributed-review` as for the other hosts. Claude and Codex receipts are imported as today.

## Placement

Placement is controller guidance in the operating brief, not a runtime gate; the runtime admits any admitted candidate order.

- Leads: a GLM lead on Vibe is the default first candidate whenever Vibe is available, to save Claude and Codex usage. The fallback candidates in the same request are ordered Codex before Claude (Sol, then Opus), whichever host the controller runs on, keeping Claude usage for interactive work, where its harness is strongest. When Vibe is unavailable (executable missing, signed out, usage exhausted), the fallback candidates run as today, with the substitution reason recorded.
- Peers: a GLM lead that returns incomplete asking for peer coverage cannot be given peers, since peers clone their lead's model on Claude or Codex. The controller treats that report as incomplete and dispatches a fresh lead from the fallback order, whose peers can clone it.
- Skeptics: each skeptic runs on a different host from the lead whose findings it validates, preferring the controller's own host, so that lead and skeptic sit on different hosts even when only Claude and Codex are available. With a GLM lead, or a Codex lead under a Claude controller, the skeptic runs on the controller's host; only when the lead runs on the controller's own host, as a Sol fallback lead under a Codex controller does, the skeptic moves to the other host. When the host other than the lead's is unavailable, the skeptic falls back to the lead's host in a fresh session, never on GLM, with the substitution reason recorded; the brief's rule that fresh qualified same-host review is valid still covers that fallback. This replaces the other-host preference for skeptics.
- Disposition: GLM leads raise more weak scope findings, which the skeptic tends to confirm as true observations, so the controller's value and obligation decisions carry that filtering.

## Guidance

Placement above is the single lead and skeptic order controllers receive; every guidance site states it or defers to the brief, and none keeps an other-host preference for leads.

- `internal/workflow.md`: the strong-model paragraph says strong lead and strong skeptic admission can differ and that GLM on Vibe is a strong lead only; the sentence in the working-hypotheses paragraph that any strong model can perform any required role is limited to the roles each model is admitted for; the placement paragraph replaces its other-host lead preference with the placement above, keeps the sentence that fresh qualified same-host review is valid, and has its strong-substitute clause follow the fallback order rather than prefer the other host.
- `WORKFLOW.md`: its sentence preferring the other host when a permitted, equally qualified reviewer is available is restated as the placement above.
- `VISION.md`: its sentence preferring a lead reviewer of the required strength on the other host is restated as the placement above, keeping that same-host review is valid.
- `AGENTS.md`: the lifecycle paragraph's clause preferring equivalent-strength cross-host review defers to the brief's placement paragraph, still requiring permitted models of the required strength. This and the two direction documents above are repository-only edits.
- `internal/runtime/REFERENCE.md`: the `candidates` rule lists the Vibe family, its plain form, the lead-only admission and the Vibe effort rule; the dispatch passage documents the Vibe isolation rule, the dropped `VIBE_*` variables, the effective-configuration check, the recorded Vibe version, `vibe-trust-unavailable` and `vibe-version-unprobed`; the resume passage adds Vibe's resume mechanism, or `resume-unsupported` and the `continue: replace` routing if resume is unsupported, and says that a resumed Vibe dispatch's pre-launch refusals name `review.replaces` and route the lineage to `continue: replace`; the `hostFailure` passage adds Vibe's source, and its `sessionFailed` definition also covers a resumed Vibe dispatch refused before launch; the output-loop passage names Vibe beside Claude as unchecked; and receipt import documents `attributionEvidence`.
- `skills/revise-code` and `skills/revise-docs`: their other-host lead preference is replaced by deferral to the brief's placement paragraph; skeptic instructions are unchanged. `skills/revise-spec` and `skills/handover` say only "strong" lead or assessment, which the brief's definition now covers, so they are unchanged.

- Tracking: the Exploring entry moves to `FEATURES_HISTORY.md` as shipped, and the deferred quick win's clause about that entry's system-prompt sentence is dropped with it. `CHANGELOG.md` records the release with its evidence qualifications.

The results settle the provisional points above and are recorded in the release's acceptance report.
- Deterministic tests: role admission for every host and family, including a Vibe skeptic refused at dispatch and at import, a Vibe lead on a request with an omitted kind, and a bare-major GLM identifier; one case per lead kind importing a clean fresh Vibe receipt and asserting that the task's review gate is met; the Vibe launcher's isolation arguments for every channel the isolation bullet lists, the dropped `VIBE_*` variables, the effective-configuration check refusing a differing or missing configuration and a changed key outside the allowlist that no earlier list named, such as `default_agent` or `compaction_prompt_id`, its pre-launch trust check refusing a trusted copy, a trusted ancestor and an unreadable trust state before spawn, the unprobed-version refusal, a pre-launch refusal on a resumed dispatch routing the lineage to `replace`, parsing, attribution, effort mapping including an omitted effort, configured-level fallback, host-failure and failure paths, moved from `tests/seeded-defects.test.js` where they exist; the import branch, including a changed export or journal file, an absent or empty `attributionEvidence`, an omitted journal generation and a non-Vibe receipt carrying the field, each refused; `resume-unsupported` and the `closureRoute` rule if they ship; `tools/fortnight.js` per-host figures in `tests/fortnight.test.js`.
- Installed-host evidence, each dispatched and imported through the runtime CLI on a small project with its skeptic on Opus or Sol: one fresh Vibe code lead, with a canary instruction in the small project's `AGENTS.md` and `.vibe` folder that its report must show no sign of following, so the runtime launcher's actual invocation is shown to keep project channels closed; one resumed closure and one lead dialogue turn on a Vibe lineage if resume is supported; and one replacement dispatch on a Vibe lead, which also carries the closure and the dialogue turn when resume is unsupported.
- A seeded-defect run of GLM leads with Opus skeptics through the runtime launcher, compared as its own input rather than against the Opus targets, which the corrected baseline scopes to Opus. It spends Opus tokens on the skeptics, so it needs an explicit budget.
- Packaging: one plugin version increase, the regenerated release manifest and the release gate.
