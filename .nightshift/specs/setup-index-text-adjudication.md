# Setup adjudicates index text that differs from its template

## Problem

Setup writes an init-backlog template only for a backlog file that is missing (`initialize` in `internal/setup.js` skips every existing file). Guidance added to a template later, such as the fold rule of the 3.3.13 batch, therefore never reaches an existing project, guidance a template later drops stays in every existing index, and running setup again changes neither. The user directed on 2026-10-19 that whenever setup runs and an index's text differs from its template, the difference is presented to the user for adjudication, and later the same day decided that container headings are not compared, that differences are presented one question per file, that a kept difference is remembered until its template text changes, and that the plugin ships a list of retired template guidance so that text a template dropped is presented for removal.

## Commitments

1. **Files compared.** Each of the seven backlog files (`BACKLOG_FILES` in `internal/backlog-catalog.js`) that exists under `.nightshift` is compared with its bundled init-backlog template. A missing file is still scaffolded from its template as today, so it has no differences.
2. **Template guidance.** A template's guidance is every top-level block of the template except its level-one title, its placeholder blocks (a paragraph whose whole text is `Nothing captured yet.`, `Nothing tracked yet.`, `Nothing being explored yet.`, `Nothing currently tracked.` or `Nothing yet.`), its placeholder section headings (`## (add sections as features emerge)` and `## (add sections as work emerges)`) and its container headings, meaning level-two headings whose section has no other guidance (today `## Open`, `## Current patterns` and `## Entries`). Each guidance block belongs to a section: the preamble, meaning everything before the template's first level-two heading, or the level-two section whose heading it follows; a guidance section's heading is itself guidance.
3. **Retired guidance.** The plugin bundles `skills/init-backlog/retired-guidance.json`, `{"schema": 1, "rules": <comparison-rules version>, "retired": {"<backlog file name>": {"blocks": ["<hash>", ...], "headings": ["<hash>", ...]}}}`, where `rules` is a positive integer naming the comparison rules its hashes were computed under. For each backlog file, `blocks` lists the comparison-text hashes (commitment 5) of non-heading guidance blocks that an earlier version of its template had and the current version lacks, and `headings` lists the hashes of the normalized text of level-two guidance headings it had and lacks, each list sorted and without duplicates. A hash that is any block or heading of the current template, its title, placeholders and container headings included, is never retired. The release gate (`tools/release-gate.js`) keeps the list complete for every published version by induction: it refuses a change in which a guidance block or heading of a template at the baseline is absent both from that template and from its retired list, or in which, while the baseline's list and the head's carry the same `rules` version, the list drops a hash the baseline's list held whose text is still absent from the current template. When the `rules` version changes, or the baseline has no list, as at the first publication, the gate needs the history and accepts the list only if it equals what `--write` produces from the baseline-reachable template versions; without the history it refuses, naming the need to run where history exists, as CI does. A head that has templates and no list is refused. `tools/retired-guidance.js` generates the file with `--write` from every version of each template reachable from the published baseline (the release gate's baseline, `origin/main` by default) plus the current one, following renames and hashing with the current comparison rules, for the initial list and for regeneration after a comparison-rule change. The `rules` version is `COMPARISON_RULES` in `internal/template-text/document.js`, which `--write` records, which setup requires the bundled list to carry, and which a change to the comparison rules increases; `--write` refuses to drop a listed hash under an unchanged version; a hash it lists for text that never reached a release matches only an index holding that exact text. Without `--write` it verifies that every listed hash is reproducible under the current comparison rules from some template version reachable from the baseline and that no listed hash is a block or heading of the current template, so a comparison-rule change that alters a retired hash is noticed while rewriting unpublished history or publishing intermediate template versions changes nothing. CI, which checks out full history, runs that verification, and so does the release gate when the history is available. Coverage starts at the earliest version of each template file reachable from the baseline; guidance older than that, such as the templates the v2 init-backlog command embedded, is not retired and reaches the user only as replacement candidates.
4. **Index text compared.** Section and entry boundaries are the lines Ready's entry grammar treats as headings: column-0 ATX `# `, `## ` and `### ` lines outside fences and raw HTML; setext underlines and indented heading lines are block content. In an index, the compared region of a section is the preamble, or the blocks of a level-two section before its first entry: a level-three heading, or in `QUICK_WINS.md` a column-0 `- ` bullet in a section Ready does not exclude, which Ready reads as a quick win. Setup takes those rules from the entry grammar Ready exports (`entryGrammar` in `skills/ready/ready.js`), so the two cannot drift. Entries, from a level-three heading to the next heading of the same or a higher level, are never compared or edited. The start of a file is after any byte-order mark and YAML front matter.
5. **Blocks and matching.** Within those boundaries, blocks come from the shared block model (`describeBlocks` in `internal/backlog-catalog.js`), so fences, raw HTML, tables and list items are the same units unwrap sees. A block's comparison text is its physical lines after joining continuation lines as unwrap would, each line with trailing whitespace trimmed, joined by a line feed. A template block is present when a block with identical comparison text exists anywhere in the index's compared regions; a guidance heading is present when a heading of the same level matches it under Ready's section-key normalization (trimmed, lowercased, a final period dropped). Hashes are SHA-256 in lowercase hexadecimal.
6. **Differences.** Each difference has an identity, its `templateHash`:
   - A *missing section* is a template guidance section whose heading no level-two heading of the index matches. Its identity hashes its normalized heading text followed by the comparison text of every guidance block of that template section in template order, each preceded by a line feed, so any change to the section's template text gives it a new identity. It carries its heading and those of its guidance blocks not present elsewhere in the index. Once the index has a matching heading, the section's absent blocks are ordinary missing blocks instead.
   - A *missing block* is a template guidance block that is not present while its section, or the preamble, exists in the index. Its identity is the hash of its comparison text.
   - A *retired block* is a non-heading block in a compared region whose comparison-text hash is in its file's retired `blocks` (commitment 3). Its identity is that hash, and it covers every occurrence of the hash in the file, each listed with its section and position.
   - A *retired section* is an index level-two section whose normalized heading hash is in its file's retired `headings`. Its identity is that hash. A heading is never removed as a block: a retired section is removable when its compared region holds nothing but retired blocks and placeholder blocks, none of the retired blocks kept by a remembered entry or by a keep among the run's decisions, and it has no level-three entries, and removing it deletes the heading and those blocks, placeholders included, which belong to the section's difference rather than being differences of their own; a retired section that is not removable can only be kept, or renamed as below, and the question says why, while its retired blocks are ordinary retired blocks.

   A missing section has a *rename candidate* when exactly one index level-two section qualifies: a retired section, or a section whose heading matches no template guidance heading, whose compared region holds at least one guidance block of that missing section and otherwise only retired blocks and placeholder blocks of the file, and which either has no entries or has a heading Ready classifies like the new one for that file. A rename candidate's identity, which a rename decision's `replaces` names, is the hash of its normalized heading text, as a retired section's is. A rename rewrites that heading line and leaves the section's body and entries under it; retired blocks in it stay ordinary retired-block differences, whose removal combines with the rename. A retired section whose compared region holds only retired blocks and that has entries qualifies for no rename, since nothing ties it to one missing section, and can only be kept; the question says so. A missing section whose guidance blocks are all present elsewhere and that has no rename candidate is recommended keep, and one partly present elsewhere is recommended insert, which carries only its absent blocks, with the question naming where the present ones sit.

   Each difference carries its file, its section, its text, and its insertion point (for a missing section or block, the heading or block it would follow or precede). A missing block also carries, as replacement candidates, the index's blocks in the same compared region that match no current template block, excluding the level-one title, headings, placeholder blocks and container headings; identical candidates are offered once, under their shared hash. A missing section carries no replacement candidates, only its rename candidate when it has one. Index text that matches no template block and no retired hash is never a difference on its own, and changes only through a replace or a rename decision.
7. **Remembered keeps.** A file meant to be committed with the backlog, `.nightshift/template-decisions.json`, records kept differences as `{"schema": 1, "kept": [{"file", "templateHash"}]}`. Absent, it records nothing. It is malformed when it is not valid JSON, has another schema, names a file outside the seven backlog files or holds a malformed hash; an unsorted or duplicated list is read as its set and rewritten sorted and without duplicates at the next write. Inspect and apply read it on every run and do not present a difference it records; they report it as kept. Apply writes it at the end of adjudication, atomically, inside the lock window of commitment 14 and before the optional unwrap, only when a keep decision adds an entry, and its report names the file whenever it creates or changes it, so the user can commit it; an adjudication that fails before its edits writes no decisions file, one that fails after some of its edits leaves those edits and records none of the run's keeps, which are presented again, and a later unwrap or validation failure leaves the applied edits and the recorded keeps in place. An entry that names no current difference stays as an inert record, so a changed template text, whose hash changes, is presented again, and inspect lists such entries as not matching the current templates so the user can remove them by hand, except entries for a file it cannot read now, which it does not judge; if a template's text reverts to an earlier text, the earlier keep applies again, and a change to the block model that alters a block's comparison text likewise presents its kept difference again. Removing an entry presents its difference again at the next run. When the file is unreadable or malformed, inspect reports it with its reason and each backlog file's count of differences, and presents no difference for adjudication until it is repaired or removed; apply refuses with `template-decisions-unreadable` before any write. Ready, unwrap and migration do not read it. Setup does not stage it; which tracking choice covers it is an open point for [Restore fresh-scaffold track, ignore or defer choice](../features/setup-tracking-choice.md).
8. **Reporting.** Inspect reports `templates`, its differences grouped by file, on every run, including when a saved setup journal exists; when inspect stops early because an unwrap must be recovered, the report says so and presents nothing. Any Ready failure that gives no structural-error report, such as a backlog file that is not valid UTF-8 or a pending unwrap record, counts as an invalid backlog: inspect reports Ready's error and presents no difference, and apply holds every non-keep decision with `backlog-invalid`. With them it reports the Ready parser's structural errors for the current backlog, the holds it can know before any answer, meaning mixed line endings, unreadable certificates and bound destinations whose span covers a region a difference would edit, with the reason, and any leftover temporary file of commitment 14; other holds can appear only at apply. Apply computes the differences again after relocation and scaffolding and reports each decision as applied, kept or pending, with the reason for a pending one, reporting a retired section that an applied rename consumed, a retired block whose every occurrence an applied replace consumed, and the retired blocks a section removal deleted as applied through that decision and so not as pending, its pending list for each file naming the differences the file still holds after its edits that no decision or keep covers, and quoting verbatim, as the file's own lines joined with its line ending, each replaced candidate, each heading a rename rewrote and the text each removal deleted, so text setup took out of an untracked backlog can be recovered from the report; whenever apply fails after its first template edit or decisions-file write, part way through adjudication included, its error output lists in `completed` each file already replaced with its applied decisions, and the decisions-file write if it happened, as it lists earlier unwrap repairs, and says that keeps not recorded are presented again. The report is computed from the current files each time and is never written to the setup journal, as the parser report is not.
9. **Adjudication.** The init-backlog skill presents one question per file with differences, through the host's question tool or, where the host offers none, as a plain-text question that ends the turn, as the operating brief's triage does. The question lists each difference with its text, its candidates and its insertion point, says which edits inspect already knows will be held and why, recommending keep where a bound destination will hold every edit of a difference, and gives the skill's recommendation for each: for a missing block, insert when nothing in the region covers the template text, replace a named candidate that is evidently an earlier version of it, or keep when a candidate evidently supersedes, extends or deliberately restates it; for a missing section, rename when it has a rename candidate, together with removing the retired blocks in that candidate, insert when nothing covers it, or insert or keep as commitment 6 recommends; for a retired block, remove, or keep when the project evidently still wants it, while a retired block whose every occurrence a recommended replace consumes needs no answer of its own; for a retired section, remove or keep as commitment 6 allows. A missing section and its rename candidate are one item, asked as one question, in either mode, whose choices are rename or keep both; inspect marks whether the rename candidate is a retired section, since only then is it a difference of its own, so keep both is a keep of the missing section plus, for a retired candidate, a keep of its heading; a retired section a chosen rename names needs no answer of its own, the recommendations for the two always agree, and when the skill nonetheless holds contradictory answers for a pair, or a section removal with a keep of a block in it, it asks again before calling apply. The question says that a recommended keep is remembered. The answers are *adopt as recommended*, *keep all* or *go through one by one*; one by one, a missing block's question offers insert, replace and keep, a missing section's offers insert and keep, a retired block's or a retired section's question offers remove, when commitment 6 allows it, and keep, and a rename pair stays one question with the pair's choices, and a replace with several candidates lists them by number in that question, with a second question taking the number only when a question tool's option limit leaves no room for them. When a file's differences are too many to show legibly in one question, the question lists each by kind, section, first line and size with its recommendation, carries the full text in option previews or descriptions where the host offers them, and steers to go through one by one for differences whose full text it did not show. The answers pass to apply as `options.templateDecisions`, an array of `{file, templateHash, action, replaces}`: `file` is one of the seven backlog file names, `templateHash` and `replaces` are 64 lowercase hexadecimal digits, `action` is `insert`, `replace`, `remove` or `keep`, `remove` applies only to a retired block or a removable retired section, a rename is a `replace` of a missing section whose `replaces` is its rename candidate, and `replaces` is required for `replace` and absent otherwise. Before any write, migration included, apply refuses with `invalid-template-decisions` only what the decision array itself, the bundled templates and the retired list show: a malformed decision (its shape, file name, hash format, action, or `replaces` present where it must be absent or absent where required), a decision naming no identity its file's template or retired list defines, an action that does not fit its identity (insert and replace only for a missing block or section, remove only for retired text, keep for any), a second decision for the same file and `templateHash`, two replace decisions naming the same hash, and a remove or a keep of a hash that a rename's `replaces` names. What depends on the files' state is judged at adjudication instead, without refusing the run: a remove of a retired section that is not removable then, its run's own keeps counted, is pending with `not-removable` while those keeps are recorded, and a replace whose `replaces` is no current candidate, a rename's included, is pending with `template-text-stale` (commitment 11). A remove of a retired block alongside a replace that consumes one of its occurrences applies to the remaining occurrences. With no user available, or no answer, there is no decision: nothing changes, nothing is remembered, and the difference is reported pending. While inspect reports structural errors or an unreadable decisions file, the skill asks no template question; it asks the user to repair the backlog, or to repair or remove the decisions file, accepting that its kept differences are presented again, and then inspects again.
10. **Migration runs.** On a legacy migration no `.nightshift` index exists at inspect, so apply computes the differences after relocation and reports them pending. Apply's report names them by template hash only, so when a user is available, the skill runs inspect again, presents its template report as for any inspect, and runs apply again in the same setup with the decisions; the completed journal limits that run to scaffolding and adjudication.
11. **Applying.** Every hold below applies to non-keep decisions only: a keep changes no text and its identity derives from the template, so keeps are recorded whenever the decisions file is readable, even for a held file. Before any template edit, apply validates the backlog with the Ready parser; a backlog with structural errors gets no template edit, its non-keep decisions are reported pending with `backlog-invalid`, and apply then fails as today. A file whose block model reports an unclosed fence, that holds a lone carriage return, which the two scanners would count as different line breaks, or that is not valid UTF-8, gets no edit; its non-keep decisions are pending with `template-text-unreadable`, and inspect likewise reports it as unreadable and presents no difference for it. A decision whose `templateHash` names no current difference of its file is reported applied when its outcome holds, meaning its template text is present or its retired block is gone, for example after an interrupted apply, and otherwise pending with `template-text-stale`; a replace whose `replaces` names no current candidate of that difference is pending with `template-text-stale`. Each file's remaining decisions are composed into one result whose postcondition is: every inserted or replacing template block is present under commitment 5 and placed by the rules below, every removed retired block is gone, every block is separated from its neighbors by a blank line as in the template, and a rerun reports none of these differences. Placement: a missing block follows the nearest block that precedes it in its template section and is present in the same region of the index, counting blocks applied earlier in the same file, which are applied in template order whatever the order of the decisions, or else directly follows the section's heading (for the preamble, the level-one title, or the start of a file without one), always before the section's first level-three heading; a missing section is placed directly before the first level-two heading of the index whose template position follows the missing section's, where a section the template has takes its own position and a section of the project's own takes the position of the template's entry slot, its placeholder section or else its first container, or else at the end of the file, with consecutive missing sections in template order, so guidance the template puts before its entry slot goes above the project's own sections and guidance it puts after the slot goes below them; a replace puts the template text at the named block's position, the first occurrence when the candidate text occurs more than once, and resolves only that occurrence of a retired difference; a rename rewrites the candidate section's heading line with the template heading, and the missing section's absent blocks are then placed within it; a remove of a retired block deletes every remaining occurrence, each with one adjoining blank line, and a remove of a retired section deletes its heading and its retired blocks. Keep changes no index text. Before writing a file, apply runs the Ready parser over its planned contents in memory and compares every entry Ready sees, keyed by its heading text and position, with the current contents: a plan that adds a structural error, or in which an entry leaves its section's span, vanishes, or changes between work entry, collected draft and excluded, gets no edit, and its non-keep decisions are pending with `entries-changed`; an approved rename of the heading over an entry is not a move.
12. **Line endings.** Inserted and replacing text uses the edited file's line ending: CRLF when every line break in the file is CRLF, LF when every one is LF, and, for a file without a line break, the ending setup gives new templates. A file mixing both gets no edit; its non-keep decisions are pending with `ambiguous-newline`.
13. **Retirement certificates.** Retained retirement certificates in the run store (`.nightshift/runs/state.sqlite`, read only) bind tracked destinations, evaluated by `targetEntry` in `internal/runtime/legacy-backlog.js`: a heading anchor in `FEATURES.md`, `BUGS.md`, `QUICK_WINS.md` or `PATTERNS.md`, hashed from the anchored heading to the next heading of the same or a higher level, where an anchor can name a level-one or level-two heading whose span covers compared text and an inserted heading can renumber a later duplicate anchor; or a breakout record, with or without an anchor, which is valid only while links from those four indexes reach it. Before writing any of those four files, apply evaluates `targetEntry` for every bound destination over the planned bytes of the files it edits, through a reader seam `targetEntry` gains for this, which leaves its result for files on disk unchanged, and compares it with the destination's value over the current files. A file whose planned bytes change an anchored destination in it gets no edit; a planned change that alters a breakout record's reachability holds all four files. Held files' non-keep decisions are pending with `certificate-bound`, naming each destination. A destination already stale before the edit is reported and does not hold edits. When the run store exists but its certificates cannot be read, edits to those four files are pending with `certificate-unverifiable`. History files are never certificate destinations.
14. **Writing.** Apply holds the existing unwrap writer lock for the `.nightshift` directory (`acquireLock` in `internal/unwrap-lock.js`) from its byte checks through its last rename, the decisions file's included, and releases it before the optional unwrap, whose own process takes the same lock; a concurrent unwrap fails as busy. The lock file persists once created and records this clone's paths and file identities, so an apply with no decision and no leftover temporary file, which writes nothing, takes no lock and neither creates the file nor fails on one copied from another clone; an apply that takes the lock names the file in its report, and the skill reports it as belonging to this clone, never to be committed. When the lock is already held, apply fails with `unwrap-busy` before any template edit, keeping migration progress in the journal, and a rerun resumes. Under the lock, a file with a pending unwrap recovery record gets no edit, its non-keep decisions pending with `unwrap-recovery-pending`. Each edited file is resolved through `projectFile`, so a linked or special file is refused as setup refuses it today, and is replaced atomically, through a temporary file in its directory that keeps the file's mode and is flushed to disk before the rename, after checking that the file still holds the exact bytes its differences were computed from; a changed file gets no edit, its non-keep decisions are pending with `template-text-drift`, a file that cannot be replaced is pending with `template-text-unwritable`, and other files proceed. A process interruption or a power loss therefore leaves each file with its old or its new bytes, so the next run sees either the differences or their applied outcome. A leftover temporary file from an interrupted apply is not a backlog file, so Ready ignores it; inspect reports it as safe to delete while its target exists and decodes as UTF-8, since it can then only be derived output of an earlier apply, and apply removes such a leftover under the lock. A leftover whose target is absent or unreadable may hold the only copy of that file's earlier content: inspect reports it as not safe to delete, and setup, at the start of its run, before unwrap recovery, migration or scaffolding can change the target, renames it under the lock to `.<file>.nightshift-preserved-<uuid>.tmp`, outside the leftover pattern, so that no later run removes it whatever its target holds by then, and apply reports it with that reason; a lock failure there stops setup before any such change, so a rerun judges the leftover again. Apply itself also preserves any leftover it still finds unsafe, and inspect lists every preserved copy for the user to recover or remove.
15. **Order.** Template adjudication runs in apply after migration relocation and scaffolding of missing files, and before the optional unwrap and the final Ready validation, which still refuses a backlog with structural errors.
