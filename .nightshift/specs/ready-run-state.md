# Ready run-state notices

This spec governs [Ready offers to pick up an interrupted run](../features/ready-interrupted-run-pickup.md), including the settled questions the user revisited on 2026-11-01, and folds in a notice for run history that has not been compacted, which [Compact run history](compact-run-history.md) made possible. It does not cover closing a stopped record without its closing lifecycle, which [Close settled records](close-settled-records.md) governs.

## Outcome

When the user runs Ready, a section before the ready set lists every open delivery run and review context in the project, with what can be done about each, and offers compaction for a run store that would gain from it. Ready stays read-only: every remedy is an offer the user answers, carried out afterwards through the existing runtime or migration operation. When there is nothing to report the section is omitted.

## Reading the stores

A new module, `internal/runtime/run-overview.js`, exports `overview(root, {context, dependencies})`: `context` is the bound context Ready's entry admission (`admitEntry` in `internal/releases/entry.js`) returns, whose `host` and `session` identify the invoking session, or null in development mode; `dependencies` is optional and is passed through to the eligibility check, where tests replace `ownerAlive`; absent, the runtime's own `ownerAlive` is used. [The Ready parser](../../skills/ready/ready.js) calls it after its backlog analysis and adds the return value as a top-level `runState` field of its JSON output. `runState` is not part of `notices` or `structuralErrors`, so `--check`, the definition of a clean parse and every existing field are unchanged; an exception from `overview` is caught by Ready and reported as `runState: { error: <message> }` without changing Ready's exit code. Because the module loads `node:sqlite`, Ready's process now prints Node's experimental SQLite warning on stderr, as `unwrap --write` already does; its stdout and exit code are unaffected.

For each store, `.nightshift/runs/state.sqlite` (`store: "delivery"`) and `.nightshift/runs/review-state.sqlite` (`store: "review"`), the module opens the file read-only through the runtime's existing openers, each called with `RUN_STORE_WAIT_MS`: the delivery opener `runDatabase`, which defaults to that wait, moved unchanged with its state check `parseRunState` from `internal/releases/service.js`, where both are module-private, into `run-overview.js` and exported there so that `service.js` imports them back, and `reviewDatabase` with its state check `parseReviewState` in `internal/runtime/review-inventory.js`, module-private today and newly exported, where the opener has no default wait, so the wait is passed explicitly. The store file names, the sidecar suffixes and the backup suffix come from `internal/runtime/history-compaction.js`, which exports them, so Ready and `compact-history` cannot disagree about them. Both already refuse a file that is not an ordinary singly linked file and a store version they cannot read (version 0, or one outside `STORE_VERSIONS`), and wait for a committing writer under `RUN_STORE_WAIT_MS`. Each store's reading has these outcomes:

- The file is absent and no `-journal`, `-wal` or `-shm` file survives beside its name: the store is left out of the result.
- A `-journal`, `-wal` or `-shm` file beside the store's name, the same sidecars `compact-history` refuses with `compaction-store-busy`, whether or not the store file itself exists: the store appears in `unavailable` with code `run-overview-busy` and contributes no records and no compaction entry, since neither its version nor its rows can be trusted while a writer's transaction may be unfinished, and a missing store beside surviving sidecars is the state the runtime refuses with `missing-predecessor` rather than treating as absent.
- An opener refusal: `unavailable` carries the opener's own code (`run-resource-state-unavailable` or `review-resource-state-unavailable`) and message. A busy timeout, a row whose state is not JSON or fails the runtime's own state check (`parseRunState`, `parseReviewState`), or any other read error: code `run-overview-unavailable`, with the error's message. Either way the store contributes no records and no compaction entry, and it is never reported as empty.
- The sum of `length(CAST(state AS BLOB))` over `runs` exceeds 64 MiB, measured before any state is parsed: the store appears in `unavailable` with code `run-overview-bound` and contributes no records, but its compaction entry is still produced, as the Compaction section describes, since such a store is the one compaction most helps.
- Otherwise every row of `runs` is parsed, the delivery store's `active` row names the current delivery selection, and its `legacy_retirements` table, when present, names the retired records, read as the runtime's `isRetired` reads it. The module never reads `history`, `artifacts` or any other accounting table.

Every `unavailable` entry is `{store, code, message}`. For a code that comes from an error, `message` is that error's message unchanged; `run-overview-busy` carries "A SQLite journal, WAL or shared-memory file survives beside the store", and `run-overview-bound` carries "Current run states exceed the 64 MiB overview bound".

## Records reported

A record is reported when it is open, meaning one of:

- its `status` is `running`;
- its `status` is `stopped`, whatever its stop kind and whether or not its tasks are complete;
- it is the current delivery selection, its `status` is `complete`, and the runtime's `reportAwaitsRecipient` (exported from `internal/runtime/creation-consistency.js` for this, not copied) says its morning report awaits its recipient. Only the current selection is checked, since only it can refuse the next handover with `report-delivery-pending`. That refusal also requires the record to be discharged, which Ready does not evaluate: the creation gate does, and an undischarged record makes the next handover refuse with `delivery-consistency-unavailable` instead, or with `overlapping-run` when its closing record was reopened after completion, so presenting a saved report is offered either way, as the Pickup section defines, and the skill does not promise that handover then succeeds.

A retired delivery record is never reported, whatever its status: retirement is the user's approved and final closure, so the user decided on 2026-11-01 that a retired record is closed, not open. Each reported record is `{store, id, kind, status, objective, updatedAt, current, stop, tasks, report, pickup}`: `store` is `delivery` or `review`, as above; `id` is the state's `id`, which the state check has matched against its row, and the short ID the skill shows is its first eight characters; `status` is the state's `status`, one of `running`, `stopped` and `complete`, the values the state checks admit; `kind` is the state's `kind` (`delivery` when absent, as `parseRunState` admits); `objective` is the state's `objective`, shortened as Ready's `truncateExcerpt` shortens excerpts (beyond 200 characters, the first 197 followed by `...`); `updatedAt` is the state's own; `current` is true only for the delivery store's active selection and always false for a review context; `stop` is the state's `{kind, reason}` with `reason` shortened the same way, or null when the state has no `stop`; `tasks` is `{complete, total}`, with `complete` the number of the state's tasks whose `status` is `complete` and `total` the number of its tasks, `{complete: 0, total: 0}` for an empty or absent list, since the state checks do not require `tasks`; `report` is, for a completed record, the saved report's project-relative `path` from `closing.reportEvidence`, or null when the state records none, and null for every other record; `pickup` is defined below. The age shown to the user is computed by the skill from `updatedAt`.

## Pickup

`pickup` is one of:

- `{offer: "present-report"}` for the completed current selection whose report awaits its recipient and whose `report` path is recorded; when the state records no saved report, so `report` is null, the pickup is instead `{offer: "none", reason: "report-unrecorded", message: "The delivery owes its morning report, but no saved report is recorded"}`, since there is no report to present. The remedy is presenting the saved report and recording `report-delivered` with the user's reply, as the handover skill already directs for that refusal; a session that does not own the completed run can record it through the cross-session confirmation route [the runtime interface](../../internal/runtime/REFERENCE.md#handover-and-the-morning-report) describes, which records that session as `recordedBy`. No adoption is offered. Once [Keep a handed-over run open for triage after delivery](../features/handover-open-for-triage.md) ships, a delivered run stays open, and that feature's wording for a delivered open run replaces this case, as the feature record's settled questions record.
- `{offer: "adopt"}` when the routing conditions below all hold and the eligibility check proves the record inactive.
- `{offer: "none", reason: <code>, message}` otherwise, with the code and message of the first routing condition that fails or, when they all hold, of the eligibility check's refusal.

The `present-report` case is decided first and never reaches the routing conditions; they decide only between the adopt offer and `none`. They are cheap reads of the record that rule out an adoption that cannot succeed. Their codes are Ready's own: they name the reason Ready saw and do not claim to equal the code or message `adopt` would return, which depend on the order of the launcher's and the runtime's checks; when the user accepts an offer, `adopt`'s own refusal, if any, is authoritative and the skill relays it. They apply in this order, each with a fixed message:

- A delivery run that is not the current selection: `not-current`, "Only the project's current unfinished delivery run can be adopted". A review context is checked individually, since each review context is selected by its own ID.
- A record whose `controller` is the invoking session: `owned-by-this-session`, "This session already owns the record". Without a bound context the session is unknown and this condition is skipped.
- Under a bound context, a record whose `resourceMode` is not `bound`: `no-retained-release`, "The record has no retained release this session could adopt it through". Without a bound context, a record whose `resourceMode` is not `development`: `not-development`, "Only a development-mode record can be adopted without a bound context". Legacy records, whose mode is neither, are covered by both.

The eligibility check is the one adoption runs. The controller and worker checks inside `adoptState` in `internal/runtime/ownership.js` move into an exported `adoptionEligibility(state, request, dependencies)` that returns `{eligible: true, controller, workers}`, the controller claim and per-worker termination evidence `adoptState` records in its eligibility today, or `{eligible: false, code, message}`, without changing the state. It keeps today's order: the controller checks first, then the native evidence map built from the request by `nativeEvidenceRequests`, whose validation refusals (`invalid-request` for an entry field that is not nonempty text, `invalid-worker-evidence` otherwise) still throw rather than returning an ineligible result, then the worker checks. `adoptState` calls it with its own request, adds the `sourceStatus` and `quiescenceEvidence` it records today itself, and throws on an ineligible result with the same code and message it uses today, so adoption's behavior, refusal codes and their precedence are unchanged. Its other checks (request identity and revision, self-adoption, status, resource mode and resources) stay in `adoptState`. Ready's call passes an empty request object, so the map is empty, nothing throws, and a worker whose termination needs native evidence reads as uncertain. The outcomes Ready can see are:

- A running record with no usable controller claim (`controller-activity-unknown`), a live former controller or one whose inactivity is unknown (`controller-not-inactive`), or a worker with active or uncertain work (`worker-activity-unknown`): the skill says the record may still be active and offers no pickup. For a running record whose former controller is live, it names [the stalled-owner stop](../features/stalled-owner-recovery.md) as the way forward once that feature ships, and until then says the owning session must stop it.
- Eligible: the adopt offer.

Release compatibility is checked by the launcher's adoption admission, which reads the release registry that Ready does not open: the exact retained release must exist, support the adoption protocol and use the same store. Ready therefore reports only the release conditions readable from the record itself, as above; a release-related refusal surfaces from `adopt` when the user accepts the offer, and the skill relays it. This narrows the settled commitment that Ready says why a run's release cannot be adopted to the reasons readable from run state, as the user accepted on 2026-11-01.

Process inspection is the runtime's own `ownerAlive` under its existing inspection budget. The former controller is inspected only for running records; the worker termination checks inspect worker processes for running and stopped records alike, and run only for records that pass the routing conditions. A failed or ambiguous inspection reads as unknown, never as inactive.

## Compaction

For each store that is available or unavailable only through the read bound, `runState.compaction` carries `{store, version, bytes, backup, due, finishDue, blockedBy}`: `version` is `PRAGMA user_version`; `bytes` is the store file's size; `backup` is whether the store's `.pre-compaction` file exists; `due` is true when `version` is below 3, `bytes` is at least 64 MiB and `backup` is false; `finishDue` is true when `version` is 3 and `backup` is true; a store below version 3 with `backup` true is neither, since `compact-history` refuses it with `compaction-backup-present`, and the skill reports that a pre-compaction backup sits beside an uncompacted store and must be inspected, offering no compaction; `blockedBy` lists the IDs of the store's running records when `due` is true and its rows were read, is null when `due` is true but the read bound left its rows unread, and is empty otherwise. The skill offers `compact-history` for a due store, saying it is blocked until the listed records stop when `blockedBy` is nonempty and that a running record would block it when `blockedBy` is null, and offers `compact-history` with `finish: true` for a store whose finish is due, both through the administrative migration entry. The compaction offer warns that sessions bound to a release before 3.3.23 can no longer use the project afterwards. A store with a surviving sidecar is in `unavailable` as `run-overview-busy`, as above, so no compaction entry is produced for it.

## Output

`runState` is `{records, compaction, unavailable}`, each an array, or `{error}` when `overview` itself failed. All three arrays are empty when neither store exists.

## Presentation

[The Ready skill](../../skills/ready/SKILL.md) presents a "Run state" section before the ready set whenever `records` or `unavailable` is nonempty, a `compaction` entry has `due` or `backup` true, or `error` is present, and omits it otherwise. Each record shows its kind, short ID, objective, status, age, stop kind and reason (omitted when `stop` is null, as for every running record and a held one, whose hold the record does not carry) and task counts, then, for a `present-report` or `adopt` pickup, that remedy phrased as an offer, and for a `none` pickup, its message as the reason no pickup is offered, worded for an eligibility refusal as the Pickup section says; an unavailable store is reported as unreadable with its cause, never as having no open records; and an `error` is reported as the run state having been unreadable this time, with its message, never as there being nothing to report. An `owned-by-this-session` record is shown as owned by this session. Ready performs no remedy itself: a yes leads to the existing operation (`adopt` under the user's authority, the report hand-off from the record's `report` path, or the migration entry's `compact-history`), each under its own admission and refusals, and selects no backlog work. The [Exploring skill](../../skills/exploring/SKILL.md), which uses the same parser, gains a sentence saying it does not present `runState`.

## Consumers

- `skills/ready/ready.js`: calls `overview` and emits `runState`.
- `skills/ready/SKILL.md`: presents it, and its sentence listing what the parser returns gains the run state.
- `skills/exploring/SKILL.md`: one added sentence saying it does not present `runState`.
- `internal/runtime/ownership.js`: `adoptionEligibility` extracted; `adoptState` unchanged in behavior.
- `internal/runtime/creation-consistency.js`: exports `reportAwaitsRecipient`; behavior unchanged.
- `internal/runtime/run-overview.js`: new; holds `overview` and the moved `runDatabase` and `parseRunState`.
- `internal/releases/service.js`: imports `runDatabase` and `parseRunState` from `run-overview.js` instead of defining them; behavior unchanged.
- `internal/runtime/review-inventory.js`: exports `reviewDatabase` and `parseReviewState`; behavior unchanged.
- `internal/runtime/history-compaction.js`: exports its backup and sidecar suffixes beside `STORES`; behavior unchanged.
- Tests that parse Ready's JSON output by exact shape: each is updated for the added field, which a search of `tests` and `skills/ready` locates at implementation time.

A session bound to a release before this one runs its original parser and sees no section, which also keeps the compaction offer from the sessions that compaction would lock out.

## Verification

- `tests/run-overview.test.js`: running records in each store; stopped records with each stop kind (`user-stop`, `resource-limit`, `adopted`) and with complete and incomplete tasks; a non-current stopped delivery (`not-current`); `owned-by-this-session`, `no-retained-release` and `not-development` records; a completed current selection with a pending report, including one owned by the invoking session, which gets `present-report`, one with no saved report (`report-unrecorded`), and one without a pending report, which is not reported; a retired current record of each status left out; the adopt outcome and each eligibility `none` outcome (`controller-activity-unknown` on a delivery and a review context, `controller-not-inactive` with a live and an unknown controller, and `worker-activity-unknown`), driven through injected `ownerAlive` and a saved worker termination record that makes the worker's record eligible; compaction due, below the floor, blocked, blocked unknown under the read bound, finish due, and a backup beside a store below version 3; a missing store, a store with each surviving sidecar, a missing store whose sidecars survive, an unsupported version, a row that is not JSON and one that fails the state check, and the 64 MiB bound.
- `skills/ready/ready.test.js`: the CLI passes its admitted context and the canonical project root to the overview and reports its result, and an overview that throws is reported as `runState.error`.
- `tests/runtime-*.test.js` for adoption: the existing adoption tests pass unchanged, and a new case adopts a running record whose controller is live while the request carries invalid `workerEvidence`, which must still refuse with `controller-not-inactive`, showing the extraction kept the checks' precedence.
- Ready's existing catalog-equality fixtures, which now also assert an empty `runState` for a project without run stores beside an otherwise unchanged report, and its `--check` fixture, whose report and exit codes are unchanged.
- Model-owned presentation in the skill is unverified by these tests. The user decided on 2026-11-01 to add an installed-host check, with no token limit set: Ready is run on a candidate installation of this change in an isolated Claude Code profile against a project whose run stores hold open records and an uncompacted store, and the presented section is checked against this spec. Codex presentation stays unverified unless checked the same way. [The live check](../reports/ready-run-state-live-20261101.md) records what was observed and which branches were not.

## Release

The change alters Ready's shipped behavior and the runtime, so it rides with a plugin version increase, a CHANGELOG entry and a regenerated payload manifest. [The runtime interface](../../internal/runtime/REFERENCE.md) gains a paragraph on `adoptionEligibility` and `runState`.
