## Recovery contract

Serialize writers for each canonical parent directory from the first recovery-record observation through verified cleanup. Use a persistent sibling `.nightshift-unwrap-lock.sqlite` database and an immediate SQLite transaction held for that interval. Fresh lock storage is exclusively created and initialized with its format, parent identity and own physical identity; existing storage must validate that ownership before use. An absent lock may be initialized, while an incomplete, invalid or substituted lock is preserved and blocks mutation. A competing writer fails promptly as busy without touching target or recovery evidence. Process exit releases the database lock through the operating system; retry reacquires it and rechecks durable state. Closing normally rolls back the lock-only transaction and closes the handle. The small ownership database persists, is never expired or routinely deleted, contains no backlog bytes, and is ignored by Markdown collection. Read-only detection neither creates nor acquires this writer lock. Verify lock-file and parent identity at mutation boundaries; changed or unavailable ownership fails closed. Initialize without disk rollback-journal sidecars and perform no database writes in the lock-only transaction. Bound existing lock storage to 64 KiB. Initialization failure leaves an explicit prerequisite diagnosis and the target unchanged.

Before changing a file, create and sync an exclusive sibling recovery record at the canonical target path plus `.nightshift-unwrap.json`. This suffix is reserved by unwrap, not Markdown content. The versioned record contains the original and replacement bytes, their lengths and SHA-256 hashes, canonical root and target paths, root/parent/target physical identities, and the existing meaningful file mode. The record is a complete immutable operation; it is never refreshed to adopt changed files. Limit each input and replacement to 16 MiB and each record to 48 MiB; oversized inputs fail before mutation. Validate strict shape, byte encodings, hashes, paths, identities and confinement before using a saved record.

Create the record only for a real byte change. If creation, writing, syncing or verification fails, leave the target unchanged and retain any created record for diagnosis. Existing records are never overwritten. Invalid or incomplete records block mutation and remain untouched; absence of a valid record never grants recovery authority.

Keep the target's existing physical object and write through its validated open descriptor. The recovery record must have been fully written, synced and read back before truncation. Revalidate the existing root, parent, target and alias authority immediately before writing. Verify actual target bytes, identity and meaningful mode after syncing. Delete the owned record only after successful verification, with its own identity and content checked before cleanup. A cleanup failure is an incomplete operation with recovery evidence retained. Do not claim protection against arbitrary hostile filesystem races or storage hardware that violates successful sync semantics; preserve the current identity-check boundary and test substitutions at observable mutation boundaries.

## Durable states and retry

Each file is an independent repair. Earlier verified repairs may remain when a later file fails; the command reports the completed files and the failure and returns nonzero. Stop further writes after the first failure. There is no whole-directory atomicity claim.

- No record: ordinary analysis applies. Unchanged files create no artifacts.
- Record creation interrupted or record invalid: the target has not been authorized for mutation by that record; preserve all available files and fail with a recovery diagnosis. Do not infer safety from apparently intact target contents.
- Valid record and the same target still contains the exact original bytes: a write invocation can retry the recorded replacement after all identity and alias checks. Read-only invocations report pending recovery and do not write.
- Valid record and the same target contains the exact replacement bytes: a write invocation syncs/verifies the target and finishes cleanup. Read-only invocations still report pending recovery.
- Valid record but target bytes match neither original nor replacement, or an owned root, parent, target or record has changed identity: preserve the current file and record and report a recovery conflict. This includes partial target writes. The original remains extractable from the record for explicit user-directed recovery; unattended code must not guess whether unfamiliar bytes are damage or a later user edit.
- Target verified but record deletion interrupted: the preceding exact-replacement rule finishes cleanup idempotently. After successful deletion, normal analysis resumes.

There is no automatic expiry or deletion of unresolved recovery evidence. A missing target, malformed record, changed mode, alias substitution, hard-link addition or unavailable verification is a failure, never a clean result. Recovery does not authorize recreating missing targets or adopting same-byte replacements with different identities.

## Consumers and reporting

Standalone unwrap write mode resolves pending records before ordinary wrap detection, even when a partially written file has no detectable wraps. Its check mode reports pending recovery without modifying anything. Both single-file and directory targets detect applicable records; directory discovery also diagnoses orphan records whose target is missing. Follow existing contained aliases to their canonical target and preserve alias identity checks.

Setup apply checks for unresolved unwrap recovery before migration/scaffolding can claim completion. With unwrap disabled or omitted it fails with the recovery location and preserves the pending files. With unwrap enabled it may resolve only the safe original/replacement states above, then continue normal setup and unwrap. Setup inspection reports incomplete recovery without mutating it. Ready reports pending recovery as a structural error rather than a clean empty backlog. Unwrap, Ready and setup share recovery detection so the file suffix cannot silently disappear from one consumer's view. Diagnostics name the affected target and recovery record and distinguish invalid evidence, conflicting content and a safe pending retry.

These checks also cover the legacy backlog before relocation. Setup recognizes validated lock databases as coordination artifacts, retains them in their original directories and excludes them from content relocation and reference rewriting; it does not copy or rebind their identities. Existing source locks are acquired for the migration's mutation interval, and busy or invalid ownership stops migration before relocation. A directory containing only retained coordination artifacts still has its logical backlog-content mapping relocated, while the physical old directory remains to contain the lock. Destination directories create their own locks on later repair. Invalid objects at reserved lock paths are preserved and diagnosed, not silently excluded as owned state. Verify standalone legacy unwrap followed by setup with unwrap both enabled and omitted, later destination repairs, interrupted migration and an active source lock. This extends only the lifecycle of the artifacts introduced here; ordinary migration still requires quiescent unrelated writers.

Recovery records are excluded from Markdown content collection by their non-Markdown suffix. Recovery discovery does not follow escaping directory links or reinterpret arbitrary similarly named directories as owned records. Recovery files have restrictive creation permissions where the platform supports them; broader Windows ACL assurance remains the existing separate feature. No journal is deleted merely because its filename looks owned.
