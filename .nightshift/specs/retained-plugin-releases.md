# Retained Nightshift releases

Governing design. Acceptance and delivery state are recorded in the runtime run, not inferred from this document's presence. The user agreed the retained-release direction, granted 16,000,000 aggregate live-probing tokens, and approved host-level setup with "host-level sounds good". The run began attended and the user subsequently handed it over for unattended delivery. There is no publication authority.

The [automatic preparation design](automatic-plugin-preparation.md) amends first-use preparation and Ready/Exploring admission. The corresponding commitments below reflect that change; the original acceptance report remains historical evidence.

## Outcome and scope

An installed-plugin update must not remove the workflow resources needed by an active Nightshift operation, controller, worker or resumable delivery run. New work may adopt the newly installed release; already-started work keeps the complete release against which it began. The fix covers both supported Windows hosts, all eight public skills, runtime operations, review receipt collection, and SessionStart, PreCompact and Stop integration.

The governing bug is "Installed plugin-cache replacement disrupts active runs" in the [active bug index](../BUGS.md), moved to [bug history](../BUGS_HISTORY.md) when fixed. On 2026-09-13, Codex session `01a09c60-dd6e-7d42-b8a0-7333fd211d92` read the 3.0.11 Ready skill, then failed to execute its script after that cache disappeared and 3.0.12 became available. The bug record carries this incident alongside the earlier active-review and receipt-import reports. The separate Ready recommendation bug is outside this implementation.

Autonomy comes first, independent quality second, then speed and economy, within authority and resource limits. A disappearing source is recoverable when the required complete release can still be established. Neither choosing the largest version string nor successfully opening the SQLite database proves runtime compatibility.

## Release identity and complete capture

Ship a generated, committed release manifest with every new release. It describes the complete retained runtime payload, including both plugin manifests, all public skill instructions and scripts, shared internal resources, hook resources and the license. Repository-only backlog, evidence, tests, CI and development scratch are not runtime dependencies. Packaging checks must detect a runtime dependency outside the declared payload and a distributable resource omitted from the manifest. The manifest itself is outside its own file-entry list; its digest identifies the manifest and is included in the retained bundle identity alongside the human-readable version. There is no installation-time build step: regenerate the manifest whenever payload bytes change, and make the release gate regenerate it from the candidate committed Git tree and fail on any inventory, version, length or hash difference. Include a stale-hash mutation control as well as omitted-file coverage.

The manifest lists each payload file's normalized relative path, byte length and SHA-256. Paths use forward slashes, are unique under the supported filesystem's identity rules, and may not escape the bundle or name links, devices or special entries. Raw committed file bytes are authoritative. Set repository attributes so every retained text resource and the manifest check out with LF on both hosts; binary resources retain their raw bytes. Hash and copy raw bytes without newline normalization or mismatch exceptions during capture. Update the obsolete Windows runner attribute when establishing this policy. Manifest schema and bundle compatibility are explicit. A schema the installed launcher cannot validate is unavailable, not implicitly supported. The manifest is an integrity/completeness baseline from the installed release, not a signature establishing publisher authenticity.

Read and validate the shipped manifest before enumerating or copying source files. Copy only its complete declared payload into a fresh staging directory, validate lengths and hashes in the destination, and verify the destination inventory contains exactly the manifest and its entries. Do not construct the expected inventory from a source directory already being deleted. Missing, changed, extra or unsafe payload entries prevent publication. Concurrent valid captures may converge on the same already-verified bundle; they must never combine partial copies.

Publish a verified staging directory atomically as an immutable bundle under a Nightshift-owned per-user store outside host-managed caches. Consumers cannot select staging directories. An existing verified bundle with the same identity can be reused; a corrupt bundle is quarantined from selection and never overwritten beneath a running consumer. Recovery reacquires the exact identity into a new validated location or reports unavailable resources. The store holds workflow resources and binding metadata, not project source or review evidence.

## Initial selection and the start boundary

Before any Nightshift operation begins, inspect whether the session or requested delivery run already owns a binding. A missing operation in the current turn is not evidence that an older run is unbound. Existing bindings follow the recovery rules below.

For genuinely new work, select the host's currently enabled Nightshift installation using the native plugin listing for the registered host/profile and its exact configured plugin identity. The invoking skill's root is a permitted initial source when it matches that enabled installation; it is not an alternative to checking enablement. Claude's listing exposes an installation path; a host whose listing omits a usable root needs a verified, versioned adapter to its installation metadata, with native fixture coverage for that adapter. Unreadable, unrecognized or contradictory listing/metadata is unavailable discovery, not permission to scan for the largest version directory or guess a root. If initial capture fails because an update removed or changed source files, discard that attempt from selection, rediscover the current enabled installation and retry its shipped manifest. This automatic switch is authorized by the user because no Nightshift work has begun. It does not require a new budget or implementation approval. Refresh the applicable skill and shared instructions from the release actually selected before carrying out the request.

The start boundary is publishing a durable session binding and admitting the first skill/runtime operation against it. No operation is admitted from a partially captured bundle. A capture alone does not create a delivery run or authorize implementation. Discovery and capture retries are bounded and stop with a recoverable diagnosis when no complete enabled release is available or updates keep invalidating capture. The implementation names the bounds in its interface and tests their exhaustion; waiting indefinitely is not recovery.

## Bindings, consumers and recovery

A session binding records host/profile identity, actual native session identity, bundle version and manifest digest, verified bundle location, creation/retirement state, and the canonical project roots and run identities attached to it. Its scope is that session's Nightshift work, including read-only Ready and Exploring use. A per-user registry indexes these references across projects; it does not discover projects by scanning the user's filesystem. Register a project/session reference before admitting its first operation, then attach the created run identity while retaining the provisional reference across any interrupted write. Delivery runs record the same binding in durable run state before dependent work. Workers and their saved assignments inherit the parent's binding and hold operation references until their actual termination is observed; reviewer and skeptic sessions never acquire independent permanent bindings merely because a host started them. Receipt collection and private probes use the bound resources. A new unrelated session may choose a newer release without changing any existing binding.

Work resources resolve from the binding: skill instructions and their relative references, setup and backlog parsers, runtime CLI/modules, runtime dispatch helpers, hook handlers, probe preparation and receipt validation. The administrative launcher and the closed Ready admission bridge described in the automatic-preparation design are separately verified administrative resources: they may use the current protected administrative bundle to admit and contain execution of the original bound Ready parser. This does not replace the parser, runtime or hook payload of existing work. The development checkout is a candidate source only when deliberately selected for testing; it is never an implicit fallback for a published release. Retained payloads are not edited in place.

On resume or compaction, resolve saved ownership and the bound bundle before running model-owned workflow instructions or mutating delivery state. A live session resuming a different run must reconcile that run's binding rather than replacing it with the newest session default. A surviving worker retains its original resources and receipt identity. Missing or unreadable binding/state is a recovery problem; do not manufacture a new run or conclude no work exists.

An active binding may recover automatically from any locally available copy that verifies as the exact manifest identity. Upgrading an active run to a different identity requires a separately defined and tested compatibility/migration path; this fix provides no generic automatic migration. Legacy sessions or runs without a manifest identity remain legacy and require explicit reconciliation against their recorded evidence. A newer runtime's ability to parse an old receipt alone does not establish compatibility. When exact recovery or validated compatibility cannot be established, preserve state, receipts and workers, report the dependent capability blocker, and continue independent authorized work where possible.

## Stable host entry points

Prepare and register a stable launcher in the actual host profile automatically when the user invokes a skill, while preserving an explicit setup maintenance operation and explicit removal. Use user-level hooks in the selected Codex profile's `config.toml` and the selected Claude profile's `settings.json`; do not replace either complete configuration with a template. Registration is outside plugin-owned hook discovery so cache removal cannot unregister the launcher. The shared store is per-user; registrations and session identities remain separate for each host/profile. The setup command verifies and publishes its launcher and initial bundle before installing references to them. It preserves unrelated configuration and never grants itself hook trust or disables host approval/security controls. When the requested operation requires host trust, explain its concrete native action in plain language and verify actual execution after trust is supplied. Preparation never grants trust.

Every installed operation requires complete retained resources and a consistent registration. Ready and Exploring use the closed `ready` entry exception and do not require trusted hooks or observed activation. Other ordinary entries, including unattended handover, require trusted, observed continuation; existing runtime diagnostics and maintenance retain their recovery permissions. Automatic preparation resolves missing setup without a separate setup conversation, while removal, deliberate disabling and configuration conflicts require explicit resolution. No silent plugin-only continuation fallback is allowed. Deliberately selected development/test execution remains available and does not claim installed-session retention or unattended continuation. Preserve the existing development capabilities through explicit selection, updating their documented command forms and affected fixtures together; do not preserve an ambiguous bare invocation by treating it as implicit development.

The admitted form for Ready, Exploring, init-backlog and the runtime-backed skills is a stable-launcher operation that resolves the session/run binding and dispatches the corresponding entry point inside that verified bundle. Current administrative admission supplies the Ready/Exploring exception for existing retained 3.1.0 bindings as well; the parser itself remains in their original bundle. The launcher and each executable entry point (ready.js, init-backlog.js, unwrap.js and runtime/cli.js) enforce the binding context and executing-root match; an unbound or mismatching by-path invocation is refused with a launcher/setup diagnosis, even if its cached script still exists. Skill prose directs callers to the launcher but is not the sole guard. A file deleted before Node can open it cannot execute its guard; the session uses the cache-independent launcher, or the initial pre-work discovery recovery, for that case.

The first argument `--development` explicitly selects unprotected execution from the invoked checkout/fixture for parser, setup and runtime CLI development use. It is never inferred from invocation by path, a missing binding or the target project's Git directory, and installed skill instructions never select it as recovery. The flag is the development-mode marker; preserve existing parser output schemas and record development mode in newly created runtime runs. Internal library APIs used deliberately by tests remain development surfaces, not installed entry points. Update developer command examples and negative CLI fixtures to pass the explicit flag and still reach their intended behavior. Helper subprocesses inherit their invoking operation's mode: bound parents pass their validated binding context to guarded children, while explicitly selected development/test parents propagate development selection. This applies to both Ready validation and unwrap calls inside setup; do not add an unconditional development flag to installed helper calls. Read-only runtime status/recovery diagnostics remain available without an installed binding or the flag. No discovery/recovery branch may silently substitute a development checkout for a missing installed bundle.

Setup records durable preparation before configuration changes. A verified launcher/bundle without hook registration is reusable preparation; matching installed hook entries with an unfinished setup journal are reconciled to registered-but-unverified status; absent entries can be installed after rechecking the current configuration; conflicting Nightshift-owned entries require a reported conflict rather than overwrite. In each case unrelated user edits are preserved. Registration supports continuation only after native invocation of the expected hook generation is observed. Ready and Exploring can use the registered retained resources before this activation. An already-open session lacking activation must restart or reopen only when required for a dependent operation, particularly when upgrading from pre-retention plugin hooks. Explain that concrete action when needed; a configuration write does not establish host activation.

On Codex, append owned entries after existing entries for each event. Positional hook-state keys are part of the configuration that must be preserved. Before removal or another index-changing edit, establish a complete mapping of the affected existing definitions and their current native hashes/trust/enabled state; carry surviving entries' existing state to their resulting keys only when their definitions and hashes are unchanged. Clear obsolete mappings so an untrusted survivor cannot inherit a deleted entry's trust. This preserves prior user trust; it does not create trust for new or changed Nightshift hooks. If a complete safe mapping or current configuration identity cannot be established, make no configuration change and report the conflict. Re-read the native listing afterward to verify surviving entries' semantics and trust, and retain the setup/removal journal until reconciliation succeeds.

The launcher dispatches to the session/run's bound hook handler. With no binding and no Nightshift project, SessionStart records only host activation and stays silent; it neither copies releases nor creates session bindings. With a Nightshift project but no work binding, it can identify the usable launcher without binding a release; initial capture and binding occur at the first explicit Nightshift operation. With an existing binding or run, unavailable required resources produce a qualified recovery message. The launcher does not start delivery work without authority. Stable registration must reach the same binding across startup, resume and compaction, and keep Stop tied to the actual run owner.

Activation records are separate from work bindings: at most one record per host/profile/native session identifies the observed hook generation, refreshes on genuine native activation, and becomes unusable when the registration generation or native trust changes. They never pin a release merely because a session opened and are retired with the named session or host registration. Activation uses the same registry serialization as admission, with a nonblocking lock attempt when no owned run is identifiable. A locked/unwritable store, unsupported schema or other activation-record failure in that case returns empty successful hook output without a session-visible warning or block; failure is available to explicit status/setup through the missing or unusable activation state, with best-effort diagnostics only where writable. Do not invent a successful record or require a second writable diagnostic location. Existing identifiable owners retain the qualified recovery diagnosis. An absent or stale activation record cannot admit activation-dependent installed work, which explains the required native action. The Ready/Exploring exception still requires valid retained resources and enabled registration, but no activation record.

Keep bundled plugin hooks only as a setup-prerequisite notice before usable registration. They perform no delivery-state mutation in the retained-release implementation and become silent when the host registration is usable under the current trust/activation checks; all continuation mutations belong to the stable registered hook. Both hook paths also obey the preceding no-owner activation-failure silence rule, so the bundled notice cannot surface a warning that the stable hook must suppress. Explicit Nightshift operations still diagnose their prerequisites, and identifiable owners retain recovery messages. A native listing that no longer reports the expected registration enabled and trusted invalidates its continuation usability and returns it to registered-but-unverified for dependent operations. Read-only view admission distinguishes missing trust from deliberate disabling. Setup/status and installed-operation admission perform this check; a still-callable bundled notice can diagnose the prerequisite subject to the same silence rule. A hook prevented from executing cannot emit its own warning, so passive continuation with externally disabled/untrusted hooks is an unavailable host capability, not guaranteed in-band diagnosis. Do not restore trust automatically. Update the package test to assert the mutation/notice split. Existing pre-retention sessions follow legacy reconciliation and the activation requirement above; installing a second handler into an already-running legacy session is not proof that double delivery is safe. Native checks must establish one lifecycle transition per event through first setup, restart and subsequent updates.

If automatic preparation cannot establish the required host-level registration, explain the blocked request and concrete recovery in plain language and preserve progress; do not claim seamless hook continuation from plugin-only recovery. This failure cannot silently weaken the promised active-run behavior.

The store-resident launcher provides its own status and host-removal operations, independent of the plugin cache or an enabled installation. Removing host registration removes only its exact owned hook entries after checking for conflicting edits, records the resulting disabled registration, and preserves bundles, bindings, run history and review evidence. A crash after hook removal but before the registry write resumes by observing the absent owned entries and finishing the disabled-state record; removal can be retried safely. It reports changed owned entries without removing them and leaves unrelated settings intact. The launcher/removal resources remain protected from collection while any host registration references them.

Disabling or uninstalling Nightshift must not turn the stable hook into a hidden continuing installation. Setup/removal documentation and status expose the registration and the cache-independent removal command. New operations require an enabled/trusted installation; an explicitly disabled or uninstalled plugin admits only status, removal, termination reconciliation and preservation of already-produced receipts, not new model work or engineering. User disabling of execution remains authoritative. With no affected binding/run the hook stays silent; an affected owner receives a qualified capability message. A missing cache with the plugin still enabled is resource loss, not evidence of an uninstall or permission to rewrite settings or clean bundles.

## Persistence and retention lifecycle

Creation proceeds through unselected staging, complete verified bundle, durable session binding, then admitted operation/run binding. A crash with staging only leaves no selectable bundle and can retry fresh. A complete bundle without a binding is reusable but confers no work authority. Administrative promotion preserves the existing native hook definitions/generation and records their former bootstrap as a retained route. Its registry commit protects the new administrative bundle before locator publication; an interruption before that commit leaves the old registration authoritative and a reusable unselected bootstrap. A session binding without an admitted operation is still protected from arbitrary replacement because admission may have been interrupted; resume verifies actual state before proceeding. A run binding with an interrupted session attachment retains its original identity, and reconciliation completes the attachment before dependent work. Every multi-write setup, attachment, worker handoff or retirement transition must likewise enumerate its partial durable states and deterministic recovery in the implementing interface and tests.

Refresh checks validate the selected identity when resources are acquired and after missing/corrupt-resource errors; they do not follow a moving newest-release pointer. Bound operations hold resource ownership until process/worker completion is observed. Crashed or disconnected sessions remain resumable references unless explicitly retired; process death or elapsed age alone does not release their bundle. Completing a run releases its active-run retention reference only after all workers are reconciled, while preserving the historical identity. A stopped unfinished run remains protected. Temporary worker operation references are released by their controller after observed termination; worker startup never creates an independent permanent session reference.

Provide explicit session/run retirement operations through the retained launcher. Status lists the exact identities, associated projects, active operations and protected runs before the user selects retirement. Retirement is the user's explicit decision to abandon guaranteed local recovery for those identities; refuse it while any associated operation or worker is active or its termination is uncertain, and require all associated run references to be complete or explicitly retired as well. Persist a retired tombstone before making that reference eligible for collection. An old session/run cannot subsequently resume by silently binding the newest release: it must explicitly recover the same identity if a complete copy remains available, or report that the retired resources are unavailable. Interrupted retirement is resumed from the tombstone, never inferred from age. This gives cleanup a usable release path without equating session disconnection with abandonment.

Cleanup is explicit and conservative. It enumerates the registry's session, project/run, registration and active-operation references under the same concurrency protection used for admission; it reconciles registered project state and retains resources when a registered project or its state cannot be read. It never deletes a referenced or uncertain bundle, and removes only complete unreferenced bundles or abandoned staging entries whose writer is established inactive. A failed inventory or ownership check means retain. Reports expose retained size and unresolved references rather than imposing an age-based deletion that breaks resume. No background cleanup is required by this fix. Launcher replacement uses compatible side-by-side versions and preserves the ability to dispatch existing bindings; removing registrations does not delete project run history or review evidence.

## Evidence and acceptance

Native feasibility observations on 2026-09-13, Windows, Codex CLI 0.153.4 and Claude Code 2.1.268:

- Codex expanded plugin-data hook paths outside the versioned cache. In one native session, a copied UserPromptSubmit handler executed before and after the fixture cache was moved away, with the latter handler observing its original root absent. Both turns stopped in the hook before inference, and Windows descendant cleanup was confirmed. This verifies that particular active-session hook path, not restart, compaction, Stop or delivery-run compatibility.
- A further Codex probe registered user-level SessionStart and UserPromptSubmit hooks in the isolated profile's `config.toml`, then explicitly trusted their observed hashes through fixture `hooks.state` entries. After the cache was parked and the native host restarted, `hooks/list` identified both handlers as trusted user hooks with no plugin identity; both executed from retained storage before inference. This proves the user-registration mechanism and its trust prerequisite for these two events. Raw evidence: `.tmp/cache-retention/codex-bootstrap-ffe8d5c5-6120-4131-a8d7-25bf522d12e2/inspect-5fd1f6f2-3782-4ad6-9637-f8633f01128c/native-results.json` and `native-events.json`.
- A repeated Codex restart checkpoint explicitly persisted source absence before native launch and after exit, both handler observations, process cleanup and source restoration: `.tmp/cache-retention/codex-recorded-restart-0109f254-e11a-4407-bc0f-0308c9d4c8e1.json`. A separate positional-trust probe inserted a preceding entry, observed an unchanged existing content hash become untrusted under a new key, and restored trust by relocating only its existing key. The fixture configuration was restored byte-identically. Evidence: `.tmp/cache-retention/codex-trust-position-d7329e51-e31e-49c0-95db-fa22263707e3.json` and `codex-trust-position.cjs`.
- Claude's local marketplace used the marketplace source as its resolved root. Moving only the cache was therefore an inadequate removal test. Removing the actual resolved root stopped plugin-hook invocation on the next prompt. Adding a user-level hook to the isolated profile preserved invocation after the same removal. The terminal results reported no API usage and descendant cleanup was confirmed. This establishes the host-registration direction for UserPromptSubmit, not the complete production lifecycle.
- Restarting Claude with that source still absent also invoked its separately registered UserPromptSubmit handler and returned zero API usage. This covers host restart for that handler, not SessionStart, compaction, Stop or runtime recovery. Raw evidence: `.tmp/cache-retention/claude-bootstrap-69da0e59-1319-43b6-84d3-6bbb68aaf1dc/inspect-f7eddfb5-19ed-43a5-a009-29c4d0a0b724/summary.json`.
- A repeated Claude checkpoint persisted source absence before launch and after exit, retained-hook execution, zero API usage, cleanup and restoration: `.tmp/cache-retention/claude-recorded-restart-4cc73ff5-dcba-4514-99b9-2a7f941b19cc.json`.
- Raw evidence is in `.tmp/cache-retention`; no actual user profile, installed production cache or model credentials were modified. The sandboxed Windows containment runner initially failed; its escalated isolated invocation worked. Host execution permission is distinct from plugin completeness.

Deterministic verification must cover manifest omission and unsafe paths; deletion/change at every capture boundary; incomplete staging; simultaneous captures and admissions; stable identity across new releases; missing/corrupt retained bundles; absent/stale/legacy bindings; receipt collection after source removal; every partially persisted transition; duplicate hook delivery; conservative cleanup; and install/remove/configuration preservation. Verify the real Ready parser after backlog reconciliation and the release gate against the publication baseline, with synchronized version/manifests and generated payload manifest.

Installed-host acceptance has separate claims on each host for initial capture, automatic rediscovery before work, blocked initial capture, first skill use, explicit development selection, rejected unbound installed-script invocation, activation-record failure in unrelated projects, existing-session source removal, resumed run and compaction, Stop continuation, active review removal, receipt import after removal, unavailable exact recovery, disabled/untrusted hooks, trust-preserving setup/removal, later trust invalidation and duplicate-registration handling. Each remains `(live-claim: provisional)` until that exact behavior is observed. The UserPromptSubmit feasibility probes do not cover these distinct claims. Use isolated profiles and candidate installations; never remove the user's live cache to test the fix.

The aggregate live-model allowance is 16,000,000 tokens for live checks of installed behavior, including cached input, retries and additional model participants in those checks. Ordinary implementation, independent spec/code assessment and skeptical validation are outside this allowance, as the user clarified on 2026-09-14. Controller-owned estimates, reservations and stop thresholds may be adjusted within it. Capture finalized native usage, keep interrupted/unmeasured usage qualified, and verify termination and spending controls before model campaigns. Native host operations that stop before inference have no model-token charge. The controller conversation is separate from this live-probing campaign. Preserve an auditable ledger and headroom for in-flight work and recovery; do not equate a delayed usage threshold with a hard token cap.

Independent whole-spec assessment and user agreement precede implementation. Delivery then requires revise-code with skeptical validation and cumulative reassessment, revise-docs/backlog reconciliation, revise-lore and follow-up triage. The final report distinguishes implemented behavior, deterministic evidence, observed installed-host claims and remaining limitations. Publication requires a later user instruction.
