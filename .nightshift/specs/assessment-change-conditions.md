# Assessment change conditions

## Outcome and authority

Preserve independent assessments as evidence about what they examined while engineering continues. Intermediate reviews guide work; only an unresolved consequential question holds work that depends on its answer. The final release gate establishes assurance of the actual candidate. Pending assurance is deferred work, not a waiver, degraded result or reason to ask for bypass approval.

This draft develops [the vision](../../VISION.md#record-decisions-without-locking-them) and [the assessment worklist](../reports/assessment-worklist-20261018.md). Implementation coverage and verification are recorded separately in [the candidate report](../reports/assessment-applicability-20261104.md); this design does not itself supply implementation or publication authority. The owning final-gate exception policy is linked below; its host evidence and persisted contracts still require implementation design and verification. [The parallel spec-review feature](../features/implement-beside-spec-review.md) owns review scheduling; [the open-run feature](../features/handover-open-for-triage.md) owns the closing sequence. Both records name this draft as their assessment-currency design context.

## Intermediate reviews and scheduling

A later edit does not erase an assessment or automatically block the task it covers. Record what changed and preserve outstanding findings and coverage obligations. An unresolved consequential dependency holds only the affected work, with the question, cause and route forward visible. The controller cannot turn a broad assessment-currency flag into a blanket implementation hold.

The main cumulative code review normally waits for spec review to settle, avoiding token spend on an assessment likely to be invalidated. The controller may start it earlier only when outstanding spec questions cannot materially change what it would assess and early feedback would prevent meaningful rework, with that reason recorded. The intended runtime permits this exception without making parallel review routine; since 3.3.34, spec readiness holds only a code task's completion and run completion, as [Spec readiness as a condition](spec-readiness-conditions.md) settles. When the benefit or stability cannot be established, wait for spec settlement and continue independent authorized implementation.

Do not request a relevance turn after every intermediate edit. Schedule assessment when it informs a consequential engineering decision or establishes the coverage needed at final acceptance. A changed spec can require reassessment of affected coverage and interactions; compatible corrections do not automatically erase all prior evidence. Material changes to commitments still need the user's authority.

## Preserve evidence and explain applicability

File drift in the canonical project alone must neither discard a returned assessment nor refuse its import. Keep its original snapshot, assignment and attributed result. Verify provenance, reviewer independence, resource binding and the identity of the actual private copy reviewed. A changed private copy that no longer matches its assignment is a different failure from later canonical edits and cannot be treated as valid evidence about that assignment. Evidence bound to earlier commitments remains attributed to those commitments and cannot silently count for amended ones.

Compare against the recorded assessment scope, including explicit inclusions and exclusions. Inventory snapshots include additions and removals as well as modifications. Do not retrospectively narrow an old assessment to the diff, a directory or the paths its report names. Retain the existing Git-equivalent line-ending treatment. Evidence outside a changed scope needs no relevance decision, but scope must include the requirements and context on which the assessment relied; unchanged source bytes alone do not establish unchanged applicability. For the bounded release, preserve spec assessments' existing governing-artifact scope, include explicitly selected deciding context in `artifactPaths`, and compare accepted commitments. The broader private project copy is orientation and probe context, not an implicit whole-project spec-currency binding. A spec reviewer assesses that declared deciding set. If a deciding conclusion requires an additional input outside it, the reviewer returns incomplete and names the required project-relative paths in `summary`, without silently relying on undeclared deciding inputs; the controller can then arrange a new assessment with the needed declared scope. When no additional deciding input is needed, ordinary assessment of the declared set continues. This model-owned scope-completeness reporting has no installed-host evidence (live-claim: provisional on Claude Code; live-claim: provisional on Codex). Broader spec-context policy is deferred; unrelated implementation and closing edits do not reopen spec assurance. Code and docs assessments retain their recorded project-context binding.

Status identifies affected tasks, assessment kind and identity, changed project-relative paths, known coverage gaps and the next useful action. It includes completed tasks and changes made without a repair transition. No differences means no input-change condition. A comparison that fails or encounters missing, corrupt, unreadable or unsafe evidence is not a clean result. Report the structural failure and preserve the obligation. A lightweight status that skips comparison says currency is unevaluated. Status inspection writes no state.

## Independent applicability decisions

When applicability needs deciding, resume the originating reviewer or use the supported independent replacement route. Supply the original assessment, intervening changes, current commitments and relevant context. The reviewer may preserve applicability with a reason, require reassessment, or leave it unresolved. The controller's assertion is not an independent relevance decision.

Bind the answer to the original assessment, named tasks, commitments and exact inputs considered. Preserve it separately from the original receipt. An answer preserving applicability does not convert a resumed turn into a fresh assessment, discharge pending finding closures or settle checks. A reassess or unresolved answer remains a coverage obligation after later edits until a later independent preserving decision settles it, a fresh assessment establishes a new basis, or exact original reversion restores original coverage. A later preserve settles the older negative obligation without approving subsequent inputs; those inputs return to ordinary applicability comparison. A failed answer supplies no settlement. New findings follow validation and disposition. A shared assessment can retain applicability for one task without settling its siblings.

Later changes require a new applicability comparison; a decision does not cover new content merely because the same paths changed again. Reversion to the original inputs restores their original coverage only where the commitments and relevant context also match. Keep superseded decisions as history. A valid unique later decision supersedes an earlier answer; malformed identities or decision ordering that cannot identify a unique successor fail closed rather than selecting a permissive answer. Replacement reviewers independently examine the decision's basis rather than inheriting a favorable answer.

## Final release gate and exceptions

The final release gate requires applicable independent review and verification covering the actual candidate and its integrated behavior, with agreed obligations fulfilled and required findings resolved or explicitly settled by the user. Earlier applicable assessments can contribute; unrelated clean reviews whose interactions remain unassessed are insufficient. Final repairs require the affected assurance to be established on the resulting candidate. Neither a time limit nor a passing subset of checks establishes missing coverage.

Readiness and publication authority are separate. An explicit acceptance of named unmet obligations must identify the candidate, missing evidence and consequences, and must be recorded separately from what evidence established. It does not waive ownership, provenance, safety or the user's limits. No user answer means no exception. With no user available, preserve the question and continue independent authorized work.

The [manual-gate-bypass record](../features/manual-gate-bypass.md#direction) owns exception approval, reporting and renewal policy, including the independently verified reply to the exact briefing without a confirmation code. Applicability cannot turn an exception into evidence or supply publication permission. This approval boundary remains unverified on Claude Code and Codex (live-claim: provisional on each host).

## Session close

The [open-run feature](../features/handover-open-for-triage.md#agreed-direction) owns the complete session-close sequence, publication choice and completion stamp. For this currency design, the deciding invariant is that the candidate covered by assurance, user authority and completion evidence is the same. Post-report repairs and tracking edits need affected assurance before the final stamp. A later finding returns to its affected decision or repair without replaying unchanged report delivery, retrospective or settled triage.

Recovery must distinguish a publication already performed from a failed local stamp, partial or uncertain external effects and deliberate user takeover. Applicability or a report acknowledgement alone cannot discharge those closing obligations.

## Bounded implementation and lifecycle

The evidence foundation may be implemented independently of the full closing lifecycle: preserve original assessments through canonical drift, expose applicability gaps and support attributed relevance decisions at acceptance boundaries. It must not claim the new end-to-end workflow while old intermediate barriers remain. Spec readiness, finding validation, probe currency and closing-baseline rules remain worklist commitments whose consumers must be reconciled as their behavior changes. Standalone assessment completion retains its assurance obligations and does not acquire a publication ritual merely because delivery close does.

Define persisted state at its governing module, including creation, initialization, scope, refresh, invalidation, bounds, absence and failure behavior. Missing decisions mean no settlement; malformed or conflicting records cannot select a permissive answer. Enumerate every reader and writer of affected currency and decision state, including cross-task, status, repair, recovery, completion and closing consumers. Clearing or replacing state must preserve its obligations, explicitly settle them or fail closed. Undefined branches are omissions, not permission to continue.

Local evidence and its admitted decision must be crash-consistent and retryable without duplication. Define deterministic recovery after every successful write and external action. Unavailable reviewers and denied or unavailable approval leave the relevant obligation pending with an explanation. An old record lacking new fields cannot imply new approval or completion evidence.

## Verification and remaining design

Exercise drift during assessment, before import and after import; changed private copies; changes outside scope; added, removed and unreadable inputs; requirements and context changes; old records; shared and completed tasks; relevance outcomes and replacement; subsequent edits and reversion; duplicate admission and interrupted persistence. Verify that findings, checks and closing duties remain owed independently and that intermediate applicability gaps do not categorically block unrelated engineering.

For exception approval, exercise a valid explicit reply to the exact briefing without a code, an ambiguous reply, a reply to another briefing or candidate, controller-authored text, missing or unreadable native history, duplicate admission, affected exceptions requiring renewed approval and unrelated changes preserving it. For the closing implementation, exercise final repairs, user publication versus takeover, absent answers, partial and uncertain publication, candidate changes, and recovery after external success before the local stamp. Define the stamp and approval record shapes before implementing those persisted contracts. Validate actual reviewer relevance behavior, spec scope-completeness reporting and the chosen approval mechanism separately on Claude Code and Codex; unexecuted branches stay provisional. Real-model campaigns require an explicit aggregate budget.

Reconcile shipped instructions, status and every affected consumer with the implemented boundary. Record the actual scope of each release, retain unfinished worklist obligations and apply the repository's version, manifest and focused verification requirements. This draft authorizes no publication.
