Independent assessment, checked by six further reviewers

# Nightshift Assessment

repo **astenlund/nightshift** commit **76c8654** plugin **3.3.12** date **2026-10-18**

**What this document is.** Nightshift is a Claude Code and Codex plugin that carries agreed engineering work through implementation, independent review, skeptic validation, verification and a morning report, with durable run state in SQLite. This page is an outside-in assessment of its implementation and backlog, made on 2026-10-18 at the commit above by one model context that read the repository cold, then verified and qualified by four further independent model contexts that had no access to the first one's reasoning, and two more in the maintainer's checkout two days later; their corrections are applied in place and recorded below. It is advice to the maintainer. It carries no authority of its own: the repository's AGENTS.md still governs, nothing here is a backlog entry, and nothing here authorizes implementation. An agent acting on it should treat each item as a proposal to confirm with the maintainer, and should read the "Fortnightly check" section before adding anything to the backlog.

**Verdict.** The direction is right and the execution has drifted into the failure mode the vision itself warns against. The three-role review structure (reviewer, skeptic, fresh gate) and content-bound evidence are a real idea nobody else ships. But five and a half weeks after 3.0.0, almost every release, every runtime line and most of the backlog serve the machinery rather than the product, and the project's own records show cost and reliability both going the wrong way.

## Terms used here

Controller

The model session that owns a run: it implements, dispatches reviewers, records evidence through the runtime CLI and writes the report.

Lead reviewer

A fresh strong model given the whole cumulative change in a read-only private copy. Its report is a receipt.

Skeptic

A fresh model that validates each reviewer finding against evidence and returns confirmed, refuted or unverified with a repair proposal.

Resumed closure

After a repair, the reviewer that raised a finding is resumed in its own session to record whether the repair closed it.

Fresh gate

Only an assessment from a reviewer in a fresh context can pass a review gate; a resumed reviewer never can.

Minor-only cycle

A repair batch whose repaired findings all carry severity minor, followed by the resumed closure and fresh gate the rules require.

Closing record

The run-level record that reviews tracking edits made after follow-up triage, with its own docs review, findings and checks.

Check, probe

A check is a command the controller runs and records with its input hashes. A probe is a command a read-only reviewer asks the controller to run in a private copy.

Retained release

A manifest-verified copy of the plugin kept outside the host's plugin cache, with a registry of sessions, hook generations and activations, so a run keeps its release across updates.

Continuation

What keeps a handed-over run going when the controller yields: a Stop hook on Claude Code, a persistent goal on Codex, with a reminder budget kept by the runtime.

Backlog

Four Markdown indexes under `.nightshift` (features, bugs, quick wins, patterns) with breakout records, read by the `ready` parser, which resolves `Requires` dependencies.

## Findings

**The product's core claim is unmeasured while its plumbing is over-proven.** Trust is supposed to come from review catching defects. The only evidence that it does is one README anecdote, and the backlog entry "Measure whether the lifecycle catches defects" sits in Exploring. Meanwhile about 800 lines, store integration included, implement tamper-evident reminder accounting (schema-2 progress markers, `reminderHash`, `discharge_index`, `accounting_commits`, transaction-private discharge capabilities), and 1,195 lines plus 1,714 test lines implement content-addressed retirement certificates for legacy run records. The adversary this defends against is the user's own controller in the user's own session, which already runs with the user's privileges, and no substitution of saved state by a controller has been observed. The one substituted-state case on record, a newer runtime importing an older run's state after the host replaced the plugin cache, is a release problem that the bundle copy addresses. The project's own record for the manual gate bypass says "deliberate tampering is outside the user's threat"; the provenance tables ignore that sentence. VISION.md says machinery must be proportionate to the consequence it prevents. That sentence applies to `internal/runtime/progress-store.js`.

**Cost is not under control, and the backlog records it without acting.** The figures in the table are the project's own. The cause is structural, not tuning. Every repair, however small, triggers resumed closure plus a full fresh assessment. Any edit discards every piece of evidence keyed on the whole-project digest, including host-behavior probes that have nothing to do with the edit. Reviewers re-run suites the controller already recorded (seven observations in one quick win). The documentation stage sits after review. Since 3.3.4 a code review stale only through backlog, record or root-Markdown edits counts as current once a docs review covers the task, but an edit under `docs`, `skills` or `internal` still stales it, and the brief now holds tracking edits for the documentation stage, where the code lead raises the unfinished move as an important finding (the 2026-10-17 recurrence): the contradiction moved rather than closed. VISION.md's sentence "repair size does not restrict coverage" costs nothing by itself; the expensive rules are the ones WORKFLOW.md and the operating brief build on it: resume the raiser after every batch, then a fresh lead, and "repairing any of its findings resumes that reviewer and repeats the cycle". They are asserted, not measured.

**Autonomy is not holding either.** Runs strand on a hook-generation change, lose activation after `/clear`, overflow a Codex context without compacting, refuse engineering because the acknowledgement landed in a thinking block, refuse handover because the session log passed 64 MiB, and reopen an accepted spec because the user answered a yes/no question. Each is a bug in or around a mechanism whose purpose is to keep the run going. Two of the six come from the retained-release system, which also costs 1.4 to 1.7 seconds per hook; two from the native acknowledgement observer; one from the lifecycle's own semantics, the unblock that reopens an accepted spec; and one, the Codex overflow, from the host, which the runtime neither caused nor detected.

**The instructions cannot be followed by the models that must follow them.** A controller is pointed at about 25,000 words of reference material plus the skills, of which the 15,000-word runtime reference is mostly narrative invariants about accounting. The backlog concedes the result in the entry on skeptic ordering: "the operating brief and the runtime reference already state the rule in plain words, so the text alone does not hold." The same pattern recurs elsewhere in the records: the acknowledgement route failing in five runs, a controller inventing its own budget ceilings, agent-directed rules echoed to the user as quotations, and the skeptic ordering broken three times in one run. About twenty-one of the 68 quick wins ask for a sentence in the brief or a skill. Adding sentences to a document that is already not read is not a fix. The finding needs one distinction: the resume-then-fresh cycle is not a sentence but a store gate, since `repair` marks every repaired finding as pending closure and every gate waits on it, so changing it is runtime work; the same rule is also restated in prose in the `rules` string every `status` response carries, a third copy beside the brief and the skills, reviewed as code and tested by nothing.

**The backlog is larger than the code and tells Ready nothing.** 205 active entries and 243,000 words of backlog prose stand against 14,600 lines of bundled JavaScript. 164 items are "ready" because no top-level feature in this repository declares a dependency, so here the dependency walk does no work; the maintainer reports it earning its keep in other projects, and the parser's link, anchor and grammar checks still earn their fixtures. Entries are incident logs: dated recurrences, verbatim user quotes, run UUIDs and token counts, with 107 copies of "Tracking does not authorize implementation" and 119 mentions of "version increase". One design decision, "evidence is keyed on a whole-project digest and any difference discards it", is filed as eleven to thirteen separate entries. About 29 further sentences across the three indexes say "coordinate with", "whichever ships first" or "relates to": each is a dependency or merge decision deferred into prose, which the dependency walk cannot see and the agent selecting either entry must re-derive. The fifty most recent commits, all this shallow clone can see, are documentation commits from one day of inbox triage; that shows where such a day goes, not the overall cadence.

## What to remove

- **Reminder accounting, provenance commits and discharge capabilities** (`internal/runtime/progress-store.js`, `provenance-store.js`, `discharge.js`, the accounting parts of `creation-consistency.js` and `store.js`). The Stop hook in `internal/runtime/hook.js` already blocks while the brief's `next` list is non-empty or workers are unreconciled; keep that idleness test and replace only the accounting behind `store.remind` with a three-reminder cap the runtime derives from new receipts, checks and task transitions, so that no request field can set or replenish it. A few dozen lines, no hashing.
- **Legacy migration and certificates** (`internal/runtime/legacy-*.js`, `migration-*.js`). The repository's 45 legacy records are retired. `store.js` imports its table definition and the creation gate reads its certificates, so this is surgery rather than a move: cut a new store version that refuses older stores and delete the code. Today it ships to every user in the payload.
- **Native acknowledgement observation** (`internal/runtime/native-acknowledgement.js`, `acceptance-checkpoint.js`). Reading the host's session log to verify that a "Handover accepted" paragraph was printed is fragile by construction, and relaying the text from the runtime would verify nothing either. Drop the check, put the paragraph in the `handover` result, and accept whether the model prints it as model-owned behavior. That removes two of the six autonomy bugs, one still open and one fixed in 3.3.13, and the tail read that 3.3.13 added for histories over 64 MiB, and it is the registry's main runtime consumer after `entry.js`, so it goes on its own in step 4, under a 3.3.x version increase, before the release system is reduced in step 5. No store table changes, but the obligation is written into run state at creation, renewed on unblock and adoption, gated on every engineering action in `cli.js`, exposed in status and the progress markers, and named in three instruction files, the 47 tests of its two suites and fixtures in eight other suites, plus the shared claim fixture several more suites load, so the removal is of an obligation, not of two modules; the continuation outcome stays gated independently. Whether the paragraph remains as model-owned guidance in the `handover` result is the maintainer's decision.
- **Most of the retained-release system** (`internal/releases`). Keep the manifest-verified bundle copy made on first use, and what a hook-reachable bundle needs with it: a stable bootstrap, the locator, hook registration and the session-to-bundle lookup, roughly 700 lines in all. The host does replace the plugin cache mid-run, and a pinned version with no code behind it would leave every in-flight run dead. Drop the generations, activations, hook re-registration and the adoption compatibility matrix, where the release bugs and the hook cost live. Adopting a stalled run needs only the ownership and dead-process check. The runtime imports this layer in sixteen modules, twelve once the legacy files go, and the run state carries its identifiers (`executionResources`, checked by `store.js` on acceptance replay and exposed in status), so this reduction and the store cut below are one breaking change, not two.
- **From the backlog:** recurrence paragraphs out of the index entries and under one evidence heading in each record, since they are the only cost data the project has; the version-increase boilerplate; and most Exploring drafts (operational UI, Claude Code mods, Night Guard, user proxy consultation, model instinct map, keyword-scored question ledger, workflow composition, GUID-anchored principles file). Keep a one-line ideas list.
- **The lifecycle on tracking prose.** Chat-agreed documentation already runs direct. The expensive case is tracking edits inside a run's closing stage, 13.6M tokens in one run: make the closing docs review of tracking edits optional, or make those edits after `complete`.

## What to add or change

- **Mine the receipts before building a harness**, as a script in `tools/` rather than a day of queries. The run store holds every finding, verdict, disposition and closure for 47 runs, 45 of them completed, with 475 validate and 202 repair transitions; the 864 receipts under `.nightshift/runs/reviews` cover these runs (805) and three standalone review contexts (59). Count skeptic refutations, fresh-gate catches after resumed closure, minor-only repair cycles, tokens per batch, tokens per task and elapsed time per task, and classify each current quick win and bug by origin by hand: original implementation, review fix or instruction change. The script's first run decides whether a seeded-defect suite is worth building and tests two of the maintainer's reports that later items rest on. The "Fortnightly check" section says where each number comes from; the stores live on the maintainer's machine, so this is not a job for a cloud agent.
- **Then seeded-defect measurement, with the criteria written first.** The lifecycle's claim is that independent review catches defects, and nothing measures it: the only evidence is one README anecdote, and the acceptance campaigns were few, expensive and graded by reading. The Exploring record "Measure whether the lifecycle catches defects" is the vehicle and already holds the open questions. Anthropic's test-and-evaluate guidance applies directly: specific, measurable, achievable and relevant criteria; fixtures that mirror the real task distribution with its edge cases; automated grading; volume over quality; code grading wherever a ground truth exists. Criteria, with targets set from the first run's baseline: detection rate, the share of planted defects a fresh lead cites at the planted location; false-positive rate after skeptic validation, findings confirmed on changes that contain no defect; severity accuracy against a written rubric; skeptic accuracy, verdicts matching the planted truth with decoys included; tokens per fixture; and, for a smaller set of fixtures that run a repair, a resumed closure and a fresh gate, the fresh-gate catch rate, meaning planted defects the resumed closure passes and the fresh gate catches. Two things the design must settle: a reviewer finding today carries id, severity, consequence, evidence and required but no location, so either the report schema gains a location field, which the feature "Keep every affected surface when merging findings" already proposes, or the grader parses the evidence text and the design says so; and a true finding outside the agreed scope is graded correct when it is raised and disposed as out of scope, not when it is implemented. Fixtures: thirty to fifty small project states, each with an agreed outcome and a change holding zero or more planted defects drawn from the real defects in BUGS.md and from defects fresh gates actually caught, plus the edge cases: clean changes, a defect in a sibling path outside the diff, a true finding outside the agreed scope, and decoy findings for the skeptic. Run one fresh lead and its skeptic through the runtime's own `buildPrompt` without the rest of the lifecycle, grade by location and verdict match with no model as grader, and rerun on every prompt or model change; a rerun is 60 to 100 dispatches, so state its token budget as AGENTS.md requires. The one small-fixture campaign on record, the resumable-reviewer campaign of 2026-10-01, measured 1,352,189 tokens over 24 dispatches, about 56,000 each, while this store's fresh lead receipts on real changes run about 1M at the median and 3M at the ninetieth percentile on Fable and Astra, about 2M at the median on Sol's five, and about 7M to 25M on Opus across the 3.3.13 delivery and two standalone review contexts of 2026-10-19 (one of that delivery's reviewers read outside its copy, an effect on usage the bug record leaves unmeasured), so a rerun on small fixtures is of order 3M to 6M tokens and fixture size, not reviewer choice, dominates; the first run's tokens-per-fixture reading sets the budget of later reruns. A cheaper resume changes little here: only the smaller set of fixtures that run a resumed closure is affected. Check Anthropic's evals cookbook and the `claude plugin eval` runner before writing a harness. Every decision about review depth, resume versus fresh, and dual review is blind without these numbers.
- **Scoped evidence.** Checks, probes and reviews declare the paths they depend on. A host-behavior probe declares none and survives any edit; review staleness compares the already computed `changedPaths` against the directories the diff touched, and `repair` stops clearing `task.probeEvidence` on every repair. This closes the evidence-invalidation cluster and the staleness that documentation edits under `docs`, `skills` and `internal` still cause.
- **A repair rule the numbers can defend.** The fresh gate stays mandatory. Resumed closure only for critical and important findings; minor repairs are closed by the controller's check evidence and confirmed by the fresh gate, which reads the cumulative change anyway. Cost then scales with batches, so dispose the whole batch before repairing, as the brief already asks. This is a lifecycle change before it is a brief change: `repair` sets `pendingClosure` on every repaired finding regardless of severity and every gate returns unmet while one is pending, so the gate, the brief, the skills and the status `rules` string change together. The resume-cost record reserves this floor change for the maintainer's decision, so it ships only after the experiment under "Resumed reviewers" has been read; until then today's rule, resume then fresh for every repaired finding, stays live.
- **Fix the review prompt's incentives** in `buildPrompt` in `internal/runtime/review.js`. It tells the lead to return incomplete with probes when evidence is missing but never shows the recorded checks, so on one run 11 of 20 passes came back incomplete and nine asked to rerun recorded suites. Attach the latest passing checks with their input hashes, say that a passing check on matching inputs is evidence, state the probe-copy layout, and say what the controller-supplied `rules` slot must not contain, since it is placed verbatim in the reviewer's system prompt and a controller pasting the brief into it multiplies every dispatch.
- **Define severity.** The report schema enforces critical, important and minor, and the loop's cost hangs on the distinction, but no prompt text defines the levels.
- **Token limits that bind.** Receipts record a token count per attempt since 3.3.3, so a `maxTokens` limit summed from receipts is an edit to `internal/runtime/limits.js` and status, stated in the readback and respected by the Stop hook, which today calls `exhaustedLimit` without the dispatch flag and so stops a run on the deadline alone; the new limit needs its own branch there. It bounds the runtime's own dispatches only; the controller's usage is invisible to the runtime and stays outside any limit. `maxDispatches` is not a budget.
- **Rewrite the operating brief** (`internal/workflow.md`) as a per-stage checklist under 1,500 words over the real operation set (36 runtime actions, about 18 on the happy path), with example requests. Move invariants to a design document no run loads. The existing backlog entry "Separate run-time guidance from reference material" is the right vehicle. Much of the handover skill's 1,238 words describes migration and acknowledgement mechanics that go with the removals above. Shape the result to Anthropic's skill-authoring guidance, which Nightshift follows at the top two levels (SKILL.md bodies of 12 to 34 lines, third-person descriptions with triggers, scripts for deterministic work) and inverts at the third: a handover is told to read the brief and the whole runtime reference before its first operation, about 20,000 words including 2,005 words of administrative migration content no ordinary run needs; revise-code and revise-spec link about 8,700 words by section anchor; none of the three files has a table of contents, and no skill carries a checklist. State the targets in words, since every file here is already under Anthropic's line limits (the brief is 4,898 words in 97 lines because the repository keeps paragraphs on single lines). Compliance here means four things: each SKILL.md becomes a table of contents plus a checklist of what precedes the first `status` call, under 400 words; the runtime reference splits one level deep along its own sections (start and observe, claims and adoption, standalone contexts, delivery and evidence, handover and report, independent assessment, documentation review, staffing and follow-ups, continuation hooks), each under 2,000 words with a contents list and the request and response shapes of its operations, with the migration section moved to the administrative branch; invariant narratives move to a design document no skill links; and once a run exists `status` names the operation, fields and reference file due, and the skill says to do what status says, so the procedure has one copy and disclosure follows the run's state; the operation and fields ship with the scoped-evidence release, the reference file due with this rewrite. Before a run exists, and for hooks and standalone contexts, the skill names the file. The entry's settled direction is one operations guide; a split by stage amends that commitment, which is the maintainer's call when the governing spec is written.
- **Fold documentation into implementation** so one cumulative review covers code and docs, and the docs review gates only documentation paths. Since 3.3.4 the runtime already relieves backlog, record and root-Markdown edits; this extends the relief to every documentation path and removes the held backlog move that the code lead now raises as a finding.
- **Backlog hygiene.** Index entries under 150 words. Records with four fixed sections: problem, decision, open, evidence. Declare the dependencies that exist here, since the `Requires` walk earns its keep in other projects and only this backlog leaves it idle. Declare every other relation between entries through the agreed Related field (the feature "Related field for non-dependency relations", settled on 2026-10-04 and not yet implemented: no index carries a Related line and the parser checks only `Requires` and `External`, so Related lines written before it ships are unchecked): a `Requires` line where one entry must ship first, a merge where two entries are one feature, otherwise a Related line on both entries whose sentence names what is shared and who defines it. Quick wins take Related and never `Requires`. "Coordinate with" and "relates to" are not declarations.
- **Drop the Windows-only coupling.** The deterministic suites pass on Linux with process inspection stubbed by the fixtures (delivery 73 of 73, review 66 of 72 with four skipped), so the coupling is confined to the PowerShell process-ancestry walk behind claims and activation, the settings writer, the Codex signature check and the 1,030-line job runner. The case for it is weaker than first stated: a minority of bug entries mention Windows, PowerShell or the job runner at all, no sentence in VISION.md, WORKFLOW.md or the README names adoption by others as a goal, and the Exploring record "Native helper for Windows process work" already frames the work as performance. It goes last, and only if adoption becomes a stated goal or that record's performance case is measured.
- **Cut v4 now, as one breaking release.** With every legacy record retired and the store clean, this is the moment for a new store version instead of another migration, and the release reduction belongs in the same cut because the run state carries the registry's identifiers. Minimal v4: handover and tasks; check with the scoped paths from the item above; dispatch fresh or resumed with receipts; validate, dispose, advance; a complete gate of fresh checks plus one fresh assessment; a Stop hook that blocks while `next` is non-empty with a runtime-counted three-reminder cap; a SessionStart brief; morning report and triage. Running runs complete before the upgrade, and the run that delivers v4 runs on 3.3.x. Keep self-hosting for code under the cheaper repair rule once it is adopted; stop running the lifecycle on prose.
- **Change the repair step as one delivery, not four.** The maintainer reports that most of the quick wins and bugs now in the backlog came from review fixes, which the origin classification in the first item tests, and that deferring minor findings to close runs faster saved nothing, which follows: the cost is per cycle, not per finding, so a deferred item still pays its cycles and then costs a delivery of its own. The four things that make a fix good are three filed entries and one runtime requirement: a check that fails before the repair and passes after it (the feature "Reproduce a bug with a failing check before repairing it", whose record scopes it to defect work and keeps the runtime unchanged, so applying it to every repair widens that scope and should say so); the fixer tracing every reader of the state it changed before closing the batch (the revise-code tracing quick win); the smallest repair that meets the obligation (prefer the smallest repair); and a stated approach before the edit, which the skeptic's `repairProposal` already supplies in part, since the runtime refuses a repair without one, and which the repair conversation would complete with the implementer's own approach checked against the reviewer; the first version uses the existing `repairProposal` alone, with no reviewer turn. Ship the three entries as one change to the repair step, editing the status `rules` string with it, in a version of its own only if the fresh-gate catch rate can be read within a fortnight by repair batch across every project's store, and otherwise with the scoped-evidence release; no instruction rule can tell whether fixes got better, that number can, read slowly and confounded by reviewer model changes.
- **Treat instruction files as code, with the eval as their test.** A code change has an oracle, a check that fails before and passes after, so its review findings are decisive. A prose rule has none, so reviewing it is opinion against opinion, its findings are wording, each repair is more prose, and the loop converges slowly: eighteen spec reviews with thirty minor findings is what that looks like. The maintainer reports more defects from instruction changes than from code changes, which the origin classification also tests. Sort the brief's rules into three kinds and move two into the runtime. Procedure, meaning which operation comes next with which fields, becomes the runtime's instruction: today `status.next` lists the ready tasks with their stage and review state, and its `review` field already names the review-stage class due (validate and dispose, repair, resume or fresh assessment) with resume and fresh targets, so the extension derives an operation and its fields from what the response already carries, after which a skill says to do what status says. Enforceable invariants that are not yet gates become gates, such as validating a finding against the snapshot of the review that raised it (the skeptic-ordering bug), a deferral route that resolves to a recorded follow-up or entry (today only a non-empty route is required), and refusing unknown request fields; stale skeptic evidence and a repair without a proposal are already refused. Only judgment stays as prose, a few hundred words, and the `rules` string that `status` emits on every call either goes or carries the same text as the brief, since it is a third copy today. Validate a change to the brief or a review prompt by rerunning the seeded-defect suite rather than by a docs review of its wording. Giving such a change one code assessment and no prose review loop before the suite exists would contradict VISION.md and AGENTS.md, which keep independent review and user approval for instruction changes, so that is a document decision for the fortnightly question below, not a rule this page can set. Rules of the form "if this then that" for rare conditions are not recalled when the condition occurs, so a recurring failure is countered mechanically, not with another sentence.

## What to keep

- **The three-role review.** Reviewer, fresh skeptic, and a gate only a fresh reviewer can pass.
- **Receipts bound to input hashes**, with completion refused on stale evidence. This is the one gate that matters.
- **SQLite state restored through hooks** across compaction and closed sessions.
- **Read-only reviewer copies**, with probes as untrusted proposals the controller executes.
- **The manifest-verified bundle copy** that keeps a run's code alive across a plugin update.
- **The deterministic test corpus and the release gate.** 19,600 lines of tests that run on Windows CI and, with inspection stubbed, on Linux, and a gate that refuses an unversioned behavior change.
- **The Opus and Sol cost defaults** and the cap below max reasoning effort.
- **The evidence discipline.** Every changelog entry separates deterministic evidence from model-owned behavior, the two most important fixes (defect measurement, guidance separation) were filed before this assessment, and the resumed-reviewer record is already the per-host cost measurement for that question, down to compaction trials. The problem is prioritization, not blindness.

That is the product. Everything else should have to earn its place against the detection numbers the project does not have yet.

## Resumed reviewers and the repair conversation

After the assessment was written, the maintainer named the two intentions behind reviewer resumption and a planned rework. The backlog records that own this ground are "Make resumed reviewers actually cheap" and "Show review progress without being asked", which carries the per-attempt cache categories; "Adversarial repair dialogue" is a v2 record whose reviewer-to-skeptic dialogue shipped in 3.3.0, and the implementer-to-reviewer turn described below has no entry of its own unless the maintainer's second record covers it. These lines belong beside those records, not as new entries.

**The two intentions.** Continuity: the reviewer that raised a finding is the best judge of whether a fix closes it. Economy: it already knows the issue, so it need not research again, and its session may hit the prompt cache. The planned rework turns resumption into a conversation in which the implementer checks an approach with the reviewer before applying it.

**Why the economy has not shown up.** A resume is cheap only when the host serves the session's history from the prompt cache, a prefix match: a hit costs 0.025x of the input price on Fable 5.1 and 0.05x on Opus 5.5, roughly forty and twenty times cheaper than a miss, and on a miss a resume is not reliably cheaper than a fresh review, since it replays its history at full price and still reads the changed files from the new private copy the runtime gives it; one Fable resume cost 500,544 tokens against 819,505 for its fresh pass, and resumes elsewhere cost as much as fresh ones. The resume-cost record shows the misses are not a timing problem. Claude's writes already use the one-hour lifetime. In the companion-project run of 2026-10-08, two resumed Fable assessments read nothing from cache and wrote 219,536 and 352,468 cache-creation tokens; in the Hermes runs of 2026-10-16 to 18, Opus reviewers resumed 3.7 to 12.4 minutes after a last call that had read 73,000 to 137,000 tokens from cache read nothing on their first call and wrote 79,000 to 114,000, and eight more in another Hermes run, resumed 2.3 to 37.9 minutes later, wrote 125,000 to 242,000. A direct resume of a small Claude session from a different directory, made outside the dispatcher and without a schema, hit the cache, though it was a 3,000-token probe whose evidence is gone. Something in the dispatch changes the prefix, and on Codex the new directory itself is not ruled out. The record names two candidates: the per-dispatch JSON schema, which `schemaFor` binds to the new request id, a skeptic's assigned finding ids and a resume's closure fields and `hosts.js` passes as `--json-schema`, and which the record says Claude turns into its structured-output tool, where a per-dispatch byte change would invalidate everything after it if tools render first in the prefix, as Anthropic documents; and a synthetic "No response requested." assistant record that precedes the resumed prompt in every missing session examined. Neither is verified, and the schema differs between a review and its resume by construction on both hosts: a closure resume adds a required closures property bound to the pending finding ids and a dialogue turn its positions, and Codex receives the schema as `outputSchema` on every turn.

- **Test the two candidates first, outside any dispatch.** Repeat the 2026-10-03 probe with `runClaude` and `runCodex` in arms with no schema, the same schema on the fresh call and its resume, and a schema differing only in the request id enum, and on Codex also from the same and from a new working directory; about 3,000 tokens per arm settles both candidates for cents in an hour, and the hitting Claude session's history then shows whether it carries the synthetic record. A byte-identical dispatch schema is not achievable, since closures and positions bind finding ids known only after the review; if the schema is the cause, the fix is a lineage-constant schema: drop the request id enum, which `validateReport` already checks; give every dispatch in a lineage the same property set, with `closures` and `positions` always present as optional unbound arrays and no per-turn `findings` bounds or skeptic id enum; and check all of these after the fact, as `validateClosures` already does. Then each closure and dialogue turn reads its history from cache on its first call instead of rewriting it; the record shows later calls already hit, and that resumed rounds which hit still read about as many tokens as a fresh pass, so the saving is that first call's write, which the per-attempt cache recording below measures. Until the prefix is stable, keep-alives and longer windows cannot help.
- **Record cache reads per attempt.** Claude's result reports cache-read and cache-creation tokens, and `hosts.js` sums them into the one `tokens` figure an attempt keeps. Keeping the categories per attempt shows on every run whether the premise holds, instead of in a one-off trial.
- **The conversation is arm B of an experiment, not yet a rule.** Consult the reviewer on the approach, implement, run the checks, then let the fresh gate confirm: two dispatches per batch instead of three, and a reviewer that approved an approach is no longer independent on closure anyway. The runtime already has the relayed dialogue turn, the skeptic's repair proposal and positions on findings; the missing piece is a turn that carries the controller's proposed approach and returns approve, adjust with a reason, or object. The resume-cost record says that resuming only for closure falls below the maintainer's own review-loop routine and needs their decision, so this is for the maintainer to choose on measured results.
- **One turn per reviewer, kept out of the fresh gate.** Batch every finding the reviewer raised into one message, as the brief already asks for dispositions, and never hand the approach discussion to the fresh lead, which receives acknowledgements only.
- **The experiment.** Arm A is today's rule, resume then fresh, and stays live while the experiment runs; arm B is consult then fresh; measure tokens per batch and what the fresh gate finds afterwards. The receipts of the retired runs already supply arm A, and the result means little until the cache question is settled, since what a resume saves changes the arithmetic for both arms.

## Fortnightly check

A full assessment like this one costs several hundred thousand tokens of reading and gets its value from fresh eyes. Repeating it every two weeks would anchor on the previous page and would tend to produce backlog entries, which is the pattern this page criticizes. The recurring part should be a script and a short pruning pass, with a full assessment only at a milestone (after the v4 cut, after the brief rewrite) or when the numbers move the wrong way.

### Eight numbers, every two weeks

Record each with its date in one file, so the trend is visible. Numbers 1 to 4 and 7 come from the run store and the receipts, which live on the maintainer's machine under each project's `.nightshift/runs`; the other projects' runs (Hermes, McpTools, the companion) live in those projects. Numbers 5 and 6 come from the checkout, and number 8 from the checkout's bug and quick-win indexes, classified by hand. The first run establishes the baseline for the store-derived numbers; the baseline for 5 and 6 is in the table above. A reading on 2026-10-20 at 3.3.13, 43 commits later, gave 209 active and 167 ready entries and 31,319 instruction words, both the wrong way before the first check; the runs-completed half of number 7 is readable without the script: 45 completions from 47 runs between 2026-09-13 and 2026-10-18, by fortnight 5, 30 and 10 (the first a partial fortnight from the store's start on 2026-09-13), and 202 repair batches. The three readings of the maintainer's goals are 8 for fewer review-fix defects, 5 for a backlog that stops growing, and 7 for features built faster.

| # | Number | How |
| --- | --- | --- |
| 1 | Tokens per completed task | For each run's latest state, for each task, sum `attempts[].tokens` over every dispatch receipt on it, and keep `threadTokens` beside it. An attempt's `tokens` is null when unknown, as for a Codex output loop; count those separately, never as zero. Before 3.3.3 a resumed Claude attempt recorded the session's cumulative total in `tokens` and had no `threadTokens`, so for those receipts subtract the continued receipt's `tokens` instead of summing. |
| 2 | Tokens per repair batch | Group the dispatches between one `repair` transition and the next fresh assessment import, using the `kind` and `revision` columns of the `history` table, which the runtime's `history` operation lists without state. A `review` row does not say fresh or resumed; the receipt's `continues` field does. The median and the worst batch both matter. |
| 3 | Skeptic refutation rate | Over every `task.findings[].validation.verdict`: refuted divided by confirmed plus refuted plus unverified. Only the latest verdict per finding survives in `runs.state`, since re-validation replaces it, and closing-record findings sit on the closing record rather than on a task; the skeptic receipts hold every verdict if the history matters. A low rate with high cost means skeptics are not earning their dispatches; a high rate means reviewers are manufacturing findings. |
| 4 | Minor-only repair cycles | Share of `repair` transitions whose repaired findings, matched by `repairRevision`, all carry severity `minor`. Each such cycle is one the cheaper repair rule would have avoided. |
| 5 | Active and ready backlog entries | `node skills/ready/ready.js --development . --check`; count `ready`, `blocked`, `external` and `exploring`. If the active count has not fallen after two checks, the pruning pass is decorating the backlog rather than pruning it. |
| 6 | Instruction words | Word count of every instruction file a `skills/*/SKILL.md` links, transitively, plus the skills themselves, one total; today that is the brief, the two references and the eight skills, 29,463. Counting by links keeps a split from lowering the number while agents read the same words; a design document counts only once a skill links it. `wc` is not native on the verified PowerShell host, so use Git Bash or a Node one-liner. This number should fall below 10,000 after the brief rewrite and stay there. |
| 7 | Elapsed time per completed task, and runs completed per fortnight | From `history.recorded_at`: the task's `start-task` transition to its completing `advance`, and the count of `complete` transitions in the fortnight. The direct reading of features built faster. |
| 8 | Review-fix bugs filed per fortnight | Entries added to BUGS.md or QUICK_WINS.md in the fortnight whose origin is a review fix, by the classification the first run establishes and each later pass keeps up. The direct reading of fewer review-fix defects. |

Where to read: `.nightshift/runs/state.sqlite` holds each run's latest state as JSON in `runs.state` and every transition in `history` (`run_id`, `revision`, `kind`, `recorded_at`, `state`); `kind` is the request action for lifecycle transitions such as `repair`, `review`, `validate` and `dispose`, plus a few internal kinds. Read the state column of `runs` and only the metadata columns of `history`, or use the runtime's `history` operation: each history row carries a full state copy, and this repository's store was 7.6 GB on 2026-10-11. Receipts live under `.nightshift/runs/reviews/<requestId>/receipt.json` with `kind`, `model`, `findings`, `continues`, `threadTokens` and the attempts; `internal/runtime/review.js` and `hosts.js` define the exact shapes. One extra question belongs to the first run only, not to the fortnightly list: how often a fresh gate after a resumed closure raised a critical or important finding. That number decides whether the resume-then-fresh cycle is worth what it costs.

### The pruning pass

A backlog check that asks whether entries align with VISION.md and WORKFLOW.md would pass this backlog: nearly every entry justifies itself in the vision's own language, and the most expensive machinery was built in faithful service of sentences those documents still contain. The useful check is narrower and runs in both directions.

- **Intake first.** The fold rule, filed in the index preambles after the assessed commit and shipped as the feature "Fold fixes into the feature that replaces their code", which routes a fix into the feature that would remove or rewrite the lines it touches instead of a new entry, is the admission test for every new entry. An entry that reached an index without passing it is the first thing the pass retires.
- **Entries changed in the last two weeks only.** Ask of each the four questions VISION.md already states under "How this guides the transformation": what user outcome it serves, which observed failure it prevents, whether that failure still exists in the intended workflow, and whether its value warrants the complexity and recurring cost. The only permitted outputs are keep, merge or retire. The check never creates an entry.
- **One question of the documents.** Which sentence in VISION.md or WORKFLOW.md did this fortnight's evidence contradict? If the maintainer's beliefs have moved and the documents have not, the backlog will keep aligning with a document the maintainer no longer agrees with. The answer is one proposed sentence change, for the maintainer's decision. The first such question is already known: whether instruction changes keep a prose review loop or are tested by the eval instead.
- **The first pass is bigger.** Apply the fold rule retroactively over the current quick wins and bugs, and resolve the roughly 29 relation sentences into a dependency, a merge, a Related line with its shared-ownership sentence, or nothing; Related lines written before that feature ships are unchecked, so ship it first or accept a sweep later. Later passes cover only the fortnight's changes.
- **Budget.** The eight numbers, the entries of the fortnight and the two documents: under an hour of a strong model's time, and no reading of any previous assessment, so each pass forms its own view before comparing.
