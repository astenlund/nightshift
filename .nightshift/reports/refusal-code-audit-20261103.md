# Refusal-code audit

Audit of every refusal code the Nightshift runtime can emit, classified against the principle VISION.md records under "Record decisions without locking them" (2026-11-03): hard refusals are reserved for provenance, ownership and safety; review coverage and verification are obligations of trust that hold only the work depending on them and show as incomplete; everything else is a condition shown with its cause and way forward; evidence goes stale only where a later change reaches what it examined, and whether a change inside that bears on the assessment is the reviewer's call; a recorded user decision that a condition is settled is a way forward. The audit is the input the refusal-friction pattern record (`.nightshift/patterns/refusal-friction.md`, Open section) asks for; it measures, it does not propose a re-sequencing.

Repository `C:/Git/nightshift`, branch `main` at commit `9fb0220b` (clean working tree), read on 2026-11-03. Every count comes from two scripts that were kept beside the audit in the session scratch folder and are not in the repository: `inventory.js` (finds every refusal site and writes `inventory.json`, `inventory.tsv`, `inventory-by-code.tsv`, `active-codes.tsv`) and `totals.js` (joins the inventory with `classes.json`, the per-code classification, and writes `tables.md`, whose sections are copied below, then corrected by hand on 2026-11-03 where a review found a summary figure wrong: the `unsafe-path` count, the fed-sites count with its exclusion clause, the friction-map row count and the sentence disclosing the four-code gap). The classification itself is judgment from reading each call site; the scripts make the counts and the coverage mechanical (`totals.js` exits nonzero if any active code lacks a class or any class has no site).

## Mechanism

Every runtime refusal is a `RunError` (`internal/runtime/errors.js`): `{name: 'RunError', code, message}` thrown by `requireCondition(condition, code, message)`, by `requireBound`, which additionally sets `limitExceeded: true` so that `creation-consistency.js:resourceLimit` can tell a bound from a defect, or by `new RunError(code, message)` directly (11 sites). `errors.js:text(value, name)` is the one site behind every nonempty-text field check; `inventory.js` counts 84 `text(` calls under `internal/runtime`, all of which reach that single `invalid-request` site, so the per-code table under-represents `invalid-request` by design.

What reaches the caller: `cli.js:main` catches the error and writes `{"error": code ?? "operation-failed", "message": message}` as one JSON line to stderr, with `process.exitCode = 1`. No other field exists: no `route`, no `nextOperation`, no structured cause. Whatever way forward a refusal names lives in its message text alone. The `status` response (`lifecycle.js:obligationBrief`) is the other carrier of the way forward: `next[].stage`, `next[].review {next, resumeTargets, freshDue, freshTargets}`, `next[].reviewCurrent`, `next[].docsReviewCurrent`, `next[].specAcceptance {recorded, current}`, `staleChecks [{taskId, name, reason}]`, `closing {ready, stage, docsReview {current, satisfied}}`, `blockers`, `docsExemptions`, `scratch.notices` and the `rules` string. A refusal never points at the status field that explains it. The Stop hook (`hook.js:handleHook`) does not surface codes: a refusal inside it becomes `{continue: false, stopReason: '... (code) ...'}` naming only the code, or a `decision: 'block'` reminder.

`internal/releases` uses its own `ReleaseError` through `io.js:requireValue` (and `bootstrap.js` a two-argument `requireValue` that throws a plain `Error` without a code); `launcher.js` and `bootstrap.js` print the same `{error, message}` shape. Those sites are inventoried but, as the brief directs, only counted by module under the slated group.

## Method and scope

- Sites: every `requireCondition(`, `requireBound(`, `new RunError(`, `requireValue(` and `new ReleaseError(` under `internal/runtime` and `internal/releases`, parsed with balanced parentheses so multi-line calls count once; the helper definitions themselves are excluded. 993 sites, 359 distinct literal or expression codes. Nine active sites pass a code expression rather than a literal; the table "Expression-coded sites" lists each with the code it is counted under (for example `ownership.js:adoptState` rethrows `adoptionEligibility`'s verdict code, counted as `adoption-ineligible`, the three codes `controller-activity-unknown`, `controller-not-inactive` and `worker-activity-unknown`).
- Slated: a site is slated when its module is one the assessment worklist's Remove 1 to 4 schedules for removal (`progress-store.js`, `provenance-store.js`, `discharge.js`, `progress.js`, `creation-consistency.js`, `legacy-*.js`, `migration-*.js`, `native-acknowledgement.js`, `acceptance-checkpoint.js`, `acknowledgement.js`, everything under `internal/releases`) or is the `remind` method of `store.js` (the accounting behind `store.remind` that Remove 1 replaces). Two judgment calls widen the brief's list: `progress.js` holds the accounting's semantic layer (`semanticFacts`, `validateFrontier`, `validateClosingTransition`) whose only codes are `progress-evidence-unavailable` and `progress-frontier-unavailable`, consumed by the three modules Remove 1 names; `acknowledgement.js` is the obligation Remove 3 removes. `creation-consistency.js` is counted under Remove 1 although Remove 2 also names its certificate reads. Five codes with sites in kept modules read only what Remove 1 or Remove 2 deletes (`retired-run` and `legacy-run-state` read `legacy_retirements` and `.claude/runs`; `close-accounting-unavailable` and `invalid-reminder-state` read the reminder accounting; `migration-evidence-bound` fires only under the budgets the creation gate and the legacy modules pass); they are classed `slated-by-content` and kept out of the lifecycle totals. Remove 4 keeps the bundle copy, bootstrap, locator, registration and session lookup, a line that runs through `service.js` and `registry.js`; which of their 132 sites survive is not resolved here.
- Classes: the brief's six, assigned from the condition tested, plus one the brief does not list: `environment`, for a tool or infrastructure failure (`git-failed`, `host-start-failed`, `executable-not-found`, `operation-owner-unavailable` and the like). Those are neither malformed requests nor conditions the workflow tracks, and counting them as friction of any kind would be false. A code whose condition straddles classes keeps one primary class for the count and carries its branches in the table ("split"); twelve codes are split.
- Active: 452 sites over 230 codes outside the slated modules. The lifecycle classes (provenance, ownership, safety, obligation, bookkeeping) hold 219 of those sites over 102 codes; validation 201 over 109; environment 18 over 14; slated-by-content 14 over 5.

## Reading the totals

- Hard refusals the principle reserves (provenance 63 sites, ownership 36, safety 69) are 168 of the 219 lifecycle sites. Most of them refuse a receipt, a worker or a store write, not a controller's next step: `changed-assignment` (8), `unattributed-review` (10), `unsafe-path` (8), `run-closed` (6) are integrity checks a controller meets only when something is actually wrong.
- Obligation holds 21 sites over 11 codes. Three of them refuse unrelated progress: `spec-review-required` holds every action on the code task, a repair of an unrelated finding included; `review-required` and `docs-review-required` at `complete` hold the whole run for any task's gate. The rest hold only the task or finding that depends on them, as the principle allows.
- Bookkeeping holds 30 sites over 21 codes: lifecycle ordering (`retrospective-required`, `report-required`, `closing-required`, `closing-before-work`), re-recording rituals (`stale-validation`, `stale-dialogue`, `stale-probe`, `stale-evidence`, `repair-proposal-required`, `missing-repair-proposal`), path classification (`closing-scope`), and the inventory-wide staleness branches of the obligation codes.
- The number that matters for the user's complaint is not the class count but the staleness lever: eleven codes, through 17 of their 21 active sites, the other four refusing over dispositions, the receipt path or model admission, fire from one comparison over a snapshot of the whole project inventory, carried by `evidence.js:fresh` and, for the closing baseline, `changedPaths` (every tracked and untracked file outside `.nightshift/runs`, `.nightshift/inbox` and `.tmp`). Two of the nine rows in the friction map below, holding three refusals between them, go through it (the closing ritual's two refusals and `closing-scope`), and two more (the spec cases) go through a declared-path comparison whose declared set reached what a later stage edited. Narrowing what a snapshot covers (worklist Add 3) changes every one of those sites at once; reclassifying codes does not.
- After the scheduled removals, 541 of 993 sites go (284 under Remove 4, 127 under Remove 2, 114 under Remove 1, 16 under Remove 3) plus 14 slated-by-content sites, leaving 438 sites, of which 219 are lifecycle refusals. The removals take out almost no lifecycle friction: the slated modules refuse migration, accounting, release and acknowledgement conditions, not reviews, checks or closings.

## Staleness: every place that decides evidence is stale

### The comparison primitives (`internal/runtime/evidence.js`)

- `snapshot(root, paths)`: `{digest, files: [{path, sha256, blob?}]}` over the named paths, sha256 of each file's bytes (null for a missing file), `digest` the sha256 of the JSON of `files`; with Git available, `blob` is the Git object id of the same bytes, kept only when a write stamp proves nothing changed between the two reads (`verifiedBlobs`).
- `inventorySnapshot(root, excluded, included)`: a `snapshot` over `projectInventory`, which is `git ls-files --cached --others --exclude-standard` less `.nightshift/runs/`, `.nightshift/inbox/` and `.tmp/`, with `inventory: true` and the exclusion and inclusion lists. This is the whole reviewable project.
- `fresh(root, evidence)` and `freshAll`: an evidence record is fresh when its `files` is nonempty, its `digest` still matches its `files`, for an inventory snapshot the current `projectInventory` path list is exactly the recorded path list (one file added or removed anywhere in the project makes it stale), and every recorded file's current sha256 equals the recorded one; a byte change is tolerated only when the current content's Git blob id equals the recorded `blob` (a CRLF renormalization). Judging never throws: an unreadable entry or a failed inventory counts as not fresh.
- `changedPaths(root, evidence)`: for an inventory snapshot, the sorted set of paths added, removed or byte-changed without renormalization; null when the inventory cannot be read.

Whether a change outside what the evidence examined can stale it therefore depends only on the path set the snapshot was taken over. Two kinds exist:

- Declared-path snapshots: a check's `paths`, a spec review's `artifactPaths` (default the task's `agreement.spec`), `agreement.specSnapshot` and `task.specAcceptance.snapshot` (the spec file), the morning report (`reportEvidence.sha256`). Only a change to a declared path can stale these. They already meet the principle's scoping rule; their remaining friction is that the refusal does not name the path (see `verification-required`) or that the declared set was too wide (the 41e7d80c spec review that listed the feature record).
- Inventory snapshots: every code, docs and skeptic review's `snapshot` and `contextSnapshot` (`review.js:dispatchReview` sets `captured = contextSnapshot` for every kind but spec), every docs exemption (`inventorySnapshot` at `advance`), and the triage baseline (`lifecycle.js:triageBaseline`). Any file change anywhere in the project stales these, whether or not it bears on what was assessed. The reviewer did receive the whole inventory in its private copy, so nothing is strictly "outside" what it examined; but the principle's test is whether the change bears on the assessment, and that judgment is never asked. The runtime-written `onboarding.seen.busy_input_prompt` line in Hermes' `config.yaml` is the recorded example.

### The deciders

1. Lead review gate: `lifecycle.js:reviewGateFailure`. Takes the latest acceptable lead assessment (`leadEntry`), requires `fresh(root, review.snapshot)` (inventory for code and docs tasks; the spec files for a spec task), with one relief: `documentationRelief` accepts a stale code assessment when `changedPaths` are all documentation paths (`isDocumentationPath`: the seven backlog files, the four documentation directories, root Markdown other than host instruction files) and a current docs review covers the task. Also stale by decision rather than by file: `acceptableAssessment` rejects an assessment whose `revision` is below `task.requirementsRevision` or whose bound `commitments` differ from the task's current agreement, which `unblock` with a `user-decision` blocker causes by raising `requirementsRevision` (lifecycle.js:transition, case `unblock`). Feeds: `review-required` (`requireReviewGate` at `advance` and `requireStandaloneAssessment`; the stale branch gets the `STALE_REVIEW` message, the decision branch the generic one), `stale-review` at `complete` (`reviewGate` over every task), status `reviewCurrent`, `staleGateEntries` and `freshTargets`. A stale check reaches this gate too (`verificationGate` inside `reviewGateFailure`) and is reported as `'unmet'`, so the refusal reads as a missing assessment.
2. Docs gate: `lifecycle.js:docsReviewFailure` and `docsGateFailure`. `fresh(root, review.snapshot)` of the latest covering docs review (task-level or closing), inventory-wide, no relief; or a fresh `task.docsExemption.snapshot` (inventory-wide). Feeds `docs-review-required` (`requireDocsGate`, `requireStandaloneAssessment`, `advance` of a docs-reviewed task, `complete`) and status `docsReviewCurrent`, `docsExemptions[].current`.
3. Verification gate: `lifecycle.js:verificationGate`. For each latest named check, `check.passed && !check.pending && fresh(root, check.snapshot)` over the declared `paths` (`operations.js:reservedCheck` snapshots before and after, `evidence.js:verifyCommand` likewise). Feeds `verification-required` (`advance` of a code task's implementation stage, documentation and retrospective stages, `complete`, standalone), `review-required` and `docs-review-required` as `'unmet'`, `closing-review-unresolved` for the closing record, and status `staleChecks` with reason `inputs-changed`, `failed` or `pending`.
4. Spec readiness: `lifecycle.js:specReady`. Either `agreement.specReviewed === true` with `agreement.specSnapshot` (the spec file) fresh, or the spec task complete with a passing `reviewGate` (its reviews' snapshots are the spec's `artifactPaths`). Feeds `spec-review-required` in `assertAction` (every task action on the code task), `start-task` and `complete`, and status `stage: 'governing-spec-review'`. `specAcceptanceCurrent` compares `task.specAcceptance.snapshot` (the spec file) and feeds only status `specAcceptance.current`; no refusal reads it.
5. Import-time freshness in `lifecycle.js:transition`: `check` requires `fresh(request.evidence.snapshot)` (declared paths) else `stale-evidence`; `review` requires `fresh(review.snapshot)` else `stale-review`; `validate` requires `fresh(validation.snapshot)` else `stale-validation`, where the skeptic's snapshot is its `contextSnapshot`, the whole inventory; `dialogue` requires `fresh(reply.snapshot)` (inventory) else `stale-dialogue`; `dispose` requires `fresh(finding.validation.snapshot)` (inventory) else `stale-validation`. The disposition one is the widest: a repair of one finding on any task stales every undisposed validation on every task until each is validated again.
6. Dispatch-time freshness in `review.js:dispatchReview` and `readReceipt`: `snapshot-drift` when `fresh(contextSnapshot)` fails after the private copy is made (the copy would not match its manifest); `review-input-drift` when `inputsUnchanged(root, kind, captured, contextSnapshot)` fails after the host returns, or the copy no longer matches the manifest, which discards the whole dispatch without writing a receipt; `invalid-receipt` when `inputsUnchanged` fails again at import (`readReceipt`); `stale-commitments` when a covered task's agreement or `requirementsRevision` changed since the dispatch bound them. `inputsUnchanged` is inventory-wide for code, docs and skeptic kinds and spec-file-only for spec. `attachedChecks` (not a refusal) attaches to a dispatch only checks whose declared paths are fresh.
7. Probe evidence in `probes.js`: `runProbe` requires `fresh(receipt.contextSnapshot ?? receipt.snapshot)` (inventory) before and after copying the fixture (`stale-probe`), and again after the command (`probe-input-drift`, which still writes the result file); `loadProbeEvidence` silently drops saved evidence whose `snapshotDigest` or `contextDigest` differs from the new dispatch's snapshots, so every re-dispatch after any file change loses all probe evidence; and `lifecycle.js:transition` case `repair` sets `task.probeEvidence = []`, so every repair discards the task's probe evidence outright (the bug "Probe evidence about the host is discarded on any edit"). Probe evidence about host behavior depends on no project file, yet it is bound to the inventory digest.
8. Closing coverage in `lifecycle.js`: `triageBaseline` records `inventorySnapshot` at `triage` (or, outside Git, the documentation files on disk); `closingCoverageFailure` computes `changedPaths(root, record.baseline)` and, when nonempty, requires a closing review whose `snapshot` is fresh and whose record passes `closingRecordFailure`, else `closing-review-required`; `closingScopeFailure` at closing review import requires every changed path, less the review's `excludedPaths`, to be a documentation path, else `closing-scope`. A non-documentation change after triage can never be covered: no closing review imports, and `complete` refuses until the change is reverted. `nextTriageBaseline` then keeps the earlier baseline on a repeated `triage` unless the closing review is current or a complete task assessment is fresh against the whole inventory, which is why the e43c9099 way out needed the revert before the second `triage`.
9. Morning report: `lifecycle.js:reportIsCurrent` compares `fileSha256(evidence.path)` with the recorded hash; feeds `report-stale` at `report-delivered` and status `report.current`.
10. Skeptic validation: no decider compares the skeptic's snapshot with the snapshot of the review that raised the finding (`transition` case `validate` checks only `fresh(validation.snapshot)`); worklist Add 14 names that as a gate still to add, not an existing one.
11. Decision-driven staleness, the reverse of the principle's "recorded decision is a way forward": `unblock` with a `user-decision` blocker raises `task.requirementsRevision` and the spec task's, resets the spec task to pending and deletes the docs exemption, so every earlier assessment of the task becomes unacceptable (`review-required` 'unmet', `stale-commitments` for a dispatch in flight) and the spec must be assessed again; `add-spec-review` sets `specReviewed = false`; `spec-accepted` records the user's acceptance but, as `REFERENCE.md` states, never gates another operation, so it settles nothing.
12. Slated deciders: `acknowledgement.js:scopeHash` (Remove 3), `creation-consistency.js:closingDischargedSince` and `lifecycle.js:historicalDischarge` under the creation gate (Remove 1), `progress.js:snapshotIdentity` and the accounting's binding checks (Remove 1).
13. Not evidence staleness: `store.js:save` and `update` refuse `stale-state` when a request's revision is not the committed one; `cli.js:execute` folds the same comparison into `stale-owner`. This is optimistic concurrency, kept under safety, and it is what the Stop hook's reminder write trips.
