# Recoverable unwrap acceptance

Candidate 3.2.2, based on published commit `856a1cf9a26d6ced9334329d08e71bd746b53b3c`. Delivery run `16d148ab-5297-4077-80e9-c993afc81433` implements the [agreed recovery contract](../specs/recoverable-unwrap.md). Publication is separate from this local delivery.

## Behavior and evidence

An isolated actual setup CLI probe against the unchanged baseline reproduced the defect: an injected ENOSPC reduced a 95-byte FEATURES.md to 6 bytes, and setup without unwrap then returned success with no ready entries or structural errors. The original [audit](pre-v3-shipped-capability-audit-20260921.md) independently recorded the corresponding 115-to-6-byte case. This run's scratch baseline script, preload and result are `.tmp/unwrap-baseline.cjs`, `.tmp/unwrap-baseline-fault.cjs` and `.tmp/unwrap-baseline-result.json`.

The replacement implementation syncs and verifies an original/replacement recovery record before in-place mutation, serializes cooperating writers with a persistent identity-bound SQLite lock, and verifies target bytes before cleanup. Safe retries finish only exact original/replacement states. Partial or independent edits, substituted objects and invalid evidence remain untouched with an incomplete diagnosis. A record sync is required again on retry, including after an earlier sync failure. Legacy migration retains validated source locks instead of copying stale identities.

`tests/unwrap-recovery.test.js` exercises actual standalone unwrap, setup and Ready CLI entries in isolated project fixtures. Its preload injects failures only in subprocesses and logs the exact fault boundary; each scenario asserts that its intended boundary was reached. Coverage includes interrupted lock/record creation, partial and short writes, sync and verification failures, interruption before and after cleanup, repeated safe/conflicting retries, setup without unwrap, read-only consumers, missing/replaced/edited targets, altered record schemas and hashes, oversized inputs/records, saved alias substitution, hard links, multi-file failure, concurrent writers, a killed writer, legacy migration with both unwrap options, and interrupted migration.

The existing parser, unwrap and setup suites retain ordinary Markdown joining, protected syntax, strict UTF-8, BOM/EOL, path identity and migration coverage. The new recovery suite is included explicitly in Windows CI. Package and release-manifest checks cover the versioned payload. Run records retain exact named-check outputs and input snapshots for acceptance; the source tests define the reproducible assertions rather than relying on prose pins.

Independent private probes found and fresh skeptical validation confirmed three implementation gaps: a replaced alias hid an orphan canonical-target record, a writer failure during Ready's read bypassed its initial preflight, and migration omitted locks outside the prose catalog. The repair separates recovery discovery from current alias visibility, guards reads and verifies their snapshots before reporting, and derives migration artifact discovery from all selected source roots and saved ownership policy. Regression cases cover directory consumers after alias replacement, writer failure and completion during reads, locks in inbox/plans/specs/runs and explicitly selected paths, preserved sources, and interrupted-policy retry. The pre-repair deciding evidence remains under review `dafa5315-b969-4a82-931f-f86ea8069f2d`, probe `f98136e1-42ed-4ed8-be86-93027ce7e954`, in the ignored run store; later source changes do not turn those earlier failures into passing evidence.

Further assessment and skeptical validation identified the write-mode no-op variant of the read race, the directory-junction variant of orphan discovery, and omitted predecessor results in setup errors. No-op reads now use guarded snapshots, write-mode reporting checks pending recovery, discovery traverses former target folders while respecting protected runtime/setup/Git trees, and setup preserves completed results across recovery phases and serializes them in failure output. The suite includes all three deciding cases, both file and directory write scopes, protected evidence fixtures, and current/legacy predecessor reporting. The earlier runtime probe is `d13a424b-e93f-42a3-bcea-5ea2d18ffab5/probes/8b3c4302-8b57-4d47-a976-e14df01d3206`; the separate controller directory-junction reproduction is retained in `.tmp/unwrap-directory-alias-probe.cjs` and `.tmp/unwrap-directory-alias-result.json`. Those saved observations describe the pre-repair implementation.

The repeated selection/reporting findings led to a shared-cause repair: coordination artifacts are classified by their guarded directory or file rather than by the artifact's own filename, and the complete standalone input set is validated before recovery can mutate anything. Tests cover individually selected migration files, narrow ownership overrides inside preserved directories, safe recovery of an individually selected file, both missing-input orders and a collection failure. The deciding pre-repair probe is `66ad22ec-3c03-4da8-8753-5818f64cc931/probes/44e02175-d03e-4ea0-b5d9-d533d80d5f7a`. A separate suspected legacy-junction clean-success case was refuted by actual setup execution: existing Ready validation already blocks it; its diagnostic now retains the parser's complete recovery-location details.

A subsequent user-requested direct review found that migration inventory applied ownership to a recovery record's filename while discovery applied it to the target. An individually preserved damaged file could therefore lose its sibling record to migration, leaving later unwrap to report success. Inventory and discovery now share the artifact ownership subject. Actual CLI regressions verify that exact-file preservation retains target, recovery record and lock bytes in place, with setup unwrap both enabled and disabled, and that later standalone retries still distinguish safe completion from conflicting partial contents. Cumulative reassessment caught an overbroad suffix classification in that repair; ordinary directories now retain literal ownership decisions, with empty-directory preservation and migration covered through the setup CLI. These repairs belong to the additional direct review loop after the completed Nightshift delivery lifecycle.

## Limits

These are deterministic Windows/Node.js 22.23.2 observations, not a native model-behavior campaign. No new model-owned skill behavior was introduced. Process exits and injected I/O errors exercise durable state boundaries; physical power loss, hostile arbitrary filesystem races and hardware violating successful sync semantics are not claimed. Repairs are per file, so earlier verified files remain repaired when a later file fails. Recovery records persist only for unfinished repairs; original bytes need not remain after verified cleanup.

Partial or independently changed contents deliberately require explicit reconciliation because matching filesystem identity alone cannot establish which bytes the user wants. Malformed records and interrupted lock initialization also fail closed. The separate partial-template defect, mixed-ending normalization and broader migration physical-ownership feature are not closed by this repair.

The private regression probe `dc5f51c7-afa9-4035-a650-60796388b2b8` reported 113 passing Node subtests and one failure: the existing setup case `a migrated stopped run resumes default spec assessment with current paths and original history` hit Git's filename-length limit while initializing a further nested review copy. The same case passes in the normal checkout. This matches the already-tracked quick win `Private review copies fail at Windows path depth`; this delivery does not claim that deep-copy verification infrastructure is repaired or that the private suite passed completely. Initial reviewer probes also needed corrected millisecond bounds within the producer schema's 120000 ms maximum before they could be executed; original receipts were preserved.
