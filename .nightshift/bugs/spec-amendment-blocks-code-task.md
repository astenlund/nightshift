# Amending a governing spec inside its code task blocks the task until a whole-spec reassessment

Moved from QUICK_WINS.md on 2026-11-11, when the user chose at the first pruning pass to fold it into [Implement beside the spec review after a broad-strokes pass](../features/implement-beside-spec-review.md), whose work removes the lines it concerns. The text below is the entry as it stood.

Observed in delivery `ede318dd` on 2026-11-02 and tracked by the user's triage decision. The code task's agreement required amending the spec for deferred minor findings; any spec edit makes the linked governing-spec task's assessment stale, and `specReady` gates every code-task action through `assertAction`, so even recording checks refused `spec-review-required` until another fresh whole-spec assessment, about 12 to 17 million Claude Opus tokens, completed. Deferring spec findings to the implementation therefore costs a full spec reassessment whenever the fix touches the spec text.

Decide between two designs: require deferred spec findings to be fixed in the spec before acceptance, or let a spec amendment made under the code task's agreement be reassessed without blocking implementation already under way. The user decided on 2026-11-04, under [Implement beside the spec review after a broad-strokes pass](../features/implement-beside-spec-review.md): a spec amendment under a recorded decision no longer blocks implementation already under way, `spec-review-required` holds only what depends on spec readiness, and a deferred spec finding goes to the spec when it concerns a decision and to the code when it concerns mechanics, so this entry's repair follows that design. Runtime or brief change; tracking does not authorize implementation.

In disco-elysium-companion run `f5a12322` on 3.3.15, a handover queue held a `spec` task over `.nightshift/features/runtime-powershell-dependency.md` and a dependent `code` task naming the same `agreement.spec`; the spec task completed on a passed fresh assessment, yet `start-task` on the code task refused `spec-review-required`, because `specReady` in `internal/runtime/lifecycle.js` accepts only the task `add-spec-review` creates or `specReviewed: true` with a snapshot, so the same spec text needed a second whole-spec assessment, twice in that run. In Hermes run `41e7d80c` on 3.3.25, a code task and its governing-spec task carried checks of the same names over overlapping inputs; when a repair added a reproduction test that failed before the fix, the spec task's check went stale and then failed, and since `specReady` reads the spec task's `reviewGate`, whose failure test requires its verification gate, and `assertAction` applies `specReady` to every task action, every `check` on the code task was refused `spec-review-required` until the spec task's check passed, in four repair rounds, so the failing reproduction could only be recorded on the spec task. The decision above should also settle whether a completed queued spec task over the same spec satisfies the gate and whether a spec task's checks belong in it.
