# Claude Code can store the in-turn handover acknowledgement as thinking

Moved from BUGS.md on 2026-11-10, when the user chose to fold it into [Remove the handover acknowledgement obligation](../features/remove-acknowledgement-obligation.md), whose work removes the lines it concerns. The text below is the entry as it stood.

[The handover skill](../../skills/handover/SKILL.md) has the controller, once the continuation outcome is recorded, emit the `Handover accepted: ... You can leave.` paragraph as ordinary text and call `status` in the same tool-use turn, and [the handover-only delivery design](../features/handover-only-delivery.md) requires that text to be "a normal assistant text content block, not intended narration held in thinking". On Claude Code on Windows that route has failed repeatedly: the session history stored no text block for the paragraph, only a thinking block paraphrasing it, sometimes after an empty thinking block, before the tool call, so `status` kept returning inspection `missing` with nextStep `emit-text-then-status`. Ending the turn with the acknowledgement as the final message, which the skill permits once continuation is verified, worked every time: the Stop hook continued the run and the next `status` returned `request-engineering`. Observed in Hermes home run `e8e6130d-387f-4106-ba06-bbfa81917a0f` on installed 3.3.11 (session `5cd619ec-7674-49ef-a7dc-537b545a68bf`, four attempts between 20:58 and 21:00 UTC on 2026-10-15); in this repository's run `27dea6a9-8d0a-4b0c-85c7-880b96ae88b3` on 3.3.11 (session `f9864d83-cd95-4e65-880b-cc1b0058ad8e`, entry at 2026-10-15T22:38:08.096Z); in Hermes runs `eb9c8e10-f4d1-44a0-9157-3e527811ef25` (entries from 2026-10-16T12:32:58.488Z to 12:35:55.293Z) and `6ef27759-2b80-4112-8a71-2480d2df4103` (entry at 2026-10-16T22:54:07.991Z), both on 3.3.12 in session `ae5bbe0f-c5a7-4e94-9376-ea41edf691fa`; and in Hermes run `1c64da0e-f0fb-469b-b3de-e3230621d0e6` on 3.3.12 with `claude-opus-5-5`, after adoption and resumption in session `1da8e4a1-63f5-4744-97dc-5098e5fc3192` (three attempts from 2026-10-17T15:43:07Z to 15:44:59Z), where two short progress sentences were also lost as text; that report's evidence is the session history around lines 282-284, 318-319, 540-542 and 579-581 (entries at 15:42:41Z, 15:43:07Z, 15:44:36Z and 15:44:59Z), with the progress sentences around lines 283 and 448. It recurred in Hermes run `912e2720-abe0-40c3-9559-63e70716264b` on 3.3.12 with `claude-opus-5-5`, in the new session `f440f75c-9923-452c-8741-b2a201624835` (entries at 2026-10-17T21:44:55.045Z and 21:44:55.049Z), whose loaded memory index already said that ending the turn on the acknowledgement worked, yet the in-turn route was tried first; the turn-ending acknowledgement that followed was stored as text. Elsewhere in those stretches short progress sentences were mostly stored verbatim, and length alone does not explain it, since a compact attempt of about 150 characters was affected too. The cause is not established: host "The user hasn't heard from you in a while" nudges preceded several affected responses and were not checked for others, but text after earlier nudges was stored verbatim, and in `6ef27759` the turn-ending acknowledgement was stored as text after another nudge. It may be host or model behavior rather than a Nightshift defect, but it makes the skill's in-turn route fail while the turn-ending route succeeds. The missing acknowledgement is older than the route: in the 3.2.10 campaign, six in-turn attempts, five on Opus and one on Fable, drew no visible acknowledgement, each going straight into the work and the Fable one after composing it only in a thinking block, which led 3.2.10 to make it the turn-ending message on Claude Code, as [the campaign report](../reports/unattended-stop-hook-20260926.md) records, and [the handover-only delivery design](../features/handover-only-delivery.md) notes that its Claude trace did not establish the complete in-turn sequence. The accounts come from three maintainer inbox reports, one carrying recurrences added at later runs' triage; the user chose at inbox triage on 2026-10-17 to track the first two together and on 2026-10-18 to add the third.

Establish the cause and, while it is unknown, consider having a Claude controller whose continuation is verified acknowledge through the turn-ending route first; the design is open. From 2026-10-18 until its removal on 2026-11-12, recorded below, a user-level instruction on the maintainer's machine, approved at Hermes run `912e2720`'s triage, directed Claude sessions to end the turn on a message a gate checks whenever a verified continuation can resume the work, including after the gate reports it missing, rather than write it before a tool call, and called that the route the handover skill permits; fewer in-turn occurrences during that period would therefore not show the cause resolved. The design must also reconcile [the runtime reference](../../internal/runtime/REFERENCE.md), whose missing-text step calls for "actual ordinary assistant text followed by status in the same ongoing turn", with the skill, which also permits a turn-ending acknowledgement when verified continuation can continue work afterwards. The user chose at inbox triage on 2026-10-18 to record these points from a maintainer inbox report. A change to the skill or the runtime reference ships with a version increase. Tracking does not authorize implementation.
