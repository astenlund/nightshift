# A Stop hook reminder write can invalidate a request launched in the background

Moved from BUGS.md on 2026-11-15, when the user chose at the fortnightly pruning pass to fold it into [Cut store v4 and reduce the release system](../features/store-v4-cut.md), whose derived reminder cap writes no revision and so rewrites the lines it concerns, with no stopgap in the operating brief. The text below is the entry as it stood, less a closing sentence about the `operation-time-limit` refusal, which concerned another matter that [the runtime reference](../../internal/runtime/REFERENCE.md) already documents.

Recorded at the user's inbox triage on 2026-11-12 from the maintainer inbox report `2026-11-11-memory-background-dispatch-stop-hook-race.md`, with the first occurrence kept until then as a local note here. When a controller launches a revision-stamped runtime request in the background and ends its turn, the Stop hook's reminder write advances the run revision (`store.remind` in `internal/runtime/hook.js`, whose comment says "The reminder write advances the revision"), so the request, stamped a moment earlier, can be refused when the write lands before the request is admitted. Hermes run `451da04e` on 3.3.9 (2026-10-11): a background claim and dispatch was refused `stale-owner` about six seconds after the hook blocked the stop, and re-sending at the current revision worked. Hermes run `fa3336ef` on 3.3.14 (2026-10-24): a skeptic dispatch and later a code review dispatch, each launched in the background before the turn ended, were refused `stale-state`, and the next hook turn showed no worker. Hermes runs `8b84d53f` (version not recorded) and `95578fbc` on 3.3.33 (2026-11-09): a background check driver and a background `check` were refused `stale-owner` when the turn ended. In the later cases, what worked was staying in the turn until the worker registered and then holding it on runtime `wait`, plus a send helper that re-reads status and retries. [The operating brief](../../internal/workflow.md) says to "Await managed dispatches through runtime `wait` rather than yielding while workers remain active", which covers active workers but not a request still awaiting admission, before any worker exists, so the brief does not by itself rule the trigger out.

Decide whether a reminder-only write should leave an in-flight request admissible, or whether the refusal should say that a Stop hook reminder advanced the revision and how to resend. Runtime changes ship with a version increase. Tracking does not authorize implementation.

Two more recurrences were recorded at the user's inbox triage on 2026-11-16, which kept the store v4 fix with no stopgap. In Hermes delivery `c4991249` on 3.3.36, a background chain sent `repair` (revision 215) and then `check`, which was refused `stale-owner` although the helper had read status just before, and status afterwards showed revision 216; since the rest of the chain had already started resumed review dispatches, a `claim-controller` was refused `retained-bootstrap-unavailable` and the resumed reviews ran without the rerun checks attached, so the checks and resumes had to be repeated (maintainer inbox report `2026-11-15-stop-hook-revision-race-on-chained-calls.md`). In this repository's delivery `fb72582d` on 3.3.37, two separate single background dispatches, a fresh code assessment and a skeptic, each sent just before the turn ended, were each refused `stale-owner` with no worker registered, and staying in the turn until the worker registered succeeded for about a dozen dispatches afterwards (maintainer inbox report `2026-11-16-stale-owner-single-background-dispatch-recurrence.md`). Both reporters inferred the hook's write from timing and from a fresh `hookIntegration.observedAt` in the next status, but that stamp cannot tell the hook's write from another: the Stop hook's `store.remind` saves its revision without recording an integration observation, while runtime mutations admitted through `internal/runtime/cli.js` and saved through `update` in `internal/runtime/store.js` refresh it. The revision advance itself is consistent with the reminder write, and the hook's own logs were not read.
