# A hook generation change strands a running run's session

Reported to the maintainer inbox on 2026-10-06 from `C:/Git/disco-elysium-companion`, run `cffcf94d-49be-4cab-afcb-3fad1dabfd95`, handed over unattended on Claude Code 2.1.291 and bound to 3.3.5. The run was recording thirteen checks, each after a successful `claim-controller`; the fifth wrote its output at 12:53:22 local time, and from 12:53:31 every protected request was refused with `retained-bootstrap-unavailable`, "This native session has not observed the current Nightshift hook generation; open or reopen it before protected work". The plugin cache had gained 3.3.7 at 12:52:26 and 3.3.8 at 12:52:37, a new retained launcher directory was created at 12:53:26, between the last admitted check's output and the first refusal, and a later resource status showed the shared registration on a hook generation other than the one the session's activation had recorded. Only a SessionStart hook records an activation, so the run had no recovery of its own: the Stop hook kept firing but could not restore admission, and the run waited until the user quit and resumed the session, after which a `claim-controller` succeeded and the eight refused checks were recorded and passed. The refusal follows the designed rule, since [the retained-releases spec](../specs/retained-plugin-releases.md) says an activation "becomes unusable when the registration generation or native trust changes". What changed the generation was not established; [the 3.3.8 notes](../../CHANGELOG.md) say that the new bootstrap reaches an existing installation only through an explicit maintenance `setup`, which changes the hook generation, so such a setup run elsewhere that morning is the likely trigger, by inference. [Say when registered hooks run an older bootstrap than the installed release](../QUICK_WINS.md#say-when-registered-hooks-run-an-older-bootstrap-than-the-installed-release) names reopening open sessions as that setup's cost, but nothing tells the owner of a running run, or whoever runs the setup, that a handed-over run will halt. The user chose to track it at inbox triage on 2026-10-11.

Investigate whether a running run can keep or regain admission across a generation change, for example while the bootstrap its session observed is still retained, without weakening the activation check for other work. At least, have setup name the live runs whose sessions it would strand before it rewrites the hooks, and have the owner's continuation report the reopen it needs rather than meeting the refusal mid-batch. Compare with [Missing session activation blocks agreed work until restart](../BUGS.md#missing-session-activation-blocks-agreed-work-until-restart) without assuming a shared cause. Launcher and runtime changes ship with a version increase. Tracking does not authorize implementation.
