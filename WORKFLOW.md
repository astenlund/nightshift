# Nightshift workflow design

Working draft, updated 2026-11-06, developing [the vision](VISION.md). The workflow and dimension brief record the agreed direction. [Handover as the delivery boundary](.nightshift/features/handover-only-delivery.md) governs delivery creation, standalone revision and continuation from 3.3.10; existing bound runs keep their retained runtime. Where a sentence below states direction [the operating brief](internal/workflow.md) does not yet carry (including conditions reported with their cause and way forward in place of refusals, implementation started beside the lead spec review after a broad-strokes pass, amendment of a confirmed spec with unreached work continuing, intermediate reviews separated from final release readiness, assessment currency narrowed beyond the current recorded context and documentation-only relief, and the session-close sequence after the morning report), the brief governs today's runs. This document grants no implementation authority.

## Governing priorities

The [vision's invariant priorities](VISION.md#invariant-priorities) govern every workflow decision: reliability, through autonomy and trust as equal parts, with speed, efficiency, and economy counting only where they cost neither. Handover should support the user going to bed without routine stalls, and independent review and verification must earn trust in the result without depending on the user auditing the code. Efficiency improvements remain valuable when they preserve reliability and respect explicit limits.

## Project files

Use `.nightshift` at the project root for Nightshift-owned backlog, feature and spec documents, and durable run records on both hosts. Fresh setup uses that home. The MVP migrates existing Nightshift-owned files from `.claude`, preserving content, links, tracking choices, and recoverable work while keeping the backlog format. Preserve host-owned configuration in its required location.

## User-facing review requests

For standalone review requests, Nightshift's review skills activate only for explicit `revise` intent. Plain `review` and `review-loop` requests use the user's global direct-agent routines and do not activate the plugin. Reviews required within an authorized Nightshift lifecycle still use the shared machinery described below. The detailed global routines belong in the user's canonical global instructions, outside the plugin skills.

## Start with a shared understanding

For a small fix, the controller investigates enough to understand the behavior and gives a brief readback before implementation. For example: "Refresh should reload the list while preserving the selected status filter. Shall I go ahead and make that change?" It waits for a yes to that question before changing code; agreeing with an idea, a wording or a direction while it is still being discussed is not that answer. The exchange supplies the agreed outcome without a separate spec, formal digest, or implementation plan. An already-confirmed scope does not need another routine confirmation at each later stage. Handover is the user's act. For a queue, every item's readback or decisions are settled in the interactive phase first, and one handover then releases the whole queue for unattended work.

For a substantial feature, the controller explores the project and resolves consequential product decisions with the user, then writes a concise spec. It launches the broad-strokes pass, the spec review's challenge of the overall approach, immediately before presenting that same draft to the user, and the human reading and that pass proceed concurrently against a stable version; the lead spec review is queued at handover and runs beside the implementation, as the user decided on 2026-11-04 and [Implement beside the spec review after a broad-strokes pass](.nightshift/features/implement-beside-spec-review.md) designs, direction the operating brief does not yet carry, since today the full independent spec review launches before presenting. User feedback and skeptic-validated review findings inform the next draft; a revised spec returns to the reviewer as a whole. For a feature whose value shows only in use, the user may choose a prototype phase before the spec, as [the vision](VISION.md#implement-directly-with-evidence-throughout) describes: the spec is then written from what the user observed, and the prototype is not a delivered result. As the user decided on 2026-11-04, the controller offers the prototype, with a budget, when the investigation finds consequential decisions that discussion cannot settle because nobody can predict the experience, and the user may ask for one at any time. A prototype skips the governing spec and its review, handover and the run, independent review before use, verification campaigns and documentation edits; it keeps chat agreement on its scope and budget, its own branch or local-only checkout with commits marked as a prototype, no release and no push to a shared main, the safety floor of the user's authority, and a record of what was tried, what was changed and why, and what failed, which is its deliverable. The spec is written from that record and cites it, so its review challenges the approach against evidence. The lifecycle takes over when the user records, in their words, that the shape is right: the spec follows, then handover, and the run implements from the prototype branch as its starting point under full review and verification of the whole change; nothing from the prototype counts as reviewed.

For the substantial-feature path, implementation starts only when the user has confirmed the commitments with the broad-strokes pass's result in hand; the lead spec review's resolution no longer precedes it, direction the operating brief does not yet carry, since today implementation waits for independent spec review to be resolved. Earlier user confirmation remains valid through compatible corrections. A material change to the commitments requires confirmation of the changed decisions, without repeating the entire agreement exchange. A confirmed spec can be amended while the run is open: the amendment is recorded with its reason and the decision it rests on, it returns to the reviewer as a whole like any revised spec, and work it does not reach continues meanwhile; the earlier text stays as history and is not enforced against the amendment. If the user is unavailable, preserve the unanswered decision and pause dependent work while continuing independent authorized work.

Before handing work over for unattended execution, ensure every queued item has the required user agreement through the small-change or substantial-feature path and resolve known blocking user decisions. One agreement or shared spec may cover multiple items; independent review and engineering can continue unattended. Check essential execution and review capabilities within the agreed scope and limits. During the run, the controller handles routine decisions and recoverable failures autonomously, using allowed fallbacks and sound continuation. A newly discovered material decision requiring the user pauses dependent work while independent items continue. Ordinary follow-up questions wait for the closing triage; a genuine authority or capability blocker remains explicit and does not count as completed work.

## Accept handover and observe continuation

Handover alone creates a delivery run. Ordinary chat agreement authorizes direct work. Ready explains that selecting work requests handover after investigation; confirmation of the investigated scope releases it, unless the user explicitly requests direct work or a pause. Selection alone starts no implementation. All four standalone revise skills use durable review contexts with attributed assurance, without delivery closing stages. Revision inside an owned delivery continues on its task.

After durable acceptance and the recorded continuation outcome, emit the separate visible acknowledgement before engineering. It begins `Handover accepted: <scope and limits>. You can leave.` and names the report location. Failed continuation also discloses that automatic continuation is unavailable, the failure was recorded and resumption is needed if the session stops. The runtime observes the owning native assistant output before admitting runtime engineering; this does not intercept arbitrary editor or shell writes. After the acknowledgement paragraph, inspect runtime status in the same ongoing tool-use turn. Its read-only acceptance checkpoint distinguishes an awaiting continuation outcome, missing output, available output and unavailable history. Reconcile an awaiting outcome, emit ordinary text when missing, and recover unavailable history through bounded diagnostics. Available output permits requesting engineering, whose runtime transition independently observes and captures the acknowledgement. Inspection itself discharges no obligation. Use turn-ending acknowledgement only with verified continuation; otherwise keep working in the active turn. Actual ordering remains a per-host verification obligation.

New deliveries have no attended/unattended mode. Attempt the host's continuation without enabling deliberately disabled hooks or granting trust. Preserve accepted authority when continuation fails, record the actual failure and follow-up, and continue otherwise authorized work in the current turn. Ownership, permissions, exact resources, explicit stops and exhausted limits retain their gates. A user-requested hold suspends engineering and continuation pressure; authorized resumption reconciles activity and refreshes continuation on the same run.

## Implement directly

A capable model implements from the agreed request or spec, using the repository and real execution feedback to choose and refine its approach. Select a model meeting the role's required strength and capabilities, respecting the user's model choices. A run need not use both hosts. Subagents get bounded assignments where they offer a clear benefit, and one owner remains responsible for the complete result. A written implementation plan is exceptional guidance for a deliberately chosen weaker or cheaper implementer that needs it.

The controller chooses assignments using task fit, observed model strengths, availability, context, and cost within the invariant priorities, taking the cheapest permitted model that meets each role's required strength and running no role at or above max reasoning effort. The user's reported tendencies inform that judgment without prescribing a fixed team or a fixed model for each stage; structured model teams are deferred beyond the MVP. Respect explicit model choices and preserve control of an existing run. Investigation establishes the problem before editing regardless of the implementer.

When coordination load warrants it, the controller may use a lower-tier shift supervisor for assignments, progress, result collection, and routine recovery. The controller retains consequential engineering decisions, scope and authority judgments, finding dispositions, and final acceptance. Direct coordination remains available, with ownership and activity reconciled before a handoff. The optional layer is justified by reliability before cost savings.

Tests, builds, and live verification establish the agreed behavior and meaningful failure handling throughout implementation. A repair follows the repair paragraph of [the operating brief](internal/workflow.md), which states how large a repair is, what reproduction evidence precedes it and reaches its review, which state it traces and when repeated misses call for the shared cause. Additional checks need a reason tied to the change or unresolved evidence.

## Maintain continuity throughout the run

Preserve accepted commitments, current work, unresolved findings, dispositions, and evidence through growing context and compaction. Supply focused current obligations and applicable rules at consequential decision boundaries. Reliable workflow operations check transition prerequisites so omitted review work or stale evidence cannot become successful completion. Which prerequisites refuse follows [the vision's recording of decisions](VISION.md#record-decisions-without-locking-them): provenance, ownership and safety refuse; during engineering an unresolved consequential question holds only work that depends on its answer; pending assurance remains an obligation for the final release gate without making the run degraded or blocking unrelated progress; a bookkeeping condition is reported with its cause and the way forward and holds no work. Models retain engineering judgment.

After compaction or takeover, reconcile the record with the actual project and in-flight work before dependent actions. Resolve recoverable gaps autonomously; a genuine blocker leaves dependent work incomplete while independent authorized work continues. MVP acceptance must exercise long runs and deliberate compaction during implementation and review, including findings still awaiting resolution and repairs awaiting cumulative re-review.

Skeptics use a different host from the lead, preferring the controller's host, and never Vibe. When the other host is unavailable for a Claude or Codex lead, a fresh qualified same-host skeptic is valid; a GLM lead waits for Claude or Codex validation when neither is available. Fresh qualified same-host review remains valid. Placement still considers task fit, independence, availability and run constraints. Explicit model requirements, required independent-assessment strength and peer-cloning rules remain binding. Fable/Astra and Opus/Sol are corresponding-tier examples, not permission to lower required review strength. Cross-host placement does not guarantee independent errors. Verify the dispatch capability, review context, model and result attribution, and unavailable-counterpart fallback on both controller hosts.

One fresh strong reviewer starts with the complete dimension brief, the agreed outcome, full cumulative change, applicable constraints, and access to surrounding code. The author supplies factual context rather than excluding dimensions or predeclaring them irrelevant. The reviewer assesses every lens and can briefly explain an inapplicable one without producing an elaborate report for it.

A small change normally needs that one reviewer. For substantial work, the independent reviewer decides whether to recruit additional reviewers after examining the complete change. Helpers use the lead reviewer's model and effort in fresh contexts and receive the full dimension brief for their assigned area and the shared requirements and constraints. The original reviewer retains the integrated assessment, including interactions across areas, and can challenge the initial size or risk classification.

The final release gate requires applicable broad independent assessment of the actual candidate and its integrated behavior, verification of the final inputs, and required findings resolved or explicitly settled by the user. Judge coverage from the actual scope examined, current commitments, relevant context, supporting evidence and review behavior; neither a model label nor literal LGTM establishes it alone. Earlier assessments can contribute where they remain applicable, while uncovered changes and interactions need assessment. Intermediate reviews guide work and preserve unfinished assurance without requiring a release-ready result at every task transition. The main cumulative code review normally waits for spec review to settle. The controller may start it earlier only when outstanding spec questions cannot materially change that assessment and early feedback would prevent meaningful rework, with the reason recorded. The intended runtime permits that exception without making parallel review routine; the bounded implementation still retains its legacy spec-readiness prerequisite.

## Validate findings and decide their value

Every finding receives skeptic validation and its own evidence and verdict. One fresh skeptic can validate the initial findings from a small review together; no findings means no skeptic is needed. How to allocate skepticism across larger reviews remains a design choice, while individual validation is mandatory.

Factual validity, authority, and practical value are separate decisions. Straightforward findings can be disposed of from the reviewer and skeptic's existing evidence. Where consequences, value, or repair quality remain unclear or disputed, the controller relays an adversarial dialogue between the reviewer and the skeptic, continuing each through a resumed dispatch or, when its native session cannot resume, a replacement that preserves its assessment lineage; the two never exchange messages directly, and the skeptic gives the approach a repair would take for every finding it confirms. The controller decides whether to implement, defer with a concrete reason and durable route, or skip with an accepted tradeoff. Missing evidence is unresolved; a required commitment cannot be waived because repairing it is expensive.

The controller or assigned implementer applies accepted repairs and runs the relevant checks. After every repair batch, the controller resumes the reviewer that raised each repaired finding in its own session, with the current inputs in a new copy or, on Vibe, in the lineage's copy refreshed in place, to record whether each repair closes its finding and to re-examine the complete cumulative change across all dimensions; a reviewer of another kind whose reviewed files changed, including the latest docs reviewer after a code repair, retains its assessment and outstanding obligations. At a consequential acceptance boundary, resume that reviewer or use its independent replacement to decide applicability, or obtain cumulative reassessment; do not schedule relevance merely because another repair batch landed. When reassessment is needed, schedule it after the repaired kind's cycle settles, on an open task covering a completed one where possible. The operating brief now carries that boundary-based relevance route without requiring a turn after every edit. The bounded implementation preserves its documented legacy readiness and stage prerequisites. A reviewer that cannot be resumed is replaced by a fresh one given its record; when the resumption was for that call, the replacement makes it in its place. Each checks affected surrounding code, sibling paths, earlier fixes, and continued fulfillment of the agreed outcome. The latest patch explains what changed but does not limit the review. A revised spec likewise receives another whole-spec review. Small repairs receive no exemption from this coverage. The intended scope rule follows [the vision's recording of decisions](VISION.md#record-decisions-without-locking-them): an edit outside what an assessment examined leaves it current, while the originating reviewer or its independent replacement judges whether an edit inside it bears on coverage. The bounded runtime foundation still binds code and docs assessments to their full recorded project context and retains documentation-only relief for ordinary pending code-input changes covered by a current docs assessment; replacing that relief and narrowing currency further remain worklist obligations.

New findings receive skeptic validation. When the reviewed artifact is unchanged and the required strong, broad independent assessment is already complete, resolved skips, verified deferrals, and refutations do not require another pass solely to obtain literal LGTM. Resolved findings cannot substitute for that coverage, and every repair batch still receives full cumulative review. New evidence can invalidate earlier dispositions. A continued reviewer verifies repairs well but can develop tunnel vision, so a continued assessment does not by itself supply the fresh independent coverage required by the final release gate: once no critical or important finding awaits repair and none awaits closure, a fresh strong reviewer of the same kind assesses the complete artifact or change, and the final release gate requires that fresh coverage or applicable earlier fresh coverage, with affected changes and interactions assessed. These assurance obligations do not create a blanket barrier to independent engineering while they are pending. Every reviewer receives the recorded acknowledgements, meaning settled dispositions, refutations and intentional choices scoped narrowly, so settled points are not raised again while adjacent issues stay in scope.

## Recognize repeated failure to make progress

A second missed case of the same kind after a repair, a fix undoing an earlier fix, or the same violated invariant raised again means the repair was too narrow. Count recurrence across repair attempts, not several findings reported together. Same area alone is weak evidence.

The controller pauses routine patching and fixes the shared cause the repairs missed instead of the next case. It may reconsider the implementation or seek a fresh specialist assessment, explaining the conclusion briefly. The signal does not automatically fail the run, launch a swarm, or require user approval. Act earlier when the evidence warrants it; a clean round with no edits is progress. Tune the heuristic from actual runs.

## Close with evidence and the existing follow-up triage

Before the session retrospective and morning report, update the documentation and backlog for completed work. The morning report presents what was delivered, how it meets the agreed outcome, evidence, limitations, accepted tradeoffs, follow-ups and incomplete work or decisions, and starts session close while the run stays open. It does not claim that final validation or publication has already happened. Agreed follow-on work joins the run, and live defects return as repairs. The user retains settlement authority; a run waiting for their decision is not automatically completed. A later user decision can reopen a settled run until another run supersedes its work, preserving earlier reports and completion records as history.

After documentation and backlog updates, perform the session retrospective, retaining revise-lore's purpose before follow-up triage. Examine how the run went, identify useful lessons and workflow problems, and prepare worthwhile proposed improvements for user decision. Proposed instruction changes receive the agreed independent review and approval. If reflection yields no worthwhile proposal, complete the retrospective without creating one.

Keep the existing follow-up triage. Present decision-requiring items one at a time, with the context and concrete content needed to decide, a recommended route, and the consequences of the options. Use fix now, track, or skip where applicable. Deferred approval questions retain their own approve, adjust, or revert terms. Wait for the user's decision before presenting the next item, and place tracked work in its appropriate project or workflow home.

After every follow-up has a disposition and the resulting edits and other cleanup are applied, perform final validation and the release gate against the actual candidate, including changes after the report. A new finding returns to its required decision or repair and then validation; it does not reset unchanged report delivery, retrospective or settled triage. Record the report and the subsequent changes together so the closing result describes the final candidate.

Where the final gate has unmet obligations the user may accept, present the candidate, named obligations, missing evidence, consequences and alternatives, then ask explicitly whether they accept those exceptions for that candidate. Use no confirmation code: independently verify the actual user reply and bind it to the exact briefing, separately from evidence and publication permission. Ambiguous, absent or unverifiable replies leave acceptance pending. Renew approval only when later changes affect those exceptions or their consequences; otherwise preserve it with its applicability recorded. Completion says "completed with user-accepted exceptions" and lists them, without implying all assurance passed.

The runtime then asks whether to publish the changes or leave publication to the user. Record that choice against the candidate and the agreed publication scope. If publication is requested, record its actual outcome before stamping completion; a failure or uncertain outcome keeps close pending until reconciled and completed or the user explicitly takes over. Reconcile partial external effects after interruption before retrying. If the candidate changes, reassess affected assurance and whether the existing authorization still covers it. Leaving publication to the user completes the agent's responsibility without asserting that publication happened. The completion stamp records the candidate, validation outcome, settled exceptions and publication outcome. An administrative close as unfinished is a different outcome and never receives a successful-completion claim.

No follow-ups means no empty triage ceremony. If the user is unavailable, preserve the items and distinguish completed engineering work from outstanding decisions. Do not imply that a pending answer has been given. Waiting only for the user does not create continuation pressure. Publication remains subject to the explicit closing choice; absent approval leaves it pending. Proposed changes to workflow instructions are follow-ups for user decision, not automatic additions to the rules.

## Review dimensions

These are the agreed coverage lenses for the reviewer, independent of the number of agents. They consolidate overlapping criteria and make requirements and verification explicit. The runtime's [review dimensions](internal/runtime/review.js) implement these coverage lenses.

### Spec review

| Lens | Main question |
|---|---|
| Intent, scope, and acceptance | Does the spec express the desired outcome, consequential behavior, boundaries, and evidence of success? |
| Soundness and integration | Can the proposed approach satisfy those commitments in the actual project and operating environment, with its real dependencies and assumptions? |
| Failure, safety, and recovery | Are consequential failure outcomes, trust and data boundaries, concurrency, and recovery expectations understood where the behavior requires them? |
| Clarity, consistency, and proportionality | Can the user and implementer understand the commitments and their important reasoning without contradictions, missing decisions, or unnecessary prescription? |

Spec review checks the mechanisms the design actually commits to. It does not invent an implementation and then report gaps in that invention. Field grammars, concrete values, and exact technical shapes belong in the spec when they define a meaningful contract. Important tradeoffs need reasons; every imaginable alternative does not need a rejection paragraph. Future work constrains the design through real commitments and credible consequences, rather than the mere existence of a backlog entry.

### Code review

| Lens | Main question |
|---|---|
| Requirements and user experience | Does the implemented flow fulfill the agreed behavior and constraints, and can its intended users use and understand it, including relevant accessibility needs? |
| Correctness and integration | Does it work across normal, boundary, concurrent, and failure conditions, including callers, consumers, state transitions, wiring, and affected sibling paths? |
| Security and data safety | Are trust boundaries, permissions, confidentiality, data integrity, and consequential preservation and recovery obligations respected? |
| Design and maintainability | Is the local code and overall system decomposition understandable and proportionate, with suitable reuse, ownership, abstraction boundaries, and coupling? |
| Performance and resources | Does it avoid consequential latency, throughput, resource, or operating-cost problems under realistic conditions? |
| Tests and evidence | Do meaningful assertions, realistic execution, integration checks, and regression protection establish the required behavior and expose remaining uncertainty? Does a fix of misbehavior carry a check that failed before it, or, when no practical automated reproduction exists, a recorded reason and stand-in evidence? |

Design and maintainability explicitly covers two scales:

- **Local structure:** clarity, state ownership, reuse, duplication, responsibilities, and abstraction boundaries.
- **System structure:** module boundaries, dependency direction, service decomposition, shared contracts, and coupling across components.

Tests and evidence examine assurance across the other lenses, without automatically creating another verifier role or repeating every test. Similar code, a long method, or an opportunity to introduce concurrency is a reason to investigate, not sufficient evidence that a change is beneficial.

### Shared review discipline

Reviewers and skeptics on either host must not change reviewed project inputs. Checks that would mutate those inputs run in isolated fixtures or copies; ordinary verification may run against the project when it leaves reviewed inputs unchanged. Repairs belong to the controller or assigned implementer. Acceptance verifies reviewer and skeptic write isolation on both hosts.

Findings identify a concrete consequence and its supporting evidence. Verify claims about existing code and external behavior against the actual relevant source or execution; state uncertainty where that evidence is unavailable. Examine related pre-existing code and structural problems, but finding one does not automatically authorize a repair or backlog entry. Applicable project conventions remain in view.

Report one underlying problem once, even when several lenses expose it. Retain sibling sweeps, cumulative review, and the agreed finding-disposition process as common instructions rather than duplicating them in each lens. Looking through every lens does not require equal depth, a finding quota, or a separate narrative per lens.
