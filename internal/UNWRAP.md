# Unwrap recovery

Unwrap preserves an original before rewriting existing Markdown. A changed file has a sibling `<filename>.nightshift-unwrap.json` until its replacement is synced and verified. The record contains both versions as base64 bytes with lengths, hashes and filesystem ownership. Treat it as project content with the same confidentiality needs as the original. Files and replacements are limited to 16 MiB, recovery records to 48 MiB.

Rerun the same authorized unwrap write to finish a pending repair when the same physical target contains either the original or the complete replacement. Setup with `unwrap: true` resolves those safe states before continuing. Setup without unwrap refuses unfinished repairs. Setup inspection, standalone unwrap check mode and Ready report pending recovery without modifying it.

Recovery records remain discoverable when the alias that selected a target has changed. Read-only assessment checks for pending repair around file reads and verifies its read evidence before reporting; a concurrently changed file requires a retry. If the recovery search itself cannot complete, the report is incomplete.

Backlog-root recovery discovery includes former canonical target directories even after their selecting junction disappears. Git metadata and the root `runs` and `setup` state trees remain outside backlog prose scans; catalog aliases cannot opt those protected trees into repair. Explicit single-file requests retain their own scope, and migration separately inspects its selected legacy source domain.

If a write stopped partway through, a file was replaced or independently edited, or recovery evidence is invalid, automatic retry preserves both the current file and record and reports a conflict. Do not delete the record to silence the error. Preserve the current file separately and inspect `original.bytes`, `original.length` and `original.sha256` in the JSON record before deciding whether to restore the original. Restoring content is a separate explicit recovery decision; the tool does not guess which version the user wants. An incomplete record from interrupted creation has not authorized target mutation, so the original target remains the source of truth and the invalid record needs explicit reconciliation.

Writers use a small persistent `.nightshift-unwrap-lock.sqlite` in each affected canonical parent directory. It contains ownership metadata, not backlog contents. A busy lock means another writer may still be active; retry after it finishes. Process exit releases the operating-system lock. Invalid or substituted lock storage is preserved and requires reconciliation. Lock databases are limited to 64 KiB and are not routinely removed. Setup holds existing locks across its selected migration sources, including explicitly selected paths, and retains validated legacy locks at their old locations instead of copying their physical identities into the new backlog. Explicitly preserved sources retain their ownership policy on retry.

Repairs are independent per file. Standalone unwrap validates the requested input set before starting recovery, so a missing or uncollectable input does not leave an unreported earlier repair. If a later repair fails, earlier verified repairs remain and the command stops further writes with a nonzero result. Setup's error JSON includes those earlier repairs in `completed`. This does not provide whole-backlog atomicity or protection against hostile filesystem races or hardware that violates successful sync semantics.
