# Retained resource interface

Installed Nightshift work uses a complete session-bound release outside host-managed plugin caches. All eight skills use this interface. Invoking a skill authorizes automatic Nightshift preparation, including necessary owned hook registration, while readiness still does not authorize implementation. Direct parser/setup/runtime CLI development commands require `--development` as their first argument. Internal test/library callers are development surfaces. Development mode never supplies installed retention or permits mutating an existing bound run with another runtime.

## Skill activation

On first invoking a skill from this release, prepare Nightshift automatically and reconcile its session-bound resources, including when the native session already has an older binding. Do not ask whether to perform routine setup. Preserve an already resolved matching binding; do not repeat preparation merely because this reference was opened. The invoking skill/plugin root supplies the initial `internal/releases/launcher.js`; never choose the newest cache directory, guess a native identity or select development mode for installed work. If that source disappears before preparation, rediscover the enabled installation through native plugin/skill metadata. Existing bindings keep their exact release. Read the skill from the resolved bound root before continuing. Each public skill carries only this shared policy link and the Claude native marker.

Write an `action: "prepare"` request with `host`, actual native `session`, absolute `project`, and `entry` (`ready` for Ready/Exploring, `setup` for init-backlog, `runtime` for handover and all revise skills). Optional `profile`, `store` and `pluginId` select the actual installation. Run `node <CURRENT_PLUGIN>/internal/releases/launcher.js <request.json>`. Preparation establishes the exact session binding before returning, so activity in an older session cannot redirect the next invocation through an older administrative fallback. It may update the administrative bootstrap while retaining previous routes, actual native hook definitions and their generation. It does not rewrite matching hooks or replace existing bindings. The current bootstrap applies the Ready exception even to retained 3.1.0 bindings, running their original parser under current administrative admission. Runtime and hook dispatch remain bound to their original release. Read the skill from its returned `root`; use the returned `bootstrap` and `registration` for `run`. For Ready/Exploring, this current administrative admission policy governs preparation, and the bound skill governs backlog presentation. Do not reapply an older shared setup or activation prerequisite after preparation has supplied the current launcher. Other entries retain their bound shared workflow instructions. The result also includes `identity` and `version`. A separate `resolve` is unnecessary immediately after successful preparation. Preparation binds resources without claiming native activation; every later operation still enforces its admission requirements. For runtime creation, include `request: {action: "create"}`; for a selected run include its `runId`, using the same run-selection rules as resolve below. A missing locator is recovered from the selected store; an explicitly removed registration is never restored automatically. After preparation from this release, reuse its bound root and current launcher while the registration still matches. An older cached launcher alone is not proof that current Ready admission is available.

Successful preparation is silent in the user-facing report: continue the requested skill. Clean up only the temporary request files created by this invocation after they are no longer needed; preserve pending recovery evidence and unrelated files. Leave routine preparation artifacts out of the report. After execution and cleanup, check the final answer once more: remove preparation and housekeeping details, even when describing cleanup or confirming that project files were preserved. Report the requested result and any necessary user action that still blocks it. Keep locator paths, release identities and request JSON in diagnostics. If trust is required for the requested operation, state the exact native approval action in plain language. Do not quote internal admission or activation diagnostics to the user. Ask to reopen only when genuine activation requires it. If approval is denied or no user is available, preserve progress and leave dependent work pending. Conflicting configuration or preparation failures explain the blocked request and concrete recovery, never an empty backlog. Do not grant trust, enable deliberately disabled plugins/hooks, restore removed registrations or change unrelated configuration.

## Find the launcher and actual session

Host setup writes `nightshift-resources.json` in the selected host profile: `CODEX_HOME` or the user's `.codex` directory for Codex, and `CLAUDE_CONFIG_DIR` or `.claude` for Claude. Its `schema: 1` record supplies `store`, `registration`, `bootstrap`, `generation` and `state`. Use its exact bootstrap and registration, or the values from a native Nightshift hook. Do not select an arbitrary launcher directory or the highest version. A `removed` locator requires explicit restoration authority; automatic preparation preserves it.

On Codex, `CODEX_THREAD_ID` in the tool environment supplies the actual session identity. Claude native skill activation expands the session marker carried in each public skill. Preserve that expanded identity when re-reading the bound skill; a literal, unexpanded placeholder is not an identity. If neither native activation nor a hook supplies a Claude identity, invoke the skill through the native Skill interface rather than guessing a recent session.

If a locator is absent after interrupted setup, the current installed `internal/releases/launcher.js` accepts a read-only `status` request and lists registrations with their bootstrap paths. If that initial helper path disappeared before work began, rediscover the currently enabled installation through native plugin/skill metadata and retry its helper. A failed discovery is unavailable capability, not an empty ready set. Existing work never changes release merely because a newer cache exists.

## Automatic preparation and explicit maintenance

Write request JSON in the target project's ignored `.tmp` directory. Run commands in PowerShell 7 (`pwsh -NoProfile` when invoking PowerShell), with absolute paths passed as separate quoted arguments:

```text
node <CURRENT_PLUGIN>/internal/releases/launcher.js <setup-request.json>
```

The request uses `action`, not `op`. Skills use `prepare` as described above. Explicit maintenance may still supply `action: "setup"`, `host` (`codex` or `claude`), optional absolute `profile`, optional absolute `store`, and optional `pluginId`. The default store is `%LOCALAPPDATA%/Nightshift`; the default plugin identity is `nightshift@astenlund`. A custom installation must name its actual identity. The profile must already exist. Setup verifies the native installation and complete manifest, retains the payload, then registers user-level SessionStart, PreCompact and Stop hooks. It preserves unrelated configuration. Codex hook trust remains a native user decision; setup never grants itself trust. Ready and Exploring do not require native trust or an observed activation. Other ordinary operations require a native session that has observed the configured generation, reopening an older session only when needed.

The locator is written after registration. If this last write fails or is interrupted, the registered hooks and retained resources remain recorded; `status` or a repeated setup recovers the locator. A locator that names another live store is a conflict, not an overwrite target. Codex command paths currently reject shell-expansion characters; choose an explicit store path without them if a default path contains one. Claude uses native hook argument arrays. Native inspection depends on the host exposing its effective settings: the `--safe-mode` control channel with `get_settings` on Claude Code, and `config/read`, `hooks/list` and `plugin/list` on the Codex app-server; the verified baselines are Claude Code 2.1.268 and Codex CLI 0.154.0, and a host without these surfaces fails every dependent admission closed with a native-host diagnosis whose recovery is updating the host.

## Bound operations

Write each request as JSON and invoke the exact cache-independent values returned by setup:

```text
node <BOOTSTRAP> <REGISTRATION> <request.json>
```

`resolve` takes `session`, absolute `project`, optional `runId`, and an `entry` identifying the intended consumer. It verifies registration, enabled installation and exact resource ownership. The closed `ready` entry exception permits Ready and Exploring without trusted hooks or observed activation; removed or explicitly disabled hooks still fail. On Claude, whether hooks are disabled is the host's own effective `disableAllHooks`, resolved against the operating project, so managed, command-line, project local, shared project and user settings all apply in their documented precedence and a project may equally disable or re-enable what the user profile set. Every operation that carries a project resolves its inspection against that project, on both hosts, so registration, the Ready view and dependent admission cannot disagree within one session on the current release; a session bound to a retained 3.1.0 release keeps that release's runtime and hooks by design, so its dependent operations and hooks still apply the old profile-only check while its Ready view uses current admission; a hook whose Nightshift project root cannot be established still inspects its actual working directory. Profile-scoped operations carry no project and resolve against the profile: removal, maintenance `setup` invoked without one, and `status` invoked without one, which therefore cannot observe a project-level opt-out. One operation resolves the Claude effective value once and reuses it; the Codex listing is not reused, because the same snapshot is the input to configuration writes. An inspection that cannot run is a distinct recoverable failure, never an enabled result. A deliberate opt-out and a removed or changed registration are distinct states with distinct recoveries but share the `nightshift-disabled` code, separated by their message; denied trust reports `hook-activation-required`. Deliberate disabling wins on every path that retains a registration: if the retained registry itself is lost while disabled hook entries remain in the profile, preparation has no record to recognize them by and registers afresh, so a lost registry is not a deliberate-disabling signal. All other ordinary entries require current native trust and observed activation. Runtime diagnostics and existing maintenance permissions remain unchanged. With no binding it captures the current enabled release and creates a binding before admitting work; missing/changing initial source files can trigger at most three discovery/capture attempts. It returns the bound `root`, `identity` and `version`. Read the skill and shared instructions from that root before continuing. Existing or retired bindings never silently select a new identity. A successful Ready operation does not create activation evidence; a later dependent operation checks continuation afresh.

For runtime creation, include `request: {action: "create"}` when resolving resources before the invocation. A completed or stopped previous run with no active or uncertain workers does not select resources for genuinely new creation unless an explicit `runId` names it. An existing session still keeps its own release binding. Unfinished runs and uncertain workers retain their ownership, and the runtime independently enforces its creation gate before replacing the project's active-run pointer.

`run` takes the same `session` and `project`, an `entry`, and its entry-specific fields:

- `ready`: runs the Ready parser against the admitted project; Exploring uses this same parser and then its own presentation rules.
- `unwrap`: optional `write: true` and project-relative `target` (default `.nightshift`).
- `setup`: `setupAction` of `inspect` or `apply`, plus optional `options` object for init-backlog.
- `runtime`: the ordinary runtime request in the `request` object. Preserve its current `revision`. Controller/actor identity comes from the admitted native session; runtime ownership checks still apply.

An optional positive `timeoutMs` bounds the child operation. The launcher holds a resource lease until Windows process containment establishes descendant completion. The child receives a validated binding context and executing-root guard. Ready may use current administrative admission with the original bound parser; both administrative and parser bundle references are retained through verified termination. Ready, init-backlog, unwrap and runtime entry points refuse an ordinary unbound or mismatching by-path call. Helper subprocesses inherit a bound parent's context; only development/test callers propagate `--development`. Runtime checks choose `check.resourceMode: "development"` for checkout tests and private library fixtures, while the default `inherit` preserves genuine installed-helper propagation. Private probe copies explicitly use development mode. Temporary request files live in the admitted project's `.tmp/nightshift` directory and are removed after verified termination and required reference reconciliation.

`status` is read-only with respect to project engineering and reports registrations, bindings, activations, operations and bundles. With a registration and `session`, it also checks native hook/activation usability. Missing setup, invalid state and an unavailable native check remain distinct. Runtime `status`, `inspect`, `history` and `wait` diagnostics remain available without a bound invocation. Through the retained launcher they may overlap a running project operation, and their leases do not prevent a later writer; every entry keeps its own resource lease until termination and reference reconciliation. Other project entries remain serialized, including when a previous writer's termination is uncertain. A run records `resourceMode` as `bound` or `development`; historical absent mode is legacy. Bound runs and review receipts retain their exact resource identity.

## Ownership transfer and current execution

Run creation retains `resources` as immutable provenance. After adoption, `executionResources` identifies the current admitted execution binding, with the same `{schema, store, registration, session, identity}` grammar; an unadopted historical run without that field uses its original resources. Resource selection, runtime admission, hooks, current run references and report notices follow current execution ownership. Native activation alone is not a controller claim: before canonical engineering each new/resumed turn, obtain successful `claim-controller` (or successful `create`/`resume`) through the runtime interface. Read-only preparation and status never grant it.

An explicitly authorized runtime `adopt` request identifies the current `runId`, latest revision and exact previous controller. The launcher authenticates the target session independently of creation provenance and admits takeover only under the runtime's worker/operation and former-controller inactivity rules. A stopped source may keep its original chat open; a running source needs proof that its recorded native host process has ended. Native process inspection failure is unknown, not inactive. Adoption is restricted to the same store, compatible exact retained payload and resource mode. It never upgrades an older retained runtime that lacks adoption or moves work between machines. Mismatches require explicit recovery, not a substituted binding or development-mode bypass.

For bound adoption, target binding and provisional run retention precede the ownership transaction. If interrupted before ownership commits, the former controller remains owner and target protection remains conservative. A rejected proposal remains protected until another adoption attempt succeeds or deliberate target retirement cancels that never-owned reference as described below; source completion or another adopter winning does not make retry the only recovery route. If ownership committed before target-reference attachment completes, retry reconciles the current execution record and retains both references until the target protects the exact payload and evidence dependencies. Only then can the source run reference become historical. Its provenance remains inspectable but it no longer blocks source-session retirement on account of the adopted run. The source session's own binding still retains its bundle until ordinary retirement. Missing state, unknown workers/operations or incomplete target protection continue to block retirement and collection. Development runs have no registry-transfer phase; their transactional ownership record is the durable boundary.

Adoption leaves the run stopped and attended with its continuation and current claim cleared. Reconcile terminated worker records and unfinished command results, then resume only under authority to continue. New worker environments and assignments describe the actual executing session; receipts retain their original dispatch resources and controller attribution, which runtime import checks against ownership history. Former controllers cannot supply new independent review or skeptical validation. Current-owner hooks route saved report obligations without letting former sessions issue continuation instructions.

Continuation observation and admission remain separate. If admitted but current continuation is inactive or unknown, use owner-only `invalidate-continuation` with the observation, preserve handover/report duties and continue useful authorized work attended. Refused admission cannot persist that downgrade and leaves saved state untouched. Only permitted diagnostics/maintenance and independent work may continue until the actual enablement, trust or activation recovery occurs. Do not silently restore disabled integration or treat historical verification as current proof.

## Removal, retirement and collection

`remove` unregisters only owned hooks for this profile, preserving unrelated entries and their trust state. It remains callable through the retained bootstrap after plugin uninstall. It marks the locator and registration removed, retaining work, resource history and administrative code. A missing profile is already unregistered. Disabled/uninstalled plugins do not admit new work; only status, removal, termination reconciliation and import of already-produced receipts remain available for existing bindings.

`retire` names `targetSession`. Status includes activation-only sessions as well as work bindings, so either can be retired explicitly. Active or uncertain operations prevent retirement. Associated currently owned unfinished runs must first be stopped and explicitly selected in `retireRuns`; a historical source reference after completed adoption follows the target-protection rule above; completion alone releases a run reference only after workers are reconciled. Retirement preserves a tombstone and historical identities. `recover` explicitly names a retired `targetSession` and can restore only its exact identity, if a complete copy or matching enabled source is available. Dependent operations require genuine native activation again; the Ready/Exploring exception remains available after exact recovery.

For a failed pending proposal, `retire` additionally accepts `cancelAdoptions`, an array of unique run IDs whose never-owned provisional references should be abandoned. Once the user has directed retirement of that target session, the controller can derive this selection from verified status; no additional user confirmation is required. Under registry admission, cancellation requires readable compatible run state and ownership history proving the target was never a controller, reconciled workers, and no active or uncertain project writer. It removes only those pending references while retiring the session, leaving the run and its real ownership unchanged. Omitting the selection preserves protection and diagnoses this cancellation route. Current or historical owner references cannot be cancelled, including when a transfer committed before reference reconciliation; they follow ordinary retirement. Missing evidence fails closed. Session recovery does not recreate removed proposals, and ordinary collection never cancels them automatically.

`collect` is explicit. It checks the full registered reference inventory under the same serialization as admission. Active/uncertain operations, bound sessions, unfinished non-retired runs and administrative registrations keep their resources. Missing project state, unknown record kinds and invalid records fail closed. Complete unreferenced bundles and staging directories with proven inactive writers can be collected; no age-based cleanup runs automatically. Administrative bootstrap versions remain outside the disposable cache and current administrative bundles remain retained while registration records reference them.

## Persistence and recovery

The per-user `registry.sqlite` uses protocol 1 and transactional records for registrations, activations, sessions, bundles, operations and project references. File paths are canonical and bundle identity is the version plus the SHA-256 of the shipped manifest bytes. The manifest lists raw-byte lengths and SHA-256 values, with LF checkout policy for retained text. The release gate verifies the committed manifest against committed payload bytes and requires every hashed resource, including the manifest itself, to have `eol=lf` with text handling or explicit `-text` for binary resources. A fresh-index checkout fixture verifies hashes with `core.autocrlf=true`. Unsupported schemas or dependencies are not accepted as compatible.

Capture holds registry serialization through publication and binding creation. Staging is never selectable. A complete directory published before its registry transaction committed is verified and recovered as an orphan publication on the next inventory/capture. Incomplete or unsafe directories remain unselected. A session binding without a started child stays protected because admission may have been interrupted. Projects are indexed before work and newly created run references are reconciled before releasing operation ownership. A failed post-child state read preserves the operation lease. Retirement, collection and reconciliation of a terminated operation inspect the provisionally indexed projects and attach matching run identities before releasing protection, including references missed by earlier bookkeeping. Missing or unsupported project state and inventories over 10,000 saved runs prevent that reconciliation.

Collection writes a durable `deletions/<bundle-key>.json` intent before deleting a verified unreferenced bundle. The intent binds its key and exact identity and survives registry rollback. With intent only, retry checks references again before deletion; after a partial directory deletion it can finish the same confined ordinary directory; after directory deletion but before the database commit it removes the stale record on retry. Once the record deletion commits, a separate pass removes the intent. A crash before that final pass leaves a removable completed intent. Protected references still win over an outstanding intent. Missing, malformed or conflicting intent cannot authorize removal of an arbitrary damaged bundle; it remains a recovery diagnosis. No age-based deletion is introduced.

Setup records a pending owner and configuration plan before writing. A dead pending owner can be recovered; a live or unknown owner is not displaced. Preparation reconciles pending registration before deciding whether new setup is needed. Recovery of an applied journal preserves its native definitions and generation. A no-op configuration write can have no journal: matching native definitions allow metadata completion without rewriting configuration; otherwise the pending setup remains unfinished and follows the ordinary setup/recovery checks. Codex uses its version-checked configuration API and verifies surviving positional hook identities/trust after changes. Recovery distinguishes the unchanged pre-write version from the prepared result; conflicting state is preserved. A Codex journal records the directory its surviving hooks were listed against and prefers it on recovery; when that directory has since been deleted, recovery compares against the recovering caller's context instead, so a deleted checkout never blocks preparation, setup or removal. Claude retains original and planned bytes inside its profile, then writes under an exclusive file lock. An already-written result is idempotent; unchanged original bytes can be replayed. A target matching neither saved state, including an indeterminate interrupted write, is a conflict: preserve both recovery files and obtain explicit resolution rather than overwrite possible user edits. After registration/removal commits, matching recovery files are discarded.

Operations record admission before launch, then runner and contained-child identity. A prepared operation whose owner died did not launch a child. A contained operation can be reconciled after its owner, runner and child are gone; unavailable liveness remains uncertain. Runtime entries record their requested runtime action; Ready, unwrap and setup entries record null. Missing action metadata on an older lease is potentially run-creating. Recovery of a runtime or older unknown entry requires readable project run state before releasing its lease, and run creation requires that state at the initial post-child attachment too. A missing database retains protection rather than implying no run exists. Genuinely unused Ready-only projects need no database, while projects with attached run references must retain readable state. Unknown launch state is retained rather than treated as completion. Bootstrap and capture leases carry no independent project engineering; dead leases can be reconciled while session/run references continue protecting work.

Activation has one record per host/profile/native session and generation, with a native process identity. It does not pin a release. Actual native activation refreshes it, trust/generation changes invalidate it, and explicit retirement/removal deletes it. When no owner is identifiable, activation-record failure is silent and uses nonblocking registry admission; explicit status and activation-dependent work admission diagnose missing activation. Bundled notices follow the same silence rule and never mutate delivery state. Native hook invocation and supported permissions must be observed on the actual host; a stored flag alone is not continuation proof.
