# Nightshift operating brief

Use this brief inside an authorized Nightshift lifecycle or an explicit revise request. A project's governing requirement to use Nightshift for implementation also activates this lifecycle once the user agrees the implementation scope; handover is not required. Plain review and review-loop requests belong to the user's direct-agent routines and do not enter this workflow.

## Priorities and authority

Reliability comes first: autonomy and trust as equal parts, never one bought at the other's expense, with trust earned through independent quality assurance. Where both cannot be had, keep what can be trusted, make the blocker explicit and continue independent work. Speed, efficiency and economy count only where they cost neither. All of this stays within the user's authority and limits. Before a destructive, irreversible or outward-facing action that recorded authority does not cover, ask the user; with no user available, as in unattended work, block the task that needs it with a `user-decision` blocker and continue independent work. Continue until the authorized work and its required evidence are complete, the user stops it, a resource limit is reached, or every remaining item is blocked without an authorized recovery. A routine failure calls for recovery or a changed approach. It is not an occasion to declare the session done.

Investigate the actual problem before editing. Small work needs a short understanding readback and confirmation; substantial work needs a concise spec of consequential commitments, boundaries and acceptance evidence. Either form ends with a plain question asking whether to begin the work, and only a yes to that question is implementation agreement. Agreeing with an idea, a wording or a direction while it is still being discussed is not, so the session stays interactive and no implementation starts until that question has been asked and answered. Start independent spec assessment through a nonblocking dispatch, then promptly present that same complete stable draft for the user's review while assessment runs. Preserve the worker handle and draft identity. Do not wait for assessment results or work its findings before making the draft available to the user; a progress notice alone is not the presentation. If nonblocking dispatch is unavailable, disclose the sequencing limitation and obtain both reviews without claiming overlap. Implement once the commitments are agreed and the spec assessment is resolved. A governing spec states its commitments only: record the user's acceptance with the runtime `spec-accepted` operation, never in the spec's text, keep assessment counts and the narration of decisions out of it, and write a decision that changes commitments into the commitments themselves through the user-decision route the runtime reference describes. Compatible corrections preserve agreement; material changes need the user's decision. A shared agreement may cover a finite queue. Handover is the user's act, invoked through the skill or in prose, and until then the session stays interactive. Every item the user intends to hand over has its readback or governing decisions settled and confirmed in that interactive phase first, so a queue is handed over once and then runs unattended. A handover requested before that settlement is answered with the outstanding readback or decisions, not accepted; the settlement then happens in the same interactive exchange, and a renewed handover is accepted only once it is confirmed. Saved files, backlog readiness and a stage label do not themselves confer authority.

Implement directly with a strong model. Written implementation plans are exceptional guidance for deliberately selected weaker or cheaper implementers. There is no routine plan stage, plan-review ladder or Superpowers dependency.

Nightshift establishes root `.nightshift` as the home for its new project-owned artifacts, whether or not the directory exists yet. Create new standalone governing specs in `.nightshift/specs`; keep feature and backlog documents in their established `.nightshift` locations. This is the workflow's established convention, so the generic per-host fallback does not apply to these new artifacts. Honor user-supplied or explicitly selected document locations and required host configuration paths; applying Nightshift review does not transfer ownership of those files.

## Durable execution

Read [the runtime interface](runtime/REFERENCE.md) before starting or resuming a run. For implementation governed by a project lifecycle requirement, create an attended run before implementation or reconcile the compatible run already owned by this session. Explicit handover uses unattended mode and its continuation requirements: with continuation verified, a run created at handover starts unattended, and a run already underway is handed over with the runtime `handover` operation, which records the handover and switches the mode in one write when continuation is verified. Never recreate a run to change its mode. When continuation cannot be verified, create new work attended or invalidate an existing run's continuation first, then record the handover in attended mode; when the session is not admitted to the runtime nothing can be recorded and the handover is not accepted. Investigation without implementation agreement does not create a delivery run, and a run owned by another session requires ownership reconciliation rather than replacement. Capture the accepted outcome, the source of authority, queue dependencies, publication authority, limits, actual controller session and current evidence, and name the intended branch and checkout in the run's objective. Review, skeptic and dialogue dispatches are part of the lifecycle and need no token budget, so do not ask the user for one; a token or cost limit the user gives covers live verification, such as real-model probes and acceptance campaigns, unless the user says it also covers those dispatches. Use the transactional operations for consequential transitions. A failed write or stale revision requires reconciliation before dependent work. A status operation supplies focused current obligations; read it when beginning work, dispatching or accepting review, changing a finding disposition, claiming completion, and after compaction or reopening.

Before canonical engineering in every new or resumed controller turn, reconcile status and obtain a successful `claim-controller` result; successful `create` or `resume` also grants that turn's claim. A status read, native activation or old claim is not a grant. If the claim fails, preserve files and use permitted diagnostics until ownership or admission is resolved. To take over another session's run, use explicit adoption authority and the runtime's inactivity and compatibility checks, then reconcile terminated workers while stopped and resume only under authority to continue. Never replace an unfinished run or treat an open original chat as proof of active work. The runtime reference defines the distinct stopped and abandoned-running cases.

The continuation mechanism depends on the host. On Codex, whose models tend to yield their turn early, only a verified native persistent goal carries unattended work. On Claude Code, whose models do not, and which exposes no native goal, a verified functioning Stop hook carries it: registered, enabled and trusted for the project, with activation observed in the controller's current session, as the resource interface's `status` reports. Record the mechanism with its kind, `goal` or `stop-hook`; the runtime refuses a Stop hook for a Codex controller. Neither mechanism recovers work after a host exit or restart. At renewed handover, adoption, resume, compaction recovery and before unattended yield, reconcile the queue, files, workers and current continuation. Classify a goal as active, inactive or unknown from actual host evidence, distinguishing absent, blocked, paused and complete states, and re-verify a Stop hook's registration, enablement, trust and session activation. Use a supported native resume operation only when available and authorized, then read back the result. If no resume operation is available, name the necessary user action and verify restoration when observed; do not replace an unfinished goal or infer success from a request. A worker running elsewhere does not continue the controller. The verified mechanism supplies continuation; the run's state and current evidence establish completion.

The registered host hooks use retained resources to restore focused obligations and resist premature completion. Follow [the resource interface](releases/REFERENCE.md) for automatic preparation, native activation and session binding; passive bundled hooks do not install Nightshift. Ready and Exploring use retained resources without continuation activation. Other ordinary operations retain their activation requirements. Verify that the chosen continuation mechanism is loaded, trusted and functional on the actual host at those reconciliation boundaries. With admission available but continuation inactive or unknown, call `invalidate-continuation` with the observation before treating the run as attended, preserve its handover/report duties, and continue useful authorized work in the active turn. Fresh verified continuation plus `handover` can restore unattended mode. When admission itself is refused, no downgrade is persisted: saved verification is unusable, and only permitted diagnostics, maintenance and independent work may continue until the actual trust, activation or enablement recovery occurs. Never use development mode to bypass admission or silently restore disabled integration.

After compaction, reconcile the record against actual files and surviving activity before dependent operations. Preserve other writers. Reject stale checks and reports. Recover failed tools, workers, reviews and transient provider errors within the user's limits; after repeated failures, change approach. Pause only dependent work when a material decision or capability is blocked, and continue independent queue items. Await a long dispatch inside the turn with the runtime `wait` operation. For a running handed-over run, a functioning Stop hook protects against premature yielding even after downgrade to attended, but it establishes continuation only through a fresh `stop-hook` verification on Claude Code, and never on Codex. Short of verified completion, an explicit stop or exhausted limit, or a blocked run's recorded session closing, end the turn only when every remaining item waits on a user decision and no worker is active, which the Stop hook permits as a conversational pause, or, on Claude Code, with the acknowledgement of a verified unattended handover, after which the Stop hook resumes the work. Its three-reminder no-progress bound survives claim-only writes and repeated invalidations that change no execution state. An unavailable hook provides no protection. A merely attended run without handover retains conversational yielding. A stopped host may end unattended execution until the user reopens it; automatic relaunch after exit or Windows restart is outside v3's MVP.

## Model roles and ownership

Fable and Astra are interchangeable strong-role reference models. Either supported Windows host must be able to carry the complete lifecycle with fresh independent contexts. Choose assignments using task fit, observed strengths, availability, context and cost under the priorities. Establish the problem first regardless of model. There is no fixed controller/implementer team.

Working hypotheses from the user's reports: Fable tends toward deeper deliberation, broad contextual reading, sustained focus and strong visual design; Astra tends toward fast precise coding, computer use, quantitative work and skeptical evaluation of plausible prose, often through effective intuition. Both handle browser interaction well. Use these observations as preferences to test against actual task evidence. Longer reasoning is not itself a correctness signal, and either strong model can perform any required role.

Prefer an equivalent-strength lead reviewer on the other host when suitable and available. The controller chooses placement based on independence from the reasoning that shaped the solution and the actual task constraints. Fresh qualified same-host review is valid. Explicit model requirements bind; a preference permits an adequately capable allowed substitute, with the reason recorded. If the strong reviewer becomes unavailable, secure a permitted strong substitute, preferably on the other host, before applying further repairs to the affected work. Without one, pause those repairs while independent authorized work continues. Advisory assessment never supplies the required strong review coverage.

Use bounded helpers when authorized and useful. Record assignment, host/session, model/effort, and exclusive write ownership. For recoverable in-host work, arrange the registered helper's terminal report and preserve its actual native event evidence as the runtime reference specifies; a turn ending does not establish termination of a continuing assignment or its surviving work. Reviewers, skeptics and reviewer peers never change reviewed inputs. After adoption, exclude every former controller as well as the current controller from new independent assignments. Preserve valid imported historical evidence with its original attribution; an adopter-authored unimported receipt needs fresh independent assessment. Other historical receipts remain usable only when their original attribution, independence and current inputs pass the runtime checks. Peers clone their lead's model and effort. Checks that mutate inputs need isolated fixtures. A lead can ask the controller to dispatch peers and incorporate their assessments; the lead owns credible integrated coverage. A lower-tier supervisor can coordinate assignments, progress and routine recovery; consequential engineering judgment, authority, finding dispositions and final acceptance stay with the controller. Direct or sequential coordination remains valid when it meets the workload without sacrificing assurance or causing avoidable stalls.

## Review and repair

Use [revise-code](../skills/revise-code/SKILL.md) for implementation assessment and repair within the run. Give the fresh strong lead the agreed requirements, complete cumulative change or whole spec, surrounding context, applicable conventions, every dimension below and the recorded acknowledgements: settled dispositions, refuted findings and intentional choices that the governing requirement or the user made, each scoped narrowly and never the author's reasoning. A fresh lead receives no other earlier findings. Do not choose only relevant dimensions or supply the author's correctness rationale. One reviewer is normally enough for a small change. The lead decides whether greater depth or peer assistance is needed for credible coverage. A failed or partial assessment is incomplete even if it reports no findings.

Every finding receives fresh skeptic validation against concrete evidence. A skeptic can validate a small batch; an empty finding set needs no skeptic. Convergence is a reason to investigate, not proof. Keep factual validity, authority and practical value distinct. Every confirmed verdict carries the skeptic's repair proposal: the approach a repair would take, with enough reasoning to judge it. Decide implement, defer with a reason and durable route, skip as an accepted tradeoff, or refuted based on evidence. Missing evidence stays unresolved. A required commitment cannot be waived because its repair is expensive. When a finding's consequence, value or repair quality stays unclear or disputed after validation, relay a dialogue between the reviewer that raised it and the skeptic that validated it through resumed dispatches, or replacements when a session cannot be resumed; never connect them directly, and keep every disposition yourself. Before implementing a finding whose current verdict carries no repair proposal, as when you implement against a refutation, obtain one through a dialogue turn with the skeptic.

When a read-only assessor needs execution evidence, inspect the exact command and fixture source in its untrusted probe proposal, establish that all effects fit authorized verification, and run it through the private-copy probe operation. This uses controller privileges, so the private directory and inventory drift check are not a security sandbox. Return the raw command and output for independent interpretation. Keep execution-dependent claims unresolved until the evidence decides them; do not grant canonical write access to solve a tool limitation.

Validate and dispose the complete intended batch against current evidence, and read back that the runtime recorded each disposition, before editing. Never issue a repair edit in the same message as the validations or dispositions it waits on: the edit uses none of their output, so it looks independent, but calls issued together can run in any order. Interleaved edits can invalidate evidence for remaining dispositions; re-establish that evidence rather than narrowing its scope automatically. A paused strong review gate also pauses further repair application to the affected work until a permitted strong reviewer is available to assess it; advisory feedback does not lift that pause or count as the required review coverage. Recover the strong assignment under the model-role rules above while continuing independent authorized work. After every repair batch, however small, run relevant verification, then resume the reviewer that raised each repaired finding, the latest reviewer of any other review kind whose reviewed files the repairs changed and, whenever a repair changes code, the latest docs reviewer of the affected tasks. Each records closure of its own repaired findings and reassesses its kind's full cumulative change across all dimensions, including sibling paths and previous repairs; revised specs receive whole-spec assessment. A reviewer that cannot be resumed gets a replacement given its findings. A resumed reviewer verifies repairs well but can develop tunnel vision, so a continued assessment never passes a gate: repair first, and once no critical or important finding awaits repair and none is pending closure, follow it with a fresh strong lead of its kind. A completed fresh assessment with no edits needed can pass after no-edit dispositions resolve its findings; a literal extra LGTM is unnecessary, and its minor findings may be deferred. Repairing any of its findings resumes that reviewer and repeats the cycle. Weak or narrow coverage cannot pass the gate.

Three successive passes raising related findings after repairs are a signal to investigate the shared cause and the repair approach. Same area alone is weak evidence. Missed siblings, repeated invariant violations and repairs undoing earlier repairs are stronger signals. Reconsider the approach or seek a specialist when warranted; do not automatically launch a swarm, halt or ask the user.

### Spec dimensions

- Intent, scope and acceptance: desired outcome, meaningful behavior, boundaries and success evidence.
- Soundness and integration: feasibility in the real project and operating environment.
- Failure, safety and recovery: consequential failures, trust boundaries, data preservation and recovery.
- Clarity, consistency and proportionality: understandable commitments and reasoning without contradictions, missing decisions or unnecessary prescription.

Review mechanisms the spec actually commits to. Do not invent an implementation and report its unchosen details as spec gaps.

### Code dimensions

- Requirements and user experience: agreed behavior, usable flows and relevant accessibility.
- Correctness and integration: normal, boundary, concurrent and failure cases, callers, state transitions and siblings.
- Security and data safety: trust boundaries, permissions, confidentiality, integrity and recovery.
- Design and maintainability: readable local code and coherent system decomposition, ownership, reuse and coupling.
- Performance and resources: consequential latency, throughput, resource use and operating cost.
- Tests and evidence: meaningful assertions and realistic execution, with remaining uncertainty explicit.

### Documentation dimensions

- Claim accuracy: each changed or affected claim matches the code, records and evidence it describes, at the version it names.
- Sweep completeness: documentation, changed or not, that the change left stale, contradictory or missing.
- Backlog conventions: the project's backlog grammar, dependency, history and retirement conventions.
- Sibling consistency: agreement with sibling entries, index excerpts, their records and history files.
- Proportionality: depth proportionate to importance, useful reasoning preserved, nothing overstated or stated as current before it exists.

A docs review judges what the documentation says about the code, with the code as context. Files agents load as operating instructions, such as skills, this brief and the runtime references, are code and need code assessment even when a documentation pass edits them.

One problem is one finding even if several lenses expose it. Every lens receives consideration, without finding quotas, equal-depth narration or duplicated criteria.

## Close and report

Use [revise-docs](../skills/revise-docs/SKILL.md) to reconcile documentation and backlog records with actual delivered behavior and evidence. Preserve source references and rationale for retirement; retired proposals are not shipped features or fixed bugs. Run the real ready parser after backlog changes and record it as the ready parser check: a runtime check that runs the bound release's `skills/ready/ready.js` with `--check`, which exits nonzero unless the parse is clean, with no structural error, notice or missing index. Without the flag the parser exits 0 despite such problems, so a passing check without it establishes nothing about validity. Retain its dependency walk and history conventions. Make these edits after the task advances to documentation: an edit after a review import makes that review stale and blocks the advance. Then obtain a strong independent docs review of the complete change with the documentation dimensions, fresh skeptic validation of its findings and, after every repair batch, the resumed docs reviewer's closure and reassessment followed by a fresh docs review, as under Review and repair; code and docs tasks cannot complete without it, unless a purely mechanical change records its exemption. Edits confined to the backlog, meaning the four indexes, their history files and records under `.nightshift/features`, `.nightshift/bugs` and `.nightshift/patterns`, are covered by that docs review. Any other edit to work under code assessment, meaning a code task or a docs task that imported a code assessment, and any edit to operating instructions, also needs a current cumulative code assessment before task completion; descriptive prose in a docs task without one needs only its docs review.

Complete task documentation before releasing dependent engineering. Internal governing-spec assessment ends when its independent assessment is accepted. Use [revise-lore](../skills/revise-lore/SKILL.md) to perform one session retrospective after actionable work settles and before the closing follow-up triage; do not repeat those closing steps for each queue item or internal prerequisite. When the only remaining work is a task blocked on a user decision, ask first and close after the answer, since an answered decision invalidates closing evidence recorded before it; closing stays due if the user does not return, and the question carries the same stand-alone context as a morning-report item. Optional follow-up decisions are different: they never delay closing, the morning report or a completed delivery. Examine user corrections, recurring failures, ineffective rules and useful lessons. Prefer concise principles grounded in observed evidence. Propose worthwhile instruction changes as concrete diffs with motivation and independent assessment before asking the user to approve. Do not modify instructions merely because a retrospective suggested an improvement. With no worthwhile proposal, finish the retrospective without manufacturing one.

A handed-over run, meaning one with a recorded handover whatever its saved mode, owes the user a morning report, and the runtime holds that obligation: after the retrospective, write the report to `.nightshift/runs/reports/` and record it with `report` before triage; completion requires it. Write it for a reader who saw nothing of the run. Never assume that progress output, the continuous log or a question asked while the user was away was read. In this order it gives: what was delivered and its verification with stated limits; which of revise-code, revise-docs and revise-lore actually ran, naming any omitted, blocked or later-recovered stage and any task a mechanical exemption let complete without a docs review, with its reason; commits and publication status; the material retrospective outcomes, distinguishing implemented repairs, open tracked work, recovered incidents with no durable follow-up, and instruction proposals or the reason none was worthwhile; whether the run operated unattended or stayed attended with its recorded limitation; and, last, every unresolved item with what it is, where it is, what failed, its impact and the pending choice. An acceptance artifact, a saved retrospective or a commit confirmation is not the report, and "follow-ups are tracked" is not a readout.

The report and the follow-up triage are one hand-off. With the user absent, record the report, record triage evidence stating which decisions stay deferred, complete with those follow-ups pending, and end with the full report itself as the final message. A summary of it, or a statement that it was saved, is not the report, and a run that closes blocked ends the same way, with the blocker in the report's unresolved items. The report as presented always ends with its unresolved items, which list every pending follow-up, followed by a plain question asking whether the user is ready to triage them, or with a plain statement that no decision is pending. When the user is next present in the owning session, through a reply or the SessionStart morning-report notice, present the report that way if they have not seen it, re-presenting it from the saved file yourself instead of sending the user to find it. Their first reply is the delivery authority: record `report-delivered`, then start triage with the first pending follow-up. That reply answers no follow-up; if it says the user is not ready, the follow-ups stay pending until the user asks to triage them. An unanswered final message is not delivery. When the notice marks the saved report as not current, rewrite it and record `report` again before presenting. Delivery blockers are reported as blockers, never as optional follow-ups.

A run without a handover has no report stage. Its final message still lists pending follow-ups and other loose ends (unfinished or blocked obligations, qualified verification, mechanical exemptions with their reasons, unpublished commits) with enough context to act on, beside the readout of which workflows ran.

Triage decision-requiring follow-ups one at a time, with concrete context, a recommendation and the effect of each choice. Every triage item, including the first after a morning report, is a host question: present it through the host's native multiple-choice question tool, such as AskUserQuestion on Claude Code, with the item's full context, the recommendation and the effect of each option inside the question and option descriptions, since text sent alongside the dialog may not render; fall back to a plain-text question only where the host offers no such tool. Use fix now, track or skip where appropriate; preserve the original approve, adjust or revert terms for deferred approvals. Wait for the answer before presenting the next item. When the user is unavailable, preserve unanswered items in the run and report that they remain decisions, not completed work. Mid-run ideas go into this follow-up record so they do not derail the authorized queue.

Apply the tracking edits that triage decisions call for after triage is recorded, keeping them to the backlog. Rerun checks whose inputs they touched, such as the ready parser check, and obtain a closing docs review of them through the runtime's closing record before completing the run; its findings take the same skeptic, disposition and repair loop and never reopen tasks. A change outside the backlog is not tracking: on a running run it needs ordinary cumulative reassessment, and on a completed run a finding that needs one is deferred with a durable route, or stays unresolved when it is a required obligation. For a handed-over run that completed before its follow-ups were answered, record the closing checks and closing docs review as bookkeeping after the tracking edits. The run's recorded limits still bind them; when a limit prevents them, report the tracking edits as not independently reviewed rather than overriding it. An unresolved closing record, or tracking edits a limit kept from its review, are not independent review coverage for publication, so publishing those edits needs another independent review.

Commit coherent local work under the user's Git policy and required hooks. After every commit, by the controller or a helper, confirm that it landed on the run's intended branch and checkout; on a mismatch, stop the dependent work and reconcile it only within recorded authority, since a reconciliation that would rewrite history or discard work needs the user's decision as Priorities and authority describes. Publication proceeds only when authorized and independently reviewed, including any applicable advance handover authority. Do not repeat settled approvals. Without publication authority, finish locally and report unpublished status. Report delivered work, verification and its limits, accepted tradeoffs, deferred work and every incomplete obligation accurately. Identify the required workflows actually performed and any omitted or blocked stage from their execution evidence. Reading a skill, recording a stage label, or substituting a direct review or ordinary file edit does not establish completion of that workflow. When required machinery is unavailable, preserve the evidence and capability limitation; do not claim the lifecycle complete. Later recovery records when the missing work actually happened without claiming it had happened earlier.
