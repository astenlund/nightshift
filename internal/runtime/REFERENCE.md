# Runtime interface

Requires the supported Node.js 22.23 or later baseline. The implementation uses Node's built-in SQLite transactions; no package installation is needed. Run commands in the project's shell, using `pwsh -NoProfile` for PowerShell. For installed work, follow [automatic preparation in the retained resource interface](../releases/REFERENCE.md#skill-activation). Runtime admission still requires native continuation activation for ordinary operations, even if the session previously ran Ready without activation. Write an envelope with `action: "run"`, `entry: "runtime"`, the actual native `session`, absolute `project`, and the runtime request under `request`. The runtime request names its operation in `action`, as in `{action, actor, revision, ...}`; a missing or unknown `action` is refused before any state or ownership check with a message listing the accepted actions, as `invalid-request` from the runtime and `invalid-runtime-request` from the launcher. Invoke the exact bootstrap and registration from the host locator:

```text
node <BOOTSTRAP> <REGISTRATION> <envelope.json>
```

Explicit repository development uses `node <CHECKOUT>/internal/runtime/cli.js --development <PROJECT> <request.json>`. This creates development runs and cannot mutate an installed bound run. Preserve matching controller/actor identities and current revisions in runtime requests. Bound runs, workers and review receipts record their retained resource identity.

Stdout is JSON. Nonzero exit and an error object on stderr mean the operation did not complete. Do not convert an error or missing result into a clean check. Use the host's background-process facility for long dispatches; preserve the process handle and artifact paths for later collection. Await a running dispatch inside the turn with `wait`, described under Staffing and follow-ups, rather than by ending the turn: for handed-over or unattended running work, a functioning Stop hook resists a yield while a dispatch worker is active. For spec intake, present the complete stable draft after dispatch starts and before polling or awaiting its result, so the user can review it while the independent assessment runs. Process completion and receipt import remain separate from launch; an uncollected or failed assessment cannot satisfy the review gate.

## Start and observe

`create` accepts `objective`, `authority` describing the actual user agreement, `controller: {host, session}`, and a finite `tasks` array. Host is `claude` or `codex`; session is the actual host identity supplied in the SessionStart binding. Each task has a stable `id`, `title`, `agreement: {source, outcome}`, optional `requires` containing other task ids, and optional `kind` of `code` (default), `spec`, `docs` or `lore`. The task identity `#closing` is reserved for the closing record described under Documentation review. Substantial code tasks record their governing spec in `agreement.spec`. Record `agreement.specReviewed: true` only for an already observed valid independent assessment; creation binds that fact to the current spec bytes. Otherwise use `add-spec-review` on the code task to create a linked governing-spec assessment task, complete its strong whole-spec review, and continue implementation. `agreement.specReviewTaskId` identifies that task. Implementation changes do not invalidate the accepted spec assessment merely because surrounding code changed; a changed spec does require whole-spec reassessment.

`spec-accepted` records the user's acceptance of a task's governing spec. It names `taskId` and takes `authority`, the user's actual reply after the spec was presented, and stores `specAcceptance: {authority, revision, snapshot}` on the task beside its agreement, never inside it, because assessments bind the agreement and a change there would make them stale. The snapshot binds the spec's current content with the same line-ending tolerance as review freshness. It is refused with `missing-spec` when the task's agreement names no spec or the spec file is missing, and with `run-complete` on a complete run; it is accepted on a running or stopped run and on a blocked task. Recording it again while the spec still has that content keeps the original record; after the spec changes, it replaces the record. It never gates another operation. Status gives `specAcceptance: {recorded, current}` for each listed task whose agreement names a spec, where `current` is false once the spec's content has changed. Record acceptance this way rather than in the spec's text, which is what its assessments review.

Use `mode: unattended` for a run created at handover. It requires verified host evidence before execution, recorded afterwards by the `continuation` operation or by the `handover` operation described under Handover and the morning report, not by a field of `create`, and it records the handover from the run's `authority`. An absent mode means attended operation. An existing run is handed over with `handover`, never by creating a replacement. When continuation cannot be verified, create the run attended and record `handover` without a mechanism instead, because unverified unattended execution is refused with `unverified-continuation`; claims, explicit invalidation and permitted bookkeeping remain available for recovery. Agreed implementation under a project requirement to use Nightshift starts an attended run before implementation, or reconciles an existing compatible run; it does not require handover. That lifecycle uses revise-code, revise-docs and revise-lore under the operating brief, with their actual evidence recorded through the operations below. Include publication authority when granted; absence means local delivery only. Supported deterministic `limits` are a UTC `deadlineUtc` ending in Z, and nonnegative `maxDispatches`, counting actual host attempts including fallback. Unknown limits are rejected rather than ignored. Establish any separately requested token/cost limit through a verified host or campaign mechanism, recording its metric and coverage before unattended work; an unavailable enforcement path is a capability blocker.

`status` returns current obligations; `inspect` returns the complete state; `history` returns the saved transitions. They accept an optional `runId`; otherwise they use the current run. The database at `.nightshift/runs/state.sqlite` is authoritative. History and current state commit in the same transaction; large immutable evidence is stored once and referenced by content identity. An interrupted transaction rolls back on reopening; completed transitions survive. Missing, unsupported or contradictory state is a recovery problem, not permission to restart work over another owner. Hooks restore a focused brief without loading large evidence payloads; acceptance operations perform the actual freshness checks.

Every mutating operation after creation includes `actor: {host, session}` matching the owner and `revision` from the latest status, except the explicitly authorized ownership transfer below. Stale revisions require another read and reconciliation. Task operations name `taskId`. `create` is refused with `overlapping-run` unless the checkout has no run or its current run is complete or stopped with no active workers. The runtime therefore permits replacing a stopped run whose tasks are still pending; [the operating brief](../workflow.md) forbids replacing an unfinished run, so such a run is resumed or adopted rather than replaced. Completed/stopped runs remain in history when a new authorized run starts.

## Controller claims and adoption

Before canonical engineering in each new or resumed controller turn, read status, reconcile actual activity and call owner-only `claim-controller` with the current actor and revision. Successful `create` and `resume` also establish that turn's claim. Only these successful results carry `controllerReady`; viewing state, native activation, continuation verification and a previously saved claim do not grant it. Native process identity comes from the actual invoking host, never a caller-supplied PID, found through the process ancestry that [the resource interface](../releases/REFERENCE.md#automatic-preparation-and-explicit-maintenance) describes. Failed claim observation grants no engineering authority; when the ancestry reaches an exited parent, the claim reason names the last live process below it and the likely invocation shape to change. Failed creation leaves the run and active pointer unchanged; failed resume leaves the run stopped. Use allowed diagnostics to resolve the cause rather than editing under an earlier grant.

Owner bookkeeping for reports, report delivery, spec acceptance, retrospective and triage, and closing-record operations on a complete run, does not require an engineering claim. Its existing lifecycle and evidence gates still apply, including on stopped or completed runs. This permits preserved closing duties after adoption or process replacement without granting source edits or requiring authority to resume engineering.

The `review`, `validate` and `dialogue` receipt-import maintenance paths likewise require ownership and full receipt validation, but no fresh engineering claim. They do not restore disabled integration, grant source edits or authorize a new dispatch. This preserves already-produced evidence when ordinary admission cannot refresh the claim.

`controllerClaim` records the current owner, native process identity, revision and observation, with previous observations retained in history. It supports conservative abandoned-run recovery, not automatic detection of every new turn: the controller must refresh it before engineering. Adoption clears it. A live or shared host process, missing claim or unknown process identity cannot establish abandoned-controller inactivity.

`adopt` takes the explicit current `runId`, latest `revision`, `previousController: {host, session}`, the new admitted `actor: {host, session}`, and nonempty user `authority`. The run must still be the project's current unfinished run. Adoption of a stopped run requires confirmed inactivity of all workers and project operations; the former chat may remain open. Adoption of a run still marked running additionally requires positive proof that the exact former host process in its latest supported controller claim has ended. Unknown or active activity blocks both cases. Permission alone is not inactivity evidence. A former owner can explicitly stop an eligible run; there is no force-adopt or replacement-run escape for missing evidence.

Adoption keeps run identity, queue, commitments, limits, imported evidence, follow-ups, publication authority and report duties, but leaves execution stopped and attended. It clears the current claim, continuation verification and Stop reminders and records the ownership change. The former owner loses write authority. Reconcile terminated workers and unresolved operation results under the new owner before `resume` with explicit authority to continue. A nonterminal worker record can qualify for takeover only when positive native termination or verified containment evidence proves inactivity; adoption does not mark that work complete. `resume` establishes the new claim, preserves existing limits and remains attended until fresh verified handover. Ownership-only authority never resumes execution.

For a plain in-host worker without managed process/operation metadata, `adopt` accepts optional `workerEvidence: [{workerId, path}]`. Omission or an empty array supplies none; null, duplicate/unknown workers and entries for terminal or managed workers are rejected. `workerId` is the exact registered id. `path` is a regular, singly linked project-relative native JSON-lines export under `.nightshift/runs/worker-evidence/`, using forward slashes and the ordinary evidence-path rules. Preserve the actual native events at a new path; never manufacture them from a user statement, an idle/absent status or a model's assertion of completion. A completed turn of an assignment that still has continuation or surviving work is not terminal helper evidence.

Arrange each such helper's terminal JSON report to carry `runId` equal to the exact saved run id and `requestId` equal to its exact registered worker id, without normalization or empty values. Claude evidence requires a native assistant attribution and successful terminal result in that session whose structured output or JSON result carries both markers. Codex evidence requires the native thread/model opening, a correlated agent message and its completed native turn, without later turn/item activity or observed unfinished goal continuation. A missing host, marker, terminal signal or attribution, a mismatched model/session, malformed/changing bytes, a BOM or an export larger than 32 MiB is unknown, not permission to adopt. This export route does not override managed-process reservations or prove engineering success. The adoption record retains the verified native identity, path, hash and observation time; preserve the export for later audit. The time records verification of those bytes, not their native completion time. The new owner still reconciles the saved worker record before resuming.

Bound adoption requires the same retained store, exact compatible payload and authenticated target binding; development adoption stays development. `resources` is immutable creation provenance, while `executionResources` describes the current binding. Both use `{schema, store, registration, session, identity}`; absent execution resources on an unadopted historical run fall back to creation resources, never to arbitrary current defaults. New dispatches use current execution resources; historical receipts retain their original assignment resources. Missing evidence, legacy releases without adoption, mixed modes, different stores, unavailable payloads, completed/replaced runs and active-controller transfer do not qualify. Do not silently upgrade the run. The [resource interface](../releases/REFERENCE.md) describes durable target retention and interrupted-transfer recovery.

Managed reservations enter `preparing` before preparation can spawn commands, then `launching` and `launched` or `contained` for the managed process, and `finalizing` before postprocessing. A dead helper in the original `reserved` phase proves that preparation never began. In an interrupted preparation/finalization phase, a model or command termination artifact alone cannot prove that surrounding subprocesses ended, so takeover remains blocked pending reconciliation. Missing or unknown phases also remain uncertain. Codex native exports with later active, erroneous, missing or unrecognized thread status similarly fail reconciliation; only later `idle` or `notLoaded` status is compatible with the correlated terminal turn.

## Delivery and evidence

`start-task` enforces agreement and dependencies. Implement directly from the outcome or spec. `check` executes a real check from `check: {name, executable, args, paths, timeoutMs?, resourceMode?}`. Paths are all project inputs covered by the check, using forward slashes, and name regular files: a directory is refused with `unsafe-path` before any worker is reserved, so list the files it contains. It records output, exit, input hashes and whether the check left its inputs unchanged. The executable and its arguments are actual commands chosen under the user's authority. An executable named by path runs as given; a bare name resolves before reservation to an absolute path from the check environment's PATH, outside the project and with `.exe` implied on Windows, is recorded as that path, and fails with `executable-not-found` when nothing qualifies. Test fixtures that mutate data must be separate from these reviewed inputs. Checks and private probes reserve internal operation workers before launch in both resource modes, so takeover cannot pass through an unrecorded execution window. A check also records its pending named result first; an interrupted rerun cannot fall back to an older pass. Result evidence and terminal worker state commit together. A refusal before the contained launch leaves the worker `failed`; only an attempted launch without termination evidence leaves it `unverified`. A check or probe finishes when its command exits: descendants still running 5 seconds later, such as a compiler or build server a build leaves behind for reuse, are ended and recorded as `lingeringDescendants: {total, processes: [{pid, image}]}` (`image` is the executable path, or null when it could not be read; at most 64 are listed, while `total` counts all, or is null when the listing failed), and the command's own exit code decides the result. A check or probe that left nothing running records `lingeringDescendants: null`. Dispatched reviewer hosts and the launcher's own operation still wait for every descendant to end. These internal workers are not public model-role registrations.

`check.resourceMode` is either `inherit` (the default) or `development`; null, empty and other values are rejected. Use `development` for deliberately selected checkout tests or private library fixtures when the controller is bound to an installed release. That child and its descendants receive explicit development mode without the controller's operation context or worker binding. The parent and saved run binding do not change. Keep `inherit` for genuine installed helpers that need the parent's bound context. Direct terminal test commands outside a bound operation keep their existing behavior. The chosen mode is recorded with the check.

`advance` moves a code/spec task from implementation to review, review to documentation, and documentation to task completion. Documentation requires an evidence description and current review/checks, so documentation edits can require cumulative reassessment. A linked governing-spec prerequisite completes directly after its strong assessment; it does not manufacture documentation or session-closing work. A standalone spec retains documentation. Docs tasks start in documentation; lore tasks perform their requested retrospective work and complete. A lore task can import a direct `code` assessment of its instruction proposal, and a docs task a `code` or `docs` assessment of its complete change, using the same independent findings and repair loop. Accepted assessment returns to documentation for docs or retrospective for lore; it does not authorize applying an instruction proposal. A lore task without an assessment keeps its direct completion path; once assessed, its current review is required at task and run completion. Code and docs tasks need the docs review that Documentation review describes before they complete. A no-edit assessment refresh of completed work preserves closing evidence. Task completion releases dependent engineering without a premature session retrospective or triage.

Session closing is shared by the run. Once actionable tasks have finished or are blocked and all workers are reconciled, call `retrospective` with evidence, then `triage` with evidence; a handed-over run records `report` between them. When every remaining blocker is a user decision and no worker is active, the controller may instead end its turn to ask, as a conversational pause; closing stays due when the run resumes or ends, and answering the decision would have invalidated closing evidence recorded before it. `status.closing` gives readiness and the next closing stage. Unanswered user decisions remain pending, rather than being inferred. A last standalone lore task supplies the session retrospective itself. New engineering, repairs or changed agreements invalidate the saved closing evidence; a no-edit assurance refresh preserves it. Absent closing state means those obligations are still due. `complete` requires every task complete, current required assurance, including docs reviews and a resolved closing record, no active workers, both closing records and, on a handed-over run, the recorded morning report. A blocked run can record its session closing without claiming unfinished engineering complete.

## Handover and the morning report

A handed-over run is a run with a recorded handover, whatever its saved mode. `handover` applies to a running run owned by the caller and takes `authority` (the user's actual handover words) and an optional `mechanism: {verified: true, kind, evidence, ...}` in the shape `continuation` accepts. It performs one write. With a verified mechanism it stores the mechanism, sets `mode` to `unattended` and records `handover: {authority, revision}`. Without a mechanism it records the handover in attended mode for an attended run; it does not itself downgrade an existing unattended run. A mechanism that is unverified or lacks evidence is rejected with `unverified-continuation`, one without a `kind` of `goal` or `stop-hook` with `invalid-continuation-kind`, and a `stop-hook` for a Codex controller with `unsupported-continuation`; a rejected mechanism writes nothing. The three handover categories remain: no handover; handover recorded, attended; handover recorded, unattended. A repeated `handover` keeps the original record and can restore unattended mode after fresh verification. Use explicit invalidation for negative observations as described below. Queue, workers, agreements, evidence, limits, follow-ups, publication authority and recorded closing evidence are preserved. Handover is refused on a stopped run with `run-stopped`; resume first under user authority. The status brief carries `mode`, `handover` and `report`.

The mechanism depends on the host. A `goal` is a native persistent goal; Codex requires one, because its models tend to yield their turn early. A `stop-hook` is the registered Stop hook, verified as registered, enabled and trusted for the project with activation observed in the controller's current session; it carries unattended work only for a Claude Code controller, whose host exposes no native goal and whose models do not yield early. Neither recovers work after a host exit or restart. At renewed handover, adoption, resume, compaction recovery and before unattended yield, observe the current host mechanism and reconcile saved work. Classify native goals as active, inactive or unknown from actual host output, retaining the distinction between absent, blocked, paused and complete, and re-verify a Stop hook the same way it was first verified. Use an authorized supported resume operation only if the host exposes one and verify its result. Otherwise name the required user action, such as resuming the blocked goal in the host, and verify restoration when observed. Do not replace an unfinished goal or use another worker's activity as controller continuation. Host capability can change; inspect the available surface instead of assuming permanent support or absence.

Owner-only `invalidate-continuation` takes nonempty `reason` text describing the observation. It is admitted bookkeeping on running or stopped runs, including saved unattended runs with stale verification. It records the latest unverified observation, changes mode to attended, and preserves run status, handover, limits, agreements, evidence and closing duties. Thus a running run stays running and a stopped run stays stopped. After response loss read status before retrying, and repeat only for a newer observation. It grants no claim or native goal. `continuation` records a currently verified mechanism without changing mode or granting handover authority; `handover` can then restore unattended operation. Unverified supplied mechanisms still fail ordinary `continuation` and `handover` without a write.

Current continuation evidence is scoped to the controller, run, mechanism and observation. Initialize it unverified; refresh at the boundaries above and invalidate on ownership change, observed inactivity, missing/failed inspection, deliberate disablement or lost trust/activation. Keep the latest observation in current state and prior observations in history. Missing or historical unscoped evidence is unverified until refreshed; no elapsed-time heuristic replaces boundary verification, and ordinary source edits alone do not invalidate a host observation. With admission available, persist invalidation and continue useful authorized work in the active turn. A functioning Stop hook still protects a handed-over run after downgrade, but does not resume a native goal, and it establishes unattended continuation only through a fresh `stop-hook` verification on a Claude Code controller. If the hook is unavailable, it provides no protection.

When admission itself is refused, invalidation cannot be recorded. Leave saved state unchanged and explicitly treat its old verification as unusable. Name the actual recovery: user restoration of disabled integration, native trust approval or genuine activation in a reopened session. Only already-permitted diagnostics/maintenance and work independent of admission may continue. Never silently restore trust or use development mode to bypass the binding. Once admission returns, reconcile fresh evidence and persist the appropriate mode before dependent work.

`handover`, `report` and `report-delivered` are ordinary operations for admission. When the session is not admitted (untrusted or disabled hooks, or no observed activation) none of them can run, nothing is recorded, and the handover is not accepted; tell the user the concrete recovery. While a runtime dispatch holds the project lease a bound `handover` is refused with `resource-operation-busy`; that refusal is temporary, so await the dispatch with `wait` and retry. A run bound to a release without these operations keeps that release's runtime and does not gain them.

On a handed-over run the closing order is `retrospective`, `report`, `triage`, `complete`, and `status.closing.stage` reads `report` while the report is due. `triage` and `complete` each reject a handed-over run without report evidence with `report-required`, so a handover that arrives after triage was already recorded still cannot complete without a report. `report` takes `path`, a project-relative Markdown file under `.nightshift/runs/reports/`, requires the recorded retrospective, reads the file, rejects a missing, empty or out-of-tree path with `invalid-report` or `unsafe-path`, and stores `{path, sha256}`. It is rejected with `report-not-due` on a run without a handover. Recording it again replaces the evidence and clears any recorded delivery, and is accepted on a complete run. Resumed engineering clears the report and its delivery with the other closing evidence. A run without a handover keeps the two-stage closing.

Saving the report is not delivering it. `report-delivered` takes `authority`, the user's actual reply received after the report was presented, and stores `{authority, revision, sha256}` bound to the delivered report. It is accepted on a running, stopped or complete run, is idempotent for the same report, never gates `complete`, and is rejected with `report-stale` when the saved file is missing or no longer matches its recorded hash; the recovery is to rewrite the file and record `report` again. `status.report` gives `recorded`, `delivered`, `path` and `current`. Report operations reach the checkout's active run and its current owning session, including after adoption. Adoption preserves saved reports and follow-ups; ordinary resumed engineering still invalidates closing evidence as before.

A cumulative code assessment dispatched on a code or docs task includes the agreed commitments of the earlier completed code and docs tasks, and lists them in `coveredTaskIds`; the review gate of each listed code or docs task admits it, so one integrated current assessment can cover them without a separate historical-task review. Each covered task still needs its own current checks and resolved findings, and the covering assessment must postdate its latest requirements revision and repairs. Spec tasks keep their own whole-spec assessment and lore tasks the assessment of their proposal: neither is covered or admits a covering assessment. A docs review dispatched on a code or docs task covers the same completed tasks for their docs reviews in the same way.

`block` records `blocker: {kind, reason, recoveryAttempted}`; kind is `user-decision`, `capability`, `resource` or `dependency`. Continue independent tasks. `unblock` requires evidence that the condition changed. Unblocking a `user-decision` blocker also records that evidence as an agreed decision in `agreement.decisions`, replaces `agreement.outcome` with the optional nonempty `updatedOutcome` text, advances the task's requirements revision so assessments bound to the earlier commitments become stale, reopens a linked governing-spec task (or clears `specReviewed` for a task that names its spec directly), and invalidates saved closing evidence; other blocker kinds leave the agreement unchanged. This is the route for recording an agreement the user changes mid-run: `block` the task with kind `user-decision` naming the change, then `unblock` it with the user's words as evidence and the revised outcome as `updatedOutcome`. `stop` requires `kind` of `user-stop` or `resource-limit` and its actual `reason`. Do not use a stop to sidestep incomplete work. `resume` requires explicit user `authority` and reconciled workers; it preserves the same run, commitments and evidence, establishes a fresh controller claim and does not change existing limits. Unavailable continuation leaves resumed execution attended. `continuation` records `mechanism: {verified: true, kind, evidence, ...}` only after observing the actual host behavior, with the same validation as `handover`.

## Independent assessment

`dispatch` accepts `taskId` and `review: {kind, baseSha, requirements, rules, candidates, requiredModel?, substitutionReason?, findings?, artifactPaths?, excludedPaths?, timeoutMs?}`. `kind` is `code`, `spec`, `docs` or `skeptic`; a skeptic assessment uses the documentation dimensions when every finding assigned to it came from a docs review. `baseSha` is the immutable base for the complete cumulative run change, not just the latest repair, given as the full 40- or 64-digit lowercase hexadecimal object name; an abbreviated name or a ref such as `HEAD` is refused with `invalid-base`. `requirements` includes the agreed commitments; `rules` contains all applicable conventions. Spec `artifactPaths` names every governing artifact; it defaults to the task's `agreement.spec`. The complete surrounding project is still supplied. `candidates` is the controller's ordered list of permitted `{host, model, effort}` assignments. Current strong reference models are `claude-fable-5-1` and `gpt-6-astra`. A required model prohibits substitution. More than one candidate needs a nonempty `substitutionReason`, and every candidate rule is checked before a worker is reserved. Unavailable or inadequate permitted models leave the assessment incomplete. `timeoutMs` (default 900000) bounds each attempt, not the dispatch, so a fallback gets its own full timeout. Under the retained launcher the whole operation also ends at the envelope `timeoutMs` (default and maximum one hour). Before reserving a worker, dispatch refuses with `operation-time-limit` unless all candidate attempts, capped by any run deadline, fit in the time left before that launcher deadline less a 60-second exit margin; launcher startup counts against the bound, so set the envelope `timeoutMs` above the time a refusal says is needed. Each dispatch attempt, check and probe is also capped at that point as it launches, after any preparation, so a runtime timeout records its evidence before the launcher ends the process.

The dispatcher captures tracked and visible new files and the cumulative diff, then gives the reviewer an isolated copy with read-only tool permissions. Review and probe copies each live in a short directory under `.nightshift/runs/c/`, named by eight hex digits and recorded as `workspace` in the dispatch's `request.json` or `copy` in the probe's `result.json`, because Windows cannot start a process in a working directory longer than 260 characters and suites run in a copy nest further copies in their own fixtures; requests, attempts, receipts and probe results stay under `.nightshift/runs/reviews/<id>/`. For any assessment kind, `artifactPaths` also explicitly supplies selected project-relative regular files, including ignored spec or proposal files, without changing their Git tracking or including unrelated ignored files. It defaults to the task's governing spec when present; pass the same selected supporting artifacts to its skeptic when needed. Selected files appear in the manifest, reviewer and private-probe copies, and freshness checks. For spec assessment they are the governing snapshot, the only project inputs whose change discards or stales it, while its reviewer still reads the whole surrounding project and must leave every file of its own copy unchanged; code, docs and skeptic assessment watch the full cumulative context. Selection is recorded as `contextSnapshot.includedPaths`; older snapshots without that field retain their original Git-visible inventory behavior. `excludedPaths` is only for user-owned unrelated inputs that must be preserved, not a way to omit part of the implementation or select review dimensions. Exclusions name individual file entries; directory exclusions are rejected. Existing aliases are resolved by filesystem identity for selection, exclusion and deduplication, and recorded Git spelling is excluded from the cumulative diff too. An absent exclusion must use an exact path from the current index or immutable review base; an unresolved spelling fails before assessment. Selecting and excluding the same file is rejected. Supply a skeptic's assigned findings from the saved task's findings array, retaining each complete durable `id`; `localId` and raw reviewer-local ids are not interchangeable with it. The skeptic receives each finding's claim (`id`, `localId`, `severity`, `required`, `consequence`, `evidence`, `relatedTo`), not the saved record's validation snapshot or other run bookkeeping. The lead can request scoped peer assistance when needed; register peers with the same model and effort, dispatch their bounded assignments, and return the evidence to the lead for integrated assessment.

`review.resume` continues a reviewer: it names the request id of the latest dispatch on a native session of the same run and task that produced a receipt, whose host, model, effort and session the runtime takes from that receipt, whatever status its worker record shows, so the request supplies no candidates, a `requiredModel` must equal the resumed model, and the attempt never falls back. It is refused with `unknown-dispatch`, `foreign-dispatch` for another task, `incomplete-dispatch`, `sessionless-dispatch`, `superseded-dispatch` when a later dispatch that produced a receipt continued the session, or `session-held` while an active or unverified worker holds it; with `wrong-review-kind` when the requested kind differs from the named dispatch's; and with `invalid-continuation` for candidates on a resume, for both `resume` and `replaces`, for a skeptic continued outside a dialogue, or for a request that supplies `continuation` or `continuationContext`, which only the runtime resolves. Each resumed dispatch captures a new private copy and context, and its prompt names that location and marks earlier copies stale. Claude resumes with `--resume <session>`; Codex starts a new app-server process and calls `thread/resume` with the thread id, the new copy as `cwd` and the same read-only policy and configuration. The receipt must come from that session. A resume that fails because of its session, meaning the host cannot find or continue it, its context is exhausted, the attempt times out or it returns no usable report, fails with `resume-failed`; other failures keep their codes, and unproven termination keeps `termination-unverified` with an unverified worker that holds the session until reconciled. After `resume-failed`, dispatch `review.replaces` naming the same dispatch with ordinary candidates: a new session receives that reviewer's findings, marks those pending closure as unverified repairs and inherits their closure. Receipts record `continues: {kind, requestId}` (`kind` is `resumed`, which also names its `session`, or `replacement`) and `lineage`, the request id of the fresh dispatch the reviewer began with; a receipt without them, including one from an earlier release, is a fresh dispatch of its own lineage. A resumed Codex attempt records its own usage, the thread total at the end of its turn less the total before it, and keeps the thread total as `threadTokens`; Claude usage stays per invocation. `review.acknowledgements` lists settled statements that any dispatch records with its request and presents as settled.

A dialogue turn is a resumed dispatch, or a replacement when its session cannot be resumed, carrying `review.dialogue: {findingIds, message}`. A lead's turn names only findings its lineage raised and returns `positions`, one `{id, position, evidence}` per named finding with `position` `maintain`, `revise` or `withdraw`, and no findings; the `dialogue` operation imports it as evidence on those findings. A skeptic's turn names only findings its lineage validated and returns verdicts; `validate` imports each, replacing the finding's verdict and proposal, returning it to disposition, keeping any pending closure and recording the exchange. `review` refuses a dialogue receipt with `dialogue-receipt`, `dialogue` refuses a skeptic's, and no dialogue receipt satisfies a gate. Importing an unchanged receipt already recorded on its target again returns the current state unchanged; one whose findings a replaced closing record carried into the current one is refused with `duplicate-review`, so the carried findings keep a single record.

The skeptic verdict list contains exactly one entry per assigned durable id. Its producer schema binds those ids and the entry count, while consumer checks still enforce uniqueness and meaningful evidence. Every confirmed verdict carries a nonempty `repairProposal`, the approach a repair would take with enough reasoning to judge it, and dispatch and `validate` refuse one without it. Broader observations stay in the summary for separate controller routing and independent assessment before disposition.

Independent assignments exclude every current and former controller session. Adoption preserves already imported assessments under their original attribution while inputs and commitments remain current; it does not rewrite their authorship. An adopter-authored receipt cannot be newly imported or used for skeptical validation by that adopter: obtain a fresh independent assessment. Other completed historical receipts may be imported when their original assignment/resources, original and current independence, native attribution and current inputs all pass. Missing historical attribution is diagnosed without guessing or discarding the receipt. Subsequent repairs still require fresh cumulative independent coverage.

Dispatch registers durable ownership before launch, captures the actual process/session as it becomes available, and preserves the result or failure. Windows host processes run in a job whose descendant cleanup is observed. Unverified termination retains ownership for reconciliation. The result names a durable `receiptFile`. Record a lead assessment using `review` with a project-relative `receipt` path. Record each skeptic verdict using `validate` with its `receipt` and durable `findingId`; imported findings namespace the review-local name so repeated names do not discard a later report. Receipt import checks the native events, assignment and run record, expected review kind, actual model and current inputs. For code, docs and skeptic assessments, current inputs means the reviewed inventory and file contents captured at dispatch: no tracked or visible new file outside `.nightshift/runs`, `.nightshift/inbox` and `.tmp` and not named in `excludedPaths`, and no selected artifact, may change, appear or disappear between dispatch and receipt import. For a spec assessment it means its governing artifacts alone, so project edits elsewhere while it runs keep it, as they do once it is imported, although its reviewer judged the surrounding project as it was at dispatch and a probe it requests still needs that project unchanged. A change to current inputs while a dispatch runs, or a reviewer of any kind changing any file of its own copy, is detected once an attempt returns a usable report: the dispatch then fails with `review-input-drift`, after that reviewer's usage is spent, without trying later candidates. An attempt that fails before that check, for example with an unusable or malformed report, is followed by the next candidate as usual, which spends its own usage on the same changed inputs, and the dispatch reports the error its last attempt meets. Hold such edits until the result returns. A change after the dispatch returns and before its import makes the import fail with `invalid-receipt`. An edit after import likewise makes that assessment stale, and both gated advances refuse it with `review-required` naming the stale assessment. A change to a file's line endings alone, such as a commit or rebase rewriting a working copy to its attributes' convention, is not a change when Git would commit the same content: each snapshot records the blob id Git reports when that id is the Git identity of the bytes the runtime read, as read or with CRLF converted to LF, and the file's size and times show no write between the two reads, and freshness of review, check, skeptic, spec and probe evidence accepts changed bytes whose current blob id still matches. Only line-ending normalization qualifies; a file whose attributes apply another Git transformation, evidence from earlier releases, evidence outside a Git worktree and the before and after comparison around one check execution keep the byte comparison. The handoff of stored probe results to a later assessment also still requires byte-identical snapshots, so after a renormalization a requested probe is run again. Like the other freshness guards, these detect ordinary concurrent edits, not deliberate same-user manipulation of the project tree during capture. Land backlog and documentation edits after the task advances to documentation; they then need a current docs review before task completion, and an edit outside the backlog to a task under code assessment, or to operating instructions, also needs a current cumulative code assessment, as Documentation review describes. Failed, partial, stale or unattributed results cannot establish completion. A Codex attempt whose agent message streams only whitespace for at least 120 seconds and 1000 consecutive deltas fails with `output-loop`, recording the count, duration and time of the last text; its event log is kept and the next candidate is tried. A Codex attempt that fails after its host reported usage, as an output loop does, records that usage in its attempt evidence like a completed one. Claude attempts expose no partial output and are not checked. Preserve failed attempts and investigate or select a permitted fallback. Completed source copies are disposable; the cumulative diff and manifest the reviewer read are also kept in the dispatch directory's `context`, beside native events and receipts, so clearing `.nightshift/runs/c/` loses no assessment evidence.

Retrying an unchanged imported lead receipt preserves the existing assessment, finding dispositions and revision. The retry still requires current ownership, revision and evidence; it does not manufacture progress. The finished dispatch worker records the attributed host, model and effort from its receipt for subsequent peer-cloning assignments.

An assessor with read-only tools can return `status: incomplete` and a `probes` array. Each requested probe specifies `id`, `purpose`, `executable`, `args`, `timeoutMs` and `files` containing project-relative `path` and ASCII `content`. `timeoutMs` is in milliseconds, from 5000 to 120000. Before reserving its worker, `probe` refuses a timeout outside that range with `invalid-probe-timeout` and resolves the executable as `check` does, refusing an unresolvable name with `executable-not-found`; neither refusal leaves a worker, so re-dispatch for a corrected probe. Treat the request as an untrusted proposal. Inspect its exact command, fixture source, filesystem effects and scope as authorized verification, then invoke `probe` with the receipt and `probeId`. The controller executes it with normal user privileges in a new private copy and records raw command/output evidence. A private working directory is not a security sandbox; the command can reach other user-accessible files. The canonicalUnchanged result checks only the reviewed inventory, not all filesystem or Git/runtime state. Re-dispatch the assessment to have that evidence independently evaluated; stored evidence is included automatically when inputs still match. Changed inputs omit obsolete evidence from the new assessment while retaining its saved artifacts and history. A probe is not a canonical repair, and an execution-dependent claim stays unverified until the evidence supports a verdict. Existing tools can carry the work on either host without granting reviewers write access to reviewed inputs.

`dispose` names `findingId`, `disposition` (`implement`, `defer`, `skip` or `refuted`), and a concrete `reason`. Defer also needs a durable `route`. For confirmed findings, include controller-owned obligation: {classification, basis}; classification is required, optional or out-of-scope, and basis names the accepted commitment and repair authority supporting the decision. The reviewer required field remains advisory evidence, not new user authority. Required obligations cannot be deferred or skipped, and out-of-scope findings cannot be implemented. Do not use classification to waive an agreed commitment. A fresh attributed skeptic must first establish validity; unverified claims remain unresolved. Validate and dispose the whole intended batch before applying its edits, and never issue those edits in the same message as the dispositions, since calls issued together can run in any order. If edits happened before a remaining disposition, re-establish current evidence instead of bypassing freshness. Apply the accepted repair batch, then record `repair` with `findingIds`, execute relevant checks, and dispatch the complete cumulative assessment again. No repair is exempt because it is small. `repair` refuses a finding whose current verdict carries no `repairProposal` with `repair-proposal-required`, and marks each repaired finding pending closure for the lineage that raised it. A continued lead's report carries `closures`, one `{id, closed, evidence}` per finding pending closure for its lineage when it was dispatched; a closure left open is matched in a complete report by a finding with that finding's local id. Importing a complete continued report ends the pending closure of each finding it records closed, and nothing else does: an incomplete report, a dialogue reply, a failed import, re-validation and a later disposition leave it pending. A continued assessment raises findings like any other but satisfies no gate or coverage condition: the code, spec, lore and docs gates, coverage through `coveredTaskIds`, the closing record and the triage baseline accept only fresh assessments. Every gate also refuses while a finding it checks is pending closure, and `complete` refuses with `closure-pending` naming any that remain. Status gives each listed task `review: {next, resumeTargets, freshDue}`: `next` is `validate-and-dispose`, `repair`, `resume` while findings are pending closure, `fresh-assessment` when the latest assessment of a kind is a continued one, or null; `resumeTargets` names the dispatch to resume, with its `taskId`, for each lineage owing closures and, after a task repair, for each assessment of a kind the repair batch did not repair that a code, spec or docs gate of the task or of any other task reads, that predates the repair and that no longer matches current inputs, which for an assessment its gate accepts means the gate finds it stale and for any other, such as a continued or incomplete one, means its reviewed inputs changed; a closing repair adds only its closures, and the hook's continuation brief, which verifies no freshness, adds `staleTargets: 'reconcile at acceptance'` in place of the stale ones; `freshDue` lists those kinds.

## Documentation review

A `docs` assessment is a strong independent review of the complete cumulative change with the documentation dimensions `claim-accuracy`, `sweep-completeness`, `backlog-conventions`, `sibling-consistency` and `proportionality` in place of the code dimensions. Its reviewer receives the same inputs as a code lead, judges what the documentation, including the backlog, says about the code rather than the code itself, and reports any changed file it judges to be operating instructions. Its findings are recorded with their kind and take the same `validate`, `dispose` and `repair` operations.

Runs created by this release carry `docsGate: true`. Each code and docs task of such a run needs, when it advances from documentation, when a reopened completed task advances from review straight back to completion, and at `complete`, a current docs review: owned by the task, covering it through `coveredTaskIds`, or the closing record's, and complete, strong, independent rather than continued, covering all five dimensions, fresh, bound to the task's current commitments, with every docs finding validated and disposed, none pending closure, and no docs repair after it. Spec and lore tasks have no docs gate. For a purely mechanical change, `advance` from documentation can instead carry nonempty `docsExemption` text; the runtime binds it to the project inventory at that moment, it counts only while that content is unchanged, and reopening, repair, a new review import on the task or a changed requirements revision clears it. It is refused with `invalid-exemption` on other task kinds and on runs without the docs gate. Status shows `docsReviewCurrent` for each gated task still ahead, and `docsExemptions` lists every recorded exemption with its task, reason, revision and whether it is `current`. Each gate counts only the findings and repairs of its own kind, so a docs repair needs a docs reassessment and reaches the code gate only through the files it changed. Leaving the review stage after a docs review needs that review current and resolved, and task completion without one fails with `docs-review-required`; at `complete` the refusal names the tasks that lack one.

Backlog paths are `.nightshift/FEATURES.md`, `.nightshift/BUGS.md`, `.nightshift/QUICK_WINS.md`, `.nightshift/PATTERNS.md`, `.nightshift/FEATURES_HISTORY.md`, `.nightshift/BUGS_HISTORY.md`, `.nightshift/QUICK_WINS_HISTORY.md` and files under `.nightshift/features/`, `.nightshift/bugs/` and `.nightshift/patterns/`. A code assessment of a code, docs or lore task that is stale only because backlog paths changed, appeared or disappeared counts as current when a current docs review covers the task: for code and docs tasks their own, a covering or the closing docs review, and for lore tasks only the closing docs review. Spec assessments never gain this relief, because a changed governing artifact needs whole-spec reassessment. Checks are unaffected: a check whose inputs changed is rerun.

On a gated run, `triage` starts the closing record, whose baseline is the project inventory at that moment (an empty inventory gives an empty baseline, and outside Git the baseline is the backlog files on disk); recording triage again replaces the record, and anything that clears closing evidence clears it. Its findings not yet settled or still pending closure survive either replacement: status lists them as `closing.carriedFindings` until the next triage moves them into the new record, where each must still be validated, disposed and, once repaired, closed before completion. The baseline outlives its record: a later triage keeps the run's earlier baseline while the changes since it lack independent review, meaning no current resolved closing review covers them and no complete cumulative code or docs assessment of a task is fresh against the whole inventory, so recording triage again never absorbs unreviewed tracking edits. Only a run whose changes since its earlier baseline were reviewed, or which captured none, records a new baseline at that triage. Task operations address the record with `taskId: "#closing"`: `dispatch` of a `docs` or `skeptic` assessment, `probe`, `check`, `review`, `validate`, `dialogue`, `dispose` and `repair`; other operations are refused with `invalid-closing-action`, and a run without a record refuses them with `closing-review-unavailable`. They are admitted on a running run once triage evidence exists and on a complete run as owner bookkeeping without an engineering claim, and refused on a stopped run until it is resumed. Recorded limits still bind them. A closing dispatch covers every code, docs and lore task. Its `review` import is refused with `closing-scope` unless every path changed since the baseline, apart from the dispatch's `excludedPaths`, lies in the backlog, and when the baseline could not be captured. Recording the review, its findings, their repairs and its checks never reopens a task or clears closing evidence. `complete` refuses with `closing-review-unresolved` while the latest closing review is not a complete strong docs assessment covering all five dimensions, a closing finding is unsettled, a closing repair postdates the latest closing review or a closing check fails. It also refuses with `closing-review-required` while anything changed since the baseline lacks a current, complete and resolved closing review, including in a run whose task gates do not depend on it, such as one with only unassessed lore tasks. A missing or unreadable baseline fails closed until triage is recorded again. When Git cannot inventory the project, only a project positively outside Git gets a baseline, read from its backlog files on disk: no `GIT_DIR` or `GIT_WORK_TREE` redirects discovery, no `.git` entry of any kind lies in the project or an ancestor Git would search, and Git refuses with its no-repository wording. A Git failure, an unusable `GIT_DIR` or a broken `.git` entry never counts as outside. No review can be dispatched outside Git, so there any backlog change after triage refuses completion: revert the tracking edits, or make them in a Git worktree where a closing docs review can cover them. For the same reason a docs task cannot complete outside Git, since it can neither be reviewed nor record an exemption, which needs a Git inventory. Status shows the record under `closing.docsReview`, with `satisfied` telling whether completion's closing coverage holds. On a complete run the record gates nothing; a finding whose repair lies outside the backlog is deferred with a durable route, and a required one cannot be deferred, so it leaves the record unresolved. An unresolved record is not review coverage of the tracking edits for publication.

## Staffing and follow-ups

`worker` registers `worker: {id, session, assignment, role, writes, host?, model?, effort?, lead?}`. Roles are `implementer`, `reviewer`, `skeptic`, `peer` or `supervisor`. Optional `host` is exactly `claude` or `codex`; omission stores the registering controller's host, while null and other values are rejected. The stored host belongs to that assignment and is preserved through completion and adoption. An absent historical host is unknown for native-event recovery, not a current-host default. Writes are exclusive project-relative paths; directory ownership includes descendants. Review staff and supervisors have an empty write list. A peer names its registered reviewer `lead` and matches the lead's model/effort. `worker-finished` names `workerId`, a `status` of `complete`, `failed` or `stopped`, and underlying `evidence`; merely registering a worker does not dispatch it. Verify actual process or registered native-assignment completion before releasing its ownership. Reconciling a review or skeptic worker records how its process ended, not an assessment: only a dispatch that produced a receipt can be resumed, replaced or named as a resume target, and a receipt that cannot be read counts as none. Runtime artifacts are written through a temporary file and a rename, so a failed write leaves none behind. The controller retains all consequential transitions.

`wait` is read-only, like `status`, and needs no actor or revision. `{action: 'wait', workerId, runId?, timeoutMs?}` observes the saved worker until its status leaves `starting` or `running`, its recorded runner process no longer exists, the run stops or completes (a complete run still admits closing-record work, so a `#closing` worker is observed until its own result), the run deadline passes, or `timeoutMs` elapses (default five minutes). It resolves the run once, so a later run cannot change what is observed. The result carries `runId`, `revision`, `runStatus`, `workerId`, `workerStatus`, `active`, `runnerAlive` (null when the runner was not probed: no runner process is recorded, or the worker had already left `starting` and `running`), the project-relative `receipt` path for `review` or `validate` when the dispatch wrote one, the saved failure `evidence`, `elapsedMs` and a `reason` of `worker-result`, `runner-missing`, `timeout`, `deadline` or `run-stopped`. Dispatch worker ids come from `inspect`, which lists every saved worker; `status` lists active ones only. A result with `active: true` needs reconciliation before the worker is released: `runner-missing` and `unverified` mean the process outcome is unknown, so verify it and record `worker-finished`. `worker-result` with status `complete` means the dispatch process ended; receipt import still performs the assessment's own checks. Keep `timeoutMs` below the host's tool-call limit and call `wait` again on `timeout`; repeated waits record no progress and neither consume nor reset the Stop hook's reminder budget, because the turn never ends.

`followup` records `item: {id, context, recommendation, ...}`. Preserve the concrete proposal and original decision terms in additional fields. Pending follow-ups survive engineering completion. `resolve-followup` records `followupId`, the actual `decision`, its user `authority`, and any durable `route`. Do not write inferred user answers. The session retrospective prepares worthwhile instruction proposals for independent review and user approval; triage follows it.

## Continuation hooks

The registered host SessionStart hook supplies native activation and restores obligations through the current execution binding after reopening/compaction. Bundled plugin hooks are notices only and do not mutate run state. For a running run with recorded handover or unattended mode, a functioning Stop hook resists premature yield by its current controller while actionable work, final reconciliation or workers remain. This protection survives continuation invalidation to attended mode; it does not verify or resume a native goal. Await a running dispatch with `wait` instead of yielding. Stop permits conversational pause when nothing is actionable, no worker is active and every remaining blocker is a user decision, preserving closing duties; other blocker kinds keep protection until closing is recorded. A merely attended run without handover may yield for conversation, and Stop returns nothing for it. Explicit user stops and exhausted limits take precedence, and an unavailable hook provides no protection.

For a handed-over run with a recorded report, whether running, stopped or complete, SessionStart in the current owning session carries a morning-report notice while the report is undelivered or any follow-up is pending: an instruction fitting the state (rewrite and record a missing or changed report, present an undelivered one, or after delivery continue triage through the host's question tool if the user has asked for it and otherwise ask whether they are ready), then `recorded`, `delivered`, `path`, `current` (false when the saved file is missing or changed) and pending follow-up ids. Adoption routes this notice to the new owner. A closed run restores nothing else. Stop never resists yield for unrecorded delivery or pending follow-ups on a closed run, because both need a user who may be absent.

After three consecutive reminders with no intervening progress transition, Stop permits no further continuation in that activation and reports incomplete recovery. Reminders, claim-only writes and repeated invalidation observations that change neither mode nor verification do not reset the count, although concurrency revisions still advance. A real progress transition resets the bound; `stop_hook_active` alone does not imply failure. Reconcile the cause before unattended resumption. Unrelated and former owner sessions are not controlled. Use native host interruption to stop active execution and record an explicit stop for that user intent; Claude does not expose an Interrupt hook event. A native persistent goal, where the host requires one, must refer to verified run completion rather than a model's claim. Verify actual installed hook/goal behavior and trust at reconciliation boundaries; neither configuration nor a saved `verified` flag proves itself.

Reviewed project inventory currently requires regular, singly linked files. Symlinks, hardlinks, gitlinks and other special entries produce a path-specific prerequisite diagnosis. Reconcile these explicitly before handover; do not silently omit changed entries from coverage. Native Windows .exe host installations are required; command-shim-only installations are not yet supported.

Each dispatched assessment binds the accepted commitments and requirements revision of every covered task. Import time is separate history metadata. An approved commitment change while an assessment is running makes that result stale even when source bytes remain unchanged. Reassess the current commitments; do not refresh an old result by importing it later.

Check names identify verification obligations within a task. A later invocation with the same name supersedes its earlier invocation, even if the earlier command finishes last. Each pending check stores its operation id as `attemptId`; completion replaces that attempt's reserved result in place. Every latest named check must pass on current inputs at task and run acceptance, regardless of task kind or whether an independent assessment was needed. A new failed check cannot be masked by an unrelated pass, and an earlier pass cannot mask a failed rerun. Keep the name when retrying or updating the verification of the same obligation. Code tasks require at least one check. Spec, docs and lore tasks can have none when no executable check applies; once registered, their checks remain acceptance obligations.

Probe copies have their own initially empty Git repository. Ordinary local Git commands resolve to that copy. History-dependent probes need a deliberately prepared Git fixture; they must not borrow the controller checkout through parent-directory discovery. The runtime explicitly selects development mode for private probe execution and records it in the result, keeping the controller's operation context and worker binding out of the private process. Older probe results without `resourceMode` inherited the caller environment; absence does not prove isolation. This boundary does not sandbox explicit absolute paths or hostile Git environment overrides.

The Windows transport keeps child input writes and output pumping independently progressable, preserves ordered input acknowledgements, and accepts termination while a write is pending. A requested termination, including a timeout, gives the job runner 30 seconds to end the job and report it empty, enough for a runner that is still starting on a loaded machine; a runner that cannot is ended, which still ends every process in its job, but the result is reported as unverified termination. Pending input is bounded at 32 MiB; exceeding that bound fails the dispatch rather than silently dropping input. A host that cannot start fails with an error naming the executable and the launch stage that failed (`command`, `setup`, `create-process`, `job-assignment` or `resume`), plus the Windows error code and message when Windows refused to create the process; when termination of a partially started process is unproven, the error names the executable and that condition instead of a stage. Reviewer attempts on either host record it as the attempt's error, and checks and probes as their operation worker's failure evidence.
