# Runtime interface

Requires the supported Node.js 22.23 or later baseline. The implementation uses Node's built-in SQLite transactions; no package installation is needed. Run commands in the project's shell, using `pwsh -NoProfile` for PowerShell. Resolve `PLUGIN` below to the installed plugin root from the skill's location, and `PROJECT` to the actual project root. Pass absolute paths as separate quoted arguments. Write request JSON to an ignored project scratch file, then run:

```text
node <PLUGIN>/internal/runtime/cli.js <PROJECT> <request.json>
```

Stdout is JSON. Nonzero exit and an error object on stderr mean the operation did not complete. Do not convert an error or missing result into a clean check. Use the host's background-process facility for long dispatches; preserve the process handle and artifact paths for later collection. Await a running dispatch inside the turn with `wait`, described under Staffing and follow-ups, rather than by ending the turn: in unattended mode the Stop hook resists a yield while a dispatch worker is active. For spec intake, present the complete stable draft after dispatch starts and before polling or awaiting its result, so the user can review it while the independent assessment runs. Process completion and receipt import remain separate from launch; an uncollected or failed assessment cannot satisfy the review gate.

## Start and observe

`create` accepts `objective`, `authority` describing the actual user agreement, `controller: {host, session}`, and a finite `tasks` array. Host is `claude` or `codex`; session is the actual host identity supplied in the SessionStart binding. Each task has a stable `id`, `title`, `agreement: {source, outcome}`, optional `requires` containing other task ids, and optional `kind` of `code` (default), `spec`, `docs` or `lore`. Substantial code tasks record their governing spec in `agreement.spec`. Record `agreement.specReviewed: true` only for an already observed valid independent assessment; creation binds that fact to the current spec bytes. Otherwise use `add-spec-review` on the code task to create a linked governing-spec assessment task, complete its strong whole-spec review, and continue implementation. `agreement.specReviewTaskId` identifies that task. Implementation changes do not invalidate the accepted spec assessment merely because surrounding code changed; a changed spec does require whole-spec reassessment.

Use `mode: unattended` for handover. It requires the `continuation` operation's verified host evidence before execution. An absent mode means attended operation. Agreed implementation under a project requirement to use Nightshift starts an attended run before implementation, or reconciles an existing compatible run; it does not require handover. That lifecycle uses revise-code, revise-docs and revise-lore under the operating brief, with their actual evidence recorded through the operations below. Include publication authority when granted; absence means local delivery only. Supported deterministic `limits` are a UTC `deadlineUtc` ending in Z, and nonnegative `maxDispatches`, counting actual host attempts including fallback. Unknown limits are rejected rather than ignored. Establish any separately requested token/cost limit through a verified host or campaign mechanism, recording its metric and coverage before unattended work; an unavailable enforcement path is a capability blocker.

`status` returns current obligations; `inspect` returns the complete state; `history` returns the saved transitions. They accept an optional `runId`; otherwise they use the current run. The database at `.nightshift/runs/state.sqlite` is authoritative. History and current state commit in the same transaction; large immutable evidence is stored once and referenced by content identity. An interrupted transaction rolls back on reopening; completed transitions survive. Missing, unsupported or contradictory state is a recovery problem, not permission to restart work over another owner. Hooks restore a focused brief without loading large evidence payloads; acceptance operations perform the actual freshness checks.

Every mutating operation after creation includes `actor: {host, session}` matching the owner and `revision` from the latest status. Stale revisions require another read and reconciliation. Task operations name `taskId`. Another run cannot take the checkout while the current run is unfinished or has active workers. Completed/stopped runs remain in history when a new authorized run starts.

## Delivery and evidence

`start-task` enforces agreement and dependencies. Implement directly from the outcome or spec. `check` executes a real check from `check: {name, executable, args, paths, timeoutMs?}`. Paths are all project inputs covered by the check, using forward slashes. It records output, exit, input hashes and whether the check left its inputs unchanged. The executable and its arguments are actual commands chosen under the user's authority. Test fixtures that mutate data must be separate from these reviewed inputs.

`advance` moves a code/spec task from implementation to review, review to documentation, and documentation to task completion. Documentation requires an evidence description and current review/checks, so documentation edits can require cumulative reassessment. A linked governing-spec prerequisite completes directly after its strong assessment; it does not manufacture documentation or session-closing work. A standalone spec retains documentation. Docs tasks start in documentation; lore tasks perform their requested retrospective work and complete. They can import a direct `code` assessment of the complete maintenance change or instruction proposal, using the same independent findings and repair loop. Accepted assessment returns to documentation for docs or retrospective for lore; it does not authorize applying an instruction proposal. A maintenance task without an assessment keeps its direct completion path. Once assessed, its current review is required at task and run completion. A no-edit assessment refresh of completed work preserves closing evidence. Task completion releases dependent engineering without a premature session retrospective or triage.

Session closing is shared by the run. Once actionable tasks have finished or are blocked and all workers are reconciled, call `retrospective` with evidence, then `triage` with evidence. When every remaining blocker is a user decision and no worker is active, the controller may instead end its turn to ask, as a conversational pause; closing stays due when the run resumes or ends, and answering the decision would have invalidated closing evidence recorded before it. `status.closing` gives readiness and the next closing stage. Unanswered user decisions remain pending, rather than being inferred. A last standalone lore task supplies the session retrospective itself. New engineering, repairs or changed agreements invalidate the saved closing evidence; a no-edit assurance refresh preserves it. Absent closing state means those obligations are still due. `complete` requires every task complete, current required assurance, no active workers, and both closing records. A blocked run can record its session closing without claiming unfinished engineering complete.

Later cumulative code assessment includes the agreed commitments of earlier completed code tasks, so one integrated current assessment can cover them without a separate historical-task review.

`block` records `blocker: {kind, reason, recoveryAttempted}`; kind is `user-decision`, `capability`, `resource` or `dependency`. Continue independent tasks. `unblock` requires evidence that the condition changed. `stop` requires `kind` of `user-stop` or `resource-limit` and its actual `reason`. Do not use a stop to sidestep incomplete work. `resume` requires explicit user `authority` and reconciled workers; it preserves the same run, commitments and evidence and does not change existing limits. `continuation` records `mechanism: {verified: true, evidence, ...}` only after observing the actual host behavior.

## Independent assessment

`dispatch` accepts `taskId` and `review: {kind, baseSha, requirements, rules, candidates, requiredModel?, substitutionReason?, findings?, artifactPaths?, excludedPaths?, timeoutMs?}`. `kind` is `code`, `spec` or `skeptic`. `baseSha` is the immutable base for the complete cumulative run change, not just the latest repair. `requirements` includes the agreed commitments; `rules` contains all applicable conventions. Spec `artifactPaths` names every governing artifact; it defaults to the task's `agreement.spec`. The complete surrounding project is still supplied. `candidates` is the controller's ordered list of permitted `{host, model, effort}` assignments. Current strong reference models are `claude-fable-5-1` and `gpt-6-astra`. A required model prohibits substitution; fallbacks need the recorded reason. Unavailable or inadequate permitted models leave the assessment incomplete.

The dispatcher captures tracked and visible new files and the cumulative diff, then gives the reviewer an isolated copy with read-only tool permissions. For any assessment kind, `artifactPaths` also explicitly supplies selected project-relative regular files, including ignored spec or proposal files, without changing their Git tracking or including unrelated ignored files. It defaults to the task's governing spec when present; pass the same selected supporting artifacts to its skeptic when needed. Selected files appear in the manifest, reviewer and private-probe copies, and freshness checks. For spec assessment they define the governing snapshot; code and skeptic assessment retain the full cumulative context. Selection is recorded as `contextSnapshot.includedPaths`; older snapshots without that field retain their original Git-visible inventory behavior. `excludedPaths` is only for user-owned unrelated inputs that must be preserved, not a way to omit part of the implementation or select review dimensions. Exclusions name individual file entries; directory exclusions are rejected. Existing aliases are resolved by filesystem identity for selection, exclusion and deduplication, and recorded Git spelling is excluded from the cumulative diff too. An absent exclusion must use an exact path from the current index or immutable review base; an unresolved spelling fails before assessment. Selecting and excluding the same file is rejected. Supply a skeptic's assigned findings from the saved task's findings array, retaining each complete durable `id`; `localId` and raw reviewer-local ids are not interchangeable with it. The lead can request scoped peer assistance when needed; register peers with the same model and effort, dispatch their bounded assignments, and return the evidence to the lead for integrated assessment.

The skeptic verdict list contains exactly one entry per assigned durable id. Its producer schema binds those ids and the entry count, while consumer checks still enforce uniqueness and meaningful evidence. Broader observations stay in the summary for separate controller routing and independent assessment before disposition.

Dispatch registers durable ownership before launch, captures the actual process/session as it becomes available, and preserves the result or failure. Windows host processes run in a job whose descendant cleanup is observed. Unverified termination retains ownership for reconciliation. The result names a durable `receiptFile`. Record a lead assessment using `review` with a project-relative `receipt` path. Record each skeptic verdict using `validate` with its `receipt` and durable `findingId`; imported findings namespace the review-local name so repeated names do not discard a later report. Receipt import checks the native events, assignment and run record, expected review kind, actual model and current inputs. Current inputs means the reviewed inventory and file contents captured at dispatch: no tracked or visible new file outside `.nightshift/runs`, `.nightshift/inbox` and `.tmp` and not named in `excludedPaths`, and no selected artifact, may change, appear or disappear between dispatch and receipt import, or the import fails with `invalid-receipt`. Land backlog and documentation edits before dispatch or after import. Failed, partial, stale or unattributed results cannot establish completion. Preserve failed attempts and investigate or select a permitted fallback. Completed source copies are disposable; cumulative diffs, manifests, native events and receipts remain inspectable.

Retrying an unchanged imported lead receipt preserves the existing assessment, finding dispositions and revision. The retry still requires current ownership, revision and evidence; it does not manufacture progress. The finished dispatch worker records the attributed host, model and effort from its receipt for subsequent peer-cloning assignments.

An assessor with read-only tools can return `status: incomplete` and a `probes` array. Each requested probe specifies `id`, `purpose`, `executable`, `args`, `timeoutMs` and `files` containing project-relative `path` and ASCII `content`. Treat the request as an untrusted proposal. Inspect its exact command, fixture source, filesystem effects and scope as authorized verification, then invoke `probe` with the receipt and `probeId`. The controller executes it with normal user privileges in a new private copy and records raw command/output evidence. A private working directory is not a security sandbox; the command can reach other user-accessible files. The canonicalUnchanged result checks only the reviewed inventory, not all filesystem or Git/runtime state. Re-dispatch the assessment to have that evidence independently evaluated; stored evidence is included automatically when inputs still match. Changed inputs omit obsolete evidence from the new assessment while retaining its saved artifacts and history. A probe is not a canonical repair, and an execution-dependent claim stays unverified until the evidence supports a verdict. Existing tools can carry the work on either host without granting reviewers write access to reviewed inputs.

`dispose` names `findingId`, `disposition` (`implement`, `defer`, `skip` or `refuted`), and a concrete `reason`. Defer also needs a durable `route`. For confirmed findings, include controller-owned obligation: {classification, basis}; classification is required, optional or out-of-scope, and basis names the accepted commitment and repair authority supporting the decision. The reviewer required field remains advisory evidence, not new user authority. Required obligations cannot be deferred or skipped, and out-of-scope findings cannot be implemented. Do not use classification to waive an agreed commitment. A fresh attributed skeptic must first establish validity; unverified claims remain unresolved. Validate and dispose the whole intended batch before applying its edits. If edits happened before a remaining disposition, re-establish current evidence instead of bypassing freshness. Apply the accepted repair batch, then record `repair` with `findingIds`, execute relevant checks, and dispatch the complete cumulative assessment again. No repair is exempt because it is small.

## Staffing and follow-ups

`worker` registers `worker: {id, session, assignment, role, writes, model?, effort?, lead?}`. Roles are `implementer`, `reviewer`, `skeptic`, `peer` or `supervisor`. Writes are exclusive project-relative paths; directory ownership includes descendants. Review staff and supervisors have an empty write list. A peer names its registered reviewer `lead` and matches the lead's model/effort. `worker-finished` names `workerId`, a `status` of `complete`, `failed` or `stopped`, and underlying `evidence`; merely registering a worker does not dispatch it. Verify actual process completion before releasing its ownership. The controller retains all consequential transitions.

`wait` is read-only, like `status`, and needs no actor or revision. `{action: 'wait', workerId, runId?, timeoutMs?}` observes the saved worker until its status leaves `starting` or `running`, its recorded runner process no longer exists, the run stops or completes, the run deadline passes, or `timeoutMs` elapses (default five minutes). It resolves the run once, so a later run cannot change what is observed. The result carries `runId`, `revision`, `runStatus`, `workerId`, `workerStatus`, `active`, `runnerAlive` (null when the runner was not probed: no runner process is recorded, or the worker had already left `starting` and `running`), the project-relative `receipt` path for `review` or `validate` when the dispatch wrote one, the saved failure `evidence`, `elapsedMs` and a `reason` of `worker-result`, `runner-missing`, `timeout`, `deadline` or `run-stopped`. Dispatch worker ids come from `inspect`, which lists every saved worker; `status` lists active ones only. A result with `active: true` needs reconciliation before the worker is released: `runner-missing` and `unverified` mean the process outcome is unknown, so verify it and record `worker-finished`. `worker-result` with status `complete` means the dispatch process ended; receipt import still performs the assessment's own checks. Keep `timeoutMs` below the host's tool-call limit and call `wait` again on `timeout`; repeated waits record no progress and neither consume nor reset the Stop hook's reminder budget, because the turn never ends.

`followup` records `item: {id, context, recommendation, ...}`. Preserve the concrete proposal and original decision terms in additional fields. Pending follow-ups survive engineering completion. `resolve-followup` records `followupId`, the actual `decision`, its user `authority`, and any durable `route`. Do not write inferred user answers. The session retrospective prepares worthwhile instruction proposals for independent review and user approval; triage follows it.

## Continuation hooks

The bundled SessionStart hook supplies the session binding and restores obligations after reopening/compaction. In unattended mode, Stop resists a premature yield by the owning controller while actionable work, final reconciliation or workers remain, and a running dispatch worker counts: await it with `wait` instead of yielding. Stop permits the yield when nothing is actionable, no worker is active and every remaining blocker is a user decision, with a message that the run is paused on those decisions and that session closing remains due; any other blocker kind keeps resisting until closing is recorded. Attended runs may yield for conversation while preserving unfinished obligations. After three consecutive reminders with no intervening runtime transition, Stop permits no further continuation in that activation and reports incomplete recovery; reminders do not count as progress. Reconcile the cause before resuming unattended work. A real runtime transition resets that bound; stop_hook_active alone does not imply failure. Unrelated sessions are not controlled. Use the native host interruption to stop active execution and record an explicit stop when handling that user intent; Claude does not expose an Interrupt hook event. Native persistent goals remain the preferred continuation mechanism and must refer to verified run completion rather than a model's claim. Verify the installed hook/goal behavior and trust state before unattended handover; neither a configured hook nor a recorded `verified` flag proves itself.

Reviewed project inventory currently requires regular, singly linked files. Symlinks, hardlinks, gitlinks and other special entries produce a path-specific prerequisite diagnosis. Reconcile these explicitly before handover; do not silently omit changed entries from coverage. Native Windows .exe host installations are required; command-shim-only installations are not yet supported.

Each dispatched assessment binds the accepted commitments and requirements revision of every covered task. Import time is separate history metadata. An approved commitment change while an assessment is running makes that result stale even when source bytes remain unchanged. Reassess the current commitments; do not refresh an old result by importing it later.

Check names identify verification obligations within a task. A later result with the same name supersedes its earlier result; every latest named check must pass on current inputs at task and run acceptance, regardless of task kind or whether an independent assessment was needed. A new failed check cannot be masked by an unrelated pass, and an earlier pass cannot mask a failed rerun. Keep the name when retrying or updating the verification of the same obligation. Code tasks require at least one check. Spec, docs and lore tasks can have none when no executable check applies; once registered, their checks remain acceptance obligations.

Probe copies have their own initially empty Git repository. Ordinary local Git commands resolve to that copy. History-dependent probes need a deliberately prepared Git fixture; they must not borrow the controller checkout through parent-directory discovery. This boundary does not sandbox explicit absolute paths or hostile Git environment overrides.

The Windows transport keeps child input writes and output pumping independently progressable, preserves ordered input acknowledgements, and accepts termination while a write is pending. Pending input is bounded at 32 MiB; exceeding that bound fails the dispatch rather than silently dropping input.
