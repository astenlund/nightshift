# Runtime interface

Requires the supported Node.js 22.23 or later baseline. The implementation uses Node's built-in SQLite transactions; no package installation is needed. Run commands in the project's shell, using `pwsh -NoProfile` for PowerShell. For installed work, follow [automatic preparation in the retained resource interface](../releases/REFERENCE.md#skill-activation). New runtime admission independently requires native identity, plugin enablement, registration, resource integrity and operation permissions. Unavailable hook trust, configuration or session activation is reported as integration failure while runtime work can continue without that mechanism; retained runtimes keep their execution code and admission rules for operations other than delivery creation; the current bootstrap sends handover and older create admission through the current service. Write an envelope with `action: "run"`, `entry: "runtime"`, the actual native `session`, absolute `project`, and the runtime request under `request`. The runtime request names its operation in `action`, as in `{action, actor, revision, ...}`; a missing or unknown `action` is refused before any state or ownership check with a message listing the accepted actions, as `invalid-request` from the runtime and `invalid-runtime-request` from the launcher. Invoke the exact bootstrap and registration from the host locator:

```text
node <BOOTSTRAP> <REGISTRATION> <envelope.json>
```

Explicit repository development uses `node <CHECKOUT>/internal/runtime/cli.js --development <PROJECT> <request.json>`. This creates development runs and cannot mutate an installed bound run. Preserve matching controller/actor identities and current revisions in runtime requests. Bound runs, workers and review receipts record their retained resource identity.

Stdout is JSON. Nonzero exit and an error object on stderr mean the operation did not complete. Do not convert an error or missing result into a clean check. Use the host's background-process facility for long dispatches; preserve the process handle and artifact paths for later collection. Await a running dispatch inside the turn with `wait`, described under Staffing and follow-ups, rather than by ending the turn: for accepted running delivery, a functioning Stop hook resists a yield while a dispatch worker is active. For spec intake, present the complete stable draft after dispatch starts and before polling or awaiting its result, so the user can review it while the independent assessment runs. Process completion and receipt import remain separate from launch; an uncollected or failed assessment cannot satisfy the review gate.

## Start and observe

`handover` creates delivery when its request supplies `controller: {host, session}`, `objective`, actual user `authority` and a finite `tasks` array. A preserved UUID `handoverId` binds safe acceptance retries to the same original request; changing its original owner, scope, resources or authority is a conflict. Reconciliation also requires the current controller and execution binding, so an original request cannot reclaim an adopted delivery. Completed acceptance returns its existing state without rewriting it, and a historical acceptance identity cannot create another current delivery. Handover refuses every `reviewContextId` selector. Each task has a stable `id`, `title`, `agreement: {source, outcome}`, optional `requires` naming other queued tasks, and `kind` of `code` (default), `spec`, `docs` or `lore`. `#closing` remains reserved. Substantial code tasks name `agreement.spec`; a current valid independent pre-delivery assessment may supply `specReviewed: true`, and otherwise a queued spec task over the same spec, a spec task linked through `agreement.specReviewTaskId` or one `add-spec-review` creates settles the spec, as the spec readiness paragraphs below describe with handover's refusals of a link. Public `create` is not a new-runtime action. Existing bindings retain their original runtime and action surface.

`spec-accepted` records the user's acceptance of a task's governing spec. It names `taskId` and takes `authority`, the user's actual reply after the spec was presented, and stores `specAcceptance: {authority, revision, snapshot}` on the task beside its agreement, never inside it, because assessments bind the agreement and a change there would make them stale. The snapshot binds the spec's current content with the same line-ending tolerance as review freshness. It is refused with `missing-spec` when the task's agreement names no spec or the spec file is missing, and with `run-complete` on a complete run; it is accepted on a running or stopped run and on a blocked task. Recording it again while the spec still has that content keeps the original record; after the spec changes, it replaces the record. It never gates another operation. Status gives `specAcceptance: {recorded, current}` for each listed task whose agreement names a spec, where `current` is false once the spec's content has changed. Record acceptance this way rather than in the spec's text, which is what its assessments review.

Spec readiness holds only completion. A code task whose agreement has a `spec` key is ready when its agreement carries `specReviewed: true` with no link and a single-file `specSnapshot` of that spec that still matches, or when its governing spec task is complete, names the same spec, and its latest lead assessment passes that task's review gate with checks left out, still matches that task's requirements revision and commitments, and postdates the latest material amendment of every code task that spec task governs, dated by its dispatch registration when it has one, and treated as predating every amendment when its dispatch record carries no usable registration, so an amendment that could not reopen the spec task, as while its file is missing, still holds every code task sharing it until an assessment dispatched after it. Malformed assessment evidence leaves the code task unready with a structural cause. A preserving applicability call by the spec's originating reviewer or its independent replacement therefore settles a compatible spec edit, while no relevance decision covers an assessment that predates a material amendment. The spec task's own checks are verified at its own completion and at run completion, not at the code task's. Each transition that completes a code task, `advance` from documentation and a reopened task's return from review, and run `complete` refuse `spec-review-required`, naming each unready task with its cause and next step; `start-task` and every other action proceed whatever the spec's assessment state, and a code task whose `requires` names its spec task still waits under `dependency-blocked`. A code task already complete when its spec changes is not reopened; run completion holds instead. Review contexts are unaffected.

The governing spec task is the code task's link, read from the task's own `specReviewTaskId` beside the agreement first and `agreement.specReviewTaskId` second, where an absent or falsy value is no link. Without a link it is the run's single queued spec task over the same spec: a `spec` task that no task of any kind links in either place and that does not require the code task, directly or through other tasks' `requires`; none, or several, leave no governing task. Two spec paths match when the strings are equal or, with both files present, when their file identities are equal, which admits case variants of one file on a case-insensitive filesystem; an identity that cannot be established is no match. A link naming a missing task, a task of another kind, a spec task over a different spec or a spec task that requires the code task is an unresolvable link. Governance is itself a dependency, so a governance edge on a cycle of `requires` and governance edges governs nothing: a linked task there is an unresolvable link, and a queued one leaves its code task without a governing task. A missing governing spec file is a cause of its own, reported before any link comparison. Delivery `handover` refuses `invalid-queue` when a code task's `agreement.specReviewTaskId`, other than an absent or falsy value, does not name a queued spec task over the same spec or names one that requires the code task, when any task carries `specReviewTaskId` outside its agreement, and when `requires` and governance edges form a cycle; a link in the agreement of any other task is accepted unchecked, and opening a review context applies none of these refusals. The resolution is read each time and persists nothing.

`add-spec-review` creates the spec task `<taskId>-governing-spec` over the code task's spec and records its id as the code task's own `specReviewTaskId`, beside the agreement, so the validations and assessments that bind the agreement stay current; it leaves `specReviewed` unchanged, and the new link then governs. It refuses `missing-spec` for a task of another kind or an absent or unusable `spec` value, refuses `duplicate-task` naming the queued spec task when one governs, and does nothing for a task already linked in either place.

A delivery's status carries `specReadiness`, one `{taskId, ready, specTaskId, cause, next, specAcceptance}` for every code task whose agreement has a `spec` key, completed tasks included. `specTaskId` is the governing spec task or null; `cause` and `next` are null when the task is ready and otherwise one sentence each; `specAcceptance` is the reading `spec-accepted` describes. With freshness verification skipped the whole list reads `'reconcile at acceptance'`, and a review context's and a closed record's status omit it. The `governing-spec-review` stage is retired, and each listed task's `agreement.specReviewTaskId` echoes the link from either place, never an inferred queued task. An unresolvable link and an unusable `spec` value have no repairing operation; for them, and for a missing spec file that is not restored, `next` names the user's decision on the run: blocking an incomplete code task with kind `user-decision`, and `hold`, `stop` or the administrative close once stopped. Neither `spec-accepted` nor a recorded decision settles readiness. A session bound to a release before 3.3.34 reads neither the link beside the agreement nor the queued route, so its historical discharge refuses a run completed through either unless the code task also carries a current `specReviewed: true` snapshot; restart such a session on the current release before handing over again.

New delivery has no attended/unattended mode. A request supplying `mode`, including null or an empty value, is refused. Every new delivery records its handover and reporting duties at creation. Attempt native continuation and record its observed success or technical failure before dependent engineering. Failure permits authorized work without the mechanism and creates a pending follow-up; it never removes handover, limits or assurance. Supported deterministic limits retain their existing grammar: `deadlineUtc` is a UTC timestamp ending in Z; `maxDispatches` is a nonnegative safe integer counting actual attempts, including fallback. An absent limit stays absent, zero dispatches permits none, malformed values and unknown keys are refused. Other requested metrics need verified accounting rather than a substituted limit.

After the continuation outcome, emit a separate visible assistant message beginning `Handover accepted:`, state the agreed scope and applicable limits, and say `You can leave.`. Failed continuation also requires `Automatic continuation is unavailable`, recorded-failure disclosure and the resumption consequence. New delivery engineering observes that native message before starting: `acknowledgement-required` means no matching message was established; `acknowledgement-source-unavailable` means its native history could not be inspected; `acknowledgement-obligation-unavailable` means the recorded renewal or scope cannot be established. Keep the duty pending, emit or safely repeat the message and reconcile the actual source rather than supplying a delivered flag. Status exposes the acknowledgement status, current validity, renewal revision and emission boundary. Native discovery reads the admitted profile, at most 50,000 entries and eight candidate files, ordinary singly linked history files without a BOM, and captures at most 65,536 characters of attributed visible text. Each file is read at the size observed when it is opened: whole up to 64 MiB, and beyond that by its last 64 MiB from the first line that starts inside them, plus, for a Codex rollout, its first line, the `session_meta` attribution, which must end within 1 MiB. Each complete line read must decode as valid UTF-8 and the file's first three bytes must not be a BOM; an unfinished final line, which may still be mid-write, the partial line before a larger file's window and the bytes outside what is read are not checked, so unlike 3.3.12 an invalid byte in an unfinished final line no longer makes the history unavailable. An acknowledgement older than that window is reported missing, so repeating the message recovers it, and a Codex message without its own id is identified by its line's byte offset, `offset:<n>`, which stays stable as the file grows. A complete earlier message can be inspected while an unfinished final log line remains unusable. Captured evidence survives later source-log append, rotation or removal. Material agreement decisions and requirements revisions renew the scope and recording-time boundary even without changed outcome wording; adoption renews ownership; same-owner holds/resumption and compatible corrections preserve a discharged duty. Hold/stop, claims, continuation observation and permitted receipt/bookkeeping operations retain their own admission rules. Standalone revision and exact older retained runtimes keep their respective behavior.

`status` returns current obligations; `inspect` returns the complete state; `history` lists every saved transition with its `revision`, `kind` and `recordedAt` but without the run state, because each state expands the immutable evidence it references and a long run's states together exceed what one response can hold. For full states, `history` takes `fromRevision` and an optional `toRevision`, inclusive and defaulting to `fromRevision`, spanning at most 10 revisions; a missing start, a negative or fractional revision, an inverted range or a wider one is refused with `invalid-history-range`. They accept an optional `runId`; otherwise they use the current run. The database at `.nightshift/runs/state.sqlite` is authoritative. History and current state commit in the same transaction; large immutable evidence is stored once and referenced by content identity. An interrupted transaction rolls back on reopening; completed transitions survive. Missing, unsupported or contradictory state is a recovery problem, not permission to restart work over another owner. Hooks restore a focused brief without loading large evidence payloads; acceptance operations perform the actual freshness checks.

The creation result and every status brief carry `scratch`, computed when read and never stored. Outside Git it is `{applies: false}`; otherwise it is `{applies: true, ignored, tracked, trackedCount, notices}`. `ignored` says whether Git ignores new ordinary files under `.tmp`, judged by sampling two never-tracked names that share no suffix, one at its top and one nested, so a rule ignoring only dotfiles, one name or one file type does not count, or is null when Git cannot tell; `tracked` lists up to 20 of the `.tmp` paths in the index, which includes staged additions, and `trackedCount` counts them all (both null when Git cannot list them). `notices` names what needs attention: `.tmp` not ignored, with the fix of adding `/.tmp/` to `.gitignore` or `.git/info/exclude`, which Nightshift never edits; `.tmp` paths the run added to the index since its cumulative review base `baseSha`; paths already tracked at that base, or tracked on a run that recorded no base and so cannot attribute them; commits after the base that added `.tmp` paths, including commits on merged side branches and merges that introduced scratch themselves, to squash before publishing; and that Git could not answer, when it cannot list the tracked paths or read the run's commits after the base. A hook's brief, which verifies no freshness, carries `'reconcile at acceptance'` in its place.

Every mutating operation after creation includes `actor: {host, session}` matching the owner and `revision` from the latest status, except the explicitly authorized ownership transfer below. Stale revisions require another read and reconciliation. Task operations name `taskId`. After all records pass consistency, an unfinished selected record or active/uncertain worker refuses creation with `overlapping-run`. An unretired running or stopped legacy record without authenticated discharge instead produces a grouped `delivery-consistency-unavailable` refusal before the overlap check; running work must be finished or reconciled through its exact retained release when available, while unavailable retained resources need separate recovery. A stopped selected delivery with pending tasks may be resumed or explicitly adopted only when its exact retained release and acknowledgement route admit that action; a nonselected stopped legacy record remains blocking until exact approved retirement or separately authorized external recovery. Retirement requires its own approved unfinished-work decision. Delivery creation and central persistence refuse `missing-predecessor` when current selection is missing but state, history, artifacts or accounting/provenance survive, when retained history/accounting names missing records, or when the database is missing but SQLite sidecars survive. Preserve those sidecars and restore or reconcile the database before retrying; an existing version-zero database instead refuses with `state-version` and likewise needs explicit reconciliation rather than automatic initialization. Stored identities must match their selected rows. First creation requires an empty delivery store; a valid completed current record with reconciled workers remains replaceable once a handed-over record's morning report has a recorded recipient confirmation bound to that report. A completion discharges only the closing record as it stood then: a delivery whose closing record was replaced after completion, by renewed triage or a closing reset, holds replacement back until it completes again, and a closing check recorded on that same record afterwards holds it back until the record's latest closing assessment, which must be a fresh, complete docs review, has seen the content of every file the latest invocation of each such named check recorded; an older assessment never stands in, and a rerun supersedes an earlier attempt of the same name. Later file changes without recorded closing work leave the historical completion in place. While an unretired selected record lacks that confirmation, creation and fresh-identity persistence refuse with `report-delivery-pending`, without changing any table, and an exact replay of the current acceptance still returns it unchanged; present the saved report and record `report-delivered` with the user's reply, as Handover and the morning report describes. Records replaced under earlier releases do not hold creation back this way, since no confirmation route reaches them. An unretired complete or stopped delivery saved without schema-2 accounting by an older retained release is judged by bounded replay from its creation when the accounting support tables exist; with those tables absent, creation reports `no-independent-accounting` without replay and requires migration or evidence recovery; a record with schema-2 accounting but no independent provenance has lost it, and evidence that cannot be authenticated refuses creation with `delivery-consistency-unavailable`. Unretired completed records from earlier releases have closing evidence without recorded discharge admissions, so a project holding one refuses new delivery, and ordinary runtime actions do not migrate such records. Standalone contexts keep their explicit identities and same-identity history protection. Completed/stopped runs remain in history when a new authorized run starts. Records have a fourth status, `closed`, written only by the migration entry's `close` that [Legacy delivery migration](#legacy-delivery-migration) describes: creation counts a closed delivery discharged by its own close row, so a closed selection is replaceable and a closed nonselected record does not block, and close is a route for a stopped nonselected delivery whose accounting is current.

## Legacy delivery migration

The current installed release exposes a separate administrative `migration` entry through the retained launcher. Preparation selects that entry without changing a session's older run binding. Use the usual `action: "run"`, native `session` and absolute `project`, with `entry: "migration"` and an operation under `request`. `inventory` takes optional zero-based `page` (default 0) and returns `page`, `pages`, at most 20 exact IDs with task, closing, worker, report, follow-up and retirement details, counts and a store inventory hash; an exceeded detail bound leaves the IDs and counts visible with `detailUnavailable`. `manifest` takes one to 100 distinct exact `ids`, optional proposed `choices` and optional zero-based `page` (default 0); it returns `schema`, `storeInventoryHash`, `page`, `pages` and at most 20 members per page under the same full-manifest hash. Fetch pages 0 through pages minus one for the same exact IDs and choices, comparing schema, storeInventoryHash, page count and full-manifest hash on every response. If a page fails, is missing or differs, discard every earlier page and restart from page 0; if a stable complete set cannot be obtained, leave approval pending. Present only that complete consistent set and its hash before the final authority reply, since retirement cannot verify which pages the user saw. The approval artifact stores schema 1 for this release, includes incomplete tasks and the full saved closing record alongside the objective, stop, hold, workers, report and follow-ups, and binds the complete raw state and latest history by hash. Artifact-backed task and closing fields appear as content hashes after validation, not as expanded bodies. If a decision depends on a body, present it through a separate read-only evidence route such as retained runtime inspect when that binding returns hydrated content; if no reliable route is available, leave the decision pending. Later projection formats must keep schema 1 derivation and validation for saved retirements and their supersession chains; only the current certificate rechecks a tracked destination against the live backlog. `raw-inspect` diagnoses an exact saved record. These operations use a read-only connection. When no delivery database or SQLite sidecars exist, inventory reports no store while manifest, raw inspection and retirement refuse with migration-store-unavailable. Surviving sidecars make even inventory refuse with migration-store-unavailable until the database is restored or reconciled; a remaining `.claude/runs` database instead refuses with legacy-run-state until setup migration.

`manifest` may omit `choices` for diagnosis, in which case its `hash` is null and it cannot authorize retirement; an incomplete supplied choices set refuses with migration-decision-unavailable. For approval, `choices` contains one `{runId, disposition, report, followups}` for every requested ID. `disposition` is `retired-complete` or `retired-stopped` matching the saved status. `report` has `kind` of `none`, `already-delivered`, `confirmed` or `waived` as shown by the report projection. `followups` contains one `{id, disposition, destination}` per pending item, with `disposition` of `tracked` or `dismissed`; with no pending items it may be omitted and normalizes to an empty array; a dismissed item has no destination, while a tracked item uses `{path, anchor}` for an existing reachable active backlog entry. Before asking the user to track one, explain that a later edit or move of that entry makes the certificate stale and blocks new handover until the user approves a superseding certificate. `anchor` is a heading anchor in an index or breakout record, using the Ready backlog link scanner's LF-based heading and duplicate-slug order before entryHash line-ending normalization, or null for a whole breakout record. A tracked target with a top-level fence left open under that Ready block model is unavailable whether the anchor names a heading or is null. `raw-inspect` accepts `runId`, optional inclusive `fromRevision` and `toRevision` spanning at most ten revisions, with fromRevision defaulting to the current revision and toRevision defaulting to fromRevision, or `report: true` for a current saved-report preview.

`retire` takes the exact manifest `ids`, `choices`, `manifestHash`, the user's final `authority` reply after all pages and relevant reports were presented, and the admitted `actor`. Each choice names a completed or stopped record, its report disposition and one track or dismiss disposition for every pending follow-up. A stopped record needs its own displayed choice. A tracked follow-up names an existing active backlog entry; Nightshift binds that entry's content. Any owed report may be expressly waived after its saved-hash and file condition is shown, including a missing, changed or unreadable file; confirmation requires present bytes matching the saved hash. No record is retired from an abbreviated inventory preview, an earlier broad policy choice, an omitted decision or an unavailable user. The writer checks the same canonical manifest under its transaction, so changed run selection, another delivery, changed report bytes or a changed tracked entry makes approval stale. An identical successful retry returns the existing certificates. Read-only inventory can diagnose a stale certificate and new-release `status` exposes retired follow-ups, including tracking destinations that later drift.

An existing session bound to an older release keeps that runtime after administrative retirement. The current bootstrap sends `handover` and older `create` resolution and run requests through the current service even before a retirement exists; that service can still select an older bound runtime for an eligible replay. With any retirement reference, a delivery-creating handover with tasks and an absent or different handoverId takes current creation admission even when runId is supplied. An older create action also takes current creation admission because it has no handover replay identity. A nonempty handoverId matching the requested record's saved acceptance may keep the retained runtime for an unretired record; the existing no-selector replacement rule still applies to a completed, closed or fully stopped selected record. A handover that exactly replays a running unretired record, and other nonreplacing work, still use the retained runtime. Through the current bootstrap, exact acceptance replay targeting any retired record takes new-run admission even when runId names it; a nonselected target remains refused before mutation, either at release admission or by a runtime identity or consistency check. Delivery-creating handovers classified as new-run work under a retirement reference execute on the session's own release, so a newer release installing mid-session does not block them. A session first admitted through migration receives a current retained bundle binding. New handover still validates every certificate and all other saved obligations before replacement, and refuses a certificate or approval schema its runtime does not support. Releases before 3.3.11, whose runtimes do not validate retirement certificates, are no longer supported.

When the `legacy_retirements` table exists, new-release `status` reports `legacyFollowups` with `status: "available"`, `total`, at most 20 `items` and a `truncated` flag, or `status: "unavailable"` with a reason if it cannot inspect retirement evidence. An item has `runId`, `id`, `title` (null when the saved item has no title), `disposition`, `destination`, `destinationStatus` and `retirement`. `destinationStatus` is an object with `status` of `none`, `current`, `drifted` or `unavailable` and a `reason` on unavailable; `retirement` carries the certificate status and any error. `disposition` is the validated approved choice only while retirement is valid, and `unavailable` otherwise. The saved source item and original choice remain in the manifest and certificate for raw inspection. After current-release admission, a mutating new-runtime request targeting a retired record refuses with `retired-run`; an older-bound session or different owner may be refused earlier by release admission, without changing the record.

Authority text for retirement is limited to 4 KiB; a longer reply refuses with migration-authority-required and needs a shorter exact reply. Report-file reads are limited to 16 MiB per manifest, and each tracked entry to 1 MiB, with a 16 MiB aggregate read budget per manifest for target files, active indexes and linked records used to prove reachability; repeat file reads consume that budget; split an oversized batch or recover an unsafe target before seeking approval. A changed but readable destination changes the approval hash and refuses with migration-manifest-stale, requiring new pages and a new reply; an unavailable target refuses separately until recovered. To change an approved disposition or a tracked destination, inspect the current record, present a fresh complete manifest with the replacement choices, obtain explicit user approval and call `retire` again with its new hash. The transaction writes a superseding certificate and preserves the earlier one; an identical retry returns the current certificate. A retirement made stale by external state changes can be superseded only while the record remains legacy with coherent current and latest history and supported protection. Otherwise raw inspection and separate evidence recovery are needed, and new handover stays blocked. This supersession changes the retirement decision, not the old run's state or history.

Retirement preserves run, history and artifact rows, writing content-addressed certificates and table triggers that refuse writes affecting a retired run ID in the delivery database. A version-1 store gains its version-2 support tables during retirement only in the approved transaction; other successful writes by the current runtime can also upgrade it in their own transactions. Reading coherent legacy provenance when those accounting tables are absent returns no independent rows without creating the tables. The creation gate accepts a valid explicit retirement as a distinct disposition from authenticated lifecycle discharge; damaged schema-2 accounting cannot be retired as legacy. The gate fails closed on missing protection, invalid certificates, resource bounds or uncertain writers. It checks current/latest state plus required accounting input against a 64 MiB allowance. Within it, the accounting and provenance artifacts it reads for every record share one 8 MiB allowance of distinct bodies, while the assurance snapshots and closing evidence it hydrates to judge a completed record's discharge are charged to an 8 MiB allowance of that record's own, so completed records do not accumulate against one another; a record whose own completion evidence passes its allowance still refuses creation with `delivery-consistency-unavailable`. Of the artifact bodies, which must all be valid JSON nested at most 1000 levels deep, without a raw NUL byte, its artifact identity scan, like inventory's, reads only those whose top level carries `runId`, refusing one over 8 MiB as corrupt, with no ceiling on the artifact store's total size or row count. The full-store, selected page or batch, and creation passes verify referenced artifacts without hydrating them: each distinct body is read, identity-checked and parsed once per pass and refused with `migration-evidence-bound` over 64 MiB, a repeat reference reads nothing, and no pass caps its total. Inventory and manifest each run a full-store pass and a separate output pass; creation verifies retired and resource-only legacy records under its own pass. Raw inspection instead has an 8 MiB bound for each state's distinct and expanded referenced evidence, and its artifact-ID list can be partial with `migration-evidence-bound` even when the evidence is intact. Each approval manifest is capped at 8 MiB, and one gate, inventory or retry reads at most 64 MiB of distinct approved manifests. A certificate over 8 KiB refuses with `migration-certificate-bound` naming its run; obtain a shorter exact user reply; if it still cannot fit, leave the record unretired until a separately authorized certificate-limit change is delivered. Retirement requires its newly approved certificates and checked resource bounds to pass, while unrelated damaged modern accounting or stale earlier certificates remain unavailable for later creation. Missing or corrupt evidence referenced by any saved current or latest-history state makes inventory and manifest unavailable, even outside the proposed batch; the error names the run. Use bounded `raw-inspect` on that run to diagnose it, then restore the evidence before retirement. Retirement's resource-only preflight defers replay of other unretired legacy records; a later handover still refuses them, naming a `legacy-replay-bound` record and directing the controller to migration inventory when their individual replay exceeds its limit. A grouped refusal reports `no-independent-accounting` when legacy accounting tables are absent, `legacy-replay-unavailable` when bounded replay cannot be established, `legacy-replay-bound` when that replay exceeds a bound, and `discharge-unresolved` when an unretired record lacks authenticated discharge, including running work that is not replayed or a completed/stopped replay that remains unresolved. After the first legacy blocker, later legacy IDs receive `replay-deferred-after-blocker` without another replay, and later modern accounting waits for the next attempt; migration inventory can classify those records independently. If current plus latest state alone exceeds 64 MiB, the refusal names bounded IDs but migration inventory also cannot run, so use bounded raw inspection or external store recovery. Retired records remain available through bounded raw inspection but cannot be amended, resumed or adopted through the new runtime; older retained runtimes can still work on nonretired records. The development migration CLI is read-only; retirement requires current installed administrative admission. Isolated deterministic fixtures exercise the transaction core without granting a general checkout route. Application to a real bound store needs an installed compatible release, with publication decided separately.

`compact-history` rewrites one run store into store version 3, whose history keeps each run's current revision and every 64th revision as a full row and every other revision as a backward delta from the next revision, which rebuilds that revision's exact text. It takes `store`, `delivery` or `review`, and optional `finish: true`, requires current installed administrative admission like `retire`, and holds the project write lock. It refuses, changing nothing, with `history-already-compact` for a version-3 store, `compaction-run-active` while any record in the store is running, `compaction-store-busy` while a SQLite journal, WAL or shared-memory file survives, `compaction-backup-present` when a `.pre-compaction` backup sits beside a store that is not version 3, `runtime-ownership-busy` while another writer holds the project lock, and the schema and protection errors inventory uses, `migration-store-unavailable` among them for a store that is not an ordinary singly linked file. It builds the migrated store beside the original as the store's file name with `.compacting` appended, adding an empty `artifacts` table for a version-1 store, verifies that every history row rebuilds to the original's bytes, kind and time, that every other table matches row for row and that no original table is missing, then renames the original to its name with `.pre-compaction` appended and the new file into place. Every `state: "swapped"` result, including a resumed or repeated one, carries the store's size before (the backup's) and after, the history row counts and stored bytes by encoding, and the backup path. A rename blocked by another open handle refuses with `compaction-swap-incomplete`; rerunning continues from the state reached, discarding any unswapped build, and with only the backup and the new file present it completes the swap. With only the backup present, it refuses with `migration-store-unavailable` naming the backup, which the user renames back to the store name to restore the original. `finish: true` verifies the migrated store against the backup once more, deletes the backup and returns `finished`, or `nothing-to-finish` when no backup exists; a migrated store that no longer matches refuses with `compaction-verification-failed`, and a backup that cannot be deleted with `compaction-finish-incomplete`, both keeping the backup. Inventory's store hash counts a version-3 store as version 2, so retirement manifests approved before compaction and identical retirement retries stay current after it. A store this release creates starts at version 3, and an earlier store keeps writing full history rows until compacted. Releases before 3.3.23 refuse a version-3 store with `state-version`, so a session still bound to one cannot use the project after compaction. Reading a compact history row whose rebuild does not match its recorded length and digest fails with `history-unavailable`.

`close-manifest` and `close` close settled records. A record's status then becomes `closed`, a fourth status beside `running`, `stopped` and `complete`, final in the current release and distinct from `complete`: the user dropped the record's remaining obligations, which were not discharged. Both actions take `members`, one to 20 distinct `{store, id}` pairs with exactly those keys, `store` `delivery` or `review` and a nonempty string `id`, spanning both stores if needed; malformed members, or an approval body over 8 MiB, refuse with `migration-manifest-unavailable`. They also take an optional `acknowledgedRecords`, the same `{store, id}` grammar, distinct, absent meaning empty, and hashed sorted by store then id; a malformed or duplicate entry, or one naming a record the older-release guard does not name, refuses the whole call with `migration-decision-unavailable`. `close-manifest` is read-only. It returns each member's projection (`store`, `id`, `revision`, `status`, `objective`, `stop`, `hold`, `identity`, `workers` with `reconciles`, `incompleteTasks`, `findings` counted by `pendingClosure`, `pendingRepair`, `pendingRepairRequired`, `unverified` and `pendingDisposition`, `followups`, and for a delivery `closing`), each ineligible member with its code, the older-release guard's `named` records, `refusals` and `warnings`, and `hash`. The hash is null without `choices`, or while a member is ineligible or the guard refuses. `choices` hold one `{store, id, report: {kind}, followups}` per member, using retire's report and follow-up grammar: a review context, or a delivery without a handover, takes `none`; a handed-over delivery whose report was delivered takes `already-delivered`; every other handed-over delivery takes `waived`. A malformed choice, a report kind other than the one its record allows, or choices that do not cover each member exactly once, refuse the whole call with `migration-decision-unavailable`.

A member is ineligible as `migration-run-unavailable` (absent from its store, or its store absent with no leftovers), `migration-store-unavailable` (its store present but unreadable, or absent beside SQLite sidecars or a compaction backup or build file), `close-not-needed` (complete), `run-closed` (already closed), `retired-run`, any adoption-eligibility code, or `close-accounting-unavailable`. The last applies to a delivery whose store lacks the schema-2 accounting tables, or whose accounting is not current. A worker whose termination adoption eligibility proves while its saved status reads active is reconciled to `stopped` by the close, and listed in `closure.reconciledWorkers`. The older-release guard names every other `running` or `stopped` record, apart from retired ones, whose release identity (by `executionResources()`'s rule; null or unparseable counts as older) is below the first release that ships close; such a record refuses close until the user's reply acknowledges it by name in `acknowledgedRecords`. The guard also reads the release registry the admitted migration context names, for older-bound sessions listing the project. An activation owner that is alive, or that cannot be inspected, refuses. A binding with no activation, or whose activation owner has ended while a newer activation-failure record exists, is a warning, and so is a host registration whose base release is older. The requesting session counts as live. A store that is unreadable, including an absent file beside a compaction backup or build file, is a guard refusal; an absent store with no leftovers holds no records. Close sees only sessions recorded in the admitted registry.

`close` additionally takes `manifestHash`, the user's exact `authority` (at most 4 KiB, refused with `migration-authority-required`), `reason` in their own words (at most 1 KiB, refused with `close-reason-required`) and the admitted `actor`. It requires administrative admission, so it refuses without a context (`migration-admission-required`); its own admission refuses while another project operation runs (`resource-operation-busy`) and requires the requester's live activation. It inspects process liveness before any store transaction, then writes the delivery store and then the review store, each inside its own runtime transaction, which takes the project write lock (`runtime-ownership-busy` while another writer holds it). Each transaction recomputes the manifest; it refuses with an ineligible member's own code, naming every ineligible member, with `close-older-release-present` while the guard refuses, naming each refusal's record, session or store with its remedy, and with `migration-manifest-stale` unless the hash still matches. It then saves the approval as an artifact, and saves each member with history kind `close`. A closed record carries `closure: {authority, reason, manifestHash, approval, reconciledWorkers, previousStatus, previousRevision, recordedAt, actor}`, which must serialize under 8 KiB (`migration-certificate-bound`). A delivery's accounting must be current at the close revision, or that store's transaction rolls back. A member already closed with the same hash, authority and reason is skipped and projected from its `previousRevision` history row, so an identical retry, including one after a failure that committed only the delivery store, writes the rest or nothing. `close` returns `{state: 'closed', manifestHash, members}`, each member `{store, id, closure}`, members closed by an earlier identical call included. A closed record is read-only: every operation that would change it refuses with `run-closed`, while `status`, `inspect`, `history` and `wait` still read it; through an installed release, a session other than the record's controller on its exact binding is refused earlier by release admission (`resource-owner-mismatch`, or `adoption-run-unavailable` for adoption), without changing the record; its `status` carries `closure` and no next tasks, it owes no morning report, follow-up notice or acceptance checkpoint, and the creation gate counts it discharged by its `close` row.

## Controller claims and adoption

Before canonical engineering in each new or resumed controller turn of a delivery run, read status, reconcile actual activity and call owner-only `claim-controller` with the current actor and revision. Successful creation through `handover` and `resume` also establish that turn's claim. A standalone review context takes no controller claim; [Standalone review contexts](#standalone-review-contexts) describes how it authenticates owner activity. Only these successful results carry `controllerReady`; viewing state, native activation, continuation verification and a previously saved claim do not grant it. Native process identity comes from the actual invoking host, never a caller-supplied PID, found through the process ancestry that [the resource interface](../releases/REFERENCE.md#automatic-preparation-and-explicit-maintenance) describes. Failed claim observation grants no engineering authority; when the ancestry reaches an exited parent, the claim reason names the last live process below it and the likely invocation shape to change. When the process inspection itself fails, the claim reason, and the `controller-claim-required` refusal of an action that needs the claim, name the inspection's cause and say the request can be retried, because a failed inspection does not show that a saved claim is invalid; the resource interface gives the inspection's time budget. Failed creation leaves the run and active pointer unchanged; failed resume leaves the run stopped. Use allowed diagnostics to resolve the cause rather than editing under an earlier grant.

Owner bookkeeping for reports, report delivery, spec acceptance, retrospective and triage, and closing-record operations on a complete run, does not require an engineering claim. Its existing lifecycle and evidence gates still apply, including on stopped or completed runs. This permits preserved closing duties after adoption or process replacement without granting source edits or requiring authority to resume engineering.

The `review`, `validate` and `dialogue` receipt-import maintenance paths likewise require ownership and full receipt validation, but no fresh engineering claim. They do not restore disabled integration, grant source edits or authorize a new dispatch. This preserves already-produced evidence when ordinary admission cannot refresh the claim.

`controllerClaim` records the current owner, native process identity, revision and observation, with previous observations retained in history. It supports conservative abandoned-run recovery, not automatic detection of every new turn: the controller must refresh it before engineering. Adoption clears it. A live or shared host process, missing claim or unknown process identity cannot establish abandoned-controller inactivity.

`adopt` takes the explicit current `runId`, latest `revision`, `previousController: {host, session}`, the new admitted `actor: {host, session}`, and nonempty user `authority`. The run must still be the project's current unfinished run; a closed record is not, so the release service's adoption admission refuses it with `adoption-run-unavailable`, and the runtime's own adoption guard refuses it with `run-closed`. Adoption of a stopped run requires confirmed inactivity of all workers and project operations; the former chat may remain open. Adoption of a run still marked running additionally requires positive proof that the exact former host process in its latest supported controller claim has ended. Unknown or active activity blocks both cases. Permission alone is not inactivity evidence. A former owner can explicitly stop an eligible run; there is no force-adopt or replacement-run escape for missing evidence.

The controller and worker inactivity checks are `adoptionEligibility(state, request, dependencies)` in `ownership.js`, which `adopt` runs and Ready runs read-only with an empty request; it returns `{eligible: true, controller, workers}` or `{eligible: false, code, message}` with adoption's own codes, while request validation still throws. Ready's parser adds `runState` beside its backlog result through `run-overview.js`, without changing notices, structural errors or `--check`: `records` lists every running or stopped delivery run and review context, apart from retired ones, plus the current delivery when it is complete and its morning report awaits its recipient, each with a `pickup` of `adopt`, `present-report`, or `none` with a reason and message, and a `close` with the same grammar, `{offer: 'close'}` or `{offer: 'none', reason, message}`, judged on its own from the status, adoption eligibility and, for a delivery, its saved accounting marker (null for a record Ready does not evaluate for close); closed records are not listed; `compaction` gives each readable store's version, size and `.pre-compaction` backup, with `compact-history` due for a store below version 3 of at least 64 MiB without a backup and `finish` due for a version 3 store with one; and `unavailable` names each store that could not be read, with `run-overview-busy` while a SQLite sidecar survives and `run-overview-bound` when its current states exceed 64 MiB. It reads only `runs`, `active` and `legacy_retirements`. The parser also adds `release`, the release running it: `{mode: 'bound', version}` with the version taken from the launcher context's identity, which admission checks against the session binding, and `version` null when that identity names none, or `{mode: 'development'}` without an admitted context.

Adoption preserves identity, commitments, limits, imported evidence, follow-ups, publication authority and report duties, leaving execution stopped with current owner observation, continuation and Stop reminders invalidated. Reconcile workers and unresolved operations before explicit `resume`. Review-context adoption uses its namespaced resource reference and preserves original receipt attribution; neither ownership transfer nor resumption adds handover or closing obligations to standalone revision. New execution authenticates actual ownership, and delivery refreshes continuation before engineering.

For a plain in-host worker without managed process/operation metadata, `adopt` accepts optional `workerEvidence: [{workerId, path}]`. Omission or an empty array supplies none; null, duplicate/unknown workers and entries for terminal or managed workers are rejected. `workerId` is the exact registered id. `path` is a regular, singly linked project-relative native JSON-lines export under `.nightshift/runs/worker-evidence/`, using forward slashes and the ordinary evidence-path rules. Preserve the actual native events at a new path; never manufacture them from a user statement, an idle/absent status or a model's assertion of completion. A completed turn of an assignment that still has continuation or surviving work is not terminal helper evidence.

Arrange each such helper's terminal JSON report to carry `runId` equal to the exact saved run id and `requestId` equal to its exact registered worker id, without normalization or empty values. Claude evidence requires a native assistant attribution and successful terminal result in that session whose structured output or JSON result carries both markers. Codex evidence requires the native thread/model opening, a correlated agent message and its completed native turn, without later turn/item activity or observed unfinished goal continuation. A missing host, marker, terminal signal or attribution, a mismatched model/session, malformed/changing bytes, a BOM or an export larger than 32 MiB is unknown, not permission to adopt. This export route does not override managed-process reservations or prove engineering success. The adoption record retains the verified native identity, path, hash and observation time; preserve the export for later audit. The time records verification of those bytes, not their native completion time. The new owner still reconciles the saved worker record before resuming.

Bound adoption requires the same retained store, exact compatible payload and authenticated target binding; development adoption stays development. `resources` is immutable creation provenance, while `executionResources` describes the current binding. Both use `{schema, store, registration, session, identity}`; absent execution resources on an unadopted historical run fall back to creation resources, never to arbitrary current defaults. New dispatches use current execution resources; historical receipts retain their original assignment resources. Missing evidence, legacy releases without adoption, mixed modes, different stores, unavailable payloads, completed/replaced runs and active-controller transfer do not qualify. Do not silently upgrade the run. The [resource interface](../releases/REFERENCE.md) describes durable target retention and interrupted-transfer recovery.

Managed reservations enter `preparing` before preparation can spawn commands, then `launching` and `launched` or `contained` for the managed process, and `finalizing` before postprocessing. A dead helper in the original `reserved` phase proves that preparation never began. In an interrupted preparation/finalization phase, a model or command termination artifact alone cannot prove that surrounding subprocesses ended, so takeover remains blocked pending reconciliation. Missing or unknown phases also remain uncertain. Codex native exports with later active, erroneous, missing or unrecognized thread status similarly fail reconciliation; only later `idle` or `notLoaded` status is compatible with the correlated terminal turn.

`acceptanceCheckpoint` is an ephemeral owner diagnostic returned on delivery creation, in-place handover, continuation and status while acknowledgement is pending. Ordinary foreign-session status remains readable without the owner checkpoint; legacy/review records and current captured duties return null. It preserves `requiredNextAssistantOutput`, `observedContinuation` (`available`, `failed` or `pending`) and `assistantOutputEvidenceRequired: true`, and adds `inspection: {status, reason}` plus `nextStep`. Status/step pairs are `awaiting-outcome`/`record-continuation`, `missing`/`emit-text-then-status`, `available`/`request-engineering` and `unavailable`/`recover-history`. Reason is null or explanatory ASCII text of at most 1,200 characters. These step names are workflow labels, not new runtime actions. Inspection reads the current saved bindings through the bounded native observer; absent or stale outcome boundaries and freshly admitted failure drift require reconciliation first. Missing text calls for actual ordinary assistant text followed by status in the same ongoing turn; unknown or unavailable history calls for bounded recovery, never a permissive classification or automatic polling loop. The result is discarded after each response: it changes no run state, reminders, continuation or acknowledgement flag and is not authority. Engineering independently recaptures current evidence and commits it atomically. Final-only acknowledgement without verified continuation is not an in-turn fallback.

## Standalone review contexts

`open-review` accepts `reviewContextId`, an immutable lowercase UUID preserved across retries, `controller: {host, session}`, actual user `authority`, `objective`, `kind` of code/spec/docs/lore, `agreement: {source, outcome, spec?}` and optional limits with the same deadline/dispatch grammar. Source, outcome, objective and authority are nonempty text. The spec is a regular project-relative file when present. A standalone request has no delivery queue, runId or mode. State lives in `.nightshift/runs/review-state.sqlite`, distinct from the delivery database and active delivery pointer. Repeating an identical opening returns its existing context; a changed opening conflicts rather than discarding review obligations.

Subsequent operations use the actual context UUID in `reviewContextId`, the owner actor and current revision, with assessment target `#review` as default. An empty, null or unsupported context selector is refused; its presence never defaults to delivery. Supplying a delivery runId as well is refused, including an empty or null one. The common dispatch, checks, private probes, receipt import, skeptical validation, dispositions, repair closure and fresh-assessment rules still apply. Contexts authenticate native owner activity without a delivery controller claim. `advance` and `complete` require every applicable assessment independently: a docs context needs docs assurance or its current mechanical exemption, as Documentation review describes, an imported code assessment remains required, and imported docs assurance also remains required on a code context. Stale, incomplete or continued evidence cannot finish the requested revision. No delivery retrospective, morning report, triage or goal is added. Follow-ups remain available in its final result.

Delivery-only operations, including handover, continuation, controller claims, add-spec-review and closing-record work, are refused on a review context. Explicit hold/stop and authorized resumption preserve its scope and evidence. A stopped context, or a running one whose owner has ended, can be closed as settled through the migration entry's `close`, as [Legacy delivery migration](#legacy-delivery-migration) describes; a closed context is read-only, every operation that would change it refusing with `run-closed` or, through an installed release, earlier at release admission as that section describes, and it no longer blocks compaction of its store. A conflicting delivery owner or uncertain worker prevents canonical repair; read-only assessment may use a stable private copy. Advanced staged-only and historical-range capture remain a separately tracked capability; cumulative or whole-spec scope is the current surface.

Runtime evidence identifies recordKind as delivery or review, with absent historical kind implying delivery. Review resource references use review: followed by the context UUID, so older collectors cannot confuse them with delivery UUIDs. The inventory includes both stores, exact resources, surviving workers and unresolved protection obligations. Missing or unsupported state fails retirement and collection closed; no age-based cleanup or implicit record replacement occurs.

All current run-store mutations acquire the shared SQLite mutex at `.nightshift/runs/write-ownership.sqlite` before their record transaction. The first acquisition creates its sole ownership row with format 1, the canonical parent, the parent filesystem identity and the mutex file identity; subsequent acquisitions validate the same identities and bytes. An immediate SQLite transaction holds the mutex until commit or rollback of the record transaction, then releases it without altering the ownership row. Process termination releases the SQLite lock. The file remains for later acquisitions and is not removed by completion, hold, adoption or collection. It contains no run authority or worker status. Initialization interrupted before a valid row, unexpected sidecars, links, changed identities, invalid schema or a file over 64 KiB fail closed; preserve the file and records for explicit recovery. Contention refuses the operation for a current-state retry. Read-only status, history, inspection and retained inventory do not acquire or manufacture the mutex.

Under that common mutation boundary, write registration checks delivery and review records together, including active or uncertain workers on completed or stopped records. Declared overlapping paths cannot acquire a second writer. Canonical start, repair authorization and delivery claims or resumption also preserve other records' writers; isolated read-only assessment remains possible. Missing, malformed or unsupported ownership inventory cannot grant canonical writes. A standalone writer additionally respects another owner's unfinished delivery. Before standalone canonical edits, record `start-task`; finding-driven repairs require the recorded implement disposition first. Actual workers can prevent new delivery ownership without making an otherwise idle review context an active delivery run.

## Delivery and evidence

`start-task` enforces agreement and dependencies. Implement directly from the outcome or spec. `check` executes a real check from `check: {name, executable, args, paths, timeoutMs?, resourceMode?}`. Paths are all project inputs covered by the check, using forward slashes, and name regular files: a directory is refused with `unsafe-path` before any worker is reserved, so list the files it contains. It records output, exit, input hashes and whether the check left its inputs unchanged. The executable and its arguments are actual commands chosen under the user's authority. An executable named by path runs as given; a bare name resolves before reservation to an absolute path from the check environment's PATH, outside the project and with `.exe` implied on Windows, is recorded as that path, and fails with `executable-not-found` when nothing qualifies. Test fixtures that mutate data must be separate from these reviewed inputs. Checks and private probes reserve internal operation workers before launch in both resource modes, so takeover cannot pass through an unrecorded execution window. Reservation first identifies the runtime's own helper process, as a review dispatch does; when that inspection fails, `check`, `probe` and `dispatch` refuse with `operation-owner-unavailable`, naming its cause, and reserve nothing. A check also records its pending named result first; an interrupted rerun cannot fall back to an older pass. Result evidence and terminal worker state commit together. A refusal before the contained launch leaves the worker `failed`; only an attempted launch without termination evidence leaves it `unverified`. A check or probe finishes when its command exits: descendants still running 5 seconds later, such as a compiler or build server a build leaves behind for reuse, are ended and recorded as `lingeringDescendants: {total, processes: [{pid, image}]}` (`image` is the executable path, or null when it could not be read; at most 64 are listed, while `total` counts all, or is null when the listing failed), and the command's own exit code decides the result. A check or probe that left nothing running records `lingeringDescendants: null`. Dispatched reviewer hosts and the launcher's own operation still wait for every descendant to end. These internal workers are not public model-role registrations.

`check.resourceMode` is either `inherit` (the default) or `development`; null, empty and other values are rejected. Use `development` for deliberately selected checkout tests or private library fixtures when the controller is bound to an installed release. That child and its descendants receive explicit development mode without the controller's operation context or worker binding. The parent and saved run binding do not change. Keep `inherit` for genuine installed helpers that need the parent's bound context. Direct terminal test commands outside a bound operation keep their existing behavior. The chosen mode is recorded with the check.

`advance` moves a code/spec task from implementation to review, review to documentation, and documentation to task completion. Documentation requires an evidence description and current review/checks, so documentation edits can require cumulative reassessment. A spec task a code task links, in either place, completes directly after its strong assessment; it does not manufacture documentation or session-closing work. A standalone spec retains documentation. Docs tasks start in documentation; lore tasks perform their requested retrospective work and complete. A lore task can import a direct `code` assessment of its instruction proposal, and a docs task a `code` or `docs` assessment of its complete change, using the same independent findings and repair loop. Accepted assessment returns to documentation for docs or retrospective for lore; it does not authorize applying an instruction proposal. A lore task without an assessment keeps its direct completion path; once assessed, its current review is required at task and run completion. Code and docs tasks need the docs review that Documentation review describes before they complete. A no-edit assessment refresh of completed work preserves closing evidence. Task completion releases dependent engineering without a premature session retrospective or triage.

Session closing is shared by the run. Once actionable tasks have finished or are blocked and all workers are reconciled, call `retrospective` with evidence, then `triage` with evidence; a handed-over run records `report` between them. When every remaining blocker is a user decision and no worker is active, the controller may instead end its turn to ask, as a conversational pause; closing stays due when the run resumes or ends, and answering the decision would have invalidated closing evidence recorded before it. `status.closing` gives readiness and the next closing stage. Unanswered user decisions remain pending, rather than being inferred. A last standalone lore task supplies the session retrospective itself. New engineering, repairs or changed agreements invalidate the saved closing evidence; a no-edit assurance refresh preserves it. Absent closing state means those obligations are still due. `complete` requires every task complete, current required assurance, including docs reviews and a resolved closing record, no active workers, both closing records and, on a handed-over run, the recorded morning report. It also refuses with `committed-scratch` while the index holds `.tmp` paths that the run's cumulative review base did not track, naming them, or when Git cannot list them or read the run's commits after that base; the repair is removing them from the index and committing. Paths tracked at that base, and tracked paths on a run that recorded no base, draw only a scratch notice, and outside Git the check does not apply. A blocked run can record its session closing without claiming unfinished engineering complete.

## Handover and the morning report

`hold` requires nonempty `authority` containing the actual user's hold request and nonempty `reason`. It sets execution stopped and records `hold: {authority, reason, revision}` while preserving commitments, handover, workers, evidence and closing duties. It does not establish worker termination. `resume` needs explicit authority and reconciled workers, clears the hold and refreshes owner activity; delivery then observes continuation again, while a review context adds no goal or closing stage. A held or stopped record generates no Stop continuation pressure.

Every new delivery carries handover. For an existing running delivery, `handover` refreshes the accepted request with actual `authority` and optional `mechanism`. It preserves original acceptance, queue, workers, commitments, evidence, limits, follow-ups, publication authority and closing duties. A stopped record requires explicit resumption first. Continuation is separate capability: `mechanism: {verified: true, kind, evidence}` records observed success; `{verified: false, kind, reason, operation?}` records a technical failure and its follow-up, with operation defaulting to continuation. Kind is goal or stop-hook; a Stop hook cannot carry a Codex controller. Empty/unknown kinds, missing evidence for success and missing cause for failure are refused. An explicit paused, stopped or limited mechanism is not a technical failure to bypass. Current status exposes handover and continuation, with no execution-mode field.

Attempt the native persistent `goal` on Codex and the registered `stop-hook` on Claude Code. Observe registration, enablement, trust and activation for a Stop hook rather than inferring them from a saved flag. Neither mechanism relaunches an exited host or Windows. Refresh at renewed handover, adoption, resume, compaction recovery and before a yield relying on continuation. Classify actual native output, preserving absent, blocked, paused, complete, limited and unknown states. Native paused goals and usageLimited or budgetLimited states are authoritative holds or limits, not technical failures to bypass. Resume only through an actually supported operation under existing authority and verify its result. An unavailable or failed mechanism records its technical outcome and follow-up and permits otherwise authorized work in the current turn. Do not replace an unfinished or unrelated goal, change native trust, enable disabled hooks or use another worker as controller continuation.

Owner-only `invalidate-continuation` records nonempty `reason` and leaves observation pending without changing execution status, authority or closing duties. Invalidation and resumption do not themselves establish a successful or failed attempt; dependent engineering waits for that outcome. Record an actual technical error through `continuation` with verified false, kind and cause, rather than treating pending invalidation as its fallback. Receipt-import maintenance can preserve existing evidence while observation is pending. Technical failure is scoped to the current owner, record, kind, operation and cause, with repeated unresolved observations reusing its pending follow-up. Recovery retains historical failures and their triage obligation. Native ownership or actual operation permission failures remain separate gates.

Mutating delivery operations also consume their admitted hook-integration observation. `hookIntegration` holds the last scoped integration health, owner, run and observation time; missing state means no integration observation, not health. A fresh unusable observation records its failure and deduplicated follow-up atomically with the operation. On Claude it invalidates Stop-hook continuation. On Codex it records auxiliary hook failure without overriding a separately observed goal. A healthy integration observation does not itself prove or restore native continuation, and recovery preserves historical failures. Claim-only and repeated unchanged observations retain no-progress protection; an actual continuation phase change carries new capability information.

Current continuation evidence is scoped to the controller, run, mechanism and observation. Initialize it unverified; refresh at the boundaries above and invalidate on ownership change, observed inactivity, missing/failed inspection, deliberate disablement or lost trust/activation. Keep the latest observation in current state and prior observations in history. Missing or historical unscoped evidence is unverified until refreshed; no elapsed-time heuristic replaces boundary verification, and ordinary source edits alone do not invalidate a host observation. With admission available, persist invalidation and continue useful authorized work in the active turn. A functioning Stop hook protects accepted delivery when work is eligible, but does not resume a Codex goal. Unavailable continuation records a follow-up and does not revoke handover. If the hook is unavailable, it provides no protection.

When execution admission itself is refused, preserve saved state and treat an old health flag as unavailable evidence. Resolve the actual refusal, such as disabled Nightshift, missing registration, invalid resources, unknown ownership or denied operation permission. Hook disablement, lost trust or absent activation alone is a continuation failure for new runtimes; leave those settings unchanged and record the observed failure and follow-up while continuing otherwise authorized work. Never use development mode to bypass the binding. Retained older runtimes keep their original admission requirements.

`handover`, `report` and `report-delivered` retain execution admission and ownership checks independently of continuation health. Missing hook trust or activation and disabled hooks do not by themselves refuse these new-runtime operations. A genuine refusal records no successful acceptance; report its concrete cause and preserve the pending request. While a runtime dispatch holds the project lease a bound `handover` is refused with `resource-operation-busy`; await the dispatch with `wait` and retry. An existing binding keeps its exact retained runtime, including older activation requirements and unavailable operations.

On a handed-over run the closing order is `retrospective`, `report`, `triage`, `complete`, and `status.closing.stage` reads `report` while the report is due. `triage` and `complete` each reject a handed-over run without report evidence with `report-required`, so a handover that arrives after triage was already recorded still cannot complete without a report. `report` takes `path`, a project-relative Markdown file under `.nightshift/runs/reports/`, requires the recorded retrospective, reads the file, rejects a missing, empty or out-of-tree path with `invalid-report` or `unsafe-path`, and stores `{path, sha256}`. It is rejected with `report-not-due` on a run without a handover. Recording it again replaces the evidence and clears any recorded delivery, and is accepted on a complete run. Resumed engineering clears the report and its delivery with the other closing evidence. A run without a handover keeps the two-stage closing.

Saving the report is not delivering it. `report-delivered` takes `authority`, the user's actual reply received after the report was presented, and stores `{authority, revision, sha256}` bound to the delivered report. It is accepted on a running, stopped or complete run, is idempotent for the same report, never gates `complete`, and is rejected with `report-stale` when the saved file is missing or no longer matches its recorded hash; the recovery is to rewrite the file and record `report` again. `status.report` gives `recorded`, `delivered`, `path` and `current`. Report operations reach the checkout's active run and its current owning session, including after adoption. Because a complete run cannot be adopted and its owning session may be gone, `report-delivered` on a complete delivery is also accepted from another admitted session of the same project, through a binding of the run's resource mode and store and the launcher's confirmation-only admission that [the resource interface](../releases/REFERENCE.md#ownership-transfer-and-current-execution) describes; it records that session as `recordedBy` and opens no other operation to it. Adoption preserves saved reports and follow-ups; ordinary resumed engineering still invalidates closing evidence as before.

A cumulative code assessment dispatched on a code or docs task includes the agreed commitments of the earlier completed code and docs tasks, and lists them in `coveredTaskIds`; the review gate of each listed code or docs task admits it, so one integrated current assessment can cover them without a separate historical-task review. Each covered task still needs its own current checks and resolved findings, and the covering assessment must postdate its latest requirements revision and repairs. Spec tasks keep their own whole-spec assessment and lore tasks the assessment of their proposal: neither is covered or admits a covering assessment. A docs review dispatched on a code or docs task covers the same completed tasks for their docs reviews in the same way.

`block` records `blocker: {kind, reason, recoveryAttempted}`; kind is `user-decision`, `capability`, `resource` or `dependency`. Continue independent tasks. `unblock` requires evidence that the condition changed. Unblocking a `user-decision` blocker also records that evidence as an agreed decision in `agreement.decisions`, replaces `agreement.outcome` with the optional nonempty `updatedOutcome` text, advances the task's requirements revision so assessments bound to the earlier commitments become stale, and invalidates saved closing evidence. On a code task it also reopens the spec task that governs it, linked or queued, recording the decision there and advancing its requirements revision, leaves an unresolvable link's target untouched, and clears `specReviewed` on a task naming a spec; on a task of another kind it reopens the task its agreement links, or clears `specReviewed` when none exists. The handover acknowledgement is renewed after those changes; other blocker kinds leave the agreement unchanged. This is the route for recording an agreement the user changes mid-run: `block` the task with kind `user-decision` naming the change, then `unblock` it with the user's words as evidence and the revised outcome as `updatedOutcome`. `stop` requires `kind` of `user-stop` or `resource-limit` and its actual `reason`. Do not use a stop to sidestep incomplete work. `resume` requires explicit user `authority` and reconciled workers; it preserves the same run, commitments and evidence, establishes a fresh controller claim and does not change existing limits. Unavailable continuation is recorded without changing handover authority. `continuation` records `mechanism: {verified: true, kind, evidence, ...}` only after observing the actual host behavior, with the same validation as `handover`.

## Independent assessment

`dispatch` accepts `taskId` and `review: {kind, baseSha, requirements, rules, candidates, requiredModel?, substitutionReason?, findings?, artifactPaths?, excludedPaths?, timeoutMs?}`. `kind` is `code`, `spec`, `docs` or `skeptic`; a skeptic assessment uses the documentation dimensions when every finding assigned to it came from a docs review. `baseSha` is the immutable base for the complete cumulative run change, not just the latest repair, given as the full 40- or 64-digit lowercase hexadecimal object name; an abbreviated name or a ref such as `HEAD` is refused with `invalid-base`. `requirements` includes the agreed commitments; `rules` contains all applicable conventions. `rules` is placed verbatim in every reviewer's system prompt, so it carries the user and project conventions that govern the reviewed change and nothing else: never the operating brief, a skill or this reference, which multiply every dispatch's input; never requirements or acknowledgements, which have their own fields; and never the author's reasoning for individual choices. The runtime attaches the recorded checks itself: for the dispatched target and each task its assessment covers, the latest invocation of each named check when it passed and its declared inputs are unchanged, judged as the verification gate judges them, with its command, exit code, finish time, the last 2,000 characters of its output and `inputs` as the number of its declared input files, its snapshot's digest and, under `changed`, the `{path, sha256}` of each of those files that the reviewed diff or an untracked file in it touches, and, as its `reproduction`, the failures (exiting nonzero or with an error) of the same executable and arguments in the last series of the same task's earlier settled invocations of that name that no successful invocation of that name, under any command, interrupts, where a pending invocation or one that exited zero while its inputs changed is not settled and a failure of another command is skipped: the series' first such failure, with the same fields except that `inputs` names, under `differing`, each file whose hash differs from the passing run's as `{path, failing, passing}`, a null hash standing for a run that did not declare the file or found it missing; `laterFailures`, the exit code, error, finish time and output tail of each of the next three failures in the series, since the records do not say which failure the controller confirmed, and `omittedFailures`, the number of failures after those; and `passesSince`, the number of successful runs between the series and the passing check. Executables compare after path normalization, and on Windows executables and input paths compare without regard to case. One check of the same name, command and snapshot digest recorded on several of those tasks is attached once, with every task's id under `taskIds`, when none of them has a reproduction for it; a reproduction is its own task's failing run, so a task whose check has one gets an entry of its own and no task's reproduction is lost. A failing, pending or stale latest invocation is not attached, and neither is its reproduction until the check is rerun. The attached set is saved as `checks` in the dispatch's `request.json`, and the prompt tells the reviewer that a passing check on matching inputs is execution evidence, not something to rerun by probe. Before launch a probe with usable declared files is refused with `stale-probe` only when one of them changed or is missing, naming it, so an edit elsewhere leaves a pending probe runnable; the private copy holds the project's current files under the recorded selection, a removed undeclared file being simply absent. A probe whose declared paths do not all resolve to files in the requesting receipt's context snapshot, or a receipt without the field, keeps the whole-inventory comparison before launch and the digest comparison at handoff. A receipt with a snapshot that fails its integrity check refuses the probe. Re-dispatch the assessment to have that evidence independently evaluated. A stored result joins any later assessment of its task, skeptics included, while its declared files are unchanged, and a result declaring no files always does; `repair` no longer clears them. Each travels as `context/probes/<id>.json`, one name in every dispatch of the task, which the prompt names one by one since a reviewer that can only read named files cannot list the folder, and carries its purpose, command and declared paths so the reviewer judges whether it still bears on the claim. Among eligible results with the same executable, arguments, fixture files and declared paths only the newest is attached; one dispatch attaches at most twenty, newest first, and names to the reviewer the eligible results left out, with the result that superseded each. The receipt's `withheldProbes` reports each withheld result to the controller as `{name, comparison, paths}`: `comparison` `declared` with the paths that changed, or `digest` with null paths for a result without usable declared files. A withheld result stays stored. A stored result whose artifact is missing or changed still fails the dispatch, as damaged evidence does. A probe is not a canonical repair, and an execution-dependent claim stays unverified until the evidence supports a verdict. Existing tools can carry the work on either host without granting reviewers write access to reviewed inputs.

`dispose` names `findingId`, `disposition` (`implement`, `defer`, `skip` or `refuted`), and a concrete `reason`. Defer also needs a durable `route`. For confirmed findings, include controller-owned obligation: {classification, basis}; classification is required, optional or out-of-scope, and basis names the accepted commitment and repair authority supporting the decision. The reviewer required field remains advisory evidence, not new user authority. Required obligations cannot be deferred or skipped, and out-of-scope findings cannot be implemented. Do not use classification to waive an agreed commitment. A fresh attributed skeptic must first establish validity; unverified claims remain unresolved. Validate and dispose the whole intended batch before applying its edits, and never issue those edits in the same message as the dispositions, since calls issued together can run in any order. If edits happened before a remaining disposition, re-establish current evidence instead of bypassing freshness. Apply the accepted repair batch, then record `repair` with `findingIds`, execute relevant checks, and dispatch the complete cumulative assessment again. No repair is exempt because it is small. `repair` refuses a finding whose current verdict carries no `repairProposal` with `repair-proposal-required`, and marks each repaired finding pending closure for the lineage that raised it. A continued lead's report carries `closures`, one `{id, closed, evidence}` per finding pending closure for its lineage when it was dispatched; a closure left open is matched in a complete report by a finding with that finding's local id. Every ordinary lead report carries both `closures` and `positions`, since its report schema is the same across ordinary lead dispatches; the same schema also carries `applicability`, empty outside relevance turns; an entry in `closures` on a report that is not a continued lead's, or in `positions` on one that is not a dialogue reply, is refused with `invalid-result`. Importing a complete continued report on matching current inputs ends the pending closure of each finding it records closed, and nothing else does: an incomplete report, a historical import, a relevance decision, a dialogue reply, a failed import, re-validation and a later disposition leave it pending. A continued assessment raises findings like any other but satisfies no gate or coverage condition: the code, spec, lore and docs gates, coverage through `coveredTaskIds`, the closing record and the triage baseline accept only fresh assessments. Every gate also refuses while a finding it checks is pending closure, and `complete` refuses with `closure-pending` naming any that remain. Status gives each listed task `review: {next, resumeTargets, freshDue, freshTargets}`: `next` is `validate-and-dispose`, `repair`, `resume` while findings are pending closure, `fresh-assessment` when the latest assessment of a kind is a continued one, or null; `resumeTargets` names the dispatch to resume, with its `taskId`, for each lineage owing closures, and `continue`: `replace` when the named dispatch's receipt ran on Vibe and the retained source its resume needs cannot be reused (see `review.resume` above), or when a dispatch of that lineage registered after the named one resumed the named dispatch's session and either saved a `failure.json` with `sessionFailed` true or ended after recording a host process id without saving a receipt or a readable `failure.json`, so that the session's outcome is unknown, and `resume` otherwise, including for a `failure.json` without `sessionFailed` as earlier releases write it; `replace` holds through later failed replacements and retries until a later dispatch of the lineage produces a receipt, which then becomes the named dispatch, and `review.resume` is never refused on its account; `freshDue` lists the kinds whose latest assessment is a continued one. After a task repair, `freshTargets` names each fresh assessment due because the repair left an assessment of a kind the batch did not repair, which a code, spec or docs gate of the task or of any other task reads, predating the repair and no longer matching current inputs, which for an assessment its gate accepts means the gate finds it stale and for any other, such as a continued or incomplete one, means its reviewed inputs changed. Such a reviewer has nothing to close; its applicability call, where one is available, comes before the fresh assessment. Each entry is `{kind, taskId, covers, staleAssessments, staleChanges, reopens}`: `taskId` is the stale gate's own task while it is open, otherwise a ready open code or docs task, the repaired one first, whose assessment covers it through `coveredTaskIds`, and only when no such task exists the completed task itself, with `reopens` true before triage evidence is recorded, since importing a review on a completed task then returns it to review, and `'if-findings'` after triage, when the task reopens only if the import raises findings or is not a complete fresh assessment its gate accepts; `covers` lists the tasks whose stale gates that one assessment reaches, and `staleAssessments` the request ids of the stale assessments, while `staleChanges` gives each as `{requestId, cause, changedPaths, applicabilityCall}`, `cause` being `changed-inputs`, `changed-commitments`, `unestablished` or `unmet` and `changedPaths` null unless changed paths are the cause, so an empty list never stands for the others. `applicabilityCall` is `{taskId, requestId, taskIds, resume, continue}`: the owner holding the stale assessment, the assessment the call judges, the sorted stale-gate tasks it covers within that assessment's `coveredTaskIds`, the latest dispatch with a receipt in its lineage and `resume` or `replace` by the `resumeTargets` rule, so the element carries exactly the `review.relevance` binding and its routing. It is null, and the entry's fresh assessment is the way forward, when the cause is `unestablished` (reconcile first), when the latest applicability decision on the current inputs and commitments already answered `reassess` or `unresolved`, when the assessment is continued, incomplete or narrow, when its original inputs are not retained, when it has no request id or no dispatch with a receipt, and when the run's outside-documentation hold is unsettled and the element's changed paths include a path in its set, or the set cannot be computed, in which case the hold's `next` governs; the hold nulls the call this way for code- and docs-kind elements, and for a spec-kind element only in a run whose hold a whole-spec assessment settles. A change of commitments alone does not make it null. The applicability entry's `next`, `STALE_REVIEW` at `advance` and `stale-review` at `complete` name the applicability call first exactly when this slot would be non-null. Without a task repair `freshTargets` is empty; a closing repair adds only its closures, and the hook's continuation brief, which verifies no freshness, carries `freshTargets: 'reconcile at acceptance'` after a task repair.

## Documentation review

A `docs` assessment is a strong independent review of the complete cumulative change with the documentation dimensions `claim-accuracy`, `sweep-completeness`, `backlog-conventions`, `sibling-consistency` and `proportionality` in place of the code dimensions. Its reviewer receives the same inputs as a code lead, judges what the documentation, including the backlog, says about the code rather than the code itself, and reports any changed file it judges to be operating instructions. Its findings are recorded with their kind and take the same `validate`, `dispose` and `repair` operations.

Runs created by this release carry `docsGate: true`. Each code and docs task of such a run needs, when it advances from documentation, when a reopened completed task advances from review straight back to completion, and at `complete`, a current docs review: owned by the task, covering it through `coveredTaskIds`, or the closing record's, and complete, strong, independent rather than continued, covering all five dimensions, fresh, bound to the task's current commitments, with every docs finding validated and disposed, none pending closure, and no docs repair after it. Spec and lore tasks have no docs gate. For a purely mechanical change, `advance` from documentation can instead carry nonempty `docsExemption` text; the runtime binds it to the project inventory at that moment, it counts only while that content is unchanged, and reopening, repair, a new review import on the task or a changed requirements revision clears it. It is refused with `invalid-exemption` on other task kinds and on runs without the docs gate. A standalone docs context records the same exemption when its `advance` carries `docsExemption` and it holds no docs assessment; `advance` and `complete` accept it in place of the docs assessment only while it is current, it never stands in for imported code assurance, findings or checks, and other standalone kinds refuse it with `invalid-exemption`. Status shows `docsReviewCurrent` for each gated task still ahead, and `docsExemptions` lists every recorded exemption with its task, reason, revision and whether it is `current`. Each gate counts only the findings and repairs of its own kind, so a docs repair needs a docs reassessment and reaches the code gate only through the files it changed. Leaving the review stage after a docs review needs that review current and resolved, and task completion without one fails with `docs-review-required`; at `complete` the refusal names the tasks that lack one.

Documentation paths, the edits a docs review alone covers, are the backlog paths `.nightshift/FEATURES.md`, `.nightshift/BUGS.md`, `.nightshift/QUICK_WINS.md`, `.nightshift/PATTERNS.md`, `.nightshift/FEATURES_HISTORY.md`, `.nightshift/BUGS_HISTORY.md`, `.nightshift/QUICK_WINS_HISTORY.md` and files under `.nightshift/features/`, `.nightshift/bugs/` and `.nightshift/patterns/`, plus files under `.nightshift/reports/` and Markdown files at the project root other than the host instruction files `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md` and `CLAUDE.local.md`, matched case-insensitively. Governing specs under `.nightshift/specs/`, skills, the operating brief, the runtime references, templates, Markdown below the project root and every other file are not documentation paths. The runtime judges by path alone, so a documentation path that holds operating instructions still needs the code assessment the operating brief requires, which the runtime does not enforce. On a delivery run created with the docs gate, every comparison of a task's code assessment with current inputs, at import and afterwards, ignores documentation paths, whatever the task's kind: they never make it stale, never refuse `advance` with `review-required` or `complete` with `stale-review`, never name a fresh code target and never make its import historical, so a continued reviewer's closures are still recorded. The task's governing spec and any governing artifact named in the assessment's recorded commitments stay inputs wherever they live. The only exception is `triage`'s test of whether a task assessment is fresh against the whole inventory, which keeps comparing every path. Status lists the ignored paths of each such entry as `documentationPaths`, sorted and only when nonempty, never also in `changedPaths`. Code and docs tasks still need their docs review before they complete; a lore task's documentation-path edits are independently reviewed only by the closing docs review, after triage. On runs without the docs gate and in review contexts, a code assessment of a code, docs or lore task that is stale only because documentation paths changed, appeared or disappeared counts as current when a current docs review covers the task, as before: for code and docs tasks their own, a covering or the closing docs review, and for lore tasks only the closing docs review. Spec assessments never gain either rule; they compare their declared deciding inputs, and a changed governing artifact needs the spec reviewer's applicability call or a fresh whole-spec assessment. Checks are unaffected: a check whose inputs changed is rerun.

On a gated run, `triage` starts the closing record, whose baseline is the project inventory at that moment (an empty inventory gives an empty baseline, and outside Git the baseline is the documentation files on disk); recording triage again replaces the record, and anything that clears closing evidence clears it. Its findings not yet settled or still pending closure survive either replacement: status lists them as `closing.carriedFindings` until the next triage moves them into the new record, where each must still be validated, disposed and, once repaired, closed before completion. The baseline outlives its record: a later triage keeps the run's earlier baseline while the changes since it lack independent review, meaning no current resolved closing review covers them and no complete cumulative code or docs assessment of a task is fresh against the whole inventory, so recording triage again never absorbs unreviewed tracking edits. Only a run whose changes since its earlier baseline were reviewed, or which captured none, records a new baseline at that triage. Task operations address the record with `taskId: "#closing"`: `dispatch` of a `docs` or `skeptic` assessment, `probe`, `check`, `review`, `validate`, `dialogue`, `dispose` and `repair`; other operations are refused with `invalid-closing-action`, and a run without a record refuses them with `closing-review-unavailable`. They are admitted on a running run once triage evidence exists and on a complete run as owner bookkeeping without an engineering claim, and refused on a stopped run until it is resumed. Recorded limits still bind them. A closing dispatch covers every code, docs and lore task. Its `review` import is refused with `closing-scope` when the baseline could not be captured, when the assessed difference from the baseline cannot be established or its selected-only provenance is malformed, and, on a complete run only, when a path changed since the baseline, apart from the dispatch's `excludedPaths`, is not a documentation path; on a running run it imports whatever else changed. Recording the review, its findings, their repairs and its checks never reopens a task or clears closing evidence. `complete` refuses with `closing-review-unresolved` while the latest closing review is not a complete strong docs assessment covering all five dimensions, a closing finding is unsettled, a closing repair postdates the latest closing review or a closing check fails. It also refuses with `closing-review-required` while documentation changed since the baseline lacks a current, complete and resolved closing review, including in a run whose task gates do not depend on it, such as one with only unassessed lore tasks. On every run that is not complete, a stopped one included, the paths changed since the baseline that are not documentation paths, recomputed at each reading and never stored, form the outside-documentation set, and while it is nonempty and unsettled `complete` refuses `closing-review-required` naming the paths. It is settled by a complete, fresh code assessment of any of the run's tasks whose applicability on current inputs reads `applicable` and whose inventory scope positively held every path in the set (its snapshot lists the path, or the path is absent now and the assessment selected it or Git neither ignores it nor leaves it to a runtime-owned folder; an excluded or unreadable path is unseen), or, in a run with no task that can carry a code assessment, by a spec task's fresh whole-spec assessment when every path in the set is that task's governing spec or a commitment-named governing artifact; a relevance decision and the closing review do not settle it, and reverting the paths does. Docs assessments still compare every path, so such a change also needs a closing docs review covering every task, current on the final inputs, which satisfies each task's docs gate too. Status reports the hold as `closing.docsReview.outsideDocumentation: {changedPaths, next}`, or as `closing.outsideDocumentation` in the same shape when a reset left no closing record but the carried baseline the hold is still judged against, present only while it is unsettled, with `changedPaths` null when the set cannot be computed, because the baseline is missing or a Git-inventory comparison fails, and `next` naming the `no-baseline` recovery then; otherwise `next` names a fresh code assessment on any non-spec task, listing first those whose assessment would also cover the run's other stale code gates, then the closing docs review, says that reverting settles it, and names the user's decision (`hold`, `stop` or the administrative close) only when no task assessment can settle it. `satisfied` reads false while it is unsettled; with freshness verification skipped both read `'reconcile at acceptance'`. A re-recorded `triage` keeps the earlier baseline while the hold is unsettled or cannot be computed, whichever branch would otherwise re-baseline, and a missing earlier baseline still gives way to the inventory. A project outside Git, whose baseline holds documentation only, does not evaluate the hold. A missing or unreadable baseline fails closed. Recording triage again recovers a missing baseline, which gives way to the inventory at that triage; an earlier baseline whose comparison fails, as with a Git failure, stands until the comparison can be made, and one whose stored evidence is itself unusable needs the user's decision, `hold`, `stop` or the administrative close. When Git cannot inventory the project, only a project positively outside Git gets a baseline, read from its documentation files on disk: no `GIT_DIR` or `GIT_WORK_TREE` redirects discovery, no `.git` entry of any kind lies in the project or an ancestor Git would search, and Git refuses with its no-repository wording. A Git failure, an unusable `GIT_DIR` or a broken `.git` entry never counts as outside. No review can be dispatched outside Git, so there any documentation change after triage refuses completion: revert the tracking edits, or make them in a Git worktree where a closing docs review can cover them. For the same reason a docs task cannot complete outside Git, since it can neither be reviewed nor record an exemption, which needs a Git inventory. Status shows the record under `closing.docsReview`, with `satisfied` telling whether completion's closing coverage holds. On a complete run the record gates no task or completion, although closing work recorded on it after completion holds replacement back as Start and observe describes; a finding whose repair lies outside the documentation paths is deferred with a durable route, and a required one cannot be deferred, so it leaves the record unresolved. An unresolved record is not review coverage of the tracking edits for publication.

## Staffing and follow-ups

`worker` registers `worker: {id, session, assignment, role, writes, host?, model?, effort?, lead?}`. Roles are `implementer`, `reviewer`, `skeptic`, `peer` or `supervisor`. Optional `host` is exactly `claude` or `codex`; omission stores the registering controller's host, while null and other values are rejected. The stored host belongs to that assignment and is preserved through completion and adoption. An absent historical host is unknown for native-event recovery, not a current-host default. Writes are exclusive project-relative paths; directory ownership includes descendants. On Windows one file can have several spellings, so write ownership admits only ordinary ones: a segment ending in a dot or space, a colon anywhere (NTFS stream syntax and drive-relative forms), a reserved device name such as `NUL` or `COM1` with or without an extension, and an existing component spelled other than as the filesystem names it apart from case, such as an 8.3 short name, are refused with `unsafe-path`; a missing component ends that comparison, so a later entry whose short name matches an earlier reservation is not detected. A stored reservation using a refused spelling makes ownership checks fail closed with `writer-state-unavailable` until it is reconciled, while registration without writes stays available. Review staff and supervisors have an empty write list. A peer names its registered reviewer `lead` and matches the lead's model/effort. `worker-finished` names `workerId`, a `status` of `complete`, `failed` or `stopped`, and underlying `evidence`; merely registering a worker does not dispatch it. Verify actual process or registered native-assignment completion before releasing its ownership. Reconciling a review or skeptic worker records how its process ended, not an assessment: only a dispatch that produced a receipt can be resumed, replaced or named as a resume target, and a receipt that cannot be read counts as none. Runtime artifacts are written through a temporary file and a rename, so a failed write leaves none behind. The controller retains all consequential transitions.

`wait` is read-only, like `status`, and needs no actor or revision. `{action: 'wait', workerId, runId?, timeoutMs?}` observes the saved worker until its status leaves `starting` or `running`, its recorded runner process no longer exists, the run stops, completes or is closed (a complete run still admits closing-record work, so a `#closing` worker is observed until its own result; a stopped or closed run gives reason `run-stopped`), the run deadline passes, or `timeoutMs` elapses (default five minutes). It resolves the run once, so a later run cannot change what is observed. The result carries `runId`, `revision`, `runStatus`, `workerId`, `workerStatus`, `active`, `runnerAlive` (null when the runner was not probed: no runner process is recorded, or the worker had already left `starting` and `running`), the project-relative `receipt` path for `review` or `validate` when the dispatch wrote one, the saved failure `evidence`, `elapsedMs` and a `reason` of `worker-result`, `runner-missing`, `timeout`, `deadline` or `run-stopped`. Dispatch worker ids come from `inspect`, which lists every saved worker; `status` lists active ones only. A result with `active: true` needs reconciliation before the worker is released: `runner-missing` and `unverified` mean the process outcome is unknown, so verify it and record `worker-finished`. `worker-result` with status `complete` means the dispatch process ended; receipt import still performs the assessment's own checks. Keep `timeoutMs` below the host's tool-call limit and call `wait` again on `timeout`; repeated waits record no progress and neither consume nor reset the Stop hook's reminder budget, because the turn never ends.

`followup` records `item: {id, context, recommendation, ...}`. Preserve the concrete proposal and original decision terms in additional fields. Pending follow-ups survive engineering completion. `resolve-followup` records `followupId`, the actual `decision`, its user `authority`, and any durable `route`. Do not write inferred user answers. The session retrospective prepares worthwhile instruction proposals for independent review and user approval; triage follows it.

## Continuation hooks

Registered hooks restore obligations through the exact current execution binding. Bundled notices do not mutate delivery. A functioning Stop hook protects accepted running delivery while work, required closing or worker reconciliation is actionable, including when its primary continuation observation failed. Standalone revision has no Stop continuation pressure. Explicit holds/stops, exhausted limits and waiting solely on user decisions without active or uncertain workers end eligibility. Unavailable hooks provide no protection and do not themselves revoke otherwise valid runtime admission.

For a handed-over run with a recorded report, whether running, stopped or complete, SessionStart in the current owning session carries a morning-report notice while the report is undelivered or any follow-up is pending: an instruction fitting the state (rewrite and record a missing or changed report, present an undelivered one, or after delivery continue triage through the host's question tool if the user has asked for it and otherwise ask whether they are ready), then `recorded`, `delivered`, `path`, `current` (false when the saved file is missing or changed) and pending follow-up ids. Adoption routes this notice to the new owner. A complete or stopped run restores nothing else. Stop never resists yield for unrecorded delivery or pending follow-ups on a complete or stopped run, because both need a user who may be absent. A record with status `closed` gets no notice, since its close recorded the user's report and follow-up decisions, and the hooks write nothing to it.

After three consecutive reminders without meaningful progress, Stop permits no further automatic continuation and reports incomplete recovery. Concurrency revisions record writes, while the central store derives a progress token and cumulative immutable achievement frontier from admitted semantic transitions and recorded proof. Claims, continuation observations, handover retries, worker activity, generated identities and repeated equivalent proof do not replenish reminders. Removal and restoration of already credited evidence preserve the frontier. Genuine execution authority, lifecycle progress and new engineering or assurance achievements permit a fresh sequence. `stop_hook_active` alone does not imply failure. Reconcile the cause before continuation-dependent resumption. Unrelated and former owner sessions are not controlled. Use native host interruption to stop active execution and record an explicit stop for that user intent; Claude does not expose an Interrupt hook event. A native persistent goal, where the host requires one, must refer to verified run completion rather than a model's claim. Verify actual installed hook/goal behavior and trust at reconciliation boundaries; neither configuration nor a saved `verified` flag proves itself.

Delivery accounting uses a schema-2 `progress` marker bound to the run, stored state and safe concurrency revision. Its token and frontier artifact are SHA-256 identities. `reminderHash` independently binds canonical `{schema: 1, runId, reminder}` to the exact positive reminder or explicit attested null; matching missing fields in state and history are not a zero attestation. The schema-2 frontier retains cumulative achievement credits and a `closingBasis` subset for material commitments, qualifying engineering proofs and task completion. Each set is bounded by 65,536 entries and the entire artifact by 8 MiB. Losing proof or reopening work cannot shrink that basis. Internal reminder issuance rechecks owner, revision, eligibility and accounting under the project transaction; schema-2 `stopRecovery` binds the issued count from one through three to that run and progress token. Callers cannot supply the count or token. Read-only status, history, wait and acknowledgement checkpoint operations consume no reminder. Standalone review contexts have no delivery accounting or Stop pressure.

Admitted closing operations retain internal `{schema: 1, runId, contextHash}` bindings. Retrospective captures the context established by the cumulative closing basis; report, recipient-confirmed delivery, triage and their closing review record inherit that cycle. Collected closing evidence, findings and repair closure preserve their original bindings when carried or restored. Existing prose or evidence is never rebound merely because current task/proof availability changes. Resetting current closing slots preserves cumulative credits and basis. Unknown provenance cannot earn a new credit, while valid stopped/blocked partial-delivery closing remains supported.

Missing, stale or malformed accounting is reconciled from complete creation provenance or a trustworthy schema-2 checkpoint within 256 revisions and 16 MiB. Legacy positive reminder anchors are lower bounds, not complete frontiers or proof of unused allowance. Historical reminder resets without semantic progress accumulate conservatively. Incomplete provenance, unreadable required artifacts, exhausted bounds or unsafe revisions cannot grant a new allowance. Stop returns an explicit unavailable-accounting diagnosis; independently admitted work and explicit hold/stop remain subject to their existing permissions. The next authorized transaction persists successful reconciliation without crediting recovery itself. Artifact encoding preserves validated existing references, and accounting, reminders, artifacts, derived bindings, state and history commit atomically. Existing retained releases continue using their own code; this mechanism performs no migration or runtime substitution.

Replay validates each recorded substantive-state hash before interpreting achievements. A damaged row does not become trustworthy because current state contains the same damage. Closing transitions also validate capture and inheritance against the established cycle, preserving legitimate older evidence and carried findings without accepting a newly substituted context hash as a discharge. Unknown or contradictory provenance remains unavailable; complete metadata-only recovery still preserves spent pressure.

Delivery central saves also commit independent schema-1 provenance through `accounting_commits`, keyed by run and safe revision, referencing content-addressed records outside replaceable state JSON. Each record binds the encoded state, original closing admission map, new discharge identities and exact progress/reminder checkpoint. Transaction-private discharge capabilities are registered only by admitted lifecycle or collected-evidence writers, expire on commit or rollback and cannot be supplied by request JSON. Scalar and nested closing evidence retain original context and parent admissions through carry and restoration; direct save cannot infer a new discharge from a diff. Indexed `discharge_index` references retain immutable admissions for restoration. Each provenance artifact is bounded by 8 MiB and 65,536 references/admissions. There is no independent eviction. All provenance, artifacts, state, history and accounting writes share the existing transaction.

Closing asynchronous checks and review workers pin `progressOrigin`, the lowercase SHA-256 identity of their originating closing-record admission, and the original schema-1 `progressBinding`. Unknown origin is null, never a new admission. They also pin `closingOccurrence`, the identity each closing record mints when triage creates it, independent of accounting: collection and import compare it, so unavailable accounting does not prevent collecting a result on the unchanged record, while a replaced record, including one under the same context, is refused with `closing-origin-changed`. A record created before this identity existed keeps its accounting-origin comparison. Reservations grant no credit. Collection/import verifies the original record and binding, including replacement under an otherwise identical context; failed or pending checks grant none. Receipt replay excludes internal provenance fields from the comparison with externally attributed receipt content. Standalone contexts acquire no delivery accounting. A missing revision in an established independent provenance sequence cannot silently downgrade that run to legacy trust. Independent provenance ships with schema-2 accounting, so only a record saved by an earlier release, without schema-2 accounting, is legacy. A schema-2 record without independent provenance rows, or a run whose discharge index survives without them, has lost them: its accounting is unavailable whatever its checkpoint shows, so no pressure is granted and later saves stay unavailable. Missing or contradictory distinguishing evidence stays unavailable.

Metadata-only loss can recover the exact independent checkpoint and spent reminders. A substituted substantive state fails its independent digest even when both current and history JSON match and their progress metadata is absent. Bounded reconstruction counts independent records and referenced artifacts within the existing recovery budget. Unavailable provenance remains unavailable through no-op saves; independently valid work and explicit hold/stop retain their original authority. Failed transactions discard all provisional discharge and provenance writes.

Ordinary reminder issuance uses a module-private, transaction-bound, single-use capability. Central save verifies its store, candidate and committed predecessor, and proves that only revision, updated time and owned accounting metadata differ. It preserves encoded evidence references, established token/frontier and original discharge bindings, records no new admissions, and atomically writes the new reminder and revision attestations. It does not encode/hydrate assurance bodies or rerun semantic projection. Compact verification still checks independent provenance and original admission ancestry; metadata-only recovery restores spent pressure. Unknown fields changed by an eligibility callback or after admission, stale/cross-store/replayed capabilities and forged internal flags fail. A history operation name alone selects no shortcut. Every other save retains ordinary encoding and semantic/admission validation. Standalone contexts remain pressure-free.

Reviewed project inventory currently requires regular, singly linked files. Symlinks, hardlinks, gitlinks and other special entries produce a path-specific prerequisite diagnosis. Reconcile these explicitly before handover; do not silently omit changed entries from coverage. Native Windows .exe host installations are required; command-shim-only installations are not yet supported.

Each dispatched assessment binds the accepted commitments and requirements revision of every covered task. Import time is separate history metadata. An approved commitment change while an assessment is running leaves its result bound to the earlier commitments even when source bytes remain unchanged. Preserve and import it as evidence, then establish applicability to the amended commitments independently; import time cannot refresh it.

Check names identify verification obligations within a task. A later invocation with the same name supersedes its earlier invocation, even if the earlier command finishes last. Each pending check stores its operation id as `attemptId`; completion replaces that attempt's reserved result in place. Every latest named check must pass on current inputs at task and run acceptance, regardless of task kind or whether an independent assessment was needed. Status lists those that do not under `staleChecks`, one `{taskId, name, reason}` for each latest named check of any task, completed ones included, and of the closing record (`taskId: "#closing"`), with `reason` `inputs-changed` for a passing check whose inputs changed, including an input that can no longer be read as a regular file, such as one replaced by a directory or a link, `failed` for a failing one and `pending` for a reserved run that never collected a result; the hook's continuation brief, which verifies no freshness, carries `'reconcile at acceptance'` in its place. A new failed check cannot be masked by an unrelated pass, and an earlier pass cannot mask a failed rerun. Keep the name when retrying or updating the verification of the same obligation. Code tasks require at least one check. Spec, docs and lore tasks can have none when no executable check applies; once registered, their checks remain acceptance obligations.

Probe copies have their own initially empty Git repository. A probe's working directory is the copy's root, which holds the project files at their project-relative paths, with no `project/` or `context/` folder as in the reviewer's copy, and each fixture file replaces the project file of the same path; every reviewer prompt states this layout. Ordinary local Git commands resolve to that copy. History-dependent probes need a deliberately prepared Git fixture; they must not borrow the controller checkout through parent-directory discovery. The runtime explicitly selects development mode for private probe execution and records it in the result, keeping the controller's operation context and worker binding out of the private process. Older probe results without `resourceMode` inherited the caller environment; absence does not prove isolation. This boundary does not sandbox explicit absolute paths or hostile Git environment overrides.

The Windows transport keeps child input writes and output pumping independently progressable, preserves ordered input acknowledgements, and accepts termination while a write is pending. A requested termination, including a timeout, gives the job runner 30 seconds to end the job and report it empty, enough for a runner that is still starting on a loaded machine; a runner that cannot is ended, which still ends every process in its job, but the result is reported as unverified termination. Pending input is bounded at 32 MiB; exceeding that bound fails the dispatch rather than silently dropping input. A host that cannot start fails with an error naming the executable and the launch stage that failed (`command`, `setup`, `create-process`, `job-assignment` or `resume`), plus the Windows error code and message when Windows refused to create the process; when termination of a partially started process is unproven, the error names the executable and that condition instead of a stage. Reviewer attempts on either host record it as the attempt's error, and checks and probes as their operation worker's failure evidence.


### Finding scope

A lead finding carries `surfaces`, each place the alleged problem exists as `{path, location, evidence}`, and `basis`, the project-relative paths of other files the claim reasons from; a spec review's basis names only deciding inputs. Both are required lists and may be empty. An entry is malformed unless it is an object with a nonempty string `path`, a string `location` and nonempty string `evidence`; a malformed entry or a `basis` that is not a list of nonempty strings refuses the report with `invalid-finding`, and the same applies to surfaces or basis supplied for a claim with no recorded finding. A surface is identified by its path and trimmed location, and entries sharing an identity are consolidated with their evidence joined. A skeptic's verdict carries `surfaces`, one `{path, location, verdict, evidence}` per assigned surface, where the verdict judges whether the alleged problem exists at that surface; basis files receive none. A report that omits, repeats or adds a surface is refused with `missing-validation`, and importing a verdict needs an answer for exactly the recorded surfaces, an empty list when there are none, however the skeptic was assigned. The finding verdict follows: `unverified` when any surface is, `confirmed` when one is confirmed and none unverified, `refuted` when all are, and any other combination is `invalid-verdict`. A surface refuted on a confirmed finding stays named in status (`surfaceVerdicts` on a listed finding, `closing.docsReview.surfaceVerdicts` and `closing.carriedSurfaceVerdicts`) and in the closure turn, where confirmed surfaces are listed and a repair is owed only for them; a closure stays one answer per finding, so the later fresh assessment stands behind it.

Scope is resolved once at review import and recorded with the finding: its surfaces and basis paths, when it has surfaces and every path is in the raising review's context snapshot, plus the governing specs that review's commitments name. A finding raised by a spec review is instead scoped to that review's deciding inputs, whatever its surfaces and basis name. Any other finding with no surfaces or with an unresolved path has no scope, and so does any finding recorded before scope existed. A saved finding with malformed surfaces or basis or a malformed saved scope has no scope either, and so does one, other than a spec-raised finding, whose saved scope lacks a path it names. Every comparison of a skeptic or dialogue receipt's currency compares only the concerned findings' scope, with identities from the receipt's context snapshot, at the end of its dispatch, on import, and at `validate`, `dialogue` and `dispose`; an operation over several findings compares their union. Without a scope, or for a path absent from that snapshot, a receipt keeps its kind's comparison: the whole inventory, or the deciding inputs for a spec-kind dialogue. A receipt carrying a snapshot that fails its integrity check is refused, whatever its kind, with null paths. A refusal names the changed paths. A probe request's currency follows its own declared files instead. Scope bounds what an edit can invalidate and does not certify that the skeptic relied on nothing else; cumulative assessment and the final gate remain the assurance over the whole change.

Every refusal from the review and docs gates states each failing task with its cause: changed inputs with their paths, changed commitments, a comparison that could not be established, a named failing or missing check, or unmet assurance for any other gate failure. A delivery's `complete` refuses a review-gate failure with `verification-required` when every failing task fails only because of a check, and with `stale-review` otherwise. `advance` and a review context's `complete` keep `review-required`, and docs-gate refusals keep `docs-review-required`. Wherever a task or closing record is refused because a check is failing, pending, stale or missing, whichever gate reached it, the refusal names that record and the check; a closing record's refusal separates its check cause from its other causes.

Skeptic and finding-dialogue receipts retain their current-commitment requirement as well as input currency within that scope. `validate` and `dialogue` preserve a compact `commitmentBinding`: `taskIds` names the receipt's bound tasks and `digest` is the canonical fingerprint of their accepted agreements and requirements revisions; an empty task set is allowed only for a closing record with no covered tasks. Disposition and repair recheck that binding so a later material amendment cannot reuse old validation as current authority. Legacy records use their registered dispatch commitment data where available; without either binding or dispatch evidence, any recorded material requirement revision leaves the validation unavailable for current disposition. Previously settled dispositions stay historical; they do not supply assurance for changed requirements, which still require applicable current review. Missing bindings never establish approval of amended commitments.

## Assessment applicability

For this bounded release, spec assurance binds its governing artifacts and explicitly selected deciding inputs in `artifactPaths`, plus accepted commitments, at task and final acceptance alike. The full private `contextSnapshot` remains available for orientation, integrity checking and probes; unrelated implementation or closing edits do not reopen spec assurance. Include every deciding context file in the declared artifact set. Dispatch refuses a declared scope missing the task's configured governing artifact; an older assessment with that omission remains evidence but supplies no current spec assurance. The spec reviewer is told that set and must return incomplete, naming additional paths in summary, if its decision needs undeclared inputs. This model-owned scope-completeness reporting is provisional on Claude Code and Codex; no installed-host probe has exercised it. Broader spec-context policy is deferred. Docs assessments continue to bind their recorded project context, and code assessments do too except for documentation paths on a run with the docs gate, as Documentation review describes.

**Field evaluation: assessment-applicability.** When this behavior is encountered in actual work, follow [the temporary evaluation index](../field-evaluations.md#assessment-applicability) and report observations to Nightshift's maintainer inbox. Capture the exercised relevance outcome, coverage/status usefulness, unnecessary reassessment and any lost finding, closure or check obligation; distinguish an applicable but unexercised path. Preserve attribution and evidence. Reporting itself authorizes no extra execution or budget. Remove this paragraph only through the indexed retirement decision.

Within one synchronous status evaluation, repeated inventory comparisons share results; the comparison cache is discarded at return, never persisted or reused by a later operation. Status includes `assessmentApplicability` for the latest lead and docs assessments covering every task, completed tasks included. Each entry names `taskId`, `completed`, assessment `requestId` and `kind`, changed project-relative `changedPaths`, `commitmentsChanged`, `status`, `current` and the next useful action. No input or commitment difference is `applicable`; an independently preserved later candidate is `applicable-by-decision`; on a docs-gated delivery run a code assessment whose only changes are documentation paths is `applicable` with those paths under `documentationPaths`; and on runs without the docs gate and in review contexts, qualifying documentation-only coverage is `applicable-by-docs-review`. Differences without a decision are `pending`; reviewer answers can be `reassess` or `unresolved`. An entry's `next` names the originating reviewer's applicability call first, with a fresh cumulative assessment as the fallback, exactly when the `applicabilityCall` that `freshTargets` defines would be non-null for it, and otherwise the fresh assessment first, or reconciliation for an unestablished comparison. A failed comparison, including the evidence of an associated per-task relevance decision, is `structural-failure` with unknown paths, never clean. Corrupt decision evidence cannot be silently filtered into ordinary pending coverage or hidden by original-input reversion or a later current decision. Lightweight hook status uses `unevaluated`. Inspection writes no state. These fields describe applicability only; passing assessment quality, dimensions, findings, closures and checks remain separate gate conditions. Where it still applies, documentation-only relief can settle an ordinary pending input-change condition, but never a structural failure, conflicting record or independent reassess/unresolved answer. It remains subject to commitment conditions and never treats a configured governing artifact as ordinary prose: changed governing requirements need independent code applicability or reassessment even when stored at a documentation path. Normal dispatches always include the configured governing artifacts of covered tasks, including ignored ones. Closing contexts and Git triage baselines include the configured governing artifacts of all run tasks so unchanged ignored requirements do not appear as new tracking changes. Code/docs assurance cannot count an assessment whose scope omitted its own governing artifact.

At a consequential acceptance boundary, dispatch the original kind with `review.relevance: {requestId, taskIds}` and `review.resume` naming the latest dispatch in its originating lineage, or `review.replaces` for independent replacement. `requestId` identifies an imported original assessment on the target; `taskIds` is a nonempty unique subset of the tasks that assessment covered. The runtime derives all other relevance fields, retains the original scope inclusions and exclusions, captures exact current inputs and commitments, and supplies the original assessment, source inputs and intervening changed paths. It never narrows scope to the named findings or changes. Read `original/`, `context/original-assessment.json` and the current `project/` under the assignment workspace. Missing retained source permits an unresolved or reassessment answer but cannot preserve applicability. Cached and legacy original-source materialization create their destination exclusively. A collision or copy failure records source unavailability; cleanup removes a partial destination only when this attempt created it and its directory identity still matches. Existing or replacement destinations are preserved by materialization. Shared cached source is resolved from its manifest binding without requiring the original worker registration; a legacy per-dispatch source with missing or unsafe registration is unavailable. Continuation still requires a valid registered dispatch in the originating lineage, so loss of source metadata never supplies reviewer identity or continuation authority. Actual model-owned relevance behavior remains provisional on Claude Code and Codex until separately verified on each installed host.

Relevance task bindings use the same nonempty unique task-id grammar at dispatch, source resolution and report import. Malformed bindings receive a coded `invalid-relevance` refusal at those boundaries or a structural diagnosis during applicability inspection; finding and historical scans never dereference an unchecked binding. When a noncurrent spec has missing declared deciding inputs, status adds `missingPaths` using the same sorted project-relative path grammar as `changedPaths`, only when nonempty. The field is recomputed, never persisted, and disappears when those inputs are restored. The next action directs restoration or agreement reconciliation and fresh assessment with a revised scope; existing negative applicability obligations remain. A relevance request with those missing inputs refuses `missing-spec` before registering a worker. Fresh spec capture retains its existing requirement that every declared input exists. Its missing-spec refusal names the actual missing declared paths, including additional deciding inputs, rather than blaming only the governing artifact. The relevance report fills `applicability`, exactly one `{id, outcome, evidence}` per assigned task, with `id` bound to its task id, `outcome` one of `preserve`, `reassess` or `unresolved`, and nonempty `evidence` explaining the independent decision. It leaves `coverage`, `closures` and `positions` empty and uses the ordinary new-finding and probe fields. A preserving answer requires a complete result and available original inputs. Import with the ordinary `review` operation. The receipt is stored separately beside assessments with its `relevance` binding, original assessment hash and actual current snapshots and commitments; it never becomes a fresh assessment or a closure. New findings follow skeptical validation and disposition. Unanswered siblings remain pending. Later edits are compared again; a prior decision does not cover new bytes at the same paths. A later decision for the same candidate supersedes the earlier answer while preserving history. Historical retained-assessment coverage uses the same strict selector as live applicability and preserved closing snapshots; duplicate identities or ambiguous order cannot supply retained coverage. Selection requires a unique successor in recorded dispatch order, or recorded legacy revision order when dispatch history is incomplete; ambiguous ordering reports `conflicting-decisions` and grants no coverage. An earlier reassess or unresolved answer remains a coverage obligation after later edits until a later independent preserving decision settles it or a fresh assessment establishes a new basis; input drift alone does not restore documentation relief. A subsequent edit after a preserving decision returns to ordinary comparison and does not revive the settled negative obligation or inherit approval for new bytes. A current independent preserving decision can settle the current candidate, and a new fresh assessment establishes a new assurance basis. Reversion restores original coverage only when context and commitments match too.
